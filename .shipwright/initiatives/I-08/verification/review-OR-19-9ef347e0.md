## Findings

### Major M1: assembly does not go through `plan_roster_caches`/`install_roster_caches`, contrary to the ledger entry's own requirement, duplicating cache-construction logic and leaving a schema-metadata inconsistency unfixed

`crates/hares-core/src/dwelling/mod.rs:2737-2833` (`build_from_blueprint_inner`, assembly) builds the output schema, column index, equipment/end-use/actor column maps, zone caches and the fluid-loop map with its own inline code, independent of `plan_roster_caches`/`install_roster_caches`. The OR-19 ledger entry (`03-output-reporting.md`, "Change" item 2) states: "`refresh_equipment_caches` is deleted; assembly calls plan and install." `refresh_equipment_caches` is indeed deleted, but assembly was not converted to call the new plan/install pair; it kept its pre-existing, independent construction path. Confirmed by grepping the whole file for `plan_roster_caches`/`install_roster_caches`/`enrich_schema_with_telemetry_units`: the only entrances that call plan/install are `add_actor`, `auto_register_actors`, `add_equipment`, `clear_equipment`, `remove_equipment`, `remove_equipment_by_end_use` and `replace_equipment` (mod.rs:3485, 3602, 3840, 4071, 4110, 4162, 4241) — assembly is not among them.

This duplication has a concrete, reachable consequence. Assembly enriches the schema with telemetry-unit metadata after building it (`mod.rs:2767`: `let schema = enrich_schema_with_telemetry_units(schema, &equipment);`), but `plan_roster_caches`'s `FreshSchema` branch (`mod.rs:4397-4560`, specifically the schema-building block around `mod.rs:4451-4467`) builds the schema with `build_schema` + `extend_schema_with_actor_columns` and never calls `enrich_schema_with_telemetry_units`. A whole-file grep for `enrich_schema_with_telemetry_units` shows exactly three call sites: assembly (`mod.rs:2767`) and two pre-existing unit tests (`mod.rs:17608`, `17646` in the post-edit file); none inside `plan_roster_caches` or `install_roster_caches`.

This is a pre-existing defect (confirmed against `7b7a6a7d`'s now-deleted `refresh_equipment_caches`, which also never called `enrich_schema_with_telemetry_units` — `git show 7b7a6a7d:crates/hares-core/src/dwelling/mod.rs | grep -n enrich_schema_with_telemetry_units` shows only the assembly call and the two test call sites), so 9ef347e0 did not introduce it. But the entry this commit implements is explicitly the one the ledger designed to unify the two paths ("assembly calls plan and install"), and the commit did not do that, so the defect survives unfixed through the exact commit whose stated purpose was to remove this class of path duplication. Every piece of equipment a Python caller adds after construction — `add_battery`, `add_pv`, `add_ev`, `add_protocol_bridge` (`crates/hares-python/src/py_dwelling.rs:1165,1211,1233,1320`), all of which call `dwelling.add_equipment(eq)` before the first step — gets a schema whose columns are missing the `"unit_source": "telemetry_field"` metadata that assembled equipment's columns carry. Downstream consumers of that metadata (the `04-fleet.md`/`OR-1` catalogue work explicitly spells out that today's schema metadata is read by unit-keyed rules) see different, order-dependent schema metadata for equipment that is otherwise identical in every other respect.

Required change: factor `plan_roster_caches`'s cache-construction logic (or at minimum its `FreshSchema`/pre-step branches) into a form assembly can call too — either by restructuring assembly to build a minimal `Dwelling` first and then call `plan_roster_caches`/`install_roster_caches` on it (the literal ledger instruction), or by extracting a shared free function parameterized over the handful of inputs `plan_roster_caches` currently reads from `&self` (write_output, current row count, `latest_env`, zone types, thermal solver's indoor zone id, output verbosity, current pre-step port tables) that both assembly and `plan_roster_caches` call. Either way, `enrich_schema_with_telemetry_units` must run on exactly one path so assembled and runtime-added equipment get identical schema metadata, and the ~100 lines of schema/column-map construction duplicated between `build_from_blueprint_inner` and `plan_roster_caches`'s `FreshSchema` branch should not exist twice.

### Minor m1: `std::mem::take` leaves `self.equipment`/`self.actors` fully empty across the `plan_roster_caches` call; a panic there (not an `Err`) is worse-than-before, and Python entrances are not panic-guarded

Every entrance (`add_equipment` mod.rs:3830-3862, `replace_equipment` mod.rs:4232-4280, `remove_equipment` mod.rs:4102-4145, `remove_equipment_by_end_use` mod.rs:4142-4192, `clear_equipment` mod.rs:4059-4082, `add_actor` mod.rs:3477-3499, `auto_register_actors` mod.rs:3570-3614) does `let mut roster = std::mem::take(&mut self.equipment /* or self.actors */);` before calling `self.plan_roster_caches(...)`, and only assigns `roster` back to `self` inside the `Ok`/`Err` match arms. If `plan_roster_caches` (or anything it calls: `build_schema`, `build_equipment_column_map`, `build_zone_column_caches`, etc.) were to panic instead of returning `Err`, the match is never reached, `roster` is dropped on unwind, and `self.equipment` (or `self.actors`) is left as the empty vector `mem::take` substituted — strictly worse than the pre-commit behavior, where the mutation happened in place and a mid-refresh panic left the vector merely one item larger than before (recoverable in principle), not emptied.

`crates/hares-python/src/py_dwelling.rs` wraps only `step_core` and the simulate path in `std::panic::catch_unwind` (`py_dwelling.rs:764, 819`); `add_equipment`, `remove_equipment`, `replace_equipment`, `add_actor` and friends (`py_dwelling.rs:1165-1385` and others) call straight through with no panic guard, so a panic inside `plan_roster_caches` during any of these Python-reachable calls is not isolated at that layer either (PyO3's own panic-to-exception boundary would still fire, but the `Dwelling` object survives in Python with its roster emptied instead of marked failed).

I did not find an `unwrap`/`expect`/direct indexing inside `plan_roster_caches` itself or inside the helper functions it calls that have changed in this commit (`compute_equipment_execution_order`, `compute_equipment_dispatch_targets`, `build_hvac_thermal_consistency`, `build_zone_column_caches`, `build_equipment_column_map`, `build_actor_column_map`, `build_end_use_aggregate_indices` all build via `.iter()/.map()/.collect()` or return `Result`), so this is not currently known to be triggerable with any shipped equipment/actor configuration — hence Minor rather than Blocker. But given the commit's whole purpose is "a rejection leaves the dwelling bit-for-bit as it was," a one-line acknowledgment (a doc comment on `plan_roster_caches` noting the non-panic-safety of the `mem::take` window, or restoring the original vector in a panic path via `scopeguard`/`Drop`-based guard at the two or three entrances most likely to be called from Python) would close this gap rather than leave it implicit.

### Informational: `plan_roster_caches` takes `&[Box<dyn Equipment>]`/`&[Box<dyn Actor>]`, not the ledger's `&[&dyn Equipment]`/`&[&dyn Actor]`

The ledger (`03-output-reporting.md` OR-19 item 1) specifies `plan_roster_caches(&self, equipment: &[&dyn Equipment], actors: &[&dyn Actor]) -> Result<RosterCaches>`. The implementation instead takes `&[Box<dyn Equipment>]`/`&[Box<dyn Actor>]` (`mod.rs:4397-4401`). This is a reasonable deviation, not a defect: every caller already holds an owned `Vec<Box<dyn Equipment>>`/`Vec<Box<dyn Actor>>` (obtained via `std::mem::take(&mut self.equipment)`), so passing `&roster` directly is natural and avoids allocating an intermediate `Vec<&dyn Equipment>` on every entrance call. No change requested; noting it only because the task asked whether the deviation is acceptable.

## Verified correct (no issues found)

- **Plan/mutate/install discipline**: every entrance (`add_equipment`, `replace_equipment`, `remove_equipment`, `remove_equipment_by_end_use`, `clear_equipment`, `add_actor`, `auto_register_actors`) validates its candidate, takes the live roster via `mem::take`, mutates the local candidate roster, plans against it with `plan_roster_caches`, and only on `Ok` assigns the roster back to `self` and calls the infallible `install_roster_caches`. On `Err` every entrance restores the pre-call state exactly (traced by hand for each of the seven entrances; the five new unit tests at `mod.rs:15590-15828`, covering add/replace/actor-add rejection and pre-/post-step fluid-loop behavior, exercise this directly). `install_roster_caches` (`mod.rs:4554` onward) is genuinely infallible: no `?`, no `.unwrap()`/`.expect()` on fallible input, only moves of already-computed values.
- **Restore helpers**: `partition_actors_by_target`/`restore_evicted_actors` and `partition_equipment_by_end_use`/`restore_removed_equipment` (`mod.rs:3193-3254` approx.) tag each evicted/removed item with its original index during a single forward pass and reinsert in increasing-index order on rejection. Traced through a non-contiguous eviction example (indices 1 and 3 out of 5) by hand: sequential `Vec::insert` at ascending original indices reconstructs the original order and positions exactly, because every insert before it has already restored every smaller original index. No off-by-one found.
- **Hares-python callers**: every roster-mutating Python binding (`add_battery`, `add_pv`, `add_ev`, `add_ev_with_driver`, `add_protocol_bridge`, `remove_equipment`, `replace_equipment`, `remove_equipment_by_end_use`, `add_actor`, `add_actor_by_name`) calls straight through to the Rust entrances and therefore the plan/mutate/install path transparently; none bypasses it or duplicates cache construction.
- **Fluid-loop change**: `rebuild_port_slots` (`mod.rs:4277` area) still retains thermal/humidity/custom accumulators monotonically (diff only removes the fluid-retention loop, leaving the other three untouched), and the loop-type map is now derived purely from `hares_types::ports::fluid_loop_declarations` over the live equipment's declarations (`FluidSolver::plan_loop_types`, `hares-envelope/src/fluid_solver.rs:120-131`), not from the port-slot table's retained accumulators. No envelope solver code path was touched by this commit, so no solver can read a fluid accumulator dropped pre-step (nothing has stepped yet at that point).
- **Edited test `runtime_added_equipment_declares_its_loops`** (`crates/hares-core/tests/fluid_loop_declarations.rs:200-227`): the new `None` expectation after removing a loop's only declarer is correct given the new single-source-of-truth design (a loop with no live declarer is undeclared, freeing its fluid type), not a weakening — the test still re-adds the equipment and runs a real `step()` to prove the loop is correctly redeclared and the simulation does not fail it as undeclared.

No logic duplication, no behavior change for existing `FluidSolver` callers.
- **No per-step cost**: nothing in `record_step`, `step`, or `run_timestep` was touched by this diff; `RosterCaches`/`PreStepRosterCaches`/`OutputCachesPlan` are only constructed inside `plan_roster_caches`, called only from the seven roster-mutation entrances, never per step.

# Review 5/6: Schedules, actors, weather, fleet

Read-only deep review, post-I-08, verified against the working tree. The weather pipeline (calendar-date addressing, EnergyPlus interpolation, first-hour rule, leap rules) and the RNG stream architecture (`RngStream`, `dwelling_seed`, event-load tagged streams) are in good shape - the recently-fixed list is genuinely fixed and well-tested. Defects concentrate in schedule anchoring for generated schedules, warmup state carryover, stochastic-state checkpoint/reseed gaps, and one unit-convention divergence from OCHRE.

## CRITICAL

**C1. Generated (no-CSV) schedules are rotated by the run's start day-of-year - wrong month/weekday profile for any mid-year start.**
- `crates/hares-io/src/inputs.rs:1119-1124` / `blueprint.rs:353-357` generate the schedule over `ScheduleGeneration { start: settings.sim_config.start_time, ... }` - row 0 is the run start date. But the environment indexes schedule rows by the calendar ordinal: `crates/hares-core/src/environment.rs:1185-1222` computes `idx = (doy0*86400 + secs_of_day) % (len*step) / step` (row 0 = Jan 1), the contract the CSV path follows (`schedule.rs:159-184`, test `environment_publishes_the_calendar_schedule_row`, `environment.rs:3003-3021`).
- A run starting Jul 1 00:00 reads row 4344 at step 0 - the profile generated for Jan 1 (January multiplier, weekday type of Jan 1). The whole schedule is rotated by the start ordinal for any schedule longer than a day; occupancy, plug loads, lighting and water draws all land on the wrong month/weekday. Silent. The short-schedule modulo (`len*step`) accidentally aligns 24 h schedules, which is why simple tests pass.
- Fix: generate anchored to Jan 1 of the start's year (matching the CSV's 2007-anchored calendar) for `duration + start-ordinal` rows; or add a run-relative anchor switch in `compute_schedule_idx`. Test: generated schedule, mid-year start, the value at step 0 equals the profile evaluated at the same calendar date.

**C2. Warmup carries schedule/actor state into production; only the dwelling RNG is restored.**
- `crates/hares-core/src/dwelling/mod.rs:3383-3419` snapshots and restores only `dwelling.rng` around `run_warmup_converged_inner`. Warmup runs the full timestep pipeline (actors decide: `run_timestep(false)` at `:6184-6185`), but afterwards nothing resets `ScheduleSource` state (`ScheduleSource::reset()` at `crates/hares-types/src/schedule.rs:747-775` is called nowhere in production - only unit tests), event-load `StartDraws`, or actor counters.
- Sharpest symptom: the Occupant actor indexes its presence schedule by its own step counter, not the clock (`crates/hares-core/src/actors/occupant.rs:132-133, 274-285, 295-311`). After default warmup (converged day k), production step 0 reads `presence_schedule[k*steps_per_day]` - presence rotated by the warmup day count, and the tail silently falls back to `Presence::Home` via `.get(...).unwrap_or(Presence::Home)` (release; debug-assert fires). The comment at `mod.rs:3387-3389` ("identical stochastic output even when warmup converges in a different number of iterations") is only true for `dwelling.rng` - the per-source ChaCha8 RNGs in Stochastic/noisy TimeWindows sources and event-load draw counters advance by `days_run * steps_per_day` draws.
- Fix: after warmup, `reset()` every equipment/actor `ScheduleSource`, reset event-load `StartDraws` to construction position (or snapshot/restore actor+source state the way the gym does), reset actor step counters. Invariant test: a dwelling whose warmup converges at day 2 vs day 4 (forced via tolerance) produces identical production output.

## MAJOR

**M1. RL episode seeding is broken for EV-driving dwellings: the driver's stochastic schedule sources are excluded from both checkpoint and reseed.**
- `EvDriverActor::save_state/load_state` (`crates/hares-core/src/actors/ev_driver/mod.rs:1618-1652`) serialise only `self.rng` (the day-roll stream) - not the four schedule sources `daily_drive_miles`, `departure_time`, `trip_duration`, `arrival_time`, each with its own ChaCha8Rng (`catalog.rs:576-644`). `reseed` (`:1269-1274`) likewise resets only `self.rng`. The gym's `reset(seed)` = `load_state(initial_snapshot)` + `reseed(seed)` (`python/hares/rl/gym_env.py:601-620`).
- After episode 1 the sources sit mid-stream; episode 2 with the same seed draws different departures/miles than episode 1. Deterministic per-episode seeding silently fails for the default archetype presets (stochastic by default). The capture infrastructure exists (`schedule_helpers.rs:32-52`, used by `event_load`, `scheduled_load`, `ventilation`); the driver doesn't use it.
- Fix: capture/restore the four sources' `ScheduleSourceState` in the driver snapshot; `reseed` rebuilds them from the re-derived construction seed. Test: save_state -> run a day -> load_state -> reseed -> the next day's draws equal the saved-state run's.

**M2. Setpoint schedule columns are read as C; the OS-HPXML/ResStock detailed-schedule convention they come from is F - OCHRE converts, HARES doesn't.**
- `crates/hares-io/src/schedule_resolve.rs:955-958` states the OS-HPXML convention is F ("converted in `schedules.rb:1465-1484`") but says "the column values here are read as Celsius". The thermostat reads the column raw as `heating_c` (`crates/hares-equipment/src/hvac/thermostat.rs:364-373`). OCHRE converts at ingestion: `vendors/OCHRE/ochre/utils/schedule.py:411-412` (`convert(df_norm[hpxml_name].values, "degF", "degC")`). No range validation anywhere (`check_hvac_setpoint_invariants`, `schedule_resolve.rs:2279-2308` checks presence only).
- A user supplying a schedule CSV with `heating_setpoint`/`cooling_setpoint` columns in the documented OS-HPXML convention gets 68 "C" heating and 78 "C" cooling - HVAC pegged year-round, silently. ResStock 2025.1 ScheduleCache CSVs happen to omit setpoint columns (fixtures confirmed), which is why fleet runs don't hit it.
- Fix: convert F->C for the OsHpxml family at parse (mirroring OCHRE), or at minimum validate plausibility (error/warn when a setpoint column exceeds ~40 C) at construction.

**M3. EV driver silently substitutes fabricated defaults when a schedule read fails.**
- `ev_driver/mod.rs:666-713` - departure `.unwrap_or(480.0)`, arrival `.unwrap_or(1080.0)`, duration `.unwrap_or(600.0)`, miles `.unwrap_or(30.0)`.
- `ScheduleSource::value_at` deliberately rejects non-finite/unmatched values to close the "corrupt input under-reports load with no signal" class (`crates/hares-types/src/schedule.rs:622-637`); the driver reopens it. A corrupt miles distribution or a TimeWindows with no matching window and no default becomes a silently constant 8:00 departure / 30-mile day.
- Fix: propagate the error (`?`) naming the actor; keep a clamped fallback only for the documented re-sample-exhausted arrival guard.

**M4. Shared RNG keystreams: the EV driver's day-roll RNG and the miles source are built from the identical key; noisy TimeWindows sources default to the all-zero seed.**
- `actor_registry.rs:388-392` builds `seed_bytes` once; `EvDriverActor::new(..., ChaCha8Rng::from_seed(seed_bytes))` at `:440` and `preset.build_miles_schedule(seed_bytes)` at `:404-405` -> `noisy_time_windows(..., seed)` (`ev/catalog.rs:540-565`) receive the same unmodified 256-bit key (departure/duration/arrival get single-byte XORs - `dep_seed[0] ^= 0xDE` etc., `catalog.rs:596/619/635`). Separately, `ScheduleSourceConfig::into_runtime` defaults the noise seed to `[0u8; 32]` (`crates/hares-types/src/schedule.rs:489`).
- Identical ChaCha8 keys mean the day-roll uniform and the miles LogNormal consume the same keystream; two same-seed noisy sources draw identical noise sequences (perfectly correlated across, e.g., two water heaters). Exactly the correlation the RNG-module docs promise to prevent (`hares-core/src/rng.rs:1-8`).
- Fix: derive every schedule source's seed via the existing `derive_sub_rng`/stream-nonce scheme (per component tag); require an explicit seed or derive from the dwelling key instead of `[0u8; 32]`.

**M5. Fleet API hardcodes `master_seed: 0` and `civil_timezone: None`; no seed pass-through.**
- `crates/hares-fleet/src/fleet.rs:2024-2025` (`resstock_sim_config`) - every `from_resstock` fleet run is seed 0; `from_resstock`'s signature (`:348-357`) exposes no seed. `civil_timezone: None` at 10+ construction sites.
- Ensembles/uncertainty studies cannot vary stochastic behavior through the fleet entry point. The DST part is a defensible ResStock-parity convention (schedules on local standard time) but is undocumented and inconsistent with the Python single-dwelling default path (`py_dwelling.rs:2194`).
- Fix: `master_seed: Option<u64>` on `from_resstock` (per-home streams already derive `(master_seed, bldg_id)` - one parameter); thread into the fleet report; document the standard-time convention.

**M6. Water-heater draw/mains schedule sources are not captured in checkpoints.**
- `GasWhState` (`crates/hares-equipment/src/water_heater/gas.rs:836-859`) has no state for `draw_l_per_min_source`/`mains_temp_c_source` (`:120`, `:369-374`); same for `tankless.rs`, `indirect_tank.rs`, `heat_pump_wh.rs`. The capture/restore helpers exist (`schedule_helpers.rs:32-52`) and are used by `event_load`/`scheduled_load`/`ventilation`.
- A stochastic or Shared draw-flow source silently loses its draw position on state restore - I-08's stepped-run and checkpoint flows re-read the wrong rows/draws.
- Fix: add `Option<ScheduleSourceState>` fields to the WH snapshots; restore in `load_state`.

## MINOR

- **m1.** DR compliance re-rolls every step of an event instead of latching at event start: `dr_compliance.rs:933` calls `should_comply` per step (hash of `current_time.timestamp()`, `:181-192`); a 0.8-rate home dispatches on ~80% of steps, not complies with 80% of events - intermittent coverage, effective full-event compliance rate^N. Latch the draw on the Normal->non-Normal transition or document the per-step-hazard semantics.
- **m2.** Event probability is per-step, not normalized by step length: `StartDraws::starts` draws Bernoulli(p) per step (`event_load.rs:1718-1727`); documented (`docs/equipment/loads.md:90`) but changing `time_res` changes expected events/day multiplicatively. Normalize by dt (`p_step = 1-(1-p_hour)^(dt/3600)`) or error when `time_res` differs from the probability's declared basis.
- **m3.** Dead code + stale docs: `compute_schedule_offset` (`environment.rs:1774-1793`) has no production callers (its own test comment at `:3557-3560` says the path was replaced). `docs/weather-pipeline.md:160-179, 329` documents PCHIP resampling that no longer exists - the code is EnergyPlus linear interpolation with E+ references (`weather.rs:984-1002`); `docs/schedule-sources.md:59-71` documents a `SeededNoise` variant that is actually `Stochastic` and omits noisy-TimeWindows RNG semantics.
- **m4.** Schedule resample materialises per-dwelling upsampled columns and unused timestamps: `schedule.rs:254-289` zero-order-holds the full series - a 15-min, 16-column ResStock CSV at the fleet's 1-minute step (`fleet.rs:2018`) becomes ~50 MB/dwelling (350k rows x 16 cols x 8 B, plus 5.6 MB of `DateTime<FixedOffset>` timestamps nothing reads at run time - `compute_schedule_idx` is pure arithmetic; timestamps used only at generation, `schedule_resolve.rs:1854`). With I-08's thread-based fleet, workers x 50 MB is a real chunk of the ~1 GB figure. Hold source-resolution rows and index with a divide, or store columns without timestamps.
- **m5.** Occupant away telemetry flag writes 2.0 for Sleeping: `presence_as_f64` (`occupant.rs:450-456`) maps Sleeping->2.0 into the flag documented "1 when the occupant's current presence is Away" (`:159-161`, set at `:509`). Consumers filtering `away == 1` misread sleepers.
- **m6.** Arrival re-sampling truncates the arrival distribution: `ev_driver/mod.rs:672-697` up to 5 re-draws until arrival > departure then clamps - the comment claims it preserves the unconditional distribution, but it conditions on arrival > departure (censors the tail). Fix the comment or invert-sample from the truncated distribution.
- **m7.** No holiday calendar: `DayFilter` (`schedule.rs:13-34`) is Any/Weekdays/Weekends/Day; the EPW HOLIDAYS header is parsed only for the leap flag (`epw.rs:569`); holiday lighting explicitly unmapped (`schedule_resolve.rs:257-261`). Note it in `schedule-sources.md`.

## Missing tests / validation
1. Generated-schedule alignment (C1): mid-year start, step 0 equals the profile at the same calendar date; leap-year run; sub-year wrap Dec 31 -> Jan 1 for generated schedules.
2. Warmup state neutrality (C2): force warmup convergence at different days (tolerance knob); identical production output; include an Occupant actor + a presence schedule of exactly episode length (debug build catches the rotation via the existing debug_assert).
3. Episode reproducibility end-to-end (M1): gym-style `reset(seed)` twice -> identical per-step telemetry for a dwelling with an EV archetype preset; save_state -> N steps -> load_state -> next-step draws identical (crossing a day boundary).
4. Setpoint column units (M2): F-valued fixture CSV -> resolved C values; construction-time rejection of absurd setpoints.
5. Distributional validation of EV draws (M4): sampled miles/departures match the LogNormal/Gaussian parameters (moments, clamp rates); two noisy TimeWindows sources with unspecified seeds are not identical.
6. Checkpoint roundtrip with stochastic draw sources (M6): water heater with a LogNormal draw-flow source, run, save/load, continue - continuity.
7. Event-rate invariance across `time_res` (m2): same expected events/day at 60 s vs 300 s (fails today by design - decide the contract first).
8. DR event-scoped compliance (m1): 1.0-rate dispatches every step of an event; 0.0-rate never mid-event.
9. Fleet seed propagation (M5): `from_resstock(seed=k)` -> per-home `seeded_streams()` differ by bldg_id, stable across rebuilds.

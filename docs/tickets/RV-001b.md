## Background/Context

`find_map` at line 166-169 returns only the first demand rate's ratchet config and ignores all others. Tariffs with ratchets on non-first demand rates (common in PG&E, SCE) silently lose the ratchet, producing incorrect demand charges.

## Progress

**Session 2026-03-27:**

- [x] Added `prior_period_peaks: Vec<VecDeque<f64>>` to `BillingState` for per-period peak history
- [x] Added `effective_peak_for_period(period_idx, ratchet)` that applies each rate's own `RatchetConfig`
- [x] `compute_demand_charge()` now calls `effective_peak_for_period(idx, &dr.ratchet)` for TOU demand paths
- [x] `reset()` pushes per-period peaks to history
- [x] Test added: `billing_per_period_ratchet_applied`

Still needed:
- [ ] The global `ratchet_config` on `BillingState` (populated via `find_map` in the evaluator constructor) is still used for coincident demand via `effective_peak_kw()`. This is correct for coincident demand, but `find_map` is misleading — it silently takes only the first rate's ratchet. Should be replaced with an explicit coincident-demand ratchet config field or documented with a clear comment.

## Work to Do

- [x] Update `BillingState` to track per-rate ratchet state, applying each rate's ratchet independently in `compute_demand_charge()`
- [x] Ensure backward compatibility: single-rate tariffs with a ratchet produce identical results to before
- [ ] Replace or document the `find_map` global ratchet used for coincident demand in `effective_peak_kw()`

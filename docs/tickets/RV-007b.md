## Background/Context

`GlazingCurve::from_u_shgc()` is called per window surface per step with constant U-factor and SHGC values. This is unnecessary computation if the inputs are truly constant.

**Risk:** If window surface properties can change mid-simulation (e.g., dynamic glazing, shading devices, electrochromic windows), precomputing is incorrect. This ticket must first verify immutability before optimizing.

## Work to Do

- [ ] **First:** Verify that `WindowSolarProperties::u_factor_w_m2_k` and `::shgc` are never mutated after `ThermalSolver::new()`. Grep for all write access. If they can change (shading schedules, dynamic glazing), do NOT precompute — close this ticket as "won't fix"
- [ ] **If immutable:** Precompute `GlazingCurve` in `ThermalSolver::new()` or `ThermalSolverConfig` construction. Store as a field on `WindowSolarProperties` (e.g., `glazing_curve: GlazingCurve`). Remove the per-step `from_u_shgc` call in `solar.rs`
- [ ] **If mutable:** Add a comment documenting why per-step computation is required, close ticket

## Files to Touch

- `crates/hares-envelope/src/thermal_solver/solar.rs`: Precomputed `GlazingCurve` on surface info (if applicable)

## Tests Added

- `glazing_curve_precomputed_matches_per_step` — for 5 representative window configs (single-pane, double-pane low-e, triple-pane, high-SHGC, low-SHGC), assert precomputed `GlazingCurve` produces identical IAM corrections as per-step computation at solar noon, sunrise, and 60° incidence angle
- `glazing_curve_immutability_verified` — assert `WindowSolarProperties::u_factor_w_m2_k` and `::shgc` have no `&mut` access after construction (this is a code-level verification, not a runtime test)

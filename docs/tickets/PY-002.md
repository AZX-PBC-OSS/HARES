## Background/Context

The Python bindings have three error handling issues:

1. **Mutex poisoning info loss**: All 15+ `.lock()` calls in `py_dwelling.rs` convert `PoisonError` to a generic "failed to lock dwelling state" message. Users cannot distinguish between a poisoned mutex (from a prior panic) and a transient lock failure. A poisoned mutex means the dwelling state is corrupt and unrecoverable — users need to know this.

2. **Error type inconsistency**: Methods inside `py.detach()` closures return `Result<_, String>` because `PyErr` is not `Send`. Methods outside closures return `Result<_, PyErr>`. This is functionally correct but the error messages and types are inconsistent.

3. **Panic risks that poison the mutex**: `py_dwelling.rs` has two `.expect()` calls (`default_start()` line 487, `parse_datetime_str` line 458) that panic on invalid constants. While these are compile-time-constant values and should never fail, if they did, they'd panic outside the mutex — safe but poor practice.

## Work to Do

- [ ] Create a helper function to standardize mutex lock error handling:
  ```rust
  fn lock_dwelling(mutex: &Mutex<Dwelling>) -> PyResult<MutexGuard<'_, Dwelling>> {
      mutex.lock().map_err(|_| {
          PyRuntimeError::new_err(
              "dwelling state is corrupted (internal panic occurred); \
               create a new Dwelling instance"
          )
      })
  }
  ```
  Use `PyRuntimeError` (not `PyValueError`) for mutex poisoning — it's a runtime invariant violation, not a bad input value.
- [ ] Replace all 15+ `.lock().map_err(|_| PyValueError::new_err("failed to lock dwelling state"))?` patterns in `py_dwelling.rs` with `lock_dwelling(&self.dwelling)?`
- [ ] In `py_gym.rs`, update `observation_for_fields()` (line 77) to use the same helper or a similar one returning `Result<_, String>` for the detach context
- [ ] Replace `.expect("valid UTC offset")` in `parse_datetime_str()` with `.ok_or_else(|| PyValueError::new_err("invalid UTC offset"))?` — this cannot actually fail (argument is literal `0`), but `.expect()` in library code is poor practice
- [ ] Replace `.expect("valid default timestamp")` in `default_start()` with a `const` block or `LazyLock` that validates at compile/load time, or add a `// SAFETY: compile-time constant, cannot fail` comment and keep `.unwrap()`
- [ ] Standardize error messages in `py.detach()` closures:
  - All detach closures should return `Result<T, String>` (correct, as `PyErr` is not `Send`)
  - The outer code should convert `String` to appropriate `PyErr` type:
    - Simulation errors → `PyRuntimeError`
    - Lock poisoning → `PyRuntimeError`
    - User input errors → `PyValueError`
- [ ] Add a Rust unit test: `lock_dwelling` returns correct error type on poisoned mutex
  - Create a mutex, poison it by panicking inside a lock, verify `lock_dwelling` returns `PyRuntimeError`
- [ ] Add a Python test verifying error message content:
  - Simulate a poisoned state (may require calling a method that triggers internal panic, or mocking)
  - Verify error message contains "corrupted" and "create a new Dwelling"
  - Verify error type is `RuntimeError` (not `ValueError`)

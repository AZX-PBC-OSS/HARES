## Background/Context

Three hardcoded values that should be configurable:

1. **T7-2:** URDB parser at `urdb.rs:112-121` hardcodes June-September as summer. Arizona utilities use May-October, SCE uses April-October. Wrong season classification produces incorrect TOU rates.

2. **T7-3:** Python solar override at `py_dwelling.rs:49-55` uses class name string comparison (`"DataFrame"`, `"NDArray"`, `"ndarray"`). Fragile — breaks on subclasses, renamed types, or polars LazyFrame.

3. **T7-8:** Storm watch wind speed threshold at `bms.rs:317` hardcoded to 25.0 m/s. Different utilities define storm conditions at different thresholds.

## Work to Do

- [x] **URDB summer months:** Derive season classification from the tariff's own schedule data (the `energyweekdayschedule`/`energyweekendschedule` matrices encode which months have which rate periods). If the schedule data doesn't distinguish seasons, fall back to a configurable `summer_months: Vec<u8>` field on the tariff config with a default of June-September
- [x] **Solar override:** Replace `class_name_str == "DataFrame"` with duck typing: check for `.columns` attribute (DataFrame-like) or `.dtype`/`.shape` attributes (ndarray-like). Fall back to dict parsing if neither is detected. Also added surface ID validation.
- [x] **Storm watch threshold:** Add `wind_speed_threshold_m_s: f64` field to `StormWatchTrigger::WeatherSignal` (change from unit variant to struct variant). Default to 25.0 m/s. Replace the hardcoded comparison with `env.weather.wind_speed_m_s > self.wind_speed_threshold_m_s`

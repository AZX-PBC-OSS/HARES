## Background/Context

`SimulationEngine::run` branches on `flushed_batches().is_empty()`: when batches are populated (the normal path), `compute_metrics_from_batches` correctly invokes `MetricsCalculator`. However, the fallback `metrics_from_steps` path computes only `total_electric_power_kw`, leaving comfort hours, unmet loads, renewable fraction, rolling peak demand, and gas energy all zeroed or `None`. This fallback is reachable in edge cases (zero-step runs, warmup-only runs). Additionally, the `timeseries` field is set to `None` on the fallback path, breaking fleet aggregation. This is the #1 correctness blocker.

**Note**: OCHRE computes unmet load as degree-hours (C-hours), a temperature-difference-weighted metric. HARES counts binary timesteps. This is a known acceptable divergence — HARES's binary count is simpler but less granular. Track as a future enhancement if needed.

## Work to Do

- [ ] Remove `metrics_from_steps` and the fallback branch entirely — guarantee `flushed_batches()` is always non-empty after a successful `simulate()` call
- [ ] Add an assertion or early-return guard for the zero-step edge case (duration = 0 or duration = initialization_duration)
- [ ] Ensure `SimulationResults.timeseries` is always populated (fleet mode depends on this)
- [ ] Change `MetricsCalculator::new()` failure handling (engine.rs ~line 287-294) from silent `empty_metrics()` fallback to a hard error or `SimStatus::Flagged` — silent zeros are a correctness failure
- [ ] Fix `is_hvac_at_capacity` tolerance: replace absolute `EPSILON = 1e-9` with relative tolerance (e.g., `(output - capacity).abs() / capacity.max(1.0) < 1e-6`) to avoid false negatives at high wattages
- [ ] Add integration test exercising both electric and gas metric paths, asserting `metrics.annual_energy_kwh.total > 0`, comfort hours > 0, and peak demand > 0

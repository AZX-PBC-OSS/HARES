## Background/Context

HARES hard-rejects any HPXML file with `schemaVersion != "4.0"`. OCHRE also hard-gates on `"4.0"` only (base.py:108 — the comment says "3.0 or 4.0" but the code only accepts `"4.0"`). Both are overly restrictive. Both HARES and OCHRE also reject 4.1/4.2+ which NREL's HPXML toolbox now serves.

## Work to Do

- [ ] Parse version string as integer major version (split on `.`, take first segment as `u32`) — do NOT use lexicographic string comparison
- [ ] Accept full 3.x and 4.x families (not just "3.x" and exactly "4.0")
- [ ] Warn on 3.x (may have untested element paths), accept 4.x silently
- [ ] Reject major version < 3 as unsupported
- [ ] **Before shipping**: audit the parser against a synthetic 3.x file to verify no panics or silent field omissions from 4.0-exclusive element names
- [ ] Add a test fixture with `schemaVersion="3.0"` or `"3.4"` that parses with warning
- [ ] Add a test verifying `schemaVersion="4.2"` parses without warning

## Files to Touch

- `crates/hares-io/src/hpxml/validation.rs`: relax version check to accept 3.x with warning, reject < 3.0

## Measures of Success

- [ ] HPXML 3.x files parse successfully with a warning
- [ ] HPXML 4.0 files parse without warning
- [ ] HPXML 2.x files are rejected

## Implementation Guidance

- **OCHRE reference**: Spot-check the reference implementation in `vendors/OCHRE/` (especially `ochre/models/`, `ochre/utils/`, `ochre/Equipment/`) to verify behavior, edge cases, and default values.
- **Authoritative sources**: Use web search to verify constants, formulas, and algorithms against authoritative references (ASHRAE Fundamentals, EnergyPlus Engineering Reference, NREL technical reports, NIST CODATA) rather than trusting any single implementation.
- **Better physics wins**: If HARES already has better physics than OCHRE, keep it and document the divergence. Only align with OCHRE where OCHRE is correct and HARES is wrong.

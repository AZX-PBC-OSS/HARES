## Background/Context

The RC network uses material property lookup tables (wall/roof/floor assembly
thermal resistance, capacitance) loaded from CSV files. These were never compared
against OCHRE's equivalent LUT data.

## Investigation Summary

Three CSV files are compared:

| File | OCHRE source | HARES copy | Row count |
|---|---|---|---|
| Envelope Boundaries.csv | vendors/OCHRE/ochre/defaults/Envelope/Envelope Boundaries.csv | defaults/envelope/Envelope Boundaries.csv | 33 data rows (identical) |
| Envelope Boundary Types.csv | vendors/OCHRE/ochre/defaults/Envelope/Envelope Boundary Types.csv | defaults/envelope/Envelope Boundary Types.csv | 400 data rows (identical count) |
| Envelope Materials.csv | vendors/OCHRE/ochre/defaults/Envelope/Envelope Materials.csv | defaults/envelope/Envelope Materials.csv | 1510 data rows (identical count) |

Lookup logic is in `crates/hares-io/src/envelope_lut.rs`. Lookup is called from
`crates/hares-core/src/dwelling/conversions.rs:105`.

OCHRE's algorithm is in `vendors/OCHRE/ochre/utils/envelope.py:200-290`.

## Findings

### F1 — CRITICAL: Film R constants documented as SI but they must be verified against OCHRE IP constants [RESOLVED — CONFIRMED CORRECT]

**Status: Not a defect.** HARES uses SI film R constants:
- `FILM_R_FLOOR_CEILING = 0.2642` m²·K/W
- `FILM_R_WALL_ROOF = 0.1585` m²·K/W

OCHRE uses IP constants `1.5` and `0.9` hr·ft²·°F/BTU respectively.
Conversion: 1.5 × 0.17611 = 0.26417 ≈ 0.2642. 0.9 × 0.17611 = 0.15850 = 0.1585.
Match is exact to 4 significant figures.

### F2 — CRITICAL: Boundary Types CSV Assembly R Values are pre-converted to SI [RESOLVED — CONFIRMED CORRECT]

**Status: Not a defect.** The OCHRE Boundary Types CSV stores IP R-values (e.g., Attic Floor R-49 = 49.075 hr·ft²·°F/BTU). HARES' copy at `defaults/envelope/Envelope Boundary Types.csv` stores the same values converted to SI (8.6421 m²·K/W). Spot-check: 49.07519 × 0.17611 = 8.641 ✓. The lookup comparison is therefore internally consistent: SI r_val vs SI CSV assembly_r + SI film_r.

The Materials CSV (`Resistance (m^2-K/W)` and `Capacitance (kJ/m^2-K)`) already used SI in OCHRE and is identical in HARES.

### F3 — HIGH: Minimal boundary clamping does not clear construction/finish/insulation filters

**File:** `crates/hares-io/src/envelope_lut.rs:192-194`

OCHRE (`envelope.py:217-222`):
```python
if r_value and r_value >= 100:
    r_value = 500
    construction = None   # filters cleared
    finish = None
    insulation = None
```

HARES (`envelope_lut.rs:192-194`):
```rust
let r_val = if r_val >= 17.6 { 88.0 } else { r_val };
// construction/finish/insulation filters are NOT cleared
```

For a building component with `r_value >= 17.6` SI (100 IP), HARES clamps the R-value target to 88.0 but retains any prior construction/finish/insulation filters. If those filters narrow the candidate set to rows that do not include the `Minimal` row (which has no construction type or finish type), the lookup could miss entirely or return the wrong assembly. OCHRE intentionally forces the Minimal selection regardless of those properties.

**Concrete failure path:** A wall boundary with `construction_type=Some("WoodStud")` and `assembly_r_value >= 17.6` SI. After filtering by WoodStud, the Minimal row (which has empty construction type) will have been excluded. HARES will incorrectly pick the highest WoodStud R-value row instead of the Minimal variant. Affected boundary names: any that have both a `Minimal` row and typed rows (Attic Floor, Attic Wall, Exterior Wall, etc.).

### F4 — MEDIUM: Insulation details R-value uses integer rounding instead of OCHRE's `:n` (float) formatting

**File:** `crates/hares-io/src/hpxml/building.rs:1138-1142` (foundation wall) and `1179-1195` (slab)

OCHRE uses Python's `f"{r_value:n}"` which emits the shortest decimal representation (e.g., `"5.5"` for 5.5, `"10"` for 10.0).

HARES uses `.round() as i32` then integer formatting, e.g., R=10.5 → `"R11"` instead of `"R10.5"`.

The Foundation Wall LUT only contains integer R-values (R5, R10, R13, R15, R18, R20). In practice, HPXML NominalRValue is almost always an integer, so this is low risk. However, non-integer inputs (possible in non-ResStock HPXML files) would produce a different string than OCHRE and could cause a LUT miss followed by a fallback to raw material layers.

### F5 — MEDIUM: Combined perimeter+under-slab insulation silently produces "Uninsulated" instead of failing

**File:** `crates/hares-io/src/hpxml/building.rs:1197-1199`

When a `<Slab>` element has both `r_perimeter > 0` and `r_under > 0` (but not both ≥ 100 for Minimal), OCHRE raises `OCHREException("Unknown slab insulation parameters")`. HARES' `extract_slab_insulation` falls through to `"Uninsulated"`, silently masking the unsupported case and returning a wrong LUT key.

### F6 — LOW: `lookup()` silently picks `filtered[0]` when multiple candidates remain and `r_value is None`

**File:** `crates/hares-io/src/envelope_lut.rs:211-213`

OCHRE raises an exception in this case:
```python
elif r_value is None:
    raise OCHREException(f"Boundary R Value must be specified...")
```

HARES returns `filtered[0]` (first CSV row) without warning. In practice, the progressive filters (construction, finish, insulation) usually narrow to one row, so this is rarely triggered. But when it is, wrong RC layers are selected silently.

### F7 — LOW: LUT tests pass IP values as SI in R-value arguments

**File:** `crates/hares-io/tests/envelope_lut_tests.rs:79`

```rust
let r39 = lut.lookup("Attic Floor", None, None, None, Some(39.0))
    .expect("R-39 closest match");
assert!(!r39.layers.is_empty());
```

`39.0` here is treated as SI (m²·K/W ≈ 221 IP), which would clamp to 88.0 SI (Minimal), not pick R-38. The test only checks `!r39.layers.is_empty()` and does not verify that the R-38 assembly was actually selected. Similarly `Some(10.0)` at line 23, `Some(15.0)` at line 42, `Some(5.0)` at line 104, `Some(10.0)` at line 117 are all SI values, none of which correspond to the labeled expected assembly. Tests pass but do not validate correct R-value nearest-neighbor selection.

### F8 — INFORMATIONAL: `Envelope Boundaries.csv` is loaded into `defaults/envelope/` but never parsed by HARES

**File:** `crates/hares-io/src/envelope_lut.rs:107-118`

`EnvelopeLookup::load()` only loads `Envelope Boundary Types.csv` and `Envelope Materials.csv`. The `Envelope Boundaries.csv` zone-label mapping file is not parsed. HARES derives zone assignments via `resolve_boundary_name()` (hardcoded logic). This is functionally correct and intentional — the file is shipped for reference only.

## Required Fixes

### Fix F3 (HIGH): Clear filters before clamping to Minimal

In `crates/hares-io/src/envelope_lut.rs`, modify `lookup()` to null out
construction/finish/insulation filters and re-filter from the full candidate set
when `r_val >= 17.6` (the Minimal clamping branch), mirroring OCHRE's behavior.

```rust
// OCHRE clamps R >= 17.6 m²·K/W (100 IP) to Minimal: clear all type filters.
if r_val >= 17.6 {
    filtered = candidates.iter().collect();
    r_val = 88.0;
}
```

### Fix F4 (MEDIUM): Use float formatting matching OCHRE `:n` for insulation details strings

In `extract_foundation_wall_insulation` (building.rs:1138) and `extract_slab_insulation` (building.rs:1179), replace `r_ip.round() as i32` with a helper that formats like OCHRE's `:n`: emit the float without trailing zeros (e.g., `10.0 → "10"`, `10.5 → "10.5"`).

### Fix F5 (MEDIUM): Propagate combined slab insulation error

In `extract_slab_insulation` (building.rs:1197), change the else branch to return `None` (which will cause a LUT miss logged at debug) or propagate an error, rather than silently producing "Uninsulated". Add a `tracing::warn!` so the caller can diagnose unexpected HPXML.

### Fix F6 (LOW): Warn when R-value is None with multiple candidates

In `envelope_lut.rs:211-213`, emit a `tracing::warn!` when falling back to `filtered[0]` due to missing R-value with multiple candidates, so this case is visible in logs.

### Fix F7 (LOW): Fix LUT test R-value arguments to use SI values

In `envelope_lut_tests.rs`, replace IP-magnitude R-value arguments with correct SI equivalents matching the labeled assembly. For example, `Some(39.0)` for R-39 should be `Some(39.0 * 0.17611)` = `Some(6.868)`, and the assertion should verify the matched type contains "R-38".

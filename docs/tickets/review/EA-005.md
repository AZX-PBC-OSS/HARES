No existing ticket traces full runtime EV charging physics. DT-005 covers timezone only. CW-021 covers config wiring only. The un-covered areas include: SOC model, charging curve shape, V2G/V2H discharge, unmet_load tracking, and the architectural difference between OCHRE's event-based EV and HARES's actor-driven model.

## SOC Model Comparison

### OCHRE (`EV.py`)

OCHRE uses an **AC-side taper formula** for the SOC limit:

```python
# calculate_power_and_heat()
soc_max_power = (self.soc_max_ctrl - self.soc) * self.capacity / hours / EV_EFFICIENCY
ac_power = min(max(self.p_setpoint, 0), soc_max_power)
dc_power = ac_power * EV_EFFICIENCY
self.next_soc = self.soc + dc_power * hours / self.capacity
```

The taper limit `soc_max_power` is computed **AC-side** (before efficiency). Efficiency is applied after clamping. This means:

- Power is clamped on the AC side.
- The resulting DC energy stored is `ac_power * EV_EFFICIENCY * dt_hours`.
- `soc_max_ctrl` can be overridden by an external `Max SOC` control signal, separate from `soc_max`.

### HARES (`ev/mod.rs:511`)

HARES also computes the taper limit AC-side:

```rust
let taper_limit = (soc_limit - self.soc).max(0.0) * self.battery_capacity_kwh
    / dt_hours
    / self.charging_efficiency;
```

And SOC update:
```rust
let dc_stored_kw = net_charge_kw * self.charging_efficiency;
let dc_energy_kwh = dc_stored_kw * dt_hours;
self.soc = (self.soc + dc_energy_kwh / self.battery_capacity_kwh).clamp(0.0, 1.0);
```

The math is algebraically equivalent to OCHRE for the non-heater case. **SOC model matches.**

### `soc_max_ctrl` vs `soc_max` split

OCHRE distinguishes `soc_max` (static hardware limit, initialized from config) from `soc_max_ctrl` (runtime value that can be overridden by schedule or control signal per timestep). The taper formula uses `soc_max_ctrl` exclusively.

HARES consolidates this into a priority chain: `soc_target > ready_by_soc > ready_soc`, all clamped by `soc_max`. A `SOCTarget` control signal sets `soc_target`. This is functionally equivalent and arguably cleaner, but means the `soc_max` hardware limit is only enforced via the `clamp(0.0, self.soc_max)` at the end of `effective_soc_limit()` and inside `compute_charging_power_kw()`. **No behavioral divergence identified, but OCHRE resets `soc_max_ctrl` to `soc_max` at the start of each timestep's `update_internal_control()` via schedule, while HARES persists `soc_target` across timesteps until explicitly cleared.** This is an intentional architectural difference; external controllers using HARES must clear the SOC target explicitly.

## Charging Curve Comparison

### OCHRE

OCHRE uses a **constant-power model** with no CC-CV taper shape: `ac_power = min(p_setpoint, soc_max_power)`. It charges at full rated power until the SOC limit is hit, then drops to zero. There is no continuous ramp down — the `soc_max_power` formula naturally produces a power ramp as SOC approaches the limit (because `(soc_max - soc)` shrinks), but only within the final timestep resolution. This is effectively a **bang-bang / threshold model** at practical timestep sizes (15-min typical).

OCHRE does not have a charging curve LUT or CC-CV shape model.

### HARES

HARES adds three layers beyond OCHRE:

1. **Linear taper (built-in):** The `taper_limit` formula mirrors OCHRE's `soc_max_power`, providing a ramp within the final timestep. Behaviorally identical.

2. **4D charging curve LUT** (`ev/mod.rs:483–494`): An optional `RegularGridInterpolator` over (soc, temp_c, c_rate, soh) that scales the rated power by a fractional multiplier. Applied before the taper limit. This is beyond OCHRE capability and provides real CC-CV shape from PyBaMM data.

3. **Temperature derating** (`charge_derate_factor()`): Linear ramp between `min_charge_temp_c` and `full_power_temp_c`. OCHRE has no temperature derating on charging.

The LUT is injected via `set_charging_curve_lut()` and cannot be set from config/HPXML (per CW-021 F-005). Default behavior (no LUT) matches OCHRE.

**CC_CV_MARGIN constant (`ev/mod.rs:55`):** The value `0.85` is used in `bms_ready_by_power()` to account for longer charge time in the CV region when estimating hours needed. This is a heuristic; no physical reference is cited. Low risk (affects BMS scheduling only, not power or SOC physics).

## V2G/V2H Discharge Paths

### OCHRE

OCHRE's `ElectricVehicle` class **does not implement V2G or V2H discharge**. The power is always clamped to `max(p_setpoint, 0)` — negative values are blocked. V2G is not a feature in the OCHRE EV model.

### HARES V2G (`ev/mod.rs:583–594`)

```rust
fn compute_v2g_discharge(&self, dt: Duration) -> f64 {
    if self.soc <= self.v2g_soc_reserve { return 0.0; }
    let capped = setpoint_magnitude.min(self.v2g_max_discharge_kw);
    let available_kwh = (self.soc - self.v2g_soc_reserve) * self.battery_capacity_kwh;
    let max_discharge_kw = available_kwh / dt_hours;
    -(capped.min(max_discharge_kw).max(0.0))
}
```

### HARES V2L (`ev/mod.rs:571–581`)

Structurally identical to V2G but uses `v2l_soc_reserve` and `v2l_max_discharge_kw`.

### Finding F-001 — BUG — HIGH: V2G/V2L discharge uses `charging_efficiency` inverted — wrong sign for round-trip loss

**File:** `crates/hares-equipment/src/ev/mod.rs:715–720`

```rust
if is_v2l_discharge {
    let ac_discharge_kw = charger_kw.abs();
    let dc_discharge_kwh = (ac_discharge_kw / self.charging_efficiency.max(0.01)) * dt_hours;
    self.soc = (self.soc - dc_discharge_kwh / self.battery_capacity_kwh).clamp(0.0, 1.0);
}
```

`charger_kw.abs()` is the AC power delivered to the load/grid. Dividing by `charging_efficiency` to get DC energy consumed from the battery means a discharge efficiency of `η_charge` is used — this is physically wrong for discharge. The correct interpretation is:

- Charging: `DC_stored = AC_in × η` → η is the wall-to-battery efficiency.
- Discharging: `AC_out = DC_drawn × η_discharge` → the battery must provide `AC_out / η_discharge` DC to deliver `AC_out` AC.

HARES uses the same scalar (`charging_efficiency`, defaulting to 0.9) for both charging and discharging, which is a reasonable approximation only if charge and discharge efficiencies are equal. However, the formula direction is correct: dividing `ac_discharge_kw` by `charging_efficiency` gives the DC drawn, which is larger than the AC output — consistent with lossy discharge. The math is not wrong, just uses a single shared efficiency parameter rather than separate charge/discharge efficiencies.

However, the conceptual labeling in the code is confusing: the field is named `charging_efficiency` but is being applied during discharge. **No false numeric result assuming symmetric efficiency, but the labeling is misleading and there is no separate discharge efficiency parameter.** This is a documentation/API clarity issue, not a numeric bug, unless a caller sets `charging_efficiency` believing it only affects charging.

**Revised severity: MEDIUM — documentation/API clarity defect.**

### Finding F-002 — BUG — MEDIUM: V2G priority over V2L is undocumented and may be incorrect

**File:** `crates/hares-equipment/src/ev/mod.rs:444–455`

```rust
if let Some(setpoint) = self.power_setpoint_kw {
    if setpoint < 0.0 {
        if self.v2g_enabled {
            return self.compute_v2g_discharge(dt);
        } else if self.v2l_enabled {
            return self.compute_v2l_discharge(dt);
        }
    }
}
```

If both `v2g_enabled` and `v2l_enabled` are true, V2G takes precedence unconditionally. V2L is silently disabled. This priority rule is not documented in config keys, not validated at init, and has no test covering the dual-enabled case. An operator who enables both expecting V2L to take priority (e.g., for load-serving before grid export) will get incorrect behavior.

**Fix:** Either document that V2G takes priority when both are enabled and add a test for dual-enabled, or emit a configuration warning when both are enabled, or support a configurable priority. At minimum, add a test.

### Finding F-003 — BUG — MEDIUM: V2G discharge does not apply efficiency in `apply_soc_and_thermal`

**File:** `crates/hares-equipment/src/ev/mod.rs:715–720` (same branch as above)

The `is_v2l_discharge` flag gates the discharge path for **both** V2L and V2G:

```rust
self.v2l_active = is_v2l_discharge;  // line 783
```

But `v2g_enabled` discharge also sets `is_v2l_discharge = true` via the boolean returned from `run_charging_physics`. This is fine for routing the SOC update, but `v2l_active` and `v2l_power_kw` are set to V2G discharge values when V2G is active. The telemetry fields `v2l_active` and `v2l_power_kw` therefore report V2G activity as V2L. **Telemetry mislabeling when V2G is active.**

**Fix:** Distinguish V2L from V2G at the `run_charging_physics` return level. Return a tri-state (charging, v2l, v2g) instead of `is_v2l_discharge: bool`. Emit separate `v2g_active` and `v2g_power_kw` telemetry fields. The current code has `v2l_active` telemetry key hardcoded to cover both discharge modes.

## Unmet Load Handling

### OCHRE

OCHRE tracks `unmet_load` in kWh — energy that could not be stored before departure because the event ended at a lower SOC than expected. At `end_event()`, if the propagated `next_start_soc` is negative, the deficit is recorded in `self.unmet_load` for one timestep and the next event's `start_soc` is floored at 0.

### HARES

HARES has **no `unmet_load` concept**. When the EV departs (actor sends `EvDrive { kwh }` signals), the energy is deducted from SOC. If SOC reaches 0, `EvDrive` is rejected with a `HaresError::Control` if `kwh > available_kwh` (`ev/mod.rs:1028`). The actor guards against over-discharge via its estimated-SOC tracking, but does not emit any unmet-load telemetry.

### Finding F-004 — GAP — MEDIUM: No unmet-load telemetry key

The absence of an unmet-load counter means downstream energy analysis tools cannot determine whether an EV failed to fully charge before departure. OCHRE exposes this as a result field at verbosity ≥ 3. HARES has no equivalent.

This is acceptable if the system constraint is that EV actors must be designed conservatively (which the range anxiety override achieves), but it reduces observability for post-simulation diagnosis.

**Recommendation:** Add a `unmet_charge_kwh` telemetry key that accumulates whenever a charging session ends (actor transitions from `HomePluggedIn` to `Driving`) with `soc < ready_soc`. This requires the actor to observe the EV's SOC at departure, which it already does via `current_soc()`.

## Architectural Divergence: Event-Based vs Actor-Driven

OCHRE uses a single `ElectricVehicle` class with an internal event-schedule (sampled from a PDF file at construction). Each event has a pre-computed `end_soc`, and the class propagates SOC deficit between consecutive events.

HARES separates concerns:
- `Ev` equipment handles physics (charging, SOC, thermal, degradation).
- `EvDriverActor` handles behavior (departure, driving, arrival, charging strategy).

The HARES actor rolls daily events stochastically from `ScheduleSource` distributions each new calendar day. It does not pre-compute a full season of events. The SOC deficit propagation across events is implicit: actual SOC at departure is whatever the equipment reports; the actor does not adjust future arrival SOC based on deficit.

This architectural difference is correct and intentional. However, it means OCHRE parity tests for unmet-load propagation cannot be written without a dedicated telemetry path.

## Additional Findings

### Finding F-005 — BUG — LOW: `bms_ready_by_power` deadline "just passed" window is 1 hour — too coarse

**File:** `crates/hares-equipment/src/ev/mod.rs:554`

```rust
} else if (current_hour - ready_by_hour).abs() < 1.0 {
    // Deadline just passed (within 1 hour) — charge immediately
    return derated_rated;
}
```

If the ready-by deadline passes (e.g., owner forgot to plug in the previous night), the BMS charges at full rate for up to 1 hour after the missed deadline. This 1-hour window is arbitrary. In practice, once the deadline has passed, the battery should charge immediately regardless — the window should not matter. But combined with the overnight-wrap logic, if `ready_by_hour = 7.0` and `current_hour = 8.5`, the car charges for 0.5 hours at full rate (fine), but if `current_hour = 7.9`, it also charges (correct). If `current_hour = 8.05`, the difference is 1.05 > 1.0 — the wrap logic kicks in and treats this as 22.95 hours until the "next day's" 7:00 deadline — meaning the BMS immediately delays charging until 22.95 - needed hours before 7 AM. This is incorrect post-deadline behavior: the car should charge immediately after any missed deadline, not defer to the next day's deadline.

**Fix:** After `hours_until_deadline < 0` (after deadline has passed), always return `derated_rated`. Remove the 1-hour window and replace with a clean "deadline is in the past today" check using `current_hour > ready_by_hour && (current_hour - ready_by_hour) < some_reasonable_window`.

### Finding F-006 — GAP — LOW: No V2G port contribution — V2G discharge is invisible to the electrical port

**File:** `crates/hares-equipment/src/ev/mod.rs:798–803`

```rust
if is_v2l_discharge || self.active_power_kw > 0.0 {
    ports.accumulate(&PortContribution::Electrical {
        active_power_kw: self.active_power_kw,
        ...
    })?;
}
```

When `is_v2l_discharge` is true (which covers both V2L and V2G), `active_power_kw = charger_kw` (negative). This routes the negative contribution through `PortContribution::Electrical`, which routes it to `generation_power_kw` in the port accumulator (`ports.rs:431`). This is correct for V2L (local generation). For V2G (export to grid), the same path is used — HARES does not distinguish grid-export from load-serving in the port layer. This is acceptable if the tariff layer handles grid-export correctly via the same `generation_power_kw` path, but is worth documenting.

## Recommended Tests

### T-001 — V2G and V2L both enabled: V2G wins and is documented

Construct an `Ev` with both `v2g_enabled=true` and `v2l_enabled=true`. Apply a negative `PowerSetpoint`. Assert V2G is used (power comes from `v2g_max_discharge_kw` ceiling, not `v2l_max_discharge_kw`). Document priority in config comment.

### T-002 — V2G telemetry is distinct from V2L

Construct an `Ev` with `v2g_enabled=true`, `v2l_enabled=false`. Apply a negative `PowerSetpoint`. Step. Assert:
- `active_power_kw < 0`
- Telemetry key `v2l_active == 0.0` (not reporting V2G as V2L)
- A new `v2g_active` telemetry key == 1.0

*Note: this test will fail until F-003 is fixed.*

### T-003 — Unmet charge at departure is detectable

Step an `Ev` from `soc=0.2` with `rated_power_kw=7.2` for only 5 minutes, then send `EvDrive` for 30 kWh. Assert that `telemetry["unmet_charge_kwh"] > 0`.

*Note: this requires F-004 to be implemented first.*

### T-004 — Symmetric discharge efficiency round-trip

Charge an `Ev` from `soc=0.5` with `charging_efficiency=0.9` for 1 hour at 7.2 kW. Record `soc_after_charge`. Then discharge the same energy back (V2L). Assert `soc_final ≈ soc_before_charge` within tolerance (round-trip efficiency squared). Documents the symmetric efficiency assumption.

### T-005 — BMS ready-by does not defer after missed deadline

Configure `ready_by_hour = 7.0`. Step at 08:30 (deadline passed by 1.5 hours). Assert `compute_charging_power_kw` returns `derated_rated`, not 0. This covers the wrap-around bug in F-005.

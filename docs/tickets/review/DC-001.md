## Background/Context

OCHRE has a general duty cycle control mechanism: `calculate_mode_priority()` tracks
time spent in each mode via `ext_mode_counters`, allocating mode fractions according to
`duty_cycle_by_mode`. This allows external controllers to specify "run in mode X for Y%
of the control window." HARES must have an equivalent for DR and external control.

## OCHRE Mechanism (Reference)

### Equipment.calculate_mode_priority() — vendors/OCHRE/ochre/Equipment/Equipment.py:134

OCHRE's duty cycle control operates over an external control window (`ext_time_res`):

1. **`ext_mode_counters`** — per-mode accumulators of elapsed time, incremented each step
   that a control signal is active (`Equipment.py:246`). Resets at the start of each new
   control window (`Equipment.py:149–153`).
2. **`duty_cycle_by_mode`** — fraction of `ext_time_res` each mode is allowed. Defaults to
   `{"On": 0, "Off": 1}`. Overwritten each call via `update_duty_cycles()`.
3. **`calculate_mode_priority()`** builds a priority list of modes that have not yet
   exhausted their allocated fraction. The current mode is promoted to the top when still
   in budget. If no mode has remaining budget (counters all saturated), the current mode is
   kept with a warning.
4. **`run_duty_cycle_control()` — HVAC.py:325** — shortcuts for `duty_cycle==0` (force Off,
   `speed_idx=0`) and `duty_cycle==1` (force On, `speed_idx=n_speeds`). For fractional
   values, calls `calculate_mode_priority()`, then lets the thermostat select among allowed
   modes; overrides to the top-priority mode only when the thermostat result is not in the
   priority list or `ext_ignore_thermostat` is set.
5. **`ext_ignore_thermostat`** — flag to bypass thermostat entirely and always use the
   priority mode. Not a default behavior; only activated by explicit config.

### Two-speed timer in OCHRE — HVAC.py:859–915 (`run_two_speed_control`)

- Timer `time_in_speed` is **reset to zero** whenever `speed_idx == 0` (equipment off)
  (`HVAC.py:863`).
- On a speed change or fresh on-cycle the timer is set to `time_res` (one step); otherwise
  it accumulates (`HVAC.py:911–914`).
- Minimum on-time guard (`min_time_in_speed`) is checked against `prev_speed_idx − 1`
  (1-indexed speeds), so low and high speeds each have their own minimum dwell.

## HARES Implementation

### What HARES does have

**`ctrl_duty_cycle` / `dr_duty_cycle` — multiplier model**

`AirConditioner` (`air_conditioner.rs:91,101`) and `HeatPumpHeater` (`heater.rs:112,128`) hold
separate `ctrl_duty_cycle` and `dr_duty_cycle` floats. These are applied as multiplicative
factors on the final output in `step()`:

```
effective_load = ctrl_duty_cycle * ctrl_load_fraction * dr_load_fraction * dr_duty_cycle
```

`ControlSignal::DutyCycle { on_fraction, .. }` sets `ctrl_duty_cycle`
(`air_conditioner.rs:1052`, `heater.rs:1108`). The `period_s` and `component` fields are
silently ignored (`..` pattern).

**Thermostat FSM — `update_mode()` / `can_transition_mode()`**

`HvacEquipment::update_mode()` (`hvac_core.rs:567`) implements the OCHRE deadband thermostat
with asymmetric `deadband_offset` correctly. Mode transitions respect `min_on_time_s` and
`min_off_time_s` compressor guards via `can_transition_mode()` (`hvac_core.rs:705`).

**Speed staging timer — `time_at_current_speed_s`**

`staging.rs` implements `TwoSpeedSetpoint`, `TwoSpeedTime`, and `TwoSpeedAlternating` modes
with a dwell timer (`time_at_current_speed_s`) and minimum guard (`min_time_per_speed_s`).
`advance_speed_timer()` accumulates elapsed time.

## Findings

### F-1 (HIGH) — No `ext_mode_counters` equivalent: `period_s` is a dead field

**Files:** `crates/hares-types/src/control_signal.rs:67`,
`crates/hares-equipment/src/hvac/air_conditioner.rs:1051`,
`crates/hares-equipment/src/hvac/heat_pump/heater.rs:1101`

HARES has no mechanism equivalent to OCHRE's `ext_mode_counters`/`ext_time_res` budget
tracking. `ControlSignal::DutyCycle::period_s` is declared in the type but every
`apply_control_unchecked` handler matches `DutyCycle { on_fraction, .. }` — the `period_s`
field is consumed by the `..` wildcard and never read. Any controller that sets `period_s`
expecting OCHRE-style "X% of Y-second window" behaviour will observe that the period is
silently discarded.

Without time-window accounting, a `ctrl_duty_cycle = 0.5` signal scales every step's output
to 50% rather than meaning "run at full power for 50% of the window." This is a different
semantic from OCHRE's model and will diverge under dynamic DR dispatch scenarios.

**Fix:** Either (a) implement per-window mode counters analogous to `ext_mode_counters`, or
(b) document that HARES intentionally uses a continuous fractional model instead and remove
`period_s` from the type rather than keeping a dead field.

---

### F-2 (HIGH) — Speed timer never resets on Off-cycle

**Files:** `crates/hares-equipment/src/hvac/air_conditioner.rs:644`,
`crates/hares-equipment/src/hvac/heat_pump/heater.rs` (no call to `advance_speed_timer`)

OCHRE resets `time_in_speed = 0` whenever the equipment is off (`HVAC.py:863`). HARES
`advance_speed_timer()` is called only inside the `OperatingMode::Cooling` branch of
`AirConditioner::step()` (`air_conditioner.rs:644`). The counter therefore persists across
off-cycles: after an equipment shutdown and restart, the residual dwell time from the
previous on-cycle still counts toward the minimum guard, allowing a speed escalation
earlier than OCHRE would permit.

`HeatPumpHeater` never calls `advance_speed_timer()` at all (`heater.rs`: no matches).
Its speed timer does not accumulate under any operating mode — the two-speed guard is
permanently stuck at zero, making `min_time_per_speed_s` a no-op for heating equipment.

**Fix for AirConditioner:** call `advance_speed_timer(0.0)` or explicitly reset
`time_at_current_speed_s = 0.0` in the Off branch of `step()`, matching OCHRE's reset
semantics.

**Fix for HeatPumpHeater:** add `self.hvac.advance_speed_timer(dt.as_secs_f64())` inside
the on-mode branch of `step()`, and reset to zero in the off branch.

---

### F-3 (MEDIUM) — No `ext_ignore_thermostat` equivalent

**Files:** `crates/hares-equipment/src/hvac/air_conditioner.rs`,
`crates/hares-equipment/src/hvac/heat_pump/heater.rs`

OCHRE supports `ext_ignore_thermostat=True` to let an external controller override the
thermostat entirely: when set, `run_duty_cycle_control()` always takes the top-priority mode
regardless of what the thermostat reports (`HVAC.py:347`). HARES has no equivalent flag.

A HARES `ControlSignal::ModeOverride` can force a specific `OperatingMode`, but there is no
"bypass thermostat, follow priority list" knob that respects the fractional duty cycle
budget simultaneously. This affects DR dispatch fidelity for controllers that combine duty
cycle fractions with thermostat override.

**Fix:** Add an `ignore_thermostat: bool` field to `ctrl_*` state (or support it as a
`ControlSignal` variant), guarding the `update_mode()` call in `update_control()`.

---

### F-4 (LOW) — Two-speed shortcut semantics differ from OCHRE

**Files:** `crates/hares-equipment/src/hvac/staging.rs:81–112`

OCHRE shortcuts `duty_cycle==0` to force Off with `speed_idx=0`, and `duty_cycle==1` to
force On at max speed (`HVAC.py:326–331`). HARES `select_speed()` for `TwoSpeedAlternating`
always targets high speed (`desired_index = 1`, `staging.rs:92`) and does not distinguish the
full-off shortcut path. The AC `update_control()` already gates on thermostat mode and sets
`duty_cycle=0.0` on `Deadband`; the shortcut is effectively handled, but only via the
thermostat path, not as a direct capacity-bypass. This is a design difference rather than a
bug, but it means a `ctrl_duty_cycle=0.0` signal that bypasses the thermostat will multiply
a non-zero computed capacity by zero rather than skipping the calculation entirely, causing
unnecessary compute in the off path.

## Recommended Tests

1. **`ctrl_duty_cycle_scales_output_not_window`** — send `DutyCycle { on_fraction: 0.5,
   period_s: Some(900.0) }` to an `AirConditioner` and verify that the immediate-step
   cooling output is halved (current behavior). Document that `period_s` is unused. This
   pins the current semantic explicitly so any future change to window-based accounting is
   a deliberate test break.

2. **`speed_timer_resets_after_off_cycle`** — run two-speed AC at high speed for 600 s,
   turn off for one step, restart; assert `time_at_current_speed_s == 0.0` on the first
   on-step. Currently this test would fail (F-2).

3. **`heat_pump_heater_speed_timer_accumulates`** — run `HeatPumpHeater` in two-speed mode
   for several steps; assert `hvac.time_at_current_speed_s` increases each step. Currently
   this test would fail because `advance_speed_timer` is never called (F-2).

4. **`duty_cycle_zero_forces_off_immediately`** — apply `DutyCycle { on_fraction: 0.0 }` to
   an AC that the thermostat would otherwise run; assert `operating_mode == Off` and
   `electric_kw == 0.0`.

## Review Notes

`DutyCycle.period_s` exists in the type but is silently ignored by every equipment's
`apply_control_unchecked`. Dead field. No equivalent to OCHRE's `ext_ignore_thermostat`.
No `ext_mode_counters` reset mechanism.

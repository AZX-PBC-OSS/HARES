### HIGH

#### H1 — `tier_multiplier` is a point-in-time rate lookup, not a tiered-block accumulator; callers must implement accumulation themselves

**File:** `crates/hares-tariff/src/evaluator.rs:268`

`tier_multiplier(cumulative_kwh)` returns the rate for whichever tier `cumulative_kwh` falls into at the moment of the call. It does not compute the blended cost across tier boundaries. The method name implies a multiplier; the doc-comment is absent. If any caller calls this once per billing period with end-of-period kWh to compute total energy cost, the result is wrong — all kWh would be priced at the highest applicable tier rate, not split across tiers.

Currently `tier_multiplier` is not called outside its own test file (confirmed via grep). This means tiered block costs are **never actually applied to the energy bill** — `BillingState.cumulative_energy_cost_usd` is built from flat TOU `import_price` only (billing.rs:175), and no caller integrates the tiered cost. The `tiered_rates` field on `ElectricTariff` is populated and validated, but never used in the billing path.

**Evidence:**
- `billing.rs:175`: `self.cumulative_energy_cost_usd += import_kwh * import_price;` — uses TOU price only.
- No call site outside test file passes `billing_state.cumulative_import_kwh` to `tier_multiplier` and adds a delta charge.
- URDB parser at `urdb.rs:455-479` correctly builds `TieredBlock` entries, which are then silently ignored at billing time.

**Impact:** Any tariff with tiered/inclining block rates (very common in US residential tariffs, e.g., PG&E E-1, E-TOU-C baseline) will compute wrong energy costs — typically too low, because the upper-tier premium is never charged.

**Fix required:** Either:
1. In `BillingState::update`, compute marginal tiered cost for each interval by looking up the tier bracket the current cumulative falls in, or
2. In `step()` at period close, recompute total energy cost by walking the tiered block with the final `cumulative_import_kwh`. Option 2 is simpler and avoids calling tier logic per-interval.

The `tier_multiplier` method should be renamed to `tier_rate_at` or removed in favour of an internal helper, and a test must verify that a full billing period with cross-tier usage produces the correct blended bill.

#### H2 — Net metering minimum-charge interaction: minimum charge applies after export credit, not to gross charge

**File:** `crates/hares-tariff/src/billing.rs:301-305`

```rust
let raw = energy_charge_usd + demand_charge_usd + fixed_charge_usd - export_credit_usd;
let net_bill_usd = match minimum_charge {
    Some(min) if raw < min => min,
    _ => raw,
};
```

The current formula applies the minimum charge floor to the net amount (after export credit subtraction). Most US utility tariff rate schedules apply the minimum charge to the metered charges before netting export credits. Under California CPUC NEM 3.0 rules and the majority of state regulations, the monthly minimum/basic charge is not reduced by exported generation credits — it represents the minimum cost of grid access.

With the current code, a net-zero customer with a $10/month minimum charge and $15 of export credits against $8 of import charges gets: raw = 8 - 15 = -7, then clamped to $10. This is plausible for some tariffs but wrong for the majority that floor only the non-export charges. The correct formula for most tariffs is:

```rust
let metered = energy_charge_usd + demand_charge_usd + fixed_charge_usd;
let floored = match minimum_charge {
    Some(min) if metered < min => min,
    _ => metered,
};
let net_bill_usd = floored - export_credit_usd;
```

There is no `ExportMode`-specific path or tariff field to control this behavior. This is a modeling gap regardless of which convention is chosen — the current behavior is implicit and undocumented.

**Fix required:** Add a `minimum_charge_excludes_export: bool` field to `ElectricTariff` (defaulting to `true` to match regulatory majority), update `BillingPeriodSummary::new` accordingly, and add a test that exercises a net-exporting customer against a minimum charge floor.

### MEDIUM

#### M1 — `update()` double-records peak demand when `demand_period_idx == period_idx`

**File:** `crates/hares-tariff/src/billing.rs:180-190`

```rust
if let Some(slot) = self.period_peak_demand_kw.get_mut(period_idx as usize) {
    *slot = slot.max(avg);
}
if demand_period_idx != period_idx {
    if let Some(slot) = self.period_peak_demand_kw.get_mut(demand_period_idx as usize) {
        *slot = slot.max(avg);
    }
}
```

When `demand_tou_schedule` is empty (`demand_period_idx == period_idx` from evaluator.rs:145-146), the first branch already records the peak. The guard `demand_period_idx != period_idx` correctly prevents double-writing the same slot. However, the `period_peak_demand_kw` Vec is sized to `period_name_table.len()` (evaluator.rs:205), not to the number of distinct TOU periods. Index 0 is the empty "no match" sentinel. A step with no TOU match gets `period_idx = 0`, and its demand is accumulated into `period_peak_demand_kw[0]` — this slot is later queried if a demand rate name happens to resolve to index 0, which only occurs if the demand rate's `period_name` is the empty string. Validation rejects empty period names for demand rates, so this is a latent over-accumulation into a slot that is never read, rather than a billing error. It is still noise in the data structure.

No code fix is strictly required, but the intent should be documented and `period_peak_demand_kw[0]` should either be excluded or the sizing should reflect only named periods.

#### M2 — URDB `flatdemandstructure` season assignment is a hardcoded heuristic

**File:** `crates/hares-tariff/src/urdb.rs:500-513`

```rust
let season = match flat_demand.len() {
    1 => SeasonFilter::All,
    _ => match idx {
        0 => SeasonFilter::Summer,
        1 => SeasonFilter::Winter,
        _ => { ... SeasonFilter::All }
    },
};
```

URDB `flatdemandstructure` is a list of rate periods (indexed by period number, not by season). The outer-array index does not intrinsically map to summer/winter — it maps to a demand period number, analogous to how `energyratestructure` works. For tariffs with a single flat demand period that applies year-round (index 0), assigning `Summer` is wrong and will cause the demand charge to be excluded from winter billing.

The correct approach mirrors the energy rate path: pair the `flatdemandstructure` indices against a `flatdemandmonthschedule` (or equivalent) if present, and use `period_seasons` derived from the schedule matrices. If no schedule is present, `SeasonFilter::All` is the only safe default regardless of how many entries exist.

**Impact:** Any multi-period flat demand tariff will have wrong seasonal assignment for at least one demand rate.

#### M3 — `tier_multiplier` ignores the active `SeasonFilter` when multiple `TieredBlock` entries share a season

**File:** `crates/hares-tariff/src/evaluator.rs:271-286`

```rust
for block in &self.tariff.tiered_rates {
    if !block.season.contains_month(month) {
        continue;
    }
    for (i, threshold) in block.thresholds_kwh.iter().enumerate() {
        if cumulative_kwh < *threshold {
            return block.rates_per_kwh[i];
        }
    }
    return block.rates_per_kwh[block.thresholds_kwh.len()];
}
```

This returns on the first matching `TieredBlock` for the current month, regardless of which TOU period is active. A tariff with separate tiered blocks for on-peak and off-peak consumption within the same season (some California commercial tariffs) would apply the first matching block to all TOU periods. There is no `period_name` field on `TieredBlock`. This is a structural gap — if the use case is not intended to be supported, it should be explicitly documented and validated against (reject tariffs with multiple seasonal tiered blocks at parse/validate time).

### LOW

#### L1 — Billing period close triggered by `current_time >= period_end` but `current_time` is the end of the current interval

**File:** `crates/hares-tariff/src/evaluator.rs:321`

The contract (documented in `run_all_steps` test helper at line 806) passes `step_end` (end of interval) as `current_time`. Period close fires when `current_time >= period_end`. If the billing period boundary falls in the middle of an interval (e.g., period ends at midnight but the interval straddles midnight), the step that crosses the boundary is fully credited to the old period, and only the next step starts accumulating into the new period. This is a known approximation in interval-based billing and matches OCHRE's behavior, but it should be documented on the `step()` signature — the semantics of `current_time` (interval-end vs. interval-start vs. midpoint) are not stated.

#### L2 — `compute_period_end` for `BillingCycle::Monthly` starts a new period at the same day-of-month, but February 29 → March 29 drift is not detected

**File:** `crates/hares-tariff/src/billing.rs:96-114`

For a period starting on Feb 29 (leap year), `compute_period_end` correctly advances to March 29 (test at line 557 verifies this). However, for a subsequent period starting March 29, the next end would be April 29, not April 28 — this is correct calendar behavior. The clamping logic at line 105 (`start.day().min(max_day)`) only clamps when the next month is shorter than the current day, so Feb 29 → Mar 28 would occur if `max_day = days_in_month(year, next_month)` is computed against next-month. The current code computes `max_day = days_in_month(year, month)` where `year`/`month` are the **target** month — this is correct. Test coverage for this exists and passes. Low risk, no change needed; noted for completeness.

#### L3 — `DemandWindow` running sum periodic correction occurs every 1000 pushes regardless of window size

**File:** `crates/hares-tariff/src/billing.rs:41-43`

```rust
if self.push_count.is_multiple_of(1000) {
    self.running_sum = self.samples.iter().sum();
}
```

For a 15-minute window at 5-minute intervals (3 samples), floating-point drift accumulates for at most 3 samples before eviction resets the running sum implicitly. The 1000-push correction is conservative but harmless. For a 30-minute / 1-minute interval window (30 samples), a full correction every 1000 pushes is similarly adequate. No correctness concern; the period is chosen arbitrarily large relative to any realistic window size.

### MISSING TEST COVERAGE

The following scenarios have no dedicated test:

1. **Tiered billing end-to-end:** A full billing period where consumption crosses a tier boundary and the total energy charge is verified against hand-computed blended cost. (This would currently fail given H1.)

2. **`minimum_charge` with net-exporting customer:** Verify that a customer whose export credits exceed import charges still pays at least the minimum charge, and that the specific convention (pre- vs. post-export) is enforced. (Related to H2.)

3. **Multi-season tiered block:** A tariff with both Summer and Winter `TieredBlock` entries, verified to use the correct block at each season boundary.

4. **Billing period reset preserving `period_peak_demand_kw` history for all TOU periods:** The existing `billing_per_period_ratchet_applied` test covers one period; no test exercises rollover of all N TOU periods simultaneously.

5. **URDB flat demand with >2 entries:** Parser warns and assigns `SeasonFilter::All` to extra entries. No test verifies the demand rate is still accepted by `validate()` and applied correctly.

6. **Back-to-back billing period closes in a single simulation:** No test exercises a simulation spanning 3+ billing periods to verify `prior_peaks_kw` deque management across multiple resets.

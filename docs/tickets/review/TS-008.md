## Background/Context

HARES implements a full EnergyPlus `FullInteriorAndExterior` solar distribution model: beam-to-floor 60%, diffuse by area, per-surface absorptance, `radiation_frac` split between RC node and zone air. This is a significant subsystem not covered by any existing ticket.

## Investigation Instructions

1. **Read `solar.rs` end-to-end.** Document the solar distribution algorithm: what fraction of beam goes to floor vs other surfaces? How is diffuse distributed?
2. **Trace `radiation_frac` split:** What fraction of absorbed solar goes to the RC node vs zone air? Is this applied equally to transmitted solar and absorbed-inward heat?
3. **Verify `debug_assert!(win.shgc >= win.transmittance)`** — does this hold for all window types in the HPXML library?
4. **Compare with OCHRE's solar distribution** in `Models/Envelope.py`. Does OCHRE use the same EnergyPlus model or a simplified approach?
5. **Check GlazingCurve and IAM:** Verify incident angle modifier for beam and diffuse matches EnergyPlus formulation.

## Findings

### F1 — CRITICAL: OCHRE interior solar distribution is area×absorptance weighted, not beam-to-floor biased

**File:** `crates/hares-envelope/src/thermal_solver/solar.rs:10,214–246`

HARES uses a constant `BEAM_FLOOR_FRACTION = 0.60` (EnergyPlus FullInteriorAndExterior mode), splitting 60% of beam to floor surfaces and 40% to non-floor surfaces by area, then multiplying by per-surface solar absorptance.

OCHRE uses a fundamentally different model. It distributes all transmitted solar (beam+diffuse combined, already IAM-weighted) to all interior surfaces weighted by `area × absorptivity` (line `Envelope.py:551–553`):

```python
total_area_absorptivity = sum([s.area * s.absorptivity for s in window_view_surfaces])
s.window_view_factor = s.area * s.absorptivity / total_area_absorptivity
```

There is no beam-to-floor vs non-floor bifurcation in OCHRE. The OCHRE view factor already normalises by absorptance, so `factors[i] = transmitted_total * (area_i * absorptivity_i) / sum(area_j * absorptivity_j)` is the absorbed power directly — it does not apply a separate `solar_absorptance` multiplication downstream. HARES applies `solar_absorptance` as a post-distribution multiplier, then routes the remainder as reflected to zone air.

Consequence: for typical residential geometry (floor absorptance ≈ 0.60, walls ≈ 0.50), both approaches yield similar per-surface totals, but:
- HARES can lose energy when `floor_area = 0` (entire 60% beam share is silently dropped — see `beam_with_no_floors_loses_wall_beam_fraction` test which explicitly documents a 600 W loss).
- OCHRE never silently drops energy because the distribution is always over the full surface list.

The 60% beam-to-floor constant itself is an EnergyPlus default for residential single-zone models (EnergyPlus Engineering Reference, Solar Distribution section). It is a valid model, but it diverges from OCHRE's approach and can produce different zone temperatures when geometry is unusual (no explicit floor, all-wall enclosures, attics).

**Severity:** HIGH — diverges from the OCHRE reference model and silently drops energy for zones without floor surfaces.

### F2 — CRITICAL: OCHRE applies IAM correction to beam only and uses a fixed 0.854 diffuse factor; HARES uses per-curve diffuse IAM values

**File:** `crates/hares-physics/src/solar.rs:512–521`; OCHRE: `vendors/OCHRE/ochre/utils/envelope.py:125–126`

OCHRE applies a hard-coded `0.854` diffuse multiplier to `poa_diffuse` at the irradiance preprocessing stage, unconditionally for all glazing types (line 126):

```python
# TODO: Fudge factor for diffuse irradiance: EPlus transmitted diffuse solar is lower than expected
irr["poa_diffuse"] *= 0.854
```

HARES implements per-curve hemispherical-average IAM values derived from Lambertian integration: A=0.907, Bdcd=0.866, D=0.875, E=0.855, F=0.831, J=0.771. The EnergyPlus E-curve value (0.855) is essentially the same as OCHRE's 0.854, so for double-pane windows (the common residential case, curve E or F) the two models agree within 0.1–2.4%. For single-pane (curve A, IAM_diff=0.907) or triple-pane low-e (curve J, IAM_diff=0.771) windows, HARES will differ from OCHRE by up to 6.8%.

The HARES per-curve approach is more correct per the EnergyPlus specification. The OCHRE comment labels 0.854 a "fudge factor". No action required from a physics correctness standpoint, but parity tests against OCHRE for buildings with single-pane or low-e triple-pane windows will show a systematic diffuse-solar discrepancy.

**Severity:** MEDIUM — HARES is more accurate; impairs OCHRE parity for non-double-pane windows only.

### F3 — HIGH: OCHRE does NOT apply a beam-vs-diffuse IAM split at the transmittance multiplication stage; HARES does

**File:** `crates/hares-envelope/src/thermal_solver/solar.rs:24–33`; OCHRE: `vendors/OCHRE/ochre/utils/envelope.py:123`; `vendors/OCHRE/ochre/Models/Envelope.py:1159–1160`

HARES applies the angle-of-incidence (IAM) polynomial to beam and the diffuse IAM constant to diffuse, then multiplies each by `transmittance`:

```rust
let iam_beam = window_iam(irr.angle_of_incidence_rad, curve);
let iam_diffuse = curve.diffuse_iam();
let poa_beam = irr.direct_w_m2 * iam_beam;
let poa_diffuse = irr.diffuse_w_m2 * iam_diffuse;
let transmitted_beam_w = win.area_m2 * win.transmittance * poa_beam;
let transmitted_diffuse_w = win.area_m2 * win.transmittance * poa_diffuse;
```

OCHRE applies the IAM polynomial directly to `poa_direct` (multiplying the raw irradiance by the polynomial normalised at cos(0)=1), which equals `shgc_at_normal * iam_beam * poa_direct` because the transmittance already encodes the normal-incidence fraction. Then `transmitted_gain = solar_gain * surface.transmittance` where `surface.transmittance` is the fraction from `calculate_window_parameters` (EnergyPlus Step 4). This means OCHRE's transmitted gain for diffuse is `poa_diffuse * 0.854 * transmittance` while HARES computes `poa_diffuse * diffuse_iam * transmittance` — functionally equivalent for curve E.

For beam: OCHRE normalises the polynomial so that `dot(t_params, [1^i]) = 1.0`, meaning the polynomial IS the IAM (ratio T(θ)/T(0)), not the absolute transmittance. HARES calls `window_iam` which is normalised the same way and then multiplies by `transmittance`. The approach is mathematically equivalent. No defect.

**Severity:** INFORMATIONAL — models are mathematically equivalent.

### F4 — HIGH: `absorbed_inward` uses IAM-blended `poa_w_m2` (beam+diffuse) but IAM correction is not symmetric for the absorbed portion

**File:** `crates/hares-envelope/src/thermal_solver/solar.rs:41–42`

```rust
let absorbed_inward = (win.shgc - win.transmittance).max(0.0) * win.radiation_frac;
let absorbed_zone_w = win.area_m2 * absorbed_inward * poa_w_m2;
```

`poa_w_m2 = poa_beam + poa_diffuse` where both components have been IAM-corrected. Applying the same `absorbed_inward` coefficient to this blended total implicitly assumes the absorbed fraction is angularly invariant. Per EnergyPlus, the absorbed fraction `x = shgc - transmittance` is defined at normal incidence. At oblique angles, both SHGC and transmittance vary, and the absorbed fraction does not scale identically with the IAM polynomial. The EnergyPlus Simple Window Model (Step 5) applies the same polynomial-corrected gain to both transmitted and absorbed fractions, so this approach slightly over- or under-estimates the absorbed gain at large angles of incidence.

In OCHRE, `surface.solar_gain = solar_gain * absorptivity` where `solar_gain` is the IAM-corrected global (beam×IAM + diffuse×0.854) and `absorptivity = x / radiation_frac`. For windows with `n_nodes == 0`, this is routed directly as `h_radiation * radiation_frac` to zone heat (line 1151–1152). HARES applies the same formula: `(shgc - transmittance) * radiation_frac * poa_w_m2 * area`. The two are mathematically identical given the same inputs; this is not a defect vs OCHRE.

The angularly-invariant absorbed fraction is a known limitation of the EnergyPlus Simple Window Model and is consistent with how OCHRE uses it.

**Severity:** LOW — limitation inherited from EnergyPlus Simple Window Model; matches OCHRE behaviour.

### F5 — MEDIUM: `debug_assert!(win.shgc >= win.transmittance - 1e-6)` is debug-only and does not fire in release

**File:** `crates/hares-envelope/src/thermal_solver/solar.rs:35–40`

The assertion `win.shgc >= win.transmittance - 1e-6` is a `debug_assert!`, which is compiled out in release builds. The invariant `shgc >= transmittance` is guaranteed by `calculate_window_parameters` because it clamps `transmittance` to `shgc` via `.clamp(0.0, shgc)` (`crates/hares-physics/src/solar.rs:621`). However, if `WindowSolarProperties` is constructed outside that function (e.g. in tests or via Python bindings), the invariant could be violated silently in release.

The `.max(0.0)` guard on line 41 prevents negative `absorbed_inward`, but a violation will produce silent zero-absorption rather than a diagnostic. This should be a `#[cfg(test)]` assertion or an explicit `clamp` at the construction site.

Whether the invariant holds for all HPXML window types: yes, for windows constructed via `calculate_window_parameters` the clamp ensures it. The concern is only for windows constructed via other paths.

**Severity:** MEDIUM — silent wrong output in release if invariant violated via non-standard construction path.

### F6 — HIGH: `BEAM_FLOOR_FRACTION` energy is silently dropped when `floor_area = 0` or `nonfloor_area = 0`

**File:** `crates/hares-envelope/src/thermal_solver/solar.rs:219–225`

```rust
let incident = if s.is_floor && floor_area > 0.0 {
    beam_to_floors * (s.area_m2 / floor_area)
} else if !s.is_floor && nonfloor_area > 0.0 {
    beam_to_walls * (s.area_m2 / nonfloor_area)
} else {
    0.0   // <-- beam portion is lost
};
```

When `floor_area = 0`, the 60% beam-to-floor budget vanishes; it does not redistribute to non-floor surfaces. When `nonfloor_area = 0` (all-floor zone), 40% vanishes. The unit tests `beam_with_no_floors_loses_wall_beam_fraction` and `only_floors_loses_wall_beam_fraction` explicitly document this as expected behaviour, but this is an energy conservation violation at the zone level — the dropped energy is not credited to reflected-out, it simply disappears from the balance.

OCHRE never has this issue because it distributes to all surfaces by `area × absorptance` with no floor/non-floor split.

The only scenario where this matters in practice is zones where all interior surfaces are tagged as floors (e.g. an unconditioned crawlspace floor plate) or where no floor surfaces are registered (e.g. a slab-on-grade model where the floor is treated as a ground boundary with no interior face registered). It is not a concern for standard conditioned zone models.

**Severity:** HIGH — silent energy non-conservation for pathological zone geometries; tests acknowledge but normalise the behaviour.

### F7 — LOW: Step-4 U-factor threshold discrepancy vs OCHRE

**File:** `crates/hares-physics/src/solar.rs:612`; OCHRE: `vendors/OCHRE/ochre/utils/envelope.py:409`

OCHRE uses a hard threshold at U > 3.95 W/m²·K (no interpolation). HARES implements linear interpolation over 3.4–4.5 W/m²·K per the EnergyPlus specification. This is a deliberate improvement. For windows in the 3.4–4.5 band (common aluminium-frame double-pane), transmittance will differ by up to ~1% between HARES and OCHRE. Flagging as low severity for OCHRE parity awareness; HARES is more accurate.

**Severity:** LOW — HARES intentionally more accurate; parity deviation expected in interpolation band.

### F8 — HIGH: `radiation_frac` semantics differ between the window absorbed-inward path and the interior surface distribution path

**File:** `crates/hares-envelope/src/thermal_solver/solar.rs:41,125`; `crates/hares-physics/src/solar.rs:654–661`

There are two distinct uses of `radiation_frac` in the solar path:

1. **Window `radiation_frac`** (from `WindowSolarProperties`, computed by `calculate_window_parameters`): the inward-flowing fraction of absorbed solar energy for the glazing assembly. Defined as `N_i = (R_ext + R_glass/2) / (R_ext + R_glass + R_int)`. This is the EnergyPlus Step 5 quantity. Values typically 0.4–0.6 for double-pane.

2. **Interior surface `radiation_frac`** (from `InteriorSurfaceInfo`): fraction of surface temperature attributable to the RC node, defined as `R_film / (R_film + R_material)`. Used to split absorbed solar between the mass node and zone air. Values typically 0.1–0.9 depending on surface thermal mass.

These are correctly distinct quantities used in different contexts. The naming collision is a readability risk but not a functional defect. The OCHRE code uses `radiation_frac` for both as well (surface `radiation_frac` at line 254 is the thermal split; the window `radiation_frac` from `calculate_window_parameters` is the inward-flowing fraction). No defect.

**Severity:** INFORMATIONAL — naming collision is a maintenance risk but no functional error.

### F9 — MEDIUM: IAM polynomial normalisation: OCHRE uses raw polynomial (not normalised), HARES normalises to unity at θ=0

**File:** `crates/hares-physics/src/solar.rs:547–548`; OCHRE: `vendors/OCHRE/ochre/utils/envelope.py:123`

OCHRE evaluates `np.dot(t_params, [incidence_cosine**i for i in range(5)])` and multiplies `poa_direct` by this value. At θ=0, `cos(0)=1`, so the polynomial evaluates to `sum(t_params)`. For curve E the reversed coefficients are `[-0.002577, 1.51, 2.489, -5.873, 2.883]` and `sum = 1.0063`. HARES normalises: `raw / normal_incidence_raw`, so at θ=0 HARES returns exactly 1.0.

OCHRE does NOT normalise. The raw polynomial at normal incidence ≠ 1.0 for some curves (e.g. curve A: `sum = [-0.001474+3.355-3.852+1.486+0.0147] = 1.0022`). This means OCHRE's IAM slightly exceeds 1.0 at near-normal incidence for some curves — a minor inaccuracy. HARES normalisation is correct per EnergyPlus.

Quantitative impact: at θ=0, OCHRE overestimates IAM by ~0.2% (curve A) to ~0.6% (curve E). At oblique angles the normalisation has no effect on relative shape, only on the normal-incidence anchor.

**Severity:** LOW — HARES is more accurate; small OCHRE parity deviation at near-normal incidence.

## Recommended Tests

### T1 — Parity regression: all-floor zone must not lose beam energy
Construct a zone with only floor surfaces and assert that `sum(absorbed) + reflected == beam + diffuse`. This is currently violated (test `only_floors_loses_wall_beam_fraction` expects 640 W reflected from 1000 W beam input, accepting a 400 W loss). The test should be changed to either redistribute the orphaned beam fraction to floor surfaces or explicitly document this as out-of-scope for standard residential use.

### T2 — Parity regression: zone with no floors must not lose beam energy
Same energy conservation argument for the `beam_with_no_floors_distributes_to_walls` case. Currently 600 W of the 1000 W beam is silently lost. These tests normalise a known defect rather than catching it.

### T3 — Cross-model diffuse comparison: single-pane vs triple-pane
For GlazingCurve::A (single-pane) with OCHRE's fixed 0.854 and HARES' 0.907, assert the diffuse gain ratio is within expected bounds (0.907/0.854 ≈ 1.062). This documents the intentional deviation from OCHRE.

### T4 — Boundary value: `debug_assert` bypass in release
Construct a `WindowSolarProperties` with `shgc=0.3` and `transmittance=0.35` (violating the invariant) and verify that release-mode code does not produce negative `absorbed_zone_w` — the `.max(0.0)` guard should be verified. Better fix is a production assertion or construction-time clamp.

### T5 — IAM normalisation at θ=0 returns exactly 1.0 for all curves
Add a parameterised test that calls `window_iam(0.0, curve)` for all six GlazingCurve variants and asserts the result is exactly 1.0. This already exists as `window_iam_is_unity_at_normal_incidence` — confirm it passes for all curves.

### T6 — OCHRE-equivalent interior distribution: area×absorptance weighted
Add a test comparing HARES beam-to-floor distribution against the OCHRE area×absorptance formula for a standard residential zone (one floor, four walls, one ceiling). Document the expected difference so future parity investigations have a baseline.

### T7 — Multi-window zone: confirm `absorbed_zone_w` routes to correct zone air input
Integration test with two zones each having one window: verify that `absorbed_zone_w` from window A reaches zone A's air index and not zone B's, and vice versa.

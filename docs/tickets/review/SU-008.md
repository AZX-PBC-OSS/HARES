## Background/Context

HARES uses BA 2010 / ANSI/RESNET/ICC 301-2022 Addendum C schedule profiles for
lighting, MELs, occupancy, etc. This ticket audits whether those profiles are
correctly loaded and applied against OCHRE's reference implementation.

## Findings

### Finding 1 — CSV profiles are byte-identical to OCHRE (PASS)

`defaults/Default Schedule Parameters.csv` and
`vendors/OCHRE/ochre/defaults/Default Schedule Parameters.csv` are identical
(`diff` produces no output). All 88 rows are present: weekday fractions, weekend
fractions, and monthly multipliers for every equipment type that OCHRE supports.
Coefficient values are correct.

All profiles referenced by OCHRE's `SCHEDULE_NAMES["Power"]` mapping that have
entries in the CSV are loaded correctly into `DefaultScheduleProfile` by
`load_default_profiles` (`schedule_resolve.rs:237`).

No normalization defect: HARES does not require profiles to sum to exactly 1.0
(they are fractions, not probabilities); the observed sums range from ~0.98–1.02
which is consistent with the reference source data.

---

### Finding 2 — CRITICAL: Occupancy schedule not scaled by number of occupants

**Severity: High — incorrect internal heat gains for any household with ≠ 1 occupant.**

**OCHRE** (`schedule.py:449`):
```python
s_ochre = s_hpxml * occupancy["Number of Occupants (-)"]
```
The fraction column (0–1) is multiplied by the occupant count to produce a
person-count series (e.g. 3.0 persons at peak for a 3-person household).

**HARES** (`dwelling/mod.rs:1721–1728`): reads the raw schedule column value
directly as `n_occupants`. Because the ResStock CSV contains normalized fractions
(observed peak = 1.0 in `bldg0112631_schedule.csv`), a 3-person household
produces `n_occupants = 1.0` at peak occupancy instead of 3.0.

**Impact**: internal heat gains (`n_occupants × OCCUPANT_SENSIBLE_GAIN_W`,
`n_occupants × OCCUPANT_LATENT_GAIN_W`) are under-reported by a factor of
`number_of_occupants` for all realistic inputs. For a 3-person house this is a
3× under-count of occupancy gains, which affects envelope temperature trajectory
and HVAC load calculations.

**Fix**: In `inject_schedule_into_specs`, when the `occupants` column is present,
pre-scale it by `number_of_occupants` from the Occupancy spec before storing the
column index — or, alternatively, read `number_of_occupants` from the Occupancy
spec at dwelling init time and apply the multiplier in `apply_occupancy_gains`.
The Occupancy spec stores `number_of_occupants` at `resolve_loads.rs:32`.

### Finding 3 — CRITICAL: Water draw schedule column not scaled to L/min

**Severity: High — hot water draw is ~2 orders of magnitude too low when a
schedule CSV is provided.**

**OCHRE** (`schedule.py:362–366`, `convert_water_column`):
```python
annual_mean = avg_water_draw / 1440   # in L/min
schedule_mean = s_hpxml.mean()
max_value = annual_mean / schedule_mean if schedule_mean != 0 else 0
out = s_hpxml * max_value             # now in L/min
```
The fraction column is scaled by `(avg_l_per_day / 1440) / mean_fraction` to
produce actual L/min values.

**HARES** (`schedule_resolve.rs:467–513`, `inject_water_heater_schedule_columns`):
stores only the column index of the raw fraction column as
`draw_flow_rate_schedule_col`. The water heater runtime (`water_heater/mod.rs:72–75`,
`resolve_storage_step_inputs`) interprets the column value as L/min and divides
by 60 to convert to kg/s. For a typical fraction of ~0.04 this yields
`0.04 / 60 ≈ 0.00067 kg/s`, whereas the correct value for a 200 L/day house
with `mean_fraction ≈ 0.04` is `200/(1440×0.04)/60 ≈ 0.058 kg/s` — a factor
of ~87 too low.

The `avg_water_draw_l_per_day` parameter is correctly computed and stored in the
water heater spec (`resolve_water_heater.rs:79–80`) but is not used when a
schedule column is present.

**Fix**: `inject_water_heater_schedule_columns` must pre-multiply the fraction
column by `(avg_l_per_day / 1440) / mean_fraction` to produce a L/min series
and store either a derived column or the scale factor. Alternatively, pass
`avg_water_draw_l_per_day` into the water heater config so `resolve_storage_step_inputs`
can apply the scaling when reading the column.

### Finding 4 — MEDIUM: `Freezer` has no default-profile fallback

**Severity: Medium — affects only the no-schedule-CSV code path; normal
operation with a ResStock CSV is unaffected.**

In `Default Schedule Parameters.csv`, the `freezer` rows have OCHRE Name `N/A`,
so they are filtered out when HARES loads default profiles (line 260:
`if ochre_name == "N/A" { continue }`). HARES's `COLUMN_MAPPINGS` maps
`freezer` → `"Freezer"` (`Power` category), but `profiles.get("Freezer")` will
always return `None` when falling back, causing `determine_constant_kw` to be
used with a `warn!` that labels the result potentially incorrect.

OCHRE has the same limitation (the Python code would fail to look up `"Freezer"`
in `df_default` and raise an exception). In practice both tools always receive a
`freezer` column from ResStock, so this is latent. The correct fix is to copy
the Refrigerator profile under the `"Freezer"` key when loading defaults, which
matches the BA 2010 source data intention.

### Finding 5 — MEDIUM: Missing `lighting_basement` fallback from `lighting_interior`

**Severity: Medium — affects buildings with a basement when the schedule CSV
does not provide a separate `lighting_basement` column.**

**OCHRE** (`schedule.py:390–392`):
```python
if "Basement Lighting" in equipment and "lighting_basement" not in df_norm and "lighting_interior" in df_norm:
    df_norm["lighting_basement"] = df_norm["lighting_interior"]
```
When the CSV has no `lighting_basement` column, OCHRE falls back to
`lighting_interior` fractions.

**HARES**: no equivalent logic. When `lighting_basement` is absent from the CSV,
`inject_power_schedule` falls through to either the default profile (which is
identical to `Indoor Lighting` in the CSV anyway) or a constant power warn. The
actual profile coefficients would be correct in the default-profile fallback
path, but the explicit column copy is absent, creating a divergence if a
building has `Basement Lighting` equipment but no `lighting_basement` schedule
column.

### Finding 6 — LOW: `hot_water_clothes_washer` / `hot_water_dishwasher` not processed

**Severity: Low — appliance water-demand contribution is not separated.**

OCHRE defines a `Water` category mapping:
- `hot_water_clothes_washer` → `Clothes Washer` (L/min)
- `hot_water_dishwasher` → `Dishwasher` (L/min)

These are used to compute appliance-sourced hot water demand separately from
fixture draws. HARES has no `Water` category and does not process these columns.
The appliance water draw currently enters via the `appliance_demand_kg_s` path
only when appliance equipment emits it directly (not from schedule columns).
This is a parity gap for detailed water-draw accounting.

---

### Finding 7 — LOW: Analytical `annual_mean_fraction` uses approximate 5:2 day weighting

**Severity: Low — affects only the default-profile fallback path (no CSV column).**

`annual_mean_fraction` (`schedule_resolve.rs:335–351`) computes the annual mean
fraction analytically using a fixed 5 weekday / 2 weekend ratio per week:
```rust
let hourly_mean = (5.0 * weekday_mean + 2.0 * weekend_mean) / 7.0;
```
OCHRE computes `schedule_mean` from the actual 8760-length time series generated
by `create_simple_schedule`, which uses the true calendar distribution of
weekdays and weekends for the simulation year. The true distribution deviates
slightly from 5:2 depending on the year's starting day. The error is bounded by
the weekday/weekend difference in profile means, which is ≤ 1–2% for most
equipment types. This is negligible for the default-profile fallback path but
documented for completeness.

---

### Finding 8 — LOW: Case-sensitivity gap for mixed-case CSV column names

**Severity: Low — only affects unusual inputs with non-lowercase column headers.**

`normalize_column_name` in `schedule.rs:633` only collapses internal whitespace;
it does NOT lowercase. `normalize_schedule_col_name` in `schedule_resolve.rs:818`
does lowercase (via `normalize_ascii`). If a schedule CSV provides headers like
`"Vacancy"`, `"Power Outage"`, or `"No Space Heating"` (title case, as seen in
`bldg0112631_schedule.csv`), the schedule's `column_index` keys will be
title-case, but `csv_col_map` lookups use lowercase. Since these are all `Ignore`
category, the practical effect is that HARES silently ignores them without any
warning, which is the intended behavior — but it means the `Ignore` entries in
`COLUMN_MAPPINGS` cannot reliably silence warnings for title-case column names
from older OCHRE output files. ResStock output is lowercase so this is minor.

## Recommended Tests

1. Unit test: inject an `occupants` column with value 0.5 and a spec with
   `number_of_occupants = 4`; assert `apply_occupancy_gains` computes
   `n_occupants = 2.0` (i.e. 0.5 × 4).

2. Unit test: inject a `hot_water_fixtures` column with fraction series, an
   `avg_water_draw_l_per_day = 200` water heater spec; assert the resolved
   `draw_flow_rate_kg_s` at each step equals `fraction × (200/1440/mean_fraction) / 60`.

3. Regression test: run a 48h simulation for `cz4a_ashp_hpwh` (ResStock schedule
   included) and assert hot water draw is non-trivially > 0 (would catch finding 3).

4. Regression test: run the occupancy-gains path with a 3-person HPXML and assert
   sensible gains are 3× the single-person baseline (would catch finding 2).

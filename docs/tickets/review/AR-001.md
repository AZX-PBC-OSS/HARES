## Background/Context

HARES telemetry uses `HashMap<String, f64>` with string keys like `"power_kw"`,
`"delivered_w"`, `"cop"`. These magic strings are the #1 source of wiring bugs:
misspellings, inconsistent naming, keys that exist in one equipment type but not
another, keys that change name between versions. A typo in a telemetry key is
silent — no compile error, no runtime error, just missing data.

## Investigation Instructions

1. **Inventory all telemetry keys across all equipment types:**
   - Read each equipment's `telemetry()` method.
   - List every string key inserted into the HashMap.
   - Check for inconsistencies: does HVAC use `"power_kw"` while battery uses
     `"electric_power_kw"`? Does WH use `"cop"` while HVAC uses `"COP"`?

2. **Inventory all telemetry key consumers:**
   - Where are telemetry keys read? In Python? In output? In actors?
   - Are the reader's expected keys guaranteed to match the writer's actual keys?

3. **Check `EquipmentDescriptor.telemetry_fields`:**
   - Does each equipment declare its fields accurately?
   - Could a compile-time or init-time check verify that `telemetry()` only returns
     keys declared in `telemetry_fields`?

4. **Assess type safety opportunities:**
   - Could telemetry keys be an enum? A `&'static str` constant module?
   - Could `Telemetry` be a typed struct per equipment category instead of HashMap?
   - What is the cost/benefit of each approach?
   - Could the `uom` crate be used to tag values with units at the type level?

5. **Document all inconsistencies found** and recommend a concrete migration path.

## Recommended Tests

The following tests are missing or insufficient:

1. **Lifecycle tests for all water heater types (resistance, gas, HPWH, tankless):**
   `crates/hares-equipment/tests/lifecycle.rs` only covers `ScheduledLoad`, `Battery`,
   and `Gas Furnace`. Each water heater type must have a lifecycle test that asserts
   `telemetry.len() == descriptor.telemetry_fields.len()`. This would immediately
   catch the undeclared `tank_node_N_c` and `skin_loss_w` keys (see BUG-3 below).

2. **Key consistency cross-check test:**
   A test that asserts the same key is never written with two different names across
   equipment types (e.g., `"compressor_kw"` vs `"compressor_power_w"`, `"fan_kw"` vs
   `"fan_electric_w"` vs `"fan_power_w"`). This should live in
   `crates/hares-equipment/tests/` as a parametrized test over all registered equipment.

3. **Power key reachability test:**
   A test that instantiates each registered equipment type, steps it once under
   conditions that produce non-zero power, and asserts that the 3-chain fallback in
   `dwelling/mod.rs:1543` (`"electric_kw"`, `"active_power_kw"`, `"ac_power_kw"`)
   resolves to a non-zero value. Generator fails this test today (uses
   `"electric_output_kw"`).

4. **Mode key test:**
   A test that asserts `equipment.telemetry().get("mode")` returns `Some(_)` for any
   equipment that should contribute to `DwellingTelemetry.equipment_modes`. Today every
   equipment would return `None`.

5. **`"dr_active"` undeclared key test:**
   A test that asserts the battery's `telemetry_fields` includes every key read by any
   actor that inspects `equipment_telemetry`. Specifically, `BatteryManagementActor`
   reads `"dr_active"` which is never declared.

### BUG-1: `"mode"` key never written; `DwellingTelemetry.equipment_modes` always 0

**Severity: BUG — silent data loss in every output**

`crates/hares-core/src/dwelling/mod.rs:1535`:
```rust
equipment_modes.push(telemetry.get("mode").unwrap_or(0.0));
```

`crates/hares-core/src/dwelling/mod.rs:2264`:
```rust
row[idx] = telem.get("mode").unwrap_or(0.0);
```

No equipment anywhere writes a telemetry key named `"mode"`. Every equipment uses
`"operating_mode"`. The `DwellingTelemetry.equipment_modes` field and the CSV mode
column are always 0.0 regardless of actual equipment operating state. OCHRE writes
`"{name} Mode"` as a string (e.g., `"Off"`, `"On"`); HARES opted for a numeric code
but chose the wrong key name at the reader side. This is a complete wiring miss.

**Fix:** Change `dwelling/mod.rs:1535` and `dwelling/mod.rs:2264` to read
`"operating_mode"` instead of `"mode"`.

### BUG-2: Generator `"electric_output_kw"` missing from power fallback chain — power never written to CSV

**Severity: BUG — generator electric power is always 0.0 in output CSV**

`dwelling/mod.rs:2246-2259` falls back through `"electric_kw"`, `"active_power_kw"`,
`"ac_power_kw"`. Generator writes `"electric_output_kw"` — none of the fallbacks
match. Generator electric power is always reported as 0 kW in the output CSV.

Similarly, `dwelling/mod.rs:1543-1551` (equipment_power_kw in DwellingTelemetry)
has the same gap. Generator power is always 0 in `DwellingTelemetry.equipment_power_kw`.

**Fix:** Add `"electric_output_kw"` to both fallback chains, or normalize generator
to write `"electric_kw"` like most other generation equipment.

### BUG-3: Tank-based water heaters (gas, HPWH) write undeclared keys; debug_assert fires

**Severity: BUG — fires debug_assert in debug builds; key count mismatch breaks lifecycle enforcement**

`crates/hares-equipment/src/water_heater/gas.rs:157-161` and
`heat_pump_wh.rs` both call `tank.register_node_telemetry(&mut t)` at init, which
calls `telemetry.insert(key, temp)` for N node temperature keys (`tank_node_0_c`,
`tank_node_1_c`, ...) and `skin_loss_w`. These keys are added at runtime but are not
listed in `telemetry_fields()`.

Consequence 1: The lifecycle test assertion
(`lifecycle.rs:105-112`: `telemetry.len() == descriptor.telemetry_fields.len()`)
would fail if gas WH or HPWH had lifecycle tests. Currently they do not, so this
is undetected.

Consequence 2: On subsequent steps `update_node_telemetry` calls `telemetry.set(key, temp)`
for `tank_node_N_c` and `skin_loss_w`. For gas WH and HPWH, `skin_loss_w` is NOT in
`default_telemetry()` (the pre-populated map), so `Telemetry::set` hits the
`debug_assert!(false, "Telemetry::set called with unknown key '{key}'")` path in debug
builds, then falls back to `HashMap::insert`. In release builds this is silent.

The resistance WH also has this issue: `default_telemetry()` has 6 pre-populated keys,
`tank.register_node_telemetry()` adds N+1 more via `insert`, but then subsequent steps
call `update_node_telemetry` which uses `set`. The `set` call works for the node temp
keys (already inserted at init) but `skin_loss_w` is also inserted at init so it works
there too. The mismatch is that `telemetry_fields()` declares 7 keys but the actual
map has 7 + N_nodes keys.

**Fix:**
- Add per-node temperature keys and `skin_loss_w` to the `telemetry_fields()` for
  gas WH and HPWH, generated dynamically based on `tank.telemetry_key_count()`.
- Pre-populate `skin_loss_w` in `default_telemetry()` for gas WH (it is already
  pre-populated for resistance WH and HPWH via `register_node_telemetry` at init).

**Severity: BUG — undeclared key read from actor; will always miss in production**

`crates/hares-core/src/actors/bms.rs:462`:
```rust
if let Some(&flag) = telemetry.0.get("dr_active") {
```

The `BatteryManagementActor` reads `"dr_active"` from equipment telemetry. This key

This may be intentional legacy scaffolding, but it is undocumented and the key is
not in the contract (not declared in `telemetry_fields`). If it is meant to be used,
it must be declared; if it is dead, it must be removed.

### GAP-1: Dehumidifier uses `"electric_power_w"` (Watts); dwelling power fallback never matches

**Severity: BUG (data loss) / naming inconsistency**

Dehumidifier writes `"electric_power_w"` (Watts). The dwelling power fallback chain
at `dwelling/mod.rs:1543-1551` tries: `"electric_kw"`, `"ac_power_kw"`,
`"active_power_kw"`, `"electric_power_kw"`, `"power_kw"`, `"net_power_kw"`.

None of these match `"electric_power_w"`. Dehumidifier power is always reported as
0 kW in `DwellingTelemetry.equipment_power_kw` and in the output CSV.

Additionally, `"electric_power_kw"` is in the fallback chain as a candidate but is
never written by any equipment — it is a dead fallback. The fallback chain has
accumulated entries over time without any cross-equipment verification that each
entry is actually written somewhere.

**Fix:** Normalize dehumidifier to write `"electric_kw"` (kW) to match all other
HVAC equipment, or add `"electric_power_w"` to the dwelling fallback with a W→kW
conversion. The former is cleaner.

### GAP-2: Three dead fallback candidates in dwelling power resolution

**Severity: IMPROVEMENT — dead code hides the real resolution logic**

`dwelling/mod.rs:1543-1551`:
```rust
telemetry.get("electric_kw")
    .or_else(|| telemetry.get("ac_power_kw"))
    .or_else(|| telemetry.get("active_power_kw"))
    .or_else(|| telemetry.get("electric_power_kw"))   // never written
    .or_else(|| telemetry.get("power_kw"))             // never written
    .or_else(|| telemetry.get("net_power_kw"))         // never written
    .unwrap_or(0.0)
```

No equipment writes `"electric_power_kw"`, `"power_kw"`, or `"net_power_kw"`. These
are dead fallbacks that make the resolution logic appear more robust than it is.

Similarly `dwelling/mod.rs:1540`: `telemetry.get("state_of_charge")` — no equipment
writes this key. Only `"soc"` is used.

**Fix:** Remove dead fallbacks after verifying no consumer depends on them.

### GAP-3: Inconsistent unit suffix conventions for compressor power

**Severity: IMPROVEMENT — reader confusion, cross-equipment API incoherence**

| Equipment | Key | Unit |
|-----------|-----|------|
| AirConditioner | `"compressor_kw"` | kW |
| HeatPumpHeater | `"compressor_kw"` | kW |
| HeatPumpWH | `"compressor_power_w"` | W |

HVAC uses `"compressor_kw"` (kW), HPWH uses `"compressor_power_w"` (W). A Python
consumer iterating over equipment telemetry would need to know the equipment type to
interpret the compressor power value. The project memory requires SI units internally
(watts), so `"compressor_kw"` in HVAC violates this policy.

### GAP-5: `"electric_kw"` key name violates SI-unit policy for several equipment types

**Severity: IMPROVEMENT — policy violation**

Per project memory (feedback_si_units.md): HARES must store and compute in SI units
internally. Multiple equipment types write `"electric_kw"` (kilowatts) rather than
`"electric_w"` (watts). Affected: ScheduledLoad, Ventilation, Furnace, Boiler,
Baseboard, HeatPumpHeater, AirConditioner, ResistanceWH, GasWH, HPWH. This is
widespread but consistent within itself. The policy should be enforced either by
renaming all these keys to `"electric_w"` or by establishing kW as the accepted
exception for grid-boundary power values (which is common in power systems).

### GAP-6: EventLoad uses `"active_power_kw"` while ScheduledLoad uses `"electric_kw"`

**Severity: IMPROVEMENT — inconsistent naming for the same quantity across load types**

Both EventLoad and ScheduledLoad represent electrical plug loads. They are both
`EndUse::PLUG_LOADS` (or similar). EventLoad writes `"active_power_kw"` (matching
Battery/EV naming); ScheduledLoad writes `"electric_kw"` (matching HVAC naming).
The dwelling power fallback chain handles both, but Python consumers cannot use a
uniform key to read load power.

### Assessment: `Telemetry::set` debug_assert is insufficiently enforced

`crates/hares-types/src/telemetry.rs:31-41`:

```rust
pub fn set(&mut self, key: &str, value: f64) {
    if let Some(v) = self.0.get_mut(key) {
        *v = value;
    } else {
        debug_assert!(
            false,
            "Telemetry::set called with unknown key '{key}'; ..."
        );
        self.0.insert(key.to_owned(), value);  // silent fallback in release
    }
}
```

The `debug_assert!` only fires in debug builds. In release builds, undeclared keys
are silently inserted. This means the correctness guarantee only exists during
development. The review note asks whether this should be a hard error. Given that
BUG-3 already shows this path is being hit (gas WH and HPWH call `set` on keys
pre-inserted via `register_node_telemetry` but not in `default_telemetry`), a
hard error would immediately surface BUG-3 in CI.

**Recommendation:** Make the `else` branch `panic!` in both debug and release
(`cfg!(not(test))` guard if test flexibility is needed). This is a programming
error — pre-population via `insert` at init time is the contract.

### Assessment: `EquipmentDescriptor.telemetry_fields` is mostly accurate but structurally incomplete for tank-based equipment

`TelemetryField` carries `name`, `unit`, and `description` but has no compile-time
link to the actual keys written by `step()`. The only enforcement is:

1. The lifecycle test count assertion (line 105-112), which only covers equipment
   types with lifecycle tests (currently ScheduledLoad, Battery, Gas Furnace).
2. Optional per-type spot-check tests (e.g., PV's `telemetry_fields_include_all_set_channels`).

For tank-based water heaters, `telemetry_fields()` returns a static `Vec` but the
actual map is larger by N tank nodes + 1 (`skin_loss_w`). There is no mechanism
to reconcile this at init time.

### Assessment: Type safety alternatives

**Option A: `&'static str` constant module per equipment type**

```rust
// crates/hares-equipment/src/battery/keys.rs
pub const SOC: &str = "soc";
pub const ACTIVE_POWER_KW: &str = "active_power_kw";
pub const OHMIC_LOSS_W: &str = "ohmic_loss_w";
// ...
```

Pros: Zero runtime cost; `grep`-able; find-all-references works; eliminates
typos in the writer. Cons: Readers (actors, dwelling layer) still use string
literals unless they import the constants too. Cross-crate constant sharing requires
exporting from `hares-types` or `hares-equipment`. This is the lowest-friction
migration path.

Battery already does this for config keys (`KEY_HEATER_POWER_W`, etc.) but not for
telemetry keys.

**Option B: Per-equipment-category typed struct**

```rust
pub struct HvacTelemetry {
    pub electric_kw: f64,
    pub thermal_output_w: f64,
    pub cop: f64,
    pub operating_mode: OperatingModeCode,
    // ...
}
```

Pros: Full type safety; units embedded in field type; no HashMap lookup cost in hot
loop; uom integration possible. Cons: Equipment types differ significantly (dehumidifier,
boiler, heat pump are all "HVAC" but have different fields). Would require polymorphic
return from `telemetry()` — either `enum TelemetryPayload` or a trait object. The
current `HashMap<String, f64>` allows Python consumers to iterate all fields without
knowing the equipment type. This is the highest-value but highest-effort approach.

**Option C: Enum key type (project-wide)**

```rust
pub enum TelKey {
    Soc,
    ActivePowerKw,
    ElectricKw,
    OperatingMode,
    Cop,
    // ...
}
```

`Telemetry` becomes `HashMap<TelKey, f64>`. Pros: Typos caught at compile time.
Cons: Every cross-language serialization (Python dict keys, CSV column names)
must convert `TelKey → String`. Enum is not extensible by user Python code (a
design requirement per `project_python_extensibility.md`). Not recommended.

**Option D: `uom`-tagged values**

Replace `f64` values with `uom` quantities. Pros: Unit mismatch caught at compile
time (e.g., `"compressor_kw"` kW vs `"compressor_power_w"` W issue in GAP-3
becomes impossible). Cons: `HashMap<String, uom::si::f64::Power>` would constrain
all values to the same unit dimension — but telemetry contains dimensionless values
(COP, SHR, runtime_fraction), temperatures (°C), flow rates (kg/s), etc. A
`HashMap<String, DimensionfulScalar>` would require an enum-variant type. Very
high complexity for this use case.

**Recommended migration path (incremental):**

1. **Immediate:** Fix BUG-1 (`"mode"` → `"operating_mode"`), BUG-2 (generator
   power), BUG-3 (tank WH undeclared keys), BUG-4 (`"dr_active"`), GAP-1
   (dehumidifier key).
2. **Short-term:** Introduce `&'static str` constants in `hares-types/src/telemetry_keys.rs`
   for the shared cross-equipment keys (`ELECTRIC_KW`, `ACTIVE_POWER_KW`, `AC_POWER_KW`,
   `SOC`, `OPERATING_MODE`, `COP`, `FUEL_INPUT_W`). Use these constants in both writers
   and readers (dwelling fallback chains, actors).
3. **Short-term:** Make `Telemetry::set` hard-panic on unknown key (not just
   `debug_assert!`). Add lifecycle tests for all water heater types.
4. **Medium-term:** Normalize unit suffix conventions: watts for power values in
   equipment-internal telemetry (renames `"compressor_kw"` → `"compressor_w"`,

### OCHRE comparison

OCHRE (`vendors/OCHRE/ochre/Equipment/Equipment.py:288-304`) uses dynamic
string formatting (`f"{self.results_name} Electric Power (kW)"`) so keys are
always unique per equipment instance. HARES uses generic keys like `"electric_kw"`
without equipment name prefixes — this is intentional (one equipment per slot in
the map) but means the equipment name context is external. OCHRE's `Mode` field
(`f"{self.results_name} Mode"`) writes a string like `"Off"` or `"Heating"`.
HARES writes numeric codes under `"operating_mode"`, but the reading side uses
`"mode"` — a mismatch that has no analogue in OCHRE because OCHRE's Python
attributes and output keys are the same object.

## Background/Context

OCHRE schedule CSVs contain normalized 0–1 fractions. `import_occupancy_schedule()`
converts these to physical units: lighting fractions × rated kW → actual kW, hot water
fractions × daily draw L/min → actual L/min, occupancy fractions × n_occupants →
persons, setpoint fractions → °C. HARES must do the same conversion or equipment will
receive unitless fractions instead of physical values.

## Findings

### FINDING 1 — CRITICAL: `hot_water_fixtures` fraction column is NOT converted to L/min before being stored as `draw_flow_rate_schedule_col`

**Severity:** Critical — water heater draw is orders of magnitude wrong when a ResStock schedule CSV is provided

**Files:**
- `crates/hares-io/src/schedule_resolve.rs:467–513` (`inject_water_heater_schedule_columns`)
- `crates/hares-equipment/src/water_heater/mod.rs:71–76` (`resolve_storage_step_inputs`)
- `crates/hares-io/src/draw_profile.rs:46–69` (`normalize_draw_profile`)

**Description:**

`inject_water_heater_schedule_columns` (schedule_resolve.rs:467) finds the `hot_water_fixtures` column and records only its integer column index in `draw_flow_rate_schedule_col`. No scaling or normalization is applied at this stage. The raw fractional values (range 0–1) remain in the schedule array at that column index.

At runtime, `resolve_storage_step_inputs` (water_heater/mod.rs:71–76) reads from `draw_l_per_min_source` and converts with:

```rust
(draw_l_per_min / 60.0).max(0.0)   // L/min → kg/s
```

This treats the schedule column value as already being in L/min. Because the column still contains raw fractions (0–1), the draw rate computed is `fraction / 60 kg/s`, which for a typical fraction of 0.1 is `0.00167 kg/s` — roughly 0.1 L/min — rather than the correct ~5–20 L/min for active draw.

**OCHRE reference** (`vendors/OCHRE/ochre/utils/schedule.py:349–369`):
```python
def convert_water_column(s_hpxml, ochre_name, equipment):
    avg_water_draw = properties.get("Average Water Draw (L/day)", 0)
    annual_mean = avg_water_draw / 1440  # in L/min
    schedule_mean = s_hpxml.mean()
    max_value = annual_mean / schedule_mean if schedule_mean != 0 else 0
    out = s_hpxml * max_value
    out.name = f"{ochre_name} (L/min)"
    return out
```

OCHRE produces a column in **L/min** by multiplying each fraction by `(avg_l_per_day / 1440) / mean_fraction`. The equivalent function `normalize_draw_profile` already exists in `crates/hares-io/src/draw_profile.rs:46–69`, but it is **never called** from `inject_water_heater_schedule_columns`.

**Impact:** A 3-bedroom home with avg draw of ~228 L/day has `annual_mean = 228/1440 ≈ 0.158 L/min` and a typical mean fraction of ~0.1, giving `max_value ≈ 1.58 L/min`. Actual L/min values should range from 0 to ~10 L/min during active use. HARES instead passes raw fractions (0–1) as if they were L/min, so the draw is underscaled by a factor of roughly `1.58 / mean_fraction × 60 ≈ 950×`. Water heater tanks will never deplete and thermal energy balance will be essentially wrong across all storage WH types.

**Fix required:** In `inject_water_heater_schedule_columns`, instead of injecting only the raw column index, create a derived column where each fraction value is scaled by `(avg_water_draw_l_per_day / 1440) / mean_fraction` (matching OCHRE). The `avg_water_draw_l_per_day` is already parsed from HPXML and stored in the spec parameters (resolve_water_heater.rs:79–80). Use `normalize_draw_profile` from `draw_profile.rs` and append a derived column as is done for power loads, then point `draw_flow_rate_schedule_col` at the derived column. The derived column should contain values in L/min (not kg/s) since `resolve_storage_step_inputs` applies the `/60` conversion at step time.

### FINDING 2 — MODERATE: `mean_fraction` for power schedule normalization uses simulation-window mean, not annual mean

**Severity:** Moderate — produces incorrect `max_kw` for sub-annual simulations; exact full-year runs are unaffected

**File:** `crates/hares-io/src/schedule_resolve.rs:547–548` (`inject_power_schedule`)

**Description:**

When a CSV column exists, `inject_power_schedule` computes:

```rust
let mean_fraction: f64 =
    fraction_series.iter().copied().sum::<f64>() / fraction_series.len() as f64;
```

This is the mean over only the rows present in the simulation window, not the annual mean. The normalization formula is:

```rust
Some((annual_kwh / 8760.0) / mean_fraction)
```

If `annual_kwh` is the full-year energy, dividing by the simulation-window mean gives a `max_kw` that preserves energy for the simulation window but not for the annual total. For a summer-only simulation of a load with a summer-heavy profile, the mean fraction is higher than annual, so `max_kw` will be underestimated, and simulated power will be lower than expected.

**OCHRE reference:** OCHRE always uses the full-year fraction mean (computed from the annual schedule) as the denominator, regardless of simulation duration. The comment in schedule_resolve.rs:328–333 (`annual_mean_fraction`) correctly notes this requirement for the default-profile branch, but the CSV branch does not apply it.

**Note:** The `annual_mean_fraction` function and the `DefaultScheduleProfile` path correctly compute a full-year weighted mean (schedule_resolve.rs:335–351), but this logic is only used when falling back to default profiles. The live CSV branch at line 547 uses the window mean.

**Fix required:** When the simulation uses a sub-annual schedule, `mean_fraction` in the CSV branch should be computed over the full annual dataset, or the comment should clearly document the known approximation. If the schedule file always covers a full year (8760 rows), this is a non-issue in practice, but it should be validated and documented.

### FINDING 3 — LOW: `determine_constant_kw` fallback divides by 8760 regardless of timestep resolution

**Severity:** Low — the fallback path is already flagged as potentially incorrect; this adds a unit note

**File:** `crates/hares-io/src/schedule_resolve.rs:673–685` (`determine_constant_kw`)

**Description:**

```rust
fn determine_constant_kw(spec: &EquipmentSpec) -> Option<f64> {
    ...
    .map(|kwh| kwh / 8760.0)
}
```

The divisor 8760 is correct only for non-leap-year annual schedules sampled at hourly resolution. For sub-hourly schedules (e.g., 15-minute, i.e., 35040 timesteps) or leap years (8784 hours), the constant kW derived from `annual_kwh / 8760` is approximately correct because it is a constant power that, when integrated over a year, yields `annual_kwh`. The 8760 is the annual hours count, so this is actually correct as an annual average — it does not depend on timestep resolution. The constant represents average power, not per-step energy. No bug, but the fallback code emits a loud "THIS MAY BE INCORRECT" warning, which is appropriate.

### FINDING 4 — LOW: `hot_water_delivered_l_min` column alias accepted but not documented as pre-scaled

**Severity:** Low — ambiguous contract may cause silent double-scaling if a caller ever passes a pre-scaled L/min column under this name

**File:** `crates/hares-io/src/schedule_resolve.rs:471–481`

**Description:**

`inject_water_heater_schedule_columns` accepts `hot_water_delivered_l_min` as a column name alias alongside `hot_water_fixtures`. The name implies the column is already in L/min, but `inject_water_heater_schedule_columns` passes all aliases to the same raw column-index injection path with no conversion. If `hot_water_fixtures` fractions are eventually fixed to be scaled (Finding 1), the code must conditionally skip normalization for columns that are pre-scaled (i.e., `hot_water_delivered_l_min`). The current code makes no distinction.

**Fix required:** After Finding 1 is fixed, ensure that `hot_water_delivered_l_min` columns bypass the fraction-to-L/min scaling step. The cleanest approach is to track whether a column is already in physical units during alias resolution.

### FINDING 5 — LOW: `mean_fraction == 0` guard in CSV branch silently produces `max_kw = 0`

**Severity:** Low — correct fail-safe behavior but produces silent zero-load equipment with no diagnostic

**File:** `crates/hares-io/src/schedule_resolve.rs:550–553`

**Description:**

```rust
let Some(max_kw) = determine_max_kw(spec, mean_fraction) else {
    inject_compact_constant_power(spec, 0.0);
    return;
};
```

`determine_max_kw` returns `None` when `mean_fraction <= 0.0`, which causes the equipment to be silently injected as a 0 W constant load. No `warn!` is emitted in this branch (contrast with the default-profile fallback which logs "THIS MAY BE INCORRECT"). A schedule column that is entirely zeros for the simulation window would cause this silently.

**Fix required:** Emit a `tracing::warn!` when `mean_fraction == 0.0` causes fallback to 0 W, naming the equipment and CSV column so the operator knows why the load is dead.

## Conversion Summary

| Schedule column | HARES conversion | OCHRE conversion | Match? |
|---|---|---|---|
| `lighting_interior`, `plug_loads_other`, etc. (Power category) | fraction × `(annual_kwh/8760) / mean_fraction` → derived kW column | fraction × `(annual_kwh/8760) / annual_mean_fraction` → kW | Correct formula; simulation-window vs annual mean difference (Finding 2) |
| `hot_water_fixtures` | raw fraction stored as column reference; runtime `/60` applied | fraction × `(avg_l_per_day/1440) / mean_fraction` → L/min column | **WRONG — fraction passed as L/min (Finding 1)** |
| `heating_setpoint`, `cooling_setpoint`, `water_heater_setpoint` | column index stored; equipment reads raw CSV value (°F expected; conversion elsewhere) | raw value (°F), converted at consumption | Must verify °F→°C happens at consumption point |
| `clothes_washer`, `dishwasher`, etc. (EventWindow) | fraction stored as event window col + optional `event_power_kw_series` | fraction used for event probability window | Plausible match — event semantics differ from direct power |

## Background/Context

Scheduled/event load outputs: electric power, gas power, mode. OCHRE aggregates by
end use. Each load should report its power and sensible/latent thermal gains.

## Investigation Instructions

1. Read OCHRE scheduled/event load output columns.
2. Read HARES scheduled_load and event_load telemetry.
3. Build comparison table.
4. Check: do scheduled loads report their thermal contribution to zones?


## Recommended Tests

- `scheduled_load::tests::checkpoint_preserves_reactive_power_kvar` — save state on a ZIP-configured load with non-zero kvar, restore, assert `telemetry().get(tk::REACTIVE_POWER_KVAR)` matches the pre-save value **before** calling `step()`.
- `event_load::tests::gas_active_power_kw_reflects_fuel_rate` — for a gas `EventBasedLoad` in Active phase, assert `ACTIVE_POWER_KW == FUEL_INPUT_W / 1000.0` (once F2 is fixed).

## Findings

### F1 — HIGH — `REACTIVE_POWER_KVAR` not restored in `ScheduledLoad::load_state`

**Location:** `crates/hares-equipment/src/scheduled_load.rs:493–510`

`load_state` reconstructs `ELECTRIC_KW`, `SENSIBLE_GAIN_W`, `LATENT_GAIN_W`, and `FUEL_INPUT_W` from `last_non_zero_power_kw`/`last_non_zero_gas_w`. `REACTIVE_POWER_KVAR` is left at `0.0` from `default_telemetry()` and is never restored.

It cannot be reconstructed from saved fields alone — the ZIP reactive formula needs grid voltage (`env.grid.voltage_pu`), which is not in `ScheduledLoadState`. After a checkpoint round-trip, any caller reading `telemetry().get(tk::REACTIVE_POWER_KVAR)` before the next `step()` gets stale `0.0`.

**Fix:** Add `last_reactive_power_kvar: f64` to `ScheduledLoadState`. Persist it in `save_state` from the telemetry value written at the end of `step()`. Restore it directly in `load_state`.

**Missing test:** The existing checkpoint test (`~line 1430`) only asserts `ELECTRIC_KW`. A test covering reactive power across a checkpoint boundary is absent.

---

### F2 — MEDIUM — `ACTIVE_POWER_KW` always `0.0` for non-electric `EventBasedLoad` / `WetAppliance`

**Location:** `crates/hares-equipment/src/event_load.rs:407–408, 846–847`

For gas (or other non-electric) fuel types:

```rust
let electric_power_kw = if is_fuel { 0.0 } else { active_power_kw };
self.telemetry.set(tk::ACTIVE_POWER_KW, electric_power_kw);  // always 0.0
self.telemetry.set(tk::ELECTRIC_KW, electric_power_kw);       // always 0.0
```

`ACTIVE_POWER_KW` is documented as `"Active electrical power draw"` and always emits `0.0` for gas equipment. The actual load rate is only available as `FUEL_INPUT_W` in watts. There is no kW-scale field for gas event loads.

OCHRE emits `"<name> Gas Power (therms/hour)"` separately when `is_gas=True` (`Equipment.py:298–299`). HARES has no equivalent for event loads.

The existing test at line 2295–2303 asserts `active_power_kw == 0.0` for gas equipment and treats it as correct. The test conflates correct behavior with a deliberate design choice that has not been evaluated.

**Fix:** Set `ACTIVE_POWER_KW` to `fuel_consumption_w / 1000.0` for non-electric loads so it represents total active power regardless of fuel type. Update the telemetry field description to `"Active power draw (electrical or fuel equivalent in kW)"`. Update the gas telemetry test to assert the non-zero value.

---

### F3 — LOW — Missing invariant comment on `last_non_zero_power_kw` semantics

**Location:** `crates/hares-equipment/src/scheduled_load.rs` struct definition (`~line 132`)

The inline comment in `load_state` (line 495) correctly states that `last_non_zero_power_kw` holds the post-ZIP value. This invariant is not documented at the field declaration site. A future change that stores the pre-ZIP value would silently miscalculate sensible/latent gains after restore.

**Fix:** Add a field comment at the struct level stating the value is always the ZIP-adjusted active power in kW as last emitted to telemetry.

---

### F4 — LOW — `FUEL_INPUT_W` description says "gas" for a generic-fuel device

**Location:** `crates/hares-equipment/src/event_load.rs:1436–1439, 1471–1474`

Both `event_load_telemetry_fields()` and `wet_appliance_telemetry_fields()` describe `FUEL_INPUT_W` as `"Gas fuel consumption rate converted to watts"`. `EventBasedLoad` and `WetAppliance` accept any `FuelType`. The description should be `"Non-electric fuel consumption rate in watts"`.

## Parity Assessment

OCHRE `Equipment.calculate_power_and_heat` (Equipment.py:185–191):

```python
total_power_w = (self.electric_kw + self.gas_therms_per_hour / kwh_to_therms) * 1000
self.sensible_gain = total_power_w * self.sensible_gain_fraction
self.latent_gain = total_power_w * self.latent_gain_fraction
```

HARES `ScheduledLoad.step()` mirrors this at lines 426–428 (combined electric+gas wattage drives gains). **Parity: correct.**

HARES `EventBasedLoad.update_outputs()` uses `gain_source_w = active_power_kw * 1_000.0` (lines 378–380) where `active_power_kw` is pre-fuel-split. This matches OCHRE's `total_power_w` for single-fuel equipment. **Parity: correct.**

OCHRE emits `sensible_gain` / `latent_gain` as zone contributions, not as a results column. HARES correctly emits them as telemetry fields and writes them to the thermal port. No missing field relative to OCHRE output.

OCHRE emits `"Gas Power (therms/hour)"` at verbosity >= 6 (Equipment.py:298–299). HARES stores the equivalent as `FUEL_INPUT_W` in watts after SI conversion. Values are equivalent; the unit difference is intentional per project SI policy.

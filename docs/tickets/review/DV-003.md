## Background/Context

HVAC performance curves (cap_t, eir_t, cap_ff, eir_ff, eir_plr) are loaded from CSV
files. These were never compared row-by-row against OCHRE's equivalent defaults.

## Investigation Instructions

1. List all HVAC default CSV files in HARES data/defaults/
2. For each, find the OCHRE equivalent in vendors/OCHRE/ochre/defaults/
3. Compare row-by-row: same equipment types? Same coefficient values?
4. Check for missing equipment types in either direction
5. Check coefficient ordering (a0, a1, a2... vs OCHRE convention)
6. Spot-check: evaluate a biquadratic at AHRI rated conditions (35°C OAT, 19.4°C WB) — does it return ~1.0?

### Output: Write into this file under ## Findings and ## Recommended Tests.

## Findings

### 1. Coefficient values: PASS — all CSV files are byte-for-byte matches with OCHRE

All seven HVAC coefficient CSV files in `defaults/` are exact copies of their OCHRE counterparts:

| HARES file | OCHRE file | Match |
|---|---|---|
| `defaults/hvac_cooling/ASHP Cooler.csv` | `HVAC Cooling/Biquadratic ASHP Cooler.csv` | Exact |
| `defaults/hvac_cooling/Air Conditioner.csv` | `HVAC Cooling/Biquadratic Air Conditioner.csv` | Exact |
| `defaults/hvac_cooling/MSHP Cooler.csv` | `HVAC Cooling/Biquadratic MSHP Cooler.csv` | Exact |
| `defaults/hvac_cooling/Room AC.csv` | `HVAC Cooling/Biquadratic Room AC.csv` | Exact |
| `defaults/hvac_heating/ASHP Heater.csv` | `HVAC Heating/Biquadratic ASHP Heater.csv` | Exact |
| `defaults/hvac_heating/Heat Pump Heater.csv` | `HVAC Heating/Biquadratic Heat Pump Heater.csv` | Exact |
| `defaults/hvac_heating/MSHP Heater.csv` | `HVAC Heating/Biquadratic MSHP Heater.csv` | Exact |
| `defaults/HVAC Multispeed Parameters.csv` | `HVAC Multispeed Parameters.csv` | Exact |

Coefficient ordering matches OCHRE: `[a, b, c, d, e, f]` → `a + b*x1 + c*x1² + d*x2 + e*x2² + f*x1*x2`.

The hardcoded defaults in `crates/hares-equipment/src/hvac/ac_config.rs` (`DEFAULT_AC_CAPACITY_CURVE`, `DEFAULT_AC_EIR_CURVE`, `DEFAULT_ROOM_AC_CAPACITY_CURVE`, `DEFAULT_ROOM_AC_EIR_CURVE`) match the `Single_1` column of `Air Conditioner.csv` and `Room AC.csv` exactly.

### 2. AHRI rated conditions spot-check: PASS with expected deviation

At AHRI 210/240 cooling rated conditions (indoor WB=19.44°C, outdoor DB=35°C), `Air Conditioner Single_1` cap_t evaluates to approximately 0.994. This is consistent with the comment in `crates/hares-physics/src/biquadratic.rs:98` — the OCHRE curve is not normalized to unity at AHRI conditions; it uses a different reference point. The existing test `ahri_210_240_rating_conditions_documented` correctly documents this.

### 3. CRITICAL — Biquadratic input bounds dropped in HPXML resolver path

**Severity: High — silent physics divergence from OCHRE at out-of-range conditions**

The CSV rows `min_Twb`/`max_Twb`/`min_Tdb`/`max_Tdb` are correctly parsed into `HvacCurveVariant.cap_t.x1_bounds`, `.x2_bounds`, `.eir_t.x1_bounds`, `.eir_t.x2_bounds` in `crates/hares-io/src/defaults.rs:523-536`.

However, in `crates/hares-io/src/hpxml/resolve_hvac.rs:922-928`, `select_primary_curve_pair` returns only `selected.cap_t.coeffs` and `selected.eir_t.coeffs`:

```rust
// resolve_hvac.rs:927-928
Some((selected.cap_t.coeffs, selected.eir_t.coeffs))
```

The bounds are silently discarded. The caller at lines 895-901 writes only `capacity_biquadratic_coeffs` and `eir_biquadratic_coeffs` keys to config — no bound keys are ever written.

In `crates/hares-equipment/src/hvac/hvac_core.rs:390-400`, bounds are loaded from config keys `biquadratic_x1_min/max` and `biquadratic_x2_min/max`. Since these are never populated by the HPXML resolver, the equipment falls back to `DEFAULT_BIQUADRATIC_X1_BOUNDS = (-100.0, 100.0)` and `DEFAULT_BIQUADRATIC_X2_BOUNDS = (-100.0, 100.0)`.

OCHRE uses `min_Twb=13.88, max_Twb=23.88, min_Tdb=18.33, max_Tdb=51.66` for all cooling equipment. The divergence affects:
- Low indoor wet-bulb (< 13.88°C, e.g., very dry/cool conditions)
- High outdoor dry-bulb (> 51.66°C, e.g., extreme heat events)

For heating equipment, OCHRE's CSV uses `(-100, 100)` for all bounds, so the heating path is unaffected.

**Fix:** `select_primary_curve_pair` should return the bounds alongside the coefficients, and the caller in `apply_multispeed_parameters` must write `biquadratic_x1_min`, `biquadratic_x1_max`, `biquadratic_x2_min`, `biquadratic_x2_max` keys into config.

### 4. CRITICAL — `min_ff`/`max_ff` and `min_plf`/`max_plf` from CSV are never parsed

**Severity: Medium — flow-fraction and PLF clamping diverges for MSHP equipment**

OCHRE's `_biquadratic()` function clamps flow fraction to `[min_ff, max_ff]` and clamps the PLF output to `[min_plf, max_plf]`. These values vary by speed variant in the CSV:

- `MSHP Heater.csv` `Single_1`: `min_ff=0.37778`, `min_plf=0.2195476`
- `MSHP Cooler.csv` `Variable_1`: `min_plf=0.48015`

`HvacCurveVariant` in `crates/hares-io/src/defaults.rs:54-61` has no fields for these. The `load_hvac_csv_file` parser at line 498+ never reads the `min_ff`, `max_ff`, `min_plf`, or `max_plf` rows.

HARES uses a fixed PLF floor of 0.7 (`hvac_core.rs:1625`) regardless of equipment type. For MSHP `Single_1` the OCHRE `min_plf=0.2195476` is much lower — meaning HARES will over-clamp PLF for MSHP at low part-load, producing artificially elevated efficiency.

Flow-fraction clamping is not applied at all in the HARES biquadratic evaluation path (`evaluate_biquadratic_with_flow` in `hvac_core.rs:755-763`).

**Fix:** Add `ff_bounds: (f64, f64)` and `plf_bounds: (f64, f64)` fields to `HvacCurveVariant`, parse them from the CSV, propagate through the resolver, and apply in `evaluate_biquadratic_with_flow`.

### 5. INFO — MSHP Cooler has no `min_Twb`/`max_Twb` rows; HARES CSV parser silently defaults to 0.0

The `MSHP Cooler.csv` and `MSHP Heater.csv` files do not contain `min_Twb`, `max_Twb`, `min_Tdb`, or `max_Tdb` rows. The `load_hvac_csv_file` parser uses `get_row()` which defaults missing rows to `0.0`. This means MSHP equipment would get x1_bounds=(0.0, 0.0) and x2_bounds=(0.0, 0.0) — both bounds set equal — causing all x1/x2 inputs to be clamped to 0.0°C.

OCHRE handles this correctly: its CSV parser defaults missing bounds to `(-100, 100)` (`HVAC.py:827-830`).

This is a parser bug. The `get_row()` default of `vec![0.0; n_variants]` is wrong for bound rows; it should use OCHRE's fallback convention: `(-100, 100)` for Twb/Tdb.

However, given Finding 3, these bounds are not propagated anyway in the HPXML path — so this bug is currently latent until Finding 3 is fixed.

**Fix:** Change the defaults for `min_Twb`/`min_Tdb` rows to `-100.0` and `max_Twb`/`max_Tdb` rows to `100.0` in `load_hvac_csv_file`.

## Recommended Tests

1. **Bounds propagation regression** — Load an HPXML fixture with a cooling AC, confirm that `hvac.biquadratic_x1_bounds == (13.88, 23.88)` and `hvac.biquadratic_x2_bounds == (18.33, 51.66)` after `apply_multispeed_parameters` (or single-speed resolver) runs.

2. **Missing-row default test** — In `hares-io` defaults tests, load `MSHP Cooler.csv` and assert that `variant.cap_t.x1_bounds.0 == -100.0` (not 0.0) after Finding 5 is fixed.

3. **MSHP PLF floor parity test** — For an MSHP single-speed equipment config, verify the PLF floor matches OCHRE's `min_plf=0.2195476` from the CSV rather than the hardcoded 0.7 floor.

4. **Flow-fraction clamping test** — Call `evaluate_biquadratic_with_flow` with ff < `min_ff` and verify it clamps to `min_ff` rather than extrapolating.

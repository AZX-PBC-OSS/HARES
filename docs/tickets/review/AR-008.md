## Background/Context

When a user sees unexpected energy consumption, they need to drill down: which
equipment contributed how much to which zone? If output only shows aggregated totals,
debugging is impossible. OCHRE provides per-equipment, per-end-use, and per-component
columns at increasing verbosity levels.

This ticket specifically assesses whether HARES output enables the same debugging
workflow as OCHRE, or whether premature aggregation prevents it.

## Investigation Instructions

1. **Map OCHRE's output hierarchy:**
   - Verbosity 0: totals only
   - Verbosity 2: per-end-use
   - Verbosity 4-5: per-equipment delivered, COP, duct losses
   - Verbosity 6-7: per-equipment power, mode, speed
   - Verbosity 8-9: per-boundary, per-zone, humidity

2. **Map HARES output hierarchy:**
   - What columns are produced at each `output_verbosity` level?
   - How does the streaming recorder build the schema?
   - Are per-equipment columns available?

3. **Identify debugging gaps:**
   - Can a user see per-zone thermal gains broken down by source?
   - Can a user see HVAC delivered heat separately from duct losses?
   - Can a user see WH jacket loss as a separate zone contribution?
   - Can a user see individual scheduled load contributions?

4. **Check for premature aggregation in output:**
   - Is there a point where per-equipment data is summed into per-end-use
     before any output column can capture it?
   - Are per-category thermal breakdowns available in output?

5. **Recommend output improvements** that would enable OCHRE-equivalent debugging.

## Findings

### OCHRE Output Hierarchy (Reference)

OCHRE uses a single integer `verbosity` parameter. The levels that matter:

| OCHRE verbosity | Content added |
|---|---|
| 0 | Total electric, gas, reactive power (Dwelling.py:300-307) |
| 2 | Per-end-use electric and gas power, summed over equipment in that end-use (Dwelling.py:319-325) |
| 3 | Indoor temperature, unmet HVAC load (Envelope.py:1377-1380) |
| 4 | Per-HVAC delivered heat, setpoint, COP (HVAC.py:572-584) |
| 5 | HVAC duct losses; all zone temperatures; net sensible/component loads per zone (Envelope.py:1382-1410, HVAC.py:586-588) |
| 6 | Total energy per step (kWh) (Dwelling.py:309-317) |
| 7 | Per-equipment mode, detailed HVAC power breakdown, WH total sensible gain, EV start/end times, Battery energy to discharge (Equipment.py:301-303, HVAC.py:591-594, WaterHeater.py:309-311, EV.py:342-348, Battery.py:447-450) |
| 8 | Per-end-use reactive power, grid voltage, occupancy, detailed zone heat gains (all categories), humidity state per zone (Dwelling.py:326-330, Envelope.py:1412-1444) |
| 9 | Per-boundary surface temperatures, solar/LWR gain by surface (Envelope.py:1446-1463) |

Key OCHRE characteristic: **end-use columns (verbosity 2) aggregate multiple equipment items into one column** using `equipment_by_end_use`. Individual equipment power within an end use is not separately recorded until verbosity 6 when `main_simulator` or `self.name != self.end_use` is true (Equipment.py:293-299).

### HARES Output Hierarchy

`build_schema` in `crates/hares-io/src/output/columns.rs`:

| HARES verbosity | Schema columns added |
|---|---|
| 0 | Timestamp, Total Electric Power (kW), Total Gas Power (therms/hour), Total Reactive Power (kVAR) |
| 1 | Per-equipment electric power (kW), per-equipment gas power (therms/hour) — one column per equipment instance, not per end-use |
| 2 | Temperature - Indoor (C), Unmet HVAC Load (C), Outdoor Dry Bulb (C) |
| 3 | Per-equipment Mode (-), per-HVAC/WH Setpoint (C), per-Battery/EV SOC (-) |
| 4 | Per-equipment Energy (kWh), HVAC Heating Delivered (W), HVAC Cooling Delivered (W) |
| 5 | Per-electric-equipment Reactive Power (kVAR), Power Factor (-) |
| 6 | 15 named envelope component gain columns (Window Transmitted Solar Gain, Infiltration, Forced/Natural Ventilation, Internal Heat Gain, Radiation, Opaque Surface, Duct Loss, Roof, Floor, Wall, Window, Internal Mass per Indoor zone; Infiltration and Radiation for Attic) |
| 7 | Per-equipment Schedule (-) |
| 8 | Per-equipment Capacity (W), COP (-) |

`record_step` in `crates/hares-core/src/dwelling/mod.rs`:

The step recorder populates columns through a pre-resolved `EquipmentColumns` struct and direct index lookups. The `EquipmentColumns` struct (`mod.rs:116-123`) has exactly five fields:
- `electric_power`
- `gas_power`
- `mode`
- `reactive_power`
- `power_factor`

### BUG-001 — Schema declares columns at verbosity 3-8 that `record_step` never populates (all zeros)

**Severity: High**

**Files:**
- `crates/hares-io/src/output/columns.rs:98-212` (schema declaration)
- `crates/hares-core/src/dwelling/mod.rs:115-163` (`EquipmentColumns` struct and `build_equipment_column_map`)
- `crates/hares-core/src/dwelling/mod.rs:2244-2278` (`record_step` per-equipment loop)

The following columns are declared in the Arrow schema at the respective verbosity levels but **are never written by `record_step`**. They are initialized to zero via `self.record_scratch.fill(0.0)` and never updated:

| Verbosity | Column pattern | Source missing |
|---|---|---|
| 3 | `{name} Setpoint (C)` | `EquipmentColumns` has no `setpoint` field; no `heating_setpoint_c`/`cooling_setpoint_c` lookup in the per-equipment loop |
| 3 | `{name} SOC (-)` | `EquipmentColumns` has no `soc` field; telemetry key `"soc"` is read in `build_telemetry()` (line 1539) but never in `record_step` |
| 4 | `{name} Energy (kWh)` | `EquipmentColumns` has no `energy` field; no cumulative energy is accumulated per-equipment in the recording path |
| 7 | `{name} Schedule (-)` | `EquipmentColumns` has no `schedule` field; no schedule value is read from equipment telemetry |
| 8 | `{name} Capacity (W)` | `EquipmentColumns` has no `capacity` field |
| 8 | `{name} COP (-)` | `EquipmentColumns` has no `cop` field |

A user running at verbosity 3 who expects `Battery SOC (-)` or `ASHP Heater Setpoint (C)` in their Parquet output will see a column of zeros. This is a silent data loss defect — no error is raised, the schema is valid, but the values are wrong.

The `HVAC Heating Delivered (W)` and `HVAC Cooling Delivered (W)` at verbosity 4 are correctly populated (from `component_gains()` at `mod.rs:2322-2323`), but the per-equipment `{name} Energy (kWh)` columns at the same level are not.

### BUG-002 — Verbosity level mapping diverges from OCHRE at levels 2/3 and causes user confusion

**Severity: Medium**

**Files:**
- `crates/hares-io/src/output/columns.rs:84-96` (verbosity 2 = zone temperature in HARES)
- `vendors/OCHRE/ochre/Models/Envelope.py:1377-1380` (verbosity 3 = indoor temperature in OCHRE)

OCHRE puts indoor temperature at verbosity 3. HARES puts it at verbosity 2. OCHRE puts per-end-use power at verbosity 2. HARES puts per-**equipment** power at verbosity 1 with no per-end-use aggregation column at any level.

The effect on a user migrating from OCHRE: setting `verbosity=2` in HARES gives zone temperatures (unexpected); setting `verbosity=2` in OCHRE gives per-end-use power breakdowns (not available in HARES at any level). Any documentation, tooling, or parity test that assumes OCHRE verbosity numbers are portable to HARES will silently produce wrong column sets.

---

### GAP-001 — No per-end-use aggregation columns at any verbosity level

**Severity: High (debugging gap)**

**Files:**
- `crates/hares-io/src/output/columns.rs` (entire file — no end-use aggregation columns defined)
- `vendors/OCHRE/ochre/Dwelling.py:319-325` (OCHRE verbosity 2 end-use columns)

OCHRE verbosity 2 emits `"Space Heating Electric Power (kW)"`, `"Water Heating Electric Power (kW)"`, etc. — one column per logical end-use, each summing all equipment in that end-use category. This is the primary debugging entry point: a user sees total heating power consumption without needing per-equipment instance names.

HARES has no equivalent. The verbosity 1 per-equipment columns are more granular (good) but require the user to know the equipment name. When multiple units of the same end-use are present (e.g., two baseboard heaters), the user must manually sum `"Baseboard #1 Electric Power (kW)"` and `"Baseboard #2 Electric Power (kW)"` to reproduce what OCHRE shows as `"Space Heating Electric Power (kW)"`.

### GAP-002 — WH jacket loss is merged into Internal Heat Gain, not separately visible

**Severity: Medium (debugging gap)**

**Files:**
- `crates/hares-core/src/dwelling/mod.rs:2313-2315`

`record_step` combines `gains.internal_gain_w + gains.jacket_loss_w` into the single `"Internal Heat Gain - Indoor (W)"` column. The `EnvelopeComponentGains` struct (`crates/hares-envelope/src/thermal_solver/config.rs:449`) has `jacket_loss_w` as a separate field, but this disaggregation is discarded at the output boundary.

In OCHRE, WH sensible gain to the zone is accessible at verbosity 7 via `"{end_use} Total Sensible Heat Gain (W)"` (WaterHeater.py:310). In HARES there is no equivalent column at any verbosity level; the jacket loss contribution is invisible to users who need to diagnose unexpected zone heating from a water heater.

---

### GAP-003 — HVAC duct losses not separately emittable per equipment instance

**Severity: Medium (debugging gap)**

**Files:**
- `crates/hares-io/src/output/columns.rs:173-174` (single `"Duct Loss Heat Gain - Indoor (W)"` column)
- `vendors/OCHRE/ochre/Equipment/HVAC.py:586-588` (OCHRE verbosity 5: per-end-use duct losses)

OCHRE emits `"{end_use} Duct Losses (W)"` per HVAC end-use at verbosity 5, so heating duct losses and cooling duct losses are separately visible. HARES emits a single `"Duct Loss Heat Gain - Indoor (W)"` that aggregates all duct losses to the indoor zone. When a building has both heating and cooling with separate duct efficiencies, the user cannot distinguish which is contributing.

---

### GAP-004 — No per-zone multi-zone temperature columns at intermediate verbosity

**Severity: Low (debugging gap)**

**Files:**
- `crates/hares-io/src/output/columns.rs:84-96` (verbosity 2 only emits "Temperature - Indoor (C)")
- `vendors/OCHRE/ochre/Models/Envelope.py:1382-1385` (OCHRE verbosity 5 emits all zone temperatures)

The schema for verbosity 2 hardcodes a single `"Temperature - Indoor (C)"` column. The comment at `columns.rs:86-88` acknowledges: "At schema-build time we don't know zone count, so we emit a single 'Indoor' zone. The dwelling orchestrator can extend later." — but there is no evidence that the orchestrator actually extends the schema for additional zones (attic, garage, crawlspace, etc.). Multi-zone buildings will silently drop non-indoor zone temperatures unless the schema is rebuilt.

---

### GAP-005 — No individual scheduled load power columns

**Severity: Low (debugging gap)**

**Files:**
- `crates/hares-io/src/output/columns.rs` (no scheduled load instance columns)
- `vendors/OCHRE/ochre/Equipment/Equipment.py:293-299` (OCHRE: per-equipment column at verbosity 6 when name != end_use)

OCHRE emits per-equipment columns for loads whose `name != end_use` (i.e., individually named appliances within an end-use group) at verbosity 6. HARES does emit per-equipment columns at verbosity 1, which covers this case — but this is the one area where HARES is more granular by default than OCHRE. This is ACCEPTABLE with one caveat: users must know to use verbosity 1, not verbosity 6 as in OCHRE.

---

### GAP-006 — Water heater COP not available in output at any verbosity level

**Severity: Medium**

**Files:**
- `crates/hares-io/src/output/metrics.rs:759` (explicit `water_heater_cop: None` comment)
- `crates/hares-io/src/output/columns.rs:197-210` (COP column declared at verbosity 8 but not populated — see BUG-001)

`MetricsCalculator::finish()` at `metrics.rs:759` has an explicit `water_heater_cop: None // requires WH-specific telemetry columns` comment. The verbosity-8 COP column would cover this case, but it is unimplemented (BUG-001). OCHRE computes WH COP at verbosity 4 (`WaterHeater.py:306-308`). HARES users have no path to WH COP at any verbosity.

---

### IMPROVEMENT-001 — `"Unmet HVAC Load (C)"` column is always zero

**Severity: Medium**

**Files:**
- `crates/hares-core/src/dwelling/mod.rs:2288-2292` (only a fallback "Indoor Temperature (C)" is populated; "Unmet HVAC Load (C)" is never written)

The schema declares `"Unmet HVAC Load (C)"` at verbosity 2. A search of `record_step` shows no write to this column name. OCHRE populates it from `self.unmet_hvac_load` (Envelope.py:1380). HARES has the column reserved but never fills it, so users asking "was the HVAC unable to meet the setpoint?" get no signal.

---

### IMPROVEMENT-002 — `filter_schema_to_verbosity` is unreachable dead code

**Severity: Low**

**Files:**
- `crates/hares-io/src/output/columns.rs:310-327` (`#[allow(dead_code)]` annotation)

This function was written to support post-hoc schema filtering but is currently suppressed with `#[allow(dead_code)]`. It passes an empty equipment list to `build_schema`, so for verbosity >= 1 it would always return a schema missing all equipment-dependent columns. The filtering logic is incorrect for its stated purpose even if it were used.

---

### IMPROVEMENT-003 — `expected_columns_at_verbosity` is incomplete and misleading

**Severity: Low**

**Files:**
- `crates/hares-io/src/output/columns.rs:222-232`

`expected_columns_at_verbosity` only lists static columns. For verbosity >= 1, all equipment-dependent column names (the majority of the schema) are absent from its return value. Tests using this function (`verbosity_0_column_names_match_ochre`) verify only the static subset. A user or test that calls this to validate the schema against actual output will miss all per-equipment gaps, including BUG-001.

---

### ACCEPTABLE-001 — HARES uses per-equipment naming at verbosity 1 where OCHRE uses per-end-use at verbosity 2

HARES verbosity 1 emits per-equipment instance columns (`"ASHP Heater Electric Power (kW)"`), which is strictly more informative than OCHRE's verbosity 2 per-end-use aggregation (`"Space Heating Electric Power (kW)"`). This is an intentional improvement, not a parity gap. The absence of end-use aggregation columns (GAP-001) is the separate issue.

---

### ACCEPTABLE-002 — OCHRE verbosity 9 boundary-level surface temperatures are not present in HARES

HARES does not expose per-surface temperatures, solar, and LWR gains at any verbosity level. OCHRE provides these at verbosity 9 (Envelope.py:1446-1463). These are simulation-internal physics quantities rarely needed for energy debugging and are out of scope for a first-pass output audit. Flagging as acceptable for now.

---

## Summary of Premature Aggregation Points

1. `mod.rs:2314` — `jacket_loss_w` is summed into `internal_gain_w` before output. The component is available in `EnvelopeComponentGains` but discarded. (GAP-002)
2. `columns.rs` — no per-end-use aggregation layer exists; OCHRE's verbosity-2 aggregation has no equivalent. (GAP-001)
3. `mod.rs:EquipmentColumns` — only five output column types are pre-resolved per equipment; SOC, setpoint, energy, schedule, COP, and capacity are in the schema but have no write path. (BUG-001)
4. `columns.rs:164-183` — verbosity 6 envelope component columns exist as a flat hardcoded list, not derived from actual zone names, causing multi-zone buildings to silently drop non-indoor zones. (GAP-004)

## Recommended Tests

### Test 1 — SOC column is non-zero when Battery/EV is present at verbosity 3
Run a one-step simulation with a battery at non-zero SOC, verbosity 3. Assert `"Battery SOC (-)"` column value equals the known initial SOC. Currently this will fail due to BUG-001.

### Test 2 — Setpoint column is non-zero when HVAC is present at verbosity 3
Run a one-step simulation with ASHP Heater at verbosity 3. Assert `"ASHP Heater Setpoint (C)"` is equal to the configured setpoint. Currently this will fail due to BUG-001.

### Test 3 — Unmet HVAC Load column is non-zero during a capacity-limited step
Run a simulation step where outdoor temperature is extreme and HVAC is undersized. Assert `"Unmet HVAC Load (C)"` is non-zero. Currently this will produce zero due to IMPROVEMENT-001.

### Test 4 — Jacket loss does not appear in Internal Heat Gain when WH jacket loss is zero
Run a simulation with no water heater. Assert `"Internal Heat Gain - Indoor (W)"` at verbosity 6 equals only the occupancy + appliance internal gain, not a sum with jacket loss. This validates the disaggregation contract (GAP-002 remediation target).

### Test 5 — Per-end-use aggregation matches sum of per-equipment columns
When GAP-001 is remediated, assert `"Space Heating Electric Power (kW)"` equals the sum of all per-equipment heating columns for a building with multiple heating devices.

### Test 6 — `filter_schema_to_verbosity` returns correct fields including equipment columns
Call `filter_schema_to_verbosity` on a schema built with equipment present. Assert the returned schema contains equipment-dependent columns. Currently the function passes an empty equipment list and the result will be incomplete (IMPROVEMENT-002).

### Test 7 — Multi-zone building outputs temperature for all zones at verbosity 2+
Run a simulation for a building with an attic zone. Assert all zone temperature columns are present in the output schema, not just `"Temperature - Indoor (C)"`. Currently this will fail due to GAP-004.

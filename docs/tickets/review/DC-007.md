## Background/Context

Clothes washer/dryer, dishwasher, and cooking range are event-based loads that
fire discrete cycles at times determined by the occupancy schedule. Each event has
a duration, power profile, and hot water draw.

## Investigation Instructions

1. Read HARES `event_load.rs` — how are events triggered?
   - Stochastic (Poisson) or schedule-driven?
   - What determines event start time, duration, power during event?
2. Read OCHRE `EventBasedLoad.py` — same questions.
3. Compare event triggering mechanism.
4. Does HARES emit DHW demand during wash/dishwasher events?
5. Is the event power profile (ramp up, steady, ramp down) modeled?

## Findings

### Summary of OCHRE Mechanism

OCHRE's `WetAppliance.py` is a legacy MC (Monte Carlo) profile generator that is
**no longer used in production**. The live code path is `EventBasedLoad` in
`EventBasedLoad.py`. The `__init__.py` maps Clothes Washer, Clothes Dryer,
Dishwasher, and Cooking Range all to `EventBasedLoad` (line 82-87). `WetAppliance`
is commented out of the import (`# from .WetAppliance import WetAppliance`, line 33).

OCHRE's `EventBasedLoad` supports three input modes (in priority order,
`initialize_schedule`, lines 122-136):

1. Pre-built `event_schedule` DataFrame passed directly.
2. Time-series kW schedule (`ts_schedule` from CSV): calls `extract_events()` to
   detect contiguous non-zero regions and compute average power per event — fully
   deterministic.
3. PDF/event-list files: calls `generate_events()` for stochastic generation
   (`np.random.random` in `DailyLoad.generate_events`, line 297-308).

In the PDF path (`DailyLoad`), each day gets one event with start time drawn from
a CDF lookup plus a random intra-hour offset (`np.random.random * timedelta(hours=1)`).
Duration is fixed. Power is constant at `max_power`. This is the legacy stochastic
path used when no schedule CSV is provided.

The `EventDataLoad` subclass adds per-event-type power profiles (variable power
over the cycle), but is still keyed on the same event list above.

OCHRE's `WetAppliance.py` (MC legacy, unused) used a per-minute switch-on
probability vector and a stored set-profile of (P, Q) pairs indexed by
`Profile_t`, incrementing on each active step — a variable power profile with
real reactive power. This class is dead code in modern OCHRE.

### Summary of HARES Mechanism

HARES implements two structs:

- `EventBasedLoad` — Idle/Active/Cooldown three-phase state machine.
- `WetAppliance` — Multi-phase cycle (`phases: Vec<CyclePhase>`).

Both structs share identical dual-mode dispatch logic in `step()`:

**Deterministic mode** (triggered when `KEY_EVENT_POWER_KW_SERIES` is present in
config): `extract_events_from_kw_series()` pre-parses the kW series into
`Vec<ExtractedEvent>` at `init()`. Each step, the current step index is compared
against `[start_step, end_step)` of the next event. Power during the event is the
average of the source series over the event window (constant per event). Wraps on
`schedule_len` for annual repeating schedules.

**Stochastic mode** (fallback when no kW series): per-step Bernoulli draw using
`ChaCha8Rng`. Gate is `event_window_source` (binary open/closed) AND
`event_probability_source` (draw probability). RNG is seeded from
`master_seed + building_id + FNV1a(equipment_name)`.

### Comparison

| Dimension | OCHRE | HARES |
|---|---|---|
| Primary path | `extract_events` from CSV time-series | `extract_events_from_kw_series` from config array |
| Stochastic path | daily CDF lookup + random minute offset | per-step Bernoulli via ChaCha8 |
| Power profile shape | Constant per event (EventBasedLoad); variable per event type (EventDataLoad) | Constant per extracted event (deterministic); constant per phase (stochastic) |
| Reactive power (Q) | Modeled in legacy WetAppliance; not in EventBasedLoad | Not modeled |
| Phase-resolved power | EventDataLoad only (event type selection logic) | WetAppliance: multi-phase Vec<CyclePhase>, each with own power_kw and duration_s |
| DHW draw | Not in EventBasedLoad | WetAppliance emits `PortContribution::Fluid` at `hot_water_draw_rate_kg_s` derived from `KEY_HOT_WATER_DRAW_VOLUME_L / total_cycle_duration_s` |
| Reactive power | EventDataLoad only (P profile, no Q) | Not modeled |
| RNG reproducibility | `np.random.random` — no deterministic seeding | ChaCha8Rng seeded from master_seed + building_id + name hash |

### Defects and Gaps

**DEFECT — SEVERITY: HIGH**
`event_load.rs:529` — In deterministic mode for `EventBasedLoad`, the extracted
event's `power_kw` (average over event window) overwrites `self.active_power_kw`
in-place every step the event is active:

```rust
self.active_power_kw = self.extracted_events[self.event_cursor].power_kw;
```

This mutates the configured field, meaning if `init()` is called again or state is
inspected outside `step()`, the field no longer reflects configuration. This is
consistent with the rest of the struct only by accident: when load_state is called,
`active_power_kw` is not saved/restored, so a checkpoint-resume during an active
deterministic event will replay with the original config value for one step until
`step()` re-overwrites it. `WetAppliance` avoids this problem by reading
`extracted_events[cursor].power_kw` directly inside `update_outputs()` without
mutating configuration state.

**DEFECT — SEVERITY: HIGH**
`event_load.rs:784-796` — `WetAppliance::update_outputs()` reads
`self.extracted_events[self.event_cursor].power_kw` while in deterministic mode,
but the cursor may be at or past `extracted_events.len()` if no event is active and
the guard is:

```rust
let base_kw = if !self.extracted_events.is_empty()
    && self.event_cursor < self.extracted_events.len()
{
    self.extracted_events[self.event_cursor].power_kw
} else {
    self.phases[self.phase_index].power_kw * self.n_units
};
```

The outer condition `if self.active` gates entry. But `self.active = in_event` was
set earlier in `step()`. If `in_event == true` but `event_cursor >= len()` (possible
at end-of-schedule before wrap resets cursor), this branch falls through to
`phases[phase_index].power_kw * n_units`, silently using stochastic phase power
for what is intended to be a deterministic event. No error is raised. The wrap
reset (`self.event_cursor = 0`) happens only when cursor is past the end AND
`schedule_len > 0`; the cursor is already reset before `update_outputs()` is called,
but the off-by-one at the exact boundary step where `end_step == schedule_len`
deserves explicit testing.

**DEFECT — SEVERITY: MEDIUM**
`event_load.rs:1336-1358` — `derive_rng_seed` uses `config.get_f64(KEY_MASTER_SEED)
.unwrap_or_default() as u64`. If `master_seed` is absent from config, all equipment
in all buildings share seed bytes `[0;8]`, differentiated only by `building_id` and
name hash. If `building_id` is also absent (defaults to 0), then all equipment with
the same name (e.g., two "Clothes Washer" units in a fleet) will produce identical
event streams. There is no check or warning for this situation. The TODO comment at
line 1337 acknowledges this is incomplete.

**GAP — SEVERITY: MEDIUM**
HARES `WetAppliance` multi-phase power profiles (`phases: Vec<CyclePhase>`) model
variable power across a cycle (e.g., wash fill phase vs. spin phase). However in
deterministic mode (`extracted_events` present), `update_outputs()` ignores
`phase_index` and uses the extracted average power instead. The per-phase structure
is wasted in deterministic mode; callers configuring phase-resolved power AND
providing a kW series will see the phase power silently overridden. This is not
documented in config or error messages.

**GAP — SEVERITY: MEDIUM**
`EventBasedLoad` state serialization (`save_state`, lines 559-575) does not persist
`active_power_kw`. After a checkpoint restore mid-event in deterministic mode, the
first call to `step()` will re-populate `active_power_kw` from the extracted event,
but between `load_state` and the first `step()` call, `telemetry` will show 0 W
(the `new()` default). This is a one-step telemetry gap.

**GAP — SEVERITY: LOW**
OCHRE's `EventDataLoad` assigns each event an `event_type` from a set of named
power profiles (e.g., different dishwasher fill cycles), chooses the best-fit type
by minimizing combined duration and energy error, and scales energy and duration
multipliers per event. HARES has no equivalent event-type selection or energy
scaling for multi-phase cycles. This matters for realism of per-cycle energy
distribution but not for fleet-level totals if the schedule CSV drives power
directly.

**GAP — SEVERITY: LOW**
Reactive power (Q, kVAr) is tracked per step in OCHRE's legacy `WetAppliance`
(two-column P/Q profile). HARES only models active power. Not a parity issue
against OCHRE's current production code (which also drops Q in `EventBasedLoad`),
but is a gap versus the physics-correct legacy model.

**GAP — SEVERITY: LOW**
OCHRE's `update_external_control` can delay events in two modes: delay-end (default,
extends event window) or delay-start-only (capped at event end). HARES
`EventDelay` only increments `delay_remaining_s`; it does not distinguish whether
the event window (end time) should also extend. For schedule-driven deterministic
events, delaying the start without extending the end silently truncates the cycle.

### DHW Demand

DHW demand is modeled in HARES. `WetAppliance::init()` derives
`hot_water_draw_rate_kg_s = hot_water_draw_volume_l / total_cycle_duration_s`
(lines 893-902). During each active step `update_outputs()` emits a
`PortContribution::Fluid` to `DHW_DEMAND_LOOP` scaled by `load_fraction`
(lines 836-844). The port is only declared if `hot_water_draw_rate_kg_s > 0`.
OCHRE's current `EventBasedLoad` does not model DHW demand directly — hot water
draw is a separate equipment model. HARES's approach is therefore an improvement.

### Event Power Profile Shape

Neither OCHRE `EventBasedLoad` (production) nor HARES `WetAppliance` models a
ramp-up or ramp-down within an event. Power is piecewise-constant per phase
(HARES) or constant per event (OCHRE). OCHRE's legacy `WetAppliance` used a
stored set-profile array that could represent any waveform, but this class is dead
code.

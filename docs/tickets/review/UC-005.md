## Background/Context

HPXML envelope surfaces specify: `Area` (ft²), `Insulation/AssemblyEffectiveRValue`
(ft²·°F·hr/BTU), `UFactor` (BTU/hr·ft²·°F for windows). Each must be converted to SI.
The ENVELOPE-* tickets already found the window U-factor was a major source of error.

## Investigation Instructions

1. **Read `building.rs` surface parsing:**
   - Wall/roof/floor `Area` — ft² → m²? (Factor: 0.0929)
   - `AssemblyEffectiveRValue` — ft²·°F·hr/BTU → m²·K/W? (Factor: 0.17611)
   - Or is R-value inverted to U-value? What's the conversion then?
   - Window `UFactor` — BTU/hr·ft²·°F → W/m²·K? (Factor: 5.678)
   - Window `SHGC` — dimensionless, no conversion needed — confirmed?
   - `ConditionedBuildingVolume` — ft³ → m³?
   - `ConditionedFloorArea` — ft² → m²?

2. **Check for the OCHRE window U-factor bug:**
   - ENVELOPE-INDEX.md documents that OCHRE treats the HPXML U-factor (in imperial)
     as-is in SI — making windows 5.7x more insulating than intended.
   - Does HARES correctly convert? (It should — verify the fix is in place.)

3. **Compare with OCHRE `parse_hpxml_surface()`:**
   - What conversions does OCHRE apply per surface field?
   - Map each OCHRE conversion to its HARES equivalent.

4. **Write findings** with per-field conversion table.

## Findings

### F-001 (HIGH): `AssemblyEffectiveRValue` silently dropped for standard HPXML structure

**File:** `crates/hares-io/src/hpxml/building.rs:910`

```rust
parse_value_with_units(node.child("AssemblyEffectiveRValue"), ValueKind::RValue)
```

In standard HPXML, `AssemblyEffectiveRValue` is nested under the `<Insulation>` element:
```xml
<Roof>
  <Insulation>
    <AssemblyEffectiveRValue>2.194</AssemblyEffectiveRValue>
  </Insulation>
</Roof>
```

`XmlNode::child()` only searches **direct children**. On a `<Roof>` node,
`AssemblyEffectiveRValue` is not a direct child — it is a grandchild via `<Insulation>`.
The call returns `None` silently. The fallback `node.child("RValue")` also finds nothing
for walls/roofs (doors have `<RValue>` as a direct child; walls/roofs do not).

**Result:** `boundary.assembly_r_value_m2_k_w` is always `None` for
walls/roofs/floors parsed from real-world HPXML files (e.g. all ResStock fixtures in
`tests/fixtures/parity/`). LUT matching falls through to summing `r_value_layers_m2_k_w`
(nominal layer R-values), which is a less accurate proxy and can produce wrong LUT row
matches.

**Fix:** Replace `node.child("AssemblyEffectiveRValue")` with
`node.first_descendant("AssemblyEffectiveRValue")` so it finds the value regardless of
nesting depth. The `first_descendant` method already exists on `XmlNode`.

```rust
// Before (line 909-911):
let assembly_r_value_m2_k_w =
    parse_value_with_units(node.child("AssemblyEffectiveRValue"), ValueKind::RValue)
        .or_else(|| parse_value_with_units(node.child("RValue"), ValueKind::RValue));

// After:
let assembly_r_value_m2_k_w =
    parse_value_with_units(node.first_descendant("AssemblyEffectiveRValue"), ValueKind::RValue)
        .or_else(|| parse_value_with_units(node.child("RValue"), ValueKind::RValue));
```

**OCHRE comparison:** OCHRE reads `bd_data.get("Insulation", {}).get("AssemblyEffectiveRValue")` — it naturally traverses the `Insulation` dict key. HARES must replicate this two-level descent.

No test in the codebase currently covers nested `AssemblyEffectiveRValue`. The existing
`SAMPLE_XML` in `building.rs` test module uses walls with only `<Layer><NominalRValue>`,
so the bug is invisible to all existing unit tests.

### Window U-factor: HARES corrects OCHRE's known bug (PASS)

OCHRE `parse_hpxml_surface` line 209-213 explicitly converts:
```python
"U Factor (W/m^2-K)": convert(bd_data.get("UFactor"), "Btu / (hour * ft**2 * delta_degF)", "W / (m**2 * delta_degC)")
```
This conversion was NOT applied in older OCHRE code and is still absent from some OCHRE
versions. HARES applies `ValueKind::UValue` → `u_value_ip_to_si` (×5.678) unconditionally.
This is correct. Test `parses_zones_boundaries_windows_and_ducts` at line 2115 already
verifies `UFactor 0.31 IP → 1.760 W/m²·K`.

---

### R-value conversion direction (PASS)

HARES does NOT invert R to U during parsing. `r_value_ip_to_si` computes `1 / u_value_ip_to_si(1/r_ip)`, which is the correct R(SI) = R(IP) × 0.17611 identity. The assembly R-value is stored as `assembly_r_value_m2_k_w` (higher = better insulated), not as U-value. Correct.

---

### LUT unit consistency (PASS)

- OCHRE LUT (`vendors/OCHRE/.../Envelope Boundary Types.csv`): `Assembly R Value` in IP (e.g. `R-13` row = 13.07).
- HARES LUT (`defaults/envelope/Envelope Boundary Types.csv`): `Assembly R Value` in SI (e.g. `R-13` row = 2.30 m²·K/W).
- Ratio: 13.07 / 2.30 ≈ 5.68 (= IP-to-SI U-factor conversion, confirming units differ by exactly the conversion factor).
- HARES converts `assembly_r_value_m2_k_w` to SI at parse time and compares against SI LUT. OCHRE uses raw IP against IP LUT. Both are internally consistent.

Film R-value constants in `envelope_lut.rs`:
- `FILM_R_FLOOR_CEILING = 0.2642 m²·K/W` = 1.5 IP × 0.17611. PASS.
- `FILM_R_WALL_ROOF = 0.1585 m²·K/W` = 0.9 IP × 0.17611. PASS.

R≥100 IP threshold: HARES uses `r_val >= 17.6 m²·K/W` = 100 × 0.17611. PASS (minor
rounding: exact is 17.611, HARES uses 17.6; error is 0.06%, negligible).

### Foundation wall area scaling (PASS)

`parse_boundary_area` converts ft² → m² first (via `ValueKind::Area`). The depth ratio
`depth_below_grade / height` is computed from two `ValueKind::Length` values, both
converted to meters, so the ratio is dimensionless. The scale is then applied to the
already-SI area. Order is correct: ft²→m² first, then multiply by scale factor.

---

### Framing factor (PASS)

HPXML `<FramingFactor>` is a fraction (0.0–1.0). HARES reads it via `ValueKind::Raw`
and guards `0.0 < ff < 1.0` (lines 987-991). Correct. Default values of 0.25 (WoodStud,
SteelFrame) are fractions, not percentages. OCHRE does not parse framing factor from
HPXML — it relies entirely on LUT rows that already bake in framing. HARES applies
framing correction only to raw material layer paths, not to LUT-resolved paths
(documented at `boundary_rc.rs:114`). This is correct.

---

### Door U-factor audit (PASS — not applicable)

HPXML `<Door>` does not have a `<UFactor>` element in the standard schema. Doors use
`<RValue>` (direct child). HARES reads this via `parse_value_with_units(node.child("RValue"), ValueKind::RValue)` at line 911, which converts IP R-value to SI. This is correct and consistent with how OCHRE handles doors (raw IP R-value stored, matched against IP LUT; HARES uses SI R-value against SI LUT).

No door `UFactor` exists to audit.

---

### `r_value_layers_m2_k_w` Vec (PASS)

`parse_nominal_r_layers` (lines 1568-1574) uses `node.descendants("NominalRValue", ...)`
which recurses into all children, including those under `<Insulation>/<Layer>`. Each
`NominalRValue` is converted via `ValueKind::RValue`. The resulting Vec in SI is used as
a fallback when `assembly_r_value_m2_k_w` is `None`. Since F-001 causes
`assembly_r_value_m2_k_w` to always be `None` for standard HPXML, the sum of this Vec
becomes the de-facto R-value used for LUT matching in production.

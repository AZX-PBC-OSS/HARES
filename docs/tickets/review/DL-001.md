## Background/Context

ASHRAE 152 DSE (Distribution System Efficiency) is a complex calculation involving
supply/return leakage fractions, duct areas, R-values, zone temperatures, heat
exchanger effectiveness, and seasonal corrections. HARES implements this in
`ashrae152.rs`. This ticket traces the full calculation vs OCHRE's implementation.

## Algorithm Step-by-Step (OCHRE reference)

Both OCHRE and HARES follow the same structural sequence:

1. Convert inputs to IP units (ft³, ft², CFM, Btu/h, IP R-value).
2. Apply linear R-value transform: supply `2.2438 + 0.5619 * R_nom`; return `2.0388 + 0.7053 * R_nom`; uninsulated → 1.7.
3. Haversine nearest-station lookup from embedded ASHRAE152_climate_data.csv.
4. Zone temperature formulas (by zone type) to get seasonal supply/return temps and regain factors.
5. Compute ambient temps (heating: 68°F, cooling: 78°F) and seasonal enthalpy.
6. Compute supply/return zone temperatures and enthalpy.
7. Compute cycle loss (`fcycloss`) and infiltration baseline (`infil_fan_off`).
8. High-speed duct factors: `as`, `ar`, `dTe`, `Bs`, `Br`, infiltration imbalance.
9. Low-speed duct factors (multi-speed only).
10. Uncorrected delivery effectiveness (`seas_uncorr_de`).
11. Load factor (`seas_load_factor`).
12. Equipment factor (`seas_equip_factor`).
13. Delivery effectiveness with thermal regain (`seas_de`).
14. Final DSE = `seas_de * seas_equip_factor * seas_load_factor * (1 - fcycloss)`.

## Findings

### F1 — CRITICAL: `dTe_low` air density constant differs between OCHRE and HARES

**Severity: High (systematic numeric error for all multi-speed heating systems)**

OCHRE `equipment.py:322`:
```python
dTe_low = capacity_low * hvac.hvac_mult / (60 * fan_flow_low * 0.0775 * 0.24)
```

HARES `ashrae152.rs:471-472`:
```rust
let denom_low = 60.0 * flow_low * 0.075 * 0.24;
let dte_l = cap_low * hvac_mult / denom_low;
```

OCHRE uses `0.0775` (lb/ft³) in `dTe_low` but `0.075` everywhere else — including `Bs_low` and `Br_low` in the same block (`equipment.py:323-324`). HARES uses `0.075` consistently throughout. OCHRE's `0.0775` in `dTe_low` is almost certainly a transcription bug in OCHRE (the ASHRAE 152 standard uses standard air density 0.075 lb/ft³ uniformly), but it exists in the reference implementation. The difference is small (~3.3%) but creates a deterministic divergence in computed `dTe_low` for all multi-speed heating DSE results.

Per project policy (`feedback_ashrae_not_ochre.md`), HARES should target ASHRAE 152 physics, not replicate OCHRE bugs. HARES's use of `0.075` is correct per the standard. This is a known OCHRE defect that HARES intentionally does not replicate.

**Action required:** Document this intentional deviation explicitly in the code with a comment referencing OCHRE's typo, so future parity comparisons are not confused by the numeric mismatch.

### F2 — CRITICAL: `resolve_duct_dse` always passes `capacity_low_w: None` and `fan_flow_low_m3_s: None` for multi-speed systems

**Severity: High (wrong DSE for all multi-speed HVAC systems with duct losses)**

`crates/hares-equipment/src/hvac/helpers.rs:253-254`:
```rust
capacity_low_w: None,
fan_flow_low_m3_s: None,
```

This is hardcoded `None` regardless of `n_speeds`. When `n_speeds > 1`, `calculate_dse` falls back to `capacity_w` and `fan_flow_m3_s` (high-speed values) as substitutes:

`ashrae152.rs:462-463`:
```rust
let cap_low = input.capacity_low_w.unwrap_or(input.capacity_w) * W_TO_BTU_H;
let flow_low = input.fan_flow_low_m3_s.unwrap_or(input.fan_flow_m3_s) * M3S_TO_CFM;
```

For multi-speed systems the uncorrected DE uses the low-speed branch (`as_low`, `dte_low`, `bs_low`, `br_low`), but because `capacity_low_w` and `fan_flow_low_m3_s` are `None`, the "low-speed" computation is actually done using high-speed values. This makes the multi-speed calculation identical to the single-speed calculation, defeating the purpose of the `n_speeds > 1` branch entirely.

OCHRE correctly fetches `capacity_list[1]` / `flow_rate_list[1]` (low speed) and `capacity_list[2]` / `flow_rate_list[2]` (high speed) from the HVAC equipment object.

All call sites — `air_conditioner.rs:459`, `furnace.rs:122`, `furnace.rs:290`, `heat_pump/heater.rs:416` — pass only high-speed capacity/fan-flow. The `resolve_duct_dse` function signature accepts `n_speeds` but has no mechanism to receive or forward low-speed values.

**Action required:** `resolve_duct_dse` must accept `capacity_low_w: Option<f64>` and `fan_flow_low_m3_s: Option<f64>` parameters, and all call sites must supply the actual low-speed rated values when `n_speeds > 1`.

### F3 — MEDIUM: `seas_de` regain term always uses high-speed `br_high`/`ar_high` — correct but undocumented

Both OCHRE (`equipment.py:449`) and HARES (`ashrae152.rs:552`) use high-speed `Br_high`/`ar_high` in the `seas_de` thermal regain correction term regardless of `n_speeds`. This is consistent between implementations and is a known ASHRAE 152 simplification (the regain term applies to duct wall heat exchange which is evaluated at high speed). No bug, but the code contains no comment explaining why high-speed values are used in a section that otherwise uses low-speed values. This will confuse future maintainers.

**Action required:** Add a single-line comment at `ashrae152.rs:551-554` explaining that the regain correction always uses high-speed heat exchanger factors per ASHRAE 152 section 7.3.

---

### F4 — MEDIUM: Multi-speed heating equipment factor detection uses `is_heat_pump` field; OCHRE checks equipment name string

OCHRE `equipment.py:407`:
```python
elif hvac.name in ["ASHP Heater", "MSHP Heater"]:
    seas_equip_factor = 0.44 + 0.56 * seas_uncorr_de
else:
    seas_equip_factor = 0.91 + 0.09 * seas_uncorr_de
```

HARES `ashrae152.rs:533-536`:
```rust
} else if input.is_heat_pump {
    0.44 + 0.56 * seas_uncorr_de
} else {
    0.91 + 0.09 * seas_uncorr_de
}
```

HARES's approach using a boolean `is_heat_pump` is cleaner and semantically correct. The important risk is whether `is_heat_pump` is set correctly at all call sites.

- `heat_pump/heater.rs:416-417`: passes `true` — correct.
- `furnace.rs:122`: passes `false` — correct (gas furnace is not a heat pump).
- `air_conditioner.rs:459-460`: passes `false` — correct (cooling equipment factor uses a different branch entirely).

No bug. No action required.

### F5 — LOW: HARES NaN/Inf guard falls back to DSE=1.0 silently; OCHRE raises exception for DSE < 0 or > 1.1

OCHRE prints a warning for `1 < dse <= 1.1` and raises an exception for `dse < 0` or `dse > 1.1`. HARES silently falls back to `1.0` on NaN/Inf and uses `clamp(MIN_POSITIVE, 1.0)`.

`ashrae152.rs:560-565`:
```rust
if !seas_dse.is_finite() {
    return 1.0;
}
seas_dse.clamp(f64::MIN_POSITIVE, 1.0)
```

The silent fallback can mask physically degenerate configurations (extreme leakage, zero duct area) that would otherwise surface as configuration errors. The behavior is safer for production but hides misconfigured inputs.

**Action required:** Emit a `tracing::warn!` at the NaN/Inf fallback site and when `seas_dse > 1.0` before clamping (i.e., values in `(1.0, 1.1]` that OCHRE warns about). This preserves the no-panic guarantee while making misconfiguration observable in logs.

---

### F6 — LOW: `n_speeds` branching is asymmetric — OCHRE handles 1/2/4 explicitly; HARES maps any `n_speeds > 1` to two-speed

OCHRE raises `OCHREException` for unknown speed counts. HARES treats anything `> 1` as two-speed. This is a reasonable design choice for a greenfield codebase, but it silently computes DSE for 4-speed systems using only two speed points (high and low from the first two entries). OCHRE selects speeds 2 and 4 (not 1 and 2) for 4-speed systems. If HARES ever needs to handle 4-speed HVAC, the speed index selection logic must be revisited.

No immediate action required; document as a known limitation in `DuctDseInput` doc comment.

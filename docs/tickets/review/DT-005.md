## Background/Context

The EV driver actor decides when to plug in, charge, and depart based on time-of-day
schedules (e.g., depart 7:30 AM, arrive 5:30 PM). These must be in local time. A
UTC error would cause the EV to depart/arrive at wrong hours, breaking charging
schedules and SOC targets.

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### Verdict: HARES uses wall-clock local time — correct by design, but three concrete defects exist.

---

### How time flows in HARES

1. `SimClock::current_time()` returns `DateTime<FixedOffset>`. The offset is set once at construction from the weather file's `timezone_offset_h` (via `FixedOffset::east_opt(secs)`). After that the offset is frozen — no UTC conversion occurs. `clock.rs` module-level comment documents this explicitly.

2. `environment.rs:563` — `update_in_place` writes `state.current_time = clock.current_time()`. No re-conversion. The FixedOffset from the weather file is carried through the full simulation.

3. `mod.rs:482` computes:
   ```rust
   let current_minute = (env.current_time.hour() * 60 + env.current_time.minute()) as u16;
   ```
   This reads wall-clock local time directly — correct when the offset is set from the weather file.

4. `departure.rs:21` — `find_today` calls `ctx.env.current_time.weekday()` — also reads local wall-clock, consistent.

All departure/arrival comparisons operate in local civil time, not UTC. This matches OCHRE's behavior.

---

### How OCHRE handles time

OCHRE's `EV.py` does not store departure/arrival as minute-of-day integers. It uses absolute `pd.Timestamp` objects (`start_time`, `end_time`) generated in `generate_events` by adding `pd.to_timedelta(df["start_time"], unit="minute")` to a `date` object. The `date` objects are derived from `self.start_time` which carries a `tzinfo` localized from the weather file's timezone integer — also local civil time.

OCHRE does **not** implement a configurable departure schedule with `DepartureConstraint` / `DayFilter`. Departure times are stochastically sampled from EVI-Pro PDFs. HARES's deterministic `departure_minute` field is a HARES design choice with no direct OCHRE analog.

---

### DEFECT 1 — `FixedOffset` does not shift for daylight saving time (Severity: High)

`FixedOffset` is a fixed UTC offset, not an IANA timezone. For a site in `America/Denver` (UTC-7 in winter, UTC-6 in DST), the offset is baked in once from the EPW file and never changes. If the simulation spans a DST boundary, `env.current_time.hour()` will report the wrong civil hour — a departure configured at 07:00 local will fire one hour early or late across the DST transition.

Evidence:
- `crates/hares-io/src/schedule.rs:513–521` — `weather_timezone_offset` converts `timezone_offset_h` to a `FixedOffset`. No IANA resolution.
- `crates/hares-io/src/config.rs:76–82` — `civil_timezone: Option<String>` field exists but is not used anywhere in `EvDriverActor`'s departure minute computation.
- `crates/hares-core/src/actors/ev_driver/mod.rs:482` — departure comparison uses `.hour()` and `.minute()` on the fixed-offset `DateTime`.

Fix: In `maybe_roll_daily_event` and in the `current_minute` derivation (`mod.rs:482`), if `civil_timezone` is configured in the dwelling's config, convert `env.current_time` to the IANA-zoned time before extracting `.hour()` and `.minute()`. The `chrono-tz` crate is the standard approach. If `civil_timezone` is absent, document the limitation explicitly at both call sites.

---

### DEFECT 2 — `resolve_departure` applies today's `DayFilter` to a midnight-wrap departure (Severity: Medium)

`departure.rs:58–65`:
```rust
fn resolve_departure(&self, ctx: &DecisionContext) -> Option<(u32, f64)> {
    if let Some(dep_min) = ctx.next_departure_minute {
        let dc = self.find_today(ctx)?;   // DayFilter checked against today's weekday
        return Some((dep_min as u32, dc.target_soc));
    }
    ...
}
```

When `next_departure_minute` is `Some` and wraps past midnight (i.e., `dep_min < current_minute`), `find_today` resolves the `DayFilter` against today's weekday. But the departure event was rolled for the **previous** calendar ordinal. Under the midnight-wrap scenario the actor should look up the **next** day's weekday for the `DayFilter` match; instead it reads today's, potentially selecting the wrong `target_soc` for users who configure different SOC targets per weekday (e.g., weekday vs weekend commute).

Fix: When `ctx.next_departure_minute` wraps past midnight, advance the weekday by one before calling `find_today`. Alternatively, have `DayEvent` carry its `target_soc` so `resolve_departure` does not re-query the schedule.

---

### DEFECT 3 — Unit tests only cover UTC (offset 0), masking timezone offset regressions (Severity: Low)

All departure unit tests in `departure.rs` (lines 174–435) and `mod.rs` (`env_at_minute`, `TestEnvBuilder`) construct `current_time` with `FixedOffset::east_opt(0)` (UTC). A regression that incorrectly normalizes `current_time` to UTC before extracting `.hour()` would be invisible in these tests.

Fix: Add at least one parametrized departure test that constructs `current_time` with a non-zero `FixedOffset` (e.g., `FixedOffset::east_opt(-7 * 3600)`) and verifies that a departure configured at 07:00 local (minute 420) fires at the correct step.

---

### No defect: `minutes_until_departure` midnight wrap

`departure.rs:44–54` correctly handles wrap-around by adding 1440 when `diff <= 0`. The test `departure_midnight_wrap` (line 226) covers this path.

### No defect: departure_minute units

`DepartureConstraint.departure_minute` is minutes-since-midnight (u32), consistent with `current_minute` as `hour * 60 + minute`. No unit mismatch.

## Review Notes

`maybe_roll_daily_event` (mod.rs:335) uses `ordinal0() + year() * 366` for day-boundary detection — DST-vulnerable if `current_time` is UTC. `current_minute` is computed from `.hour() * 60 + .minute()` — correctness depends on `FixedOffset` carried in `current_time`.

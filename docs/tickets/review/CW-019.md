## Background/Context

Standalone dehumidifiers operate on humidity setpoint, not thermal demand. Config
includes: capacity (pints/day or L/day), energy factor (L/kWh), and humidity setpoint.

## Investigation Instructions

1. Read OCHRE dehumidifier handling — is it a `ScheduledLoad` or dedicated class?
2. Read HARES `dehumidifier.rs` — config keys consumed.
3. Build comparison table.
4. Check HPXML-001 status (DehumidistatSetpoint, FractionDehumidificationLoadServed).


## Findings

### F-1 (CRITICAL): No HPXML-to-equipment wiring exists for `<Dehumidifier>` nodes

`resolve_equipment` in `crates/hares-io/src/hpxml/equipment.rs` calls `resolve_scheduled_loads`, `resolve_hvac`, `resolve_water_heaters`, `resolve_batteries`, `resolve_ev`, and `resolve_generators`. None of these functions look for `Appliances/Dehumidifier` XML nodes. The `resolve_scheduled_loads` loop at line 70–77 of `resolve_loads.rs` is an explicit allowlist of six tags (`ClothesWasher`, `ClothesDryer`, `Dishwasher`, `Refrigerator`, `Freezer`, `CookingRange`). `Dehumidifier` is absent. Any HPXML file containing `<Dehumidifier>` will silently produce no dehumidifier equipment spec. HPXML-001 was raised to address this but is unimplemented.

OCHRE confirms this is also unimplemented on the reference side: `vendors/OCHRE/ochre/utils/hpxml.py` line 1678 contains `# TODO: add dehumidifier` in its `parse_appliances` function. OCHRE's Humidity model (`Models/Humidity.py` line 44) contains a matching `# FUTURE: Dehumidifier?`. There is no OCHRE dedicated dehumidifier class; dehumidifiers are not exercised at all in OCHRE parity runs.

### F-2 (MEDIUM): Config field comparison table

| HPXML element | HPXML unit | HARES key consumed in `dehumidifier.rs` | HARES unit | Default if absent | Notes |
|---|---|---|---|---|---|
| `<Capacity>` | pints/day | `Capacity` / `capacity_pints_day` / `capacity_l_day` | L/day (internal) | 30.0 L/day | Converted via `PINTS_TO_LITERS = 0.473176473`. Unit is pints/day per HPXML spec. No HPXML parsing code exists to route this. |
| `<EnergyFactor>` | L/kWh | `EnergyFactor` / `energy_factor` | L/kWh | 1.8 | Applied directly. IEF preferred over EF when both present. |
| `<IntegratedEnergyFactor>` | L/kWh | `IntegratedEnergyFactor` / `integrated_energy_factor` | L/kWh | 1.8 | When IEF is supplied the model emits a `tracing::warn!` that IEF with EF-era curves may deviate. No IEF-specific curve correction is applied. |
| `<DehumidistatSetpoint>` | fraction (0–1) or percent (1–100) | `DehumidistatSetpoint` / `dehumidistat_setpoint` / `target_rh` | fraction | 0.50 | `parse_rh_fraction` normalises percent to fraction. No HPXML parsing code exists to route this. |

### F-3 (MEDIUM): IEF vs EF conflation — no curve correction

HPXML distinguishes `<EnergyFactor>` (pre-2019 DOE test procedure, ANSI/AHAM DH-1-2008) from `<IntegratedEnergyFactor>` (post-2019, IEF includes standby and off-mode losses, ~30% lower than EF for same unit). The model accepts both under a single `rated_energy_factor_l_kwh` field and emits only a warn log when IEF is supplied. No correction factor or runtime partitioning (on-cycle vs. standby) is applied. Using IEF directly overestimates power consumption relative to the EF-era physics the biquadratic curves expect. See `dehumidifier.rs` lines 305–318.

### F-4 (LOW): Rated condition constant is hard-coded as 80°F / 60% RH (DOE 2019 test)

`RATED_DRY_BULB_C = 26.666...` (80°F) and `RATED_RH_FRACTION = 0.60` match the DOE 2019/IEF test conditions. Units are correct. EF-era ratings used 65°F / 60% RH (18.33°C). If a pre-2019 EF rating is paired with these rated conditions the normalisation factor will be incorrect. There is no field to override the rated-condition point.

### F-5 (LOW): `<Location>` field is silently dropped; zone routing unimplemented

All HPXML sample files place the dehumidifier in `"living space"`. If a whole-home dehumidifier serves multiple zones, the current model always attaches to `ZoneId(1)`. This is acceptable for now since multi-zone dehumidifier routing is out of scope, but the silent drop should be documented.

### F-6 (LOW): `update_control` called redundantly inside `step`

`step` calls `update_control` then immediately calls `update_is_on` again through `performance_snapshot`. Actually looking at the code: `step` calls `self.update_control(env)` at line 407 and then calls `self.performance_snapshot(zone.temperature_c, ...)` which reads `self.is_on`. This is correctly sequenced. No double-update bug — but `update_control` is also called separately by the engine's control phase before `step`, so control is actually applied twice per timestep. This is consistent with other equipment in the codebase but worth noting.

### F-7 (LOW): No `UsageMultiplier` extension passthrough for dehumidifier

HPXML's `extension/UsageMultiplier` is threaded through for washers, dryers, dishwashers, and ranges in `resolve_loads.rs`. There is no equivalent mechanism for dehumidifiers. Since dehumidifier output is physics-driven (not schedule-driven), this gap is not a blocker but would be needed for fleet-level scenario modelling.

---

### Summary

The root defect is F-1: the equipment model is fully implemented and correct at the physics level but completely unreachable from HPXML because `resolve_loads.rs` does not iterate over `Appliances/Dehumidifier` nodes. All other findings are secondary to this wiring gap. HPXML-001 (unimplemented) covers the fix.

## Recommended Tests

All tests should live in `crates/hares-io/tests/` or as `#[test]` functions in `equipment.rs`.

**T-1 — HPXML round-trip: EF portable dehumidifier**
Parse an HPXML snippet containing:
```xml
<Dehumidifier>
  <SystemIdentifier id='D1'/>
  <Type>portable</Type>
  <Location>living space</Location>
  <Capacity>40.0</Capacity>
  <EnergyFactor>1.8</EnergyFactor>
  <DehumidistatSetpoint>0.5</DehumidistatSetpoint>
  <FractionDehumidificationLoadServed>1.0</FractionDehumidificationLoadServed>
</Dehumidifier>
```
Assert: `resolve_equipment` returns exactly one spec with `name == "Dehumidifier"`, `parameters["Capacity"] == 40.0` (pints/day), `parameters["EnergyFactor"] == 1.8`, `parameters["target_rh"] == 0.5`, `parameters["fraction_dehumidification_load_served"] == 1.0`.

**T-2 — HPXML round-trip: IEF whole-home dehumidifier**
Same structure but with `<IntegratedEnergyFactor>1.5</IntegratedEnergyFactor>` and `<Type>whole-home</Type>`.
Assert: spec has `parameters["IntegratedEnergyFactor"] == 1.5` and `parameters["dehumidifier_type"] == "whole-home"`.

**T-3 — Multiple dehumidifiers produce multiple specs**
Use the `base-appliances-dehumidifier-multiple.xml` fixture (two `<Dehumidifier>` nodes with `FractionDehumidificationLoadServed` of 0.5 and 0.25).
Assert: `resolve_equipment` returns two specs, fraction sums correctly, names are distinct.

**T-4 — Missing fields fall back to defaults without panic**
Parse a bare `<Dehumidifier><SystemIdentifier id='D1'/></Dehumidifier>` (no `Capacity`, no `EnergyFactor`, no `DehumidistatSetpoint`).
Assert: no error, spec is produced, equipment `init` succeeds with default values (`capacity_l_day ~= 30.0`, `EnergyFactor ~= 1.8`, `target_rh == 0.5`).

**T-5 — Capacity unit conversion fidelity**
Construct an `EquipmentConfig` with `Capacity = 40.0` (pints/day) and `capacity_l_day = 18.927...` (40 × 0.473176...) and assert both initialise to the same `rated_water_removal_l_day` within float tolerance. This test belongs in `dehumidifier.rs` and verifies the unit-branching logic at lines 282–297 is consistent.

**T-6 — IEF warning is emitted**
Construct an `EquipmentConfig` with `IntegratedEnergyFactor = 1.5`. Capture tracing output or verify `rated_energy_factor_l_kwh == 1.5` after `init`. Confirms IEF is accepted without error and that the warn path is exercised (important for CI coverage).

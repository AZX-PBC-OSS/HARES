## Background/Context

`EquipmentSpec` uses `Map<String, Value>` (serde_json) for parameters. The HPXML
resolver writes keys like `"capacity_w"`, `"eir"`, `"fan_power_w"` as strings.
Equipment reads them with `.get("capacity_w")`. If the resolver writes `"capacity_W"`
and equipment reads `"capacity_w"`, the value is silently missing and a default is
used — a silent, hard-to-debug bug.

This is the single most dangerous architectural pattern in the codebase. Every
CW-series ticket is ultimately checking whether magic string keys match between
writer and reader.

## Investigation Instructions

1. **Inventory all config keys written by each HPXML resolver:**
   - `resolve_hvac.rs` — list every `.insert("key", value)` call
   - `resolve_water_heater.rs` — same
   - `resolve_der.rs` — same
   - `resolve_loads.rs` — same
   - Count total unique keys.

2. **Inventory all config keys read by each equipment model:**
   - For each equipment file, list every `.get("key")` or similar access
   - Count total unique keys.

3. **Cross-reference writer vs reader:**
   - Are there keys written but never read? (Dead config)
   - Are there keys read but never written? (Missing config, silently defaulted)
   - Are there case/spelling mismatches?

4. **Assess type safety alternatives:**
   - **Option A: Typed config structs per equipment** — e.g., `FurnaceConfig { capacity_w: f64, eir: f64, ... }` with `#[serde(deny_unknown_fields)]`.
     Pro: compile-time safety, IDE autocomplete. Con: one struct per equipment type.
   - **Option B: Shared key constants module** — `pub const CAPACITY_W: &str = "capacity_w";`
     used by both writer and reader. Pro: smaller change. Con: still string-based at runtime.
   - **Option C: Builder pattern** — equipment-specific builders that validate required
     fields at construction. Pro: runtime validation. Con: more code.
   - Recommend which approach (or combination) best fits HARES.

5. **Assess the `overrides` path:** When Python kwargs override equipment config via
   `nested_update()`, how are key names validated? Can a user pass a misspelled key
   and have it silently ignored?

## Recommended Tests

1. **End-to-end key round-trip test for gas water heater:** Construct an `EquipmentConfig`
   with `"fuel_type": "Gas"` (as `build_spec` writes it) and verify `GasWH::init` correctly
   reads the fuel type as `FuelType::Gas`. Currently this test would fail because the
   reader looks up `"FuelType"` (PascalCase).

2. **End-to-end key round-trip test for tankless water heater:** Same as above — verify
   `TanklessWH::new` and `TanklessWH::init` correctly read fuel type from `"fuel_type"` key.

3. **EV capacity key round-trip test:** Write `"battery_capacity_kwh"` into config (as
   `resolve_loads.rs` does for the PlugLoad EV path), construct an `Ev` from that config,
   and verify it reads the correct capacity. Currently this silently defaults to
   `DEFAULT_CAPACITY_KWH = 75.0 kWh`.

4. **Ventilation flow rate key round-trip test:** Write `"ventilation_rate_cfm"` into config
   (as `resolve_loads.rs` does), construct a `Ventilation` equipment from that config, and
   verify the flow rate is used. Currently this silently defaults to `DEFAULT_FLOW_RATE_M3_S`.

5. **Ventilation effectiveness key round-trip test:** Write `"sensible_recovery_efficiency"`
   and `"latent_recovery_efficiency"` into config (as the resolver writes), construct a
   `Ventilation` equipment, and verify those values are used. Currently this silently
   defaults because the reader expects `"sensible_effectiveness"` and `"latent_effectiveness"`.

6. **Override key validation gap test:** Verify that passing a misspelled key to the
   overrides dict (e.g., `{"Gas Furnace": {"heating_efficiencyy": 0.9}}`) is silently
   ignored with no warning. Document this as the known-unfixed gap.

7. **`fuel_type` Debug format stability test:** Write `FuelType::Electric` and
   `FuelType::Gas` using `format!("{:?}")` and assert the strings are exactly `"Electric"`
   and `"Gas"`. This pins the contract that `parse_fuel_type` depends on.

### FINDING 1 — BUG (HIGH): `GasWH` and `TanklessWH` read wrong fuel_type key

**Files:**
- `crates/hares-equipment/src/water_heater/gas.rs:350`
- `crates/hares-equipment/src/water_heater/tankless.rs:80,171`
- `crates/hares-io/src/hpxml/equipment.rs:88`

**Evidence:**

`build_spec` in `equipment.rs:88` writes the fuel type into every `EquipmentSpec.parameters`
under the key `"fuel_type"` using `format!("{fuel_type:?}")` — producing strings `"Electric"`,
`"Gas"`, `"Propane"`, `"Oil"`, `"None"`.

`GasWH::init` at `gas.rs:350` reads:

```rust
self.fuel_type = parse_fuel_type(config.get_str("FuelType")).unwrap_or(FuelType::Gas);
```

`TanklessWH::new` at `tankless.rs:80` and `TanklessWH::init` at `tankless.rs:171` both read:

```rust
let fuel_type = parse_tankless_fuel_type(config.get_str("FuelType"));
```

The key `"FuelType"` (PascalCase, the HPXML XML tag name) does not match the key `"fuel_type"`
(snake_case) that `build_spec` writes. `config.get_str("FuelType")` returns `None` in all
HPXML-sourced configs.

**Impact:**

- `GasWH` silently defaults to `FuelType::Gas`. This happens to be correct for gas water
  heaters, masking the bug entirely in normal use.
- `TanklessWH` calls `parse_tankless_fuel_type(None)` which defaults to `FuelType::Electric`
  (`parse_tankless_fuel_type` falls back to `Electric` when given `None`). A gas tankless
  water heater created from HPXML will have `fuel: FuelType::Electric` in its descriptor,
  which means it will report wrong fuel consumption, wrong port types, and wrong end-use
  accounting. This is an active correctness bug for gas tankless water heaters.

**Fix:** Change `gas.rs:350` and `tankless.rs:80,171` to read `"fuel_type"` instead of
`"FuelType"`. Alternatively, have `resolve_water_heater.rs` write both `"fuel_type"` (via
`build_spec`) and a separate `"FuelType"` key, but that deepens the inconsistency. The
correct fix is to normalise the reader to use `"fuel_type"`.

### FINDING 2 — BUG (HIGH): `resolve_loads.rs` EV path writes `"battery_capacity_kwh"`, EV model reads `"capacity_kwh"`

**Files:**
- `crates/hares-io/src/hpxml/resolve_loads.rs:425`
- `crates/hares-equipment/src/ev/config.rs:8` (`KEY_BATTERY_CAPACITY_KWH = "capacity_kwh"`)
- `crates/hares-equipment/src/ev/config.rs:9` (`KEY_BATTERY_CAPACITY_HPIXML_KWH = "BatteryCapacity"`)

**Evidence:**

When resolving a `<PlugLoad><PlugLoadType>electric vehicle charging</PlugLoadType>` entry,
`resolve_loads.rs:425` writes:

```rust
ev_params.insert("battery_capacity_kwh".to_string(), json!(battery_capacity_kwh));
```

The `Ev` model's `resolve_capacity_kwh` function at `ev/config.rs:68-69` reads only
`KEY_BATTERY_CAPACITY_KWH` (`"capacity_kwh"`) and `KEY_BATTERY_CAPACITY_HPIXML_KWH`
(`"BatteryCapacity"`). Neither key matches `"battery_capacity_kwh"`.

**Impact:**

Any EV defined via the PlugLoad path in HPXML will silently ignore the resolved battery
capacity. The `Ev` model will default to `DEFAULT_CAPACITY_KWH = 75.0 kWh`, regardless of
the range-miles calculation in the resolver. The `"range_miles"` key written at `resolve_loads.rs:420`
is also not read by the EV model (the model only reads `KEY_RANGE_MILES = "range_miles"` in
a fallback path, but `resolve_capacity_kwh` tries `"capacity_kwh"` first and `"BatteryCapacity"`
second — `"battery_capacity_kwh"` is never tried). Checking `ev/config.rs:77`: `"range_miles"`
is attempted if the direct `capacity_kwh` lookup fails. So in practice the PlugLoad EV path
will fall through to `resolve_capacity_kwh` → first two keys miss → `range_miles` is found →
capacity computed from range. The `"battery_capacity_kwh"` key is therefore dead config.

**Fix:** Change `resolve_loads.rs:425` to write `"capacity_kwh"` (matching
`KEY_BATTERY_CAPACITY_KWH`), not `"battery_capacity_kwh"`.

### FINDING 3 — BUG (HIGH): Ventilation resolver writes wrong keys for flow rate and effectiveness

**Files:**
- `crates/hares-io/src/hpxml/resolve_loads.rs:554,578,585`
- `crates/hares-equipment/src/ventilation.rs:32-34`

**Evidence:**

`resolve_ventilation` in `resolve_loads.rs` writes:

| Key written by resolver | Key read by `Ventilation::init` |
|-------------------------|----------------------------------|
| `"ventilation_rate_cfm"` (line 554) | `"flow_rate_m3_s"` (`KEY_FLOW_RATE_M3_S`) |
| `"sensible_recovery_efficiency"` (line 578) | `"sensible_effectiveness"` (`KEY_SENSIBLE_EFFECTIVENESS`) |
| `"latent_recovery_efficiency"` (line 585) | `"latent_effectiveness"` (`KEY_LATENT_EFFECTIVENESS`) |

None of these three key pairs match. Additionally, the resolver writes the flow rate in CFM
(`RatedFlowRate` in HPXML is in CFM) but the model reads `"flow_rate_m3_s"`. Even if the key
names matched, the unit would be wrong (1 CFM ≈ 0.000472 m³/s).

**Impact:** Every ventilation fan parsed from HPXML will silently use:
- `DEFAULT_FLOW_RATE_M3_S` for the flow rate (ignoring the HPXML value).
- `DEFAULT_SENSIBLE_EFFECTIVENESS = 0.0` for sensible recovery (even for HRV/ERV fans with
  real SRE values).
- `DEFAULT_LATENT_EFFECTIVENESS = 0.0` for latent recovery.

This is a complete loss of HRV/ERV effectiveness data from HPXML. The `"fan_power_w"` key
is correctly matched, so fan electrical power is correctly propagated.

**Fix:** In `resolve_loads.rs`:
1. Convert `flow_cfm` to m³/s before writing and write it as `"flow_rate_m3_s"`.
2. Rename the written key `"sensible_recovery_efficiency"` to `"sensible_effectiveness"`.
3. Rename the written key `"latent_recovery_efficiency"` to `"latent_effectiveness"`.

### FINDING 4 — BUG (MEDIUM): `fuel_type` serialized via Debug format — fragile contract with no compile-time guard

**Files:**
- `crates/hares-io/src/hpxml/equipment.rs:88`
- `crates/hares-equipment/src/hvac/helpers.rs:107-115`
- `crates/hares-equipment/src/water_heater/gas.rs:350`
- `crates/hares-equipment/src/event_load.rs:446,884`

**Evidence:**

`build_spec` writes:

```rust
Value::String(format!("{fuel_type:?}"))
```

`FuelType` derives `#[derive(Debug)]`, so the output is the variant name: `"Electric"`, `"Gas"`,
`"Propane"`, `"Oil"`, `"None"`. Readers call `parse_fuel_type(config.get_str("fuel_type"))`,
which calls `normalize_ascii` (lowercase), then matches `"electric"`, `"gas"`, etc. This
round-trips correctly because `"Electric"` → lowercase `"electric"` → matched.

However, if any future refactor adds a `#[derive]` attribute or a custom `Debug` impl that
changes the output (e.g. `"FuelType::Electric"` or `"electric_fuel"`), all fuel-type-gated
behaviour silently uses the fallback. There is no compile-time test of this contract.

Note that `gas.rs:350` reads `"FuelType"` not `"fuel_type"`, compounding this (see Finding 1).
`event_load.rs:446,884` reads `config.get_str("fuel_type")` correctly (snake_case).

**Fix:** Pin the serialization format. Either:
- Add a `Display` impl to `FuelType` that produces a stable lowercase string, and write
  `format!("{fuel_type}")` instead of `"{fuel_type:?}"`.
- Or add a `const` mapping from `FuelType` → `&str` and use it for both writer and all readers.
- Add a test that asserts `format!("{:?}", FuelType::Electric) == "Electric"` etc. for all
  variants, acting as a compile-time tripwire.

### FINDING 5 — BUG (MEDIUM): EV resolver (HPXML `<ElectricVehicle>` path) uses PascalCase keys not read by `Ev` model

**Files:**
- `crates/hares-io/src/hpxml/resolve_der.rs:115-121`
- `crates/hares-equipment/src/ev/config.rs:10-13`

**Evidence:**

`resolve_ev` in `resolve_der.rs` writes PascalCase keys from the HPXML XML tag names:

```rust
params.insert("ChargingLevel".to_string(), ...);
params.insert("MaxChargingPower".to_string(), ...);
params.insert("BatteryCapacity".to_string(), ...);
```

The `Ev` model's `charging_level_from_config` at `ev/mod.rs:31-32` reads both
`KEY_CHARGING_LEVEL` (`"charging_level"`) and `KEY_CHARGING_LEVEL_HPIXML` (`"ChargingLevel"`).
`resolve_rated_power_kw` at `ev/config.rs:91-92` reads both `KEY_MAX_CHARGING_POWER_KW`
(`"max_charging_power_kw"`) and `KEY_MAX_CHARGING_POWER_HPIXML_KW` (`"MaxChargingPower"`).
`resolve_capacity_kwh` at `ev/config.rs:68-69` reads both `KEY_BATTERY_CAPACITY_KWH`
(`"capacity_kwh"`) and `KEY_BATTERY_CAPACITY_HPIXML_KWH` (`"BatteryCapacity"`).

The `Ev` model has explicit HPXML alias constants for these PascalCase keys. So for the
`resolve_der.rs` path the keys are deliberately paired and currently work.

**Status:** ACCEPTABLE for the `resolve_der.rs` EV path. The dual-alias pattern is an
intentional bridge but is opaque — it would benefit from a comment linking the PascalCase
constants to `resolve_der.rs`.

However, the `resolve_loads.rs` PlugLoad EV path writes `"battery_capacity_kwh"` (neither
the canonical `"capacity_kwh"` nor the HPXML alias `"BatteryCapacity"`), so that path's
capacity key is still broken (see Finding 2).

### FINDING 6 — GAP: Override keys are never validated — misspelled override keys silently no-op

**Files:**
- `crates/hares-io/src/hpxml/equipment.rs:59-78` (`apply_overrides`)
- `crates/hares-core/src/dwelling/conversions.rs:358-368` (`apply_equipment_overrides`)

**Evidence:**

`nested_update` merges a user-supplied `Map<String, Value>` into the equipment parameters map
without any schema validation. If a user passes `{"Gas Furnace": {"heating_efficiencyy": 0.95}}`
the extra `y` causes the override to be silently stored as a dead key, with no warning emitted.
The same applies to Python callers supplying `Equipment` kwargs that traverse the `python_to_json`
→ `apply_overrides` path.

OCHRE has the same behaviour (pure dict merge, no schema). This is an acceptable gap in
OCHRE-parity terms but is a genuine usability hazard.

**Impact:** Users writing automation or tests that tune equipment parameters via overrides have
no feedback when a key is mistyped.

**Fix:** No immediate code change required. Document the gap. Long-term, the typed-config
alternative (Finding 8) would close this.

### FINDING 8 — IMPROVEMENT: Three-way name contract is unguarded

**Files:**
- `crates/hares-io/src/hpxml/resolve_hvac.rs` (name producer: `canonical_hvac_heating_name`, etc.)
- `crates/hares-core/src/dwelling/conversions.rs:338` (`ochre_class: spec.name.clone()`)
- `crates/hares-equipment/src/registry.rs:44` (registry key)

**Evidence:**

The full name pipeline is:

1. `resolve_*.rs` canonical name function produces a string such as `"Gas Furnace"`.
2. `equipment_config_from_spec` copies `spec.name` → `EquipmentConfig.ochre_class`.

character, the equipment silently falls back to the `Err` branch at `dwelling/mod.rs:864`
with a warning log and the equipment is skipped. No compile-time guard exists.

All currently registered names were verified to match:

### FINDING 9 — IMPROVEMENT: Type safety assessment

**Current approach:** Flat `HashMap<String, ConfigValue>` with string keys. Both writer
(HPXML resolver) and reader (equipment `init`) use raw string literals.

**Option A: Typed config structs per equipment** — e.g., `GasFurnaceConfig { capacity_w: f64, afue: f64, ... }` with `#[serde(deny_unknown_fields)]`.

Pros: Compile-time safety for all fields; unknown keys become hard errors at deserialization.
Cons: ~20 new structs; significant refactor of all equipment `init` signatures; rigid — makes
Python override injection harder since the map-based merge must occur before deserialization.
Cost: High. Not recommended for this codebase given the Python-extensibility requirement.

**Option B: Shared key constants module** — a single `crates/hares-equipment/src/keys.rs`
(or per-equipment `config.rs` as already done for `ev/config.rs`, `battery/mod.rs`) exporting
`pub const` strings used by both writer and reader.

Pros: Minimal change; reuses the existing pattern in `ev/config.rs`; the compiler sees a
constant reference at both the insert and the get site; text search for a constant name finds
all uses.
Cons: Still string-based at runtime; a constant containing a wrong value would go undetected
until tested; does not prevent override typos from Python.
Cost: Medium. **Recommended as the primary fix** for all config keys. Every equipment that
currently uses inline string literals in `init()` should move to a `config.rs` side-file
with named constants, mirroring what `ev/config.rs` already does.

**Option C: Builder pattern with required-field validation** — each equipment exposes a
`FurnaceConfigBuilder` that panics or returns `Err` when a required field is absent.

Pros: Runtime validation catches missing required keys during `init`.
Cons: Verbose; does not protect against key misspellings in overrides; still does not give
compile-time safety.
Cost: Medium. Useful as a supplement to Option B, not a replacement.

**Recommended approach:** Adopt Option B as a mandatory standard:
1. Every equipment module that uses inline string keys in `init()` must migrate to a
   `config.rs` side-file with named `pub const` keys.
2. The HPXML resolvers must import and use those same constants when inserting into `params`.
3. A `#[test] fn all_written_keys_are_named_constants()` lint test (or clippy rule) should
   be added to prevent future regressions.

### FINDING 10 — ACCEPTABLE: Cross-cutting keys injected by `build_spec` are consistent

**File:** `crates/hares-io/src/hpxml/equipment.rs:80-113`

`build_spec` injects three cross-cutting keys into every `EquipmentSpec`:
- `"fuel_type"` (string, Debug format of `FuelType`)
- `"sensible_gain_fraction"` (f64, from `default_gain_fractions`)
- `"latent_gain_fraction"` (f64, from `default_gain_fractions`)

Guard logic checks for legacy aliases `"frac_sensible"` / `"frac_latent"` before inserting
to avoid clobbering HPXML-provided values.

Equipment readers that consume these keys:
- `event_load.rs:436-441` reads `"sensible_gain_fraction"` with fallback to `"frac_sensible"`. Consistent.
- `scheduled_load.rs:246-247` reads `"sensible_gain_fraction"` with fallback to `"frac_sensible"`. Consistent.
- `event_load.rs:446` / `scheduled_load.rs` reads `"fuel_type"`. Consistent (snake_case).

This is an acceptable pattern. The cross-cutting keys are handled correctly.

## Review Notes

- Three-way magic string contract: `resolve_*.rs` (name producer) → `EquipmentSpec.name` → `equipment_config_from_spec()` sets `ochre_class: spec.name.clone()` → `registry.create()` looks up `ochre_class`. All three legs must spell the string identically.
- `build_spec` in `equipment.rs` injects cross-cutting keys (`"fuel_type"`, `"sensible_gain_fraction"`, `"latent_gain_fraction"`) not in any resolver — needs separate inventory entry.
- `fuel_type` is serialized with `{fuel_type:?}` (Debug format) then inserted as a string key. If `FuelType` Debug output changes, all fuel-type-gated behavior silently breaks.
- Investigation question: "Trace the equipment name → ochre_class → registry key pipeline for every equipment type."

## Background/Context

Gas water heaters have a single burner (bottom), recovery efficiency, pilot light,
and flue losses. Config differs from ERWH in efficiency handling and combustion.

## Investigation Instructions

1. Read OCHRE `GasWaterHeater.py` — all config keys.
2. Read HARES `gas.rs` — config keys consumed.
3. Build comparison table with attention to:
   - Recovery efficiency (eta_c) derivation from EF
   - Pilot light power
   - Flue losses / tank UA
   - Volume correction factor (0.95 for gas)


## Findings

### Finding F-1: `fuel_type` key casing mismatch (AR-002 recurrence)

`build_spec()` at `crates/hares-io/src/hpxml/equipment.rs:87` writes `"fuel_type"` (snake\_case, Rust `Debug` produces `"Gas"`). `GasWH::init()` at `gas.rs:350` reads `config.get_str("FuelType")` (PascalCase). These keys never match. The fuel always falls through to `unwrap_or(FuelType::Gas)`, which is accidentally correct for gas WHs but masks the bug and will fail for propane or oil-fired WHs (when those are added).

Evidence: `equipment.rs:87`, `gas.rs:350`.

Severity: **Medium** — silent no-op for gas, latent defect for other fuels.

### Finding F-2: `"EnergyFactor"` / `"UniformEnergyFactor"` case mismatch → `burner_efficiency_constant` always defaults to 0.78

`resolve_water_heater.rs:64-68` inserts keys `"energy_factor"` and `"uniform_energy_factor"` (all lowercase). `gas.rs:338-347` reads via `first_f64(config, &["burner_efficiency", "thermal_efficiency", "EnergyFactor", "UniformEnergyFactor"])`. PascalCase lookups miss the lowercase keys. `burner_efficiency_constant` is always `DEFAULT_BURNER_EFFICIENCY = 0.78` regardless of the actual EF in HPXML.

This cascades to `skin_loss_fraction`: the default\_skin\_loss\_fraction threshold is evaluated against 0.78, always producing 0.91. For a WH with EF < 0.70 the correct fraction is 0.64 — a 42% error in zone heat gain from standby losses.

Evidence: `resolve_water_heater.rs:64-68`, `gas.rs:338-347`, `gas.rs:353-356`.

Severity: **High** — standby skin loss to zone is wrong for all EF values; particularly wrong for low-EF units.

### Finding F-3: `recovery_efficiency` not written to params

`resolve_water_heater.rs:37` reads `RecoveryEfficiency` from HPXML. It is passed into `UaInputs` for the UA derivation at line 90, but is never written into `params`. No downstream equipment code can access the bare recovery efficiency. This is not a direct operational error today (the value only affects UA derivation which is handled), but it means any equipment code that might need RE (e.g., future reporting or diagnostics) cannot recover it.

Evidence: `resolve_water_heater.rs:37,90` — no `params.insert("recovery_efficiency", ...)` call exists.

Severity: **Low** — informational gap, no current runtime error.

### Finding F-4: `conversion_efficiency` (eta\_c) computed but silently dropped

`water_heater_ua.rs:ua_for_gas_storage()` computes `eta_c = RE + ua*(T-T_env)/heating_capacity` and stores it in `UaResult::conversion_efficiency`. This is the OCHRE-equivalent `"Efficiency (-)"` parameter — the net fraction of fuel input that reaches the water. The resolver at `resolve_water_heater.rs:95-96` only writes `ua_result.ua_w_per_k`; `ua_result.conversion_efficiency` is never forwarded to `params`.

Consequence: `GasWH` uses `burner_efficiency_constant = 0.78` (the bare recovery efficiency default) and then additionally applies `flue_loss_fraction = 0.10`, yielding net efficiency `0.78 × (1-0.10) = 0.702`. OCHRE uses `eta_c` directly (typically ~0.782 for EF=0.59, RE=0.76, 36 kBtu/hr), applying it as a single multiplier with no separate flue deduction. HARES underestimates delivered heat by approximately `(0.782 - 0.702)/0.782 ≈ 10%` relative to OCHRE for a typical gas storage WH.

Fix requires: (a) writing `conversion_efficiency` to params as `"burner_efficiency"`, (b) setting `flue_loss_fraction = 0.0` for HPXML-derived configurations (or restructuring the model to use a single net-efficiency parameter matching OCHRE).

Evidence: `water_heater_ua.rs:166-167,188-189`, `resolve_water_heater.rs:95-96`, `gas.rs:338-347,425-428`.

Severity: **Critical** — ~10% error in fuel consumption and heat delivered to tank for all gas storage WHs loaded from HPXML.

### Finding F-5: Tank jacket R-value correction formula diverges from OCHRE

OCHRE (`hpxml.py:1133-1138`) models the jacket as modifying a pre-existing tank skin conductance using:
```python
u_pre_skin = 1.0 / (jacket_thickness * 5.0 + 1/1.3 + 1/52.8)
ua_corrected = ua_base - tank_jacket_r / (1/u_pre_skin + tank_jacket_r) * u_pre_skin * a_side
```
`jacket_thickness` is 1 inch for electric WH with EF<0.7, else 2 inches. This accounts for the existing tank foam insulation plus convective boundary layers, applying the added jacket as a parallel resistance to the skin layer only.

HARES (`mod.rs:136-151`) instead adds the jacket R directly in series to the total UA:
```rust
let r_total = 1.0 / ua_base + jacket_r / lateral_area_m2;
```
This is physically wrong: `ua_base` is derived from the EF (already incorporating all tank insulation), so adding another R in series double-counts. OCHRE's formula correctly adds the jacket R in parallel to the existing skin conductance (reducing only the jacket-accessible losses, not the end-cap losses).

Additionally, OCHRE applies jacket correction before writing `"UA (W/K)"` to the output dict; HARES splits it — UA is corrected at `init()` time, not at resolution time. This is architecturally fine but the formula must match.

Evidence: `vendors/OCHRE/ochre/utils/hpxml.py:1133-1138`, `crates/hares-equipment/src/water_heater/mod.rs:149-151`.

Severity: **Medium** — jacket is uncommon in HPXML inputs but will produce wrong UA when present.

### Finding F-6: Pilot light always assumed (IgnitionType never extracted)

HARES reads `["ignition_type", "IgnitionType"]` in `gas.rs:294-295` to decide whether to apply `DEFAULT_PILOT_POWER_W = 5.0`. However, `resolve_water_heater.rs` never reads `IgnitionType` from the `<WaterHeatingSystem>` node or any extension, so the key is absent from `params`. `ignition_uses_standing_pilot(None)` returns `true` (line 787 default). Every gas storage WH gets 5 W standing pilot power regardless of HPXML content.

Real HPXML files (e.g., ResStock-generated) do include `<PilotLight>false</PilotLight>` for electronic ignition units. OCHRE also has this commented out (`hpxml.py:844-845`) — it is not actively parsed in OCHRE either, so this is a HARES internal inconsistency rather than a parity gap, but it is still an unresolved data-flow error: the `gas.rs` code anticipates the key being present but the resolver never supplies it.

Fix: either extract `<PilotLight>` from `<extension>` in the resolver and write `"ignition_type"` to params, or change the `gas.rs` default to `false` (no pilot) to match the OCHRE/ResStock ResStock population median (most modern units are electronic ignition).

Evidence: `gas.rs:294-302`, `resolve_water_heater.rs` (no IgnitionType extraction), `vendors/OCHRE/ochre/defaults/Input Files/bldg0112631-up00.xml:1301`.

Severity: **Medium** — adds ~5 W continuous fuel load to every gas WH from HPXML; 5 W × 8760 h ≈ 43.8 kWh/yr added gas consumption.

### Finding F-7: Dual efficiency model (burner\_efficiency × flue\_loss\_fraction) is incompatible with OCHRE's single eta\_c model

OCHRE represents gas WH thermal efficiency as a single `eta_c` (net efficiency): `fuel_kW = delivered_heat_W / eta_c / 1000`. There is no separate flue loss; flue losses are implicitly captured in `eta_c`.

HARES uses `gross_heat_w = burner_input_w * burner_efficiency` then `tank_heat_w = gross_heat_w * (1 - flue_loss_fraction)`. Net efficiency = `burner_efficiency * (1 - flue_loss_fraction)`. Defaults: 0.78 × 0.90 = 0.702.

OCHRE's typical `eta_c` for the parity fixture (EF=0.59, RE=0.76, 36 kBtu/hr): `eta_c = RE + ua*(T-T_env)/capacity ≈ 0.782`. HARES net efficiency 0.702 vs OCHRE 0.782 → ~10% underdelivery to tank, ~10% excess fuel consumption reported.

This finding overlaps F-4 but is stated separately because it requires a model-level design decision: either eliminate `flue_loss_fraction` for HPXML paths (set it 0, use `eta_c` as `burner_efficiency`), or re-derive `flue_loss_fraction` from the DOE test and write both consistently from the resolver.

Evidence: `gas.rs:425-428`, `vendors/OCHRE/ochre/Equipment/WaterHeater.py:276,284-286`.

Severity: **Critical** (duplicate of F-4 root cause, included for completeness).

### Finding F-8: Skin loss fraction threshold uses wrong proxy value

`default_skin_loss_fraction(ef)` thresholds on `ef < 0.70` and `ef < 0.80`. OCHRE thresholds on `"Energy Factor (-)"` which is the full EF from HPXML. HARES thresholds on `burner_efficiency_constant`, which as shown in F-2 is always 0.78 (default) due to key casing mismatch. Gas WHs with EF < 0.70 will use `skin_loss_fraction = 0.91` instead of `0.64` — a 42% overestimate of zone heat gain from standby losses.

Evidence: `gas.rs:353-356`, `gas.rs:739-749`.

Severity: **High** (root cause is F-2; severity amplified by the 42% magnitude).

### Finding F-9: Solar fraction not applied to UA

OCHRE applies `ua *= (1 - solar_fraction)` at `hpxml.py:1139`, where `solar_fraction` is passed in when a solar thermal system is present. HARES has no solar thermal equipment model and makes no attempt to read `FractionDHWLoadServed` or a solar fraction from HPXML. For homes without solar thermal this is a no-op. For homes with solar thermal the UA and delivered heat will be overstated.

This is an acceptable gap given solar thermal is not yet in scope, but should be flagged.

Evidence: `vendors/OCHRE/ochre/utils/hpxml.py:1013,1139`, resolver has no solar fraction handling.

Severity: **Low** — out of scope until solar thermal is modelled.

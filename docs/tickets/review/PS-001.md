## Background/Context

`Dwelling.from_hpxml()` accepts `**kwargs` that are converted to a JSON blob via
`python_to_json()`. This is maximally brittle: misspelled keys are silently ignored,
wrong types are silently coerced or dropped, and there's no IDE autocomplete or
type checking. Users get no feedback when they pass `capacty_w=5000` instead of
`capacity_w=5000`.

## Investigation Instructions

1. **Inventory every kwarg `from_hpxml()` accepts:**
   - Read `py_dwelling.rs` — what kwargs are extracted?
   - Read `py_config.rs` — what config fields exist?
   - Are any kwargs documented? In docstrings? In type stubs?

2. **Trace the kwargs→config path:**
   - `python_to_json()` — what type coercion happens?
   - Can a Python `int` silently become a string? Can `None` silently drop a field?
   - What happens with unexpected kwargs? Silently ignored? Error?

3. **Inventory `SimulationConfig` Python exposure:**
   - Is it a typed pyclass with getters/setters? Or a dict?
   - Can users construct it with wrong types?

4. **Assess alternatives:**
   - **Typed pyclass with `__init__` parameters** — IDE autocomplete, type errors at call site.
   - **Pydantic model** — runtime validation, JSON schema, error messages.
   - **`@dataclass` + `__post_init__` validation** — lighter than Pydantic.
   - **Keep kwargs but validate** — check for unknown keys, validate types at boundary.
   - Recommend the best approach.

5. **Check `overrides` dict specifically:**
   - How does the user override per-equipment config?
   - Can they pass `{"wrong_equipment_name": {"capacity_w": 5000}}` and have it
     silently ignored?
   - What validation exists?

## Review Notes

`from_hpxml` silently drops `overrides` and `resample_overrides` (hardcoded `None` at `py_dwelling.rs:1605-1615`). `build_config` has no unknown-key detection. `extract::<u8>()` for `output_verbosity` silently succeeds with Python `True` (bool is int subclass). ## Findings

### F1 — CRITICAL: `from_hpxml` silently drops `overrides` and `resample_overrides`

**File:** `crates/hares-python/src/py_dwelling.rs:1605–1615`

`build_config` hard-codes `overrides: None` and `resample_overrides: None` regardless of what the caller passes. A user calling:

```python
Dwelling.from_hpxml(hpxml, sched, weather, overrides={"hvac": {"capacity_w": 5000}})
```

will get a silently misconfigured dwelling with no error. The `DwellingConfig` pyclass (`py_config.rs`) correctly wires both fields, but `from_hpxml` never calls `DwellingConfig.to_dwelling_config()` — it has its own parallel `build_config` function that is permanently behind on features.

### F2 — HIGH: No unknown-key detection in `build_config`

**File:** `crates/hares-python/src/py_dwelling.rs:1452–1616`

`build_config` pulls individual known keys via `k.get_item("start_time")`, etc. Unknown keys passed by the caller — including typos like `duraiton_s=86400` or deprecated names — are silently ignored. There is no cross-check of `dict.keys()` against the set of recognized names.

### F3 — HIGH: Two parallel construction paths with feature divergence

**Files:** `crates/hares-python/src/py_config.rs`, `crates/hares-python/src/py_dwelling.rs`

`DwellingConfig.__init__` (py_config.rs) and `Dwelling.from_hpxml` (py_dwelling.rs `build_config`) are independent implementations of the same logic. `DwellingConfig` supports `overrides`, `resample_overrides`, and has input validation (e.g. `initialization_duration < 0`, `setpoint_deadband_c` finiteness, `duration % time_res == 0`). `build_config` omits all of those features. Any future field added to one path must be manually copied to the other.

### F4 — MEDIUM: `.pyi` stub advertises `**kwargs: Any` on `from_hpxml`

**File:** `python/ochre_next/_hares.pyi:1645`

The stub types `from_hpxml` with `**kwargs: Any`, giving zero type-checker coverage for callers. Mypy/Pyright will accept any keyword argument with any value silently. This is consistent with the runtime behavior but means the stub actively prevents static analysis from catching errors.

### F5 — MEDIUM: `overrides` dict has no key validation at runtime

**File:** `crates/hares-python/src/py_config.rs:438–452`

The `overrides` dict in `DwellingConfig.__init__` accepts any string key. It serializes the dict to `serde_json::Value` and passes it to the Rust core as an opaque blob. Wrong equipment names, misspelled field names, or structurally incorrect values are not checked at the Python boundary. Errors, if any, surface deep in the Rust deserialization path with context-free messages.

### F6 — LOW: Bool-as-int coercion in `build_config`

**File:** `crates/hares-python/src/py_dwelling.rs:1518–1523`

`output_verbosity` is extracted via `obj.extract::<u8>()`. Python `True` extracts as `1` and `False` as `0` because `bool` is a subclass of `int` in Python. A caller passing `output_verbosity=True` gets verbosity `1` silently rather than a type error. This is the same risk for `bldg_id`, `master_seed`, and `output_chunk_size`.

### F7 — LOW: `initialization_duration = 0` is silently normalized to `None`

**File:** `crates/hares-python/src/py_dwelling.rs:1590–1596`, `crates/hares-python/src/py_config.rs:462–463`

Both code paths convert `initialization_duration=0` to `None`. This is a semantic normalization the user may not expect — passing `0` to mean "disabled" is already semantically clear, but the conversion is undocumented and could mask bugs if a computed value evaluates to zero unexpectedly.

## Recommended Tests

1. **Regression: `overrides` propagates through `from_hpxml`** — Pass a known-valid override key through `from_hpxml` and verify the Rust core receives it. Currently this would fail (F1 is confirmed broken).

2. **Misspelled kwarg rejected** — Pass `duraiton_s=86400` to `from_hpxml` and assert `PyValueError` is raised. Currently this silently ignores the key (F2).

3. **`DwellingConfig` round-trip** — Construct `DwellingConfig`, call `to_dwelling_config()`, verify `overrides` and `resample_overrides` are not `None` when provided.

4. **Bool-as-verbosity rejected** — Pass `output_verbosity=True` and assert `PyValueError`. Currently silently accepted.

5. **Type stub accuracy** — Confirm that `_hares.pyi` `from_hpxml` signature enumerates all accepted kwargs explicitly once F2 is resolved.

---

## Recommendation

`Dwelling.from_hpxml` should be refactored to delegate to `DwellingConfig.to_dwelling_config()` rather than maintaining a parallel `build_config`. The signature should accept an explicit `config: DwellingConfig | None = None` plus individual flat kwargs that `build_config` already handles, constructing a `DwellingConfig` internally. The `.pyi` stub must enumerate all kwargs explicitly and remove `**kwargs: Any`. Unknown keys must raise `PyValueError` at the boundary.

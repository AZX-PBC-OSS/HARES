## Background/Context

The `Occupant` actor drives presence-based equipment behavior (lights on/off, appliance
use patterns). Presence schedules must use local time — a UTC error would shift
occupancy patterns, affecting internal gains and appliance loads.

## Investigation Instructions

1. **Read `crates/hares-core/src/actors/occupant.rs`:**
   - How does the actor determine current presence/absence?
   - What time source feeds into the schedule lookup?
   - Does it use `TimeWindow` / `ScheduleSource`?

2. **Trace `EquipmentBehavior` triggers:**
   - When the occupant turns equipment on/off, is the timing based on local time?

3. **Compare with OCHRE** — how does OCHRE's occupancy schedule feed into
   equipment behavior? What timezone does the occupancy index use?

4. **Write findings** with line numbers and recommendations.

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### 1. The `Occupant` actor is a pure dispatch actor — no time awareness of its own

`crates/hares-core/src/actors/occupant.rs`

The `Occupant` struct holds a `Vec<Presence>` indexed by `self.current_step` (line 128),
which is a simple counter incremented by one on each `decide()` call (line 218). The actor
never reads `env.current_time`, never queries a `TimeWindow`, and never touches any schedule
source. It is completely time-unaware.

The `_env` parameter in `decide(&mut self, _env: &EnvironmentState, ...)` (line 347) is
explicitly ignored. Presence at each step is determined solely by position in the
pre-computed array.

**Consequence**: the timezone correctness question is entirely upstream — it belongs to
whoever builds the `Vec<Presence>` and passes it to `with_presence_schedule()`.

### 2. The `Occupant` actor is NEVER auto-attached by the dwelling builder

`crates/hares-core/src/dwelling/mod.rs`

The dwelling builder's `ActorSeed` variants (lines 2576–2680) only auto-create
`BatteryManagementActor` (for `ActorSeed::Battery`) and `EvDriverActor`
(for `ActorSeed::Ev`). There is no `ActorSeed::Occupant` variant and no code path that
auto-attaches an `Occupant` actor.

The `Occupant` is registered in `ActorRegistry` (lines 118–127 of `actor_registry.rs`) and
is reachable via `add_actor_by_name()`, but only if the caller explicitly configures one.
No HPXML resolver, no synthetic dwelling builder, and no integration test attaches an
`Occupant` actor. The synthetic dwelling helper (`dwelling/synthetic.rs`) contains no
occupant references whatsoever.

**Consequence**: the `Occupant` actor is dead code in all current simulation paths.
No test exercises it end-to-end through a full dwelling step.

### 3. Occupancy heat gains flow through the schedule CSV, not the actor

`crates/hares-core/src/dwelling/mod.rs` lines 1707–1740

The OCHRE-equivalent occupancy internal heat gain path is implemented independently of the
`Occupant` actor. `apply_occupancy_gains()` reads `n_occupants` from the schedule payload
in `latest_env.custom_domains` using `occupancy_column_idx` — an index resolved at init
time from the CSV column named `"occupants"` or `"occupancy"` (environment.rs lines
364–383). The constants used are `OCCUPANT_SENSIBLE_GAIN_W = 66.0 W` and
`OCCUPANT_LATENT_GAIN_W = 51.2 W` (physics/constants.rs lines 121, 127), matching OCHRE
`Envelope.py:904-908`.

This heat gain path is exercised whenever the schedule CSV has an occupancy column. It is
independent of whether any `Occupant` actor is attached.

### 4. Schedule timezone: fixed-offset default, optional DST-aware civil time

`crates/hares-core/src/environment.rs` lines 316–344

`compute_schedule_idx()` has two modes:

- **Default (no `civil_timezone` configured)**: index is
  `(step + schedule_start_offset) % schedule_len` — purely UTC/fixed-offset arithmetic
  derived from `start_time` (the EPW file's fixed offset). No DST correction.
- **DST-aware (`dst` feature + `civil_timezone` set in config)**: converts the simulation
  UTC timestamp into the specified IANA timezone and computes a civil-time index, allowing
  occupancy and rate schedules to follow DST transitions naturally.

OCHRE `utils/schedule.py` lines 634–652 does the equivalent: it optionally localizes the
schedule index to a DST-aware US timezone (e.g., `"US/Eastern"`) via `pytz`. Both
implementations are architecturally consistent. The key difference is that in HARES the
DST path is opt-in via a feature flag and config field, whereas OCHRE defaults to DST for
US locations.

The `civil_timezone` default is `None` in both `DwellingConfig` builder paths (lines 659
and 727), so DST correction is off unless explicitly enabled by the caller.

**For the occupancy heat gain path**: the schedule index used in `apply_occupancy_gains()`
is determined by `compute_schedule_idx()` during `EnvironmentManager::update_in_place()`.
Therefore, the occupancy count read each step follows the same timezone treatment as all
other schedule columns — correct if `civil_timezone` is set, fixed-offset otherwise.

### 5. OCHRE comparison

OCHRE occupancy is a continuous numeric column `"Occupancy (Persons)"` in the schedule
DataFrame (schedule.py line 450, Envelope.py lines 1266–1268). It is a fractional count
(persons present), not a binary state. The DataFrame uses a timezone-aware
`DatetimeIndex`, so OCHRE naturally reads the correct local-time row at every step.

HARES maps the equivalent CSV column (`"occupants"`) to a `ScheduleCategory::Occupancy`
entry (schedule_resolve.rs lines 40–44). The resolved column index is stored in
`occupancy_column_idx` and the count is used with the same gain constants as OCHRE. The
occupancy value is a continuous float (persons), matching OCHRE's model.

There is no OCHRE occupancy concept equivalent to the HARES `Occupant` actor (binary
home/away + dispatch signals). OCHRE does not model occupant behavioral actions on
equipment — it only uses the occupancy count for thermal and latent heat gains.

### 6. Defects and gaps

**DT-006-A — Severity: Medium**
The `ActorRegistry` registers an `Occupant` actor factory (actor_registry.rs line 119),
but the factory only wires up `lighting_target` from config (lines 122–125). There is no
mechanism to inject a `presence_schedule` via `ActorConfig` — the factory always produces
an actor with the default single-step `[Presence::Home]` schedule. Any actor created via
the registry will be permanently stuck in `Home` state and will advance
`current_step` past the schedule on step 2, triggering the `debug_assert` in release
builds silently (unwrap falls back to `Presence::Home` via `.unwrap_or`). This is a broken
factory that makes the registry-based code path unusable for occupant modeling.

**DT-006-B — Severity: Low**
The `Occupant` actor has no `Actor::telemetry()` implementation. Dispatched signals are
logged at `tracing::debug` level (line 371–378), but no structured telemetry is emitted.
The project memory `feedback_actor_telemetry.md` requires actors to emit telemetry for
inspecting dispatched actions.

**DT-006-C — Severity: Low / Documentation gap**
The disconnect between the `Occupant` actor (binary presence → equipment dispatch) and the
occupancy heat gain path (continuous `n_occupants` from schedule CSV → thermal gain) is
not documented. A user who attaches an `Occupant` actor expecting it to affect thermal
gains would be surprised — the two systems are completely independent and there is no
integration between them.

**DT-006-D — Severity: Low / Test coverage gap**
The `Occupant` actor has comprehensive unit tests within `occupant.rs` itself, but zero
integration tests through a full dwelling step. No test verifies that:
- An attached `Occupant` actor's dispatch signals actually reach and affect equipment.
- The occupancy heat gain path and the `Occupant` actor coexist correctly when both are
  active.

## Review Notes

**Scope correction**: The `Occupant` actor uses a pre-computed `Vec<Presence>` indexed by `self.current_step` — it never calls `env.current_time`. The timezone risk is upstream in whoever builds the `Vec<Presence>`. Investigate who calls `with_presence_schedule()` — likely in `dwelling/mod.rs` or an I/O layer. OCHRE reference should point to occupant model file, not `utils/schedule.py`.

## Background/Context

Electric baseboards are simple resistive heaters with no ducts and COP=1. Config is
minimal but must be traced.

## Investigation Instructions

1. Read OCHRE `ElectricBaseboard.py` — config keys, defaults.
2. Read HARES `baseboard.rs` — config keys, defaults.
3. Build comparison table. Note: baseboards should have no ducts (DSE=1).
4. Document any discrepancies.

### Finding 1 — Basement heat routing applied to baseboard (correctness, medium)

**File:** `crates/hares-io/src/hpxml/resolve_hvac.rs:306-308`

`basement_params` (containing `basement_zone_id` and `basement_airflow_ratio=0.2` when a finished
basement is present) is injected for **every** `HeatingSystem` node, including `Electric Baseboard`.
`hvac_core::init` then reads `basement_airflow_ratio` and sets `self.basement_heat_frac = 0.2`.

In OCHRE, `ElectricBaseboard.__init__` forces `duct_dse = 1` after `super().__init__()`, but
`super().__init__()` still runs the shared HVAC init that sets `basement_heat_frac` via the HPXML
kwargs. However, `update_zone_heat_fractions` in HARES uses
`conditioned_frac = dse * (1 - basement_frac)`. With `dse=1` and `basement_frac=0.2`, the
conditioned zone only receives 80% of the baseboard's thermal output even though OCHRE routes
`1 * (1 - 0.2) * basement_heat_frac = 0` duct losses but still distributes
`dse * (1-basement_frac) = 0.8` to the conditioned zone and `dse * basement_frac = 0.2` to the
basement.

The issue is correctness for baseboard specifically: an electric baseboard should deliver all heat
to the conditioned space it is installed in. The physical justification for routing 20% to the
basement is that forced-air systems in a finished basement naturally leak conditioned air downstairs.
A baseboard heater radiates directly into the room it occupies — there is no forced-air pathway to
the basement. HARES currently inherits this fraction from the shared init without suppressing it for
baseboard.

**Required fix:** In `ElectricBaseboard::init`, after `self.hvac.init(config, env)?`, unconditionally
zero out `self.hvac.basement_heat_frac` and `self.hvac.basement_zone_id`, then call
`self.hvac.update_zone_heat_fractions()` (same pattern as the DSE override on lines 92-94). This
overrides whatever `hvac_core::init` read from config.

```rust
self.hvac.duct_dse = 1.0;
self.hvac.duct_zone_id = None;
self.hvac.basement_heat_frac = 0.0;   // ADD
self.hvac.basement_zone_id = None;    // ADD
self.hvac.update_zone_heat_fractions();
```

### Finding 2 — Startup degradation coefficient injected for baseboard (correctness, low)

**File:** `crates/hares-io/src/hpxml/resolve_hvac.rs:309`

`insert_startup_degradation(&mut params, &name, true)` is called for every `HeatingSystem`,
including `Electric Baseboard`. This inserts a `startup_degradation_coeff` key. The `hvac_core::init`
startup path reads this and sets `self.startup`. For a resistive heater there is no startup
degradation — the element reaches full power instantly. OCHRE does not model startup degradation for
`ElectricBaseboard` (no override in `ElectricBaseboard` or `Heater`; the base `HVAC.startup` only
applies in certain `DynamicHVAC` subclasses).

The injected value would be 0.0 if `calc_startup_degradation` returns 0 for baseboard, but this
depends on internal lookup logic. The call is harmless only if the returned coefficient is 0.0.
This should be verified or the call should be guarded:

```rust
if name != "Electric Baseboard" {
    insert_startup_degradation(&mut params, &name, true);
}
```

### Finding 3 — Duct params injected for baseboard, then silently overridden (maintainability, low)

**File:** `crates/hares-io/src/hpxml/resolve_hvac.rs:303-305`

`duct_params` (containing ASHRAE 152 duct geometry keys) is injected for all `HeatingSystem` nodes.
For `Electric Baseboard` these are read by `hvac_core::init` and used to compute a non-trivial DSE,
but then `baseboard.rs:92` overrides `duct_dse = 1.0` and clears `duct_zone_id`. This ordering
means the duct computation work was wasted and could produce misleading intermediate state if init
ever fails partway through. The correct fix is to skip duct param injection for baseboard in the
resolver, mirroring the `if name != "Room AC"` guard used on the cooling path
(`resolve_hvac.rs:359`):

```rust
if name != "Electric Baseboard" {
    for (k, v) in &duct_params {
        params.insert(k.clone(), v.clone());
    }
}
```

This is the resolver-side complement to Finding 2's guard pattern and follows the existing precedent.

### Finding 4 — electric_kw computation misapplies space_fraction (correctness, medium)

**File:** `crates/hares-equipment/src/hvac/baseboard.rs:118`

```rust
let electric_kw = thermal_output_w / 1_000.0 * self.hvac.space_fraction;
```

`thermal_output_w` is `rated_capacity_w * duty`. `space_fraction` is then applied to derive
`electric_kw`. However, `write_zone_thermal_contributions` on line 125 receives the raw
`thermal_output_w` (not scaled by `space_fraction`) and distributes it via `zone_heat_fractions`.
Since `zone_heat_fractions` for a baseboard is `[(zone_id, 1.0)]` (DSE=1, no basement), the full
`thermal_output_w` reaches the zone.

OCHRE (HVAC.py lines 543, 558-559) applies `space_fraction` to both `delivered_heat` (result
reporting) and `electric_kw`, but thermal zone gains (`sensible_gain`) are distributed via
`zone_fractions` *before* the `space_fraction` reduction (line 564 `add_gains_to_zone` uses
`self.sensible_gain`, which has *not* been scaled by `space_fraction`). So OCHRE also delivers
unscaled heat to the zone while scaling only the reported power.

This means the current HARES code is actually consistent with OCHRE's zone gain behavior, but
**the telemetry `ELECTRIC_KW` will be under-reported relative to actual heat deposited in the zone
when `space_fraction < 1`**. A baseboard only in one unit of a multi-unit building genuinely uses
`rated_capacity_w * duty * space_fraction` of electrical power while depositing
`rated_capacity_w * duty` into the zone it serves — this is the physically correct behavior for a
partial-load fraction. No code change is needed for physics correctness, but the `run_time_s`
accumulation occurs only when `electric_kw > 0` (line 120-131), which means runtime is also subject
to the `space_fraction > 0` condition. This is correct.

No action needed beyond documenting the intentional behavior.

## Recommended Tests

### Test 1 — Baseboard delivers 100% heat to conditioned zone even with finished basement in building

In `crates/hares-equipment/src/hvac/baseboard.rs` test module:

```rust
#[test]
fn baseboard_ignores_basement_params() {
    let mut cfg = config();
    cfg.raw_config.insert("zone_id".to_string(), 1.0.into());
    cfg.raw_config.insert("capacity_w".to_string(), 2_000.0.into());
    cfg.raw_config.insert("heating_setpoint_c".to_string(), 21.0.into());
    cfg.raw_config.insert("cooling_setpoint_c".to_string(), 27.0.into());
    // Simulate resolver injecting basement params for a finished-basement building
    cfg.raw_config.insert("basement_zone_id".to_string(), 2.0.into());
    cfg.raw_config.insert("basement_airflow_ratio".to_string(), 0.2.into());

    let mut eq = ElectricBaseboard::new(cfg.clone());
    let env = env(18.0);
    eq.init(&cfg, &env).unwrap();

    // After init, baseboard must suppress basement routing
    assert_eq!(eq.hvac.basement_heat_frac, 0.0);
    assert_eq!(eq.hvac.basement_zone_id, None);

    // All heat goes to conditioned zone, none to zone 2
    let mut ports = PortSlots {
        thermal: vec![
            ThermalAccumulator::new(ZoneId(1)),
            ThermalAccumulator::new(ZoneId(2)),
        ],
        ..PortSlots::default()
    };
    eq.update_control(&env);
    eq.step(&env, Duration::from_secs(60), &mut ports).unwrap();
    assert!((ports.thermal[0].sensible_gain_w - 2_000.0).abs() < 1e-9);
    assert!((ports.thermal[1].sensible_gain_w).abs() < 1e-12);
}
```

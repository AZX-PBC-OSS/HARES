## Background/Context

HARES has a dedicated `defrost.rs` with OnDemand and Timed control modes, ReverseCycle and Resistive strategies. OCHRE has a single on-demand reverse-cycle implementation using hardcoded EnergyPlus coefficients. CW-007 covers only config wiring, not physics behavior.

---

## Model summary

### HARES OnDemand (humidity-based, default for ASHP/MSHP)

Activation threshold: OAT < `DEFROST_ENABLE_TEMP_C` = 4.4445 °C

```
coil_out_temp   = 0.82 * OAT − 8.589
omega_sat_coil  = sat_HR(coil_out_temp, coil_out_temp, pressure)
delta_omega     = max(1e-6, outdoor_HR − omega_sat_coil)
time_frac       = 1 / (1 + 0.01446 / delta_omega)
cap_mult        = 0.875 * (1 − time_frac)
pwr_mult        = 0.954 / 0.875   ≈ 1.091  (constant)
q_defrost       = 0.01 * time_frac * (7.222 − OAT) * (rated_cap_W / 1.01667)
extra_power     = 0.1528 * (current_cap_W / 1.01667) * time_frac + defrost_power_w
```

Application (`heater.rs` L784–791):
```rust
hp_capacity_w = max(0, hp_capacity_w * cap_mult − q_defrost) * capacity_reduction_factor
hp_electric_w = hp_electric_w * pwr_mult + extra_power_w
```

### HARES Timed (fixed time fraction, default 0.058 ≈ 3.5 min/hr)

Multipliers from EnergyPlus / DOE-2, clamped to [0, 1]:
```
cap_mult = clamp(0.909 − 107.33 * delta_omega, 0, 1)
pwr_mult = clamp(0.90  −  36.45 * delta_omega, 0, 1)
```

Strategies: ReverseCycle (biquadratic EIR curve with 15.555 °C input floor) or Resistive (zero q_defrost; power from rated heater capacity). Both scale with `runtime_fraction`.

### OCHRE OnDemand (HVAC.py L1128–1173)

- Same 4.4445 °C threshold, same coil-temp formula, same delta_omega, same time_frac (exact constant parity confirmed)
- `capacity_max` reduced first: `capacity_max = capacity_max * cap_mult − q_defrost`
- `q_defrost` uses `capacity_max` (rated)
- `power_defrost = 0.1528 * (post_defrost_capacity / 1.01667) * time_frac`  ← uses **post-defrost** capacity
- EIR update: `eir = (eir * capacity * (0.954/0.875) + power_defrost) / capacity`
- Outside defrost: `defrost_power_mult = 0` (no-op, guarded by `if self.defrost`)
- No Timed mode, no Resistive strategy

## Findings

### F1 — CRITICAL: `extra_power_w` uses pre-defrost capacity; OCHRE uses post-defrost capacity

**File:** `defrost.rs` L152–155; OCHRE HVAC.py L1162

HARES:
```rust
let extra_power_w = DEFROST_EIR_TEMP_MODIFIER
    * (current_capacity_w / DEFROST_CAPACITY_UNIT_FACTOR)
    * time_fraction
    + config.defrost_power_w;
```

OCHRE computes `power_defrost` after reducing capacity by `defrost_capacity_mult * capacity − q_defrost`.  The capacity fed into OCHRE's extra-power formula is the post-defrost value; HARES uses the raw pre-defrost `current_capacity_w`.

At typical defrost conditions (OAT ≈ 0 °C, time_frac ≈ 0.25–0.40, `cap_mult` ≈ 0.55–0.66) the post-defrost capacity is 45–55% lower than pre-defrost, meaning HARES **overestimates defrost extra power by roughly 2×**. This inflates electrical consumption during defrost and corrupts COP.

**Fix:** Compute `extra_power_w` from the post-defrost capacity:
```rust
let post_defrost_cap_w = (current_capacity_w * capacity_multiplier - q_defrost_w).max(0.0);
let extra_power_w = DEFROST_EIR_TEMP_MODIFIER
    * (post_defrost_cap_w / DEFROST_CAPACITY_UNIT_FACTOR)
    * time_fraction
    + config.defrost_power_w;
```
The `DefrostResult` returned by `evaluate_defrost` must then carry this corrected value.

### F2 — HIGH: `DEFAULT_DEFROST_CAPACITY_REDUCTION_FACTOR = 0.75` fallback has no EnergyPlus basis

**File:** `constants.rs` L22; `heater.rs` L422–424

```rust
self.defrost_config = DefrostConfig::on_demand(
    first_f64(config, &["defrost_capacity_reduction_factor"])
        .unwrap_or(DEFAULT_DEFROST_CAPACITY_REDUCTION_FACTOR),  // = 0.75
    ...
```

OCHRE has no equivalent secondary scaling after `defrost_capacity_mult`. EnergyPlus OnDemand defrost also has no such factor. When `defrost_capacity_reduction_factor` is absent from config (the common case), HARES applies an additional 25% capacity penalty on top of the physically-derived `cap_mult`. This reduces net heating output by ~25% under all defrost-active steps.

**Fix:** Change `DEFAULT_DEFROST_CAPACITY_REDUCTION_FACTOR` to `1.0` (no secondary scaling). Alternatively, remove the field and its application entirely for the OnDemand/ReverseCycle path, leaving it only as an explicit user override.

### F3 — MEDIUM: Ideal-capacity mode does not cap to defrost-reduced rated maximum

**File:** `heater.rs` L769–791

OCHRE:
```python
self.capacity_max = self.capacity_max * defrost_capacity_mult - q_defrost  # reduces the ceiling
if self.use_ideal_capacity:
    capacity = min(capacity, self.capacity_max * self.ext_capacity_frac)   # enforces it
```

HARES applies defrost to the already-computed `hp_capacity_w` uniformly, without updating the ceiling. When `use_ideal = true` and the solver requests near-rated capacity, the cap is not enforced at the defrost-reduced level. The solver can deliver more than the physically available post-defrost maximum.

**Fix:** After computing the defrost-reduced maximum (`rated_cap * cap_mult - q_defrost`), clamp `hp_capacity_w` to that ceiling when `use_ideal = true`.

### F4 — MEDIUM: EIR multiplier pipeline order may diverge in multi-speed paths

**File:** `heater.rs` L749 vs L791; OCHRE HVAC.py L1168–1172

OCHRE's `update_eir` rescales the fully-composed EIR (after biquadratic + PLF) so that `eir * capacity` yields the correct power. HARES instead multiplies `hp_electric_w` (already `hp_capacity_w * stage_eir * eir_ratio`) by `pwr_mult` and adds `extra_power_w` afterward. The two are algebraically equivalent only in the single-speed steady-state case where `hp_electric_w = eir * capacity`. In multi-speed interpolated mode the interpolated EIR is applied before the defrost correction, so the ordering matches. However, if startup capacity degradation (`apply_startup_capacity_degradation`, L744–746) changes `staged_capacity_w` after the EIR was computed, the EIR correction no longer tracks the actual capacity. This is a pre-existing pipeline issue but defrost exposure makes it visible.

**Fix (low priority):** Recompute `hp_electric_w` from `hp_capacity_w * effective_eir` after all capacity adjustments, then apply defrost power correction — matching OCHRE's post-capacity EIR composition.

### F5 — LOW: Missing defrost telemetry fields

**File:** `heater.rs` L634–666

`DEFROST_ACTIVE` and `DEFROST_TIME_FRACTION` are emitted. The fields `extra_power_w`, `q_defrost_w`, `capacity_multiplier`, and `power_multiplier` from `DefrostResult` are not. These are essential for parity diagnostics when defrost is suspected to be a source of energy balance error.

**Fix:** Emit `defrost_extra_power_w`, `defrost_q_w`, and `defrost_capacity_multiplier` as telemetry keys.

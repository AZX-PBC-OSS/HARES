## Background/Context

HPXML specifies HVAC capacities in BTU/hr. HARES must convert to watts (SI). The
conversion factor is 1 BTU/hr = 0.29307107 W. Any error here directly scales all
heating/cooling energy output.

## Investigation Instructions

1. **Read `crates/hares-io/src/hpxml/resolve_hvac.rs`:**
   - Find every instance where `HeatingCapacity`, `CoolingCapacity`,
     `BackupHeatingCapacity` is parsed.
   - What conversion is applied? Is it `value * 0.29307107` or `value / 3.412`?
   - Is the converted value stored with a `_w` suffix key?
   - Are there any fields stored in BTU/hr without conversion?

2. **Check for double conversions:**
   - Is capacity converted at parse time AND again in the equipment model?
   - Search for BTU/hr constants in `hares-equipment/src/hvac/` files.

3. **Compare with OCHRE `parse_hvac()` in `hpxml.py`:**
   - Find the equivalent capacity parsing — what conversion does OCHRE apply?
   - Does OCHRE store intermediate BTU/hr values for any purpose?

4. **Check fan power:**
   - `FanPowerWattsPerCFM` — is CFM converted to m³/s? Or is the per-CFM value
     used directly with CFM airflow?

5. **Write findings** as a table:
   ```
   HPXML Field          | HPXML Unit | HARES conversion | OCHRE conversion | Match?
   ---------------------|------------|------------------|------------------|-------
   HeatingCapacity      | BTU/hr     | ?                | *0.29307         |
   CoolingCapacity      | BTU/hr     | ?                | *0.29307         |
   BackupHeatingCapacity| BTU/hr     | ?                | *0.29307         |
   FanPowerWattsPerCFM  | W/CFM      | ?                | ?                |
   ```


## Findings

### F-1 — Conversion factor: correct, matches OCHRE (PASS)

`crates/hares-physics/src/units.rs:96`

```
const BTU_PER_HOUR_TO_WATT: f64 = 0.293_071_07;
pub fn power_btu_h_to_w(btu_h: f64) -> f64 { btu_h * BTU_PER_HOUR_TO_WATT }
```

OCHRE (`hpxml.py:847`) uses `convert(value, "Btu/hour", "W")` which resolves to the same
NIST factor 0.29307107 W/(BTU/h). HARES uses multiply (correct); OCHRE uses pint
(equivalent). No `/3.412` approximation anywhere in the path.

### F-2 — HeatingCapacity / CoolingCapacity parse paths (PASS, with one design note)

`resolve_hvac.rs:276-277, 324-330, 381-394`

Every `HeatingCapacity` and `CoolingCapacity` parse calls two helpers back-to-back:

1. `insert_capacity_kbtu_h(params, node, tag)` — writes key `heatingcapacity_kbtu_h`
   (or `coolingcapacity_kbtu_h`) with value `btu_h * 0.001`. Unit: kBTU/h.
2. `insert_capacity_w(params, node, tag, "heating_capacity_w")` — writes key
   `heating_capacity_w` (or `cooling_capacity_w`) with value `btu_h * 0.29307107`. Unit: W.

**Design note (not a bug):** the `*_kbtu_h` keys are written into the JSON params
alongside the `*_w` keys. Equipment models read capacity via `HEATING_CAPACITY_KEYS`
(`helpers.rs:16-21`) which lists `["capacity_w", "heating_capacity_w", "capacity",
"HVAC Heating Capacity (W)"]`. None of these keys match `*_kbtu_h`, so equipment cannot
accidentally pick up the kBTU/h value. Confirmed: `grep -r kbtu_h crates/hares-equipment`
returns zero matches.

The `*_kbtu_h` values appear to be dead weight in the params map — they are produced but
never consumed by any equipment code. No correctness risk, but unnecessary allocation.

### F-3 — BackupHeatingCapacity (PASS)

`resolve_hvac.rs:403-407`

```rust
if let Some(cap_btu) = child_f64(heat_pump, "BackupHeatingCapacity") {
    params.insert("backup_capacity_w", json!(conv::power_btu_h_to_w(cap_btu)));
}
```

Single conversion, stores watts under `backup_capacity_w`. OCHRE `hpxml.py:943-944`
does the same: `backup_capacity = convert(backup_capacity, "Btu/hour", "W")`. Match.

### F-4 — No double conversions (PASS)

All equipment init paths (`furnace.rs:285`, `air_conditioner.rs:402-416`,
`heat_pump/heater.rs:363-368`, `baseboard.rs:95`, `boiler.rs:167`) call
`first_f64(config, HEATING_CAPACITY_KEYS)` or `load_stage_values(config, ..., "cooling_capacity_w_stage", ...)`.
These read the already-converted watt values written by `insert_capacity_w`. No
BTU/hr constant or secondary conversion exists anywhere in `crates/hares-equipment/src/hvac/`.

### F-5 — FanPowerWattsPerCFM: BEHAVIORAL DIVERGENCE FROM OCHRE (DEFECT)

**Severity: Medium** — wrong fan power for any building that supplies `FanPowerWattsPerCFM`
in the HPXML extension block.

**OCHRE path (`hpxml.py:893-898`):**
OCHRE converts `FanPowerWattsPerCFM` to an absolute watt value at parse time:
```python
cfm_per_ton = 350 if is_heater else 312
power_per_cfm = hvac_ext.get("FanPowerWattsPerCFM", 0)
aux_power = power_per_cfm * cfm_per_ton * convert(capacity, "W", "refrigeration_ton")
# stored as "Rated Auxiliary Power (W)"
```
Result: a single absolute `W` value, capacity-scaled.

**HARES path (`resolve_hvac.rs:293-298`):**
```rust
if let Some(w_per_cfm) = child_f64(ext, "FanPowerWattsPerCFM") {
    params.insert("fan_power_w_per_cfm", json!(w_per_cfm));
}
```
The raw W/CFM rate is stored. `hvac_core.rs:338-339` converts it to W/(m³/s):
```rust
self.fan_power_w_per_m3_s = w_per_cfm * CFM_PER_M3_S;
```
`fan_power_w(airflow_m3_s)` then returns `airflow_m3_s * fan_power_w_per_m3_s`.

**Consequence:** the approaches are architecturally different. OCHRE materialises a fixed
absolute `aux_power` (capacity * cfm_per_ton * W_per_cfm) that is constant across all
operating conditions. HARES stores a rate and multiplies by actual airflow at runtime, so
fan power scales with load/duty. For cycling equipment at full speed these converge; for
partial-load or variable-speed they diverge. Additionally, OCHRE hard-codes 312 CFM/ton
for cooling and 350 for heating, while HARES uses equipment-type-specific constants
(central AC: 400, MSHP: 312, room AC: 320, heating: 350 — `hvac_core.rs:69-72`). So even
at full speed the central-AC fan power will differ: OCHRE uses 312 CFM/ton, HARES uses 400.

This divergence is intentional in that HARES targets correct physics rather than OCHRE
parity, but it means fan-power parity tests against OCHRE will fail for central AC.

### F-6 — FanPowerWattsPerCFM: CFM conversion is correct (PASS)

`hvac_core.rs:339`: `w_per_cfm * CFM_PER_M3_S` correctly converts W/CFM → W/(m³/s).
`CFM_PER_M3_S = 1 / 0.000_471_947_443_2 ≈ 2118.88` (constants.rs:99). This is the exact
NIST factor. No error here.

### F-7 — airflow_cfm_per_ton end-to-end (PASS)

`hvac_core.rs:329-335`:
```rust
let mut airflow_cfm_per_ton = extract_numeric(config, "airflow_cfm_per_ton")
    .unwrap_or_else(|| self.equipment_type.default_airflow_cfm_per_ton());
let airflow_defect_ratio = extract_numeric(config, "AirflowDefectRatio")
    .or_else(|| extract_numeric(config, "airflow_defect_ratio"))
    .unwrap_or(1.0);
airflow_cfm_per_ton *= airflow_defect_ratio;
self.airflow_m3_s_per_w = airflow_cfm_per_ton * CFM_TO_M3_S / W_PER_TON;
```
`W_PER_TON = 3516.852842...` (constants.rs:89 — correct ASHRAE definition: 1 ton =
12 000 BTU/h = 3516.85 W). `CFM_TO_M3_S = 0.000_471_947_443_2` (correct). Dimensional
analysis: (CFM/ton) × (m³/s / CFM) / (W/ton) = m³/s / W. Correct.

### F-8 — W_PER_TON value (PASS)

`3_516.852_842_066_667` = 12 000 BTU/h × 0.29307107 W/(BTU/h) = 3516.8528... W/ton.
Matches ASHRAE Fundamentals.

### Summary

No conversion bugs. No double conversions. No kBTU/h value misread as watts. The only
material divergence is F-5: `FanPowerWattsPerCFM` produces a different numeric fan-power
result versus OCHRE because HARES stores a rate and scales at runtime against actual
airflow, while OCHRE collapses to a fixed absolute watt value at parse time using
hard-coded 312/350 CFM/ton. For parity testing with OCHRE-generated fixtures this will
produce measurable differences in fan electricity whenever `FanPowerWattsPerCFM` is
supplied in the extension block for central AC (OCHRE: 312 CFM/ton, HARES: 400 CFM/ton).

Minor: the `*_kbtu_h` keys written by `insert_capacity_kbtu_h` are allocated into every
HVAC params map but are read by nothing. They should be removed.

`crates/hares-io/tests/` — parse a synthetic HPXML fragment containing
`HeatingCapacity = 36000` (BTU/h), `CoolingCapacity = 24000`, `BackupHeatingCapacity =
10000`. Assert that the resolved params contain `heating_capacity_w ≈ 10548.6`,
`cooling_capacity_w ≈ 7034.1`, `backup_capacity_w ≈ 2930.7` (all `× 0.29307107`).
Assert that `heatingcapacity_kbtu_h = 36.0` and `coolingcapacity_kbtu_h = 24.0` are

### T-2 — Equipment init reads watts, not kBTU/h
Directly populate an `EquipmentConfig` with both `heating_capacity_w = 10000.0` and
`heatingcapacity_kbtu_h = 10.0`. Init a `GasFurnace`. Assert `rated_capacity_w ≈ 10000`
(not 10.0 or 3412). Equivalent test for `AirConditioner` with `cooling_capacity_w`.

### T-3 — FanPowerWattsPerCFM stored as rate, not absolute
Parse an HPXML HeatingSystem extension with `FanPowerWattsPerCFM = 0.365`. Assert that
the resolved params contain `fan_power_w_per_cfm = 0.365` (rate preserved). Confirm no
`fan_power_w` key is emitted. After `HvacEquipment::init`, assert
`fan_power_w_per_m3_s ≈ 0.365 × 2118.88 ≈ 773.9`.

### T-4 — airflow_cfm_per_ton with defect ratio
Create an `HvacEquipment` config with `airflow_cfm_per_ton = 400.0`,
`airflow_defect_ratio = 0.8`. After init assert
`airflow_m3_s_per_w ≈ 320.0 × 0.000471947 / 3516.853 ≈ 4.294e-5`. This test already
exists in `hvac_core.rs` as `airflow_cooling_defaults_to_312_and_scales_by_defect_ratio`;
confirm it exercises the defect-ratio path for central AC (400 CFM/ton × 0.8 = 320).

### T-5 — kBTU/h intermediate key is dead (coverage gap)
Add an assertion in the `hares-io` integration test that no equipment model's
`HEATING_CAPACITY_KEYS` or equivalent cooling-capacity key list contains any `kbtu_h`
substring, preventing future accidental registration of the intermediate key.

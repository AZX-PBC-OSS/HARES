## Context

DC-007 and CW-020 covered the primary behavioral comparison and config-formula gaps
respectively. This ticket goes deeper on three areas called out in the brief: event
generation mechanics, power profile fidelity, hot water demand, and the gas/electric
fuel split through the full pipeline. Several new defects were found beyond DC-007
and CW-020.

---

## Findings

### F1 — Gas fuel consumption is always zero for gas dryers and gas cooking ranges

**Severity: Critical**
**Files:** `crates/hares-io/src/schedule_resolve.rs:651-671`, `crates/hares-io/src/hpxml/resolve_loads.rs:204-213, 278-283`

`resolve_loads.rs` correctly computes `annual_gas_therms` for gas dryers and gas
cooking ranges and inserts it into the spec parameters. However,
`schedule_resolve.rs::determine_max_kw()` at line 663 only reads `annual_electric_kwh`;
`annual_gas_therms` is never consulted anywhere in `schedule_resolve.rs`. As a result,
`inject_event_schedule()` at line 720 derives `max_kw` only from the electric parasitic
fraction — for a gas dryer that is ~7% of total energy. The `event_power_kw_series`
array therefore encodes only the electric parasitic, and `EventBasedLoad::update_outputs()`
routes `active_power_kw` to the `Fuel` port because `fuel_type == Gas`, meaning
the combustion energy that should be emitted is entirely absent.

Concretely: for a gas dryer with a 3-bedroom household at CEF=3.01, OCHRE computes
roughly 600 kWh electric and ~153 therms gas annually. HARES emits only the ~600 kWh
electric parasitic; the ~153 therms of gas combustion are zero. The gas cooking range
has the same structural problem: `annual_gas_therms = oven_ef * (22.6 + 2.7 * n_bedrooms)`
is populated but never used to set fuel power.

There is no error, no warning, and no existing test covering this path.

**Fix:** In `determine_max_kw()` or a new sibling, when `spec.fuel_type == FuelType::Gas`,
read `annual_gas_therms`, convert to average watts (1 therm = 105,480,400 J;
31,536,000 s/yr), and add to the electric parasitic. The `event_power_kw_series`
values must represent total input power (electric + fuel equivalent). `EventBasedLoad`
already routes the total to the correct port via `fuel_type`.

### F2 — `PowerSetpoint` override fires unconditionally regardless of phase

**Severity: High**
**File:** `crates/hares-equipment/src/event_load.rs:361-367`

`EventBasedLoad::update_outputs()` consumes `power_setpoint_override` before the
`active_now` guard:

```rust
let active_power_kw = if let Some(override_kw) = self.power_setpoint_override.take() {
    override_kw
} else if active_now {
    ...
} else {
    0.0
};
```

A `PowerSetpoint` control received while the load is in `EventPhase::Idle` will
produce non-zero power output for that step. OCHRE's equivalent in
`calculate_power_and_heat()` gates `p_setpoint` on `self.mode == "On"`. An actor
that issues `PowerSetpoint` proactively (before the event window opens) will inject
a phantom load through HARES.

**Fix:** Gate the override on `active_now`:

```rust
let active_power_kw = if active_now {
    self.power_setpoint_override.take()
        .unwrap_or(self.active_power_kw * self.load_fraction.max(0.0) * month_scale)
} else {
    self.power_setpoint_override = None;
    0.0
};
```

### F3 — `EventBasedLoad` mutates `active_power_kw` configuration field in deterministic mode

**Severity: High**
**File:** `crates/hares-equipment/src/event_load.rs:529`

Previously recorded in DC-007 but the full impact was not characterised. The mutation
`self.active_power_kw = self.extracted_events[self.event_cursor].power_kw` runs
every step while an extracted event is active. `active_power_kw` is not persisted in
`EventBasedLoadState`, so after `load_state()` mid-event the field reverts to the
`init()` default until the next `step()` overwrites it. For one step after restore,
power output reflects the init-time default (1.0 kW) rather than the event's actual
average power. Calling `init()` a second time on the same instance also permanently
corrupts the configured value.

`WetAppliance` avoids both problems by reading
`extracted_events[cursor].power_kw` inline inside `update_outputs()`.

**Fix:** Read extracted event power inline in `update_outputs()` instead of
pre-assigning to `self.active_power_kw`. Remove the line 529 assignment.

### F4 — Forced-active mode freezes phase timer; duration doubles on override release

**Severity: Medium**
**File:** `crates/hares-equipment/src/event_load.rs:317`, `755`

`EventBasedLoad::advance_phase_timer()` and `WetAppliance::advance_cycle()` both
return early when `ForcedMode::Active` is set, freezing `remaining_phase_s`. When the
override is later cleared, `remaining_phase_s` still holds its original value. The
load then runs for its full original `active_duration_s` additional seconds before
transitioning, effectively doubling the event duration after override release.

**Fix:** When `ForcedMode::Active` is cleared via `apply_control_unchecked`, reset
`remaining_phase_s` to a single timestep worth of remaining time so the phase
expires at the next step. Document the invariant that `remaining_phase_s` is
meaningless while forced-active.

### F5 — Hot water draw is uniform across all cycle phases

**Severity: Medium**
**File:** `crates/hares-equipment/src/event_load.rs:836-844, 893-902`

`WetAppliance` derives a single `hot_water_draw_rate_kg_s` by dividing the total
cycle volume by `total_cycle_duration_s`, then emits it at a constant rate across
every phase. Clothes washers draw hot water only during the fill phase (typically
phase 0); spin and rinse phases draw none. Spreading the draw uniformly underestimates
peak demand during fill and provides incorrect thermal stimulus to the water heater
at sub-hourly resolution.

**Fix:** Accept an optional `hot_water_draw_phase_index` config key (default: 0).
During that phase only, emit the full cycle volume concentrated over its duration.
Other phases emit zero draw.

### F6 — Dishwasher and clothes washer `RatedAnnualkWh` default still missing (CW-020/F1, F5 unresolved)

**Severity: High**
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:114-115, 228-229`

CW-020/F1 and F5 identified that HPXML files without `<RatedAnnualkWh>` silently
produce zero-energy appliances. The current code still conditions the energy
conversion on `params.get("annual_electric_kwh")` being present, which requires the
HPXML node to have supplied the value. OCHRE defaults 400.0 kWh (washer) and 467.0
kWh (dishwasher) unconditionally. These defects are confirmed unresolved in the
current diff.

### F7 — `delay_remaining_s` accepts unbounded values including non-positive

**Severity: Low**
**File:** `crates/hares-equipment/src/event_load.rs:639, 1097`

`EventDelay` signals accumulate via `self.delay_remaining_s += delay_s` with no
bounds check. A `delay_s <= 0.0` is silently accepted; the subtraction in `step()`
with `.max(0.0)` means a negative delay would immediately expire (reducing the delay
by one timestep's worth), but the signal contract does not document this. An extremely
large `delay_s` parks the load indefinitely with no warning.

**Fix:** Reject `delay_s <= 0.0` with `HaresError::Control`. Optionally log a warning
when accumulated delay exceeds a threshold (e.g., 24 hours).

---

### F8 — `update_control` returns `OperatingMode::Standby` for active phase

**Severity: Low**
**File:** `crates/hares-equipment/src/event_load.rs:487-492`

`EventBasedLoad::update_control()` returns `OperatingMode::Standby` for
`EventPhase::Active`. Standby means powered but not performing useful work. An active
load consuming power should return `OperatingMode::On`. Any actor or telemetry
consumer using this mode to determine whether the load is working will misclassify it.

**Fix:** Return `OperatingMode::On` for `EventPhase::Active`.

## Hot Water Demand Detail

OCHRE passes hot water demand as an independent daily schedule column
(`hot_water_clothes_washer`, `hot_water_dishwasher`) consumed by `WaterHeater` as a
draw independent of whether the appliance event is firing. The decoupling gives the
water heater smooth daily demand.

HARES emits `PortContribution::Fluid` only during active events and spreads the draw
uniformly across all phases. This is closer to physical reality for event timing, but
uses a wrong fixed volume (CW-020/F3) and distributes across all phases rather than
the fill phase (F5).

## Gas/Electric Split Detail

For gas dryers and gas cooking ranges, the full pipeline is:

1. `resolve_loads.rs` computes `annual_electric_kwh` (parasitic, ~7% of total) and
   `annual_gas_therms` (combustion, ~93% of total). Both are inserted into spec params.
2. `schedule_resolve.rs::determine_max_kw()` reads only `annual_electric_kwh`.
   `event_power_kw_series` encodes only the parasitic fraction.
3. `EventBasedLoad::update_outputs()` routes `active_power_kw` (the parasitic kW) to
   `PortContribution::Fuel` because `fuel_type == Gas`.
4. Result: gas port emits only the ~7% parasitic as "gas". The ~93% combustion load is
   entirely absent.

This is not a rounding error; it is a complete omission of the dominant energy
component for gas appliances.

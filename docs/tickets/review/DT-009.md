## Background/Context

The user specifies `start_time` as a datetime string or Python datetime object.
This must arrive in Rust as a `DateTime<FixedOffset>` carrying the correct local
timezone offset. If the offset is lost or defaulted to UTC, all downstream time-of-day
logic breaks.

---

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

## Propagation Chain

```
Python str  (ISO 8601)
  → parse_datetime_str()            [hares-python/src/utils.rs:32]
  → DateTime<FixedOffset>           stored in PySimulationConfig
  → to_rfc3339() / getter           surfaces back to Python as str (offset preserved)
  → to_sim_config()                 [py_config.rs:321]  direct field copy
  → SimulationConfig.start_time     DateTime<FixedOffset>   [hares-io/src/config.rs]
  → from_preparsed()                [dwelling/mod.rs:761–767]
  → naive_local() + EPW timezone    OFFSET REPLACED — see D2 below
  → local_start                     DateTime<FixedOffset> (EPW-local wall-clock)
  → EnvironmentManager::new()       [environment.rs:113]
  → compute_annual_offset()         uses .ordinal0(), .hour(), .minute(), .second()
  → compute_schedule_offset()       same wall-clock components
```

`extract_datetime` in utils.rs:60 handles Python datetime objects by calling
`.isoformat()` and then feeding the result into `parse_datetime_str`.  Aware datetimes
produce an RFC3339 string with the offset; naive datetimes produce a string with no
offset suffix and fall through to the naive/UTC branch.

---

## Input Parsing (`parse_datetime_str`, utils.rs:32)

Three input forms are accepted:

| Input format | Result | Offset |
|---|---|---|
| `"2019-01-01T00:00:00Z"` | RFC3339 parse succeeds | +00:00 preserved |
| `"2019-01-01T00:00:00+05:30"` | RFC3339 parse succeeds | +05:30 preserved |
| `"2019-01-01T00:00:00"` (no offset) | NaiveDateTime fallback | **silently assumed UTC** |
| `"2019-01-01"` (date only) | NaiveDateTime fallback | **silently assumed UTC** |
| Python naive `datetime(2024,1,1)` | `.isoformat()` → no suffix → UTC fallback | **silently assumed UTC** |

## EPW Timezone Rebase (`from_preparsed`, dwelling/mod.rs:755–767)

```rust
let local_start = config.sim_config.start_time
    .naive_local()                           // strips offset, keeps wall-clock
    .and_local_timezone(tz_offset)           // re-attaches EPW timezone offset
    .single()
    .unwrap_or_else(|| config.sim_config.start_time.with_timezone(&tz_offset));
```

The user-supplied offset is **discarded**.  `naive_local()` preserves the wall-clock
date/time components (year, month, day, hour, minute, second) as the user expressed them,
then stamps them with the EPW file's fixed UTC offset (`timezone_offset_h * 3600`).

Effect: if the user passes `"2019-01-01T00:00:00+00:00"` (UTC midnight) and the EPW file
is US/Central (UTC-6), the simulation starts at `2019-01-01T00:00:00-06:00` — six hours
earlier in absolute time than the user intended.  Wall-clock hour is preserved; absolute
UTC moment is not.

This design treats `start_time` as a wall-clock/local time to be interpreted in the
building's geographic timezone.  It is intentional but undocumented at the API boundary.

## `civil_timezone` Interaction

`civil_timezone` is an IANA string (`"America/New_York"`) stored separately on
`SimulationConfig` and forwarded as-is to `EnvironmentManager`.  It controls only
DST-aware schedule row indexing (gated on the `dst` cargo feature).  It has no effect on
`local_start` or the EPW-rebase above.  If `civil_timezone` is supplied together with a
non-UTC offset on `start_time`, the offset is still replaced by the EPW offset; the IANA
timezone only shifts which schedule row is read each step.

## Defects

### D1 — MEDIUM: Naive input silently assumed UTC (utils.rs:38–51)

A user passing `"2019-07-01T08:00:00"` (no suffix) intending local time will silently get
UTC stored, which after the EPW rebase will shift the simulation by the EPW timezone
offset with no error or warning.

**Fix**: reject naive input with a descriptive error asking for an explicit offset, or
emit a warning that UTC is assumed.

### D2 — MEDIUM: EPW rebase silently discards the supplied offset (dwelling/mod.rs:761–767)

Nothing in the Python API surface or the `_hares.pyi` type stub warns that the supplied
offset is discarded and replaced with the EPW file's timezone.  A caller who passes
`"2019-01-01T06:00:00Z"` expecting UTC midnight Mountain Time will get the wrong
absolute time.

**Fix**: document this contract explicitly in `_hares.pyi` and `py_config.rs`.  Consider
adding a runtime warning when the supplied offset differs from the EPW offset by more than
30 minutes.

### D3 — LOW: `start_time` getter returns the user-supplied value, not the effective simulation start (py_config.rs:169–171)

After `Dwelling` construction the EPW rebase has already changed `local_start`, but
`config.start_time` still returns the original RFC3339 string.  The Python caller cannot
observe the actual start time the simulation uses.

**Fix**: document that `config.start_time` is the user-supplied value and not the
post-rebase effective start, or expose the effective value via the `Dwelling` object.

---

## Coverage Gap

No test constructs a `Dwelling` (or calls `from_preparsed`) with a `start_time` whose UTC
offset differs from the EPW file's `timezone_offset_h`, then asserts on the resulting
`local_start` or the first weather row read.  The existing `compute_annual_offset` unit
tests all use a `utc_offset()` helper that matches the weather fixture timezone, so D1
and D2 are undetectable by the current test suite.

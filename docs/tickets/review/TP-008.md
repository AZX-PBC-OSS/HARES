## Background/Context

OCHRE dwelling/envelope outputs: zone temperatures, total electric/gas power,
per-end-use power, humidity, infiltration, ventilation heat gains, window solar gains,
component loads, unmet HVAC load. This is the primary simulation output users inspect.

## Investigation Instructions

1. **Read OCHRE `Dwelling.generate_results()`** — dwelling-level columns.
2. **Read OCHRE `Envelope.generate_results()`** — per-zone and per-component columns.
3. **Read HARES output system** — what columns does the streaming recorder produce?
4. **Build comparison table** covering:
   - Zone temperatures
   - Total and per-end-use power
   - Humidity (RH, wet bulb, humidity ratio)
   - Infiltration/ventilation heat gains and flow rates
   - Window solar gains
   - Component loads
   - Unmet HVAC load
5. **Assess naming convention** — are HARES column names clear and unit-tagged?


## Findings

### FINDING 1 — CRITICAL: `Unmet HVAC Load (C)` declared in schema, never written

**Files:** `columns.rs:33,94`, `dwelling/mod.rs` (record_step, line 2218–2348)

`columns.rs:94` adds `"Unmet HVAC Load (C)"` to the schema at verbosity >= 2. `record_step` initialises the scratch buffer to 0.0 (`mod.rs:2219`) and never writes to this column's index. Every row silently emits 0.0.

OCHRE reference (`Models/Envelope.py:1338–1344, 1380`) computes it as the signed deviation from the thermal comfort band:
```python
self.unmet_hvac_load = 0
if self.cooling_setpoint is not None:
    hot_comfort_temp = self.cooling_setpoint + self.cooling_deadband / 2
    self.unmet_hvac_load += max(t_liv - hot_comfort_temp, 0)
if self.heating_setpoint is not None:
    cold_comfort_temp = self.heating_setpoint - self.heating_deadband / 2
    self.unmet_hvac_load -= max(cold_comfort_temp - t_liv, 0)
```

This is a per-timestep output column distinct from the `MetricsCalculator::unmet_load_hours` scalar. `MetricsCalculator` does not read this column and so its post-hoc unmet-hours count is unaffected — but any external consumer reading the column gets fabricated zeros.

The dwelling already tracks per-zone setpoints in `setpoint_heat_c` / `setpoint_cool_c` (`mod.rs:1524–1570`), but these are local to the step loop and not retained for `record_step`. They must be stored on the struct and used to compute the comfort-band deviation.

**Fix:** Store active heating and cooling setpoints on the `Dwelling` struct. In `record_step`, compute the signed comfort-band deviation for the Indoor zone and write it to the `"Unmet HVAC Load (C)"` column index.

### FINDING 2 — HIGH: `EquipmentColumns` missing `setpoint`, `soc`, `energy`, `capacity`, `cop` indices

**Files:** `dwelling/mod.rs:116–123` (`EquipmentColumns`), `dwelling/mod.rs:127–164` (`build_equipment_column_map`), `columns.rs:98–141, 198–211`

`build_schema` declares at verbosity >= 3: `"{name} Setpoint (C)"` (HVAC/WH), `"{name} SOC (-)"` (battery/EV). At verbosity >= 4: `"{name} Energy (kWh)"`. At verbosity >= 8: `"{name} Capacity (W)"`, `"{name} COP (-)"`.

`EquipmentColumns` struct only holds `electric_power`, `gas_power`, `mode`, `reactive_power`, `power_factor`. `build_equipment_column_map` resolves only those five. `record_step` writes only those five. All remaining per-equipment columns are always 0.0.

OCHRE (`Equipment/HVAC.py:583`) emits `"{end_use} Setpoint (C)"` from `self.temp_setpoint`. Equipment already exposes setpoint and SOC via telemetry for the dispatch machinery.

**Fix:** Add `setpoint`, `soc`, `energy`, `capacity`, `cop` fields to `EquipmentColumns`. Resolve them in `build_equipment_column_map` using the same `is_hvac_or_wh` / `has_soc` predicates already applied in `build_schema`. Write them from equipment telemetry in `record_step`.

### FINDING 3 — HIGH: `MetricsCalculator` looks up `"HVAC Heating/Cooling Setpoint (C)"` but these columns are never in the schema

**Files:** `metrics.rs:801–808`, `columns.rs` (entire file)

`metrics.rs:801–808`:
```rust
let heating_setpoint_idx = optional_float64_column(schema, &["HVAC Heating Setpoint (C)"])?;
let cooling_setpoint_idx = optional_float64_column(schema, &["HVAC Cooling Setpoint (C)"])?;
let (Some(heating_setpoint_idx), Some(cooling_setpoint_idx)) = ... else {
    return Ok(None);   // ← always taken
};
```

Neither `"HVAC Heating Setpoint (C)"` nor `"HVAC Cooling Setpoint (C)"` appears in `build_schema`. The early `return Ok(None)` is always taken, so `SimulationMetrics::unmet_load_hours` and `comfort_hours` are always `None` in production.

OCHRE reference (`defaults/Variable names and units.csv` rows 30, 41) places these at verbosity 4. They are also present in every OCHRE sample output CSV header.

Note: these are aggregate HVAC setpoint columns, separate from the per-equipment `"{name} Setpoint (C)"` columns in FINDING 2. Both sets are missing.

**Fix:**
1. Add `"HVAC Heating Setpoint (C)"` and `"HVAC Cooling Setpoint (C)"` to `build_schema` at verbosity >= 4.
2. Populate them in `record_step` from the active thermal setpoints (available from the step loop, see FINDING 1).

### FINDING 4 — MEDIUM: Five boundary-component heat gain columns declared in schema, not written

**Files:** `columns.rs:173–177`, `dwelling/mod.rs:2294–2324`, `hares-envelope/src/thermal_solver/stepping.rs:159–171`

`build_schema` adds at verbosity >= 6:
- `"Roof Heat Gain - Indoor (W)"`
- `"Floor Heat Gain - Indoor (W)"`
- `"Wall Heat Gain - Indoor (W)"`
- `"Window Heat Gain - Indoor (W)"`
- `"Internal Mass Heat Gain - Indoor (W)"`

`EnvelopeComponentGains` (`hares-envelope/src/thermal_solver/config.rs:458–466`) holds `roof_heat_gain_w`, `floor_heat_gain_w`, `wall_heat_gain_w`, `window_heat_gain_w`, `internal_mass_heat_gain_w` and these are correctly accumulated in `stepping.rs:159–171`.

`record_step`'s `envelope_cols` slice (`mod.rs:2296–2319`) includes window solar, infiltration, ventilation, internal gain, radiation, opaque solar, duct loss, HVAC heating, HVAC cooling — but none of these five boundary-component values. They are computed correctly in the solver but never written to output.

**Fix:** Extend the `envelope_cols` array in `record_step` with the five missing boundary mappings from `gains.roof_heat_gain_w`, `gains.floor_heat_gain_w`, `gains.wall_heat_gain_w`, `gains.window_heat_gain_w`, `gains.internal_mass_heat_gain_w`.

### FINDING 5 — MEDIUM: `expected_columns_at_verbosity` omits `"Outdoor Dry Bulb (C)"`

**Files:** `columns.rs:222–232`, `columns.rs:95`

`build_schema` adds `"Outdoor Dry Bulb (C)"` at verbosity >= 2 (`columns.rs:95`). `expected_columns_at_verbosity(2)` returns only `"Temperature - Indoor (C)"` and `"Unmet HVAC Load (C)"` and omits this column. Any test driving column-completeness checks off this utility function silently misses the outdoor temperature column.

**Fix:** Add `OUTDOOR_TEMP_COL` to the verbosity >= 2 branch of `expected_columns_at_verbosity`.

---

### FINDING 6 — LOW: Dead fallback for non-existent column name `"Indoor Temperature (C)"`

**Files:** `dwelling/mod.rs:2283–2287`

```rust
if let Some(&idx) = self.output_column_index.get("Indoor Temperature (C)")
    && let Some(&(_, temp_c)) = self.zone_temp_scratch.first()
{
    row[idx] = temp_c;
}
```

`build_schema` never produces a field named `"Indoor Temperature (C)"`. The OCHRE/HARES convention is `"Temperature - Indoor (C)"`, which the zone-column loop above this block already handles correctly. The lookup always returns `None`; this block is unreachable.

**Fix:** Remove the dead block.

## Recommended Tests

These tests do not currently exist and should be added after the fixes:

1. **`record_step_populates_unmet_hvac_load`** — Run a synthetic step with indoor temp above cooling setpoint and assert `"Unmet HVAC Load (C)"` is positive. Run with indoor temp below heating setpoint and assert it is negative. Run within the band and assert zero.

2. **`record_step_populates_equipment_setpoint_and_soc`** — Construct a dwelling with HVAC and Battery. After one step, read verbosity-3 output and assert `"{name} Setpoint (C)"` is non-zero for the HVAC and `"{name} SOC (-)"` is in `[0.0, 1.0]` for the battery.

3. **`metrics_unmet_load_hours_non_none_with_setpoint_columns`** — Build a `RecordBatch` that includes `"HVAC Heating Setpoint (C)"` and `"HVAC Cooling Setpoint (C)"` columns (once added to the schema) and assert that `SimulationMetrics::unmet_load_hours` is `Some(...)`, not `None`.

4. **`boundary_component_gains_written_at_verbosity_6`** — Run a dwelling at verbosity 6 for one step and assert `"Wall Heat Gain - Indoor (W)"`, `"Roof Heat Gain - Indoor (W)"`, etc. are non-zero (requires a building with finite UA values for these boundary types).

5. **`expected_columns_at_verbosity_matches_schema`** — Parameterised over verbosity 0–8: assert that every column returned by `expected_columns_at_verbosity(v)` is present in `build_schema(&[], v)`. This would have caught FINDING 5 automatically.

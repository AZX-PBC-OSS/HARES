## Background/Context

HPXML temperatures are in °F. HARES stores in °C (SI). The conversion is
`°C = (°F - 32) × 5/9`. However, temperature *differences* (deadbands, deltas) use
a different factor: `Δ°C = Δ°F × 5/9` (no offset). Confusing these is a common bug.

## Investigation Instructions

1. **Find every temperature field parsed from HPXML across all resolve files:**
   - Heating/cooling setpoints
   - Deadband temperatures
   - HP lockout temperatures (compressor, backup)
   - Water heater setpoint
   - Thermostat setup/setback temperatures

2. **For each field, verify:**
   - Is it an absolute temperature or a temperature difference?
   - Is the correct conversion applied? (`(F-32)*5/9` for absolute, `F*5/9` for delta)
   - What function is used? (`temperature_f_to_c`? manual? `uom` crate?)

3. **Search for hardcoded temperature constants:**
   - Are there any hardcoded °F values in the Rust equipment code that should be °C?
   - Grep for common values: 32.0, 212.0, 140.0, 120.0, etc.

4. **Compare with OCHRE:**
   - What `convert()` calls does OCHRE make for temperature fields?

5. **Write findings** with per-field table showing conversion type and correctness.


## Findings

### Summary

All absolute temperature conversions are correct. No hardcoded °F values exist in Rust equipment code. The `51.67` and `60.0` constants in `resolve_water_heater.rs` are valid °C values sourced from OCHRE. The `DEFAULT_BACKUP_ENABLE_OFFSET_C = 8.0` constant in `hpwh_compressor.rs` has no documented °F source and its derivation is unclear. One unit-recognition gap exists in `child_temperature_c()`.

### 3. `resolve_water_heater.rs` Hardcoded Values 51.67 and 60.0

**`51.67`** (`resolve_water_heater.rs:120–121`):
- Used as tempering valve setpoint threshold and value.
- `125°F → (125-32)×5/9 = 51.6̄°C`. The literal `51.67` is a 2dp rounding of this; the constant `DEFAULT_SETPOINT_C = 51.666_666_7` is more precise.
- OCHRE reference: `vendors/OCHRE/ochre/utils/hpxml.py:1181`: `"Tempering Valve Setpoint (C)": convert(125, "degF", "degC")`.
- Source is correct, but the hardcoded literal `51.67` inconsistently differs from the more precise `DEFAULT_SETPOINT_C = 51.666_666_7` defined in the same crate. See Finding F-3.

**`60.0`** (`resolve_water_heater.rs:118–119`):
- Used as the default HPWH storage setpoint fallback.
- `140°F → (140-32)×5/9 = 60.0°C exactly`.
- OCHRE reference: `vendors/OCHRE/ochre/utils/hpxml.py:1180`: `"Setpoint Temperature (C)": convert(140, "degF", "degC")`.
- The value is exactly correct and matches `DEFAULT_MAX_TANK_TEMP_C = 60.0`.

### 4. Delta Temperature Conversions (deadbands, differentials)

All deadband constants are confirmed to be temperature *differences* and are converted correctly using `ΔF × 5/9` without the −32 offset.

| Constant | Raw °F | Conversion applied | Result °C |
|---|---|---|---|
| ERWH `DEFAULT_DEADBAND_C` | 10°F | `10 × 5/9` | 5.5̄5°C |
| HPWH `DEFAULT_DEADBAND_C` | 14.7°F | `14.7 × 5/9` | 8.16̄6̄°C |
| HP `DEFAULT_ER_SETPOINT_OFFSET_MULTIPLIER` / `DEFAULT_ER_SETPOINT_DEADBAND_OFFSET` | N/A | Pure scale factors (dimensionless), not temperature conversions | N/A |

OCHRE equivalent: `kwargs.get("Deadband Temperature (C)", 5.56)` for ERWH and `kwargs.get("Deadband Temperature (C)", 8.17)` for HPWH. The HARES value `8.166_666_667` differs from the OCHRE literal `8.17` by ~0.003°C — this is a benign rounding difference in OCHRE's documentation string; the HARES value is more precise.

### 5. Defects Found

**F-1 (Medium) — `child_temperature_c()` does not recognise all unit string variants**
- File: `crates/hares-io/src/hpxml/xml_helpers.rs:50`
- `child_temperature_c()` only matches `"f"`, `"degf"`, `"fahrenheit"` as °F indicators and falls through to treating any other non-empty `units` value as already °C. If the HPXML file contains `units="degF"` (capital F, which `to_ascii_lowercase()` normalises to `"degf"`) that is handled. However, the variant `units="F"` is only handled after lowercasing to `"f"`. This is fine.
- The real gap: the default branch (no `units` attribute) assumes °F, which is correct for HPXML. **But if `units` is an unrecognised string (e.g. `units="Fahrenheit"` — capital F), the code silently passes the raw °F value as °C**. The `convert_temperature_to_c` function used by `ValueKind::Temperature` in `building.rs` handles this identically but with a `tracing::debug` warning. `child_temperature_c()` does not warn on unrecognised units strings.
- Confidence: high; the silent passthrough is a latent data-quality risk. In practice HPXML files use `"F"` consistently, but there is no safeguard.

**F-2 (Low) — `DEFAULT_BACKUP_ENABLE_OFFSET_C = 8.0` in `hpwh_compressor.rs` has no documented origin**
- File: `crates/hares-equipment/src/water_heater/hpwh_compressor.rs:23`
- This is a delta °C value (the tank temperature must drop `8.0°C` below the setpoint before the backup resistance element is enabled). No OCHRE source reference or °F original is given in any comment.
- `8.0°C` does not correspond to a round °F value: `8.0 × 9/5 = 14.4°F`. OCHRE does not appear to have a matching explicit constant for this threshold in the searched files.
- This should be documented with its source or verified against OCHRE's HPWH backup-enable logic.

**F-3 (Low) — Literal `51.67` in `resolve_water_heater.rs` should use `DEFAULT_SETPOINT_C`**
- File: `crates/hares-io/src/hpxml/resolve_water_heater.rs:120–121`
- The magic literal `51.67` is a rounded value of `51.666_666_7` (= 125°F → °C). The crate already exports `DEFAULT_SETPOINT_C = 51.666_666_7`. Using the literal introduces a 0.003°C inconsistency in the threshold and the value inserted into params.
- The threshold comparison `storage_setpoint_c > 51.67` could fail to activate the tempering valve when the parsed setpoint equals the exact converted value `51.666_666_7` (since `51.666… < 51.67` is false, but the valve should fire). This is a correctness edge case.

---

### 6. OCHRE Comparison

All HPXML temperature paths in HARES that have OCHRE equivalents use the same conversion formula as OCHRE's `convert(value, "degF", "degC")` (pint-based). The uom-backed `temperature_f_to_c` function in `hares-physics/src/units.rs` is verified correct (`(F-32)*5/9`) by the existing unit tests at `units.rs:313–317`.

No setup/setback temperature fields were found in the HPXML schema sections covered by the codebase. HPXML does not have dedicated setup/setback XML elements; these are encoded as the hourly setpoint schedule arrays (`WeekdaySetpointTemps*`).

1. **`child_temperature_c_warns_on_unrecognised_units`** — Pass a `<HotWaterTemperature units="Kelvin">330</HotWaterTemperature>` node to `child_temperature_c()` and assert the returned value is not treated as °C silently. Either a warning is logged or the function returns `None`. Currently it returns `330.0` (the raw value) without any warning, while `ValueKind::Temperature` at least issues a `tracing::debug` trace. The two paths should behave consistently.

2. **`tempering_valve_activates_when_setpoint_exactly_125f`** — Parse a water heater node with `<HotWaterTemperature>125</HotWaterTemperature>` (no units attribute, so parsed as °F = 51.666_666_7°C). Assert that `tempering_valve_setpoint_c` is present in the resulting params, confirming the threshold `> 51.67` comparison does not silently suppress the valve when input is exactly 125°F. Currently this test would **fail** due to F-3.

3. **`lockout_temps_round_trip_from_hpxml`** — Parse a heat pump node with `<CompressorLockoutTemperature>0</CompressorLockoutTemperature>` and `<BackupHeatingLockoutTemperature>40</BackupHeatingLockoutTemperature>`. Assert `hp_lockout_temp_c ≈ -17.778` and `er_lockout_temp_c ≈ 4.444` (within 1e-3°C).

4. **`setpoint_24h_array_converts_all_elements`** — Parse a control node with a 24-element `WeekdaySetpointTempsHeatingSeason` array where all values are `68` (°F). Assert all 24 elements in the resulting `heating_weekday_setpoints_c` are `≈ 20.0°C` (within 1e-3).

5. **`hpwh_storage_setpoint_default_60c`** — Parse a HPWH node with no `HotWaterTemperature` element. The resolver defaults to `60.0°C` from `DEFAULT_MAX_TANK_TEMP_C`. Confirm `setpoint_c` in params equals `60.0` and `tempering_valve_setpoint_c` equals `51.666_666_7` (from `DEFAULT_SETPOINT_C`), not `51.67`.

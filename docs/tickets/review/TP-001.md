## Background/Context

OCHRE outputs specific columns per HVAC heating equipment at various verbosity levels:
`"{end_use} Delivered (W)"`, `"{end_use} Setpoint (C)"`, `"{end_use} COP (-)"`,
`"{end_use} Duct Losses (W)"`, `"{end_use} Main Power (kW)"`, `"{end_use} Fan Power (kW)"`,
`"{end_use} Speed (-)"`, `"{end_use} Capacity (W)"`, `"{end_use} Max Capacity (W)"`.

HARES should emit equivalent telemetry fields.

## Findings

### F-1 (High) — `operating_mode` encodes as float enum; OCHRE emits human-readable string

**File:** `crates/hares-equipment/src/hvac/heat_pump/heater_config.rs:14-17`

OCHRE emits `"HVAC Heating Mode"` as a string (`"Off"`, `"HP On"`, `"HP and ER On"`, `"ER On"`,
`"On"`) at verbosity >= 7 via `Equipment.generate_results()`. HARES encodes operating mode as a
float ordinal (`0.0`, `3.0`, `4.0`, `5.0`) under the key `"operating_mode"`. The numeric encoding
is not self-describing. Any consumer expecting the OCHRE column name or string value will silently
get the wrong answer.

AR-001 previously identified this as `"mode"` vs `"operating_mode"` — the finding here adds that
the value type also differs (string vs float) and that the float encoding scheme is private to
`heater_config.rs` with no public constant or doc string for the full mapping.

The furnace `operating_mode` codes are defined only as integer constants in `heater_config.rs:14-17`
with no corresponding documentation in the furnace path (furnace mode 1 = Heating, but this is only
described inline in the `TelemetryField` description string, not as constants).

**Fix:** Either expose a canonical mode-to-string mapping that consumers can use, or emit the mode
as a string key alongside the float ordinal. The float ordinal is acceptable for performance in the
engine hot loop, but the output layer must map it to the OCHRE string form for parity.

---

### F-2 (Medium) — Gas furnace unit for fuel consumption is W, not therms/hour

**File:** `crates/hares-equipment/src/hvac/furnace.rs:386`, `crates/hares-types/src/telemetry_keys.rs:16`

HARES emits `fuel_input_w` in **Watts** (SI). OCHRE emits `"HVAC Heating Gas Power (therms/hour)"`.
This is an intentional SI-first design (see memory: `feedback_si_units.md`) and is correct
internally. However, any output adapter mapping HARES telemetry to OCHRE-compatible column names
must convert W → therms/hour at the boundary. The current `metrics.rs:18` defines
`GAS_POWER_SUFFIX = " Gas Power (therms/hour)"` but it is marked `#[allow(dead_code)]`, meaning
there is no active output conversion path for the gas furnace fuel key.

If the output metrics layer is supposed to produce OCHRE-compatible columns, this path is broken and
the `dead_code` annotation is masking it.

---

### F-3 (Medium) — `heating_setpoint_c` and `cooling_setpoint_c` emitted by furnaces but not HP heater

**Files:** `furnace.rs:462-463`, `heater_config.rs:19-31`

`ElectricFurnace` and `GasFurnace` emit both `heating_setpoint_c` and `cooling_setpoint_c`
(six fields total). `HeatPumpHeater` emits neither. OCHRE emits `"HVAC Heating Setpoint (C)"`
(the active heating setpoint) for all heaters at verbosity >= 4. The HP heater is missing this
field entirely. A downstream consumer looking at setpoints cannot observe the HP heater's active
setpoint from telemetry.

---

### F-4 (Medium) — `cop` emitted by HP heater only; `fan_kw` emitted by gas furnace only; `speed_index` emitted by HP heater only

**Files:** `heater_config.rs:26`, `furnace.rs:469`

OCHRE emits `"HVAC Heating COP (-)"` for all HVAC heating equipment at verbosity >= 4, including
furnaces (where it equals `thermal_output_w / (electric_kw * 1000)`). For the electric furnace COP
is always 1.0; for the gas furnace it equals AFUE. HARES only emits `cop` for the HP heater.

Similarly, `fan_kw` is emitted by `GasFurnace` but not by `HeatPumpHeater`, even though the HP
heater has an indoor fan. OCHRE emits `"HVAC Heating Fan Power (kW)"` for all dynamic HVAC
including ASHPs.

`speed_index` is emitted by HP heater but not by other multi-speed paths if any are ever added.
This is lower risk but sets an inconsistent pattern.

---

### F-5 (Low) — `capacity_w` and `max_capacity_w` not exposed in any heating equipment telemetry

**Files:** `furnace.rs`, `heater_config.rs`

OCHRE emits `"HVAC Heating Capacity (W)"` (current operating capacity) and
`"HVAC Heating Max Capacity (W)"` at verbosity >= 5. Neither is in any HARES heater telemetry map.
These are useful for debugging and are required for full parity at verbosity 5+.

---

### F-6 (Low) — ER power not separately exposed for ASHP heater

**File:** `crates/hares-equipment/src/hvac/heat_pump/heater.rs`

OCHRE's `ASHPHeater.generate_results()` emits `"HVAC Heating ER Power (kW)"` (electric resistance
strip power, separate from HP compressor power) at verbosity >= 7. HARES emits `compressor_kw`
(compressor-only) and `electric_kw` (total), but not ER strip power as a discrete field. Given
that `electric_kw - compressor_kw` would give ER strip power implicitly, this is low severity
unless ER strip diagnostics are needed in the output layer.

---

### F-7 (Low) — `runtime_fraction` semantics differ between HARES and OCHRE

**File:** `heater_config.rs:69-71`

HARES defines `runtime_fraction` as "Compressor runtime fraction (part-load ratio) this timestep".
OCHRE does not emit a `Runtime Fraction` column for HVAC — this is a HARES-specific field
(OCHRE uses `speed_idx` and `duty_cycle` internally but does not surface `runtime_fraction` in
output). This field exists in HARES but has no OCHRE counterpart; it is not a mismatch per se, but
it should be documented as a HARES extension to avoid confusion during parity validation.

---

### F-8 (Low) — Electric furnace `fuel_input_w` checkpoint field hard-coded to 0.0

**File:** `crates/hares-equipment/src/hvac/furnace.rs:207`

The `ElectricFurnace` checkpoint encodes `fuel_input_w: 0.0` unconditionally (line 207). Because
electric furnaces have no fuel, this is semantically correct, but the field is present in the
checkpoint struct and could mislead a reader expecting the struct to mirror reality. A named unit
struct with a `PhantomData` or a single-variant tuple would be cleaner; at minimum the struct
should not carry a `fuel_input_w` field for a device that never uses fuel.

The following specific assertions should be verified once fixes are applied:

1. After F-2 fix: assert `GasFurnace` output adapter emits `"HVAC Heating Gas Power (therms/hour)"`
   equal to `fuel_input_w / 3412.14` when OCHRE-compat output is requested.

2. After F-3 fix: assert `HeatPumpHeater.telemetry().get("heating_setpoint_c")` returns the active
   setpoint at each step in an existing integration test (e.g. the `cz4a_ashp_hpwh` parity fixture).

3. After F-1 fix: assert the mode-string mapping covers all five OCHRE mode strings and round-trips
   to the same float ordinal, tested as a unit test in `heater_config.rs`.

4. For F-5: add assertions in `hvac_tests.rs` that `capacity_w` and `max_capacity_w` are present
   in telemetry and non-zero when the heater is on.

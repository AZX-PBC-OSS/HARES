## Background/Context

BMS TOU (time-of-use) windows determine when to charge/discharge the battery. These
must align with the utility's local rate schedule. A UTC error means the battery
charges during peak instead of off-peak.

## Investigation Instructions

1. **Read `crates/hares-core/src/actors/bms.rs`:**
   - How are TOU windows / `BmsScheduleWindow` evaluated?
   - What time field drives the window check?
   - Does it use `env.current_time.hour()` or something else?

2. **Check price signal interaction:**
   - When `PriceSignal` is present, does the BMS use price directly (no time needed)
     or does it also check time windows?
   - Is the price signal timestamp in local time?

3. **Compare with OCHRE Battery.py** — how does OCHRE determine TOU periods?

4. **Write findings** with line numbers and recommendations.

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### TOU window time source

`BmsMode::Scheduled` evaluates windows at `bms.rs:330-332`:

```rust
let weekday = env.current_time.weekday();
let minute_of_day =
    (env.current_time.hour() * 60 + env.current_time.minute()) as u16;
```

`env.current_time` is `DateTime<FixedOffset>` (`environment.rs:190`). The fixed
offset is whatever was baked into `start_time` when the `SimClock` was constructed
(`clock.rs:55-59`). The `clock.rs` module-level comment states:

> Pass the intended local hour in `start_time`. If you mean noon Denver time,
> pass `12:00` — not `19:00 UTC`.

This means `.hour()` and `.weekday()` on `current_time` produce local wall-clock
values as long as the caller constructed the clock with the correct local offset.
**There is no automatic conversion inside the BMS or the clock.** If the caller
passes a UTC `start_time` (offset = +00:00) for a location that is UTC-7, all
window evaluations are 7 hours early.

The `civil_timezone` path (`environment.rs:103-169`) provides DST-aware
reinterpretation but it only applies to schedule-array indexing in
`EnvironmentManager`, not to the `current_time` field itself. The `current_time`
field still reflects the `FixedOffset` supplied at construction.

**Verdict: local time, correct by convention.** No timezone conversion happens
inside the BMS. Correctness depends entirely on the caller supplying a
properly-offset `start_time`. This is documented in `clock.rs` but the
invariant is not enforced or validated anywhere.

### `TimeOfUseOptimization` mode — price-schedule day indexing

`BmsMode::TimeOfUseOptimization` uses `env.current_time.ordinal0()` as a
day-of-year index into `price_schedule` (`bms.rs:215`, `443`, `508`).
`ordinal0()` on `DateTime<FixedOffset>` returns the 0-based day-of-year in the
local date expressed by the fixed offset.

If `price_schedule` was built from a UTC-indexed annual series but `current_time`
carries a negative-offset locale (e.g. UTC-8), the day rolls over at 16:00 local
time the previous calendar day rather than at midnight. At that moment
`ordinal0()` returns the next calendar day, while the first 8 hours of the new
UTC day's prices are still indexed against the old day's price array. This is
the UTC/local mismatch described in the Review Notes.

**Severity: MEDIUM.** Manifests only when `TimeOfUseOptimization` is used with
a non-UTC offset AND the price schedule is UTC-indexed. If the price schedule is
already local-time indexed (as it should be for a residential TOU tariff), there
is no bug. The code has no documentation or validation to enforce that alignment.

### `PriceSignal` scalar path

`PriceSignal.electricity_price` is a plain `Option<f64>` with no timestamp
(`environment.rs:203`). When the BMS reads it (`bms.rs:228`, `302`) it receives
only the scalar; time is irrelevant for the comparison against the computed
thresholds. The thresholds themselves are computed from `price_schedule` using
`ordinal0()` (see above). The PriceSignal scalar is presumed to be the correct
current-step price already delivered by the tariff evaluator.

### OCHRE comparison

OCHRE `Battery.py` has no TOU window logic at all. TOU/scheduling is handled
upstream by the OCHRE orchestrator (via external control signals such as
`P Setpoint`, `Min SOC`, `Max SOC`, `SOC`). `Battery.update_external_control`
(`Battery.py:169-197`) and `Battery.update_internal_control`
(`Battery.py:205-247`) operate on pre-resolved setpoints; they do not parse
time windows internally. OCHRE's degradation check at midnight uses
`self.current_time.time() == dt.time(0, 0)` (`Battery.py:317`), which is Python
`datetime.datetime` in whatever timezone the simulation runs — no explicit
UTC/local handling there either.

**Conclusion: OCHRE has no equivalent window evaluation to compare against.** The
HARES `BmsMode::Scheduled` and `BmsMode::TimeOfUseOptimization` are HARES-native
constructs; there is no OCHRE reference to diverge from.

### Summary of defects

| # | Severity | Location | Description |
|---|----------|----------|-------------|
| 1 | MEDIUM | `bms.rs:215,408,443` | `ordinal0()` used as a day-of-year price-array index. If `price_schedule` is UTC-indexed and `current_time` carries a non-UTC offset, the daily threshold recomputation fires one step too early at day boundaries, misaligning price buckets for up to `abs(utc_offset_hours)` hours. |
| 2 | LOW | `clock.rs`, `bms.rs` | The invariant "caller must supply a local-time `start_time`" is undocumented at the actor call sites and not validated. A misconfigured UTC `start_time` silently produces wrong window evaluations with no error or warning. |

### Recommended fixes

**Defect 1** — Add a doc comment on `BatteryManagementActor::new` (and the
`price_schedule` field) stating that `price_schedule` must be indexed in the same
local time as `start_time`, i.e. step 0 = midnight on day 0 of the simulation.
If the price schedule will ever be sourced from a UTC-indexed series, the
`ordinal0()` slicing must be replaced with a step-counter-relative index that is
independent of the calendar date.

**Defect 2** — Add a `debug_assert` in `SimClock::new` or the `EnvironmentManager`
constructor that rejects a zero-offset `start_time` with a non-zero building
latitude (or more broadly: emit a warning when `FixedOffset::east_opt(0)` is used
with a timezone that is clearly not UTC). Alternatively, expose a constructor
that accepts `chrono_tz::Tz` directly and converts `start_time` internally,
removing the caller-responsibility entirely.

## Recommended Tests

1. `bms_scheduled_window_respects_offset` — construct an actor in
   `BmsMode::Scheduled` with a window `[22:00, 06:00)`, set `env.current_time` to
   23:00 UTC-5 and assert the window matches; set to 23:00 UTC+0 (same wall clock,
   different calendar) and assert the same match. Then set to 05:00 UTC-5 and
   assert match; 07:00 and assert no match.

2. `tou_price_thresholds_recomputed_on_day_boundary_local` — build a 48-step
   price schedule with distinct AM/PM blocks for two local days; run the actor
   through a midnight crossing with a UTC-5 offset and assert that thresholds
   switch at local midnight (step 24 of day-1 prices), not 5 hours early.

## Review Notes

`price_schedule` path uses `env.current_time.ordinal0()` as a day-of-year index — if price array is UTC-indexed but `ordinal0()` reflects local time, there's a 1-day offset risk. Reframe PriceSignal question: `PriceSignal` is a scalar `electricity_price: Option<f64>` with no timestamp — ask whether BMS uses `env.current_time` exclusively for TOU period identification.

## Background/Context

HARES stores all physical quantities as bare `f64` values. While the convention is
"store in SI," nothing in the type system enforces this. A value in watts and a value
in kilowatts are both `f64` — the compiler cannot catch `power_kw + power_w`. This
is a chronic source of bugs, especially at boundaries (HPXML parsing, Python API,
telemetry output) where unit conversions happen.

The `uom` crate provides compile-time unit checking. The memory feedback says to use
it for unit conversions. This ticket assesses where it would provide the most value.

## Findings

### F1 — GAP — Duplicate `W_TO_BTU_H` constant in `ashrae152.rs` is lower precision than the canonical constant

**File:** `crates/hares-physics/src/ashrae152.rs:15`

```rust
const W_TO_BTU_H: f64 = 3.41214;   // 5 significant figures
```

**Canonical value:** `crates/hares-physics/src/constants.rs:92`

```rust
pub const BTU_PER_HR_PER_W: f64 = 3.412_141_633;  // 10 significant figures
```

The `ashrae152.rs` module defines its own local conversion constant rather than importing
the canonical value from `constants.rs`. The relative precision error is ~4.8e-7, which
propagates into every `capacity_btu_h` computation in the ASHRAE 152 DSE calculation
(lines 344, 462, 504). While the DSE output is bounded [0,1] and the resulting error
on DSE is negligible, the pattern defeats the purpose of having a centralised constants
module. The constant should be imported from `hares_physics::constants::BTU_PER_HR_PER_W`.

The same constant is also redeclared locally in
`crates/hares-equipment/src/hvac/air_conditioner.rs:40` with full precision:

```rust
const BTU_PER_HR_PER_W: f64 = 3.412_141_633;
```

That too should import from `hares_physics::constants` rather than re-define.

**Severity:** LOW. Numerical impact is sub-ppm. Code-quality impact is MEDIUM — violates
the DRY principle the constants module was created to enforce.

### F2 — GAP — `THERMS_TO_KWH` in `metrics.rs` is lower precision than `GAS_THERMS_PER_HOUR_TO_W`

**File:** `crates/hares-io/src/output/metrics.rs:26`

```rust
const THERMS_TO_KWH: f64 = 29.3001;
```

**Canonical derivation:** `crates/hares-physics/src/constants.rs:105`

```rust
pub const GAS_THERMS_PER_HOUR_TO_W: f64 = 29_307.107_017_222_2;
```

1 therm = 29,307.107 W·s/s at 1 therm/hour = 29.307_107 kWh. The `metrics.rs` constant
uses `29.3001`, which differs from the NIST-derived value by ~0.024% (29.3001 vs
29.307107). These two constants describe the same physical quantity (energy per therm)
and must agree. The divergence means that gas energy summed via metrics (`total_kwh_equivalent`)
does not match gas energy computed by the simulation engine when it back-converts W to
therms using `GAS_THERMS_PER_HOUR_TO_W`. For a 10 therm/year building the error is
~0.7 kWh/year — small but unnecessary since the precise value is already available.

`THERMS_TO_KWH` should be defined as `GAS_THERMS_PER_HOUR_TO_W / 1000.0` or import
the constant from `hares_physics::constants`.

**Severity:** LOW numerically. MEDIUM for internal consistency. The test at
`crates/hares-io/tests/comprehensive_tests.rs:303–307` hard-codes `29.3001` directly,
reinforcing the drift.

### F3 — GAP — `ashrae152.rs` conversion constants are all private manual floats; `uom` could validate several of them

**File:** `crates/hares-physics/src/ashrae152.rs:13–18`

```rust
const M3_TO_FT3: f64 = 35.3147;       // precise: 35.314666...
const M2_TO_FT2: f64 = 10.7639;       // precise: 10.763910...
const M3S_TO_CFM: f64 = 2118.88;      // precise: 2118.880...
const SI_R_TO_IP_R: f64 = 5.67826;    // precise: 5.678263...
```

These are internal-to-IP-back-to-SI bridge constants for an algorithm that specifies
its calculation in IP units. The values have been rounded to 4–6 significant figures.
The corresponding exact values derivable from `uom` or the existing `units.rs` helpers
carry 7–12 significant figures. The rounding is consistent across all uses within the
function, so no asymmetric precision error occurs, but the precision floor is
unnecessarily low.

For completeness: `M3_TO_FT3 = 1.0 / CFM_TO_M3_S * (1/60)` — not quite, since they
are different conversions, but `uom` has exact `cubic_meter` → `cubic_foot` and
`cubic_meter_per_second` → `cubic_foot_per_minute` conversions that should be used at
module init (via `OnceLock`) rather than hand-entered constants.

**Severity:** LOW for physics results (error < 0.001%). IMPROVEMENT for maintainability.

### F4 — ACCEPTABLE DIFFERENCE — Default supply air temperatures stored as rounded °C values

**File:** `crates/hares-equipment/src/hvac/hvac_core.rs:77–84`

```rust
Self::GasFurnace    => 54.4,   // 130°F exact = 54.444...°C  → error +0.044°C
Self::ElectricFurnace => 48.9, // 120°F exact = 48.888...°C  → error +0.011°C
Self::AshpHeatPumpAux => 40.6, // 105°F exact = 40.555...°C  → error +0.044°C
Self::MiniSplitHeat => 43.3,   // 110°F exact = 43.333...°C  → error -0.033°C
Self::AshpHeatPumpOnly => 32.2,// 90°F exact  = 32.222...°C  → error -0.022°C
```

These are RESNET/ASHRAE default reference temperatures defined in Fahrenheit. The
values stored are truncated rather than properly converted via `temperature_f_to_c()`.
Each rounded value carries a maximum error of ±0.05°C. Because these are defaults
overridden by HPXML or config, and because OCHRE itself uses `convert(105, "degF", "degC")`
(which yields 40.555°C), the HARES rounding causes a systematic offset of up to +0.05°C
in supply air temperature for unoverridden cases.

The values should be computed at const-eval time using `temperature_f_to_c` if possible,
or replaced with the precise decimal (e.g., 54.444, 40.556). Given that OCHRE thermal
parity is already documented at 0.4–0.9°C MAE, this 0.05°C contribution is not the
dominant error source. Classifying as ACCEPTABLE DIFFERENCE pending a separate physics
accuracy pass.

**Note:** The tests at `hvac_core.rs:1008–1027` assert against the rounded stored values,
not the precise converted values. They would need updating if the constants are corrected.

### F5 — GAP — `outdoor_temp` observation field name lacks unit suffix

**File:** `crates/hares-core/src/telemetry.rs:37`

```rust
if field == "outdoor_temp" {
    out.push(self.outdoor_temp_c);
```

The public observation field key `"outdoor_temp"` returns a value in Celsius, but the
name contains no unit indicator. The struct field itself is named `outdoor_temp_c`,
which is consistent with the rest of the codebase convention. The `to_observation_vec`
string API is used from Python (`py_dwelling.rs:1323`) and gym environments.

A Python user who reads the field name `"outdoor_temp"` has no type-system indication
of the unit. If a Fahrenheit assumption is made, the error is large (e.g., treating
21°C as 21°F is a 11.7°C error). The field should be named `"outdoor_temp_c"` and the
old name should be removed (greenfield codebase, no backward compat required per
project memory).

**Severity:** MEDIUM. Silent data misinterpretation risk for Python gym users.

### F6 — GAP — `CurtailmentPercent` Python constructor has no input validation

**File:** `crates/hares-python/src/py_control.rs:186–191`

```rust
pub fn curtailment_percent(percent: f64) -> Self {
    Self {
        signal: ControlSignal::CurtailmentPercent { percent },
    }
}
```

No bounds check is applied at the Python boundary. The Rust equipment layer at
`crates/hares-equipment/src/pv/mod.rs:672` validates `[0, 100]`, but only for the PV
equipment. If `percent = 150.0` or `percent = f64::NAN` is passed, it will pass through
the Python API silently, and only fail (or silently clamp/ignore) when the PV equipment
processes it. Other equipment that might consume `CurtailmentPercent` may not perform
the same validation. The public API boundary should validate `[0.0, 100.0]` and
`is_finite()`.

**Severity:** MEDIUM. User API correctness.

### F7 — GAP — `convert_conductivity_to_w_m_k` has no `None` (missing units) fallback

**File:** `crates/hares-io/src/hpxml/building.rs:1686–1694`

```rust
fn convert_conductivity_to_w_m_k(value: f64, units: Option<&str>) -> f64 {
    match units {
        Some("btu/hr-ft-f") | Some("btu/(h*ft*f)") => ...,
        Some("btu-in/hr-ft2-f") | ...  => ...,
        _ => value,    // ← None AND unrecognised units fall here silently
    }
}
```

Unlike `convert_area_to_m2`, `convert_volume_to_m3`, `convert_u_to_w_m2_k`, and
`convert_length_to_m`, the conductivity converter has no `None` branch and no log
warning when units are absent. An HPXML file that omits the `units` attribute on a
conductivity element will silently pass through the value unchanged. Since HPXML
conductivity values are typically expressed in BTU units, a missing `units` attribute
would result in a value ~7× too small (1 BTU/(hr·ft·°F) = 1.7307 W/(m·K)), causing
significantly under-insulated envelope elements.

**Severity:** HIGH. Silent data corruption for malformed HPXML files. No test coverage
for this case exists.

### F8 — GAP — `convert_density_to_kg_m3` and `convert_specific_heat_to_j_kg_k` have no `None` (missing units) warning

**File:** `crates/hares-io/src/hpxml/building.rs:1711–1722`

```rust
fn convert_density_to_kg_m3(value: f64, units: Option<&str>) -> f64 {
    match units {
        Some("lb/ft3") | ... => ...,
        _ => value,    // ← None falls here silently
    }
}
fn convert_specific_heat_to_j_kg_k(value: f64, units: Option<&str>) -> f64 {
    match units {
        Some("btu/lb-f") | ... => ...,
        _ => value,    // ← None falls here silently
    }
}
```

Same pattern as F7 but for density and specific heat. Density in BTU-IP is lb/ft³;
1 lb/ft³ = 16.02 kg/m³. If units are absent and the value is e.g. `0.075` (lb/ft³ for
dry air) the function returns `0.075` kg/m³ instead of `1.2` kg/m³ — a 16× error.
These converters should emit `tracing::debug!` for missing units and assume an IP
default (matching the HPXML spec, which is IP-native), consistent with the area and
length converters.

**Severity:** MEDIUM. Malformed HPXML will produce silently wrong material properties.

### F9 — ACCEPTABLE DIFFERENCE — `uom` is already a dependency but is only used in `hares-physics`, `hares-equipment`, and `hares-io`

`uom = "0.38"` is declared in the workspace `Cargo.toml` and pulled into
`hares-physics`, `hares-equipment`, and `hares-io`. Internal hot-loop code in
`hares-core`, `hares-envelope`, and `hares-equipment` correctly uses plain `f64` for
performance and uses `uom` only at conversion boundaries. This is the intended
"boundary adoption" strategy documented in `units.rs`. The existing pattern is
appropriate.

**Not a defect.** The absence of `uom` from `hares-core` is intentional.

**File:** `crates/hares-equipment/src/hvac/air_conditioner.rs:40`

## Existing Unit Conversion Inventory

### `crates/hares-physics/src/units.rs`
Complete and well-structured. Provides `uom`-backed helpers for:
- Temperature (°F/°C/K), with a `_delta_c_to_f` variant for differentials
- Area (ft² ↔ m²)
- Length (ft, in → m)
- Power (BTU/h ↔ W, BTU/h → kBTU/h) — manual constant, cited as NIST
- U-value and R-value (IP ↔ SI, via `uom::HeatTransfer`)
- Thermal conductivity (two BTU variants — manual constants)
- Density (lb/ft³ → kg/m³)
- Specific heat (BTU/lb·°F → J/kg·K)
- Volume (ft³, gal → m³)
- Composite BTU/(hr·°F) → W/K for water heater UA

All functions tested in the `units.rs` test module with numerical tolerances. The module
documents the uom limitation (no BTU/h power unit) explicitly.

### `crates/hares-physics/src/constants.rs`
Defines 22 shared physical constants, all cited to ASHRAE HOF, NIST, or ISA. Notable:
- `GAS_THERMS_PER_HOUR_TO_W = 29_307.107_017_222_2` (NIST SP 811 derivation documented)
- `W_PER_TON = 3_516.852_842_066_667` (ASHRAE definition)
- `CFM_TO_M3_S / CFM_PER_M3_S` pair
- `BTU_PER_HR_PER_W = 3.412_141_633`
- Temperature offset constants (`CELSIUS_TO_KELVIN`, `FAHRENHEIT_OFFSET`, `FAHRENHEIT_SCALE`)

### HPXML parsing (`crates/hares-io/src/hpxml/`)
Has a centralised `convert_*` function family (`building.rs:1624–1738`) with `units`-
attribute dispatch. Most converters handle `None` with a `tracing::debug!` warning and
an IP-first default assumption. Exceptions are conductivity, density, and specific heat
(see F7, F8).

### Python API (`crates/hares-python/src/`)
All Python-facing parameters use SI units with unit-encoding names (`_c` for Celsius,
`_kw` for kilowatts, `_kwh` for kilowatt-hours, `_w` for watts). The `SimulationConfig`
and `DwellingConfig` parameters are correctly named. The observation vector API uses
free strings that lack enforcement (see F5).

## Recommended Tests

### T1 — Test conductivity converter with `None` units (F7)
Add a unit test in `crates/hares-io/src/hpxml/building.rs` (or its test module) that
calls `convert_conductivity_to_w_m_k(0.023, None)` and asserts the function logs a
warning AND applies an IP-default assumption (i.e., returns `0.023 * 1.730_734_67`).
Currently the `None` arm silently returns `0.023` without conversion.

### T2 — Test density/specific-heat converter with `None` units (F8)
Similar to T1: add tests asserting that `convert_density_to_kg_m3(0.075, None)` and
`convert_specific_heat_to_j_kg_k(0.24, None)` emit tracing events and apply IP defaults.

### T3 — Test THERMS_TO_KWH constant consistency (F2)
Add a test in `crates/hares-io/src/output/metrics.rs` that asserts:
`(THERMS_TO_KWH - GAS_THERMS_PER_HOUR_TO_W / 1000.0).abs() < 1e-4`
This would have caught the existing 0.024% drift.

### T4 — Test `CurtailmentPercent` Python boundary validation (F6)
Add a Python test in `tests/python/` that asserts `ControlSignal.curtailment_percent(-1.0)`
and `ControlSignal.curtailment_percent(101.0)` raise `ValueError`, and that `NaN` also
raises `ValueError`.

### T5 — Test `outdoor_temp` observation field name is deprecated/renamed (F5)
After renaming to `"outdoor_temp_c"`, add a test that confirms the old field name
`"outdoor_temp"` returns an `Err` from `to_observation_vec`, and that `"outdoor_temp_c"`
returns the Celsius value.

### T6 — Test that `BTU_PER_HR_PER_W` canonical constant matches ashrae152 `W_TO_BTU_H` (F1/F10)
Add a test asserting `(BTU_PER_HR_PER_W - 1.0 / 0.293_071_07).abs() < 1e-9` to confirm
the inverse relationship is consistent, as a regression guard once the local constants
are consolidated.

## uom / Newtype Strategy Recommendation

### Assessment

The existing architecture already follows the optimal pattern for a hot-loop simulation
codebase:

1. **`uom` at conversion boundaries** (units.rs) — conversions are typed and tested.
2. **Plain `f64` in hot-loop code** (equipment step functions, envelope solver) — avoids
   `uom` overhead in inner loops.
3. **Naming convention enforces units** (`_c`, `_kw`, `_w`, `_m2`, `_m3`, etc.) — human
   readable contract at all public struct fields.

**Full `uom` adoption** across all internal structs would require wrapping every struct
field, substantially increasing verbosity and API friction with no physics improvement.
The hot-loop cost of `uom::Quantity` arithmetic is measurable on repeated simulations.

**Newtype wrappers** (e.g., `struct Watts(f64)`) would be intermediate but do not prevent
accidental arithmetic between same-unit quantities (`Watts + Watts` is fine but
`Watts / Seconds` requires manual boilerplate). They add friction without compile-time
dimensional analysis.

### Recommendation

Maintain the current **boundary adoption** strategy. Address the concrete defects above
(F1–F8) rather than investing in a full `uom` migration. The highest value follow-up
would be:

1. Fix F7 (silent conductivity pass-through) — this is a latent correctness bug.
2. Fix F5 (`outdoor_temp` → `outdoor_temp_c`) — prevents Python API misuse.
3. Fix F2 (align `THERMS_TO_KWH` with `GAS_THERMS_PER_HOUR_TO_W`) — internal consistency.
4. Fix F6 (validate `CurtailmentPercent` at Python boundary) — public API contract.
5. Consolidate duplicate constants (F1, F10) — maintenance hygiene.

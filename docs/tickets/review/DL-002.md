## Background/Context

OCHRE distributes HVAC delivered heat across zones:
- `conditioned_zone: dse * (1 - basement_frac)`
- `duct_zone: 1 - dse` (duct losses go to the zone where ducts are located)
- `basement_zone: dse * basement_frac` (if applicable)

HARES must replicate this distribution for correct zone-level energy balance.

## Investigation Instructions

1. **Read OCHRE HVAC.py `zone_fractions`** (line ~188) — document the exact distribution.
2. **Read HARES `duct_distribution.rs` `update_zone_heat_fractions()`:**
   - Compare fraction formulas.
   - What happens when `duct_zone == conditioned_zone`? (Known: duct loss is discarded.)
   - Is this correct? OCHRE routes it as a zone gain for same-zone ducts.
3. **Check `basement_heat_frac`** — is 0.2 correct? Only for heating? What about cooling?
4. **Write findings** with fraction comparison table.


## Fraction Formula Comparison

| Zone | OCHRE (`HVAC.py:189–197`) | HARES (`duct_distribution.rs:23–41`) | Match? |
|---|---|---|---|
| Conditioned | `dse * (1 − basement_frac)` | `dse * (1 − basement_frac)` | Yes |
| Duct zone (distinct, dse < 1) | `1 − dse` | `1 − dse` | Yes |
| Basement zone (distinct) | `dse * basement_frac` | `dse * basement_frac` | Yes |
| Basement zone == duct zone | `(1 − dse) + dse * basement_frac` (additive merge) | **two separate vec entries** (functionally correct via accumulator, but semantically wrong) | Partial |
| Duct zone == conditioned zone | OCHRE: resets `dse = 1`, delivers 100% | HARES: delivers `dse * (1 − basement_frac)`, discards `1 − dse` | **NO** |
| Default `basement_frac` for cooling | 0.0 | 0.2 (resolver injects unconditionally) | **NO** |

## Findings

### FINDING 1 — HIGH: `duct_zone == conditioned_zone` silently discards `(1 − dse)` of gross capacity

**Location:** `duct_distribution.rs:35–41`, `hvac_core.rs:1918–1931`

OCHRE (`HVAC.py:175–178`) detects `duct_zone == self.zone` at init, resets `duct_dse = 1`, clears `duct_zone`, and warns. Result: 100% of gross capacity reaches the conditioned zone — duct losses are physically impossible when ducts are inside the conditioned space.

HARES skips adding the duplicate duct-zone entry but retains the original `dse` value, so `conditioned_frac = dse * (1 − basement_frac)`. With DSE = 0.85 this delivers only 85% of gross capacity; the remaining 15% is permanently lost. The test `update_zone_heat_fractions_same_duct_zone` (`duct_distribution.rs:211`) and `write_zone_thermal_contributions_duct_zone_same_as_conditioned_merges` (`hvac_core.rs:1918`) codify and assert this incorrect behaviour.

Quantified impact: a building with DSE = 0.85 and ducts in the conditioned zone sees 15% less delivered heat than OCHRE for every heating/cooling step. This directly affects setpoint attainment and energy metrics.

**Fix:** In `update_zone_heat_fractions()`, when `duct_zone_id == Some(zone_id)`, set `dse = 1.0` before computing fractions (mirroring OCHRE), emit a `tracing::warn!`, and update `self.duct_dse`. Update the two affected tests to assert `conditioned_frac = 1.0` (no duct loss).

---

### FINDING 2 — HIGH: Default `basement_heat_frac = 0.2` applied to cooling equipment

**Location:** `crates/hares-io/src/hpxml/resolve_hvac.rs:245`

OCHRE (`HVAC.py:183`):
```python
default_basement_frac = 0.2 if basement_zone.zone_type == "Finished Basement" and self.is_heater else 0
```

The 0.2 default is **heating-only**. Cooling equipment gets 0.0.

`compute_basement_params()` in HARES unconditionally inserts `basement_airflow_ratio = 0.2` for any finished-basement building, regardless of whether the equipment is a heater or a cooler. Both heating and cooling equipment call `hvac_core::init()` which reads this value. A cooling system in a finished-basement building will route 20% of its gross cooling output to the basement zone, undercooling the conditioned zone.

No test covers cooling-equipment + finished-basement.

**Fix:** Pass heating/cooling context to `compute_basement_params()` (or produce separate param maps per system type), and emit `basement_airflow_ratio = 0.0` for cooling equipment.

---

### FINDING 3 — MEDIUM: `basement_zone_id == duct_zone_id` emits duplicate zone entries

**Location:** `duct_distribution.rs:26–41`

OCHRE merges the basement and duct fractions additively when they share a zone:
```
zone_fractions[basement_zone] = (1 − dse) + dse * basement_frac
```

HARES builds two separate `(zone_id, fraction)` entries in `zone_heat_fractions`. The accumulator in `write_zone_thermal_contributions()` sums both, so the numerical result is identical to OCHRE for the standard ports path. However:

- The vec is documented as "one entry per zone" (`hvac_core.rs:177–179`) but is not enforced.
- Any consumer that finds unique zone keys (e.g. ideal-capacity solver, telemetry, serialisation) will see duplicate entries and may produce incorrect results or double-counts.
- There is no test for this configuration.

**Fix:** After building `zone_heat_fractions` in `update_zone_heat_fractions()`, merge entries that share the same `ZoneId` by summing their fractions. Add a test that sets `basement_zone_id == duct_zone_id` and asserts a single merged entry with the correct combined fraction.

---

### FINDING 4 — LOW: `HvacEquipment::init()` does not call `update_zone_heat_fractions()` — fragile contract

**Location:** `hvac_core.rs:460–483`

`init()` reads `basement_zone_id` and `basement_airflow_ratio` but does not call `update_zone_heat_fractions()`. Each concrete equipment type must call it manually after `hvac.init()`. Currently furnace, AC, heat-pump heater, and baseboard all do. If a future equipment type omits this call, `zone_heat_fractions` silently defaults to `[(zone_id, 1.0)]` set in `new()`, ignoring all DSE config.

**Fix:** Document the required call sequence explicitly on `HvacEquipment::init()` with a `# Panics` or `# Contract` doc comment. As a stronger guard, add a `debug_assert!` at the start of `write_zone_thermal_contributions()` that `zone_heat_fractions` is non-empty and that no zone appears more than once.

## Background/Context

Refrigerators and freezers should run on a fixed schedule profile, independent of
occupancy or thermal state. Their power consumption is typically flat (24/7 with minor
schedule modulation).

## Investigation Instructions

1. Read HARES `scheduled_load.rs` — how is a refrigerator/freezer configured?
2. Does it use the schedule CSV column? Or a constant power?
3. Read OCHRE — how is the refrigerator load scheduled?
4. Compare: is the annual energy converted to correct instantaneous power?

## Findings

### Summary

Both refrigerator and freezer use `ScheduledLoad` in HARES and OCHRE. The schedule mechanism
is **schedule-modulated by a daily + monthly profile**, not a flat constant. The profile is
identical in both codebases when a CSV schedule column is provided. When no CSV column exists,
HARES falls back to a default hourly profile loaded from `Default Schedule Parameters.csv`,
or (if that file is absent) a constant-power fallback with a loud warning. This behavior
matches OCHRE's fallback to its own default schedule parameters file.

### OCHRE behavior

`ScheduledLoad.update_internal_control` (ScheduledLoad.py:67-82) reads `self.current_schedule["Power (kW)"]`
each timestep — this is the schedule-column value (kW), already scaled to match annual energy.
The schedule is built from 24 hourly weekday/weekend fractions and 12 monthly multipliers
sourced from `Default Schedule Parameters.csv` (or from HPXML `WeekdayScheduleFractions`/
`WeekendScheduleFractions`/`MonthlyScheduleMultipliers` extension fields).

The refrigerator default profile (OCHRE `Default Schedule Parameters.csv`):
- Hourly fractions: uniform ~0.036–0.050, peaking at hour 20 (8 pm), sourced from
  2010 BA House Simulation Protocols Figure 16.
- Monthly multipliers: range 0.835–1.096, highest in summer months (Jun–Sep ≈ 1.096),
  lowest in winter (Feb ≈ 0.835). Sourced from 2010 BAHSP Figure 24.
- Freezer profile: same hourly fractions and monthly multipliers as refrigerator.

Two additional coefficient arrays (`ConstantScheduleCoefficients` and
`TemperatureScheduleCoefficients`, sourced from ANSI/RESNET/ICC 301-2022 Addendum C,
Table C.3(2)) appear in the defaults CSV but are **not referenced anywhere in OCHRE's Python
code**. OCHRE does not implement temperature-dependent refrigerator power modulation.

### HARES behavior

**`crates/hares-equipment/src/scheduled_load.rs`**

Refrigerator and Freezer are registered as `ScheduledLoad` (lines 557-568). The step
function reads from `self.power_source`, which is one of:
- `ScheduleSource::ColumnRef` — reads a named column from the simulation schedule CSV
- `ScheduleSource::DailyProfile` — reads a precomputed 24×12 profile baked from weekday/
  weekend/month-multiplier arrays
- `ScheduleSource::Constant` — flat constant kW (fallback only)

Month multipliers are applied at runtime for `ColumnRef` sources (line 368-373); for
`DailyProfile` sources they are already baked in and the runtime multiplier is cleared
(lines 277-281) to avoid double-scaling.

**`crates/hares-io/src/schedule_resolve.rs`**

When `refrigerator` or `freezer` CSV columns are present, HARES maps them via `COLUMN_MAPPINGS`
(lines 62-71) to `ScheduleSource::ColumnRef`. The max_kw is derived from `annual_electric_kwh`
divided by the profile mean fraction (line 670: `annual_kwh / 8760 / mean_fraction`).

When no CSV column is present, HARES checks for a default profile in `Default Schedule
Parameters.csv`. If found, it builds a `ScheduleSource::DailyProfile` (inject_compact_profile_power,
line 587). If neither CSV column nor default profile exists, it falls back to
`ScheduleSource::Constant` with a loud warning (line 590-594: "THIS MAY BE INCORRECT").

**`crates/hares-io/src/hpxml/resolve_loads.rs`**

For Refrigerator and Freezer, `annual_electric_kwh` is populated from:
1. `AdjustedAnnualkWh` extension field (refrigerator only, OCHRE hpxml.py:1389-1390)
2. `RatedAnnualkWh` HPXML element (line 81-82)
3. `child_load_kwh` — extension `Load` value (line 84-85)

**BUG — Missing default annual kWh for refrigerator/freezer**

OCHRE falls back to `637 + 18 * n_bedrooms` kWh for a primary refrigerator when no
rated energy is present (hpxml.py:1393-1394), and `319.8` kWh for a freezer
(hpxml.py:1418-1420).

HARES has no such fallback in `resolve_loads.rs` (lines 78-92, match arm `_ => {}`
for Refrigerator/Freezer). If the HPXML file omits `RatedAnnualkWh` and contains no
extension load value, `annual_electric_kwh` will be absent from `params`. The
schedule resolver will then see `annual_electric_kwh = None`, `determine_max_kw` will
return `None` (schedule_resolve.rs:666), and `determine_constant_kw` will also return
`None`, resulting in `0.0 kW` — a silent zero-energy refrigerator. This is a correctness
defect: the dwelling appears to have no refrigerator electricity draw despite having
one modeled.

**BUG — Freezer heat gain fraction mismatch**

HARES sets `frac_sensible = 1.00, frac_latent = 0.00` for both Refrigerator and Freezer
(resolve_loads.rs:614). This matches OCHRE's refrigerator behaviour (convective_gain = 1.0
when indoor). However, OCHRE's `parse_freezer` explicitly sets `gain_frac = 0` regardless
of location (hpxml.py:1424), meaning OCHRE currently ignores freezer heat gains entirely.
The HARES value of 1.0 is arguably more physically correct (a freezer located indoors does
reject heat to the space) but represents a divergence from OCHRE parity. This should be
documented as a deliberate choice, or matched to OCHRE, per project policy
(`feedback_ashrae_not_ochre.md` says prefer ASHRAE physics over OCHRE bugs).

**`extra_refrigerator` column ignored**

`extra_refrigerator` is listed in COLUMN_MAPPINGS as `ScheduleCategory::Ignore`
(schedule_resolve.rs:173-176). OCHRE also has no `Extra Refrigerator` equipment class in
its `__init__.py` — the extra_refrigerator schedule column is not consumed by any equipment.
This is consistent between HARES and OCHRE.

**Temperature-dependent coefficients not implemented in either system**

Neither OCHRE nor HARES implements the ANSI/RESNET/ICC 301-2022 Addendum C temperature
coefficients for refrigerator power adjustment. HARES is not behind OCHRE here. This is a
future physics enhancement opportunity, not a current defect.

### Fix Required — Finding 1

In the `Refrigerator`/`Freezer` match arm (or after the match block at line 286), add
bedroom-count-based defaults when `annual_electric_kwh` is still absent:

```rust
// Refrigerator: OCHRE hpxml.py:1393-1394
"Refrigerator" => {
    if !params.contains_key("annual_electric_kwh") {
        let kwh = (637.0 + 18.0 * n_bedrooms) * multiplier;
        params.insert("annual_electric_kwh".to_string(), json!(kwh));
    }
}
// Freezer: OCHRE hpxml.py:1418-1420
"Freezer" => {
    if !params.contains_key("annual_electric_kwh") {
        let kwh = 319.8 * multiplier;
        params.insert("annual_electric_kwh".to_string(), json!(kwh));
    }
}
```

Note: the `multiplier` variable is already resolved at this point in the surrounding
HPXML parse context (e.g., `extension.UsageMultiplier`). If it is not currently parsed for
refrigerator/freezer, add `child_f64(node.child("extension"), "UsageMultiplier").unwrap_or(1.0)`.

### Fix Required — Finding 2

Add a code comment at resolve_loads.rs:614 stating the intentional divergence:

```rust
// Refrigerator: 100% sensible gain (all heat rejected to conditioned space).
// Freezer: OCHRE uses gain_frac=0 (TODO comment in hpxml.py:1422-1424), which
// ignores heat gain from indoor freezers — a known OCHRE simplification. HARES
// uses 1.00 consistent with ASHRAE for indoor units, per feedback_ashrae_not_ochre.
"Refrigerator" | "Freezer" => Some((1.00, 0.00)),
```

## Background/Context

HPWHs are the most complex water heater: heat pump compressor + backup electric
resistance, wet-bulb COP scaling, operating modes (HP only, hybrid, ER only),
zone interaction (removes heat from ambient air). Config wiring is critical.

## Investigation Instructions

1. **Read OCHRE `HeatPumpWaterHeater.py`** — all config keys:
   - HP COP and capacity as f(wet-bulb, water temp)
   - Operating modes and mode switching logic
   - Backup element capacity and position
   - Zone interaction: sensible/latent heat removal from ambient
   - Compressor location (indoor/outdoor/garage)

2. **Read HARES `heat_pump_wh.rs` and `hpwh_compressor.rs`:**
   - Config keys consumed
   - COP model — biquadratic or lookup table?
   - Mode switching logic

3. **Build comparison table** (expect 20+ fields).

4. **Pay special attention to:**
   - HPWH COP derivation from UEF (linear formula `1.174536058 * UEF`)
   - Zone heat extraction (sensible + latent) — is this wired to thermal ports?
   - Operating mode from HPXML `HPWHOperatingMode` — is it parsed?
   - Tempering valve logic when setpoint > 51.67°C
   - PARITY-013 HPWH HP/ER duty cycle — was this completed?

### DEFECT-1 — Tempering valve setpoint hardcoded to 51.67°C, ignores HPXML setpoint

**File:** `crates/hares-io/src/hpxml/resolve_water_heater.rs:115-122`

OCHRE sets `Tempering Valve Setpoint (C) = t_set` for all HPWHs, where `t_set` is the
HPXML `HotWaterTemperature` field (default 125°F = 51.67°C). HARES hardcodes the valve
to 51.67°C regardless of the HPXML setpoint.

Consequence: when the HPXML specifies a setpoint other than the default 125°F (e.g., 130°F = 54.4°C), HARES sets the tempering valve to 51.67°C but OCHRE would set it to 54.4°C. This changes the mixed delivery temperature and the hot-water volume available to fixtures.

The condition `if storage_setpoint_c > 51.67` is also incorrect: OCHRE always sets
the tempering valve to `t_set` for HPWHs unconditionally. If the setpoint is 48°C
(below 51.67), HARES emits no tempering valve at all while OCHRE would still set one.

**Fix:** Emit `tempering_valve_setpoint_c = setpoint_c` (whatever the HPXML setpoint is)
for all HPWHs, without a conditional.

### DEFECT-2 — EF-only HPWH gets no COP derivation

**File:** `crates/hares-io/src/hpxml/resolve_water_heater.rs:111-113`

When an HPXML file specifies `EnergyFactor` but not `UniformEnergyFactor` for a HPWH,
HARES emits no `cop` key. The equipment model then uses `cop_scale = 1.0` (pure curve
output, unanchored to the rated performance). OCHRE converts EF→UEF first:

```python
# ochre/utils/hpxml.py:1169-1170
if uniform_energy_factor is None:
    uniform_energy_factor = (0.60522 + energy_factor) / 1.2101
```

then derives COP as `1.174536058 * uef`.

For a typical HPWH EF of 2.0, OCHRE would compute UEF = (0.60522 + 2.0) / 1.2101 ≈ 2.15,
COP ≈ 2.53. HARES would leave cop_scale = 1.0 (curve unscaled, different effective COP).

**Fix:** Add EF→UEF→COP fallback in resolver when `uniform_energy_factor` is `None` but
`energy_factor` is present.

### DEFECT-3 — Low-power HPWH (UEF == 4.9) overrides not wired

**File:** `crates/hares-io/src/hpxml/resolve_water_heater.rs`

OCHRE applies a special override block when `uniform_energy_factor == 4.9`:

```python
# ochre/utils/hpxml.py:1174-1184
if uniform_energy_factor == 4.9:
    wh.update({
        "Low Power HPWH": True,
        "HPWH COP (-)": 4.2,
        "HPWH Capacity (W)": 1499.4,
        "Setpoint Temperature (C)": 60.0,
        "Tempering Valve Setpoint (C)": 51.67,
        "hp_only_mode": True,
    })
```

HARES resolver does not implement this override. If a ResStock-style HPXML file
specifies UEF = 4.9 (a 120V dedicated-circuit HPWH), HARES will:
- Use the standard GE GeoSpring COP curve scaled to `1.17 * 4.9 = 5.75` (vs OCHRE's 4.2)
- Use a default compressor power of 1200W (vs OCHRE's 1499.4W)
- Leave the setpoint at whatever HPXML specifies (vs OCHRE's forced 140°F storage)
- Not enable hp_only_mode (backup element will incorrectly fire)
- Use the standard (not low-power) lockout bounds

OCHRE also uses separate biquadratic coefficients for low-power HPWHs:
```python
# WaterHeater.py:469-470
self.hp_capacity_coeff = np.array([0.813, 0.0160, 0.000537, 0.0020319, -0.0000860, -0.0000686])
self.cop_coeff = np.array([1.1332, 0.063, -0.0000979, -0.00972, -0.0000214, -0.000686])
```

Neither the `dedicated_circuit` nor the `low_power` curve-set selection is wired.

**Fix:** Implement the UEF == 4.9 override block in the resolver, emitting `low_power_hpwh`,
the overridden COP, compressor capacity, setpoint, tempering valve, and `hp_only_mode`.
Also define the low-power biquadratic coefficients in `hpwh_compressor.rs` and route
them when `low_power_hpwh = true`.

### DEFECT-4 — `heating_capacity_w` emitted by resolver is silently ignored for HPWH

**File:** `crates/hares-io/src/hpxml/resolve_water_heater.rs:70-72`; `crates/hares-equipment/src/water_heater/heat_pump_wh.rs:425-434`

The resolver emits `heating_capacity_w` (from `<HeatingCapacity>` in HPXML) for all
water heater types. In OCHRE, `Capacity (W)` is the **backup resistance element**
capacity (`ElectricResistanceWaterHeater.capacity_rated`). The HPWH inherits this.

In HARES, `HeatPumpWH::init()` reads `backup_element_power_w` from keys
`["backup_element_power_w", "BackupElementPower"]` — neither of which matches the
`heating_capacity_w` key emitted by the resolver. The backup element always defaults
to 4500W regardless of the HPXML `<HeatingCapacity>`.

For HPWHs where HPXML specifies a non-default backup element capacity (common in
ResStock fixtures where element sizes vary from 2250W to 5500W), this produces silent
incorrect behavior.

**Fix:** The resolver should also insert `backup_element_power_w` for HPWHs when
`heating_capacity_w` is present. Alternatively, `HeatPumpWH::init()` should add
`"heating_capacity_w"` to its lookup list for `backup_element_power_w`.

### DEFECT-5 — `lost_heat_fraction` and `wall_heat_fraction` default to 0 instead of OCHRE defaults

**File:** `crates/hares-equipment/src/water_heater/hpwh_compressor.rs:46`

OCHRE:
```python
# WaterHeater.py:481-483
lost_heat_default = 0.75 if self.zone_name == "Indoor" else 1
self.lost_heat_fraction = 1 - kwargs.get("HPWH Interaction Factor (-)", lost_heat_default)
self.wall_heat_fraction = kwargs.get("HPWH Wall Interaction Factor (-)", 0.5)
```

OCHRE's default `HPWH Interaction Factor (-)` is 0.75 for Indoor zone, 1.0 otherwise.
`lost_heat_fraction = 1 - 0.75 = 0.25` (Indoor) or `1 - 1.0 = 0.0` (non-Indoor).
`wall_heat_fraction` default is 0.5.

HARES: `DEFAULT_LOST_HEAT_FRACTION = 0.0` and `wall_heat_fraction` defaults to 0.0.

The resolver does not emit these fields. The equipment default `lost_heat_fraction = 0.0`
matches the non-Indoor case only. For the common case where the HPWH is in a conditioned
zone (Indoor), the correct default is 0.25. Since the resolver knows the zone from
`Location`, it could emit the appropriate default.

The `wall_heat_fraction = 0.0` default diverges from OCHRE's 0.5 for all zones with an
interior wall surface. This reduces the fraction of sensible gain directed to wall mass,
which affects zone temperature modeling.

**Fix:** Emit `lost_heat_fraction` from the resolver based on the parsed zone (0.25 for
conditioned/indoor zones, 0.0 for unconditioned). Emit `wall_heat_fraction = 0.5` for
conditioned zones.

### DEFECT-6 — Jacket R-value formula diverges from OCHRE

**File:** `crates/hares-equipment/src/water_heater/mod.rs:136-152`; `ochre/utils/hpxml.py:1131-1138`

OCHRE's formula models pre-existing insulation as a resistance layer:
```python
jacket_insulation = 5.0  # R5, in F-ft2-hr/Btu
jacket_thickness = 1 if is_electric and energy_factor < 0.7 else 2  # inches
diameter = 2 * sqrt((volume / 1000 / height / pi)) * 3.281  # ft
a_side = pi * diameter * (height * 3.281)
u_pre_skin = 1.0 / (jacket_thickness * jacket_insulation + 1/1.3 + 1/52.8)
ua -= jacket_r / (1/u_pre_skin + jacket_r) * u_pre_skin * a_side  # Btu/hr-°F
```

HARES simply places `jacket_r/lateral_area_m2` in series with `1/ua_base`:
```rust
// mod.rs:150-151
let r_total = 1.0 / ua_base + jacket_r / lateral_area_m2;
1.0 / r_total
```

These are different approximations. The OCHRE formula accounts for the existing foam
insulation layer and the interaction between the jacket R-value and the original UA.
At typical jacket R-values (R-8 to R-20), the error can be 5–15% of the jacket UA
reduction. This is a secondary effect but should be documented; the current HARES
formula is a reasonable approximation for most cases.

### DEFECT-7 — `cop_scale` lookup key list includes `UniformEnergyFactor` raw value

**File:** `crates/hares-equipment/src/water_heater/heat_pump_wh.rs:451`

```rust
self.cop_scale = if let Some(cop_rated) =
    first_f64(config, &["cop", "rated_cop", "UniformEnergyFactor"])
```

The fallback `"UniformEnergyFactor"` would read the raw UEF value (e.g., 3.45) as a
COP, which is incorrect since `cop_scale` is used as a multiplier on top of the
biquadratic curve evaluation. The raw UEF is not the COP (COP = 1.174536 * UEF). If
a config were ever constructed with `UniformEnergyFactor` but not `cop`, the COP
curve would be scaled by the wrong factor.

In practice the resolver always writes `cop` when UEF is present, so this key is
dead. But it is a footgun — the list should contain only `["cop", "rated_cop"]`.

---

### DEFECT-8 — `HPWHOperatingMode` HPXML field not parsed

Neither OCHRE nor HARES parses `<HPWHOperatingMode>` from HPXML. OCHRE has no
handling for it. HARES also lacks it. This is currently acceptable since the field
is optional in HPXML 4.x and defaults to "Hybrid" in practice. Document as a known
gap for HPXML 4.0 compliance.

---

### Architecture note — OCHRE vs HARES rated capacity semantics

OCHRE models `hp_capacity_nominal` as rated **thermal output** (W). Electrical input
is derived as `power = capacity / cop`. Default `hp_capacity_nominal = 500W_input * cop`.

HARES models `compressor_power_w` as rated **electrical input** (W). Thermal output
is derived as `delivered = input * cop`. Default `compressor_power_w = 1200W`.

These are inverse representations of the same physics and produce equivalent results
when parameterised consistently. However, since the resolver's `heating_capacity_w`
(from `<HeatingCapacity>`) represents the backup element thermal capacity, not the
compressor input, the field name mismatch contributes to DEFECT-4.

## Background/Context

Foundation height determines foundation zone volume. OCHRE reads it from HPXML
`Foundation Wall Height`. A wrong default affects foundation thermal mass and
ground coupling.

## Investigation Instructions

1. Read `building.rs` — how is foundation zone height determined?
2. Is it from HPXML `FoundationWall/Height`?
3. What is the default when not specified?
4. Compare with OCHRE.
5. Is the unit converted (ft→m)?


## Findings

### CRITICAL — Foundation zone volume uses conditioned ceiling height instead of wall height

**Location:** `crates/hares-io/src/hpxml/building.rs:677-679`

```rust
ZoneType::Garage | ZoneType::Foundation => {
    zone.floor_area_m2.map(|a| a * default_height_m)
}
```

`default_height_m` is derived at line 672 as `ceiling_height_m.unwrap_or(2.5)`,
where `ceiling_height_m` is `ConditionedBuildingVolume / ConditionedFloorArea`
(lines 418-421) — the per-storey height of the conditioned living space.  This
value is unrelated to the actual foundation wall height.

**OCHRE reference** (`vendors/OCHRE/ochre/utils/hpxml.py:679-680`):

```python
foundation_height = boundaries["Foundation Wall"]["Height (m)"]
foundation_volume = first_floor_area * foundation_height
```

OCHRE reads `<Height>` directly from the HPXML `<FoundationWall>` element
(converted ft→m at line 183) and uses it exclusively for the foundation zone
volume.

**Impact:** Foundation zone volume is overstated whenever foundation wall height
< conditioned ceiling height (typical for crawlspaces: 0.6–1.0 m wall vs.
2.4–2.7 m assumed).  A 2.5x overestimate of volume understates thermal
capacitance per unit air mass, inflates infiltration-driven load, and corrupts
ground-coupling calculations.  The error direction reverses for tall conditioned
basements only when their wall height exceeds the conditioned ceiling height,
which is rare.

### CRITICAL — Foundation wall height is parsed but not stored

`extract_foundation_wall_insulation` (`building.rs:1096`) already reads
`<FoundationWall><Height>` for the insulation area-scale calculation, but the
value is a function-local variable and is never returned or stored.  The `Zone`
struct has no `height_m` field; `Building` has no per-zone height map.  There
is no code path that could connect the parsed wall height to the volume loop.

### HIGH — ELA stack coefficient will receive wrong height

OCHRE passes `foundation_height` to `calculate_ela_coefficients("Foundation",
foundation_height)` (`hpxml.py:708`).  The stack coefficient is proportional to
`zone_height` (`envelope.py:675`).  If HARES implements an equivalent ELA
coefficient calculation for foundation zones and feeds `default_height_m`, the
stack pressure term will carry the same wrong-height error.

### MEDIUM — No regression test for foundation zone volume

There is no test that asserts `zone.volume_m3` for a fixture containing a
`<FoundationWall>` with an explicit `<Height>` value.  The bug has no regression
guard.

---

## Required Fix

1. After boundaries are built, find the `FoundationWall` boundary and read its
   `<Height>` (or derive it by re-scanning the HPXML foundation wall nodes with
   the same logic already in `extract_foundation_wall_insulation`).  Store the
   result in a local `foundation_height_m: Option<f64>`.

2. Change the `ZoneType::Foundation` arm in the volume loop to:
   ```rust
   ZoneType::Foundation => zone.floor_area_m2
       .zip(foundation_height_m)
       .map(|(a, h)| a * h),
   ```

3. Avoid parsing `<FoundationWall><Height>` twice — factor the height extraction
   out of `extract_foundation_wall_insulation` or return it alongside the
   insulation string and area scale.

4. Add a unit test in `crates/hares-io/tests/` (or in the `#[cfg(test)]` block
   in `building.rs`) with a synthetic HPXML containing a 0.9 m foundation wall
   and asserting `zone.volume_m3 == floor_area * 0.9`.

## Background/Context

`PyDwelling.step()` returns a Python dict with keys like `time`, `net_electric_power_kw`,
`hvac_heating_w`, `hvac_cooling_w`, `Temperature-*`. Users need predictable, documented
keys that align with OCHRE's output columns where possible.

---

## Findings

### HARES step() return keys (crates/hares-python/src/py_dwelling.rs:565-577)

`PyDwelling.step()` returns a `PyDict` with exactly these keys:

| Key | Type | Unit |
|-----|------|------|
| `timestamp` | `datetime.datetime` | — |
| `net_electric_power_kw` | `float` | kW (positive = import, negative = export) |
| `hvac_heating_w` | `float` | W (positive, heat delivered to zone) |
| `hvac_cooling_w` | `float` | W (positive, heat removed from zone) |
| `"Temperature - Indoor (C)"` | `float` | °C (zone 0) |
| `"Temperature - Zone_N (C)"` | `float` | °C (zones 1..N, present only if multi-zone) |

Zone temperature keys are synthesised at first-step time and cached in `self.zone_keys`. The key set is stable across steps for a given dwelling instance but the zone temperature keys are absent from the `StepResult` `TypedDict` stub in `_hares.pyi:13-24` (they are documented only in a docstring comment at line 16-17).

`SteppableFleet.step()` (py_fleet.rs:419-433) emits the same keys **plus** `reactive_power_kvar` (conditionally, when telemetry is available), matching the `SteppableStepResult` stub at `_hares.pyi:26-27`.

### OCHRE step() equivalent

OCHRE has no `step()` method. The per-step API is `Dwelling.update(control_signal, schedule_inputs)` (Simulator.py:326-336), which calls `update_results()` → `generate_results()` and returns the results dict for that timestep. The Dwelling-level `generate_results()` (Dwelling.py:295-332) plus the base Envelope and Equipment `generate_results()` chain produce the following key groups (verbosity ≥ 0 is always active in the `update()` call path):

**Verbosity 0 (always present)**
| Key | Unit |
|-----|------|
| `Time` | `datetime` |
| `Total Electric Power (kW)` | kW |
| `Total Reactive Power (kVAR)` | kVAR |
| `Total Gas Power (therms/hour)` | therms/hour |

**Verbosity 3 (Envelope)**
| Key | Unit |
|-----|------|
| `Temperature - Indoor (C)` | °C |
| `Unmet HVAC Load (C)` | °C |

**Verbosity 5 (Envelope)**
| Key | Unit |
|-----|------|
| `Temperature - <zone> (C)` | °C (all zones + exterior) |
| `Net Sensible Heat Gain - <zone> (W)` | W |
| `Infiltration Heat Gain - Indoor (W)` | W |
| `Forced Ventilation Heat Gain - Indoor (W)` | W |
| `Natural Ventilation Heat Gain - Indoor (W)` | W |
| `Internal Heat Gain - Indoor (W)` | W |
| `Window Transmitted Solar Gain (W)` | W |

**Verbosity 2 (Dwelling, per end-use)**
| Key pattern | Unit |
|-------------|------|
| `{end_use} Electric Power (kW)` | kW |
| `{end_use} Gas Power (therms/hour)` | therms/hour |

**Equipment-level (verbosity 3, per-equipment)**
| Key pattern | Unit |
|-------------|------|
| `{name} Electric Power (kW)` | kW |
| `{name} Gas Power (therms/hour)` | therms/hour |
| `{name} Mode` | string |
| `HVAC Heating Delivered (W)`, `HVAC Cooling Delivered (W)` | W |
| `HVAC Heating Setpoint (C)`, `HVAC Cooling Setpoint (C)` | °C |
| `HVAC Heating COP (-)`, `HVAC Cooling COP (-)` | — |
| `Water Heating Delivered (W)` | W |
| `Water Heating COP (-)` | — |
| `EV SOC (-)` | 0-1 |
| `EV Unmet Load (kWh)` | kWh |
| `EV Parked` | bool |
| `Battery SOC (-)` | 0-1 |
| `Battery Energy to Discharge (kWh)` | kWh |
| `PV Electric Power (kW)` | kW |

## Gap Analysis

### SEV-1 — Missing `gas_power` in step() dict

HARES `step()` emits no gas power key at all. OCHRE always returns `Total Gas Power (therms/hour)` at verbosity 0. Callers that drive gas-heated dwellings and read the step dict for real-time energy accounting silently get nothing for gas consumption.

**Evidence:** `StepResult` struct (`crates/hares-core/src/dwelling/mod.rs:235-243`) has no gas field. The `py_dwelling.rs` step() block (`lines 565-577`) sets no gas key.

**Fix required:** Add `gas_power_w: f64` (SI; watts, thermal) to `StepResult` and expose it as `"gas_power_w"` in the step dict. The column `"Total Gas Power (therms/hour)"` from OCHRE must be unit-converted; HARES stores SI internally (feedback_si_units.md).

---

### SEV-2 — Zone temperature keys absent from TypedDict stub

`_hares.pyi:13-24` declares `StepResult` with only four typed fields. The dynamically generated `"Temperature - Indoor (C)"` and `"Temperature - Zone_N (C)"` keys are present at runtime but absent from the stub, making static type checkers report `TypedDict` key errors for any caller that accesses zone temperatures. This is a broken contract for downstream Python consumers.

**Evidence:** `_hares.pyi:13-24`; zone key generation in `py_dwelling.rs:550-575`.

**Fix required:** Either (a) add `"Temperature - Indoor (C)": float` as a required key and make the TypedDict an open-ended `total=False` variant with a `__extra_items__: float` annotation (Python 3.13+), or (b) introduce a `zone_temperatures: dict[str, float]` sub-key in the step dict and update the stub accordingly. Option (b) is cleaner and avoids dynamic key naming in the type system.

---

### SEV-2 — `reactive_power_kvar` conditionally present in `SteppableFleet.step()` but typed as required

`_hares.pyi:26-27` declares `SteppableStepResult` with `reactive_power_kvar: float` as a required field. In `py_fleet.rs:424-426` it is only set when `fleet.telemetry(idx)` returns `Some`. This means the value can be absent at runtime while the stub claims it is always present. Any `mypy`/`pyright` user reading `result["reactive_power_kvar"]` will assume no `KeyError` is possible.

**Evidence:** `py_fleet.rs:424-426`; `_hares.pyi:26-27`.

**Fix required:** Change `reactive_power_kvar` to `NotRequired[float]` in `SteppableStepResult`, matching the conditional emission in the Rust code.

---

### SEV-3 — `"Review Notes"` pre-existing incorrect claim (kW vs W inconsistency)

The prior review note in this ticket stated: *"SteppableFleet.step() returns `net_electric_power_w` (watts) while PyDwelling.step() returns `net_electric_power_kw` (kilowatts)"*. This is **incorrect** — both APIs emit `net_electric_power_kw` in kW (`py_fleet.rs:421`; `py_dwelling.rs:567`). No unit inconsistency exists between these two methods. The pre-existing review note should not be acted on.

---

### SEV-3 — `Unmet HVAC Load (C)` not surfaced in step dict

OCHRE exposes `Unmet HVAC Load (C)` at verbosity 3. HARES does not surface any unmet-load metric in `step()`. While `hvac_heating_w`/`hvac_cooling_w` are present, there is no direct way for a caller to know whether the setpoint was reached. This is a parity gap but lower priority than the gas-power omission since it can be inferred.

---

### SEV-3 — Naming convention divergence for HVAC power

OCHRE uses `"HVAC Heating Delivered (W)"` and `"HVAC Cooling Delivered (W)"` in per-equipment results, while HARES uses `"hvac_heating_w"` / `"hvac_cooling_w"` (snake_case, no unit suffix in name). This is a deliberate HARES design choice (snake_case dict keys), but the parity test at `tests/python/test_ochre_parity.py:137-150` must maintain an explicit mapping. This is documented behaviour, not a defect, but the parity mapping table should cover these keys explicitly.

## Recommended Tests

1. `test_step_result_has_gas_power_w` — step a dwelling with a gas-heated configuration (use any existing `cz2a_gas_furnace_ac_res_wh` fixture), assert `"gas_power_w"` key is present and `> 0` during a heating period.

2. `test_step_result_zone_temp_key_present` — step any single-zone dwelling, assert `"Temperature - Indoor (C)"` is present and a `float` in `[10.0, 35.0]`.

3. `test_step_result_stub_matches_runtime_keys` — iterate the declared `StepResult` TypedDict fields; assert every field name is present in an actual `step()` return dict. This would have caught the zone-temperature omission.

4. `test_steppable_fleet_reactive_power_optional` — build a fleet where telemetry is unavailable for at least one member and assert that `result.get("reactive_power_kvar")` is `None` rather than raising `KeyError`. Ensures the `NotRequired` fix is covered.

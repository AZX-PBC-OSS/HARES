## Background/Context

`resolve_der.rs:resolve_generators()` wires `rated_power_kw` and a derived `eta_electric`. CHP heat output, fuel type mapping for non-gas generators, and ramp-rate parameters are not verified. EA-002 covers behavioral comparison but not config wiring.

## Investigation Instructions

1. **Read `resolve_der.rs:resolve_generators()`** — list every field extracted.
2. **Compare with OCHRE `parse_generator`** — build field comparison table.
3. **Check CHP thermal output config:** Is CHP heat output wired from HPXML?
4. **Check ramp rate units:** HARES uses kW/s (`DEFAULT_DELTA_KW_PER_S = 1.0`), OCHRE uses kW/min. Verify conversion path from config.
5. **Check fuel type:** Does non-gas generator fuel type reach the equipment correctly?

## Findings

### Field Comparison Table

Note: OCHRE has no `parse_generator` function in `ochre/utils/hpxml.py` — generators are not parsed from HPXML in OCHRE at all. The OCHRE `GasGenerator` is instantiated entirely from `default_parameters.csv` (`vendors/OCHRE/ochre/defaults/Gas Generator/default_parameters.csv`). HARES introduces HPXML generator parsing as a new capability with no OCHRE equivalent to compare against.

| `eta_electric` / `efficiency` | 0.95 (from CSV — suspiciously high; this CSV is shared with Battery) | Derived: `AnnualOutputkWh / (AnnualConsumptionkBtu * 0.293)` | 0.30 | Wired |

### F-001 — SEVERITY: HIGH — Fuel type parsed but silently dropped for non-gas generators

**File:** `crates/hares-io/src/hpxml/resolve_der.rs:143`, `crates/hares-equipment/src/generator.rs:378,666`

`resolve_generators()` calls `parse_fuel()` and passes `fuel` to `build_spec()`, which injects `"fuel_type"` as a string into the `parameters` map (line 87–88 of `equipment.rs`). However `Generator::new()` never reads this key. The `descriptor.fuel` field is hardcoded to `FuelType::Gas` at line 378 of `generator.rs`, and the `PortContribution::Fuel` at line 666 also hardcodes `FuelType::Gas`. A propane or fuel-oil generator parsed from HPXML will always report gas fuel consumption, causing incorrect energy accounting and tariff calculations.

### F-002 — SEVERITY: HIGH — CHP thermal output has no HPXML extraction path

**File:** `crates/hares-io/src/hpxml/resolve_der.rs:133–168`

`resolve_generators()` extracts zero CHP-related fields. The `eta_thermal`, `loop_id`, `flow_rate_kg_s`, `supply_temp_c`, and `return_temp_c` config keys exist in `generator.rs` and are fully functional, but there is no corresponding HPXML extraction. Any HPXML file describing a CHP generator will instantiate with `eta_thermal = 0.0`, silently disabling all thermal recovery. There is no warning or error emitted.

### F-003 — SEVERITY: MEDIUM — OCHRE default_parameters.csv for Gas Generator appears to share Battery values

**File:** `vendors/OCHRE/ochre/defaults/Gas Generator/default_parameters.csv`

The OCHRE defaults CSV shows `efficiency = 0.95` and `capacity = 6 kW`. An efficiency of 0.95 is appropriate for a battery round-trip but is not a realistic gas generator electrical efficiency (typical residential gas generators are 25–35%). This appears to be a copy-paste from the Battery defaults. HARES uses its own default of 0.30, which is correct. This is an OCHRE defect, not a HARES defect, but it affects parity testing: if comparing against OCHRE's default-configured generator, the efficiency baseline differs significantly (0.95 vs 0.30). Any parity test must inject an explicit `eta_electric` to compare apples-to-apples.

### F-004 — SEVERITY: MEDIUM — FuelCell type is not reachable from HPXML

**File:** `crates/hares-io/src/hpxml/resolve_der.rs:162–167`

`resolve_generators()` always calls `build_spec("Gas Generator".to_string(), ...)`. There is no mechanism to resolve a fuel cell from HPXML — the type name is hardcoded. A fuel cell is meaningfully different (quadratic efficiency curve by default) and is a valid ResStock equipment type. The function has no branch for distinguishing generator sub-type from any HPXML element.

### F-005 — SEVERITY: LOW — Ramp rate has no HPXML source; unit divergence from OCHRE is intentional but undocumented at the config boundary

**File:** `crates/hares-io/src/hpxml/resolve_der.rs:133–168`, `crates/hares-equipment/src/generator.rs:66–70`

HPXML has no standard field for generator ramp rate, so neither HARES nor OCHRE can parse it. HARES uses kW/s (`delta_kw_per_s`) while OCHRE uses kW/min (`ramp_rate`). The generator.rs module-level comment documents this divergence, but the config key name `delta_kw_per_s` is not mentioned in any user-facing documentation or in the HPXML layer. A user providing `delta_kw_per_s` via an HPXML override would need to know this unit independently. Low risk since ramp rate is override-only.

### F-006 — SEVERITY: LOW — No validation when both annual energy fields are absent

**File:** `crates/hares-io/src/hpxml/resolve_der.rs:152–160`

When `AnnualOutputkWh` or `AnnualConsumptionkBtu` is absent (as in most HPXML files where generators are specified by rated power only), `eta_electric` is silently omitted and the equipment falls back to `DEFAULT_ETA_ELECTRIC = 0.30`. This is correct behavior, but there is no diagnostic when only one of the two fields is present (i.e., `AnnualOutputkWh` present but `AnnualConsumptionkBtu` absent). The partial-presence case is silently ignored, which could mask a malformed HPXML file.

### F-007 — SEVERITY: INFO — OCHRE has no `parse_generator` in hpxml.py

The ticket references `vendors/OCHRE/ochre/utils/hpxml.py (parse_generator)` but no such function exists in that file. OCHRE does not parse generators from HPXML. The HARES HPXML generator path is greenfield. All comparison conclusions above are drawn from OCHRE's `default_parameters.csv` and `Generator.py` directly.

## Recommended Tests

1. **Test: non-gas fuel type is preserved through to the fuel port** — construct a generator spec from HPXML XML with `<FuelType>propane</FuelType>`, resolve it, and assert the resulting `PortContribution::Fuel` carries `FuelType::Propane`. Currently this test would fail (F-001).

2. **Test: CHP fields absent from HPXML result in eta_thermal=0.0 with no panic** — confirm the default CHP-off path is exercised cleanly when no CHP fields are present in HPXML.

3. **Test: partial annual energy fields (only one of two present) are handled without panic** — supply an XML node with `AnnualOutputkWh` but no `AnnualConsumptionkBtu` and assert `eta_electric` is absent from the resulting params map.

4. **Test: FuelCell cannot be produced from HPXML resolve_generators** — document and assert that `"Gas Fuel Cell"` never appears in the output of `resolve_generators()`. This is a coverage gap, not necessarily a bug, but should be an explicit known limitation test.

5. **Test: eta_electric derived from annual energy figures is arithmetically correct** — supply `AnnualOutputkWh = 5256.0` and `AnnualConsumptionkBtu = 63150.0` (≈ 18500 kWh consumption → expected eta ≈ 0.284) and assert the computed `eta_electric` matches to within 1e-4.

6. **Test: rated_power_kw is passed through from ElectricalPowerOutput** — supply `<ElectricalPowerOutput>7.5</ElectricalPowerOutput>` and assert `rated_power_kw = 7.5` in the resulting spec.

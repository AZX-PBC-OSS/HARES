## Background/Context

Type stubs (`.pyi` files) are the primary way Python users discover the API.
Incomplete or inaccurate stubs mean wrong usage, missing IDE autocomplete, and
false confidence from type checkers. PY-015 was supposed to audit these but
may not be complete.

## Investigation Instructions

1. **Cross-reference every `#[pyclass]` and `#[pymethods]` in `crates/hares-python/src/`
   against `_hares.pyi`:**
   - Is every class present in the stub?
   - Is every method present with correct signature?
   - Are return types correct? (Not `Any` when they could be specific)
   - Are optional parameters marked with `= None` or `= ...`?

2. **Check `__init__.py` re-exports:**
   - Does `python/ochre_next/__init__.py` re-export everything users need?
   - Are there classes in `_hares` that aren't re-exported?

3. **Check for missing type information:**
   - Are enum variants documented?
   - Are property getters/setters typed?
   - Are classmethods marked as `@classmethod`?

4. **Run `pyright` or `mypy` check** if possible — does the stub pass type checking?

## Findings

### Methodology

Every class registered in the `#[pymodule]` block in `lib.rs` was traced against
the stub. All `#[pymethods]` blocks were read for exported methods, including
factory statics, property getters, and setters. No classes registered in `lib.rs`
are wholly absent from the stub file.

---

### F1 — CRITICAL: `StormWatchTrigger` stub is structurally wrong

**Location:** `python/ochre_next/_hares.pyi:484–489`

The stub treats `StormWatchTrigger` as an enum with class-level constants:

```python
class StormWatchTrigger:
    ManualEnable: StormWatchTrigger
    WeatherSignal: StormWatchTrigger
```

`StormWatchTrigger` is a `struct`, not an enum (`py_enums.rs:2084`). It is
constructed via two static factory methods and exposes two property getters.
The enum-constant names `ManualEnable` / `WeatherSignal` are internal Rust
variant names — they do not exist as Python attributes. At runtime, any
`StormWatchTrigger.ManualEnable` call raises `AttributeError`.

Rust implementation (`py_enums.rs:2102–2130`):
- `StormWatchTrigger.manual_enable() -> StormWatchTrigger`
- `StormWatchTrigger.weather_signal(wind_speed_threshold_m_s: float = 25.0) -> StormWatchTrigger`
- `@property is_manual: bool`
- `@property wind_speed_threshold_m_s: float`

Required stub:
```python
class StormWatchTrigger:
    @property
    def is_manual(self) -> bool: ...
    @property
    def wind_speed_threshold_m_s(self) -> float: ...
    @staticmethod
    def manual_enable() -> StormWatchTrigger: ...
    @staticmethod
    def weather_signal(wind_speed_threshold_m_s: float = ...) -> StormWatchTrigger: ...
    def __repr__(self) -> str: ...
    def __eq__(self, other: object) -> bool: ...
    def __hash__(self) -> int: ...
```

### F2 — CRITICAL: `Signal` class missing three EV control factory methods

**Location:** `python/ochre_next/_hares.pyi:667–705`

The `PySignal` enum (`py_actor.rs:199–250`) has three EV-specific variants.
The corresponding `#[pymethods]` static constructors exist (`py_actor.rs:660–676`)
but are absent from the stub:

- `Signal.ev_plug_in(state: EvConnectionState) -> Signal`
- `Signal.ev_drive(kwh: float) -> Signal`
- `Signal.ev_set_ready_by(departure_hour: float, target_soc: float) -> Signal`

These are the only way a Python actor can emit EV dispatch signals. Their absence
makes EV actor authoring invisible to type checkers and IDE autocompletion.

### F3 — HIGH: `SimulationConfig` stub missing setters for eight properties

**Location:** `python/ochre_next/_hares.pyi:1360–1375`

The stub exposes `start_time`, `duration_s`, and `time_res_s` as settable.
The Rust implementation (`py_config.rs:212–297`) also has `#[setter]` for:

| Property | Has setter in Rust |
|---|---|
| `output_verbosity` | yes — missing from stub |
| `output_path` | yes — missing from stub |
| `output_to_parquet` | yes — missing from stub |
| `write_output` | yes — missing from stub |
| `output_chunk_size` | yes — missing from stub |
| `setpoint_deadband_c` | yes — missing from stub |
| `master_seed` | yes — missing from stub |
| `civil_timezone` | yes — missing from stub |

Type checkers will reject `config.write_output = False` as an assignment to a
read-only property, even though it works at runtime.

---

### F4 — MEDIUM: `EV.from_vehicle_with_archetype` marks `seed` as required

**Location:** `python/ochre_next/_hares.pyi:1110–1114`

The Rust signature is `#[pyo3(signature = (vehicle_id, archetype_id, seed=0))]`
(`py_equipment.rs:582`), giving `seed` a default of 0. The stub marks `seed: int`
as a required positional argument. The corresponding `Dwelling.add_ev_with_driver`
at `py_dwelling.rs:847` takes `seed: u64` with no default and the stub correctly
reflects that — but `EV.from_vehicle_with_archetype` is different and should be:

```python
@staticmethod
def from_vehicle_with_archetype(
    vehicle_id: VehicleId,
    archetype_id: EvArchetypeId,
    seed: int = 0,
) -> EV: ...
```

---

### F5 — HIGH: `DRLevel.from_str` stub method does not exist at runtime

**Location:** `python/ochre_next/_hares.pyi:158`

The stub declares:

```python
class DRLevel:
    @staticmethod
    def from_str(name: str) -> DRLevel: ...
```

`PyDRLevel` in `py_actor.rs` has five `#[staticmethod]` constructors (`normal`, `moderate`,
`high`, `critical`, `grid_emergency`) and a `__repr__`, but no `from_str` method at all.
Any code calling `DRLevel.from_str(...)` at runtime receives `AttributeError`. The stub
falsely advertises this as a safe call.

---

### F6 — LOW: `power_setpoint` parameter name inconsistency (noted in Review Notes)

**Location:** `py_control.rs:24` vs stub `_hares.pyi:568`

`ControlSignal.power_setpoint` takes `kw: f64` as its first parameter (Rust name).
The same conceptual field in `ControlSignal.from_dict` uses the key `active_power_kw`.
The stub correctly reflects the Rust parameter name `kw` for the static constructor.
This is not a stub defect but it is a naming inconsistency in the API itself that
will surprise callers comparing the two construction paths.

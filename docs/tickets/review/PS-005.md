## Background/Context

Users construct `Battery(capacity_kwh=13.5, ...)`, `PV(capacity_kw=6.0, ...)`,
`EV(capacity_kwh=75, ...)` from Python. These constructors must validate inputs:
negative capacity, SOC > 1.0, efficiency > 1.0, etc. Invalid values should fail
loudly at construction, not silently produce wrong simulation results.

## Findings

### F1 — MEDIUM: `PyBattery.__new__` accepts all invalid physical values at construction time

`crates/hares-python/src/py_equipment.rs` lines 186–261 (`PyBattery::new`) stores every
parameter directly into `Self` with zero validation. The following inputs are accepted
without error and silently forwarded to `battery::mod.rs` at `add_battery()` time, which
is after the object is fully constructed and returned to Python:

- `capacity_kwh <= 0`, `NaN`, `Inf`
- `min_soc > 1.0`, `max_soc > 1.0`, or `min_soc >= max_soc`
- `charge_efficiency > 1.0`, `discharge_efficiency > 1.0`, `inverter_efficiency > 1.0`
- `initial_soc < 0` or `> 1`

The Rust `Battery` equipment does validate some of these (`capacity_kwh > 0`,
`min_soc < max_soc`) in `battery::mod.rs` around line 781, but only when `add_battery()`
is called on a `Dwelling`. Python users can construct a `Battery` object with
`Battery(name="x", capacity_kwh=-1)`, pass it around, store it, and will only
receive an error when it is attached to a dwelling — not at construction time.

Fix: Add explicit range checks in `PyBattery::new` raising `PyValueError` for:
- `capacity_kwh`: must be finite and > 0
- `min_soc`, `max_soc`, `initial_soc`: must be finite and in [0.0, 1.0]
- `min_soc < max_soc` when both are provided
- `charge_efficiency`, `discharge_efficiency`, `inverter_efficiency`: must be finite and in (0.0, 1.0]
- `max_charge_kw`, `max_discharge_kw`: must be finite and >= 0 when provided

### F2 — MEDIUM: `PyEv.__new__` performs no validation on `initial_soc` or `capacity_kwh`

`py_equipment.rs` lines 552–573 (`PyEv::new`). The LUT extraction path raises a
`PyValueError` on malformed LUT data, but numeric scalar parameters are not validated:

- `initial_soc = 1.5` or `initial_soc = -0.1` is accepted silently
- `capacity_kwh = 0.0` or `capacity_kwh = -1.0` is accepted silently
- `max_charging_kw = -5.0` is accepted silently

The downstream EV equipment (`ev/mod.rs` line 247+) validates `charging_efficiency`,
`soc_max`, and temperature thresholds at `init()` time, but `initial_soc` is only
clamped (line 198: `.clamp(0.0, 1.0)`) rather than rejected. `capacity_kwh = 0` or
negative will cause division-by-zero in the energy accounting at line 485.

Fix: Validate `initial_soc` in `[0.0, 1.0]`, `capacity_kwh > 0` (when provided),
and `max_charging_kw >= 0` (when provided) in `PyEv::new`.

### F3 — LOW: `PyPv.__new__` delegates all range checks to downstream equipment init

`py_equipment.rs` lines 506–521 (`PyPv::new`). No validation is performed on:
- `capacity_kw`: negative or zero accepted silently at construction
- `tilt`: the range `[0, 180]` is enforced by `pv/array_config.rs:157` but only at
  `add_pv()` time
- `azimuth`: only a finiteness check is performed downstream (`array_config.rs:162`),
  so `azimuth = 400.0` is accepted (normalized by `normalize_azimuth`) — this is
  arguably acceptable behaviour but should be documented

The downstream `pv/array_config.rs:147–169` does correctly enforce `capacity_kw > 0`,
`tilt in [0,180]`, and `azimuth.is_finite()`, so the exposure window is narrower than
for Battery/EV. Still, failing at `PV(capacity_kw=-1)` construction is better UX than
failing at `dwelling.add_pv(pv)` with an opaque equipment error.

Fix: Validate `capacity_kw > 0`, `tilt in [0.0, 180.0]` in `PyPv::new`.

### F4 — LOW: `PyPvSoilingConfig.__new__` performs no range validation

`py_equipment.rs` lines 440–461. The following unvalidated fields can produce silently
wrong physics:

- `max_loss`: a value > 1.0 would allow more than 100% soiling loss
- `initial_loss`: negative value accepted
- `loss_rate_per_day`, `cleaning_threshold_mm`, `grace_period_days`, `rain_accum_hours`:
  negative values accepted

Fix: Validate `max_loss in [0.0, 1.0]`, `initial_loss in [0.0, max_loss]`,
and all time/rate scalars `>= 0` in `PyPvSoilingConfig::new`, raising `PyValueError`.

### F5 — LOW: `PyPv.soiling` field is silently dropped in `add_pv`

`py_dwelling.rs` lines 732–792 (`add_pv`) never reads `pv.soiling`. The
`PyPvSoilingConfig` struct is accepted by the Python constructor and stored on `PyPv`,
but it is never forwarded into `raw_config` when building the `EquipmentConfig`.
Users who pass a `soiling=` argument to `PV(...)` will receive no error and no soiling
model will be active.

Fix: In `add_pv`, when `pv.soiling` is `Some(...)`, insert the corresponding soiling
config keys (`soiling_enabled`, `soiling_cleaning_threshold_mm`, `soiling_loss_rate_per_day`,
`soiling_grace_period_days`, `soiling_max_loss`, `soiling_initial_loss`,
`soiling_rain_accum_hours`) into `raw_config`. Alternatively, remove `PyPvSoilingConfig`
and the `soiling` field from `PyPv` until soiling config forwarding is implemented, so
users are not misled.

### F6 — LOW: `from_vehicle_with_archetype` `seed` parameter is silently ignored

`py_equipment.rs` line 586: `#[allow(unused_variables)] seed: u64`. The `seed`
parameter is part of the public API signature but is never used. Stochastic
archetype selection is not implemented; the function always returns the same result
regardless of `seed`. This is not documented in the signature or `__repr__`.

The `allow(unused_variables)` suppressor means no compiler warning surfaces this gap.

Fix: Either implement seeded selection, or remove the `seed` parameter from the
signature and the `#[pyo3(signature)]`, or at minimum add a deprecation note in
the function body that raises a Python `UserWarning` if `seed != 0`.

### F7 — INFO: `is_polars_dataframe` uses duck-typing class name check

`py_equipment.rs` lines 866–875. The dataframe detection uses `__class__.__name__ == "DataFrame"` which will return `True` for any class named `DataFrame` (e.g. a pandas DataFrame, a custom class). Pandas DataFrames do not have `get_column`, so this will produce a confusing `AttributeError` rather than the helpful error message at line 842.

Fix: Check `obj.hasattr("get_column")` in addition to or instead of the class name
check, or check the module name (`__class__.__module__.startswith("polars")`).

## Summary by Constructor

| Constructor | Validated at construction | Validated at add_*() | Gap |
|---|---|---|---|
| `Battery.__new__` | None | `capacity_kwh > 0`, `min_soc < max_soc` | Efficiency, SOC, power params unvalidated at boundary |
| `PV.__new__` | None | `capacity_kw > 0`, `tilt [0,180]` | Acceptable but UX is poor; `soiling` silently dropped (F5) |
| `EV.__new__` | LUT parsing only | `charging_efficiency`, temp thresholds | `initial_soc`, `capacity_kwh`, `max_charging_kw` unvalidated |
| `PvSoilingConfig.__new__` | None | N/A (never forwarded) | All fields unvalidated and config is dropped (F5) |

## Background/Context

Variable-speed and two-speed HVAC use runtime interpolation between discrete stages.
DC-001/002 covered duty cycle and mode priority. CW-009/010 covered config wiring.
This ticket audits the actual speed selection algorithm at runtime.

## Investigation Instructions

1. Read `staging.rs` — how does `SpeedSelection` work? Linear interpolation between stages?
2. How is the operating speed chosen from the load signal?
3. Compare with OCHRE's `speed_idx` approach
4. Check TwoSpeedTime vs MultiSpeedInterpolated logic

## Architecture Contrast: OCHRE vs HARES

OCHRE uses a single fractional `speed_idx` float that encodes both discrete stage
identity and fractional interpolation in one value (e.g. `2.4` = 40% of the way between
stage 2 and 3). HARES separates these into an integer `speed_index` and a fractional
`speed_frac`. The interpolation arithmetic is equivalent for the common case but several
behavioural divergences exist (see Findings below).

## Findings

### [CRITICAL] F-001 — `capacity_fractions` picks the longer Vec without regard to active mode

**File:** `crates/hares-equipment/src/hvac/staging.rs:339`

```rust
let caps = if self.heating_capacities_w.len() >= self.cooling_capacities_w.len() {
    &self.heating_capacities_w
} else {
    &self.cooling_capacities_w
};
```

`capacity_fractions` is called from `select_multi_speed`, which is invoked with a
`load_fraction` that has no intrinsic association with either mode. The method silently
picks whichever Vec is longer. On a heat pump with unequal heating/cooling stage counts
this produces incorrect normalization fractions when the shorter Vec is the active one.
OCHRE avoids this by building the capacities list inline from `calculate_biquadratic_param`
for the active mode, so the correct mode-specific capacities are always used.

**Fix:** Pass `ThermostatMode` (or the capacities slice directly) into
`select_multi_speed` so the caller controls which capacity vector is used for
normalization. `capacity_fractions` should become a free function taking `&[f64]`
rather than an `&self` method that guesses.

### [HIGH] F-002 — Multi-speed biquadratic correction uses only stage 0 for all intermediate speeds

**File:** `crates/hares-equipment/src/hvac/air_conditioner.rs:811–816`

```rust
let (_, cap_ratio) = self.hvac.evaluate_biquadratic_with_flow(
    0,  // always stage 0
    coil_entering_wb_c,
    outdoor_c,
    self.flow_fraction_correction,
);
```

OCHRE evaluates `calculate_biquadratic_param` for each speed index independently in
`update_capacity`/`update_eir`. HARES evaluates the biquadratic at stage 0 only and
applies that single correction factor to the interpolated capacity and EIR. When
biquadratic coefficients differ across stages (the normal case for multi-speed
equipment), this underestimates or overestimates the corrected capacity and EIR at
intermediate stages.

**Fix:** Evaluate biquadratic at both `speed_index` and `speed_index + 1`, then
linear-blend the correction ratios by `speed_frac`, matching OCHRE's
`update_capacity`/`update_eir` pattern.

---

### [HIGH] F-003 — Sub-lowest-speed PLR does not pass through the per-speed `eir_plr` biquadratic

**File:** `crates/hares-equipment/src/hvac/staging.rs:204–210`

When `load_fraction <= cap_fracs[0]`, HARES produces `speed_frac = 0.0` and
`part_load_ratio = load_fraction / cap_fracs[0]`, then routes to `part_load_factor_for_stage`
which uses the scalar Cd formula or `eir_plr` quadratic. OCHRE uses `speed_idx = capacity /
capacities[1]` (a value between 0 and 1) and in `update_eir` branches on `speed_idx < 1` to
call `calculate_biquadratic_param(param="eir", speed_idx=1, part_load_ratio=speed_idx)` —
passing the sub-lowest PLR *into* the biquadratic EIR evaluation rather than into a
separate quadratic. The two approaches produce identical results only when the `eir_plr`
coefficients happen to match the `1 - Cd*(1-PLR)` formula.

**Fix:** When `speed_index == 0` and `speed_frac == 0.0` and the equipment has
`eir_plr_coefficients`, evaluate PLF using the stage-0 per-speed biquadratic PLR curve
with the sub-lowest PLR passed as the part-load-ratio argument, matching OCHRE's branch.

### [HIGH] F-004 — `TwoSpeedAlternating` hardcodes `speed_frac = 1.0` and skips PLR normalisation

**File:** `crates/hares-equipment/src/hvac/staging.rs:91–101`

```rust
SpeedSelection {
    speed_index: desired_index,
    part_load_ratio: load_fraction,
    speed_frac: 1.0,            // always full speed regardless of actual load
}
```

`speed_frac` is hardcoded to `1.0` regardless of load. The raw `load_fraction` is used
as `part_load_ratio` without normalisation to the stage capacity (unlike
`TwoSpeedSetpoint` which divides by `low_cap`). This means duty cycle equals raw load
fraction at all times, which is incorrect for sub-stage loads. No HARES test covers
this mode.

**Fix:** Mirror `TwoSpeedSetpoint`'s PLR normalisation for each stage in
`TwoSpeedAlternating`, or document and enforce that this mode is only valid when the
caller guarantees `load_fraction` is already a per-stage PLR. Add a regression test.

### [HIGH] F-005 — `VariableSpeedIdeal` sets duty cycle to binary 0/1, ignoring sub-unity load

**File:** `crates/hares-equipment/src/hvac/air_conditioner.rs:559–568`

```rust
SpeedControlMode::VariableSpeedIdeal => {
    if selection.speed_frac > 0.0 { 1.0 } else { 0.0 }
}
```

`select_speed` for `VariableSpeedIdeal` stores `load_fraction` in `speed_frac`
(staging.rs:103–107). The duty-cycle logic above maps any non-zero load to `duty_cycle
= 1.0` rather than the actual fraction. OCHRE stores `speed_idx = capacity /
capacity_max`, a real-valued fraction, and uses it directly as the part-load ratio.
Variable-speed capacity partial delivery at fine timesteps is therefore broken in HARES.

**Fix:** Set `duty_cycle = selection.speed_frac` (i.e. `load_fraction`) for
`VariableSpeedIdeal` instead of the binary 0/1 mapping.

### [MEDIUM] F-006 — `max_enabled_speed` initialises to `0` regardless of stage count

**File:** `crates/hares-equipment/src/hvac/hvac_core.rs:289`

```rust
max_enabled_speed: 0,
```

OCHRE initialises `_max_enabled_speed = self.n_speeds` (HVAC.py:757), pointing to the
highest stage until DR overrides it. HARES initialises to `0`, so any code path that
reads `max_enabled_speed` before `set_disabled_speeds` is called sees an incorrect
value. The `apply_disabled_speeds_two_speed` fallback path only routes to
`max_enabled_speed` when the desired speed is in the disabled list, but at init time
the disabled list is empty so the bug is silent until the first DR control signal
arrives with a disabled speed.

**Fix:** Initialise `max_enabled_speed` to `n_speed_stages().saturating_sub(1)`, or
call `set_disabled_speeds(&[])` at the end of `HvacEquipment::init()`.

---

### [LOW] F-007 — PLF floor clamp uses a hardcoded global `0.7` rather than per-stage `min_plf`

**File:** `crates/hares-equipment/src/hvac/staging.rs:291`

```rust
let plf = plf_raw.clamp(0.7_f64.max(plr), 1.0);
```

OCHRE loads a per-stage `min_plf` value from the biquadratic CSV (default 0.7, HVAC.py:833).
When `eir_plr_coefficients` are present, HARES should use the corresponding per-stage minimum
rather than a hardcoded global. For equipment where low-speed stages have a lower minimum PLF
than 0.7, this over-penalises efficiency at light loads.

**Fix:** If `eir_plr_coefficients` are loaded, also load per-stage `min_plf` values and use
them in `part_load_factor_for_stage` instead of the global 0.7 constant.

## Recommended Tests

- `TwoSpeedAlternating` with sub-unity load: verify PLR is stage-normalised.
- `MultiSpeedInterpolated` with non-flat biquadratic curves: verify corrected capacity
  and EIR differ between stages at an intermediate `speed_frac`.
- `VariableSpeedIdeal` at load_fraction=0.5 on a fine timestep: verify `duty_cycle` is
  0.5, not 1.0.
- Heat pump multi-speed where heating has 2 stages and cooling has 4: verify
  `select_multi_speed` uses the correct vector for each mode (regression for F-001).
- `max_enabled_speed` is correct before any DR control signal arrives (regression for F-006).

## Background/Context

Rust has `Dwelling::envelope_diagnostics()` and `envelope_diagnostics_json()` but
these are not exposed to Python. Users who need to debug envelope behavior (check
per-boundary UA, RC parameters) cannot access this data from Python.

## Investigation Instructions

1. Read `dwelling/mod.rs` — what do these methods return?
2. Read `py_dwelling.rs` — confirm not exposed.
3. Assess: is this needed for users? For debugging? For validation scripts?
4. Recommend: expose as JSON dict? As a typed pyclass?


## Findings

### Gap confirmed

Neither `envelope_diagnostics()` nor `envelope_diagnostics_json()` is wrapped in
`crates/hares-python/src/py_dwelling.rs`. Zero references to either method or to
`EnvelopeDiagnostics` appear in that file or in `python/ochre_next/_hares.pyi`.

### Feature-gate analysis

Both Rust methods are gated on `#[cfg(any(debug_assertions, feature = "observe_detailed"))]`
(`crates/hares-core/src/dwelling/mod.rs:1313-1322`). `EnvelopeDiagnostics` itself only derives
`serde::Serialize` under the same gate (`crates/hares-envelope/src/boundary_rc.rs:175-178`), so
`envelope_diagnostics_json()` (which calls `serde_json::to_string_pretty`) is only available
when serialisation is compiled in.

`crates/hares-python/Cargo.toml` declares only:
```toml
[features]
observe = ["hares-core/observe"]
```
There is no `observe_detailed` forwarding feature, so users cannot opt in even if they build from
source.

### Use-case assessment

- **Debugging misconfigured HPXML**: implausible thermal results are very hard to trace without
  being able to inspect per-boundary UA values and zone capacitances.
- **Integration-test validation**: currently the only way to assert RC network construction is
  through Rust unit tests; Python integration tests have no access.
- **Tooling / visualisation**: any Python tooling that wants to understand model structure
  (e.g. draw the RC graph, do model-order reduction) is blocked.

This is a meaningful usability gap for a simulation library whose primary debugging surface is
Python.

### Recommendation

Expose as **JSON string** via a single Python method `envelope_diagnostics_json() -> str`. This
avoids a parallel `PyEnvelopeDiagnostics` pyclass hierarchy — the struct is a construction-time
snapshot used purely for inspection, so letting callers do `json.loads()` is sufficient and
keeps the binding minimal.

Required changes:

1. `crates/hares-python/Cargo.toml`: add
   `observe_detailed = ["hares-core/observe_detailed"]` to `[features]`.
2. `crates/hares-python/src/py_dwelling.rs`: add a `#[cfg(feature = "observe_detailed")]`
   `#[pymethods]` wrapper that calls `dwelling.envelope_diagnostics_json()` and returns
   `PyResult<String>`.
3. `python/ochre_next/_hares.pyi`: add the stub under a comment noting the build requirement.

An always-available variant returning `None` when the feature is absent is also acceptable and
avoids requiring users to rebuild the extension.

## Recommended Tests

After the binding is added, add a test in `tests/python/test_py_dwelling.py`:

```python
def test_envelope_diagnostics_json_returns_valid_structure(dwelling):
    """envelope_diagnostics_json() must return a JSON object with expected keys."""
    import json
    raw = dwelling.envelope_diagnostics_json()
    data = json.loads(raw)
    assert "boundaries" in data
    assert "zone_capacitances_j_k" in data
    assert "total_ua_w_per_k" in data
    assert data["total_ua_w_per_k"] > 0.0
    assert len(data["boundaries"]) > 0
```

The test must be guarded or skipped if built without `observe_detailed`.

## Background/Context

Ventilation fans should run on their operating schedule (e.g., continuously, or per
ASHRAE 62.2 hours), independent of the thermal solver's heating/cooling decisions.
If ventilation only runs when the HVAC runs, outdoor air exchange is underestimated.

## Investigation Instructions

1. Read HARES `ventilation.rs` — what drives on/off decisions?
   - Is it schedule-based? Always-on?
   - Does it respond to HVAC mode (it shouldn't)?
2. Read OCHRE — is the ventilation fan a `ScheduledLoad` subclass?
3. Known limitation: HARES only supports `ScheduleSource::Constant` — document impact.
4. Does HPXML `HoursInOperation` get parsed? (See HPXML-011)

## Findings

### F-1 [CONFIRMED] Ventilation is independent of HVAC — on/off path is schedule-only

`Ventilation::update_control` (`ventilation.rs:269-278`) only ticks a DR countdown timer
and returns `self.mode` unchanged. Mode can only be changed by `apply_control_unchecked`
in response to a `ControlSignal::ModeOverride` or `ControlSignal::LoadFraction` actor
signal. There is no coupling to the HVAC operating mode. The ventilation fan runs
whenever `mode != OperatingMode::Off && dr_level != DRLevel::GridEmergency`.

OCHRE reference: the ventilation fan is registered as a `ScheduledLoad`
(`Equipment/__init__.py:100`) and its flow rate is added to the envelope schedule as a
constant column (`utils/schedule.py:474-475`). The envelope then reads
`"Ventilation Rate (cfm)"` each step (`Envelope.py:1226`). There is no HVAC-mode gate.
Both implementations are correctly independent of HVAC.

### F-2 [HIGH — CORRECTNESS] Potential double-accounting of forced ventilation sensible load

The `Ventilation` equipment computes a sensible zone load
(`q_sensible_w = m_dot * Cp * (T_supply - T_indoor)`) and writes it to the thermal port
as `ThermalCategory::InternalGain` (`ventilation.rs:352-362`). This value is injected
into the state-space input vector `u` by `apply_port_sensible_inputs`
(`thermal_solver/ports.rs:14-22`).

Simultaneously, the envelope `ThermalSolver` calls
`apply_infiltration_and_ventilation` (`thermal_solver/mod.rs:348-354`) which builds an
`InfiltrationCoupling` that carries `h_inf_w_k` — the combined thermal conductance of
infiltration + forced ventilation airflow — and applies it implicitly via the backward
Euler coupled-LU path (`thermal_solver/stepping.rs:77-92`). The forced ventilation
component of `h_inf_w_k` is derived from `config.ventilation_flow_m3_s`
(`infiltration.rs:151-160`), which is populated by `solver_builder.rs:866-868` from the
same HPXML fan spec.

The result is that the ventilation sensible load is counted twice:
- Once explicitly via the `Ventilation` equipment thermal port (an `InternalGain`
  applied as an additive input to `u`).
- Once implicitly via the `InfiltrationCoupling` conductance term in the stepped RC
  model.

This is a correctness defect. The magnitude scales as
`m_dot * Cp * |T_outdoor - T_indoor|`. For a typical residential fan (~0.035 m³/s,
ΔT = 20 K): `0.035 × 1.2 × 1006 × 20 ≈ 845 W` duplicated each step.

**Root cause:** Both the equipment-layer `Ventilation` struct and the envelope solver's
infiltration/ventilation module model the same physical phenomenon without coordination.

**Fix required:** One path must own the ventilation sensible heat exchange. Given that
OCHRE models ventilation purely inside the envelope solver (not as a separate equipment
thermal contribution), the correct fix is one of:
- Remove the `PortContribution::Thermal` output from `Ventilation::step()` and let the
  envelope solver remain the sole source of truth for forced ventilation heat exchange.
  The `Ventilation` equipment would then only report electrical power and diagnostic
  telemetry.
- Alternatively, exclude the ventilation from the envelope solver's forced-ventilation
  path when a `Ventilation` equipment instance is present. This is architecturally
  messier.

The first option aligns with OCHRE's design and avoids cross-layer coupling.

### F-3 [HIGH — CORRECTNESS] `ScheduleSource::Constant` only — `HoursInOperation` ignored

`Ventilation::init` rejects any `schedule_source` other than `"constant"` with an error
(`ventilation.rs:258-262`). The schedule fraction is hardcoded to `1.0`
(`ventilation.rs:255`). `resolve_ventilation` in `hpxml/resolve_loads.rs` (lines 532-595)
does not read `<HoursInOperation>` from the HPXML fan node at all.

OCHRE asserts `HoursInOperation == 24` (`hpxml.py:1622`), meaning it only supports
continuous operation but at least validates the assumption. HARES silently accepts any
`HoursInOperation` value and runs at full flow 24 h/day regardless.

Real-world HPXML files include intermittent schedules. The file
`data/examples/bldg0112631-up00.xml` contains `<HoursInOperation>1.0</HoursInOperation>`
on multiple fans. With HARES, those fans would run 24× longer than specified, inflating
ventilation energy and thermal exchange by up to 24×.

**Fix required (per HPXML-011):** Read `HoursInOperation` in `resolve_ventilation`.
If the value is < 24, either wire a fractional constant schedule
(`"schedule_constant": hours / 24.0`) or emit a structured warning that the value is
being clamped to continuous operation. This is a pre-existing issue tracked in
HPXML-011 but must not remain silent — at minimum a `tracing::warn!` should be emitted
when `HoursInOperation != 24`.

### F-4 [MEDIUM — CORRECTNESS] `ventilation_rate_cfm` key written but `flow_rate_m3_s` key read — ventilation equipment flow is always default

`resolve_ventilation` inserts `"ventilation_rate_cfm"` (`resolve_loads.rs:554`).
`Ventilation::init` reads `KEY_FLOW_RATE_M3_S` = `"flow_rate_m3_s"` (`ventilation.rs:215`
and constant definition at line 33).

These keys do not match. The HPXML flow rate is consumed by `solver_builder.rs:866` (for
the envelope solver) but never reaches the `Ventilation` equipment object. The equipment
always uses `DEFAULT_FLOW_RATE_M3_S = 0.035 m³/s` (~75 CFM) regardless of the HPXML
specification.

This defect is already documented in `docs/tickets/review/CW-018.md` (Finding F-1 /
Finding 3) and `docs/tickets/review/AR-002.md`. It is recorded here for completeness
because it directly affects the magnitude of the double-accounting identified in F-2 —
the envelope solver uses the correct HPXML flow while the equipment uses the wrong
default, so the two paths use different flow rates.

### F-5 [LOW — CONFIRMED SAFE] Ventilation is correctly independent of thermal solver decisions

Confirmed: no code path reads HVAC mode or thermostat state inside `Ventilation`. The
equipment runs or does not run based solely on `OperatingMode` (actor-controlled) and
`DRLevel`. This matches OCHRE's `ScheduledLoad` pattern and ASHRAE 62.2's requirement
for continuous or scheduled operation independent of heating/cooling demand.

### F-6 [LOW] HRV bypass active flag: false negative on ExhaustFan with outdoor temp in range

`bypass_active` detection in `step()` (`ventilation.rs:322-324`) uses
`eff_s == 0.0 && t_outdoor_c >= bypass_temp_min_c && t_outdoor_c <= bypass_temp_max_c`.
For an `ExhaustFan` type, `effective_sensible_effectiveness` always returns `0.0`
regardless of temperature (`ventilation.rs:171-173`). If the outdoor temperature
happens to be in the bypass range, an `ExhaustFan` would incorrectly report
`bypass_active = 1.0` in telemetry. An exhaust fan has no bypass mechanism.

**Fix:** Guard `bypass_active` with
`self.ventilation_type != VentilationType::ExhaustFan`.

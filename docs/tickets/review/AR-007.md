## Background/Context

Every equipment has an `EquipmentDescriptor` with `name`, `end_use`, `fuel_type`,
`equipment_type`, `zone`, and `capabilities`. These drive: per-end-use aggregation
in output, control signal routing (dispatch by EndUse), and fleet-level metrics.
Wrong descriptor means wrong aggregation and wrong control routing.

## Findings

### FINDING 1 — BUG: `IdealHvac` hardcodes `EndUse::HVAC_HEATING` despite being capable of cooling

**File:** `crates/hares-equipment/src/hvac/ideal_hvac.rs:72`

`IdealHvac::new` sets `end_use: EndUse::HVAC_HEATING` unconditionally. At runtime the equipment
operates in both heating and cooling modes (`ThermostatMode::Cooling`, negative `capacity_w`,
`ThermalCategory::HvacCooling` contributions to port). A `DispatchTarget::ByEndUse(EndUse::HVAC_COOLING)`
signal will never reach `IdealHvac`, making it unaddressable as a cooling plant via end-use routing.
Additionally, cooling energy is aggregated under `hvac_heating` in output metrics, producing wrong
per-end-use reporting.

OCHRE uses a single `HVAC Heating` or `HVAC Cooling` class-level annotation based on the equipment
subclass, never a combined class. `IdealHvac` is a combined heating+cooling unit with no OCHRE
equivalent — it requires its own treatment.

**Impact:** High. Any actor or external control that dispatches to `EndUse::HVAC_COOLING` will miss
`IdealHvac`; output metrics bucket all `IdealHvac` thermal output as heating.

**Fix:** Add a separate `EndUse::HVAC_COMBINED` standard constant (or `"hvac_combined"`) and use
it for `IdealHvac`. Alternatively, promote `IdealHvac` to maintain two separate
`EquipmentDescriptor`-equivalent labels per operating mode. The simpler path is a new
`EndUse::HVAC_COMBINED` constant in `hares-types/src/equipment.rs` and set it in `IdealHvac`.
Update `is_standard()` to include it.

### FINDING 2 — BUG: `HpCooler` advertises only 3 capabilities but implementation accepts 6

**File:** `crates/hares-equipment/src/hvac/heat_pump/cooler.rs:61-63`

`HpCooler::build` sets:
```
control_capabilities: ControlCapabilities::THERMAL_SETPOINT
    | ControlCapabilities::THERMAL_SETPOINT_DELTA
    | ControlCapabilities::IDEAL_CAPACITY,
```
However, `HpCooler::apply_control_unchecked` delegates directly to `self.inner.apply_control_unchecked`
which is the full `CoolingCore` implementation — and `CoolingCore::apply_control_unchecked`
handles `DutyCycle`, `LoadFraction`, `PowerLimit`, `ModeOverride`, and `DemandResponse` as well.

The inner `CoolingCore`'s descriptor (used by `AirConditioner` and `RoomAC` directly) correctly
declares all six capabilities (`air_conditioner.rs:315-322`). The outer `HpCooler` wrapper
copies the inner's `telemetry_fields` but not its `control_capabilities`, leaving a gap.

This means `Equipment::apply_control` will gate-reject `DutyCycle`, `LoadFraction`, `PowerLimit`,
`ModeOverride`, and `DemandResponse` signals sent to `HpCooler` via the capability check in
`Equipment::apply_control` (`lib.rs:103`), even though the implementation would handle them
correctly.

**Impact:** High. DR signals dispatched to the cooling side of an ASHP or MSHP via
`ByEndUse(EndUse::HVAC_COOLING)` or `ByName` are silently rejected with an error. The
`dr_compliance` actor and any cooling DR event will fail silently on HP systems.

**Fix:** In `HpCooler::build` (`cooler.rs:61-63`), copy the full capability set from the inner
descriptor rather than hardcoding a reduced set:
```rust
control_capabilities: inner.descriptor().control_capabilities,
```

### FINDING 3 — BUG: `EventBasedLoad` and `WetAppliance` hardcode `EndUse::OTHER` regardless of appliance type

**File:** `crates/hares-equipment/src/event_load.rs:225` and `event_load.rs:657`

`EventBasedLoad` and `WetAppliance` both hardcode `end_use: EndUse::OTHER`. This is used for:
Clothes Washer, Clothes Dryer, Dishwasher, and Cooking Range — appliances that OCHRE and
ResStock aggregate separately in end-use breakdowns.

This blocks `ByEndUse` routing to appliances and collapses all appliance output into the `OTHER`
bucket in metrics.

Additionally, the `EventBasedLoad` fuel bug is already tracked in FX-025 (hardcoded
`FuelType::Electric` for gas cooking ranges).

**Impact:** Medium. Output metrics do not distinguish appliance categories from miscellaneous
`OTHER` loads. DR dispatch targeting appliances by end-use is impossible.

**Separate from FX-025:** FX-025 tracks fuel type; this finding is about end_use categorization.
Both are independent bugs that should be fixed independently.

**Fix:** Add `EndUse::COOKING` (`"cooking"`) and `EndUse::CLOTHES_WASHER` / `EndUse::CLOTHES_DRYER` /
`EndUse::DISHWASHER`, or use a single `EndUse::APPLIANCE` (`"appliance"`) constant. Register the
correct end_use per equipment type in `event_load.rs::register_with_registry`. The registry mapping
at lines 1107–1128 must pass the appropriate `EndUse` to each `EventBasedLoad::new` and
`WetAppliance::new` constructor — this requires adding an `end_use` parameter to both constructors
(paralleling how `ScheduledLoad::new` already takes `end_use`).

### FINDING 4 — GAP: No `EndUse` constant for combined heating+cooling equipment or appliances

**File:** `crates/hares-types/src/equipment.rs:41-67`

The current standard `EndUse` constants cover HVAC heating, HVAC cooling, water heating, lighting,
plug loads, refrigeration, ventilation, battery, PV, EV, generator, dehumidifier, and other.
Missing:
- `EndUse::HVAC_COMBINED` (needed for `IdealHvac`, see Finding 1)

`is_standard()` at line 100 would also need updates if new constants are added.

**Impact:** Low in isolation but required to unblock Findings 1 and 3.

### FINDING 5 — GAP: `ElectricFurnace`, `GasFurnace`, `ElectricBaseboard`, `ElectricBoiler`, `GasBoiler` declare no `DUTY_CYCLE`, `LOAD_FRACTION`, `POWER_LIMIT`, `MODE_OVERRIDE`, or `DEMAND_RESPONSE` capabilities

**Files:**
- `crates/hares-equipment/src/hvac/furnace.rs:80-82` (ElectricFurnace)
- `crates/hares-equipment/src/hvac/furnace.rs:246-248` (GasFurnace)
- `crates/hares-equipment/src/hvac/baseboard.rs:58-60`
- `crates/hares-equipment/src/hvac/boiler.rs:128-130` (ElectricBoiler)
- `crates/hares-equipment/src/hvac/boiler.rs:310-312` (GasBoiler)

All five equipment types declare only `THERMAL_SETPOINT | THERMAL_SETPOINT_DELTA | IDEAL_CAPACITY`.
Examination confirms this is correct: `apply_heating_control_unchecked` (helpers.rs:171) delegates
to `HvacEquipment::apply_control_signal` (hvac_core.rs:474) which is a `match` with `_ => {}`
for all signals other than `ThermalSetpoint` and `ThermalSetpointDelta`. These equipment types
genuinely do not support duty-cycle or DR modulation.

By contrast, `HpHeater` and `AirConditioner`/`RoomAC` do support the full set and correctly
declare it.

**Assessment:** The capability declarations are accurate and internally consistent. This is an
`ACCEPTABLE DIFFERENCE` relative to the HP equipment — simple resistive/gas heating does not
support duty-cycle DR in the same way. However, this is worth documenting as a design decision
because operators might expect `ByEndUse(HVAC_HEATING)` to route DR signals to all heating
equipment uniformly. When a dwelling has both a furnace and a heat pump, a
`ByEndUse(HVAC_HEATING)` DR signal reaches both but the furnace rejects it with a capability
error. The dispatch layer logs a warning in this case but does not halt.

**Recommendation:** This requires no code change. A developer note is warranted, potentially
in `helpers.rs::apply_heating_control_unchecked`.

### FINDING 6 — ACCEPTABLE DIFFERENCE: `ByEndUse` dispatch fans out to ALL matching equipment

**File:** `crates/hares-core/src/dwelling/mod.rs:345-356`

`DispatchTarget::ByEndUse` broadcasts to every equipment whose `descriptor().end_use` matches.
When a dwelling has two heating equipment with `EndUse::HVAC_HEATING` (e.g., ASHP + gas furnace
backup), a `ByEndUse(EndUse::HVAC_HEATING)` signal reaches both simultaneously. There is no
conflict resolution or priority selection.

This is intentional and tested (`dispatch_by_end_use_targets_all_matching_equipment` at line 3719).
It means: a DR signal to `EndUse::HVAC_HEATING` adjusts the setpoint on the furnace and the HP
simultaneously, which is the correct behavior for a setpoint delta (raise cooling setpoint on both
to reduce load).

For a `PowerSetpoint` signal, sending the same kW limit to two different heating units simultaneously
is likely unintended — both will be capped independently. No caller currently does this in the
existing actors (HVAC dispatch is always `ByName` in `IdealThermostat`, `EvDriverActor`).

**Assessment:** The fan-out semantics are correct for setpoint signals but could be surprising for
power signals. No bug, but the design should be documented at the dispatch layer.

### FINDING 7 — ACCEPTABLE DIFFERENCE: `ByName`/`ByEndUse` cross-variant conflict detection returns false

**File:** `crates/hares-control/src/dispatch.rs:52-58`

`conflicts_with` returns `false` when one target is `ByName` and the other is `ByEndUse`, even
when the name string matches the end_use string (e.g., `ByName("hvac_heating")` vs
`ByEndUse(EndUse::HVAC_HEATING)`). This is correct — these are different routing mechanisms
and a ByName that matches the end_use string is a naming accident, not a routing conflict.

Test at line 166 explicitly covers this case. **No issue.**

### FINDING 8 — ACCEPTABLE DIFFERENCE: `Generator` uses `EndUse::GENERATOR` while OCHRE uses `"Gas Generator"`

**File:** `crates/hares-equipment/src/generator.rs:374`

OCHRE uses `end_use = "Gas Generator"` (Generator.py:214). HARES uses `EndUse::GENERATOR`
(`"generator"`). This is a deliberate simplification — HARES generator supports multiple fuel
configs and the `FuelType::Gas` field carries the fuel distinction. The OCHRE name encodes
fuel into the end_use string, which is a legacy artifact.

`EndUse::GENERATOR` is more correct for a greenfield design. **No issue.**

### FINDING 9 — ACCEPTABLE DIFFERENCE: `ScheduledLoad` end_use classification is correct

**File:** `crates/hares-equipment/src/scheduled_load.rs:541-678`

All `ScheduledLoad` registry entries assign appropriate end_uses:
- Lighting, Gas Lighting, Indoor/Exterior/Basement/Garage Lighting → `EndUse::LIGHTING`
- Plug Loads, MELs, TV → `EndUse::PLUG_LOADS`

- Well Pump, Pool Pump/Heater, Spa Pump/Heater, Gas Grill, Gas Fireplace → `EndUse::OTHER`

The `OTHER` bucket for Gas Grill, Pool equipment, and Spa equipment is appropriate — these are
miscellaneous loads that don't warrant dedicated EndUse constants for DR purposes.

**No issue** for scheduled loads. The appliance gap (Finding 3) is isolated to `EventBasedLoad`
and `WetAppliance`.

### FINDING 10 — ACCEPTABLE DIFFERENCE: Dispatch routing for simultaneous same-EndUse capability mismatch

**File:** `crates/hares-core/src/dwelling/mod.rs:360-378`

When `ByEndUse` fans out to multiple equipment and one accepts the signal but another rejects
due to capability mismatch, `apply_to_matching` logs a warning but continues. The signal is
considered "delivered" (returns `true`) even if some targets reject it.

Example: `ByEndUse(HVAC_HEATING)` with a `DemandResponse` signal in a dual-fuel heating system —
`HpHeater` accepts it, `GasFurnace` rejects it with a capability error warning. Delivered = true.

This is the correct behavior: the HP reduces output as requested, and the furnace warning is
informational. The overall DR objective is partially met. **No issue** but this behavior
should be documented.

### FINDING 11 — GAP: `EndUse` type-safety: string-backed open type prevents exhaustive matching

**File:** `crates/hares-types/src/equipment.rs:38-118`

`EndUse` is an extensible `Cow<'static, str>` type to support custom equipment in Python adapters.
This prevents Rust `match` exhaustiveness checking on end_use values.

Code in `dwelling/mod.rs` (lines 2198-2204) uses `if *end_use == EndUse::BATTERY` chains rather
than a match — adding a new standard end_use requires scanning all such chains manually.

This is a **known tradeoff** for Python extensibility. The `is_standard()` predicate provides
partial safety. However, `is_standard()` is not enforced anywhere; equipment that declares
custom end_use values will pass through all `== EndUse::BATTERY` checks without hitting any
branch, which is the correct silent fallthrough.

**Assessment:** GAP. As the end_use taxonomy grows, the scattered `if eq.descriptor().end_use == EndUse::X`
chains in `dwelling/mod.rs` are a maintenance burden. Consider centralizing end_use-keyed
dispatch logic into a single match-like function. No immediate bug risk, but the pattern does
not scale.

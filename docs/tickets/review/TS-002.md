## Background/Context

Mains water temperature drives water heater energy consumption — colder mains means
more energy to heat. OCHRE uses the Burch-Christensen model derived from annual average
outdoor dry-bulb and monthly range. HARES should implement the same model correctly.

## Investigation Instructions

1. **Read HARES `water_mains.rs`:**
   - What model is implemented? Burch-Christensen?
   - What inputs: `T_annual_avg`, `T_range`, day of year?
   - What is the formula? Compare with the published Burch-Christensen equation:
     `T_mains = T_avg + offset + ratio * T_range/2 * sin(2π(day - lag)/365)`
   - What are `offset`, `ratio`, `lag`? Are they the published values?

2. **Read HARES `environment.rs` mains temp computation:**
   - How are `T_annual_avg` and `T_range` derived from weather data?
   - Known issue from exploration: `compute_mains_inputs()` uses fixed
     `month_days = [31,28,...]` with no leap-year Feb correction.
   - Known issue: `ground_t_amplitude_c = mains_dt_annual_range_c / 2.0` may
     underestimate ground temperature variation (dividing peak-to-peak by 2 twice).

3. **Read OCHRE mains temp code:**
   - Compare formula, parameters, and input derivation.

4. **Check `Hemisphere` enum:**
   - Does HARES adjust the phase lag for Southern Hemisphere? (6-month shift)
   - Does OCHRE?

5. **Compute a reference case:**
   - For Denver, CO (T_avg ≈ 10°C, T_range ≈ 25°C): what does HARES compute for
     Jan 15 vs Jul 15? What does OCHRE compute?

## Findings

### 1. Formula comparison — ACCEPTABLE DIFFERENCE (cosmetic)

HARES `water_mains.rs` implements the Burch-Christensen model correctly. The full
expression at line 108–111:

```
angle_deg = DEG_PER_DAY * (day - 15.0 - lag) + sign * 90.0
amplitude = ratio * (dt_annual_range_f / 2.0)
t_mains_f = t_avg_f + OFFSET_F + amplitude * sin(angle_deg * DEG_TO_RAD)
```

OCHRE `schedule.py` line 239:

```python
tmains_ratio * dt_monthly * sin(pi/180 * (0.986*(yday-15-tmains_lag) + sign*90))
```

where `dt_monthly = (max_monthly - min_monthly) / 2` — the half-swing.

HARES receives the full peak-to-peak range (`dt_annual_range_c`) and halves it
internally: `dt_annual_range_f / 2.0`. OCHRE receives the half-swing (`dt_monthly`)
directly. These are algebraically identical. The docstring on `water_mains_temperature_c`
explains this correctly. No formula error.

Constant values match published Burch-Christensen:
- `DEG_PER_DAY = 0.986` (paper value, not 360/365.25)
- `OFFSET_F = 6.0`
- `RATIO_BASE = 0.4`, `RATIO_SLOPE = 0.01`, `T_REF_F = 44.0`
- `LAG_BASE = 35.0`, `LAG_SLOPE = 1.0`

All match OCHRE lines 233–234 and the 2007 paper. Northern Hemisphere sign = −1 matches
OCHRE's `sign = -1 if latitude > 0 else 1`.

### 2. T_annual_avg and T_range derivation from weather — BUG (leap year)

File: `crates/hares-core/src/environment.rs`, line 657.

```rust
let month_days = [31usize, 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31];
```

February is hardcoded to 28 days regardless of the actual weather file length. EPW
files are always 8760 hours (non-leap), so in practice this never triggers. However,
if a caller ever provides 8784-hour (366-day) weather data, `year_samples` stays at
365 × samples_per_day. The `temps.len() >= year_samples` check passes, but all monthly
buckets from February onward are misaligned by one day (Feb gets 28 samples instead of
29, March absorbs the 29th of February, and so on through December). The December
bucket then ends one day short and `cursor` does not reach `temps.len()`. The resulting
monthly means are incorrect.

OCHRE raises `OCHREException("Cannot parse data for a leap year.")` at line 97 and
refuses to process leap-year EPW files, sidestepping the issue entirely. HARES silently
miscomputes. Even if 8784-hour inputs are currently rare, this should fail loudly or
handle Feb=29 correctly.

Severity: LOW for current EPW-only inputs (8760 h). Becomes MEDIUM if the API is ever
exposed to arbitrary weather data.

### 3. ground_t_amplitude_c = mains_dt_annual_range_c / 2.0 — ACCEPTABLE

File: `crates/hares-core/src/environment.rs`, line 220.

```rust
ground_t_amplitude_c: mains_dt_annual_range_c / 2.0,
```

`mains_dt_annual_range_c` is the full peak-to-peak monthly range (max_monthly_mean −
min_monthly_mean). The Kusuda-Achenbach model expects `t_amplitude_c` = half of the
peak-to-peak surface temperature variation (i.e. the semi-amplitude). Dividing by 2.0
is therefore correct — no double-division.

The ticket concern about "dividing peak-to-peak by 2 twice" does not apply here: the
division happens once in `environment.rs` for the Kusuda amplitude, and separately once
inside `water_mains_temperature_c` for the mains amplitude. These are two different
computations receiving the same input. Neither double-divides.

OCHRE's `schedule.py` uses `dt_monthly` (already the half-swing) for both mains and
ground models. HARES uses the full range as the shared input and halves it at each
use site — same result, different calling convention. The docstring on
`water_mains_temperature_c` documents this convention explicitly.

### 4. Hemisphere adjustment — ACCEPTABLE

`water_mains.rs` lines 102–105 and `environment.rs` lines 181–190:

HARES detects Southern Hemisphere via `weather_meta.latitude < 0.0` and sets
`Hemisphere::Southern`, which sets `sign = +1.0`. This matches OCHRE's
`sign = -1 if latitude > 0 else 1`. The phase shift is a 180° inversion of the sine,
equivalent to a 6-month season flip.

For Kusuda-Achenbach, `DEFAULT_PHASE_DAY_SOUTHERN = 35.0 + 182.5` applies the same
half-year offset to the ground model. Both are correct.

A minor edge case: `latitude == 0.0` is treated as Northern Hemisphere (latitude not <
0.0). OCHRE's condition `latitude > 0` also treats latitude=0 as Southern (sign=+1).
This is a one-line disagreement at the equator, where the distinction is physically
meaningless. Classified as GAP rather than BUG.

### 5. Reference case — Denver (T_avg=10°C, T_range=25°C)

Conversion: T_avg = 50 °F, ΔT_range = 45 °F.
Parameters: ratio = 0.4 + 0.01×(50−44) = 0.46, lag = 35−6 = 29 days.
Amplitude = 0.46 × 22.5 = 10.35 °F.

**Jan 15 (day=15):**
- angle = 0.986×(15−15−29) + (−1)×90 = 0.986×(−29) − 90 = −28.59 − 90 = −118.59°
- sin(−118.59°) ≈ −0.877
- T_mains = 50 + 6 + 10.35×(−0.877) = 56 − 9.08 = **46.9 °F → 8.3 °C**

**Jul 15 (day=196):**
- angle = 0.986×(196−15−29) − 90 = 0.986×152 − 90 = 149.9 − 90 = 59.9°
- sin(59.9°) ≈ 0.865
- T_mains = 50 + 6 + 10.35×0.865 = 56 + 8.95 = **64.95 °F → 18.3 °C**

Seasonal swing: 10 °C. These results are physically plausible for Denver ground water.
OCHRE produces identical values for these inputs (same formula, same constants).

### 6. Minor: ratio clamping for arctic climates — ACCEPTABLE DIFFERENCE

HARES clamps `ratio` to `[0.0, 1.0]`. OCHRE does not clamp. For annual averages below
approximately −24 °C (ratio < 0), OCHRE would produce a phase-inverted curve (mains
coldest in summer). HARES returns a flat curve equal to T_avg + offset. The HARES
behavior is more physically defensible; the model is not calibrated for arctic climates.
This is a deliberate improvement, documented in the source comment.

## Recommended Tests

1. **Leap-year weather length guard** (`crates/hares-core/src/environment.rs`):
   Add a test that calls `compute_mains_inputs` with 8784-hour weather data (8784 ×
   samples_per_day entries). Assert either (a) the result matches the correct monthly
   averages with Feb=29, or (b) the function panics/errors loudly rather than silently
   miscomputing. Currently neither is guaranteed.

2. **Denver reference case numeric regression** (`crates/hares-physics/src/water_mains.rs`):
   Add a test asserting `water_mains_temperature_c(10.0, 25.0, 15, Hemisphere::Northern)`
   returns 8.3 ±0.1 °C and day 196 returns 18.3 ±0.1 °C. This pins the calibrated
   output and catches any constant drift.

3. **Equator hemisphere edge case** (`crates/hares-core/src/environment.rs`):
   Add a test with `latitude = 0.0` confirming which hemisphere is selected and document
   the choice. Currently untested and disagrees silently with OCHRE.

4. **OCHRE cross-validation for multiple climates** (`crates/hares-physics/src/water_mains.rs`):
   The existing Chicago TMY2 cross-validation test (`chicago_tmy2_cross_validation_vs_ochre`)
   is good. Add at least one more location (e.g. Miami T_avg≈24°C, Phoenix T_avg≈22°C)
   to exercise the high-ratio branch and confirm ratio clamping threshold.

## Background/Context

HARES implements a 4-component exterior LWR model (ground/sky/horizon fractions, β factor, iterative surface temperature) and area-weighted-view-factor interior LWR. The iterative convergence criterion, damping strategy, and window LWR bypass logic are not reviewed by any existing ticket.

## Investigation Instructions

1. **Read exterior LWR model** in `longwave_radiation.rs`. Document ground/sky/horizon view factor computation, β factor, and iteration convergence.
2. **Read interior LWR model** in `longwave.rs`. Document area-weighted view factor approach and `apply_interior_longwave_inputs_iterative`.
3. **Compare with OCHRE's LWR implementation.** Does OCHRE use the same iterative approach or a linearized model?
4. **Check window LWR bypass:** HARES skips exterior LWR for windows ("implicit in U-factor"). Verify this is physically correct and document the assumption.
5. **Check radiant barrier:** `longwave_radiation.rs` has emissivity override (0.05 vs 0.90 default) for radiant barriers. Verify this is applied correctly for attic boundaries.

## Findings

### F1 [MEDIUM] Interior radiation: no iterative surface-temperature update (divergence from OCHRE)

**Files:** `crates/hares-envelope/src/thermal_solver/longwave.rs:154–241`, `vendors/OCHRE/ochre/Models/Envelope.py:91–121`

OCHRE's `_solve_interior_radiation` iteratively updates each surface's temperature using heavy-ball damping over `dt // 5min + 3` iterations (e.g., 4 iterations at 5-minute timesteps, 15 at 60-minute timesteps). The converged surface temperatures feed back into the net flux calculation.

HARES computes interior surface temperatures once (`t_surf = rad_frac * t_node + (1 - rad_frac) * t_zone`, `longwave.rs:197`), then calls `net_flux_w_into` directly with those fixed values. There is no iteration loop. This underestimates the LWR exchange whenever surfaces have non-negligible film resistance (rad_frac < 1), because the surface temperature shift driven by radiation is not accounted for in the flux calculation.

At 60-minute timesteps the error accumulates over more iterations in OCHRE (15 total) versus a single pass in HARES, so the divergence grows with timestep size.

### F2 [MEDIUM] Exterior iteration count is off by one vs. OCHRE

**Files:** `crates/hares-core/src/dwelling/solver_builder.rs:537`, `vendors/OCHRE/ochre/Models/Envelope.py:207`

OCHRE: `iterations = time_res // timedelta(minutes=5) + 1`
HARES: `n_iter = ceil(dt_s / 300.0).max(1)`

For integer multiples of 5 minutes these are equivalent in floor-division, but:
- At 5-minute timesteps: OCHRE = 2, HARES = 1
- At 60-minute timesteps: OCHRE = 13, HARES = 12

HARES always runs one fewer exterior LWR iteration than OCHRE. Combined with the missing interior iteration loop (F1), this accumulates a systematic error at all timestep sizes.

### F3 [LOW] Exterior view-factor formula algebraically equivalent to OCHRE (informational, no bug)

**Files:** `crates/hares-envelope/src/longwave_radiation.rs:97–125, 206`

OCHRE computes a single combined sky factor `svf = ((1 + cos φ)/2)^1.5` and uses it as:

```python
h_lwr_inj = e * ((1 - svf) * T_air^4 + svf * T_sky^4)
```

HARES computes F_sky and β separately:

```rust
F_sky = 0.5 * (1 + cos φ)      // sky_view_factor()
beta  = sqrt(F_sky)             // beta_factor()
sky_coeff = beta * F_sky        // = F_sky^1.5
air_coeff = 1 - sky_coeff       // = 1 - F_sky^1.5
```

Since `beta * F_sky = F_sky^0.5 * F_sky = F_sky^1.5 = ((1+cos φ)/2)^1.5 = svf`, the two formulations are mathematically identical. HARES's decomposition into F_sky and β follows the EnergyPlus Engineering Reference notation more explicitly but produces the same numeric result. No defect.

### F4 [HIGH] Radiant barrier emissivity applied to wrong zone face

**Files:** `crates/hares-core/src/dwelling/solver_builder.rs:203–208`, `vendors/OCHRE/ochre/Models/Envelope.py:221–228`

OCHRE applies emissivity = 0.05 to any `BoundarySurface` whose `zone_name == "Attic"`. In OCHRE's model, a `BoundarySurface` is a single face (one side of a boundary). For a roof boundary, both the interior surface face (zone_name = "Attic") and the attic floor boundary interior face (zone_name = "Attic") receive the low emissivity.

HARES checks:

```rust
let is_attic_radiant_barrier = boundary.has_radiant_barrier
    && boundary.interior_zone.as_ref() == Some(&hares_io::hpxml::ZoneType::Attic);
```

In HPXML semantics, `interior_zone` is the "interior adjacent to" space. For an **attic floor** boundary (below the attic, above conditioned space), `interior_zone = Conditioned` and `exterior_zone = Attic`. A radiant barrier is physically installed facing the attic airspace (the `exterior_zone = Attic` side), but the current check only matches `interior_zone = Attic`. This means:

- Roof boundary (interior_zone=Attic, exterior_zone=Outdoor): correctly matched.
- Attic floor boundary (interior_zone=Conditioned, exterior_zone=Attic): **missed** — the foil face that borders the attic gets emissivity 0.90 instead of 0.05.

This is a correctness defect that silently under-predicts the benefit of attic radiant barriers. The correct condition should be:

```rust
let is_attic_radiant_barrier = boundary.has_radiant_barrier
    && (boundary.interior_zone.as_ref() == Some(&ZoneType::Attic)
        || boundary.exterior_zone.as_ref() == Some(&ZoneType::Attic));
```

No existing test exercises `RadiantBarrier: true`; all fixture XMLs use `<RadiantBarrier>false</RadiantBarrier>`.

### F5 [LOW] Window LWR bypass — physically defensible, but assumption is undocumented in code contract

**Files:** `crates/hares-envelope/src/thermal_solver/longwave.rs:39–54`

HARES skips exterior LWR for window surfaces with `BoundaryCategory::Window` and logs a comment that "LWR is implicit in U-factor". This is physically reasonable: the U-factor for a window is typically a whole-unit value measured under standard conditions that implicitly include external convective and longwave radiation film coefficients. Applying a separate explicit LWR term with the zone air temperature (used as the "node" when no RC node exists for glass) would produce a massive erroneous cooling effect as noted in the comment.

The bypass is consistent with OCHRE's treatment (windows are in `n_nodes == 0` boundaries; they're routed to the zone heat input and do not participate in exterior iterative LWR). However, this leaves the window glass exterior surface temperature undefined for diagnostics, so `surface_temp_c` is reported as `t_ext` in the diagnostic buffer — a plausible warm-start value but not physically computed.

Recommendation: Document the physical assumption in `ExteriorSurfaceInfo` or the window path that U-factor measurements include the exterior combined-film coefficient, so future maintainers understand why explicit LWR is suppressed for this category.

### F6 [LOW] Interior radiation: `ScriptF` naming is misleading

**Files:** `crates/hares-envelope/src/longwave_radiation.rs:315–419`

`ScriptFCoefficients` uses area-emissivity weighted view factors `F_i = A_i ε_i / Σ A_j ε_j`. True Gebhart "Script F" factors account for multiple inter-reflections via a full radiosity matrix. The current implementation is an area-emissivity radiosity shortcut (same approximation as OCHRE), not a true Gebhart solution. The struct name overstates the physical fidelity. This is not a numerical bug — OCHRE uses the identical method — but callers or future contributors may believe actual Gebhart factors are computed when they are not.

### F7 [LOW] Convergence check reads stale `t_prev_iter` when both branches share the variable

**Files:** `crates/hares-envelope/src/thermal_solver/longwave.rs:120–125`

```rust
let t_next = t_surf + 0.5 * (t_new - t_surf) + 0.1 * (t_surf - t_prev_iter);
t_prev_iter = t_surf;       // overwrites prev with old current
t_surf = t_next;            // advances to new
if (t_surf - t_prev_iter).abs() < 0.01 { break; }
```

After line 121–122, `t_surf` = `t_next` and `t_prev_iter` = old `t_surf`. The convergence check therefore measures the step size `|t_next - t_surf_old|`, which is the same quantity OCHRE measures (`|temperatures[b] - t_prevs[b]|`). The logic is correct. However it is easy to misread because `t_prev_iter` has two uses in close succession: it stores the heavy-ball history term AND serves as the convergence reference. A rename to `t_surf_prev` and a comment would improve clarity.

## Recommended Tests

1. **Interior LWR iteration parity test**: Build a 3-surface zone (floor, wall, ceiling) with known temperatures (e.g. ceiling 30°C, floor 15°C, wall 20°C) with non-trivial rad_frac values. Compare HARES single-pass flux output against an iterative re-solve of the same zone using the OCHRE loop (re-computing surface temps after each LWR update). Verify the difference is bounded and document the tolerance.

2. **Exterior LWR iteration count parity test**: Parametrize over timestep sizes 60s, 300s, 600s, 3600s. Verify `n_iter` gives the same converged surface temperature as a reference implementation looped to full convergence (delta < 0.001°C). Compare against OCHRE's `n_iter + 1` value to confirm that one additional iteration does not materially change the result.

3. **Radiant barrier attic floor test**: Construct an HPXML building with `RadiantBarrier: true` on the attic roof boundary. Assert that both the roof boundary exterior surface (facing attic) AND the attic floor boundary interior surface (facing attic) are assigned emissivity 0.05. Currently only the roof boundary side is correctly assigned; the attic floor side will read 0.90 until F4 is fixed.

4. **Sky-temperature NaN fallback test**: Supply `t_sky_c = NaN` and verify exterior LWR collapses to `e * A * (T_air^4 - T_surf^4)` for both horizontal and vertical surfaces.

5. **Energy conservation test for interior LWR**: For any N-surface zone with arbitrary temperatures, assert `sum(net_flux_w_into(...)) == 0` within floating-point tolerance. This invariant is guaranteed by construction for `ScriptFCoefficients` but should be verified for the linearised fallback path as well.

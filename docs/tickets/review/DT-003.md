## Background/Context

HVAC thermostat setpoints often follow day/night and weekday/weekend schedules (e.g.,
68°F daytime, 62°F overnight setback). These must evaluate in local time. A UTC-offset
error would shift the setback period, causing heating/cooling at wrong hours and
incorrect energy consumption.

1. **Trace thermostat setpoint evaluation in HARES:**
   - Read `crates/hares-equipment/src/hvac/thermostat.rs` — how are heating/cooling
     setpoints resolved each timestep?
   - If `ScheduleSource::TimeWindows` is used, what `DateTime` feeds into `value_at()`?
   - Read `hvac_core.rs` — how does `HvacEquipment::step()` obtain the current setpoints?

2. **Trace OCHRE equivalent:**
   - Read `vendors/OCHRE/ochre/Equipment/HVAC.py` — how does the thermostat read
     setpoints from the schedule DataFrame?
   - Does OCHRE support setback profiles? How are they time-indexed?

3. **Document:**
   - Is HARES using `env.current_time` (local offset) for setpoint schedule lookup?
   - Are setback/setup transitions happening at the correct local hour?
   - Does the thermostat respect DST transitions when `civil_timezone` is set?
   - Any divergences from OCHRE, their impact, and recommendations.

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### Summary

HARES correctly evaluates thermostat setpoint schedules in **local (wall-clock) time**, matching OCHRE's behavior. No UTC offset bug exists. However, there is a latent edge case and a missing test coverage gap.

---

### Finding 1 — CORRECT: `DailyProfile` evaluation uses local time (severity: none)

**Path traced:**

1. `HvacEquipment::update_mode` (`hvac_core.rs:567`) calls `self.resolve_profile_setpoints(env)`.
2. `resolve_profile_setpoints` (`hvac_core.rs:544-565`) calls `source.value_at(env)` on both `heating_setpoint_source` and `cooling_setpoint_source`.
3. `ScheduleSource::DailyProfile::value_at` (`hares-types/src/schedule.rs:478-486`) extracts:
   ```rust
   let hour = env.current_time.hour() as usize;
   let is_weekend = env.current_time.weekday().num_days_from_monday() >= 5;
   ```
4. `env.current_time` is a `DateTime<FixedOffset>` populated directly from `SimClock::current_time()` (`clock.rs:55-59`), which is `start_time + (step * time_res)`.
5. `start_time` is set at dwelling construction (`dwelling/mod.rs:758-767`) by reinterpreting the user's naive wall-clock components into the **EPW file's timezone offset** (`FixedOffset::east_opt((timezone_offset_h * 3600.0) as i32)`).

The offset is baked into `start_time`, so `.hour()` and `.weekday()` on `env.current_time` return local wall-clock values for the entire simulation. Setback transitions (e.g., midnight setback at hour 22) fire at the correct local hour, not UTC hour.

---

### Finding 2 — CORRECT: OCHRE uses the same fixed-offset local time approach (severity: none)

OCHRE builds its schedule DataFrame with a timezone-aware pandas `DatetimeIndex` sourced from the EPW metadata (`ochre/utils/schedule.py:154-157`):
```python
tz = dt.timezone(dt.timedelta(hours=weather_timezone))
df = df.tz_localize(tz)
```
The `Simulator` advances `current_time` by `time_res` each step starting from `start_time` (which already carries the local offset). The schedule is then sliced by `.loc[current_time]` producing the same effective local-hour resolution. OCHRE also supports a `"DST"` mode (`schedule.py:635-643`) that replaces the fixed offset with a pytz DST-aware timezone, parallel to HARES's `civil_timezone` / `dst` cargo feature path.

---

### Finding 3 — LATENT BUG: `ColumnRef` path is not time-aware for setpoints (severity: low)

When `heating_setpoint_source` or `cooling_setpoint_source` is a `ScheduleSource::ColumnRef` (CSV-column-backed), `value_at` reads a pre-indexed position from the schedule array (`schedule.rs:488-501`). The schedule array index is computed by `EnvironmentManager::compute_schedule_idx` (`environment.rs:324-344`), which correctly uses the civil timezone when `dst` is enabled. However:

- The `DailyProfile` branch calls `env.current_time.hour()` directly, bypassing the `compute_schedule_idx` logic entirely.
- If DST is active (`dst` feature + `civil_timezone`), the `ColumnRef` path follows civil time (correct), but the `DailyProfile` path still uses the fixed-offset `env.current_time`, which will be one hour off during the DST transition period (e.g., US summer clocks forward).

This creates a behavioral divergence between the two setpoint source variants when DST is enabled. The `DailyProfile` variant will apply setback at the wrong hour during DST — identical to the original concern in this ticket, but scoped to DST-enabled configurations only.

**Affected code:** `hares-types/src/schedule.rs:478-480` — `DailyProfile` evaluation does not convert `env.current_time` to civil time before extracting `.hour()`.

**Recommendation:** When the `dst` feature is active and a civil timezone is available, `DailyProfile::value_at` should resolve the civil hour, not the fixed-offset hour. This requires either (a) plumbing the optional `chrono_tz::Tz` into `EnvironmentState`, or (b) pre-converting `env.current_time` to civil time before it is inserted into the environment state.

---

### Finding 4 — TEST GAP: No cross-timezone thermostat setback test (severity: low)

The schedule tests in `hares-types/src/schedule.rs` that exercise `DailyProfile` all construct `env.current_time` with UTC offset (`FixedOffset::east_opt(0)`). There is no test that:

- Constructs a dwelling with a non-UTC EPW timezone offset (e.g., UTC-7, Mountain Standard Time).
- Configures a heating setpoint with an overnight setback at a specific local hour.
- Asserts that the setback applies at the correct local hour rather than the same hour in UTC.

Without this test, a regression to UTC-based setpoint evaluation would be undetected by CI.

**Recommended test location:** `crates/hares-equipment/tests/hvac_tests.rs` or a new test in `crates/hares-types/src/schedule.rs`.

**Recommended test name:** `daily_profile_setback_fires_at_correct_local_hour_with_utc_offset`

**Test sketch:**
- Create `EnvironmentState` with `current_time` using `FixedOffset::west_opt(7 * 3600)` (UTC-7).
- Set wall-clock time to hour 22 (10 PM local, which is 05:00 UTC next day).
- Construct `DailyProfile` with setback value at hour 22.
- Assert `value_at` returns the setback value, not the 05:00 hour value.

---

### Finding 5 — CORRECT: Weekend classification is correct (severity: none)

`num_days_from_monday() >= 5` correctly identifies Saturday (5) and Sunday (6) as weekend days. `env.current_time` carries the local offset, so day-of-week is evaluated in local time, not UTC. A simulation that spans a midnight UTC boundary would not accidentally flip weekend classification.

---

### Divergence from OCHRE

No behavioral divergence under standard (non-DST) operation. Under DST operation, HARES `DailyProfile` setpoints diverge from OCHRE's DST-aware schedule indexing by ±1 hour during DST transitions, as described in Finding 3.

## Background/Context

When `civil_timezone` is set and DST causes a spring-forward, `compute_schedule_idx` derives `civil_secs` from `civil.ordinal0()`. At the spring-forward transition, two consecutive simulation steps produce the same schedule index (the skipped hour means the index doesn't advance). At fall-back, a schedule row is read twice. This can silently repeat or skip schedule values affecting energy consumption, EV charging, and thermostat setpoints.

## Investigation Instructions

1. **Trace `compute_schedule_idx` with DST feature enabled** through a spring-forward transition (e.g., March 2nd Sunday at 2:00 AM).
2. **Trace the same path through a fall-back transition** (November 1st Sunday at 2:00 AM).
3. **Compare with OCHRE:** OCHRE uses `pandas.DatetimeIndex` with real timezone which handles DST transitions automatically. Does HARES's approach produce equivalent schedule values?
4. **Quantify impact:** For a building in US Eastern timezone, how many schedule rows are affected per year? What is the energy impact of a repeated/skipped hour?

---

## Findings

### Summary

The DST handling in `compute_schedule_idx` is **correct by design** for its stated contract. The `ScheduleSource::DailyProfile`, `SolarAware`, and `TimeWindows` variants have a **separate defect**: they read `env.current_time` which is a `DateTime<FixedOffset>` — permanently fixed at the simulation start offset — so they **never apply DST**. There is also a **compile-breaking test defect** when the `dst` feature is enabled.

---

### Finding 1 (CRITICAL) — DST tests fail to compile: spurious `midpoint_offset_secs` field in test fixture

**File:** `crates/hares-core/src/environment.rs:1663`

```
midpoint_offset_secs: 0,
```

`ScheduleTimeSeries` (`crates/hares-io/src/schedule.rs:54–63`) has no `midpoint_offset_secs` field. The `midpoint_offset_secs` field belongs to `WeatherMeta`, not `ScheduleTimeSeries`. The four DST tests in `dst_tests` cannot compile, and are therefore **completely unexercised** at any point in CI unless `--features dst` is explicitly passed. Running `cargo test -p hares-core --features dst` produces:

```
error[E0560]: struct `hares_io::ScheduleTimeSeries` has no field named `midpoint_offset_secs`
  --> crates/hares-core/src/environment.rs:1663:17
```

**Impact:** All four DST-specific tests (`schedule_spring_forward_skips_civil_hour`, `schedule_fall_back_reuses_civil_hour`, `weather_unaffected_by_dst_setting`, `year_round_schedule_alignment`) are dead code. The entire `dst` feature has zero test coverage. Any regression in `compute_schedule_idx` would be undetected.

**Fix:** Remove the `midpoint_offset_secs: 0` line from the `annual_hourly_schedule()` test helper at line 1663.

### Finding 2 (HIGH) — `ScheduleSource::DailyProfile`, `SolarAware`, and `TimeWindows` are permanently DST-blind

**File:** `crates/hares-types/src/schedule.rs:478, 511, 554–556`

These three variants read `env.current_time.hour()`, `env.current_time.weekday()`, and `env.current_time.minute()` directly. `env.current_time` is set from `clock.current_time()` which returns a `DateTime<FixedOffset>` carrying the **fixed** UTC offset from `start_time` — it never changes. Concretely, for a simulation started with `FixedOffset::west_opt(5 * 3600)` (EST), the offset stays `-05:00` for the entire year, even during summer when local time is EDT (UTC-4). After spring-forward, the wall clock reads one hour ahead of the value returned by `env.current_time.hour()`.

This means:
- `DailyProfile` accesses the wrong hour slot for roughly half the year in any US timezone.
- `TimeWindows` evaluates windows against a stale `minute_of_day`, causing rate schedules, thermostat setpoints, and EV departure windows to mismatch the actual wall clock by 60 minutes from the spring-forward until fall-back.
- `SolarAware` uses `hour >= 5` as its evening/overnight discriminator; off by one hour in summer.

The `csv`-backed `ColumnRef` path is **not** affected because it reads from the pre-indexed array via `compute_schedule_idx`, which correctly applies the civil timezone conversion.

**Impact:** For US locations using `civil_timezone` (DST enabled), schedule-driven equipment (lighting, appliances, EV departure windows, TOU rates) has a systematic 60-minute offset for ~7 months per year (March–November for US Eastern). Energy error per dwelling is O(hours × setpoint deviation × thermal mass), roughly comparable to the 0.4–0.9 °C MAE from thermal solver tuning.

**Root cause:** `EnvironmentState::current_time` is `DateTime<FixedOffset>`. Downstream consumers of `ScheduleSource` have no mechanism to obtain the civil-timezone-adjusted time; the DST correction is encapsulated inside `EnvironmentManager::compute_schedule_idx` and never propagated to `EnvironmentState`.

**Fix:** Add a `civil_time: Option<DateTime<chrono_tz::Tz>>` field (or equivalent) to `EnvironmentState` and populate it from `compute_schedule_idx` when `civil_tz` is set. `ScheduleSource::value_at` reads `civil_time` when present, falling back to `current_time`. Alternatively, expand `env.current_time` to carry the civil-adjusted `DateTime<FixedOffset>` (re-encoding the civil offset at each step) so no API surface changes.

### Finding 3 (MEDIUM) — `compute_schedule_idx` DST path: spring-forward skips one row; fall-back reuses one row — this is the intended behavior, not a defect

**File:** `crates/hares-core/src/environment.rs:327–341`

The implementation computes `civil_secs = doy0 * 86_400 + h * 3600 + m * 60 + s` using the civil wall-clock fields after `sim_time.with_timezone(&tz)`. Chrono-tz resolves the unambiguous (post-transition) representation for any UTC instant.

- **Spring-forward (2024-03-10 02:00 EST → 03:00 EDT):** The UTC instant `07:00Z` converts to `03:00 EDT` (civil hour 3). The prior step was `01:00 EST` (civil hour 1). The `civil_secs` jumps by 2 hours, skipping index for civil hour 2. This is correct: the schedule CSV row corresponding to 2:00 AM simply does not exist in reality on that day, and skipping it mirrors what OCHRE does via pandas `tz_localize`.
- **Fall-back (2024-11-03 02:00 EDT → 01:00 EST):** The UTC instant `06:00Z` converts to `01:00 EST`, same civil_secs as the prior `05:00Z → 01:00 EDT`. The schedule index for 1:00 AM is read twice. This is also the correct behavior: the same schedule row applies to both occurrences of 1 AM.

The tests at lines 1741 and 1781 assert this contract explicitly and the logic is sound — if they could compile (see Finding 1).

**OCHRE comparison:** OCHRE's pandas `DatetimeIndex` with `tz_localize` follows the same convention: non-existent times are skipped on spring-forward and ambiguous times select the first occurrence on fall-back by default. HARES matches this.

### Finding 4 (LOW) — Fixed-offset path in `compute_schedule_offset` treats `start_time` offset as civil time throughout, giving wrong results for simulations spanning a DST boundary without `civil_timezone`

**File:** `crates/hares-core/src/environment.rs:628–644`

When `civil_timezone` is `None`, the schedule is indexed by `(step + schedule_start_offset) % schedule_len`. `schedule_start_offset` is computed from `start_time`'s wall-clock fields (which carry the fixed offset). If the simulation spans a DST boundary and the caller did not supply `civil_timezone`, the schedule drifts by one hour after the transition — but silently, with no error or warning.

This is a documentation/UX gap rather than a code defect: the contract is stated in `clock.rs` ("pass the intended local hour in `start_time`"), but there is no runtime warning when a fixed-offset simulation runs across a DST date. Users not aware of the `civil_timezone` parameter will get wrong results and no diagnostic.

**Fix:** At `EnvironmentManager::new`, if `civil_timezone` is `None` and `start_time`'s offset does not match the offset at `start_time + duration` (which would require knowing the timezone), no automatic detection is feasible. A documentation note at the parameter level warning that `civil_timezone` must be set for DST-spanning simulations would prevent user error.

## Impact quantification (US Eastern)

| Transition | Schedule rows affected per year | Behaviour |
|---|---|---|
| Spring-forward (2nd Sunday March) | 1 row skipped per annual cycle | No energy error (hour doesn't exist) |
| Fall-back (1st Sunday November) | 1 row repeated per annual cycle | Negligible (~1 h occupancy/setpoint) |
| `DailyProfile`/`TimeWindows` DST-blind (Finding 2) | ~5040 rows/year (7 months × 24 h × 30 d avg) with 60-min offset | Systematic; can be 1–3% annual HVAC energy error |

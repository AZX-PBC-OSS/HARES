## Background/Context

OCHRE cooling outputs include latent-specific columns: `"{end_use} Latent Gains (W)"`,
`"{end_use} SHR (-)"` that heating doesn't have. These are important for humidity
modeling.

---

## Field-by-Field Mapping

### OCHRE cooling output columns (all verbosity levels)

OCHRE emits these fields under the prefix `"HVAC Cooling"`. Base class
(`Equipment.generate_results`) adds electric power.

| OCHRE field name | verbosity gate | unit |
|---|---|---|
| `HVAC Cooling Electric Power (kW)` | >=6 (base class) | kW |
| `HVAC Cooling Mode` | >=7 (base class) | string |
| `HVAC Cooling Delivered (W)` | >=4 | W |
| `HVAC Cooling Setpoint (C)` | >=4 | °C |
| `HVAC Cooling COP (-)` | >=4 | dimensionless |
| `HVAC Cooling Duct Losses (W)` | >=5 | W |
| `HVAC Cooling Main Power (kW)` | >=7 | kW |
| `HVAC Cooling Fan Power (kW)` | >=7 | kW |
| `HVAC Cooling Latent Gains (W)` | >=7, cooling only | W |
| `HVAC Cooling SHR (-)` | >=7, cooling only | dimensionless |
| `HVAC Cooling Speed (-)` | >=7 | integer index |
| `HVAC Cooling Capacity (W)` | >=7 | W |
| `HVAC Cooling Max Capacity (W)` | >=7 | W |

OCHRE's `HVAC Cooling COP` is computed as:

    main_power = electric_kw + gas_therms/kwh_to_therms - fan_kw
    cop = capacity * space_fraction / (main_power * 1000)   [compressor+crankcase in denominator]

OCHRE's `HVAC Cooling Delivered (W)` is `|delivered_heat| * duct_dse`, where
`delivered_heat = heat_gain * shr + fan_power` (sensible only; fan adds to
sensible via air heating).

OCHRE's `HVAC Cooling Latent Gains (W)` is `latent_gain * space_fraction`, where
`latent_gain = heat_gain * (1 - shr)`.

### HARES cooling telemetry fields

Source: `crates/hares-equipment/src/hvac/ac_config.rs:default_telemetry()` /
`telemetry_fields()`.

| HARES key (`telemetry_keys.rs`) | unit |
|---|---|
| `electric_kw` | kW |
| `sensible_cooling_w` | W |
| `latent_cooling_w` | W |
| `shr` | dimensionless |
| `operating_mode` | enum code |
| `cop` | dimensionless |
| `runtime_fraction` | dimensionless |
| `compressor_kw` | kW |
| `fan_kw` | kW |
| `supply_temp_c` | °C |
| `apparatus_dew_point_c` | °C |

HARES emits 12 fields. `HpCooler` delegates entirely to `AirConditioner`'s
telemetry (via `inner.telemetry()`), so ASHP Cooler and MSHP Cooler emit
identically named keys.

## Findings

### F1 — HARES COP definition diverges from OCHRE (severity: medium)

**File:** `crates/hares-equipment/src/hvac/air_conditioner.rs:685-692`

HARES COP is `(sensible_cooling_w + latent_cooling_w) / (compressor_kw * 1000)`,
explicitly excluding fan power from the denominator (comment says "AHRI/SEER
convention"). OCHRE COP is `capacity / (main_power * 1000)` where
`main_power = electric_kw - fan_kw` — which also excludes fan from the denominator
but includes crankcase heater power (crankcase is added to `electric_kw` before
`main_power` is computed). HARES `compressor_kw` is the raw compressor draw and
does not include crankcase. When crankcase is active (unit off, cold OAT), OCHRE
COP = 0 (because `on` is False); HARES also emits COP = 0 in that case because
`compressor_kw = 0`. The definitions are functionally equivalent at the relevant
operating points; no action required for correctness, but the comment should note
that OCHRE also excludes fan from the denominator (not just AHRI).

### F2 — Three OCHRE columns have no HARES equivalent (severity: medium)

The following OCHRE cooling fields have no corresponding HARES telemetry key:

| OCHRE field | notes |
|---|---|
| `HVAC Cooling Setpoint (C)` | active setpoint at time of step |
| `HVAC Cooling Capacity (W)` | actual capacity used this timestep |
| `HVAC Cooling Max Capacity (W)` | rated max capacity at current conditions |

These are used in post-processing and EBM derivations.
`SPEED_INDEX` exists in `telemetry_keys.rs` but is not emitted by
`AirConditioner` (no entry in `default_telemetry()` or `telemetry_fields()`).

**Action required:** add `cooling_setpoint_c`, `capacity_w`, and `max_capacity_w`
to `default_telemetry()` and `telemetry_fields()` in `ac_config.rs`, and write
them in the `CoolingCore::step()` telemetry block in `air_conditioner.rs`. The
values are already available: `self.hvac.setpoint_c` (or the thermostat setpoint),
`self.hvac.capacity` (current stage capacity), and `self.hvac.capacity_max`.

### F3 — `HVAC Cooling Duct Losses (W)` is not exposed in telemetry (severity: low)

OCHRE emits `Duct Losses (W) = |delivered_heat| * (1 - duct_dse)`. HARES applies
DSE to both `sensible_cooling_w` and `latent_cooling_w` before writing to
telemetry (`air_conditioner.rs:676-681`) so downstream consumers can see the
delivered value, but the duct loss magnitude itself is not emitted as a separate
field. This is sufficient for energy-balance purposes; a separate `duct_loss_w`
field would be useful for diagnostic output if duct modeling is a priority.

### F4 — `HVAC Cooling Delivered (W)` semantic vs HARES `sensible_cooling_w` (informational)

OCHRE's `Delivered (W)` is `|delivered_heat| * duct_dse` where
`delivered_heat = heat_gain * shr + fan_power` — sensible only, fan contribution
folded in. HARES `sensible_cooling_w` is the sensible coil output only (fan
power is separated into `fan_kw`). A direct column mapping is therefore:

    OCHRE Delivered (W) ≈ HARES sensible_cooling_w + (fan_kw * 1000) [before DSE application]

After DSE both are scaled. This is not a defect, but any parity test comparing
`Delivered (W)` to `sensible_cooling_w` must account for the fan contribution.

### F5 — Crankcase power is included in `electric_kw` but not broken out separately (severity: low)

OCHRE lumps crankcase into `electric_kw` with no dedicated column. HARES does the
same. Neither exposes a `crankcase_kw` telemetry key, which makes it impossible
to post-process the crankcase contribution without re-running the calculation.
This is consistent with OCHRE behaviour, but a `crankcase_kw` telemetry key would
improve diagnostics when debugging cold-start conditions.

### F6 — `RoomAC` and `AirConditioner` emit identical telemetry keys (verified, no issue)

Both use the same `CoolingCore` and therefore call `default_telemetry()` and
`telemetry_fields()` from the same `ac_config.rs`. The `is_room_ac` flag only
affects curve selection and capacity defaults, not telemetry field names.

## Recommended Tests

1. **`ac_telemetry_setpoint_field_present`** — after `step()`, assert
   `telemetry().get(tk::COOLING_SETPOINT_C)` is `Some` and equals the configured
   setpoint value. Covers F2 once the field is added.

2. **`ac_telemetry_capacity_field_nonzero_when_on`** — with zone above setpoint,
   assert `telemetry().get(tk::CAPACITY_W)` is `Some` and `> 0.0`. Covers F2.

3. **`ac_sensible_latent_sum_matches_total_cooling`** — assert
   `sensible_cooling_w + latent_cooling_w` approximates total coil heat removal
   (i.e. `sensible_cooling_w / shr` when shr < 1). Validates the fan-excluded
   latent split is self-consistent.

## Background/Context

EPW weather files use an end-of-hour convention: the record timestamped 01:00 represents
the average conditions over 00:00–01:00. OCHRE shifts all EPW timestamps forward by
30 minutes (`offset = dt.timedelta(minutes=30)`) so that each record represents the
mid-hour point. This is standard practice for building simulation tools.

HARES stores `midpoint_offset_secs` in `WeatherMeta` and applies it in
`EnvironmentManager::compute_annual_offset()`. This ticket verifies the offset is
correct and applied consistently.

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

PSM3 and ResStock CSV use beginning-of-interval timestamps, so `midpoint_offset_secs=0` is correct for both. TMY3 files also use beginning-of-hour convention (confirmed via `tmy3.rs:240`), so 0 is also correct there.

### EPW convention — OCHRE

`ochre/utils/schedule.py:167–176`:

```python
offset = dt.timedelta(minutes=30)
df, location = pvlib.iotools.read_epw(weather_file)
df = set_annual_index(df, start_year, offset=offset, timezone=df.index.tzinfo)
```

pvlib's `read_epw` internally applies `hour - 1` when building the DatetimeIndex
(`pvlib/iotools/epw.py:305`), converting hour-ending rows to hour-beginning timestamps:
EPW `hour=1` → timestamp `Jan 1 00:00`. OCHRE then applies `+30 min` via `set_annual_index`,
advancing every timestamp: EPW `hour=1` → `00:30`, EPW `hour=12` → `11:30`.

At OCHRE `current_time = T`, the resampled pandas schedule lookup resolves T through the
shifted index. OCHRE's sim clock starts at a naive local datetime; after resampling to
the target resolution the first schedule row is positioned at `start_time`.

### EPW convention — HARES

`crates/hares-io/src/epw.rs:285–287` sets `midpoint_offset_secs: 1800`.

`crates/hares-core/src/environment.rs:622–625`:

```rust
let shifted = (seconds_into_year + year_secs - meta.midpoint_offset_secs as u64) % year_secs;
(shifted / step_secs as u64) as usize
```

HARES subtracts 1800 s from the sim wall-clock time before dividing into an array index.
For a step at time `T`, this resolves to the array index of the EPW row whose midpoint is `T`.

### Algebraic equivalence

For the equivalence to hold, the sim start time must be aligned to an EPW midpoint (`:30`
for hourly data). For `start_time = 00:30`:

```
seconds_into_year = 1800
shifted = (1800 + year_secs - 1800) % year_secs = 0
index = 0  → EPW row 0 (hour=1, 00:00–01:00, midpoint 00:30) ✓
```

OCHRE at `current_time = 00:30` reads the row that was shifted to timestamp `00:30`
(EPW hour=1). Both tools read the same row. The mechanisms are dual: OCHRE shifts
timestamps forward; HARES shifts sim-time backward.

### F1 — Severity: Medium — Half-step misalignment at whole-hour sim starts
**File:** `crates/hares-core/src/environment.rs:603–625`

For a sim start at a whole-hour boundary (e.g., `13:00:00 LST`):

- HARES: `seconds_into_year = 13×3600 = 46800`. `shifted = 46800 - 1800 = 45000`.
  `index = 45000 / 3600 = 12`. Reads EPW row 12 → hour=13, covering 12:00–13:00, midpoint 12:30.
- OCHRE at `current_time = 13:00`: after resampling, 13:00 falls between EPW-shifted rows
  at 12:30 (hour=13) and 13:30 (hour=14). OCHRE interpolates at 13:00 exactly.

HARES step-0 weather at `13:00:00` represents the 12:00–13:00 average (midpoint 12:30),
while OCHRE's step-0 weather is interpolated at 13:00. This is a systematic 30-minute
lag on EPW row selection for sims starting at whole-hour boundaries.

The parity test in `tests/python/test_ochre_parity.py:28` uses `START_LOCAL = dt.datetime(2019, 5, 5, 13, 0)` — a whole-hour start — hitting this condition.

**Fix:** Document in the user-facing API (and in `EnvironmentManager::new` doc) that EPW-backed
simulations should start at `:30` past the hour to align with EPW period midpoints, or change
the HARES convention so that sim time `T` represents the *start* of a period and step-0
reads the EPW row whose midpoint is `T + step_secs/2`, removing the dependency on
start-time alignment. The latter would be consistent with OCHRE's behaviour and require
changing `compute_annual_offset` to add `step_secs/2 - midpoint_offset_secs` instead of
subtracting `midpoint_offset_secs`.

### F2 — Severity: Low — Misleading test comment at line 1268
**File:** `crates/hares-core/src/environment.rs:1268`

The docstring reads:
```
/// Forward +30min shift: (125*86400 + 12*3600 + 1800) / 3600 = 3012.
```
But `weather_series()` has `midpoint_offset_secs: 0`, so the `+1800` term is not applied.
The expected value 3012 equals `(125*86400 + 12*3600) / 3600` with no offset. The comment
falsely implies the EPW midpoint shift is being tested. Fix: correct the comment to
reflect the zero-offset fixture, or change the fixture to `midpoint_offset_secs: 1800`
and adjust the expected value accordingly.

### F3 — Severity: Low — No unit test for `midpoint_offset_secs = 1800` in `EnvironmentManager`
**File:** `crates/hares-core/src/environment.rs` (test module)

The only location setting `midpoint_offset_secs: 1800` is `crates/hares-io/src/epw.rs:287`.
All `EnvironmentManager` unit tests use a helper (`weather_series()`) with
`midpoint_offset_secs: 0`. `compute_annual_offset` is exercised only for the zero-offset
path in unit tests. Integration/parity tests load real EPW files and cover this path
implicitly, but do not provide an isolated failing-assertion for a regression.

Required test cases (all using `midpoint_offset_secs: 1800`, `step_secs: 3600`):

1. `start_time = Jan 1 00:30` → index 0 (EPW hour=1, 00:00–01:00 midpoint)
2. `start_time = Jan 1 01:30` → index 1 (EPW hour=2, 01:00–02:00 midpoint)
3. `start_time = Jan 1 00:00` → index 8759 (wraps to last hour of year — documents the
   whole-hour misalignment from F1)

These tests are feasible to write against `compute_annual_offset` directly without a full
`EnvironmentManager`, similar to the existing tests at lines 1270–1340.

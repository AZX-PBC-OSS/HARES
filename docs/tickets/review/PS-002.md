## Background/Context

`ControlSignal` has both typed static constructors (`ControlSignal.power_setpoint(kw=5)`)
and a dict-based `from_dict({"type": "PowerSetpoint", "kw": 5})`. The dict path is
brittle — wrong type strings, missing keys, and wrong value types are runtime errors
at best, silent bugs at worst.

---

## Findings

### F1 — MEDIUM: `EventDelay` has no static constructor on `PyControlSignal`

**File:** `crates/hares-python/src/py_control.rs`

`ControlSignal::EventDelay { delay_s }` is handled in `from_dict` (line 379) and in
`to_dict` (line 596), but there is no `PyControlSignal::event_delay(delay_s: f64)`
static constructor. The only way a Python caller can construct this signal is through
`from_dict`. The typed constructor path is the safer, documented API; `EventDelay` being
absent is an inconsistency that will confuse users and forces them onto the weaker path.

**Fix:** Add a `#[staticmethod] fn event_delay(delay_s: f64) -> Self` constructor and
a matching stub in `_hares.pyi`.

---

### F2 — MEDIUM: No numeric range validation anywhere — typed constructors or `from_dict`

**Files:** `crates/hares-python/src/py_control.rs`, `crates/hares-types/src/control_signal.rs`

Every f64 field is accepted without bounds checking at the Python boundary. Examples
of values that are physically nonsensical and will silently corrupt simulation state:

- `ControlSignal.load_fraction(fraction=-0.5)` — negative fractions are meaningless
- `ControlSignal.load_fraction(fraction=1.5)` — > 1.0 is meaningless
- `ControlSignal.soc_target(target=2.0)` — SOC > 1.0 is nonsensical
- `ControlSignal.duty_cycle(on_fraction=-0.1)` — negative duty cycle is nonsensical
- `ControlSignal.humidity_setpoint(target_rh=1.5)` — RH > 1.0 is unphysical
- `ControlSignal.ev_set_ready_by(departure_hour=25.0, target_soc=1.5)` — both out of range

None of these raise `PyValueError`. They pass through to the simulation engine, which
may clamp, saturate, or produce NaN/inf-contaminated output without surfacing the
input error to the caller.

The same gap exists in the `from_dict` path — `dict_required` extracts the value as
`f64` with no range check.

**Fix:** Add range validation in each static constructor and in the `from_dict` match
arm for the relevant variants. A helper `fn check_unit_interval(val: f64, field: &str) -> PyResult<()>`
and `fn check_non_negative(val: f64, field: &str) -> PyResult<()>` can keep the
implementation DRY.

### F3 — LOW: `from_dict` error message loses the original extraction error

**File:** `crates/hares-python/src/py_control.rs`, lines 619, 633

`dict_required` and `dict_optional` discard the underlying `FromPyObject` extraction
error with `map_err(|_| ...)`. If a user passes `{"type": "PowerSetpoint", "active_power_kw": "five"}`,
they receive:

```
ValueError: invalid value for `active_power_kw`
```

The actual pyo3 extraction error (e.g., "expected float, got str") is lost. This makes
debugging harder, especially for the HELICS path where the JSON payload comes from an
external federate.

**Fix:** Chain the original error:
```rust
value.extract::<T>().map_err(|e| {
    PyValueError::new_err(format!("invalid value for `{key}`: {e}"))
})
```

### F4 — LOW: Typo in unknown `type` key produces a clear error, but the error message uses backtick quoting inconsistently

**File:** `crates/hares-python/src/py_control.rs`, line 384

```rust
return Err(PyValueError::new_err(format!(
    "unsupported control signal type `{kind}`"
)));
```

This is adequate for typo detection (`"PowerSetpint"` → clear error). No silent
mismatch is possible here. The quoting style (backticks in one place, no quoting for
field names in others) is a minor inconsistency but does not cause bugs.

---

### F5 — LOW: `PySignal` (actor dispatch path) is a strict subset of `ControlSignal` variants

**File:** `crates/hares-python/src/py_actor.rs`, lines 201–250

`PySignal` covers only 13 of the 27 `ControlSignal` variants. Missing from `PySignal`
(and therefore from `DispatchRequest`):

- `HumiditySetpoint`
- `GridConnect`
- `SelfConsumption`
- `PowerFactorSetpoint`
- `ReactiveSetpoint`
- `InverterPriorityMode`
- `CurtailmentPercent`
- `ProtocolNative`
- `IdealCapacityModeOverride`
- `EvAwayCharge`
- `EventDelay`

This means Python actors cannot dispatch those signals via `DispatchRequest`. Whether
this is intentional (actor subset) or a gap is not documented. The missing variants
should either be added or explicitly documented as out-of-scope for the actor dispatch
path.

Additionally, `PySignal::DutyCycle` drops the `component` field (mapped to `None` at
line 350), making split duty cycle control inaccessible from the actor path even though
`PyControlSignal.duty_cycle()` supports it.

### F6 — LOW: `from_dict` for `EvPlugIn` accepts only string state, not `PyEvConnectionState` enum

**File:** `crates/hares-python/src/py_control.rs`, lines 362–368

```rust
"EvPlugIn" => {
    let state_str: String = dict_required(d, "state")?;
    let state = state_str
        .parse::<hares_types::EvConnectionState>()
        .map_err(PyValueError::new_err)?;
    ControlSignal::EvPlugIn { state }
}
```

All other enum-valued fields in `from_dict` accept either a string or the Python enum
object (via `parse_*_or_enum` helpers). `EvPlugIn` accepts only a string. Passing
`{"type": "EvPlugIn", "state": EvConnectionState.HomePluggedIn}` will fail with a
confusing extraction error.

**Fix:** Use a `parse_ev_connection_state_or_enum` helper consistent with the pattern
used for `ModeOverride`, `DemandResponse`, `DutyCycle`, and `InverterPriorityMode`.

---

## Round-trip Correctness

`to_dict` / `from_dict` is functionally symmetric for all implemented variants except
for the gap in F6. The `ThermalSetpoint` optional fields are serialized only when
`Some`, and deserialized with `dict_optional`, which correctly returns `None` for
absent keys. No data loss found in the round-trip for present variants.

---

## Assessment: Is `from_dict` needed?

Yes, for the HELICS integration layer. Both `python/ochre_next/helics/dwelling.py:160`
and `python/ochre_next/helics/fleet.py:177` parse control messages from an external
network federate as JSON, then call `ControlSignal.from_dict(signal_body)`. The dict
path is the only ergonomic API for this use case. It should be kept but hardened
(F2, F3, F6).

## Recommended Tests

1. **Range validation tests** (once F2 is fixed): unit tests asserting `PyValueError`
   is raised for each out-of-range constructor call. One test per validated field
   per variant. Keep in `crates/hares-python/tests/` or as Python tests in
   `tests/python/`.

2. **`from_dict` round-trip test**: for every variant, verify
   `ControlSignal.from_dict(signal.to_dict()) == original` via `__repr__` or a
   structural comparison. This should live in `tests/python/` as a parametrized pytest.

3. **`from_dict` error path tests**: verify that unknown `type` strings, missing
   required keys, and wrong-type values all raise `ValueError` (not panic, not silent
   wrong state). HELICS resilience depends on this.

4. **`EvPlugIn` enum object round-trip** (once F6 is fixed): verify that
   `from_dict({"type": "EvPlugIn", "state": EvConnectionState.HomePluggedIn})` works.

## Background/Context

Natural ventilation (window opening for free cooling) was noted in TS-006 as existing
but was never audited. The trigger logic, airflow model, and interaction with mechanical
ventilation need review.

## Investigation Instructions

1. How is natural ventilation triggered? Temperature threshold? Occupancy? Schedule?
2. What airflow model? Single-sided? Cross-ventilation? Wind-driven?
3. How does it interact with mechanical ventilation and infiltration?
4. Compare with OCHRE

## Architecture Summary

Natural ventilation in HARES is implemented across three layers:

- **Physics**: `crates/hares-physics/src/infiltration.rs:210` — `natural_ventilation_flow_m3_s()`
- **Envelope**: `crates/hares-envelope/src/thermal_solver/infiltration.rs:130` — called inside `apply_infiltration_and_ventilation()` per-zone step
- **Builder**: `crates/hares-core/src/dwelling/solver_builder.rs:928` — `NaturalVentilationConfig` populated from HPXML window data

The `crates/hares-equipment/src/ventilation.rs` file is mechanical ventilation only (HRV/ERV/exhaust fan). It has no natural ventilation code.

### Trigger Logic

Flow is computed every timestep and is non-zero only when all three conditions hold (OCHRE parity):

1. `T_zone > T_outdoor` (stack buoyancy — outdoor must be cooler)
2. `T_zone > t_base_c` (comfort gate — no benefit unless zone is above comfort base; default 22.778 °C = 73 °F)
3. `outdoor_humidity_ratio < 0.0115 kg/kg` (BA HSP humidity threshold)

No occupancy gating. OCHRE has a `# TODO: add occupancy logic` comment at line 609 but never implements it; HARES matches this omission.

`t_base_c` is hardcoded to `DEFAULT_T_BASE_C = 22.778`. OCHRE dynamically derives it as `(heating_setpoint + cooling_setpoint) / 2` when both setpoints are known, falling back to the same constant when not. HARES never substitutes the per-dwelling setpoint average.

### Airflow Model

ELA (Effective Leakage Area) stack/wind formula — identical to the infiltration driver:

```
A_eff      = open_area_m2 × 0.6 × 10000 cm²/m²
q_driver   = stack_coeff × |ΔT| + wind_coeff × v²
adj        = clamp((T_zone − t_base) / (T_zone − T_out), 0, 1)
q_nat      = min(A_eff × adj × √q_driver / 1000, 20 ACH cap)
```

This matches OCHRE `_natural_ventilation` exactly, line-for-line.

### Interaction with Mechanical Ventilation and Infiltration

`apply_infiltration_and_ventilation()` (`infiltration.rs:62`) combines all three flows using the OCHRE quadrature/balanced logic:

- `total_nat_flow = q_inf + q_nat`
- Balanced ventilation: `sensible_flow = total_nat + forced × (1 − sens_eff)`
- Unbalanced: `sensible_flow = √(total_nat² + forced²)` with proportional nat-flow scaling

This is a faithful port of OCHRE `_ventilation_flows_and_gain` (lines 59–87).

## Findings

### F1 — WRONG ELA COEFFICIENTS USED FOR NATURAL VENTILATION (severity: high)

**File**: `crates/hares-core/src/dwelling/solver_builder.rs:959`

HARES uses `attic_ela_coefficients(1.5, bldg_h)` to obtain the stack/wind coefficients for natural ventilation. `attic_ela_coefficients` is documented as computing attic zone leakage coefficients using `hor_lk_frac = 0.75` (ceiling-dominated, Walker-Wilson 1998 Table 2). This is physically wrong for window-driven natural ventilation through the conditioned zone.

OCHRE reads `nat_vent_stack_coeff` and `nat_vent_wind_coeff` directly from the indoor zone's own `zone_args` dict using the keys `"ELA stack coefficient (L/s/cm^4/K)"` and `"ELA wind coefficient (L/s/cm^4/(m/s))"` (Envelope.py lines 513–514). These are the indoor zone's infiltration ELA coefficients, not attic coefficients.

HARES uses different `hor_lk_frac` (0.75 attic value) and a derived height parameter, producing different coefficient values than the indoor zone ELA coefficients would. The error magnitude depends on building geometry but can be significant (ELA coefficients vary by roughly 2× across different `hor_lk_frac` values per Walker-Wilson Table 2).

**Fix**: Look up the conditioned zone's ELA stack/wind coefficients from the already-computed infiltration config, and reuse them for `NaturalVentilationConfig.stack_coeff` and `wind_coeff`. Do not call `attic_ela_coefficients` for this purpose.

### F2 — OPEN-AREA FORMULA DOUBLE-APPLIES FRACTION_OPERABLE WHEN DEFAULT (severity: medium)

**File**: `crates/hares-core/src/dwelling/solver_builder.rs:947,950`

HARES computes:
```
total_operable_area = Σ(window.area_m2 × window.fraction_operable)
open_area = total_operable_area × 0.5 × 0.2
```

OCHRE computes (Envelope.py line 562–564):
```python
window_area = sum(s.area for s in surfaces if s.boundary_name == "Window")
open_window_area = window_area * 0.67 * 0.5 * 0.2
```

OCHRE multiplies **total window area** by a fixed 0.67 (default operable fraction). HARES multiplies each window's area by its parsed `fraction_operable` (defaulting to 0.67 from HPXML), then multiplies by 0.5 × 0.2.

When `fraction_operable = 0.67` (the default in both HPXML parser and OCHRE), the formulas produce the same number. When the HPXML file explicitly provides `FractionOperable`, HARES correctly uses the actual value while OCHRE always uses 0.67 — so HARES is actually _more correct_ for explicit HPXML data.

However, the inline comment at line 930 reads `× 0.5 (open fraction) × 0.2 (flow fraction)`, omitting the operable fraction factor. The comment should make explicit that `fraction_operable` encodes the 0.67 factor. This is a documentation defect, not a code defect for the nominal case.

**Fix**: Update the comment to read `Σ(window_area × fraction_operable [≈0.67]) × 0.5 (open fraction) × 0.2 (flow fraction)` to avoid confusion.

### F3 — T_BASE NOT DERIVED FROM HVAC SETPOINTS (severity: low)

**File**: `crates/hares-core/src/dwelling/solver_builder.rs:964`

`t_base_c` is hardcoded to `NaturalVentilationConfig::DEFAULT_T_BASE_C = 22.778 °C`. OCHRE derives it dynamically each timestep as `(heating_setpoint + cooling_setpoint) / 2` when both setpoints are present (Envelope.py lines 1227–1230). In practice, this means a dwelling with a 20 °C heating setpoint and 24 °C cooling setpoint would use 22 °C, very close to the default.

The impact is small for typical residential setpoints (±1–2 °C from the 22.778 default) but it means HARES ignores DR events or setpoint shifts that would widen or narrow the nat-vent window.

**Fix**: Pass the current heating/cooling setpoint midpoint into `NaturalVentilationConfig` at each step, or as a mutable field updated by the thermostat actor before the envelope step. This is an enhancement, not a regression relative to the constant default.

---

### F4 — SENSIBLE GAIN H_LIMIT CLAMP NOT IMPLEMENTED (severity: low)

**File**: `crates/hares-envelope/src/thermal_solver/infiltration.rs`

OCHRE applies an `h_limit` clamp to the total infiltration+ventilation sensible gain: it solves for the maximum gain that would drive the zone to outdoor temperature in one timestep, and clips the sensible gain to that limit (Envelope.py lines 1217–1236, `_ventilation_flows_and_gain` lines 83–85). This prevents numerical overshoot when the infiltration load is large relative to zone thermal mass.

HARES does not implement this clamp. Instead it uses a semi-implicit treatment (`h_inf` enters the A-matrix diagonal, `infiltration.rs:209`) which achieves unconditional stability by a different mechanism. The semi-implicit approach is numerically superior and the h_limit clamp is a legacy compensation for OCHRE's explicit formulation, so this is not a regression. No fix required — documenting for completeness.

---

### F5 — NATURAL VENTILATION APPLIED TO ALL ZONES, OCHRE APPLIES TO INDOOR ONLY (severity: medium)

**File**: `crates/hares-envelope/src/thermal_solver/infiltration.rs:130`

The `apply_infiltration_and_ventilation()` loop iterates over all zones and applies `config.natural_ventilation` to every zone for which it is set. In the builder (`solver_builder.rs`), a single `NaturalVentilationConfig` is placed on `thermal_cfg.natural_ventilation` (a single-slot field), but it is then looked up for every zone inside the loop.

OCHRE explicitly restricts natural ventilation to the Indoor zone only (Envelope.py line 603: `if self.name == "Indoor":`). If a multi-zone building has, say, an attic zone, HARES would apply nat-vent flow to that zone using the conditioned zone's open-area parameters and the attic's temperature — producing physically incorrect results.

**Fix**: Gate the nat-vent call on `zone.id == config.indoor_zone_id`, matching OCHRE's indoor-only restriction. Add a test with a two-zone configuration.

## Recommended Tests

1. **Coefficient regression**: With a known single-zone HPXML and known outdoor conditions, assert that `NaturalVentilationConfig.stack_coeff` and `wind_coeff` match the indoor zone's infiltration ELA coefficients, not the attic ELA coefficients. (Blocked by F1 fix.)
2. **t_base setpoint variation**: Confirm that with a below-base zone temperature, nat-vent flow is zero regardless of outdoor temperature.
3. **Multi-zone gate**: Two-zone builder test asserting that nat-vent is only applied to the conditioned zone. (Blocked by F5 fix.)
4. **Open-area fraction**: Snapshot test asserting that `open_area_m2` equals `total_window_area × 0.67 × 0.5 × 0.2` when no explicit FractionOperable is set.

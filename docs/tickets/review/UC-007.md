## Background/Context

Windows have complex properties: U-factor (thermal), SHGC (solar heat gain), interior
and exterior shading fractions, frame fraction. The ENVELOPE tickets found that
OCHRE's window U-factor handling had a bug (treating imperial as SI). HARES should
handle windows correctly — this ticket verifies all window-related fields.

## Investigation Instructions

1. **Read `building.rs` window parsing:**
   - `UFactor` — BTU/hr·ft²·°F → W/m²·K? What factor? (Should be ×5.678)
   - `SHGC` — dimensionless, no conversion — verified?
   - `InteriorShading/SummerShadingCoefficient` and `WinterShadingCoefficient` —
     how are these used? Are they fractions (0–1)?
   - `ExteriorShading` — same questions
   - `FractionOperable` — used anywhere?
   - `GlassType`, `GasFill` — stored but used?

2. **Check EnergyPlus-style decomposition:**
   - Does HARES decompose window U-factor into center-of-glass and frame components?
   - ENV-003 mentions "Window U-factor EnergyPlus decomposition" — is this implemented?

3. **Compare with OCHRE window handling:**
   - What fields does OCHRE extract? Any it uses that HARES doesn't?

4. **Write findings** with per-field table.


## Findings

### Q1 — UFactor conversion (BTU/hr·ft²·°F → W/m²·K)

CORRECT. `building.rs:830` routes `UFactor` through `ValueKind::UValue` →
`convert_u_to_w_m2_k` → `conv::u_value_ip_to_si` (`hares-physics/src/units.rs:115`).
That function uses `uom`'s `btu_it_per_hour_square_foot_degree_fahrenheit` →
`watt_per_square_meter_kelvin`, which resolves to ×5.6783 (exact BTU-IT definition),
not the rounded ×5.678 OCHRE uses. The unit test at `units.rs:256` confirms agreement
with the old constant to 2 decimal places. Units attribute is handled: if absent, debug
log is emitted and BTU/hr·ft²·°F is assumed (safe default for HPXML). The in-test
fixture (`building.rs:2115`) asserts `0.31 × 5.6783 ≈ 1.760 W/m²·K` — confirmed.

**No defect.**

### Q2 — SHGC conversion

CORRECT. `building.rs:831` reads `SHGC` as raw `f64` with no conversion.
SHGC is dimensionless. OCHRE also passes it through unchanged (`hpxml.py:214`).

**No defect.**

### Q3 — InteriorShading fractions

CORRECT with minor gap. `building.rs:836–851`:
- `SummerShadingCoefficient` → `interior_shading_fraction` (clamped 0–1, default 0.70
  when `InteriorShading` node is present but coefficient missing; 1.0 when node is absent).
- `WinterShadingCoefficient` → `winter_shading_fraction` (clamped 0–1, default 0.85
  when node present but coefficient missing; 1.0 when absent).
- Applied downstream at `solver_builder.rs:291–292`:
  `shgc_summer = base_shgc × interior_shading_fraction`,
  `shgc_winter = base_shgc × winter_shading_fraction`.

OCHRE only uses `SummerShadingCoefficient` (`hpxml.py:215`) with no seasonal split.
HARES is **more correct** here.

Default 0.85 for `WinterShadingCoefficient` when node present but value absent is
justified by ANSI/RESNET/ICC 301-2019 Table 4.2.2(1) (0.70 summer / 0.85 winter).

**No defect.**

### Q4 — ExteriorShading — CONFIRMED GAP

`ExteriorShading` is not parsed anywhere in `building.rs`. The `Window` struct has no
`exterior_shading_fraction` field. OCHRE also does not parse `ExteriorShading`
(`hpxml.py:215` — only `InteriorShading` is extracted), so parity with OCHRE is
maintained, but HPXML files produced by OpenStudio/EnergyPlus (e.g., ResStock) routinely
carry exterior shading coefficients. The sample file at
`vendors/OCHRE/test/OS-HPXML Sample Files/base-enclosure-windows-shading.xml:270–312`
demonstrates windows with both interior and exterior shading on the same window.

Without exterior shading, HARES will overestimate solar gain for any window that has
exterior obstructions (overhangs, fins, neighboring structures encoded as exterior shading
coefficients). Effective SHGC should be:

  `effective_shgc = base_shgc × exterior_shading × interior_shading`

**Severity: MEDIUM.** Affects all ResStock/BEopt buildings with exterior shading, which
is common in the default OCHRE input files. The `Window` struct needs
`exterior_shading_summer: f64` and `exterior_shading_winter: f64` fields, and
`solver_builder.rs` must multiply them in.

### Q5 — FractionOperable, GlassType, GasFill

- **FractionOperable**: parsed (`building.rs:854–858`), stored in `Window.fraction_operable`,
  used at `solver_builder.rs:930–947` for natural-ventilation infiltration flow. Correct.
- **GlassType**: not parsed, not stored, silently dropped. OCHRE also ignores it. Used in
  EnergyPlus to select optical data tables — not required when SHGC/U-factor are given
  directly. Acceptable to omit.
- **GasFill**: not parsed, not stored, silently dropped. OCHRE also ignores it. Used in
  EnergyPlus for detailed layer-by-layer conduction — irrelevant when whole-window
  U-factor is provided. Acceptable to omit.
- **FrameType**: parsed (`building.rs:860`) as `Option<String>`, stored in `Window.frame_type`,
  but never consumed downstream. See Q6.

### Q6 — EnergyPlus center-of-glass + frame decomposition

NOT implemented. The whole-window U-factor from HPXML is used directly; there is no
decomposition into center-of-glass and frame conductances. `frame_type` is parsed but
ignored by all envelope-solver code (confirmed by `grep frame_type crates/hares-envelope`
returns no matches). In EnergyPlus, the frame and divider conductance can meaningfully
differ from center-of-glass — particularly for metal frames — and the frame U-factor is
typically 20–40% higher than center-of-glass.

HPXML provides `AssemblyEffectiveRValue` (whole-window, area-weighted including frame)
or separate `UFactor` for the glazing unit. When `UFactor` is given, HPXML intends it as
the NFRC whole-window U-factor, which already includes the frame weighting. The OCHRE
reference does not decompose either.

The ENVELOPE-INDEX.md ticket ENV-003 ("Window U-factor EnergyPlus decomposition") is
referenced in the background but has not been implemented. The practical impact depends
on whether input files supply NFRC whole-window U-factors (common) or only center-of-glass
values (rare in ResStock). Since ResStock uses NFRC-rated whole-window values and OCHRE
does not decompose, the current approach is parityequivalent to OCHRE.

**Severity: LOW for ResStock parity; MEDIUM if HPXML files with FrameType-based
decomposition are needed.** The `frame_type` field sitting unused without a downstream
consumer is dead state — it should either be used or removed.

**Dead field defect:** `Window.frame_type: Option<String>` is parsed but never read by
any consumer (`hares-envelope`, `hares-core`). Either implement frame-conductance
adjustment using it, or remove the field to avoid misleading callers.

### Q7 — Azimuth convention

CONSISTENT. Both HPXML and HARES use compass degrees with 0 = North, 180 = South.
`hares-physics/src/solar.rs:137–140` converts the raw atan2 south-referenced result to
north-referenced by adding π before normalising to [0, 2π). The surface azimuth passed
to `perez_tilted_irradiance` comes from `boundary.azimuth_deg` which originates from
HPXML `Azimuth` without remapping.

OCHRE also uses the same compass convention internally and passes `Azimuth (deg)` from
HPXML directly to pvlib (`envelope.py:58`). pvlib's `aoi()` and `get_total_irradiance()`
use north=0/south=180 for surface azimuth, matching the HARES solar model.

Note: OCHRE's PV code (`PV.py:58`) transforms `azimuth → (azimuth + 180) % 360` when
calling SAM, because SAM's convention is south=180 (same as north-referenced compass).
This transformation is a no-op identity for compass azimuths and does not indicate a
convention difference.

**No defect.**

### Defects to fix

**DEF-1 (Medium) — ExteriorShading not parsed.**
File: `crates/hares-io/src/hpxml/building.rs`
Add `exterior_shading_summer: f64` and `exterior_shading_winter: f64` to the `Window`
struct (defaults 1.0). Parse `window.child("ExteriorShading")` using the same pattern as
`InteriorShading` (summer default 1.0, winter default 1.0 when node absent; 0.70 / 0.85
when node present but value absent). Multiply into effective SHGC in `solver_builder.rs`.

**DEF-2 (Low) — `Window.frame_type` is dead state.**
File: `crates/hares-io/src/hpxml/building.rs`, `crates/hares-core/src/dwelling/solver_builder.rs`
Either: (a) remove `frame_type` from the struct and the parse call, or (b) implement a
frame-conductance correction using it (out of scope for current parity target). The field
as-is misleads callers into thinking frame type affects the simulation.

## Recommended Tests

1. **`window_exterior_shading_applied_to_effective_shgc`** — once DEF-1 is fixed, parse a
   window XML with `ExteriorShading/SummerShadingCoefficient=0.5` and
   `InteriorShading/SummerShadingCoefficient=0.7`, `SHGC=0.40`. Assert that
   `exterior_shading_summer == 0.5`, and that the effective summer SHGC used in the solver
   is `0.40 × 0.5 × 0.7 = 0.14`.

2. **`window_exterior_shading_absent_defaults_to_1`** — parse a window with no
   `ExteriorShading` node and assert `exterior_shading_summer == 1.0`,
   `exterior_shading_winter == 1.0` (solar gain unmodified).

3. **`window_exterior_shading_node_present_but_no_summer_coefficient_defaults_1`** — parse
   a window with an empty `<ExteriorShading>` block, assert `exterior_shading_summer == 1.0`
   (different default than InteriorShading's 0.70; exterior shading absent = unobstructed).

4. **`window_u_factor_conversion_0_31`** — existing test at `building.rs:2115` covers this.
   Verify it remains passing post-DEF-1 changes.

5. **`window_combined_shading_components_multiply`** — integration test that places a window
   in a synthetic building with known `ExteriorShading`, `InteriorShading`, and `SHGC` values,
   steps the engine for one timestep with a known solar irradiance on that surface, and asserts
   that the transmitted solar gain into the conditioned zone equals
   `irradiance × area × SHGC × exterior_shading × interior_shading`. This is a physics
   correctness gate, not just a parsing test.

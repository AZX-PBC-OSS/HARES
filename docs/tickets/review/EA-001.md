## Background/Context

HARES has a dedicated `Ventilation` struct with HRV/ERV/exhaust modes, bypass logic,
and defrost. OCHRE treats ventilation as a `ScheduledLoad` subclass (pure electric
power; thermal effects handled entirely in the `Envelope` model). This ticket traces
the full runtime behavior comparison.

---

## OCHRE Ventilation Behavior

OCHRE's ventilation is split across two subsystems:

**1. Equipment layer (`ScheduledLoad`)**
- `Equipment/__init__.py:100`: `"Ventilation Fan": ScheduledLoad` — no custom subclass.
- `utils/schedule.py:473-475`: the schedule column `"Ventilation Fan (kW)"` is injected
  with a constant `power_w / 1000` derived from HPXML `FanPower` (or W/cfm default).
- Fan power is consumed but produces **no thermal output** from the equipment layer.
- The `ScheduledLoad.calculate_power_and_heat()` path calls `super().calculate_power_and_heat()`
  which adds electrical heat to the zone via a convective/radiative gain fraction — but per
  `resolve_loads.rs:618` the gain fractions for `"Ventilation Fan"` are `(1.00, 0.00)`,
  meaning OCHRE does put fan heat dissipation into the zone as internal gain.

**2. Envelope layer (`Models/Envelope.py`)**
- `Envelope.py:498-507`: the Indoor zone stores `forced_vent_flow`, `balanced_ventilation`,
  `sens_recovery_eff`, `lat_recovery_eff`.
- Recovery efficiencies come from HPXML `SensibleRecoveryEfficiency` and
  `TotalRecoveryEfficiency - SensibleRecoveryEfficiency` (`hpxml.py:560-562`).
- `Envelope.py:59-87` (`_ventilation_flows_and_gain`): at each timestep, forced ventilation
  flow is combined with infiltration and natural ventilation to produce effective sensible
  and latent flows. Recovery efficiency directly reduces the effective forced-vent flow:
  ```
  balanced:
    sensible_flow = total_nat_flow + forced_vent_flow * (1 - sens_recovery_eff)
    latent_flow   = total_nat_flow + forced_vent_flow * (1 - lat_recovery_eff)
  unbalanced:
    sensible_flow = sqrt(total_nat² + forced²)   # quadrature
  ```
- The resulting sensible/latent gains drive the zone RC network directly — not via the
  equipment port layer.
- `Envelope.py:1225-1226`: `vent_cfm` comes from the schedule key `"Ventilation Rate (cfm)"`,
  injected per `schedule.py:475`.
- `hpxml.py:1622`: `assert vent_fan.get("HoursInOperation", 24) == 24` — OCHRE hard-asserts
  the fan must operate 24 h/day and **does not implement partial-hour operation**.

**OCHRE has no independent HRV/ERV physics object.** Heat/moisture recovery is
handled by a flow-reduction coefficient in the infiltration function of the
Envelope model. Fan electrical power is a constant schedule.

## HARES Ventilation Behavior

**Equipment layer (`crates/hares-equipment/src/ventilation.rs`)**

Each timestep `step()`:
1. Checks `mode != Off && dr_level != GridEmergency` to determine `is_running`.
2. Gets `schedule_frac` from `ScheduleSource` (currently only `Constant`).
3. Scales both `flow_rate_m3_s` and `fan_power_w` by `schedule_frac`.
4. Computes `eff_s` and `eff_l` via bypass/defrost logic.
5. Calculates supply air: `t_supply = t_out + eff_s*(t_in - t_out)`.
6. Derives `q_sensible_w = m_dot * Cp * (t_supply - t_indoor)` and
   `q_latent_w = m_dot * H_vap * (w_supply - w_indoor)`.
7. Writes `PortContribution::Electrical` (fan power) and `PortContribution::Thermal`
   with `ThermalCategory::InternalGain` to the zone.

**Envelope layer (`crates/hares-envelope/src/thermal_solver/`)**

`infiltration.rs:apply_infiltration_and_ventilation()` independently computes forced
ventilation loads from `config.ventilation_flow_m3_s` and `config.ventilation.*`, using
the same OCHRE-parity flow-reduction formula. It writes its results via `InfiltrationCoupling`
structs, which the solver adds to the zone energy balance through the semi-implicit A-matrix.

## Findings

### CRITICAL — F1: Double-accounting of forced ventilation sensible/latent load

**Severity: Critical (energy balance error)**

The `Ventilation` equipment computes `q_sensible_w` and pushes it via
`PortContribution::Thermal { category: InternalGain }`. This gain is consumed by
`thermal_solver/ports.rs:apply_port_sensible_inputs()` which adds it directly to the
zone input vector `u`.

At the same time, `apply_infiltration_and_ventilation()` in `infiltration.rs` independently
computes the same forced ventilation heat load from `config.ventilation_flow_m3_s` and
adds it to the zone energy balance via the semi-implicit A-matrix coupling
(`h_inf_w_k` diagonal term + `t_forcing_c` forcing term in `mod.rs:348`).

Both paths run every timestep for the same fan. The ventilation sensible load is counted
twice. This would cause the zone to overcool in winter and overheat in summer relative to
the correct physics.

Evidence:
- `ventilation.rs:352-363`: Thermal port contribution with `sensible_gain_w = q_sensible_w`.
- `ports.rs:14-22`: All thermal ports (including InternalGain) added to `u[zone_sensible_input_idx]`.
- `infiltration.rs:207-224`: `q_forced_vent_w_scaled` computed from `forced_flow_m3_s`.
- `mod.rs:348-362`: Both the port inputs and the infiltration coupling are applied to the
  zone state before solving.

The correct architecture is: either the `Ventilation` equipment pushes its thermal gain
as an internal gain (fan motor heat only, ~1–5% of rated power) and the infiltration solver
owns the ventilation air exchange load; or the `Ventilation` equipment owns the full
thermal calculation and `ventilation_flow_m3_s` is not set in `ThermalSolverConfig`.
Currently both paths are active simultaneously.

---

### CRITICAL — F2: Flow rate key never reaches the Ventilation equipment

**Severity: Critical (equipment runs at hardcoded default 0.035 m³/s regardless of HPXML)**

The IO parser (`resolve_loads.rs:554`) inserts:
```
params["ventilation_rate_cfm"] = flow_cfm
```

The `solver_builder.rs:866` reads this key to configure `thermal_cfg.ventilation_flow_m3_s`
(correctly, for the infiltration path). However, the `Ventilation` equipment's `init()`
reads the key `KEY_FLOW_RATE_M3_S = "flow_rate_m3_s"` (`ventilation.rs:34, 217`). The
key `"ventilation_rate_cfm"` is never converted and inserted under `"flow_rate_m3_s"` into
the equipment params, and the `"flow_rate_m3_s"` key is never inserted by the IO parser.

Result: every `Ventilation` equipment instance ignores HPXML `RatedFlowRate` and silently
uses `DEFAULT_FLOW_RATE_M3_S = 0.035 m³/s` (~74 CFM). This is independent of whatever
the building XML specifies.

---

### CRITICAL — F3: Recovery efficiency keys never reach the Ventilation equipment

**Severity: Critical (HRV/ERV recovery is permanently zero from HPXML)**

`resolve_loads.rs:574-585` inserts:
```
params["sensible_recovery_efficiency"] = sensible_re
params["latent_recovery_efficiency"]   = latent_re
```

The `Ventilation` equipment's `init()` reads `KEY_SENSIBLE_EFFECTIVENESS = "sensible_effectiveness"`
(`ventilation.rs:35, 221`) and `KEY_LATENT_EFFECTIVENESS = "latent_effectiveness"` (`ventilation.rs:36, 225`).

Neither key `"sensible_recovery_efficiency"` nor `"latent_recovery_efficiency"` is ever
read by the equipment. The `init()` silently falls back to:
- `DEFAULT_SENSIBLE_EFFECTIVENESS = 0.70` for all HRV/ERV (hardcoded, not from HPXML)
- `DEFAULT_LATENT_EFFECTIVENESS = 0.0` for ERV (hardcoded, not from HPXML)

Note also that the recovery values used in the infiltration path (F1 above) correctly come
from the equipment spec params under `"sensible_recovery_efficiency"` / `"latent_recovery_efficiency"`
via `solver_builder.rs:873-883`. So even disregarding the double-accounting issue, the
infiltration solver's recovery and the equipment's recovery would be independent values
derived from different sources.

---

### HIGH — F4: Fan type never reaches the Ventilation equipment from HPXML

**Severity: High (all HPXML fans default to HRV behavior)**

`resolve_loads.rs:571` inserts `params["fan_type"] = fan_type_string` (e.g.,
`"exhaust only"`, `"energy recovery ventilator"`, `"heat recovery ventilator"`, `"balanced"`).

The `Ventilation::new()` constructor reads `config.get_str("ventilation_type")` (`ventilation.rs:114`).
The key `"fan_type"` is never mapped to `"ventilation_type"`. The equipment silently
defaults to `VentilationType::Hrv` for every fan type, including exhaust-only fans.

An exhaust-only fan that should have zero recovery effectiveness is instead modeled with
`DEFAULT_SENSIBLE_EFFECTIVENESS = 0.70` sensible recovery (blocked by the `ExhaustFan` guard
in `effective_sensible_effectiveness`, but only if the type were parsed correctly).

---

### HIGH — F5: HoursInOperation not implemented; OCHRE asserts 24 h/day

**Severity: High (operational schedule mismatch)**

OCHRE `hpxml.py:1622` hard-asserts `HoursInOperation == 24` — it cannot model fans that
run less than 24 h/day. HARES has a `ScheduleSource` mechanism that could model this, but
the IO parser (`resolve_loads.rs:542-595`) never reads or converts the HPXML
`<HoursInOperation>` element. The effective schedule is always `ScheduleSource::Constant(1.0)`
(24 h/day, 100%).

ASHRAE 62.2-2022 §4.1.3 allows intermittent ventilation at higher flow rates to meet the
same effective ventilation requirement. Many real HPXML files specify `HoursInOperation < 24`
paired with a proportionally higher `RatedFlowRate`. Without reading this field the
effective ventilation rate is overcounted by a factor of `24 / actual_hours`.

---

### MEDIUM — F6: Air density hardcoded at sea-level 20°C standard value

**Severity: Medium (systematic flow/heat error at altitude or extreme temperature)**

`ventilation.rs:54`: `const AIR_DENSITY_KG_M3: f64 = 1.2;` (sea level, 20 °C).

The infiltration solver in `infiltration.rs:75` correctly uses
`moist_air_density_kg_m3(p_pa, t_out, w_out)` from `hares_physics::air_properties`,
which accounts for pressure, temperature, and humidity. The `Ventilation` equipment
does not. At 1500 m elevation (Denver), air density is ~1.06 kg/m³, a 12% error in
computed heat and mass flows.

---

### MEDIUM — F7: Fan motor heat not added to supply air

**Severity: Medium (missing heat source)**

EnergyPlus HeatExchanger:AirToAir models fan motor heat gain as a fraction of fan power
added to the supply airstream. HARES models fan power purely as electrical consumption
(`PortContribution::Electrical`) with no heat dissipation into the zone.

OCHRE also does not model this correctly (it would come via the `ScheduledLoad` sensible
gain fraction). This is an area where HARES has not yet improved over OCHRE. The error is
relatively small (fan power is typically 25–100 W vs. hundreds of watts of ventilation
load) but is non-zero.

---

### MEDIUM — F8: Bypass logic does not gate on humidity

**Severity: Medium (free cooling suppressed when outdoor is humid)**

`ventilation.rs:175`: bypass is triggered when `t_outdoor >= 18°C AND t_outdoor <= 24°C`.
No humidity check. ASHRAE 62.2 and EnergyPlus models suppress bypass (i.e., keep recovery
active) when the outdoor humidity ratio exceeds ~0.0115 kg/kg (the Building America HSP
threshold), to avoid importing excess moisture in humid climates. The natural ventilation
logic in `infiltration.rs:139-146` uses `max_outdoor_humidity_ratio` for exactly this
purpose; the Ventilation equipment's bypass has no equivalent.

---

### LOW — F9: `DEFAULT_DEFROST_EFFECTIVENESS_FRACTION = 0.5` is unsourced

**Severity: Low (accuracy)**

`ventilation.rs:51`: `const DEFAULT_DEFROST_EFFECTIVENESS_FRACTION: f64 = 0.5;`

No reference to ASHRAE, HVI, or EnergyPlus HRV defrost model. The EnergyPlus
HeatExchanger:AirToAir:SensibleAndLatent uses a frost-control option based on supply-side
temperature rather than a simple fractional derating. The current value is not necessarily
wrong but lacks a cited basis and may not match any real HRV datasheet.

---

### LOW — F10: `bypass_active` telemetry false-positive for ExhaustFan

**Severity: Low (incorrect telemetry)**

`ventilation.rs:322-324`:
```rust
let bypass_active = eff_s == 0.0
    && t_outdoor_c >= self.bypass_temp_min_c
    && t_outdoor_c <= self.bypass_temp_max_c;
```

For `VentilationType::ExhaustFan`, `eff_s` is always 0.0 (by `effective_sensible_effectiveness`).
When outdoor temperature happens to fall in `[18°C, 24°C]`, `bypass_active` will be `true`
even though exhaust fans have no bypass concept. This is a telemetry-only error (bypass
mode does not change behavior for exhaust fans since effectiveness is already 0) but
produces misleading output.

## Architecture Summary

The fundamental architecture problem (F1) is that the ventilation subsystem has been
implemented twice:

1. `Ventilation` equipment: computes and pushes thermal port contributions each timestep.
2. `infiltration.rs` + `solver_builder.rs`: independently configures and applies ventilation
   flow to the zone RC network.

These two paths must not coexist. The correct resolution depends on which path is authoritative:

**Option A (infiltration-solver owns thermal):** Remove `PortContribution::Thermal` from
`Ventilation::step()`. The equipment only reports fan electrical consumption and telemetry.
All thermal loads (sensible and latent) live in `apply_infiltration_and_ventilation`.
The flow rate mismatch (F2) becomes irrelevant for thermal accuracy but still affects
`effective_flow_rate_m3_s` used for latent gain in the equipment path — which would no
longer exist.

**Option B (equipment owns thermal, remove from infiltration):** The `Ventilation` equipment
owns all heat exchange physics. `solver_builder.rs` must not set `ventilation_flow_m3_s`
or `VentilationConfig` from the ventilation equipment spec. The infiltration model continues
to handle infiltration and natural ventilation only.

Given that the infiltration solver handles the infiltration+ventilation interaction (F1
quadrature/superposition formula from OCHRE), Option A (solver owns the combined physics)
is the architecturally cleaner path. The equipment should provide: fan power, telemetry,
and a mechanism to push flow rate updates back to the solver config when the schedule
changes.

## Recommended Tests

1. **No double-accounting integration test**: Run a single-zone dwelling with a
   `Ventilation Fan` and compare zone temperature trajectory against a reference where only
   one heat path is active. Verify the zone heat balance closes correctly by checking that
   `sensible_balance = HVAC + infiltration + ventilation + gains - losses`.

2. **Key-mapping round-trip test** (unit): Construct a minimal HPXML with a known
   `RatedFlowRate` (e.g., 100 cfm), parse through `resolve_ventilation`, pass to
   `Ventilation::init()`, and assert `flow_rate_m3_s == 100 * CFM_TO_M3_S`.

3. **Recovery efficiency round-trip test**: Same setup with `SensibleRecoveryEfficiency = 0.75`,
   assert `sensible_effectiveness == 0.75` after `init()`.

4. **Fan type mapping test**: HPXML `FanType = "exhaust only"` must produce
   `VentilationType::ExhaustFan`.

5. **Bypass humidity gate test**: At 21°C outdoor, 0.015 kg/kg humidity ratio (above
   0.0115 threshold), bypass should not activate. Currently it does.

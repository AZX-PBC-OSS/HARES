## Background/Context

The original ticket assumed DR events are scheduled at specific local times (e.g., "curtail 2-6 PM"). Code inspection reveals this is **false**: `DrCompliance` is level-triggered. DR events are set externally via `set_dr_level()`, and `decide()` only calls `should_comply()` which uses `env.current_time.timestamp()` as a hash input for deterministic randomness — not as a time-of-day filter.

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### 1. DrCompliance is purely level-triggered — no time-window logic exists

`DrCompliance::decide()` at `crates/hares-core/src/actors/dr_compliance.rs:336` short-circuits immediately if `self.current_dr_level == DRLevel::Normal`. The only way the actor activates is if `set_dr_level()` has been called externally with a non-Normal level. There is no internal schedule, no cron, no time-of-day filter, and no start/end timestamp. The DR level is sticky until explicitly cleared by another `set_dr_level(DRLevel::Normal)` call.

### 2. `env.current_time.timestamp()` is used only for randomness seeding

`Probabilistic::hash_inputs()` at line 135 incorporates `env.current_time.timestamp()` (a UTC epoch integer) as part of a splitmix64 mixing function alongside `self.seed` and `dr_level as u64`. This is purely to produce deterministic, per-timestep variation in compliance decisions. It has no semantic relationship to local clock time, time-of-day windows, or scheduled event boundaries. The field type is `DateTime<FixedOffset>`, so `.timestamp()` returns seconds since the Unix epoch in UTC — appropriate for deterministic hashing, and confirmed not a time-of-day gate.

### 3. DR level state is external-only: no ingestion path from environment or schedule

`DrCompliance` has no mechanism to read a DR schedule column, inspect `env.price_signal`, or read from `env.custom_domains`. The actor only reacts to imperative `set_dr_level()` calls. No code in `crates/hares-core/src/dwelling/mod.rs` or `crates/hares-core/src/engine.rs` routes a `ControlSignal::DemandResponse` signal into `DrCompliance::set_dr_level()`. The `ControlSignal::DemandResponse { level, duration_s }` variant is handled directly by equipment (AC, heat pump, water heaters, battery, ventilation) via their own `apply_control()` implementations — bypassing `DrCompliance` entirely.

This means there are two parallel DR paths:

- **Equipment-direct path**: `ControlSignal::DemandResponse { level, duration_s }` is dispatched as a `DispatchRequest` and applied by each equipment's `apply_control()`. Equipment tracks `dr_duration_remaining_s` and auto-reverts to `DRLevel::Normal` when the countdown expires (e.g., `air_conditioner.rs:515-524`). This path is duration-aware and self-clearing.
- **DrCompliance actor path**: `set_dr_level()` sets a sticky level with no expiry. The actor then dispatches secondary control signals (setpoint deltas, load fractions, mode overrides) when `decide()` runs. This path has no auto-revert: `current_dr_level` persists until explicitly cleared.

### 4. No DR scheduling mechanism exists in HARES today

There is no built-in scheduler that translates "2-6 PM local time" into DR events. Time-windowed DR requires external wiring: either a Python-side controller calling `dwelling.set_actor_dr_level()` each step, or a HELICS co-simulation message. The Python binding `py_dwelling.rs:599` mentions `DrCompliance` as a valid actor type, but there is no Python API to call `set_dr_level()` on a running actor without direct access to the actor instance.

### 5. OCHRE comparison: also externally driven, no built-in DR scheduler

OCHRE's `HVAC.update_external_control()` (`vendors/OCHRE/ochre/Equipment/HVAC.py:255`) accepts a dict with keys `Setpoint`, `Load Fraction`, `Duty Cycle`, etc. passed in from outside each timestep. OCHRE has no DR compliance actor; load-shedding is a raw setpoint/duty-cycle override injected by an external orchestrator. OCHRE's WetAppliance DR hooks (`WetAppliance.py:76-86`) are commented out entirely. HARES's `DrCompliance` actor is a behavioral model layer above OCHRE's raw overrides — architecturally richer, but equally dependent on external event delivery.

## Issues Identified

### MEDIUM — No auto-revert in DrCompliance actor path

The equipment-direct `ControlSignal::DemandResponse` path auto-reverts via `dr_duration_remaining_s` countdown. The `DrCompliance` actor path does not. If an external caller sets `DRLevel::Critical` and never calls `set_dr_level(DRLevel::Normal)`, the actor will emit override signals every timestep indefinitely. This is an asymmetry between the two DR paths that will cause incorrect behavior in any scenario where DR events have finite duration and are routed through `DrCompliance` rather than directly dispatched.

**Fix required**: `DrCompliance` should accept an optional `duration_s` on activation and auto-clear `current_dr_level` to `Normal` after the countdown expires — mirroring the equipment-direct pattern.

### LOW — No Python API to inject DR level into DrCompliance at runtime

`set_dr_level()` is a Rust-only method. Python users who want time-windowed DR must either use the equipment-direct `ControlSignal::DemandResponse` dispatch (which bypasses compliance modeling entirely) or cannot use `DrCompliance` dynamically from Python at all. This should be exposed via a Python binding.

### LOW — AlwaysComply tests Normal-level compliance (incorrect behavior)

`always_comply_returns_true` at line 372 asserts `AlwaysComply.should_comply(DRLevel::Normal, &env)` returns `true`. At `DRLevel::Normal` no DR event is active, so `should_comply` is never called in practice (the `decide()` guard at line 337 returns early). However calling `should_comply` with `Normal` and getting `true` is misleading — compliance with a non-event is a conceptually empty case. This is minor but worth noting.

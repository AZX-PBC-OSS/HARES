## Background/Context

OCHRE auto-selects ideal capacity mode when `time_res >= 5 min` OR `n_speeds >= 4`.
Ideal mode calls the thermal solver to compute the exact heat needed to hold the
setpoint, rather than cycling on/off. This is critical for simulation accuracy at
common timesteps (5–15 min).

## Investigation Instructions

1. **Read HARES `ideal_hvac.rs`:**
   - Find `IDEAL_CAPACITY_TIME_RES_THRESHOLD_S` — what value? (Should be 300s = 5min)
   - Find `IdealCapacityMode::Auto` logic — when does it activate?
   - Is `is_variable_speed` checked? How is it determined? (Should be `n_speeds >= 4`)

2. **Read OCHRE `HVAC.py` line ~240:**
   - `use_ideal_capacity = True if time_res >= 5min OR n_speeds >= 4`
   - Is this the exact logic?

3. **Compare:**
   - Does HARES match OCHRE's selection criteria?
   - What happens when `IdealCapacityMode::On` or `Off` is forced?
   - Is the ideal capacity mode configurable from Python?

4. **Write findings** with the exact selection logic from both sides.


## Findings

### 1. Auto-selection criteria — HARES vs OCHRE

**OCHRE** (`HVAC.py:239-240`):
```python
use_ideal_capacity = self.time_res >= dt.timedelta(minutes=5) or self.n_speeds >= 4
```
A single boolean is set once at construction and applies for the lifetime of the object.
Heating-only and cooling-only equipment are separate classes (`Heater`/`Cooler`) so there is never a question of which mode's capacity solver to invoke — the polarity is baked in via `hvac_mult` (+1 or -1).

**HARES `IdealHvac`** (`ideal_hvac.rs:184-193`):
```rust
IdealCapacityMode::Auto => {
    let time_res_s = env.time_res.num_seconds();
    time_res_s >= IDEAL_CAPACITY_TIME_RES_THRESHOLD_S || self.is_variable_speed
}
```
`IDEAL_CAPACITY_TIME_RES_THRESHOLD_S = 300` (5 min) matches OCHRE.
`is_variable_speed` is set during `init()` from `n_speeds >= 4.0` (`ideal_hvac.rs:363-365`) — also matches OCHRE.

**Deviation:** Unlike OCHRE, `use_ideal_capacity` in HARES is re-evaluated every timestep (inside `update_control`) rather than once at construction. This is intentional to allow the `IdealCapacityModeOverride` control signal to change mode at runtime, but the re-evaluation also means a change in timestep resolution mid-simulation could toggle the mode — a scenario OCHRE does not support.

**Inconsistency flagged in Review Notes (`HvacEquipment.use_ideal_capacity`):** `HvacEquipment` (used by `AirConditioner`, heat pump heater, etc.) has a separate `thermostat.use_ideal_capacity` bool field (`hvac_core.rs:301`) that is populated from the config key `use_ideal_capacity`. It does NOT check `n_speeds >= 4` or `time_res >= 300s` automatically. The `HvacEquipment` path is therefore inconsistent with both `IdealHvac` and OCHRE: it requires an explicit config flag rather than auto-detecting from `n_speeds` or time resolution. This affects `AirConditioner`, `GasFurnace`, `AshpHeater`, etc.

### 2. Mode switching and thermostat deadband logic

**OCHRE** uses separate heater/cooler equipment objects. Mode switching is a single-polarity on/off decision:
- Turn ON when `hvac_mult * (zone_temp - turn_on_threshold) < 0`
- Turn OFF when `hvac_mult * (zone_temp - turn_off_threshold) > 0`
- `turn_on = setpoint - hvac_mult * deadband * (1 - offset)`
- `turn_off = setpoint + hvac_mult * deadband * offset`

With `hvac_mult=1` (heating): turn on below `setpoint - deadband*(1-offset)`, turn off above `setpoint + deadband*offset`.
With `hvac_mult=-1` (cooling): turn on above `setpoint + deadband*(1-offset)`, turn off below `setpoint - deadband*offset`.

Deadband offset defaults to 0.2 in OCHRE, meaning the setpoint sits near the top of the band for heating.

**HARES `IdealHvac.update_mode()`** (`ideal_hvac.rs:223-315`) implements a three-state machine: `Heating | Cooling | Deadband`. With `offset > 0`:
- `Heating → Deadband` when `zone_temp > heating_c + hysteresis * offset` (turn-off at top of band)
- `Cooling → Deadband` when `zone_temp < cooling_c - hysteresis * offset` (turn-off at bottom of band)
- `Deadband → Heating` when `zone_temp < heating_c - hysteresis * (1-offset)`
- `Deadband → Cooling` when `zone_temp > cooling_c + hysteresis * (1-offset)`

With `offset = 0.2` and `hysteresis = 1.0` this produces turn-on at `heating_c - 0.8` and turn-off at `heating_c + 0.2`, which matches OCHRE's formula exactly.

No direct Heating→Cooling or Cooling→Heating transition is possible; the state machine must pass through Deadband. This correctly prevents simultaneous heating and cooling.

**OCHRE simultaneous H+C prevention:** OCHRE prevents this architecturally — heating and cooling are entirely separate equipment objects that cannot both be "On" in the same zone at the same timestep unless two separate objects are independently triggered. The dwelling-level orchestration is responsible for not scheduling both. HARES prevents it within a single `IdealHvac` instance via the Deadband transit requirement.

### 3. Ideal capacity enforcement at the step boundary

**OCHRE** (`HVAC.py:442-448`): when `capacity_ideal < capacity_min` (default 0), force capacity to 0 (i.e., mode becomes Off). This is the primary mechanism for turning off in ideal mode — the solver returns a negative/zero load and the equipment forces off.

**HARES** uses a two-layer approach:
1. `update_mode()` runs the three-state thermostat based on zone temperature vs setpoints. Mode is set to `Heating`/`Cooling`/`Deadband` regardless of ideal capacity value.
2. In `step()`, if mode is `Heating` and `use_ideal_cached=true`, the capacity is `(ideal_capacity_w * load_fraction).max(0.0)` — negative ideal capacity is clamped to 0.

**Critical divergence from OCHRE:** In OCHRE, a negative ideal capacity causes the equipment to turn **off** entirely (returning `"Off"` mode, affecting the results). In HARES, a negative ideal capacity in heating mode does NOT cause a mode transition — mode remains `Heating`, but 0 W is delivered. The telemetry will show `OPERATING_MODE = 1` (Heating) while `THERMAL_OUTPUT_W = 0.0`. This is a semantic mismatch: OCHRE would show mode=Off; HARES shows mode=Heating with zero output.

The practical consequence: the `ideal_target()` function will continue returning `Some((zone, heating_setpoint_c))` even when the solver has already determined no heating is needed, driving another solver call next step. OCHRE breaks the feedback loop by forcing Off mode.

### 4. Minimum on/off time — two conflicting mechanisms

HARES `IdealHvac` has two independent minimum-time enforcement paths that can conflict:

**Path A — `is_cycle_change_allowed`** (`thermostat.rs:171-183`): guards against any mode change based on `thermostat.min_cycle_time_s` and `last_mode_switch_at`. This is a single symmetric lockout that applies to both on→off and off→on transitions.

**Path B — `can_transition_mode`** (`ideal_hvac.rs:206-221`): a separate check using `min_on_time_s` (guards On→Deadband) and `min_off_time_s` (guards Deadband→On). Uses `mode_start_at` rather than `last_mode_switch_at`.

`update_mode()` checks Path A first at line 236; if blocked, returns current mode immediately without evaluating Path B. If Path A passes, `next_mode` is computed, then Path B is checked at line 302. Both `mode_start_at` and `last_mode_switch_at` are updated together in `set_mode()` (`ideal_hvac.rs:195-203`).

**Issue:** Path A uses `last_mode_switch_at` which is reset on any mode change, including Deadband→Heating→Deadband cycles. Path B uses `mode_start_at` which is also reset on any mode change (`set_mode` at line 198). When `min_cycle_time_s > 0` and `min_on_time_s > 0`, Path A may prevent evaluation before Path B has a chance to run, leading to the longer of the two lockouts always winning — but this is non-obvious from reading the code. The two fields are set from different config keys (`min_cycle_time_s` vs `min_on_time_s`/`min_off_time_s`) which could lead to unintended double-lockout if a caller sets both.

OCHRE uses a single `min_time_in_mode` dict (one entry per mode) in `Equipment.update_model()`, applied uniformly.

### 5. Setpoint update timing — current_target_c double-write

In `update_mode()`, `current_target_c` is written twice (`ideal_hvac.rs:231-233` and `ideal_hvac.rs:308-312`). The first write at lines 231-233 (inside the mode-is-current branch before the cycle-change guard) ensures the solver always has a current setpoint even during lockout. The second write at lines 308-312 (after potential mode transition) is the canonical post-transition update. Both writes are correct but the duplication is non-obvious — a future reader might remove one thinking it's redundant.

### 6. `ideal_capacity_w` stale-after-mode-switch

When `ModeOverride::Off` or `LoadFraction { fraction: 0.0 }` forces the equipment off, `ideal_capacity_w` is explicitly zeroed (`apply_control_unchecked` lines 503-508, 538-539). However, when the thermostat naturally transitions from Heating→Deadband or Cooling→Deadband (via `set_mode`), `ideal_capacity_w` is also zeroed (`set_mode` lines 200-202). This is correct.

However, when the thermostat transitions from Deadband→Heating (new mode), `ideal_capacity_w` retains its previous value (the last solver-computed capacity from the previous active period). On the first step after turning on, the equipment uses this stale cached value until the solver feedback actor runs in the next cycle and dispatches a fresh `IdealCapacity` signal. This is the "one-step-stale" behavior acknowledged in the `step()` comments, and it is structurally unavoidable given the solver-feedback loop ordering. OCHRE also has this property (the ideal capacity call runs `update_capacity()` once at the start of `update_internal_control`, using the previous-timestep envelope state). Both implementations are equivalent here.

## Recommended Tests

1. **`ideal_hvac_negative_capacity_does_not_emit_heat`** — Set mode to Heating (zone well below setpoint), inject `IdealCapacity { capacity_w: -500.0 }`, call `step()`, assert `thermal_output_w == 0.0`. This passes today but verifies the clamp behaviour is intentional and stable.

2. **`ideal_hvac_negative_capacity_mode_remains_heating`** — After injecting negative ideal capacity and calling `step()`, assert `OPERATING_MODE == 1` (Heating). Documents current behaviour that diverges from OCHRE (which would be Off).

3. **`hvac_equipment_auto_ideal_vs_manual`** — Construct an `AirConditioner` (or equivalent equipment that uses `HvacEquipment`) at 5-minute timestep with `n_speeds=4` but WITHOUT setting `use_ideal_capacity=true` in config. Verify that `thermostat.use_ideal_capacity` is NOT automatically set, confirming the known inconsistency with `IdealHvac` auto-selection.

4. **`ideal_hvac_mode_min_on_min_cycle_conflict`** — Construct `IdealHvac` with both `min_cycle_time_s=120` and `min_on_time_s=180`. Start in Heating mode at t=0. Advance to t=130s (past min_cycle but not min_on). Assert that mode does NOT transition to Deadband. Advance to t=190s. Assert that mode transitions correctly.

5. **`ideal_hvac_no_direct_heating_to_cooling_transition`** — Construct `IdealHvac` with `heating_setpoint_c=20.0`, `cooling_setpoint_c=24.0`, `hysteresis_c=1.0`. While in Heating mode, jump zone temp to 30°C (far above cooling threshold). Call `update_control`. Assert mode is `Deadband` (not `Cooling` directly), and that a second call returns `Cooling` — confirming the Deadband transit requirement.

6. **`current_target_c_tracks_schedule_during_lockout`** — Set `min_cycle_time_s` to a large value, engage lockout. Then change the heating setpoint via `ThermalSetpointDelta`. Call `update_mode` (which is blocked by lockout). Assert `current_target_c` reflects the updated setpoint (from the first write at lines 231-233), not the old one.

## Review Notes

`HvacEquipment.use_ideal_capacity()` at `hvac_core.rs:646-649` checks `self.thermostat.use_ideal_capacity` OR `time_res >= 300s` but does NOT check `n_speeds` or `SpeedControlMode::VariableSpeedIdeal`. This differs from `IdealHvac` which does check `n_speeds >= 4`. Investigate this inconsistency.

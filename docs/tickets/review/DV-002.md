## Findings

### F1 — SEVERITY: HIGH — Low-speed dTe denominator uses wrong air density constant

**File:** `crates/hares-physics/src/ashrae152.rs:471`

OCHRE `equipment.py:322` computes `dTe_low` with density `0.0775`:
```python
dTe_low = capacity_low * hvac.hvac_mult / (60 * fan_flow_low * 0.0775 * 0.24)
```
HARES uses `0.075` for both high and low speed:
```rust
let denom_low = 60.0 * flow_low * 0.075 * 0.24;
let dte_low = cap_low * hvac_mult / denom_low;
```
The standard air density used for HVAC calculations is 0.075 lb/ft³ (at 70°F standard air). OCHRE's `0.0775` on the low-speed path appears to be a typo/bug in OCHRE (it is inconsistent with every other expression in the same function, including the high-speed path and the Bs_low/Br_low exponents on lines 323–324 which still use `0.075`). However, HARES must match OCHRE output numerically until the reference behavior is explicitly superseded. Because DSE is a fixed coefficient applied at equipment init time — not re-computed per timestep — even a small dTe discrepancy changes the seasonal uncorrected DE for all multi-speed heating configurations.

**Resolution path:** Confirm whether `0.0775` is intentional in OCHRE or a typo. The ASHRAE 152 standard specifies 0.075 lb/ft³; OCHRE is inconsistent between its own `dTe_low` and `Bs_low`/`Br_low` expressions, so it is almost certainly a bug in OCHRE. Since project policy is to target correct ASHRAE physics (not replicate OCHRE bugs), HARES's use of `0.075` is the correct choice, but this must be explicitly documented and a test must assert the DSE value for a 2-speed heater configuration numerically (not just bounds-checking).

### F2 — SEVERITY: MEDIUM — No test pins a numeric DSE value; all tests are bounds-only

**File:** `crates/hares-physics/src/ashrae152.rs:627–705`

All four existing `calculate_dse` tests assert only `dse > 0.0 && dse <= 1.0` (with one additionally checking `dse > 0.6`). No test pins a known-good numeric value derived from either OCHRE or a hand-computed ASHRAE 152 result. This means any formula regression — including the `0.0775` vs `0.075` deviation identified above — would pass the test suite silently.

### F3 — SEVERITY: MEDIUM — Multi-speed heat-pump heating path has no test at all

**File:** `crates/hares-physics/src/ashrae152.rs:530–536`

The equipment factor branch `is_heat_pump && n_speeds > 1` uses `0.44 + 0.56 * seas_uncorr_de`. There is no test exercising this branch. Combined with F2, a regression here would be invisible.

### F4 — SEVERITY: LOW — Alaska stations with empty cooling fields are silently skipped

**File:** `crates/hares-physics/src/ashrae152.rs:138–139`

The parser skips any row where `cooling_des_temp` (field 7) or `cooling_seas_temp` (field 8) is empty (`parse(7)` or `parse(8)` returning `None`). CSV line 2 (`Adak, AK`) has empty cooling fields and is correctly skipped. However:

1. The skipped station still contributes to the index. The `climate_data_loads_with_sufficient_stations` test checks `data.len() > 200`, and the CSV has 223 data rows, but the actual parsed count is lower because Alaska stations with blank cooling fields are dropped. As of the current CSV, lines 1 (Adak) and 13 (Nome) appear to have empty cooling fields; Nome also appears to lack humidity data. The assertion threshold of 200 must remain valid after drops, but this is untested explicitly.
2. A station that is dropped for missing cooling data cannot be used even for heating-only queries for that location. For users at or near Adak or Nome requesting a heating DSE, the lookup silently falls back to the next-nearest station. This is the correct degraded behavior but is not documented or tested.

### F5 — SEVERITY: LOW — Denver test lat/lon offset from CSV entry by ~16 km

**File:** `crates/hares-physics/src/ashrae152.rs:609–622`

Test uses `(39.7, -104.9)` but the CSV Denver entry is `(39.833, -104.65)`. Haversine distance between these is approximately 23 km. The test asserts `dist < 100 km`, which passes. However, because two other Colorado stations (Colorado Springs: ~60 km, Pueblo: ~80 km from the test point) are plausible candidates, the `< 100 km` threshold does not strictly confirm Denver is selected. A tighter bound of `< 30 km` would actually validate the station resolution.

### F6 — SEVERITY: LOW — Phoenix CSV longitude differs from test fixture by 0.037°

**File:** `crates/hares-physics/src/ashrae152.rs:659`; CSV line 20

Test uses `longitude = -112.02`; CSV entry is `-111.983`. Distance is ~3 km, well within any reasonable nearest-neighbor tolerance. This is not a correctness issue but documents a minor inconsistency between test fixture and data.

### F7 — SEVERITY: INFORMATIONAL — Zone temperature CSV is byte-for-byte identical to OCHRE reference

**Files:** `defaults/ASHRAE152_zone_temperatures.csv`, `vendors/OCHRE/ochre/defaults/ASHRAE152_zone_temperatures.csv`

`diff` produces no output. The 16 zone type rows, all formulas (offsets, blending weights, regain coefficients), and column headers match exactly. No discrepancies found.

### F8 — SEVERITY: INFORMATIONAL — Haversine implementation matches OCHRE exactly

**File:** `crates/hares-physics/src/ashrae152.rs:165–172`

HARES uses `atan2(sqrt(a), sqrt(1-a))` form (half-versine). OCHRE uses `arctan2(sqrt(a), sqrt(1-a))` (same formula in numpy). Earth radius 6373.0 km is identical in both. No discrepancy.

### F9 — SEVERITY: INFORMATIONAL — Climate CSV field indices match OCHRE column names

The parser reads:
- idx 3 = Latitude, idx 4 = Longitude (correct)
- idx 5 = Heating Design Temp, idx 6 = Heating Seasonal Temp (correct)
- idx 7 = Cooling Design Temp, idx 8 = Cooling Seasonal Temp (correct)
- idx 10 = Wseasonal (correct; idx 9 = Wdesign, idx 10 = Wseasonal)
- idx 14 = Seasonal hout (correct; idx 13 = Design hout, idx 14 = Seasonal hout)
- idx 16 = Seasonal hin (correct; idx 15 = Design hin, idx 16 = Seasonal hin)

All index-to-column mappings are confirmed correct against the CSV header row.

### F10 — SEVERITY: INFORMATIONAL — No off-by-one in station iteration

OCHRE uses `index_col="Index"` (1-based) then `argmin() + 1` to re-index. HARES iterates `Vec<ClimateStation>` by linear scan (`min_by`), so there is no index arithmetic and no off-by-one possible.

### F11 — SEVERITY: INFORMATIONAL — OCHRE raises an exception for DSE out of bounds; HARES clamps

**File:** `crates/hares-physics/src/ashrae152.rs:560–565`; OCHRE `equipment.py:460–463`

OCHRE raises `OCHREException` if `dse <= 0 or dse > 1.1`. HARES returns `1.0` for NaN/Inf and clamps to `(f64::MIN_POSITIVE, 1.0]`. The clamping is a deliberate design choice (simulation must not crash on degenerate duct configurations), documented in the code comment. This is correct for a simulation engine.

Exercise the `is_heat_pump = true, n_speeds = 2` branch. Assert DSE within ±0.005 of a reference value. This is the only equipment factor branch currently untested.

Add a test that calls `nearest_station(51.883, -176.65)` (Adak's coordinates) and asserts the returned station is within a reasonable distance, confirming graceful fallback works when the exact station was dropped due to empty cooling fields.

Extend `climate_data_loads_with_sufficient_stations` to assert `data.len() == <exact_count>` rather than `> 200`. Count the expected number by manually counting non-skipped rows in the CSV (rows where cooling fields are non-empty).

## Summary

The zone-temperature CSV is verified identical to OCHRE. The haversine implementation and field index mappings are correct. The primary finding requiring action is **F1**: the OCHRE reference contains what appears to be a typo (`0.0775` vs `0.075`) on the low-speed `dTe` path that HARES correctly does not replicate, but this divergence is undocumented and untested, meaning any future attempt to reconcile HARES against OCHRE output for multi-speed heating may chase a phantom discrepancy. The deviation must be explicitly documented and covered by a numeric pin test. The remaining medium finding (**F2**) — bounds-only tests — is the most actionable correctness gap, as it allows formula regressions to pass silently.

## Background/Context

The tariff evaluator uses time-of-day to apply TOU rates. A UTC-vs-local error here would produce wrong billing calculations without affecting physical simulation. No existing DT ticket covers the tariff layer.

## Investigation Instructions

1. **Read `evaluator.rs`**: What time source is used for TOU period determination? `env.current_time`? A separate clock?
2. **Verify local-time correctness:** TOU periods are defined in local time (e.g., "peak = 2-7 PM"). Confirm the evaluator uses the correct offset.
3. **Check weekend/holiday handling:** Do TOU rates switch correctly for weekends? Is `.weekday()` called on a local-time DateTime?
4. **Compare with OCHRE's TOU handling** if applicable.

## Findings

### TOU Time Source

**CORRECT.** `TariffEvaluator` pre-computes the entire price, period-index, and month arrays at construction time (`TariffEvaluator::new`). The construction path is:

```
evaluator.rs:90   let ts = simulation_start + Duration::seconds(i * interval);
evaluator.rs:91   let civil = ts.with_timezone(&timezone);
evaluator.rs:92   let month = civil.month() as u8;
evaluator.rs:93   let weekday = civil.weekday();
evaluator.rs:94   let minute_of_day = civil.hour() as u16 * 60 + civil.minute() as u16;
```

`timezone` is extracted from `simulation_start.timezone()` where `simulation_start: DateTime<Tz>`. The `DateTime<Tz>` type in `chrono_tz` carries a full IANA timezone (e.g. `America/New_York`), so `.hour()`, `.weekday()`, and `.month()` are all in the correct civil (local) time including DST transitions.

### Call Site Verification

`set_tariff` in `crates/hares-core/src/dwelling/mod.rs:1466-1471` creates the `DateTime<Tz>` values correctly:

```rust
let start = self.clock.start_time.with_timezone(&tz);
let end_fixed = self.clock.start_time + self.clock.duration;
let end = end_fixed.with_timezone(&tz);
let evaluator = TariffEvaluator::new(tariff, start, end, interval_secs)?;
```

`SimClock::start_time` is `DateTime<FixedOffset>` (local wall-clock digits per `clock.rs` module docs). `with_timezone(&tz)` converts to `DateTime<Tz>` which re-expresses the same absolute instant in the IANA timezone. The wall-clock hour digits will match local civil time throughout the simulation provided the caller passed the correct IANA `Tz` to `set_tariff`. This is the sole coupling point between the clock and tariff subsystems; it is sound.

### Weekend/Weekday Handling

**CORRECT.** `civil.weekday()` is called on the timezone-adjusted `DateTime<Tz>`, so `.weekday()` returns the civil local day-of-week. This is tested by `evaluator_summer_peak_price` (July 7 = Monday) and `evaluator_winter_offpeak_price` (Jan 4 = Saturday) in `evaluator.rs`.

### DST Handling

**CORRECT.** `chrono_tz::Tz` handles DST transitions correctly via the IANA database. Two dedicated tests verify:
- `evaluator_dst_spring_forward`: March 9, 2025 (23-hour day) → `total_steps() == 23` for hourly
- `evaluator_dst_fall_back`: November 2, 2025 (25-hour day) → `total_steps() == 25` for hourly

The step count reflects real elapsed seconds, so a spring-forward hour gets zero steps and a fall-back hour gets two steps — both physically correct behaviors.

### Billing Period Boundary Comparison

The `step()` method receives `current_time: DateTime<Tz>` (same timezone as `simulation_start`) and compares it with `billing_state.period_end: DateTime<Tz>`. Both operands are in the same `Tz`, so the chrono comparison is an absolute-time comparison — correct. The caller (`dwelling/mod.rs:2180`) converts `latest_env.current_time` (a `DateTime<FixedOffset>`) via `.with_timezone(&tz)` before passing it to `step()`, which is correct.

### Missing Test Coverage

The following scenarios are untested and represent residual risk:

1. **Non-US timezone (e.g. `Europe/Berlin`, UTC+1/+2):** No test exercises a timezone where the UTC offset crosses midnight differently from `America/New_York`. An on-peak window of 16:00–20:00 CET would be misclassified as UTC if the `Tz` were accidentally dropped to `UTC`. A test using a non-North-American IANA zone would close this gap.

2. **`set_tariff` caller passing the wrong `Tz`:** The `set_tariff` API signature accepts any `Tz`. If a caller passes `chrono_tz::UTC` for a building in California, all TOU windows shift by 7-8 hours and no error is produced. There is no validation that the supplied `Tz` is consistent with the building's weather location. This is an API design gap — not a bug in the evaluator itself — but the consequence is silently wrong billing.

3. **Tiered block month boundary:** `tier_multiplier` indexes `self.months[ci]` which was computed at construction from the same civil time as the price array. No defect found, but no specific test exercises a tiered rate at a season boundary month (e.g., June 1 transitioning Summer tier thresholds).

4. **`FixedOffset` simulation_start coherence:** `SimClock::start_time` is `DateTime<FixedOffset>`. The module docs state "pass the intended local hour" and note the offset is "effectively ignored unless `civil_timezone` is set." If a caller creates `SimClock` with a `FixedOffset` that does not match the `Tz` passed to `set_tariff`, the two subsystems will disagree on civil time. This is documented but not enforced. No runtime assertion or type-level guarantee prevents mismatch.

### OCHRE Comparison

OCHRE's TOU handling in `vendors/OCHRE/ochre/utils/schedule.py` uses Python `datetime` objects in local time via `pandas` `DatetimeTZDtype`. HARES replicates the same semantic (civil local time for period matching) via `chrono_tz::Tz`, which is the idiomatic Rust equivalent. No behavioral divergence found.

## Summary

The tariff evaluator's TOU period determination is **correct**: it uses `chrono_tz::Tz`-adjusted civil time throughout construction, correctly handles DST, and existing tests cover the primary scenarios. The three gaps identified above are coverage and API-design issues, not runtime bugs in the current code.

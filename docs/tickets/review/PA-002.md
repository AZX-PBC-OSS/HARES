## Background/Context

`Battery.charging_curve_lut`, `.ocv_table`, `.u_neg_table` and `EV.charging_curve_lut`
can be SET from Python (via constructor or `update_equipment()`) but cannot be READ
back. This prevents users from inspecting or validating the LUT data.

## Investigation Instructions

1. Read `py_equipment.rs` — confirm no `#[pyo3(get)]` on LUT fields.
2. Assess: do users need to read LUTs? For debugging? Validation?
3. Check type stubs in `_hares.pyi` — do they correctly reflect the write-only nature?
4. Recommend: add getters? Return as numpy array? Or document as intentional?


## Findings

### [CONFIRMED] LUT fields are write-only — no Python getter exists

**Severity: Medium**

`crates/hares-python/src/py_equipment.rs:146-148`

```rust
pub charging_curve_lut: Option<RegularGridInterpolator>,
pub ocv_table: Option<OcvTable>,
pub u_neg_table: Option<UNegTable>,
```

All three fields on `PyBattery`, and the single `charging_curve_lut` on `PyEv` (line 545), are bare pub fields with **no `#[pyo3(get)]` attribute**. Every other scalar field on `PyBattery` (lines 98–145) carries `#[pyo3(get)]`. The LUT fields are the sole exceptions.

`_hares.pyi` confirms this: the `Battery` and `EV` classes expose `charging_curve_lut`, `ocv_table`, and `uneg_table` **only as constructor parameters**, not as properties. There are no getter stubs for these fields.

### [CONFIRMED] Post-injection read-back is impossible via the config object

Once a `Battery` or `EV` config object is constructed with a LUT, the data cannot be retrieved. There is no `get_lut`, no property, and no round-trip. The object is effectively opaque after construction with respect to LUT data.

### [CONFIRMED] Post-registration read-back is also absent

`py_dwelling.rs` exposes `has_lut(name, lut_type) -> bool` (line 1074) and write-side methods (`update_equipment`, `inject_lut`, `clear_lut`) but no method to **read back** a LUT from a registered equipment instance. The type stub at `_hares.pyi:1682` shows only write and existence-check surfaces — no getter returning the actual data.

### [ASSESSED] User impact

- **Validation/debugging is blocked.** A user cannot confirm that their LUT was parsed correctly (axis lengths, value ranges) without running a full simulation.
- **Serialisation/round-trip is broken.** A `Battery` config object carrying a LUT cannot be serialised back to Python data structures. Any persistence layer (e.g., saving a configured dwelling to disk) silently drops LUT data.
- **`__repr__` for `Battery` does not mention LUT presence at all** (lines 359–431), while `EV.__repr__` at least prints `lut=loaded` (line 677). This asymmetry makes the `Battery` case even harder to debug.

### [NOTED] `RegularGridInterpolator` is not a PyO3 class

`RegularGridInterpolator` is a plain Rust struct with no `#[pyclass]` annotation, so a direct `#[pyo3(get)]` would not work. A getter would need to reconstruct a Python-friendly representation (numpy arrays or a dict). This is the likely reason the fields were left bare, but it was not documented as intentional.

### [NOTED] `OcvTable` / `UNegTable` are type aliases

These are `Vec<(f64, f64)>` or equivalent, which _could_ be returned directly as `Vec<(f64, f64)>` via PyO3 (auto-converts to list of tuples). There is no technical blocker for adding getters on those two fields specifically.

---

## Recommendation

**Add read-back capability.** Write-only LUT injection is not acceptable for a user-facing config API.

Concrete approach:

1. **`Battery.charging_curve_lut` / `EV.charging_curve_lut`** — add a `#[getter]` method that returns a Python `dict` with keys `soc_grid`, `temp_grid`, `crate_grid`, `soh_grid`, `lut` as flat Python lists (mirroring the accepted input format). `RegularGridInterpolator` must expose its axis and value data via public accessors for this.

2. **`Battery.ocv_table` / `Battery.uneg_table`** — add `#[pyo3(get)]` or `#[getter]` returning `Option<Vec<(f64, f64)>>`. This is trivial since `OcvTable`/`UNegTable` are list-compatible.

3. **`Battery.__repr__`** — add `lut=loaded` line parity with `EV.__repr__`.

4. **`_hares.pyi`** — add property stubs for all three getters on `Battery` and one on `EV`.

5. Optionally expose a `get_lut(name, lut_type)` method on `PyDwelling` that retrieves the live LUT from a registered equipment instance, for post-registration inspection.

## Recommended Tests

- `test_battery_lut_roundtrip`: construct `Battery` with a known `charging_curve_lut` dict, read `.charging_curve_lut` back, assert axes and a spot-check value match inputs exactly.
- `test_battery_ocv_roundtrip`: same for `ocv_table` — construct, read back, assert list of tuples preserved.
- `test_battery_uneg_roundtrip`: same for `uneg_table`.
- `test_ev_lut_roundtrip`: construct `EV` with a `charging_curve_lut`, read it back.
- `test_battery_repr_has_lut_info`: assert `repr(battery_with_lut)` contains `lut=loaded` or equivalent.
- `test_battery_no_lut_repr_clean`: assert `repr(battery_without_lut)` does not mention `lut`.

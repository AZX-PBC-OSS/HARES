## Background/Context

Equipment emits `PortContribution::Thermal { zone, sensible_gain_w, latent_gain_w,
category }` into `PortSlots`. The zone ID and category are both runtime values —
there is no compile-time guarantee that equipment emits to the correct zone or uses
the correct category. A bug here means energy goes to the wrong zone or gets
miscategorized, causing both incorrect physics and incorrect reporting.

Premature aggregation is the other side of this coin: if `ThermalAccumulator` sums
contributions before the thermal solver sees them, per-category debugging becomes
impossible.

## Investigation Instructions

1. **Trace zone ID assignment per equipment:**
   - Where does each equipment get its `zone_id`? From config? Hardcoded?
   - Can a duct loss go to the wrong zone?
   - Can a water heater jacket loss go to the wrong zone?
   - Can a scheduled load go to a zone it's not physically in?

2. **Trace category assignment:**
   - Read every `PortContribution::Thermal` construction site.
   - Is the category always correct? Or are there places where `InternalGain` is used
     as a catch-all for things that should be `JacketLoss`, `DuctLoss`, etc.?

3. **Assess premature aggregation:**
   - Does `ThermalAccumulator` preserve per-category breakdowns?
   - Can the thermal solver see individual contributions or only the sum?
   - Can output/telemetry report per-category values?
   - Where is information lost?

4. **Assess type safety opportunities:**
   - Could `ZoneId` be validated at equipment registration time?
   - Could the port system reject contributions to unknown zones?
   - Could category be enforced per equipment type (e.g., HVAC can only emit
     `HvacHeating`/`HvacCooling`, not `InternalGain`)?

5. **Check multi-zone correctness:**
   - For equipment that contributes to multiple zones (HVAC with ducts, HPWH with
     zone extraction), trace each zone contribution path.

## Findings

### F-001 — BUG (Severity: High) — ScheduledLoad hardcodes garage/foundation zone IDs

**File:** `crates/hares-equipment/src/scheduled_load.rs:98-100`

```rust
const GARAGE_ZONE_ID: ZoneId = ZoneId(2);
const FOUNDATION_ZONE_ID: ZoneId = ZoneId(3);
```

`ScheduledLoad::new()` (lines 179-185) routes equipment whose name contains `"garage"` to `ZoneId(2)` and `"basement"` to `ZoneId(3)` without reading these values from the config or the building model.

Zone IDs are assigned dynamically by `initial_zones()` in `crates/hares-core/src/environment.rs:743`:

```rust
id: ZoneId(u16::try_from(idx + 1).unwrap_or(u16::MAX)),
```

The `idx` is the position of each zone in `building.zones`, which is determined by HPXML parse order. A building where the foundation zone appears before the garage in the HPXML will produce `FOUNDATION_ZONE_ID = ZoneId(2)` and `GARAGE_ZONE_ID = ZoneId(3)`, reversing the assumptions. A building with only one non-conditioned zone will produce `ZoneId(2)` for it regardless of type.

In the current test fixture set every building appears to have a single conditioned zone at `ZoneId(1)`, so this bug does not surface in parity tests. It becomes a correctness defect as soon as a multi-zone building with unconditioned spaces is used.

**Consequence:** Appliance and lighting internal-gain heat is silently deposited into the wrong zone. The conditioned-zone heat balance will be incorrect, as will the garage/foundation zone temperature evolution.

**Fix:** Pass the actual zone lookup map (or at minimum a `garage_zone_id: Option<ZoneId>` and `foundation_zone_id: Option<ZoneId>`) from the dwelling builder to `ScheduledLoad::new()` via config, the same way HVAC equipment receives `zone_id` from the resolver. The heuristic name-based routing should remain as a fallback, but the zone IDs must be resolved from the building model, not from compile-time constants.

### F-002 — BUG (Severity: High) — HVAC duct-zone and basement-zone contributions not declared in ports()

**Files:**
- `crates/hares-equipment/src/hvac/furnace.rs:88-91`
- `crates/hares-equipment/src/hvac/air_conditioner.rs:325-328`
- `crates/hares-equipment/src/hvac/heat_pump/heater.rs:309-312`
- `crates/hares-equipment/src/hvac/boiler.rs` (analogous)

Every HVAC equipment type declares only `PortDeclaration::thermal(zone)` for the primary conditioned zone in its initial `ports` vector. After `init()`, `duct_zone_id` and `basement_zone_id` are parsed from config and stored in `HvacEquipment`. During `step()`, `write_zone_thermal_contributions()` may emit contributions to these additional zones.

The `PortSlots::accumulate()` call at `ports.rs:415-421` rejects any contribution to a zone not in the accumulator's `thermal` vec with:

```rust
return Err(HaresError::Equipment(format!("undeclared thermal zone: {zone:?}")));
```

The dwelling builder mitigates this at `dwelling/mod.rs:896-904` by pushing all `initial_env.zones` into the declaration list unconditionally. This means the duct-zone and basement-zone accumulators exist **if and only if** those zones are present in the initial environment.

The result is two distinct failure modes:
1. If the duct zone IS a real zone in `env.zones`, contributions route correctly but the equipment's own `ports()` declaration is incomplete — it under-declares what it will actually emit. This breaks any tooling that reasons about equipment port declarations before simulation (e.g., a static wiring validator or fleet-level resource planner).
2. If the duct zone is configured with a `ZoneId` that is not in `env.zones` (misconfiguration, or a future scenario where duct zones are external), the `accumulate()` call returns `Err`, which is demoted to a non-fatal warning at `dwelling/mod.rs:1945-1950`. The duct-loss energy is silently discarded. The conditioned zone receives only `duct_dse * capacity_w` instead of the full gross capacity, and the duct-loss energy `(1 - duct_dse) * capacity_w` disappears from the simulation. The energy balance is violated with no diagnostic beyond a warning string.

**Fix:** After `init()` resolves `duct_zone_id` and `basement_zone_id`, the equipment must update its `ports` vec to include `PortDeclaration::thermal(duct_zone_id)` and `PortDeclaration::thermal(basement_zone_id)` for each configured zone. The `ports` field should not be set-once at construction. See `ScheduledLoad::update_ports()` at `scheduled_load.rs:219-228` for the existing pattern of a post-init port rebuild.

### F-003 — BUG (Severity: Medium) — Silent energy discard when duct_zone_id not in env.zones

**File:** `crates/hares-core/src/dwelling/mod.rs:1945-1950`

Equipment `step()` errors are demoted to warnings:

```rust
if let Err(err) = self.equipment[idx].step(&self.latest_env, dt, &mut self.ports) {
    self.warnings.push(format!(
        "equipment step failed for '{}' : {err}",
        self.equipment[idx].descriptor().name
    ));
}
```

When `write_zone_thermal_contributions()` tries to accumulate to an undeclared duct zone, the `?` propagation returns an `Err` from `step()`. That error is swallowed as a warning and simulation continues. The duct-loss energy for that timestep is not reattempted or rerouted — it is simply dropped.

This is not specific to duct zones; any step-level port error causes silent energy loss. The current warning-only handling is appropriate for non-critical load schedule failures (the original motivation for the pattern) but is incorrect for physics-bearing equipment that moves significant energy.

**Fix:** Distinguish between equipment classes that may safely be skipped (missing-schedule loads) and those that must not be skipped (HVAC, water heater, battery). For the latter category, a failed `step()` should either halt simulation or escalate to a hard error. At minimum, the energy discarded when a thermal contribution is rejected should be tracked and reported in simulation metrics.

### F-004 — GAP — HPWH uses InternalGain for net zone-heat interaction that can be negative

**File:** `crates/hares-equipment/src/water_heater/heat_pump_wh.rs:794-801`

```rust
ports.accumulate(&PortContribution::Thermal {
    zone,
    sensible_gain_w,  // can be negative when COP > 1
    latent_gain_w,
    category: ThermalCategory::InternalGain,
})?;
```

`sensible_gain_w` is computed as `(hp_waste_w * shr + fan_parasitic_w + er_waste_w) * keep_fraction` where `hp_waste_w = compressor_power_w - delivered_hp_w`. When COP > 1, `hp_waste_w` is negative (the compressor extracts more thermal energy from the zone than the electrical input), making `sensible_gain_w` negative.

`ThermalCategory::InternalGain` is semantically defined as "waste heat from appliances, lighting, occupancy" — always a positive contribution. Using it for a value that may be negative is semantically incorrect and will confuse any monitoring or reporting tool that interprets the category. The comment at line 798 acknowledges this: "InternalGain captures the mixed character."

There is no existing category for zone heat extraction by a heat pump. The closest match would be `HvacCooling` (which represents intentional zone cooling), but the HPWH interaction is incidental rather than intentional.

**Consequence for physics:** Functionally correct. The signed value is accumulated into the zone accumulator and the thermal solver handles the sign correctly. The category breakdown in `sensible_by_category` will be wrong, but the `sensible_gain_w` total used by the solver is correct.

**Consequence for reporting:** `ThermalAccumulator::sensible_for_category(InternalGain)` will return a negative value when the HPWH is extracting more than it adds. Any dashboard or report assuming `InternalGain` is non-negative will misinterpret this.

**Fix:** Add a `HeatPumpExtraction` variant to `ThermalCategory` for signed zone-heat interactions from heat-pump appliances (HPWH, potentially ASHP). Update `THERMAL_CATEGORY_COUNT`, the `index()` match, and all consumers that iterate over categories. This is a data-model clarification with no physics impact.

### F-005 — GAP — HVAC ports() declaration does not reflect post-init multi-zone configuration

**Files:** `crates/hares-equipment/src/hvac/furnace.rs:107`, `air_conditioner.rs:212`, `heat_pump/heater.rs:228`

The `ports()` method returns the `self.ports` vec populated at `new()` time, which contains only `PortDeclaration::thermal(conditioned_zone)`. After `init()`, the HVAC equipment may route heat to `duct_zone_id` and `basement_zone_id`. Those zones are never added to `self.ports`.

This means `eq.ports()` is an incomplete and inaccurate contract. Any caller that uses `ports()` for zone discovery (e.g., a future static wiring validator, a visualizer, or an external orchestrator) will not know that this equipment touches additional zones. The dwelling builder is safe only because it adds all `env.zones` as a belt-and-suspenders measure.

**Distinction from F-002:** F-002 focuses on the correctness failure when the duct zone is not in env. This finding is about the broader contract violation: `ports()` must represent all zones the equipment may emit to, not just the primary zone.

### F-006 — GAP — Ventilation redefines KEY_ZONE_ID locally instead of importing from config.rs

**File:** `crates/hares-equipment/src/ventilation.rs:30`

```rust
const KEY_ZONE_ID: &str = "zone_id";
```

`crates/hares-equipment/src/config.rs:6` already defines this constant as `pub(crate) const KEY_ZONE_ID: &str = "zone_id"`. `Ventilation` redefines it rather than importing, creating a redundant definition that could drift if the key name ever changes. Other modules (`battery`, `generator`) correctly import from `config.rs`. HVAC helpers hardcode `"zone_id"` as a string literal in `zone_id_from_config()` at `helpers.rs:36` without using the constant at all.

**Consequence:** Currently harmless since all three spellings are identical. Risk surfaces if `KEY_ZONE_ID` is ever renamed: the ventilation local and the hvac helper literal would not be caught by a global rename.

**Fix:** `Ventilation` should import and use `crate::config::KEY_ZONE_ID`. `hvac/helpers.rs::zone_id_from_config()` should also use the constant.

### F-007 — ACCEPTABLE DIFFERENCE — ThermalAccumulator preserves per-category breakdown

**File:** `crates/hares-types/src/ports.rs:158-190`

`ThermalAccumulator` maintains both a total (`sensible_gain_w`, `latent_gain_w`) and a per-category array (`sensible_by_category: [f64; THERMAL_CATEGORY_COUNT]`). The thermal solver receives the full `ThermalAccumulator` struct, not just the summed total. Per-category access is available via `sensible_for_category()`.

No premature aggregation occurs at the accumulator level. The solver can distinguish HVAC heating from internal gains from jacket losses at query time. There is no information loss at this layer.

The per-category latent breakdown is not tracked (only `latent_gain_w` total is stored). This is acceptable for current modeling fidelity but would need to be revisited if latent heat by source becomes a reporting requirement.

### F-008 — IMPROVEMENT — Zone ID validation happens at runtime, not at registration time

**File:** `crates/hares-core/src/dwelling/mod.rs:892-905`

`PortSlots::from_declarations()` deduplicates and pre-sizes accumulators. Any zone ID declared by equipment that does not match a real simulation zone will simply not have an accumulator created for it from the equipment's own declaration. The dwelling builder patches this by also declaring all `env.zones`. There is no registration-time check that all equipment-declared zone IDs are valid zones in the simulation.

A validation step after equipment init — comparing each equipment's declared zones against `env.zones` — would catch misconfigured zone IDs before the first timestep rather than silently failing during `step()`.

**Recommended pattern:**
```rust
for eq in &equipment {
    for decl in eq.ports() {
        if let (PortType::Thermal, Some(zone)) = (decl.port_type, decl.zone) {
            if !initial_env.zones.iter().any(|z| z.id == zone) {
                return Err(HaresError::Equipment(format!(
                    "equipment '{}' declares zone {:?} which is not in simulation",
                    eq.descriptor().name, zone
                )));
            }
        }
    }
}
```

This is blocked by F-002/F-005 (incomplete port declarations) but should be implemented together with those fixes.

### F-009 — ACCEPTABLE DIFFERENCE — Zone ID default fallback to ZoneId(1) is ubiquitous

**Files:** All equipment constructors (13 instances of `unwrap_or(ZoneId(1))`)

Every equipment type that accepts a `zone_id` config key falls back to `ZoneId(1)` when the key is absent. `ZoneId(1)` is always the primary conditioned zone (first zone in `building.zones`, assigned `idx + 1 = 1`). This is consistent with OCHRE behavior where missing zone assignment defaults to the Indoor zone.

The silent fallback means a misconfigured equipment type (e.g., a water heater installed in an unconditioned garage that is missing `zone_id = 2`) will deposit jacket losses into the conditioned zone with no warning. This is not a code defect but it is a diagnosis gap.

**No code change required.** A tracing warn on fallback (similar to the `sensible_gain_fraction` warning at `scheduled_load.rs:259`) would improve observability.

### F-010 — ACCEPTABLE DIFFERENCE — HVAC category assignments are correct

All `PortContribution::Thermal` sites in HVAC equipment use the correct category:
- `furnace.rs`, `baseboard.rs`, `ideal_hvac.rs` (heating): use `HvacHeating` via `write_zone_thermal_contributions(... ThermalCategory::HvacHeating)`
- `air_conditioner.rs`, heat pump cooler: use `HvacCooling`
- `boiler.rs` jacket loss: uses `JacketLoss`

The duct loss contribution in `duct_distribution.rs:63-78` uses the same `category` parameter passed by the caller, so the duct-zone entry inherits the primary HVAC category (`HvacHeating` or `HvacCooling`). This is the correct choice: the heat in the duct zone is the same physical process (lost HVAC energy), not a distinct category.

### F-011 — ACCEPTABLE DIFFERENCE — Resistance WH and Gas WH jacket losses correctly categorized

**Files:** `water_heater/resistance.rs:538-543`, `water_heater/gas.rs:499-504`

Both use `ThermalCategory::JacketLoss` for the tank skin loss contribution. `skin_loss_w()` returns positive values only (heat out of tank into zone). Category is semantically correct.

### F-012 — GAP — Battery ohmic losses use InternalGain; heater path not posted to zone port

**File:** `crates/hares-equipment/src/battery/mod.rs:1037-1045`

Battery posts only `ohmic_loss_w` to the zone thermal port with `ThermalCategory::InternalGain`. The comment at line 1033-1036 explains that heater energy enters the cell thermal mass and reaches the zone through the UA model, so adding `heater_w` directly would double-count it.

The cell UA loss (`q_loss = cell_ua_w_per_k * (cell_temp_c - ambient_c)`) is computed but never posted to the zone port. This heat flows from the cell into the ambient zone each timestep but is silently omitted from `PortContribution::Thermal`.

The magnitude depends on the UA value and temperature differential. For a typical indoor residential battery at ~25°C cell and ~20°C room, `q_loss` is small. However it represents a genuine zone heat gain that is missing from the energy balance reported to the thermal solver.

**Fix:** Post `q_loss.max(0.0)` (heat from cell to zone) to the zone thermal port each step as `ThermalCategory::InternalGain`. Negative `q_loss` (zone heating the cell when zone is warmer than cell) should also be posted, as it represents heat extracted from the zone.

## Recommended Tests

### T-001 — ScheduledLoad garage/foundation zone routing test

Create a multi-zone environment with `ZoneId(1)` = conditioned, `ZoneId(2)` = foundation, `ZoneId(3)` = garage (intentionally reversed from constants). Configure a `ScheduledLoad` named `"Garage Lights"` without an explicit `zone_id`. Assert the thermal contribution lands in `ZoneId(2)` (actual garage zone) rather than `ZoneId(3)` (compile-time constant). This test will fail with the current code, confirming the bug.

### T-002 — HVAC duct-zone contribution routes to duct zone when present in env

Build a `GasFurnace` (or any HVAC type) with `duct_dse = 0.80` and `duct_zone_id = ZoneId(2)`. Create `PortSlots` with accumulators for both `ZoneId(1)` and `ZoneId(2)`. Step the equipment and assert:
- `ZoneId(1)` receives `sensible_gain_w * 0.80`
- `ZoneId(2)` receives `sensible_gain_w * 0.20`
- Total across zones equals gross capacity

This test already has partial coverage in `duct_distribution.rs` unit tests but those tests do not go through a full `step()` call.

### T-003 — HVAC step returns Err when duct_zone not in PortSlots

Configure a furnace with `duct_zone_id = ZoneId(99)` and build `PortSlots` with only `ZoneId(1)`. Call `step()` and assert it returns `Err`. This validates that duct-loss energy is not silently discarded when the target zone is absent. With the current code, the `?` propagation should return an error from `accumulate()`.

### T-004 — HPWH sensible_gain_w is negative when COP > 1

Build a `HeatPumpWH` with a high COP setting. Step it in HP mode. Assert `sensible_gain_w < 0` is posted to the thermal port (confirming the compressor extracts more heat from the zone than it adds). Verify the zone accumulator `sensible_gain_w` decreases by the expected magnitude.

### T-005 — Battery UA heat flow posted to zone

Build a `Battery` configured with a non-trivial `cell_ua_w_per_k` and a `zone_id`. Set `cell_temp_c` above zone temperature. After one step, assert the zone accumulator received a positive `sensible_gain_w` equal to `cell_ua_w_per_k * (cell_temp_c - zone_temp_c)` (this test will currently fail, confirming F-012).

### T-006 — Port declaration completeness after HVAC init

After calling `init()` on a furnace with `duct_zone_id` and `basement_zone_id` set, assert `eq.ports()` contains `PortDeclaration::thermal(duct_zone_id)` and `PortDeclaration::thermal(basement_zone_id)`. This test will currently fail (F-002/F-005).

### T-007 — Zone ID validation at dwelling construction rejects undeclared zones

Build a dwelling where an equipment's config specifies `zone_id = 99` but the building model has no `ZoneId(99)`. Assert that dwelling construction returns `Err` rather than silently creating a simulation that drops energy at runtime. This is the F-008 validation recommendation.

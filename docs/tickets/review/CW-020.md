## Background/Context

Wet appliances (clothes washer, clothes dryer, dishwasher, cooking range) are
event-based loads that also generate hot water demand. Config includes annual energy
(derived from HPXML rated values + DOE test adjustments), sensible/latent fractions,
hot water draw volumes per cycle, and gas/electric fuel split.

## Investigation Instructions

1. **Read OCHRE** `parse_clothes_washer()`, `parse_clothes_dryer()`, dishwasher
   parsing in `hpxml.py`:
   - Annual kWh derivation formulas (MEF, IMEF, CEF, rated kWh → actual kWh)
   - Hot water volume per cycle
   - Gas dryer split (electric parasitic vs gas)
   - Sensible/latent gain fractions (85% loss for vented dryer)

2. **Read HARES `resolve_loads.rs`:**
   - Compare each formula line-by-line with OCHRE.
   - Check gas cooking range: both `annual_electric_kwh` and `annual_gas_therms` are
     set to `22.6 + 2.7*n_bedrooms` — is the electric portion correct?

3. **Read HARES `event_load.rs`:**
   - Config keys consumed
   - Hot water demand emission — is `hot_water_draw_volume_l` per-cycle or total?
   - How are events triggered? Schedule-based? Stochastic?

4. **Build per-appliance comparison table.**

### F1 — Clothes Washer: no default for `RatedAnnualkWh`

**Severity: High**

**Location:** `crates/hares-io/src/hpxml/resolve_loads.rs:81-144`

HARES reads `RatedAnnualkWh` at line 81 and stores it as `annual_electric_kwh`. The actual-kWh conversion block at line 114 only runs `if let Some(rated_kwh) = params.get("annual_electric_kwh")...`. If the HPXML element omits `<RatedAnnualkWh>`, the block is skipped and the spec is emitted with no `annual_electric_kwh` key.

OCHRE `parse_clothes_washer()` line 1245 defaults to `400.0` unconditionally. HARES produces a zero-energy clothes washer silently.

**Fix:** Insert `let rated_kwh = child_f64(node, "RatedAnnualkWh").unwrap_or(400.0);` and use that directly in the conversion, rather than reading from the params map.

---

### F2 — Label rate fields not read from HPXML (washer and dishwasher)

**Severity: Medium**

**Location:** `crates/hares-io/src/hpxml/resolve_loads.rs:132-135, 244-246`

OCHRE reads `LabelGasRate`, `LabelAnnualGasCost`, and `LabelElectricRate` per-appliance from HPXML (lines 1248-1250 for washer, 1342-1344 for dishwasher) and uses them in the energy formula. HARES hardcodes all three as constants.

In practice most ResStock HPXMLs use exactly these default values, so the effect on standard parity runs is negligible. However, any HPXML with non-standard label rates will silently produce wrong annual energy, with no indication of the override being ignored.

**Fix:** Read `<LabelGasRate>`, `<LabelAnnualGasCost>`, `<LabelElectricRate>` from the appliance XML node and fall back to the hardcoded defaults only when absent.

### F3 — Hot water draw: per-event fixed volume vs. physics-derived daily average

**Severity: High**

**Location:**
- `crates/hares-io/src/hpxml/resolve_loads.rs:109` (washer: `15.0 L`)
- `crates/hares-io/src/hpxml/resolve_loads.rs:223` (dishwasher: `6.0 L`)
- `crates/hares-equipment/src/event_load.rs:891-900` (`hot_water_draw_volume_l / total_cycle_duration_s`)

OCHRE computes a physics-based `water_draw` in gal/day from the rated/actual energy difference and the `elec_h20` / `0.02504` water constants, then passes it as `Average Water Draw (L/day)` to the water heater via a separate schedule column (`hot_water_clothes_washer`, `hot_water_dishwasher` in `SCHEDULE_NAMES["Water"]`). The daily draw is spread over the schedule regardless of when appliance events fire.

HARES uses a fixed volume (15 L washer, 6 L dishwasher) **per event** and emits it as a flow rate only during the event. This has two problems:

1. The volume is not physics-derived (it does not depend on `RatedAnnualkWh`, `Capacity`, `n_bedrooms`, or `LabelUsage`), so it will differ from OCHRE's value for non-default inputs.
2. The delivery model differs: HARES concentrates the draw during events, OCHRE smears it across a normalized daily profile. This affects water heater thermal dynamics at sub-hourly resolution.

For the OCHRE defaults (3-bedroom, standard washer):
- `cw_appl ≈ 94.0 kWh`, `acy ≈ 295 cycles/yr`
- `water_draw ≈ (400 - 94) * 0.0178 * 295 / 365 ≈ 4.41 gal/day ≈ 16.7 L/day`
- Per event: `16.7 L/day / (295/365 events/day) ≈ 20.7 L/event` — not 15.0 L

For dishwasher defaults (3-bedroom, standard):
- `dwcpy ≈ 215 cycles/yr`, `kwh_per_cyc ≈ 0.477 kWh`
- `water_draw ≈ (467 - 0.477*208)*0.02504*215/365 ≈ 3.47 gal/day ≈ 13.1 L/day`
- Per event: `13.1 * 365 / 215 ≈ 22.2 L/event` — not 6.0 L

The washer 15 L is ~27% low; the dishwasher 6.0 L is ~73% low. These are not calibration differences — they are structural mismatches in both magnitude and delivery timing.

**Fix:** Derive water draw volume per event from OCHRE's formula, using the same rated/label parameters already computed for annual kWh. The per-event volume in liters is `water_draw_gal_per_day * 3.78541 * 365.0 / acy` for the washer and `water_draw_gal_per_day * 3.78541 * 365.0 / dwcpy` for the dishwasher.

### F4 — Gas dryer sensible gain fraction: static 0.89 vs energy-weighted blend

**Severity: Low**

**Location:** `crates/hares-io/src/hpxml/resolve_loads.rs:164`

OCHRE `parse_clothes_dryer()` line 1321-1323 computes `frac_sens` for gas dryers as a weighted blend:

```
frac_sens = (1 - frac_lost) * (0.90 * elec_btu + 0.8894 * gas_btu) / (elec_btu + gas_btu)
```

where `elec_btu` and `gas_btu` are the actual computed annual energies converted to BTU. HARES hardcodes `0.89` for all gas dryers regardless of CEF, venting status, or actual electric/gas split.

For default CEF=3.01 and vented, the electric fraction is ~7% of total BTU input. The OCHRE weighted value would be approximately `0.8899`, so the approximation error is ~0.0001 for sensible fraction — negligible for typical inputs. However, for unusual CEF values where the electric/gas ratio shifts, the error could be larger. The static approximation is an unnecessary deviation from the reference formula; the actual formula is cheap to compute since `annual_kwh` and `annual_therm` are already in scope.

**Fix:** Compute the energy-weighted blend directly. When `annual_kwh` and `annual_therm` are both in scope (from the dryer energy computation), use them to weight the 0.90 and 0.8894 heat fractions.

### F5 — Dishwasher: no default for `RatedAnnualkWh`; conversion silently skipped

**Severity: High**

**Location:** `crates/hares-io/src/hpxml/resolve_loads.rs:228-256`

OCHRE line 1338 defaults `rated_annual_kwh = 467.0`. HARES only enters the conversion block `if let Some(rated_kwh) = params.get("annual_electric_kwh")...`. If HPXML has no `<RatedAnnualkWh>`, the spec is emitted with no `annual_electric_kwh` and no `annual_gas_therms`, producing a silent zero-energy dishwasher. The default_gain_fractions are still injected, so the appliance exists as a zone heat source with zero power.

**Fix:** Same pattern as F1 — read with an explicit default of 467.0 and apply the conversion unconditionally.

### F6 — Gas cooking range: `annual_electric_kwh` = gas formula value (suspected bug)

**Severity: Medium**

**Location:** `crates/hares-io/src/hpxml/resolve_loads.rs:279-282`

```rust
let annual_kwh = (22.6 + 2.7 * n_bedrooms) * multiplier;
let annual_therm = oven_ef * (22.6 + 2.7 * n_bedrooms) * multiplier;
params.insert("annual_electric_kwh".to_string(), json!(annual_kwh));
params.insert("annual_gas_therms".to_string(), json!(annual_therm));
```

`annual_kwh` is set to `22.6 + 2.7*n_bedrooms`, which is the same formula as the gas consumption. This appears to model the electric parasitic load of a gas range, which is correct: OCHRE uses `22.6 + 2.7*n_bedrooms` kWh/yr for the electric parasitic (ignition, clock, fan). The electric and gas values happen to use the same bedroom-scaled formula in OCHRE. However, `oven_ef` (defaulted to 1.0 here because `IsConvection` is not read) is applied to the therm value but not the kWh value, which is the correct OCHRE behavior since oven efficiency only affects gas consumption. This is not a bug.

The issue noted in the Review Notes ("both set to same value") is true in the default case but is correct: the OCHRE formula for electric parasitic of a gas range is `(22.6 + 2.7*n_bedrooms)` kWh/yr regardless of `oven_ef`. `oven_ef` would only deviate from 1.0 for convection ovens, which requires reading `<IsConvection>` from the sibling `<Oven>` node — HARES acknowledges this gap in the comment at line 272 but defaults to 1.0 rather than reading the field.

**Fix (partial):** Read `<IsConvection>` from the sibling `<Oven>` node and set `oven_ef = 0.80` for convection, 1.0 otherwise. This matches OCHRE. Without this, gas convection ovens compute 25% too much gas consumption.

### F7 — Event triggering model: schedule wrapping does not validate schedule length

**Severity: Low**

**Location:** `crates/hares-equipment/src/event_load.rs:507`, `963`

Both `EventBasedLoad` and `WetAppliance` use `self.current_step % self.schedule_len.max(1)` to wrap the step counter. If `schedule_len` is 0 (the fallback case when the `extracted_events` vec is non-empty but `schedule_len` was never set), `max(1)` prevents a divide-by-zero but produces incorrect step indexing. This condition cannot arise in practice given current `init()` logic, but it is fragile.

**Fix:** Assert or return an error in `init()` if `!kw_series.is_empty() && kw_series.len() == 0` (impossible by definition) — more usefully, add a debug-mode assertion that `schedule_len > 0` whenever `extracted_events` is non-empty.

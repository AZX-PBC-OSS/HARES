## Background/Context

ASHP cooling mode uses different curves and parameters than heating mode. The cooling
side of a heat pump has SEER/EER ratings, SHR, and different biquadratic curves.

## Investigation Instructions

1. Read OCHRE `ASHPCooler.py` — all config keys.
2. Read HARES `heat_pump/cooler.rs` — config keys consumed.
3. Read `resolve_hvac.rs` — how does HARES create the cooler spec from the same
   HPXML `HeatPump` element that also produces the heater spec?
4. Build comparison table.
5. Pay attention to: SHR, cooling-specific biquadratic curves, min outdoor temp.

### F-1 — SEER/EER key mismatch: resolver emits `efficiency_seer`, equipment reads `["seer", "SEER"]`

**Severity: High**

`crates/hares-io/src/hpxml/resolve_hvac.rs:643–650` — `insert_annual_efficiency` emits keys of the form `efficiency_{units_lowercase}`, so a HPXML `AnnualCoolingEfficiency` element with units `SEER` produces key `efficiency_seer`. When the efficiency is specified via a bare `<SEER>` child tag it also emits `efficiency_seer`.

`crates/hares-equipment/src/hvac/air_conditioner.rs:423–430` — `init` only looks for the keys `"seer"` and `"SEER"` when computing the SEER-derived default EIR:

```rust
let default_eir =
    first_f64(config, &["seer", "SEER"]).map_or(DEFAULT_EIR_FALLBACK, |seer| { … });
```

Neither `"efficiency_seer"` nor `"cooling_efficiency"` appear in that lookup. The consequence is that an ASHP cooler loaded from HPXML always falls through to `DEFAULT_EIR_FALLBACK = 0.35` (EER ≈ 9.8) instead of using the actual rated SEER. Capacity stage EIR values derived from the multispeed lookup — written as `cooling_eir_stage_N` — are read correctly, so the error applies primarily to single-speed systems or as the fallback EIR used for stage-count selection logic.

The `apply_default_hvac_speed_fallback` function at line 701 correctly reads `"efficiency_seer"` when choosing the number of speeds, but the equipment `init` never did, so the EIR is wrong even when the speed count is right.

**Fix:** Add `"efficiency_seer"`, `"cooling_efficiency"` (with a units check against SEER), and `"efficiency_eer"` to the lookup list in `air_conditioner.rs`. For EER, apply the conversion `EIR = BTU_PER_HR_PER_W / eer` (same formula). For `"cooling_efficiency"` the units key `"cooling_efficiency_units"` must be inspected before treating the value as SEER vs. EER.

### F-2 — Flow-fraction biquadratic curves (cap_ff / eir_ff) not propagated through defaults pipeline

**Severity: Medium**

OCHRE loads separate polynomial triples for each speed stage:
- `cap_ff`: capacity multiplier as a function of airflow fraction
- `eir_ff`: EIR multiplier as a function of airflow fraction

`crates/hares-io/src/defaults.rs:54–61` — `HvacCurveVariant` stores `cap_ff: [f64; 3]` and `eir_ff: [f64; 3]` (the field names are present in the struct), but `crates/hares-io/src/hpxml/resolve_hvac.rs:901–924` — `serialize_stage_plr_coefficients` and `select_primary_curve_pair` only serialise `eir_plr` and the temperature (`cap_t`, `eir_t`) 6-coefficient curves. The ff-correction triples are never written into the params map and thus are never passed to the equipment.

In `crates/hares-equipment/src/hvac/hvac_core.rs`, the `HvacEquipment` struct has no field for per-stage ff-correction coefficients, so even if they were emitted they would not be consumed. OCHRE uses these to adjust capacity and EIR when the actual airflow fraction deviates from the rated condition; HARES currently applies the default `flow_fraction_correction = 1.0` scalar everywhere.

For ASHP cooling this matters at low-speed operation where airflow is proportionally reduced: OCHRE's `cap_ff` for the `Single_1` curve is `[0.718664, 0.417974, -0.136638]`, which at `ff = 0.7` gives a multiplier of ~0.91 — a 9% capacity penalty that HARES silently omits.

**Fix:** Extend the HPXML resolver's `apply_multispeed_parameters` to also serialise per-speed `cap_ff` and `eir_ff` triples. Add corresponding fields to `HvacEquipment` and apply them in `calculate_performance` when evaluating the biquadratic.

### F-3 — Per-speed biquadratic temperature bounds not loaded from defaults

**Severity: Medium**

OCHRE's biquadratic CSV (`vendors/OCHRE/ochre/defaults/HVAC Cooling/Biquadratic ASHP Cooler.csv`) carries per-speed input clamping bounds:
- `min_Twb = 13.88°C`, `max_Twb = 23.88°C` (indoor wet-bulb)
- `min_Tdb = 18.33°C`, `max_Tdb = 51.66°C` (outdoor dry-bulb)

`crates/hares-io/src/defaults.rs:54–61` — `HvacCurveVariant` has no fields for these bounds. They are therefore not loaded, not stored, and not emitted by the resolver.

`crates/hares-equipment/src/hvac/hvac_core.rs:185–186` — `HvacEquipment` has `biquadratic_x1_bounds` and `biquadratic_x2_bounds` fields, defaulting to `(-100.0, 100.0)` per `DEFAULT_BIQUADRATIC_X1_BOUNDS`/`DEFAULT_BIQUADRATIC_X2_BOUNDS`. They can be overridden via `biquadratic_x1_min/max` config keys, but those keys are never written by the resolver.

The practical consequence is that HARES will extrapolate the biquadratic outside OCHRE's calibrated operating window (e.g. at an outdoor DB of 52°C or an indoor WB of 12°C), producing physically unrealistic capacity and EIR values that would otherwise be clamped to the curve boundary.

**Fix:** Add `min_twb`, `max_twb`, `min_tdb`, `max_tdb` fields to `HvacCurveVariant`. Load them from the TOML defaults files. Have the resolver emit `biquadratic_x1_min`, `biquadratic_x1_max`, `biquadratic_x2_min`, `biquadratic_x2_max` when a single-speed curve is selected, or the tightest per-speed bounds when multispeed.

### F-4 — Low-efficiency single-speed PLR correction (SEER < 13) not implemented

**Severity: Low–Medium**

`vendors/OCHRE/ochre/Equipment/HVAC.py:1065–1068` — `AirConditioner.__init__` (which `ASHPCooler` inherits) overrides the `eir_plr` polynomial for single-speed, low-efficiency equipment:

```python
if self.n_speeds == 1 and seer < 13 and self.biquad_params is not None:
    self.biquad_params[1]["eir_plf"] = np.array([0.8, 0.2, 0])
```

This replaces the default PLR curve `[0.93, 0.07, 0]` with `[0.8, 0.2, 0]`, increasing the part-load penalty for older, less efficient equipment. HARES has no equivalent in `resolve_hvac.rs` or `air_conditioner.rs`. The startup-degradation coefficient (`C_d`) is set correctly per F-1 concerns; this is an independent PLR curve override.

**Fix:** After `insert_startup_degradation` is called in `apply_multispeed_parameters` (or as a separate post-processing step), detect single-speed cooling equipment with SEER < 13 and inject `eir_plr_coefficients = "[0.8, 0.2, 0.0]"` into the params map.

### F-5 — Multispeed per-stage SHR not emitted by resolver

**Severity: Low–Medium**

`vendors/OCHRE/ochre/Equipment/HVAC.py:795–796` — for multispeed equipment, OCHRE replaces the scalar SHR with a per-stage list loaded from the multispeed parameters CSV:

```python
kwargs["SHR (-)"] = [speed_params[f"SHR {i + 1}"] for i in range(self.n_speeds)]
```

`crates/hares-io/src/defaults.rs:79` — `HvacMultispeedParameters` has a `shrs: Vec<f64>` field, populated from the CSV. However `crates/hares-io/src/hpxml/resolve_hvac.rs:860–898` — `apply_multispeed_parameters` writes per-stage `cooling_capacity_w_stage_N` and `cooling_eir_stage_N` but never writes `shr_stage_N` or any equivalent per-stage SHR.

`crates/hares-equipment/src/hvac/air_conditioner.rs:468–470` — only a single scalar rated SHR is read:

```rust
let rated_shr = first_f64(config, &["rated_shr", "shr", "SHR", "shr_rated"]).unwrap_or(0.75);
```

For two-speed and variable-speed ASHPs this means all stages use the same rated SHR (from the HPXML scalar field or the 0.75 fallback), whereas OCHRE uses different SHRs at low vs. high speed. This has a secondary effect on the coil Ao computation, which also uses the rated SHR.

**Fix:** In `apply_multispeed_parameters`, iterate `multispeed.shrs` and emit `shr_stage_N` params. In `air_conditioner.rs`, load these into a `Vec<f64>` alongside `cooling_capacities_w` and apply the per-stage SHR in `calculate_performance`.

---

### Crankcase space_fraction scaling — minor semantic difference

**Severity: Informational**

OCHRE scales crankcase power by `self.space_fraction` at the point of addition (`HVAC.py:1077`). HARES multiplies the *entire* `electric_kw` (compressor + fan + crankcase) by `self.hvac.space_fraction` at `air_conditioner.rs:667`. The result is numerically identical because the same scalar is applied; this is not a bug.

---

### Bounds check: OCHRE ASHPCooler crankcase is inherited from AirConditioner (50 W / 12.78°C), not overridden

A commented-out line in `HVAC.py:1091` reads `# crankcase_kw = 0.020`. The active values remain 50 W / 12.78°C for `ASHPCooler`. HARES correctly uses `CRANKCASE_HEATER_KW = 0.05` and `CRANKCASE_HEATER_THRESHOLD_C = 12.8` for `ashp_cooler()` and applies the 15 W / 0°C override only for `mshp_cooler()`. This matches OCHRE.

## Background/Context

When equipment is registered with a dwelling, its port declarations, zone assignments,
and execution stage are set. If any of these are wrong, the equipment silently
produces incorrect results: thermal contributions to wrong zones, electrical
contributions missing from totals, or equipment running at the wrong point in the
step sequence.

## Investigation Instructions

1. **Trace equipment registration path:**
   - How does `EquipmentRegistry` validate a new equipment instance?
   - Are port declarations checked against the dwelling's known zones?
   - Can equipment declare a zone that doesn't exist?
   - Can equipment declare overlapping or conflicting ports?

2. **Trace execution stage assignment:**
   - How is `ExecutionStage` determined per equipment?
   - Is the stage order correct? (Solvers before equipment? Equipment before actors?)
   - Can two equipment types that must run in sequence be accidentally parallelized?

3. **Trace port wiring in dwelling step:**
   - How does the dwelling collect port contributions from all equipment?
   - Is there a validation step that checks total energy balance?
   - What happens if equipment emits a `Fluid` port but no water heater reads it?

4. **Check for orphaned equipment:**
   - Can equipment be registered but never stepped?
   - Can equipment be stepped but its ports never collected?

5. **Assess validation opportunities:**
   - Init-time validation: verify all declared zones exist, all required ports are
     connected, all config keys are consumed.
   - Runtime invariant: energy in = energy out (within numerical tolerance).

## Findings

### F-001 — BUG — CRITICAL: `"Electric Vehicle"` name never registered; all HPXML-parsed EVs silently dropped

**Files:** `crates/hares-io/src/hpxml/resolve_der.rs:123`, `crates/hares-io/src/hpxml/resolve_loads.rs:429`, `crates/hares-equipment/src/ev/mod.rs:1111`

Both HPXML EV resolution paths emit the name `"Electric Vehicle"`:
- `resolve_der.rs:123`: `build_spec("Electric Vehicle".to_string(), ...)`
- `resolve_loads.rs:429`: `build_spec("Electric Vehicle".to_string(), ...)`

The equipment registry at `ev/mod.rs:1111` registers `"EV"` and `"Scheduled EV"`, but never `"Electric Vehicle"`. `equipment_config_from_spec` maps `ochre_class = spec.name` (`conversions.rs:338`), so `registry.create("Electric Vehicle", ...)` returns `Err(HaresError::Equipment("unknown equipment class: Electric Vehicle"))`. The dwelling loop at `mod.rs:864-874` catches this error, emits a `tracing::warn!`, pushes to `warnings`, and `continue`s. The EV is silently absent from the simulation. No user-visible error is returned; `Dwelling::from_config` succeeds.

This means **every HPXML building with an EV (both ResStock DER path and MiscLoads path) silently runs without the EV**. The simulation completes with a warnings list that would only be visible to callers who inspect `dwelling.warnings`.

---

### F-002 — BUG — HIGH: `"Gas Tankless Water Heater"` name never registered

**Files:** `crates/hares-io/src/hpxml/resolve_water_heater.rs:340`, `crates/hares-equipment/src/water_heater/tankless.rs:442`

`canonical_water_heater_name` at `resolve_water_heater.rs:340` produces `"Gas Tankless Water Heater"` for `(instantaneous water heater, Gas)`. The registry at `tankless.rs:442` only registers `"Tankless Water Heater"`. There is no `"Gas Tankless Water Heater"` entry. Gas instantaneous water heaters will always silently drop via the same `continue` path as F-001.

---

### F-003 — BUG — HIGH: `"Generic Heater"` and `"Generic Cooler"` fallback names never registered

**Files:** `crates/hares-io/src/hpxml/resolve_hvac.rs:583`, `crates/hares-io/src/hpxml/resolve_hvac.rs:591`

`canonical_hvac_heating_name` falls back to `"Generic Heater"` for any `(system_type, fuel)` combination that is not explicitly matched (e.g. `Propane`/`Oil` furnaces except as Gas, or unknown `FuelType::None`). `canonical_hvac_cooling_name` falls back to `"Generic Cooler"` for anything that is not `"central air conditioner"` or `"room air conditioner"`. Neither string is registered in the registry. Affected buildings silently lose their primary HVAC equipment.

---

### F-004 — BUG — MEDIUM: `"Water Heating"` fallback name never registered

**Files:** `crates/hares-io/src/hpxml/resolve_water_heater.rs:341`

`canonical_water_heater_name` falls back to `"Water Heating"` for any unrecognized `(wh_type, fuel)` combination. This string has no registry entry. Buildings with non-standard water heater types silently drop their DHW equipment.

---

### F-005 — GAP — HIGH: `EquipmentRegistry::register` silently overwrites existing entries

**File:** `crates/hares-equipment/src/registry.rs:44`

`register` calls `self.factories.insert(ochre_class.into(), factory)` with no check for an existing key. A caller invoking `register` twice with the same name silently replaces the first factory. For the built-in registry in `EquipmentRegistry::new`, this is not currently exploited, but the Python extensibility layer (`hares-python`) can call `register` via the public API and silently shadow built-in equipment. There is no diagnostic when a key is overwritten.

---

### F-006 — GAP — HIGH: No zone existence validation at equipment init time

**Files:** `crates/hares-core/src/dwelling/mod.rs:892-904`, `crates/hares-equipment/src/hvac/helpers.rs:35`

`zone_id_from_config` parses a zone ID from config (`helpers.rs:35`) and falls back to `ZoneId(1)` when absent. No check is made at dwelling construction time to confirm that the zone ID declared in a piece of equipment's port declaration actually exists in `initial_env.zones`. The `PortSlots::from_declarations` code at `ports.rs:346` allocates accumulators for every declared zone ID without cross-referencing the actual building's zone list.

Consequence: if equipment declares `ZoneId(3)` but the building only has zones 1 and 2, a thermal accumulator is created for zone 3. The thermal solver reads zone temperatures only from the accumulators whose IDs match `EnvironmentState::zones`; an orphaned accumulator receives heat gains that are never applied to any zone temperature. Energy from HVAC effectively vanishes without error.

---

### F-007 — GAP — MEDIUM: No zone existence validation when equipment steps emit port contributions to undeclared zones

**Files:** `crates/hares-types/src/ports.rs:414-421`, `crates/hares-equipment/src/hvac/duct_distribution.rs:63`

`PortSlots::accumulate` returns `Err(HaresError::Equipment("undeclared thermal zone: ..."))` when a `PortContribution::Thermal` targets a zone that was not declared in `from_declarations`. The `step` error path in the dwelling hot loop at `mod.rs:1945-1950` and `1998-2003` pushes this to `warnings` and continues. A misconfigured zone ID therefore produces one warning per timestep (8760 warnings for an annual run) but no simulation abort and no energy balance signal. The mismatch between `ports()` declaration and `zone_id` used in `step()` is structurally possible if someone constructs equipment outside the registry.

---

### F-008 — GAP — MEDIUM: Equipment `init` failures are soft-silenced with continue

**File:** `crates/hares-core/src/dwelling/mod.rs:877-889`

When `eq.init(&merged_cfg, &initial_env)` returns `Err`, the dwelling pushes a warning and skips the equipment with `continue`. For safety-critical equipment (HVAC, water heater), this means the simulation proceeds with thermally unconditioned zones and unheated water — producing wrong results rather than an initialization error. The comment says "Non-critical equipment (appliances, loads) may lack schedule data", but the same path handles HVAC and water heater init failures.

---

### F-009 — GAP — MEDIUM: Registry `create` failure treated as warning-only, not error

**File:** `crates/hares-core/src/dwelling/mod.rs:862-874`

`registry.create` returning `Err` is handled with `tracing::warn!` + `continue`. Callers who do not inspect `dwelling.warnings` have no signal that a named piece of equipment was absent. There is no way for the Python layer or integration tests to assert "all expected equipment was instantiated" without explicitly checking `dwelling.warnings()` after construction.

---

### F-010 — GAP — LOW: `ExecutionStage::EnvelopeResolution` is a dead variant for equipment

**File:** `crates/hares-types/src/equipment.rs:160`

`ExecutionStage` has four variants; `EnvelopeResolution` is listed with the comment "used by domain solvers". However, `stage_rank` at `conversions.rs:280` assigns rank 3 to `EnvelopeResolution`, so any equipment that declares this stage would step after all thermal equipment and before the solver is called — which is likely not the intent. No existing equipment uses `EnvelopeResolution`. The variant should either be documented as equipment-forbidden or removed from the `ExecutionStage` enum that `Equipment::descriptor()` uses.

---

### F-011 — GAP — LOW: Intra-stage execution order is non-deterministic (HashMap insertion order)

**File:** `crates/hares-core/src/dwelling/mod.rs:381-385`

`compute_equipment_execution_order` sorts by `stage_rank` only. Within a single stage (e.g. `Independent`), equipment order is the order they were pushed into the `Vec<Box<dyn Equipment>>`, which is determined by the order `resolve_equipment` emits specs, which is document-parse order. This is deterministic for a given HPXML file but is not guaranteed by any invariant or test. Adding equipment at runtime via `add_equipment` appends and may break inter-equipment assumptions within a stage.

---

### F-012 — ACCEPTABLE DIFFERENCE: `PortSlots` deduplicate overlapping thermal zone declarations

**File:** `crates/hares-types/src/ports.rs:353-358`

`from_declarations` deduplicates thermal zone accumulators (only one accumulator per zone ID). Multiple pieces of equipment declaring the same zone therefore share one accumulator and both contributions are summed. This is the correct and intended behavior.

---

### F-013 — ACCEPTABLE DIFFERENCE: Fluid port contributions with no reader are silently discarded

**File:** `crates/hares-types/src/ports.rs:440-457`

If equipment emits a `PortContribution::Fluid` for a loop that was not declared in `from_declarations`, an error is returned. The error propagates up through the `step()` return, is caught by the dwelling hot loop, pushed to warnings, and skipped. In practice, water heaters emit fluid contributions on `DHW_DEMAND_LOOP`; if no water heater is present (e.g. it was silently skipped due to F-001/F-002/F-004), the fluid port accumulator for that loop will not be registered, and the loop energy is silently lost. This is a consequence of F-001–F-004, not an independent defect.

---

### F-014 — IMPROVEMENT: No public API to query which equipment failed to register

**File:** `crates/hares-core/src/dwelling/mod.rs:794`

`Dwelling::warnings` is not exposed as a public method in the visible API surface. Callers who construct a `Dwelling` and want to assert that all equipment was instantiated must either iterate `dwelling.equipment()` and compare names against expected equipment, or inspect the internal `warnings` field. A dedicated `equipment_registration_errors()` method that surfaces only equipment init/create failures (as opposed to runtime step warnings) would allow callers to gate on complete equipment installation.

## Recommended Tests

### T-001: Registration coverage exhaustive check

Write a test in `crates/hares-equipment/tests/` that constructs an `EquipmentRegistry::new()` and asserts that every canonical name from the HPXML resolvers has a registered factory. Use the same string constants as the resolvers. This test would have caught F-001 through F-004.

```rust
#[test]
fn all_canonical_resolver_names_are_registered() {
    let registry = EquipmentRegistry::new();
    let expected = [
        "Gas Furnace", "Electric Furnace", "Electric Baseboard",
        "Gas Boiler", "Electric Boiler", "Air Conditioner", "Room AC",
        "ASHP Heater", "MSHP Heater", "ASHP Cooler", "MSHP Cooler", "Ideal HVAC",
        "Electric Resistance Water Heater", "Tankless Water Heater",
        "Heat Pump Water Heater", "Gas Water Heater", "Gas Tankless Water Heater",
        "PV", "Battery", "Electric Vehicle", "Gas Generator",
        "Clothes Washer", "Clothes Dryer", "Dishwasher", "Refrigerator",
        "Freezer", "Cooking Range", "TV", "Well Pump", "MELs",
        "Indoor Lighting", "Exterior Lighting", "Garage Lighting",
        "Basement Lighting", "Ceiling Fan", "Ventilation Fan",
        "Pool Pump", "Pool Heater", "Spa Pump", "Spa Heater",
    ];
    for name in expected {
        assert!(registry.get(name).is_some(), "no factory for '{name}'");
    }
}
```

### T-002: EV silently dropped integration test

Write a test that parses a minimal HPXML with an `ElectricVehicle` element (via the `Systems/ElectricVehicles` path) and asserts that exactly one piece of EV equipment is present in the constructed `Dwelling`. This directly tests the F-001 path.

### T-003: Equipment init failure does not abort; but critical equipment failure should be detectable

Write a test that verifies `dwelling.warnings` is non-empty when an equipment class is not registered, and that the dwelling still constructs. Add an assertion mode (perhaps gated on a config flag) where critical equipment classes (HVAC, water heater) failing to register cause an error return rather than a warning.

### T-004: Zone ID out of range produces orphaned accumulator

Write a test that constructs equipment with `zone_id = 99` in a single-zone building (zones: `[ZoneId(1)]`). Assert that no thermal contribution from that equipment appears in the zone's temperature trajectory across multiple steps (i.e., the orphaned accumulator is not summed into zone 1 and no panic occurs).

### T-005: `register` overwrites without warning

Write a test that calls `registry.register("Gas Furnace", factory_a)` followed by `registry.register("Gas Furnace", factory_b)` and asserts that `factory_b` is used, then file a separate ticket to add a `debug_assert!` or `tracing::warn!` on overwrite.

### T-006: Stage ordering verification

Extend the existing stage ordering test at `mod.rs:2931` to also verify that within the `Independent` stage, equipment with both electrical and thermal contributions can coexist without ordering dependency, and that equipment declaring `EnvelopeResolution` would step after thermal equipment.

## Review Notes

- Critical: `ochre_class: spec.name.clone()` at `conversions.rs` is the registration lookup key. If HPXML parsing produces a name with a trailing instance number (e.g., "Gas Furnace 1"), `registry.create` returns an error and the equipment is silently skipped.
- `ExecutionStage` has four variants: `Independent`, `Electrical`, `Thermal`, `EnvelopeResolution`. Verify stage ordering and intra-stage ordering (e.g., PV before battery in `Electrical`).
- Investigation question: "Trace every canonical name string from HPXML resolvers. For each, verify it matches exactly one registered key. What is the error behavior when `registry.create()` fails?"

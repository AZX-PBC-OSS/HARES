## Background/Context

Room ACs differ from central ACs: no ducts (DSE=1), different EER ranges, typically
single-speed. RV-015 added this equipment type. Config wiring must be verified.

## Investigation Instructions

1. Read OCHRE `RoomAC.py` — all config keys and how they differ from central AC.
2. Read HARES — how is room AC distinguished from central AC? Same struct or different?
3. Verify DSE=1 (no ducts) for room AC.
4. Build comparison table.

### F1 (SEVERITY: HIGH) — EER-specified Room AC silently uses fallback efficiency

**Files:** `crates/hares-io/src/hpxml/resolve_hvac.rs:641-650`, `crates/hares-equipment/src/hvac/air_conditioner.rs:423-430`

Room ACs are standardized on EER (AHRI 310/380), not SEER. HPXML emits them with
`<AnnualCoolingEfficiency><Units>EER</Units><Value>10</Value></AnnualCoolingEfficiency>`
or the bare `<EER>10</EER>` tag.

`insert_annual_efficiency` correctly stores `cooling_efficiency_units = "EER"` and
`cooling_efficiency = 10.0`, or `efficiency_eer = 10.0` for the bare tag. However,
`CoolingCore::init` only reads SEER to derive the default EIR:

```rust
// air_conditioner.rs:423
let default_eir = first_f64(config, &["seer", "SEER"]).map_or(DEFAULT_EIR_FALLBACK, ...);
```

Neither `efficiency_eer` nor `cooling_efficiency` (with `cooling_efficiency_units == "EER"`)
are consulted. An EER-specified Room AC silently uses `DEFAULT_EIR_FALLBACK = 0.35`
(≈ 2.86 COP, corresponding to SEER ≈ 9.8), regardless of the actual rating.

OCHRE handles EER and SEER identically (both are converted via `Btu/hour → W`, the same
formula), so EER 10 → COP 2.931, EIR 0.341. HARES produces 0.35 instead.

`apply_default_hvac_speed_fallback` also fails for EER inputs: it reads `efficiency_seer`
(absent) and falls back to `seer = 0.0`, forcing `n_speeds = 1`. For Room AC this
happens to be correct (Room AC is always single-speed), but the fallback is wrong and
fragile.

**Fix:** In `CoolingCore::init`, after the SEER lookup, also check
`efficiency_eer` / `efficiency_eer2` / `cooling_efficiency` (when
`cooling_efficiency_units == "EER"`). EER and SEER use the same conversion
formula (both are BTU/hr/W), so `eir = BTU_PER_HR_PER_W / eer_value`.

### F2 (SEVERITY: HIGH) — Room AC Cd silently set to 0.07 instead of 0.22 via HPXML path

**Files:** `crates/hares-io/src/hpxml/resolve_hvac.rs:756`, `crates/hares-equipment/src/hvac/air_conditioner.rs:383-390`

`calc_startup_degradation` contains the check:

```rust
// resolve_hvac.rs:756
} else if equipment_name == "room ac" {
    0.22
```

`insert_startup_degradation` is called with `&name` where `name = "Room AC"` (from
`canonical_hvac_cooling_name`). The string `"Room AC" != "room ac"`, so the match fails
and Room AC falls into the single-speed branch:

```
SEER = 13.0 (default, since EER path is also broken per F1) → Cd = 0.07
```

`startup_cd = 0.07` is then written into params. When `CoolingCore::init` runs its
Room AC branch, it guards with:

```rust
// air_conditioner.rs:383-387
let explicit_cd = config.get_f64("startup_cd")  // = Some(0.07) from params
    .or_else(...)
if explicit_cd.is_none() {         // false — explicit_cd is Some(0.07)
    self.hvac.plf_cooling_degradation_coeff = 0.22;  // never reached
```

The 0.22 override in `CoolingCore::init` is never reached because `startup_cd`
is already present. The result is Cd = 0.07 instead of the correct 0.22 per AHRI
and OCHRE.

OCHRE unconditionally returns 0.22 for `name == "Room AC"` in `calc_c_d`.

The unit test `c_d_cooling_room_ac` at `resolve_hvac.rs:1106` passes only because it
calls `calc_startup_degradation(false, "room ac", ...)` directly — it does not exercise
the full `insert_startup_degradation("Room AC", ...)` call path.

**Fix:** Change the comparison in `calc_startup_degradation` to
`equipment_name.eq_ignore_ascii_case("room ac")`, or normalize the name to lowercase
before calling `calc_startup_degradation`. Also add an integration test that calls
`insert_startup_degradation("Room AC", false)` and asserts `startup_cd == 0.22`.

### F3 (SEVERITY: LOW) — Flow-fraction correction uses a scalar instead of a quadratic curve

**Files:** `crates/hares-equipment/src/hvac/hvac_core.rs:738-748`, `crates/hares-equipment/src/hvac/air_conditioner.rs:809-848`

OCHRE evaluates a per-speed quadratic curve for both capacity and EIR as a function of
airflow fraction (FF): `ff_ratio = a + b·FF + c·FF²`. For Room AC the defaults are
`cap_ff = [0.887, 0.1128, 0]` and `eir_ff = [1.763, -0.6081, 0]`.

HARES replaces this with a constant scalar `flow_fraction_correction` (default 1.0),
applied multiplicatively at evaluation time in `evaluate_biquadratic_with_flow`.

At rated conditions FF = 1.0, giving OCHRE: `cap_ff(1) = 0.887 + 0.1128 = 0.9998 ≈ 1.0`
and `eir_ff(1) = 1.763 - 0.6081 = 1.1549`. The EIR FF curve at rated conditions is
**not 1.0** — it applies a 15% upward correction to EIR at rated flow. This discrepancy
will compound with off-rated airflow conditions (e.g. airflow defect ratio ≠ 1.0).

This is a bounded correctness gap rather than a structural omission: in many HPXML
simulations airflow defect ratio is absent (defaults to 1.0), so the deviation only
manifests under ResStock airflow defect scenarios. However it affects all cooling
equipment, not just Room AC.

### F4 (SEVERITY: INFO) — 320 vs 312 CFM/ton airflow divergence from OCHRE

**Files:** `crates/hares-equipment/src/hvac/hvac_core.rs:72`

HARES uses 320 CFM/ton for Room AC (per comment: "manufacturer data median across 5+
products, AHRI 310/380 conditions"). OCHRE uses 312 CFM/ton for all non-heater static
equipment (from ResStock hvac.rb line 2623). This is a deliberate divergence documented
in a code comment. No action required unless OCHRE parity is needed.

### Summary of Correctness Impact

Both F1 and F2 affect every Room AC loaded from HPXML. Their combined effect:

- Efficiency: uses fallback EIR 0.35 instead of the rated EER-derived EIR (e.g.
  EER 10 → EIR 0.341 — 2.6% error; EER 8 → EIR 0.427 vs actual 0.426 — negligible,
  but EER 12 → EIR 0.284 vs fallback 0.35 — 23% error in compressor power)
- Cd: 0.07 instead of 0.22 — cycling efficiency penalty is under-estimated by 68%

These errors are silent: no log, no panic. Existing tests pass because the unit tests
for `calc_startup_degradation` use the lowercase string and the io-layer test only
checks that `startup_cd` is absent from Room AC params (it doesn't check the value).

## Background/Context

`resolve_der.rs:resolve_ev()` wires only `ChargingLevel`, `MaxChargingPower`, and `BatteryCapacity`. OCHRE derives EV config from MEL annual kWh and infers range from energy — an entirely different schema. No CW ticket covers this config wiring gap.

## Investigation Instructions

1. **Read `resolve_der.rs:resolve_ev()`** — list every field extracted from HPXML.
2. **Read OCHRE `parse_ev` in `hpxml.py`** — list every field extracted. Build comparison table.
3. **Identify missing fields:** Which OCHRE config parameters have no HARES equivalent?
4. **Check charging curve wiring:** How does the HPXML-assembled config reach the charging curve in `ev/charging_curve.rs`?

## Findings

### F-001 — BUG — HIGH: Dead key `"battery_capacity_kwh"` emitted by PlugLoad path is never read by `Ev`

**Files:** `crates/hares-io/src/hpxml/resolve_loads.rs:425`, `crates/hares-equipment/src/ev/config.rs:8`

`resolve_loads.rs` (the ResStock/PlugLoad path for `electric vehicle charging`) inserts key
`"battery_capacity_kwh"` into the spec params (line 425). The EV equipment's `resolve_capacity_kwh()`
reads `KEY_BATTERY_CAPACITY_KWH = "capacity_kwh"` and `KEY_BATTERY_CAPACITY_HPIXML_KWH = "BatteryCapacity"`.
Neither matches `"battery_capacity_kwh"`.

The resolution falls through to the `KEY_RANGE_MILES = "range_miles"` branch, which also exists in the
spec and produces numerically identical capacity (`range_miles * 0.325`). So the simulation value is
correct **by coincidence** — the dead key carries the same value that would be computed from the range
fallback. However, the dead key is misleading: it looks correct in tests that only inspect
`ev.parameters["battery_capacity_kwh"]` without constructing an `Ev` from that spec.

The existing IO tests (`hpxml_parsing_tests.rs:307`) assert the `"battery_capacity_kwh"` key value in
the raw `EquipmentSpec.parameters`, which never exercises the `Ev::new()` resolution path. A test that
constructs `Ev::new(equipment_config_from_spec(&spec))` and checks `ev.battery_capacity_kwh` would
catch any future breakage of the coincidental fallback.

**Fix:** Rename the inserted key from `"battery_capacity_kwh"` to `"capacity_kwh"` in
`resolve_loads.rs:425` to match `KEY_BATTERY_CAPACITY_KWH`. Alternatively, add `"battery_capacity_kwh"`
as a third lookup alias in `resolve_capacity_kwh()`. Either approach eliminates the fragile fallback
through `range_miles`.

### F-002 — BUG — CRITICAL (pre-existing, confirmed still present at HEAD, partially fixed in working tree): `"Electric Vehicle"` spec name not registered in equipment registry

**Files:** `crates/hares-equipment/src/ev/mod.rs:1112–1128`, `crates/hares-core/src/dwelling/conversions.rs:338`

Confirmed and documented in AR-005 F-001. Both HPXML paths (`resolve_der.rs:123` and
`resolve_loads.rs:430`) emit `EquipmentSpec { name: "Electric Vehicle", ... }`. In
`equipment_config_from_spec()`, `ochre_class` is set to `spec.name.clone()` (line 338), so the
registry is queried with `"Electric Vehicle"`. At HEAD the entry was missing; the working tree
(`M crates/hares-equipment/src/ev/mod.rs`) adds it as a second alias:

```rust
registry.register("Electric Vehicle", Box::new(|config| Box::new(Ev::new(config))));
```

The `git diff HEAD` confirms this line is only in the working tree, not yet committed. Until
this change is committed and tested end-to-end, every HPXML-sourced EV is silently dropped.
No error is returned; the dwelling constructs successfully with a `tracing::warn!` in
`mod.rs:864–874`.

### F-003 — GAP — MEDIUM: OCHRE derives EV type from annual kWh; HARES PlugLoad path uses a fixed threshold

**Files:** `crates/hares-io/src/hpxml/resolve_loads.rs:419`, `vendors/OCHRE/ochre/utils/hpxml.py:1588–1592`

OCHRE `parse_ev()` maps annual kWh to range via a hard threshold:
```python
ev_load = ev["Annual Electric Energy (kWh)"]
range = 100 if ev_load < 1500 else 250
```
HARES replicates this threshold identically (`resolve_loads.rs:419`: `if kwh < 1500.0 { 100 } else { 250 }`).

However, OCHRE always hardcodes `vehicle_type: "BEV"` and `charging_level: "Level 2"` regardless of
input. HARES does the same. This means HPXML files that encode PHEVs via a small annual-kWh plug load
are silently mis-classified as BEV/100-mile, producing the wrong vehicle number (3 instead of 1 or 2)
and the wrong default max charge power (7.2 kW instead of 3.6 kW). This matches OCHRE behavior but
is a known limitation of the MEL kWh path that neither codebase addresses.

### F-004 — GAP — MEDIUM: HPXML `<ElectricVehicles>` path has no `vehicle_type` or `range_miles`

**Files:** `crates/hares-io/src/hpxml/resolve_der.rs:106–131`

`resolve_der.rs:resolve_ev()` extracts:
- `<ChargingLevel>` → `"ChargingLevel"` key
- `<MaxChargingPower>` → `"MaxChargingPower"` key (raw kW, no units wrapper; relies on `child_f64`)
- `<BatteryCapacity><Value/><Units/>` → `"BatteryCapacity"` key via `child_energy_kwh`

It does **not** extract or insert `vehicle_type` or `range_miles`. These are unused in the
`<ElectricVehicles>` path because `resolve_rated_power_kw` has a direct `MaxChargingPower` to fall
back to, and `resolve_capacity_kwh` has `BatteryCapacity` directly.

However, `vehicle_number_from_config()` — used in `default_max_power_kw()` when `MaxChargingPower` is
absent — reads `KEY_RANGE_MILES` and `KEY_VEHICLE_TYPE` to select among `3.6 / 7.2 / 11.5 kW`.
If `<MaxChargingPower>` is absent from the HPXML (it is optional) and neither `range_miles` nor
`vehicle_type` is present, `vehicle_number_from_config()` defaults to `range_miles = 0` → vehicle
number 3 (BEV < 175 mi range) → default 7.2 kW. This is a reasonable fallback but is undocumented.

### F-005 — GAP — LOW: Charging curve LUT is not wired from HPXML; requires explicit API injection

**Files:** `crates/hares-equipment/src/ev/mod.rs:278–280`, `crates/hares-equipment/src/ev/mod.rs:1067–1076`

`init_from_config()` unconditionally clears `charging_curve_lut` to `None` (line 280). The LUT is only
set via `set_charging_curve_lut()` which is a trait method in the `Equipment` interface, callable from
the Python layer. There is no HPXML field or config key that can wire a custom LUT. This is by design
(Python extensibility), but means all HPXML-sourced EVs use the linear CC-CV model regardless of
chemistry. The design decision is not documented in-code.

### OCHRE vs HARES Config Field Comparison

| Config Field           | OCHRE source            | OCHRE value           | HARES source                   | HARES value            | Match?        |
|------------------------|-------------------------|-----------------------|--------------------------------|------------------------|---------------|
| `vehicle_type`         | `parse_ev` hardcoded    | `"BEV"`               | `resolve_loads.rs:413`         | `"BEV"`                | YES (PlugLoad only) |
| `charging_level`       | `parse_ev` hardcoded    | `"Level 2"`           | `resolve_loads.rs:415`/`resolve_der.rs:114` | `"Level 2"` / HPXML element | YES |
| `range` (miles)        | `parse_ev` threshold    | 100 or 250            | `resolve_loads.rs:419`         | 100 or 250             | YES (PlugLoad) |
| `capacity` (kWh)       | derived from range      | range / 3.077         | `ev/config.rs:82`              | range_miles * 0.325    | YES (same constant) |

## Recommended Tests

### T-001 — End-to-end: PlugLoad EV spec constructs `Ev` with correct capacity

Write a test in `crates/hares-equipment/tests/` that:
1. Calls `equipment_config_from_spec(&spec)` with a spec produced by the PlugLoad path
   (i.e., params contain `"battery_capacity_kwh"`, `"range_miles"`, `"vehicle_type"`, `"charging_level"`).
2. Constructs `Ev::new(config)` and calls `ev.init(...)`.
3. Asserts `ev.battery_capacity_kwh` matches the expected capacity (32.5 kWh for 100-mile BEV,
   81.25 kWh for 250-mile BEV).

This test would catch the dead `"battery_capacity_kwh"` key defect (F-001) if the coincidental
`range_miles` fallback is ever removed.

### T-002 — End-to-end: `"Electric Vehicle"` registry name routes to `Ev`

Write a test that:
1. Calls `EquipmentRegistry::new()` (which calls `register_with_registry`).
2. Constructs a minimal `EquipmentConfig` with `ochre_class = "Electric Vehicle"` and
   `capacity_kwh = 60.0`.
3. Asserts `registry.create("Electric Vehicle", config)` succeeds and the returned equipment
   has `descriptor().equipment_type == "EV"`.

This would have caught AR-005 F-001 and ensures the `"Electric Vehicle"` alias stays registered.

### T-003 — Integration: HPXML PlugLoad EV reaches `Dwelling::equipment` non-empty

Write a test that parses the `cz2a_pv_ev/building.xml` fixture (which has `PlugLoadType: electric
vehicle charging`) via `Dwelling::from_config`, then asserts:
1. `dwelling.warnings()` contains no equipment-not-registered entries for `"Electric Vehicle"`.
2. `dwelling.equipment()` contains at least one item with `end_use == EndUse::EV`.

### T-004 — Integration: HPXML `<ElectricVehicles>` path constructs `Ev` with correct parameters

Write a test using the HPXML fixture format in `equipment.rs:617–658` that:
1. Parses `<ElectricVehicles><ElectricVehicle><ChargingLevel>Level 2</ChargingLevel>
   <MaxChargingPower>11.5</MaxChargingPower>
   <BatteryCapacity><Value>77</Value><Units>kWh</Units></BatteryCapacity></ElectricVehicle></ElectricVehicles>`.
2. Constructs `Ev` via the registry.
3. Asserts `ev.battery_capacity_kwh == 77.0` and `ev.rated_power_kw == 11.5`.

### T-005 — Unit: `resolve_capacity_kwh` does not read `"battery_capacity_kwh"` key

Write a negative test that constructs an `EquipmentConfig` with only `"battery_capacity_kwh"` set
(no `"capacity_kwh"`, no `"BatteryCapacity"`, no `"range_miles"`) and asserts
`resolve_capacity_kwh(&config)` returns `None`. This documents the dead-key behavior explicitly and
prevents silent regression if someone adds the key as an alias.

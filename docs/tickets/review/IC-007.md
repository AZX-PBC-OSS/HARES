## Background/Context

OCHRE `TanklessWaterHeater` is always `use_ideal_capacity=True` and has specialized `update_internal_control()` — it directly computes draw-heat and caps by rated capacity with outlet temperature degradation. No IC ticket covers tankless WH ideal behavior.

## Investigation Instructions

1. **Read HARES `tankless.rs`** — does it implement any ideal capacity mode?
2. **Read OCHRE `TanklessWaterHeater`** — document the draw-heat computation and capacity capping.
3. **Compare outlet temperature degradation** at high draw rates.
4. **Check whether HARES caps output to rated capacity** — what happens when draw exceeds capacity?

## Findings

### F1 — HARES mode is correct: on-demand, not binary thermostat (PASS)

HARES implements the right conceptual model for a tankless WH. It fires whenever there is flow (`total_draw_kg_s > 0.0`) and the unit is enabled, modulating output continuously to match demand up to the rated capacity. There is no deadband and no tank state. This matches OCHRE's `TanklessWaterHeater.update_internal_control()`, which forces `states[t_upper_idx] = setpoint_temp` (i.e., there is no meaningful tank to guard) and computes `heat_from_draw` directly from the water draw.

### F2 — Outlet temperature degradation in over-capacity case: DIVERGENCE (LOW SEVERITY)

**HARES** (`tankless.rs:280-282`):
```
outlet_c = inlet_temp_c + effective_max_w / (total_draw_kg_s * cp)
```
This uses `effective_max_w` (which is `rated_thermal_power_w` clamped by `power_limit_w`).

**OCHRE** (`WaterHeater.py:761`):
```python
t_outlet = t_mains + (t_set - t_mains) * (capacity_rated / heat_from_draw)
```
OCHRE expresses the degraded outlet as a fractional interpolation: `t_outlet = t_mains + (t_set - t_mains) * (cap / demand)`.

These are algebraically equivalent when `heat_from_draw = m_dot * cp * (t_set - t_mains)`. Expanding OCHRE: `t_outlet = t_mains + (t_set - t_mains) * cap / (m_dot * cp * (t_set - t_mains)) = t_mains + cap / (m_dot * cp)`. This is identical to HARES. No divergence in steady state — the formulations are equivalent. PASS for the math.

However: OCHRE's `max_power` clip happens **before** the capacity comparison (`heat_from_draw *= max_power / power` at line 751-752), so the effective `capacity_rated` used in the outlet formula is still the nominal hardware rating, while HARES uses `effective_max_w` (already reduced by `PowerLimit`). For `PowerLimit` control, HARES will compute a lower `outlet_c` than OCHRE would, because HARES uses the power-limited thermal ceiling as both the capacity bound and the outlet temperature formula numerator, whereas OCHRE clips the draw before comparing to `capacity_rated` and then uses the unmodified `capacity_rated` in the outlet formula. The physical interpretation differs: OCHRE's approach means the heater still fires at its rated power during the on-phase even under power-limit, while HARES treats the power limit as reducing the instantaneous firing rate. The HARES behavior is arguably more physically correct for an input-power cap on a modulating unit, but it deviates from OCHRE for `PowerLimit` + over-capacity combined.

**Severity: Low.** The deviation only manifests when `PowerLimit` is active and demand simultaneously exceeds the power-limited capacity — an uncommon operating regime.

### F3 — `PowerLimit` signal direction is inverted for gas units (BUG — HIGH SEVERITY)

`apply_control_unchecked` at `tankless.rs:429`:
```rust
let limit_w = (max_power_kw * 1_000.0 * self.efficiency_factor).max(0.0);
```

The `PowerLimit` signal carries `max_power_kw` as the **input power** cap (fuel kW for gas, electrical kW for electric). Converting to a thermal ceiling requires multiplying by efficiency: `thermal_limit = fuel_limit * efficiency`. This is what the code does — and the comment says the same.

However, the `effective_max_w` is then compared against `demand_w` and `capacity_w` — both of which are **thermal** watts. The `fuel_input_w` at `tankless.rs:292` is `thermal_output_w / efficiency_factor`. So the chain is:

- `power_limit_w` (stored as thermal W) = `max_power_kw * 1000 * efficiency`
- `effective_max_w` = min(rated, power_limit_w) — thermal W
- `thermal_output_w` <= `effective_max_w` — thermal W
- `fuel_input_w` = `thermal_output_w / efficiency` — fuel W

Upper bound on fuel: `fuel_input_w <= effective_max_w / efficiency = max_power_kw * 1000`. This is correct — the fuel consumption is capped at `max_power_kw`.

For **electric** units: `fuel_input_w` is the electrical draw (same code path, `fuel_type == Electric` takes the ZIP branch but uses the same `fuel_input_w` base). Electrical draw = `thermal / efficiency`. With the cap: max electrical = `max_power_kw * 1000`. Correct.

Actually this is correct. The test `power_limit_signal_caps_fuel_input` validates this path. No inversion bug — the comment is accurate. PASS.

### F4 — Parasitic power telemetry emitted unconditionally for electric units (BUG — MEDIUM SEVERITY)

`tankless.rs:322-323`:
```rust
self.telemetry.set(tk::PARASITIC_ELECTRIC_W, self.parasitic_power_w);
```

`parasitic_power_w` is initialized to `DEFAULT_GAS_PARASITIC_POWER_W` (7.38 W) in `new()`. For **electric** tankless units, `init()` will call `parse_tankless_fuel_type` and set `fuel_type = Electric`, but `parasitic_power_w` is **not reset to 0.0** during `init()` if no `parasitic_power_w` config key is present. The `init()` code at line 203 reads:

```rust
self.parasitic_power_w = first_f64(config, &["parasitic_power_w"])
    .unwrap_or(DEFAULT_GAS_PARASITIC_POWER_W)
    .max(0.0);
```

This means an electric tankless WH always initialises with 7.38 W of parasitic, even though:
1. It does not report parasitic electric draw through the port (the `FuelType::Electric` branch only calls `zip.apply(fuel_input_w, ...)` and does not add a separate parasitic term).
2. But the telemetry field `PARASITIC_ELECTRIC_W` is set to 7.38 W regardless of fuel type.

The port power is correct (no spurious 7.38 W electrical charge for electric units), but the telemetry is misleading — downstream consumers reading `PARASITIC_ELECTRIC_W` from an electric unit will see 7.38 W instead of 0.0. This is a telemetry accuracy defect.

**Fix**: In `init()`, after resolving `fuel_type`, default `parasitic_power_w` to 0.0 for electric units when the config key is absent:
```rust
self.parasitic_power_w = if self.fuel_type == FuelType::Gas {
    first_f64(config, &["parasitic_power_w"]).unwrap_or(DEFAULT_GAS_PARASITIC_POWER_W)
} else {
    first_f64(config, &["parasitic_power_w"]).unwrap_or(0.0)
}.max(0.0);
```

### F5 — Gas parasitic is emitted even when unit is forced off (DIVERGENCE — LOW SEVERITY)

OCHRE `GasTanklessWaterHeater.calculate_power_and_heat()` line 800 sets `self.electric_kw = self.parasitic_power` unconditionally — consistent with HARES. Both emit parasitic regardless of `Off` mode. Consistent with OCHRE. PASS.

### F6 — `update_control` is called inside `step`, consuming DR timer per step even when no draw (LOW SEVERITY)

`step()` calls `self.update_control(env)` which advances the DR timer by `dt_s`. This is correct behavior, but there is no guard against very large `dt_s` values producing a negative `remaining` that then triggers `apply_dr_level(Normal)` on the same step. The code handles this correctly: `if next <= 0.0 { ... apply Normal }`. PASS.

### F7 — `is_enabled()` checks `duty_cycle > 0.0` but allows very small positive duty cycles (LOW SEVERITY, NOT A BUG)

Duty cycles approaching zero are allowed through `is_enabled()` and produce valid but vanishingly small thermal output. This is consistent with OCHRE's continuous ideal-capacity modulation. PASS.

### F8 — No setpoint ramp rate support (DIVERGENCE — LOW SEVERITY)

OCHRE's `update_setpoint()` supports `Max Setpoint Ramp Rate (C/min)` that smoothly transitions the setpoint over multiple steps. HARES applies setpoint changes immediately. For tankless units this is lower-impact than for tank heaters (no stored energy to overshoot), but it means fast setpoint step-changes produce instantaneous thermal output changes rather than ramped ones. Not a correctness defect, but a known capability gap.

### F9 — `GasTanklessWaterHeater` in OCHRE requires `Parasitic Power (W)` as a mandatory kwarg (RISK)

OCHRE line 790: `self.parasitic_power = kwargs["Parasitic Power (W)"] / 1000`. This is a required key — missing it raises `KeyError`. HARES uses a default of 7.38 W, which is the ANSI RESNET 301 formula result for 3 bedrooms. If HPXML parsing does not supply `parasitic_power_w` for gas tankless units loaded from OCHRE-format configs, the default will differ from whatever OCHRE computed. This is low risk since 7.38 W is small relative to the rated 20 kW thermal output.

## Recommended Tests

### T1 — Electric unit parasitic telemetry is zero (covers F4)
Construct an electric tankless WH with no `parasitic_power_w` config key. After one step, assert `PARASITIC_ELECTRIC_W` telemetry == 0.0. Currently fails.

### T2 — `PowerLimit` + over-capacity: verify fuel cap respected (covers F3, regression)
Set flow high enough to exceed capacity, apply `PowerLimit` to half the rated input power. Assert `fuel_input_w <= max_power_kw * 1000` within floating-point tolerance and `thermal_output_w == fuel_input_w * efficiency`.

### T3 — `PowerLimit` outlet temperature under combined over-capacity + power-limited regime (covers F2)
With flow=1 kg/s, rated=20 kW, PowerLimit=10 kW input, efficiency=0.8: thermal ceiling=8 kW. Verify outlet_c = inlet + 8000 / (1.0 * 4183). Documents the HARES-vs-OCHRE delta for this case.

### T4 — Gas unit off via ModeOverride still emits parasitic electric (covers F5)
Apply `ModeOverride::Off`, step once. Assert `PARASITIC_ELECTRIC_W > 0` and `THERMAL_OUTPUT_W == 0` and `FUEL_INPUT_W == 0`.

### T5 — Setpoint below inlet temperature produces zero output (edge case)
Set `setpoint_c` below `inlet_temp_c`. `delta_t_c` is clamped to 0.0 at line 254. Assert `thermal_output_w == 0.0` and `fuel_input_w == 0.0`.

### T6 — Electric unit ZIP voltage sensitivity
For an electric tankless WH, vary `grid.voltage_pu` from 0.95 to 1.05. Confirm that `ports.electrical.load_power_kw` responds according to ZIP coefficients and that no spurious fuel port accumulation occurs.

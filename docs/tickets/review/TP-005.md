## Background/Context

PV outputs: DC power, AC power (after inverter), plane-of-array irradiance, cell temp,
soiling loss. HARES has a soiling model OCHRE doesn't.

## Investigation Instructions

1. Read OCHRE PV output columns.
2. Read HARES PV telemetry.
3. Build comparison table.
4. Document HARES-only soiling telemetry as an improvement.


## OCHRE vs HARES Telemetry Comparison

OCHRE `PV.generate_results()` exposes very little directly: only `electric_kw` and
`reactive_kvar` come from the parent `ScheduledLoad.generate_results()`. At verbosity >= 6
OCHRE adds `PV P Setpoint (kW)` and `PV Q Setpoint (kW)`. DC power is computed internally
(`system_model.Outputs.dc`) but is commented out of the results entirely. Cell temperature
and POA irradiance are not emitted.

HARES PV telemetry keys (`telemetry_keys.rs` + `pv/mod.rs:telemetry_fields()`):

| Key | Unit | OCHRE equivalent | Notes |
|---|---|---|---|
| `ac_power_kw` | kW | `PV Electric (kW)` | Always emitted |
| `electric_kw` | kW | same | Redundant alias; both set to `final_p_kw` |
| `reactive_power_kvar` | kVAR | `PV Reactive (kVAR)` internal only | Always emitted |
| `dc_power_kw` | kW | None (commented out) | Exceeds OCHRE |
| `cell_temp_c` | C | None | Exceeds OCHRE |
| `irradiance_w_m2` | W/m2 | None | Exceeds OCHRE |
| `inverter_efficiency` | — | None | Exceeds OCHRE |
| `curtailment_kw` | kW | None | Exceeds OCHRE |
| `inverter_clipping_kw` | kW | None | Exceeds OCHRE |
| `soiling_ratio` | — | None | Exceeds OCHRE |
| `shading_factor` | — | None | Exceeds OCHRE |

All four fields called out in the ticket spec (DC power, AC power, cell temp, POA
irradiance) are present. HARES exposes substantially more than OCHRE.

## Findings

### F1 — CRITICAL: `dc_power_kw` is wrong in the LUT path

**Location:** `pv/mod.rs:246`

```rust
let dc_power_kw = ac_power_kw / self.inverter_efficiency.max(1e-9);
```

In the LUT path, `ac_power_kw` is the SAM model output — it already encodes SAM's
internal DC→AC conversion, system losses, and all internal deratings. Dividing back by
`inverter_efficiency` alone recovers neither the true gross DC array output nor SAM's
internal DC value; it is an inflated artefact that over-reports DC power by at least the
`system_losses_fraction` (default 14%).

In the analytic path (lines 270-273) `dc_power_kw` is correctly the gross array output
before inverter conversion. The two paths are semantically inconsistent.

The `TelemetryField` description says "Total PV DC output power **before inverter
efficiency and curtailment**". The LUT path violates this contract.

**Fix:** Back-calculate DC consistently in both paths by inverting both the inverter step
and the system-losses derating:

```rust
let dc_power_kw = ac_power_kw
    / (self.inverter_efficiency * (1.0 - self.system_losses_fraction)).max(1e-9);
```

### F2 — MEDIUM: `update_control` reads stale `last_ac_power_kw` — mode lags one step

**Location:** `pv/mod.rs:491-497`

```rust
fn update_control(&mut self, _env: &EnvironmentState) -> OperatingMode {
    if self.last_ac_power_kw > 0.0 {
        OperatingMode::Standby
    } else {
        OperatingMode::Off
    }
}
```

`last_ac_power_kw` is written at the end of `step()` (line 591), so `update_control`
always reflects the **previous** timestep's output. At sunrise the mode reports `Off` for
one full timestep after generation begins; at sunset it reports `Standby` for one full
timestep after generation ends.

**Fix:** Derive mode from current-step POA irradiance (available in `env.weather`) or
move the mode decision into `step()` after computing `final_p_kw` and store it in a
field.

---

### F3 — LOW: `curtailment_fraction` effect is invisible in `curtailment_kw` telemetry

**Location:** `pv/mod.rs:552-562`

The `curtailment_fraction` derating (lines 553-555) modifies `total_ac_power_kw` in
place **before** `unclipped_ac_kw` is snapshotted. As a result, fraction-based curtailment
is silently absorbed and never appears in the `curtailment_kw` telemetry field. Only
curtailment from the `PowerLimit` control signal is measured. A user who issues
`CurtailmentPercent` cannot observe how much energy was shed from telemetry alone.

**Fix:** Capture fraction-curtailed energy before clobbering `total_ac_power_kw`:

```rust
let fraction_curtailed_kw = total_ac_power_kw * self.curtailment_fraction;
total_ac_power_kw -= fraction_curtailed_kw;
let unclipped_ac_kw = total_ac_power_kw;
if let Some(limit_kw) = self.power_limit_kw {
    total_ac_power_kw = total_ac_power_kw.min(limit_kw.max(0.0));
}
let curtailment_kw = fraction_curtailed_kw + (unclipped_ac_kw - total_ac_power_kw).max(0.0);
```

---

### F4 — LOW: `irradiance_w_m2` description says "incident" but value is post-derating

**Location:** `pv/mod.rs:220-222`, `telemetry_fields()` description

The stored value is POA irradiance after soiling and shading derating (effective cell
irradiance), not raw incident POA. The description says "incident irradiance" which
implies pre-loss. This is a documentation defect.

**Fix:** Change the `TelemetryField` description to "Effective irradiance after soiling
and shading derating, capacity-weighted across arrays".

## Recommended Tests

1. **`test_dc_power_lut_vs_analytic_consistency`** — Configure a PV with a SAM LUT and
   an identical analytic array. Run one step at the same irradiance/temperature. Assert
   that `dc_power_kw` / `ac_power_kw` ratio is equal across both paths within tolerance.

2. **`test_update_control_mode_at_sunrise`** — Step through two consecutive timesteps
   where the first has zero irradiance (night) and the second has positive irradiance.
   Assert that `OperatingMode` returned by `update_control` on the second step reflects
   the current potential to generate, not the previous step's zero output.

3. **`test_curtailment_fraction_reflected_in_telemetry`** — Issue
   `CurtailmentPercent { percent: 50.0 }`, run one step with non-zero irradiance. Assert
   `curtailment_kw == ac_power_kw` (half the max output was curtailed and half was
   delivered).

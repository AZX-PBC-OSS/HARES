## Background/Context

The original ticket assumed `IdealThermostat` has time-of-day setpoint switching logic. Code inspection reveals this is **false**: `IdealThermostat::decide()` takes `_env: &EnvironmentState` (unused). The actor is a pure override pusher — it emits a `ThermalSetpoint` control signal when `override_state.is_active()` and does nothing otherwise. There is no time-of-day schedule logic inside this actor.

## Investigation Instructions

1. **Confirm `_env` is unused** in `decide()`. Document what the actor actually does:
   - When does `override_state.is_active()` become true?
   - What control signal is emitted?
   - Is there an override expiry mechanism?

2. **Identify the architectural gap vs OCHRE:**
   - OCHRE's thermostat has a built-in schedule (heating/cooling setpoints by time of day).
   - HARES separates this: equipment owns the setpoint schedule (`ScheduleSource` in `hvac_core.rs`), and the actor only pushes overrides.
   - Is this separation intentional? Does it produce equivalent behavior?

3. **Determine how time-varying setpoints work in HARES:**
   - Via `ScheduleSource::DailyProfile` in the equipment's `ThermostatConfig`?
   - Via a Python actor calling `set_override()` each timestep?
   - Via a different actor type?

4. **Document the gap:** If a user expects OCHRE-style actor-driven schedule control, what is the HARES equivalent workflow?

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### How setpoint switching works in HARES `IdealHvac`

Setpoint switching is **purely temperature-based** — no time logic anywhere in the FSM.

`update_mode` (ideal_hvac.rs:223) runs every control tick:

1. **Schedule setpoints** are refreshed from `ScheduleSource` (daily profile, CSV column, or constant).
2. **Effective setpoints** are assembled via a three-layer priority chain:
   `static_setpoints` → `schedule_setpoints` (from `ScheduleSource`) → `runtime_setpoints` (control-signal override).
3. **Hysteresis FSM** evaluates zone temperature against asymmetric thresholds and advances the three-state machine (`Heating`, `Cooling`, `Deadband`):
   - `Deadband → Heating` when `zone_temp < heating_c − hysteresis × (1 − offset)`
   - `Deadband → Cooling` when `zone_temp > cooling_c + hysteresis × (1 − offset)`
   - `Heating → Deadband` when `zone_temp > heating_c + hysteresis × offset`
   - `Cooling → Deadband` when `zone_temp < cooling_c − hysteresis × offset`
4. A min-cycle guard (`is_cycle_change_allowed`) suppresses transitions until `min_cycle_time_s` has elapsed.
5. `current_target_c` is updated to the live setpoint after every call so the ideal-capacity solver always sees the current schedule value, even across day/night setpoint shifts.

`deadband_offset = 0.2` by default, matching OCHRE line 222, placing the setpoint near the top of the heating deadband.

### How OCHRE does it

OCHRE separates heating and cooling into two distinct equipment instances (`Heater`/`Cooler` subclasses). Each instance owns a single `temp_setpoint` drawn from its own schedule column (`HVAC Heating Setpoint (C)` / `HVAC Cooling Setpoint (C)`). The thermostat's `run_thermostat_control` returns `"On"`, `"Off"`, or `None` (hysteresis hold) based on `hvac_mult × (zone_temp − threshold)`.

**Critical difference:** In `use_ideal_capacity=True` mode OCHRE **bypasses** `run_thermostat_control` entirely:

```python
if self.use_ideal_capacity:
    self.capacity = self.update_capacity()
    return "On" if self.capacity > 0 else "Off"
```

Mode is then determined entirely by the sign of the solver output — no deadband, no hysteresis hold.

HARES always runs the hysteresis FSM first and only exposes `ideal_target()` when already in a heating or cooling mode. This means the HARES solver is never invoked for the idle tick between when the zone crosses the turn-off threshold and when the FSM would re-enter Heating/Cooling. Under coarse time resolution (15-min steps) this can produce one missed cycle relative to OCHRE.

### `_env` parameter in `IdealThermostat` actor

The `IdealThermostat` actor in `hares-core` is a **stateless override pusher**. It emits a `ThermalSetpoint` control signal when `override_state.is_active()` and does nothing otherwise. `_env` is unused because the actor carries no time-of-day schedule logic. Time-varying setpoints in HARES are owned by the equipment (`ScheduleSource::DailyProfile` in `IdealHvac`) — not by this actor.

This separation is intentional and architecturally superior to OCHRE: schedule logic lives in one place (the equipment), and actors only push transient overrides (e.g., demand response setbacks). The behavioral outcome is equivalent for standard scheduling.

## Defects

### D1 — MEDIUM — Ideal-capacity mode bypasses FSM in OCHRE but not in HARES

When `IdealCapacityMode::On` (or `Auto` at coarse resolution) is active, OCHRE skips the thermostat deadband entirely and lets solver sign determine mode. HARES still gate-keeps through the FSM. At fine time resolution the practical effect is small, but at 15-min steps a zone that has crossed the turn-off threshold will miss one 15-min solver call. Whether the HARES approach is intentionally better (min-cycle protection prevents oscillation) or an accidental divergence requires a team decision. The current code has no comment explaining the divergence.

**No test** exercises this code path — parity tests that use `ideal_capacity_mode = "on"` should be checked for the sign-switch edge case.

### D2 — LOW — Runtime setpoint overrides are not re-validated against deadband gap constraint

`init` (ideal_hvac.rs:377) calls `effective_setpoints().validate_for_deadband(hysteresis_c)` enforcing `cooling_c − heating_c ≥ 2 × hysteresis_c`. `apply_control_unchecked` (lines 485–525) can set `runtime_setpoints` with arbitrary values without re-running this check. An actor that closes the gap below `2 × hysteresis_c` will cause the FSM to oscillate between `Heating` and `Cooling` on every tick with no error surfaced.

### D3 — LOW (cosmetic/telemetry) — `current_target_c` is stale during `Deadband` after a schedule shift

Lines 229–233 and 308–311 skip `current_target_c` update when `mode == Deadband`. The telemetry field `CURRENT_TARGET_C` therefore shows the previous active-mode setpoint throughout any Deadband period, even after a large day/night setpoint shift. Actors and dashboards reading this field will see incorrect values during Deadband.

## Background/Context

Python actors receive `env` as a plain dict with nested structure:
`{zones: [{id, temperature_c, ...}], weather: {outdoor_temp_c, ...}, ...}`.
Users implementing custom actors must know the exact dict structure from documentation
or trial-and-error. A typo like `env["weather"]["outdor_temp_c"]` is a KeyError
at runtime, during simulation, potentially after hours of compute.

## Investigation Instructions

1. **Document the current env dict structure:**
   - What keys exist at each level?
   - What are the value types?
   - Is this documented anywhere users can find it?

2. **Assess alternatives:**
   - **Typed pyclass `EnvironmentView`** with `.zones`, `.weather`, `.grid`,
     `.current_time` properties that return typed objects.
     Pro: IDE autocomplete, type checking, no dict key errors.
   - **TypedDict** (Python typing) — provides static type checking without runtime
     overhead. Pro: no Rust changes. Con: no runtime validation.
   - **Pydantic model** — runtime validation. Con: performance overhead per step.

3. **Assess performance impact:**
   - `decide()` is called every timestep for every actor.
   - Dict construction vs pyclass construction cost?
   - Could the env be constructed once and passed by reference?

4. **Check the `DispatchRequest` return path:**
   - Actors return `list[DispatchRequest]`. Is this typed? Or could a user return
     a dict that gets silently misinterpreted?

## Review Notes

`environment_to_py_dict` passes `env.current_time` as RFC3339 string, not Python datetime. Verify stub type annotation. Add `crates/hares-types/src/environment.rs` to `files_to_touch`.

## Findings

### Finding 1 — CRITICAL: `EnvironmentState` fields silently dropped in `environment_to_py_dict`

**File:** `crates/hares-python/src/py_actor.rs:143–184`

`environment_to_py_dict` constructs a `PyDict` from `EnvironmentState` but omits the
following fields that exist on the Rust struct:

**`weather` sub-dict — missing fields:**
- `outdoor_wet_bulb_c` (`WeatherState`)
- `outdoor_enthalpy_j_kg` (`WeatherState`)
- `solar_azimuth_deg` (`WeatherState`)
- `mains_temp_c` (`WeatherState`)
- `rainfall_m` (`WeatherState`)
- `ground_albedo` (`WeatherState`)
- `solar_irradiance` (`WeatherState`) — entire `Vec<SurfaceIrradiance>` absent

**Top-level `env` dict — entirely absent keys:**
- `price_signal` (`PriceSignal` with `electricity_price`, `export_price`, `ghg_intensity`)
- `electrical` (`ElectricalSummary` with `pv_generation_kw`, `base_load_kw`, `net_grid_kw`, `battery_power_kw`, `ev_power_kw`)
- `equipment_telemetry` (`HashMap<String, Telemetry>`) — actors cannot observe equipment state

The `equipment_telemetry` omission is particularly severe: the Rust comment on the field
says "Actors can read equipment state (SOC, power, connection_state, etc.) to make informed
decisions." That capability is completely absent for Python actors today. A Python BMS actor
cannot know the current battery SOC.

`ZoneState` also omits `wet_bulb_c` (present in the Rust struct).

**Severity:** Critical. Python actors cannot implement any price-responsive, grid-aware, or
equipment-observing logic with the current dict. The field gaps are not documented anywhere.

### Finding 2 — HIGH: `current_time` is passed as RFC3339 string, not `datetime`

**File:** `crates/hares-python/src/py_actor.rs:180`

```rust
let _ = dict.set_item("current_time", env.current_time.to_rfc3339());
```

Python actors receive a `str`, but the stub annotation is `dict[str, Any]` — there is no
annotation at all indicating the type of `env["current_time"]`. Any actor that does
`env["current_time"] < some_datetime` will get a `TypeError` at runtime. Actors wanting to
do time-based scheduling (e.g., charge EV before departure) must manually parse the string
with `datetime.fromisoformat()`.

**Severity:** High. The correct fix is to pass a `datetime` object from PyO3 using
`pyo3_chrono` or construct one via `datetime.datetime.fromisoformat()` on the Rust side.
A `datetime` with timezone info is the appropriate Python type for `DateTime<FixedOffset>`.

---

### Finding 3 — HIGH: Stub annotation `decide(self, env: dict[str, Any])` provides zero type safety

**File:** `python/ochre_next/_hares.pyi:783`

```python
def decide(self, env: dict[str, Any]) -> list[DispatchRequest]: ...
```

`dict[str, Any]` defeats all static analysis. A user implementing an actor gets no IDE
autocomplete, no mypy errors on typos like `env["wether"]`, and no indication of what
nested keys/types are available. This is the root cause of the ergonomic problem identified
in the ticket.

**Severity:** High. Even before the full `EnvironmentView` pyclass is built, a
`TypedDict` hierarchy for the env structure would allow mypy/pyright to catch typos and
provide IDE assistance at zero runtime cost.

---

### Finding 4 — MEDIUM: `DispatchRequest` return path has a silent error swallow

**File:** `crates/hares-python/src/py_actor.rs:109–120`

```rust
Err(e) => {
    tracing::warn!(
        actor = %self.name,
        error = %e,
        "Python actor decide() returned invalid type"
    );
}
```

If a user returns a list of plain dicts instead of `DispatchRequest` objects, the simulation
silently continues with zero dispatches emitted. There is no exception propagation, no
simulation abort, and no indication to the user that their actor is producing no effect.
This can mask bugs entirely: an actor "runs" but never dispatches any control signals.

**Severity:** Medium. This should propagate as a Python exception so the user knows their
actor is broken. At minimum a `tracing::error!` with a user-visible message pointing to
the actor name and the type received.

---

### Finding 5 — MEDIUM: Performance — fresh `PyDict` allocation every timestep for every actor

**File:** `crates/hares-python/src/py_actor.rs:143–184`

`environment_to_py_dict` allocates a new `PyDict` (and nested dicts for `weather`, `grid`,
and each zone) on every call to `decide()`. For a simulation with N actors and T timesteps
this is N×T PyDict constructions. The dict is also heap-allocated Python objects that must
be GC'd.

A typed `EnvironmentView` pyclass holding a `*const EnvironmentState` (or a lifetime-bound
reference) would eliminate all per-step allocations. The pyclass would expose fields as
computed `#[getter]` properties that read directly from the Rust struct without copying.
This is the primary performance argument for the typed pyclass approach over TypedDict.

**Severity:** Medium — currently there are typically 1–5 Python actors per dwelling; at
large fleet scales (e.g. `hares-fleet`) this multiplies.

### Finding 6 — LOW: `ZoneState.wet_bulb_c` absent from zone dicts

**File:** `crates/hares-python/src/py_actor.rs:148–157`

The zone dicts include `temperature_c`, `humidity_ratio`, `relative_humidity`, and
`volume_m3` but not `wet_bulb_c`, which is present on `ZoneState` and is useful for
humidity-based control logic (e.g., dehumidifier actors).

**Severity:** Low.

## Recommended Fix: Typed `EnvironmentView` pyclass

The correct fix is a `#[pyclass] struct PyEnvironmentView` that holds a lifetime-erased
pointer or `Arc<EnvironmentState>` and exposes all fields via `#[getter]` properties.
Sub-structs (`weather`, `grid`, `zones[i]`, `price_signal`, `electrical`) should each be
separate `#[pyclass]` types. This gives:

1. Zero dict allocations in the hot path.
2. Full IDE autocomplete and mypy coverage via `.pyi` stubs.
3. No `KeyError` ever — attribute access on a pyclass raises `AttributeError` with the
   field name, which is much more informative.
4. All missing fields are automatically surfaced when the pyclass is derived from the
   struct fields.

**`TypedDict` as an intermediate step is acceptable** for the stub annotations (zero Rust
changes required) and should be done regardless of whether the full pyclass migration
happens — it provides immediate static analysis value.

The `current_time` field should be exposed as a Python `datetime.datetime` with timezone.
PyO3's `pyo3-chrono` feature provides `DateTime<FixedOffset>` → Python `datetime` conversion
automatically.

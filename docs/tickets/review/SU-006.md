## Background/Context

hares-fleet was completely untouched in the 130-ticket review. It handles multi-dwelling
batch simulation, parallel execution, and potentially fleet-level coordination.

## Verification

- `cargo check -p hares-fleet`: clean
- `cargo clippy -p hares-fleet`: clean (one unrelated warning in hares-equipment)
- `cargo test -p hares-fleet`: 14/14 tests pass

## Findings

### F-001 — MEDIUM — Progress callback panic subsumes successful simulation result

**File:** `crates/hares-fleet/src/fleet.rs:233-245`

The `catch_unwind` block in `simulate_parallel` wraps both `run_entry(entry)` and the
progress callback invocation together in one closure. If the callback panics after
`run_entry` returns `Ok`, the result is discarded and the entry is reported as
`SimError::Panic`. The test `panic_in_callback_is_isolated_to_one_result` confirms this
behaviour, but it is a correctness defect: a successful simulation is retroactively
treated as a failure solely because the notification callback panicked. The callback is
logically independent of the simulation result.

**Fix:** Move the progress callback invocation outside the `catch_unwind` scope, wrapping
only the callback call in its own separate `catch_unwind` that only emits a `tracing::warn`
on failure:

```rust
let outcome = panic::catch_unwind(AssertUnwindSafe(|| run_entry(entry)))
    .unwrap_or_else(|payload| Err(SimError::Panic { ... }));

if let Some(cb) = &progress {
    let done = completed.fetch_add(1, Ordering::Relaxed) + 1;
    let _ = panic::catch_unwind(AssertUnwindSafe(|| cb(done, total)));
}

outcome
```

### F-002 — MEDIUM — `default_resstock_sim_config` hard-codes 24-hour duration and always writes CSV output

**File:** `crates/hares-fleet/src/fleet.rs:499-517`

`Fleet::from_resstock` injects a simulation config with:
- `duration: Duration::hours(24)` — a full ResStock run is a year (8760 h); 24 hours will
  silently produce a grossly incomplete result with no error.
- `write_output: true` and `output_format: OutputFormat::Csv` — writes a CSV file for
  every dwelling to the current working directory (no `output_path` is set, so
  `output_path: None`). For a large ResStock fleet this creates thousands of CSV files in
  the working directory, has significant I/O overhead, and is surprising to callers who did
  not request file output.

There is no public API to override this config before calling `simulate()`. The Python
`Fleet.from_resstock` binding provides no `sim_config` parameter either.

**Fix (Rust):** Accept an optional `SimulationConfig` argument in `from_resstock`; fall
back to the current default only when `None`. Set `write_output: false` in the default
unless the caller explicitly requests output. The duration should either be removed from
the default (require the caller to provide it) or set to a full year.

**Fix (Python):** Expose `sim_config` in `PyFleet::from_resstock` and the `.pyi` stub.

### F-003 — LOW — Inconsistent thread-count semantics between `Fleet` and `SteppableFleet` construction

**Files:** `crates/hares-fleet/src/fleet.rs:211-223`, `fleet.rs:292-301`

`Fleet::simulate(n_threads)` accepts `0` to mean "use global Rayon pool". `SteppableFleet::from_configs(configs, n_threads)` also accepts `0` to mean "no dedicated pool (use global Rayon pool)", but in `simulate_parallel` there is no pool installed when `step_pool` is `None`, so `par_iter` will use whatever the global pool happens to be. This is internally consistent but the semantics are only documented in comments on `Fleet::simulate` — `SteppableFleet::from_configs` has no doc comment explaining the `0` meaning. A caller passing `0` expecting "sequential/single-threaded" execution will be surprised.

**Fix:** Add a doc comment to `SteppableFleet::from_configs` matching the contract stated on `Fleet::simulate`. No code change required.

### F-004 — LOW — `build_aggregate_batch` panics on `RecordBatch::try_new` schema mismatch via `unwrap_or_else`

**File:** `crates/hares-fleet/src/aggregation.rs:398`

```rust
RecordBatch::try_new(schema, arrays).unwrap_or_else(|_| empty_batch())
```

The error is silently swallowed and replaced with an empty batch. If a schema-arrays
length mismatch is introduced by a future change (e.g., a column is added to `fields` but
not `arrays`), the caller receives an empty aggregate result with no diagnostic. The only
contract guarantee is the aggregate_timeseries field is non-null — callers may interpret
silent empty batches as "no data" rather than "internal error".

**Fix:** Replace the silent fallback with `tracing::error!` logging before returning the
empty batch, or propagate the error up (requires changing return type of `aggregate`).

### F-005 — LOW — `SteppableFleet` time metadata taken from dwelling[0] only; heterogeneous fleets silently diverge

**File:** `crates/hares-fleet/src/fleet.rs:329-332`

```rust
let first = &dwellings[0].clock;
let total_steps = first.total_steps();
let time_res_s = first.time_res.num_milliseconds() as f64 / 1000.0;
```

If dwellings have different `DwellingConfig` sim configs (different durations or time
resolutions), `total_steps` and `time_res_s` are silently wrong for all but the first
dwelling. `is_finished()` uses only `current_step >= total_steps`, so the fleet halts at
the step count of dwelling[0] regardless of whether other dwellings have finished or have
more steps remaining.

This is an edge case for ResStock workloads where all configs share the same
`SimulationConfig`, but the API allows heterogeneous configs and makes no promise about
homogeneity.

**Fix:** After building `dwellings`, assert or return an error if any dwelling has a
different `total_steps` or `time_res` from dwelling[0]. Document the homogeneity
requirement explicitly.

### F-006 — LOW — `PyFleet::simulate` clones the entire fleet when a progress callback is provided

**File:** `crates/hares-python/src/py_fleet.rs:176-191`

The TODO comment (tagged `M-2`) acknowledges this. The full `Fleet` (which contains a
`Vec<FleetEntry>` with cloned `DwellingConfig` entries) is cloned solely to attach the
progress callback. For large fleets this is a significant unnecessary allocation.

The root cause is `Fleet::with_progress` and `Fleet::set_progress` take `&mut self`, but
`PyFleet::simulate` only holds `&self` due to PyO3's `#[pymethods]` constraint. The fix
does not require touching PyO3 constraints:

**Fix:** Add a `simulate_with_progress` method to `Fleet` that accepts the callback as an
argument at call time without mutating `self`. This removes the need for the clone path
entirely.

### F-007 — LOW — `progress.rs` is an empty placeholder module

**File:** `crates/hares-fleet/src/progress.rs`

The file contains only a module doc comment. It is registered in `lib.rs` but provides no
functionality. Dead modules increase cognitive surface area and can confuse contributors
who navigate to it expecting implementation.

**Fix:** Either delete the module and remove it from `lib.rs`, or add the planned
implementation.

### F-008 — INFO — `PySteppableFleet::step` queries `bldg_id` and `telemetry` in a second pass under the lock

**File:** `crates/hares-python/src/py_fleet.rs:403-409`

After calling `fleet.step()` the code walks `0..fleet.len()` twice more (once for
`bldg_id`, once for `telemetry`) while still holding the mutex. This is correct, but the
`bldg_id` values are static — they never change after construction. They could be
pre-computed outside the lock, or stored separately in `PySteppableFleet`, to reduce the
critical section length.

Not a correctness defect; flagged for maintainability.

## Missing Test Coverage

- No test covers the case where `Fleet::simulate` is given `n_threads` that exceeds the
  host CPU count (exercises Rayon's thread cap behaviour).
- No test verifies that `Fleet::from_resstock` with a filter produces the expected subset
  (the filter logic is tested only at unit level via `matches_filter`, not end-to-end).
- No test exercises `SteppableFleet` with heterogeneous `DwellingConfig` durations to
  expose the F-005 divergence.
- No test exercises `aggregate` when an individual dwelling's timeseries has zero rows
  (empty `RecordBatch`).
- `progress.rs` has zero tests (no content).
- Python-side fleet tests (`test_py_steppable_fleet.py`) skip entirely when fixtures are
  not present; they are unreachable in CI unless fixture data is bundled. No pure-logic
  unit tests exist for the Python fleet layer.

## Summary

The fleet orchestration layer is architecturally sound. Parallel execution via Rayon with
per-entry panic isolation is correct; `SteppableFleet` GIL-release semantics in PyO3 are
correct; partial-success build paths are well-handled and tested.

The most impactful defects are F-001 (successful simulations can be misreported as
failures due to callback panic coupling) and F-002 (ResStock default config silently
produces 24-hour partial runs and writes unexpected files to the working directory).
F-005 is a latent correctness hazard for callers who construct heterogeneous fleets.
Remaining findings are low-severity maintainability issues.

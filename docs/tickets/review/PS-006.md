## Background/Context

`Dwelling.step()` and `simulate()` are the hot-path Python methods. Errors here
(panics, silent data corruption, GIL issues) are catastrophic. The return values
must be predictable and typed.

## Findings

### CRITICAL — No panic boundary in `step()` or `simulate()`

**File:** `crates/hares-python/src/py_dwelling.rs:531-548`

Both `step()` and `simulate()` call into Rust via `py.detach(…)`, which releases
the GIL but provides no `std::panic::catch_unwind` boundary. A Rust panic inside
`dwelling.step()` or `dwelling.simulate()` will unwind through the PyO3 FFI
boundary and abort the Python process — not raise a Python exception. PyO3 itself
documents that Rust panics across FFI boundaries cause UB/abort unless wrapped
with `catch_unwind`.

`step_core` (line 1314) and the simulate closure (line 532) are both bare
`Result`-returning calls with no panic guard.

`batch_step_py` in `py_gym.rs:87-133` multiplies this risk: each Rayon thread
can panic independently with no recovery, and a Rayon thread panic propagates as
an abort.

**Severity:** Critical. A single `unwrap()` or `assert!` deep in the physics path
kills the Python process with no traceback.

**Fix:** Wrap the bodies of `step_core` and the `simulate` closure in
`std::panic::catch_unwind`. In `py_gym.rs`, wrap each Rayon closure in
`catch_unwind` and convert panics to the `Err(terminated=true)` path the error
branch already provides.

### HIGH — `simulate()` holds the Mutex for the entire simulation run

**File:** `crates/hares-python/src/py_dwelling.rs:531-543`

```rust
py.detach(|| {
    let mut dwelling = lock_dwelling_string(&self.dwelling)?;
    dwelling.simulate().map_err(|err| err.to_string())?;   // entire run
    Ok::<_, String>(())
})
```

The `MutexGuard` is held for the full duration of `simulate()`, which may be
millions of timesteps. Any other Python thread (or the same process via another
reference) that calls any method requiring `lock_dwelling` will block indefinitely.
Because this is a `std::sync::Mutex` (not `tokio::Mutex`), it is not async-aware;
calling `simulate()` from an async Python task will starve the event loop.

This is especially problematic for fleet use: if multiple dwellings are looped
over in Python and one calls `simulate()`, all subsequent lock attempts by other
code on that object are silently blocked.

**Severity:** High for correctness; medium for single-dwelling use, critical for
fleet/async use.

**Fix:** Step through in a loop (releasing and re-acquiring the lock each
timestep), or document that `simulate()` must not be called on a shared
`Dwelling` reference. The safest fix is to give `simulate()` an explicit "you
must not call any other method concurrently" contract enforced by an `initialized`
flag or `AtomicBool`.

### HIGH — `to_py_err` maps all `HaresError` variants to `PyValueError`

**File:** `crates/hares-python/src/py_dwelling.rs:1656-1658`

```rust
fn to_py_err<E: std::fmt::Display>(err: E) -> PyErr {
    PyValueError::new_err(err.to_string())
}
```

`HaresError` has seven distinct variants (`Physics`, `Envelope`, `Equipment`,
`Io`, `Control`, `Dwelling`, `Tariff`, `InvariantViolation`). All are flattened
to `ValueError` with a string message. Python callers have no way to distinguish
a physics invariant violation (potentially recoverable — try a different config)
from a missing input file (not recoverable), or from an invalid control signal
(caller bug). `step()` and `simulate()` both use `PyRuntimeError` for the outer
mapping, but the inner `to_py_err` call sites use `PyValueError`; the split is
inconsistent.

**Severity:** High for debuggability and catch-ability at the call site. Python
users cannot write `except SimulationError` vs `except ConfigError`.

**Fix:** Define typed Python exception subclasses (e.g., `HaresSimulationError`,
`HaresEquipmentError`, `HaresConfigError`) via `pyo3::create_exception!` and
dispatch on `HaresError` variant instead of erasing to a single `PyValueError`.

### HIGH — `step()` error message loses simulation context

**File:** `crates/hares-python/src/py_dwelling.rs:545-548` and `1314-1317`

```rust
pub fn step(&mut self, py: Python<'_>) -> PyResult<Py<PyAny>> {
    let step = py
        .detach(|| self.step_core())
        .map_err(PyRuntimeError::new_err)?;
```

```rust
pub(crate) fn step_core(&self) -> Result<hares_core::StepResult, String> {
    let mut dwelling = lock_dwelling_string(&self.dwelling)?;
    dwelling.step().map_err(|err| err.to_string())
}
```

When `step()` fails, the error message is the raw `HaresError::Display` string.
There is no timestep index, no current simulation time, and no equipment name
attached. For an invariant violation the message is
`"invariant violation in 'thermal_balance': value=1.234e+03, tolerance=1.000e-02"`,
which tells the user nothing about which timestep or building ID caused it.

**Severity:** High for diagnosability in production.

**Fix:** Augment the error with `dwelling.clock.current_step()` and the dwelling's
`bldg_id` before the error escapes `step_core`.

### MEDIUM — Corrupted-Mutex error message is actionable but state is undefined

**File:** `crates/hares-python/src/py_dwelling.rs:435-441`

```rust
fn lock_dwelling(dwelling: &Mutex<Dwelling>) -> PyResult<MutexGuard<'_, Dwelling>> {
    dwelling.lock().map_err(|e| {
        PyRuntimeError::new_err(format!(
            "dwelling state is corrupted (internal panic: {}); create a new Dwelling instance",
            e
        ))
    })
}
```

A poisoned `Mutex` means a panic occurred while the lock was held. The message
correctly tells the user to create a new instance. However, without `catch_unwind`
(see CRITICAL finding), a panic will abort the process before this code is ever
reached. This handler is therefore dead code in practice.

**Severity:** Medium. It becomes useful only if the CRITICAL panic-boundary fix
is applied first.

### MEDIUM — `step()` return type is untyped `dict` at runtime, `TypedDict` in stub

**File:** `python/ochre_next/_hares.pyi:13-24`, `crates/hares-python/src/py_dwelling.rs:565-577`

The stub declares `step() -> StepResult` where `StepResult` is a `TypedDict`
with four known keys (`timestamp`, `net_electric_power_kw`, `hvac_heating_w`,
`hvac_cooling_w`). The actual implementation returns a `PyDict` with those four
keys plus a variable number of zone-temperature keys (`"Temperature - Indoor (C)"`,
`"Temperature - Zone_N (C)"`).

The zone-temperature keys are not reflected in the `StepResult` TypedDict. Any
Python code that accesses them does so without type safety. Additionally, if a
dwelling has more than one zone, the number of keys in the returned dict is
indeterminate at the type level.

**Severity:** Medium. Silent type hole for multi-zone buildings.

**Fix:** Either extend `StepResult` with `zone_temperatures: dict[str, float]`
as a separate nested key (preserving a stable top-level shape), or document the
dynamic keys explicitly. The current approach conflates fixed and variable keys
in the same flat dict.

### MEDIUM — `batch_step_py` silently discards step error messages

**File:** `crates/hares-python/src/py_gym.rs:119-129`

```rust
Err(e) => {
    info.insert("error".to_string(), 1.0);
    let _ = e;    // error message discarded
    StepResult {
        obs: Vec::new(),
        reward: 0.0,
        terminated: true,
        ...
    }
}
```

The error `e` (a `String`) is explicitly dropped with `let _ = e`. The Python
caller receives `terminated=True` and `info["error"] = 1.0` with no message.
There is no way to distinguish a physics failure from an IO error or an invariant
violation from an RL training loop.

**Severity:** Medium. Silently swallowed errors are a maintenance hazard in RL
training pipelines.

**Fix:** Insert the error string into `info` (e.g., `info.insert("error_message",
…)`) or return it in a dedicated field. The `terminated` flag should not be the
only signal.

### LOW — `simulate()` acquires the Mutex twice: once inside GIL-free section, once outside

**File:** `crates/hares-python/src/py_dwelling.rs:530-543`

```rust
pub fn simulate(&self, py: Python<'_>) -> PyResult<Py<PyAny>> {
    py.detach(|| {
        let mut dwelling = lock_dwelling_string(&self.dwelling)?;
        dwelling.simulate()…
        // guard dropped here at end of closure
    })
    .map_err(PyRuntimeError::new_err)?;

    let dwelling = lock_dwelling(&self.dwelling)?;   // second lock
    let batches = dwelling.flushed_batches().to_vec();
    …
}
```

The first lock is released at the end of the `detach` closure, then a second lock
is taken to read results. This is correct, but the two-step lock pattern is
non-obvious. A comment should clarify why the lock is released between the two
critical sections (the GIL must be re-held before the second lock to avoid
deadlock with `lock_dwelling_string` vs `lock_dwelling`).

**Severity:** Low. Correctness is fine, but the pattern is a maintenance risk.

### LOW — `from_hpxml` error is mapped via `to_py_err` (PyValueError)

**File:** `crates/hares-python/src/py_dwelling.rs:484`

```rust
let dwelling = Dwelling::from_config(config.clone()).map_err(to_py_err)?;
```

Construction failure (e.g., missing HPXML file, invalid weather data) raises
`ValueError`. Users expecting `FileNotFoundError` or `RuntimeError` for
construction failures will be surprised.

**Severity:** Low. Consistent with other call sites but inconsistent with Python
idiom for file-not-found.

## Recommended Tests

- Unit test: confirm a Rust panic inside `step()` raises a Python exception
  (not crashes) once `catch_unwind` is added.
- Unit test: confirm `simulate()` raises `RuntimeError` with timestep context
  on an invariant violation injected via a minimal synthetic building.
- Unit test: confirm `batch_step_py` returns `info["error_message"]` on failure,
  not just `terminated=True`.
- Type-checking test (mypy/pyright): confirm `step()` return value passes strict
  type checking for a multi-zone building.

## Recommended Fixes (Priority Order)

1. Add `catch_unwind` in `step_core`, the `simulate` closure body, and each
   Rayon closure in `batch_step_py`. Convert panics to `PyRuntimeError` /
   `terminated=True` + error message.
2. Define typed Python exceptions via `pyo3::create_exception!` and dispatch
   on `HaresError` variant in `to_py_err`.
3. Augment step/simulate error messages with `bldg_id` and `current_step`.
4. Surface the error string in `batch_step_py` info dict.
5. Add zone-temperature entries to `StepResult` TypedDict as a nested dict or
   document the flat key pattern.

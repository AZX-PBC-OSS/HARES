## Background/Context

`EnvironmentManager` publishes schedule values each timestep into
`EnvironmentState::custom_domains`. The index into the schedule timeseries must use
local wall-clock time (not UTC, not weather-shifted time). Weather uses a midpoint
offset; schedules must NOT.

## Investigation Instructions

1. **Read `crates/hares-core/src/environment.rs`:**
   - Trace `compute_schedule_offset()` — what time base does it use?
   - Trace `compute_schedule_idx()` — how does it convert current_time → array index?
   - Is the schedule index separate from the weather index? (It should be.)
   - When DST is enabled, does the schedule index shift for DST transitions?

2. **Compare weather vs schedule indexing:**
   - Weather: `compute_annual_offset()` subtracts `midpoint_offset_secs` (30 min for EPW).
   - Schedule: should NOT subtract midpoint offset.
   - Verify these are indeed separate code paths.

3. **Compare with OCHRE** `schedule.py` `load_schedule()` lines 620–640 — how
   does OCHRE assign timezone to the schedule index vs weather index?

4. **Check edge cases:**
   - Year boundary wrapping
   - Leap year handling
   - Sub-hourly time resolution (does index arithmetic use seconds or steps?)

5. **Write findings** with line numbers and recommendations.


## Recommended Tests

1. **`solar_override_mid_year_start_alignment`** — construct an `EnvironmentManager` with `start_time = July 1`, set a `solar_override` table whose first entry has a known sentinel value, advance one step, and assert the irradiance in `EnvironmentState` matches that sentinel. Fails today because the override uses `step % len` not `(step + weather_start_offset) % len`.

2. **`compute_annual_offset_leap_year_after_feb28`** — call `compute_annual_offset` with a leap-year `start_time` of March 1 2024 and assert the resulting offset equals the offset computed using `365 * 86400` rather than `366 * 86400`. Verifies that the leap-year branch does not over-shift the index.

3. **`schedule_offset_independent_of_midpoint`** — verify that `compute_schedule_offset` for the same `start_time` returns a value exactly `midpoint_offset_secs / step_secs` greater than `compute_annual_offset` when `step_secs` evenly divides `midpoint_offset_secs`. This guards against accidental merge of the two code paths.

4. **`dst_path_assumes_annual_schedule`** — with `feature = "dst"` enabled, start a simulation on Jan 1 06:00 with a 15-minute schedule. Assert `compute_schedule_idx` at step 0 returns index 24, then at step 1 returns 25. Documents the annual-anchor assumption.

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### FINDING 1 — Severity: High — `solar_override` ignores `weather_start_offset`

**Location:** `environment.rs:449`

```rust
let idx = step % overrides.len();
```

Weather data is indexed as `(step + weather_start_offset) % weather_len`. The solar override skips `weather_start_offset`, so for any simulation that does not start at Jan 1 00:00 the override table is misaligned with the weather data by exactly `weather_start_offset` rows. At 1-hour resolution a July 1 start is off by 4344 rows. The feature is described in code comments as the primary path for OCHRE/pvlib parity and Python PySAM injection — both use-cases are broken for non-Jan-1 starts.

**Fix:**
```rust
let idx = (step + self.weather_start_offset) % overrides.len();
```
Alternatively, document in `set_solar_override` that the caller must pre-shift the table by `weather_start_offset` rows (expose a getter), but this is fragile and should not be the default.

---

### FINDING 2 — Severity: Medium — Leap-year `year_secs` inflates annual offset for EPW data

**Location:** `environment.rs:617–625`

```rust
let year_secs = if start_time.date_naive().leap_year() {
    366 * 86400_u64
} else {
    365 * 86400_u64
};
let shifted = (seconds_into_year + year_secs - meta.midpoint_offset_secs as u64) % year_secs;
```

EPW files always contain exactly 8760 rows (365 days × 24 hours). When `start_time` falls in a leap year, `year_secs = 366 * 86400` but the array is only `365 * 86400 / step_secs` long. For a start date after Feb 28 in a leap year, `shifted` is larger than the array by one day's worth of steps, but `% weather_len` in `update_in_place` rescues it to a valid index that is off by one day from the intended position.

**Fix:** Use `365 * 86400` unconditionally in `compute_annual_offset` since EPW source data is non-leap. The existing test `annual_offset_leap_year_may_5_noon` should be checked: if it currently passes, the test's expected value may already be wrong.

---

### FINDING 3 — Severity: Medium — DST path undocumented assumption: schedule is annual, Jan 1-anchored

**Location:** `environment.rs:327–341`

When `civil_tz` is set, `schedule_start_offset` is entirely unused. The index is derived from `civil.ordinal0()` which is the zero-based day-of-year. This only produces a correct result if the schedule array is annual (8760 or 8784 rows) and its row 0 corresponds to Jan 1 00:00 local time. This assumption is undocumented.

For a schedule that starts at the simulation's start date (not Jan 1), the DST path will compute indices up to `364 * 96` steps into the array before the modulo wraps, while the array may only have `sim_duration / step_secs` rows.

**Fix:** Add a doc comment to `compute_schedule_idx` stating: "Assumes the schedule is annual (365 × 24 × steps/hour rows) and anchored to Jan 1 00:00 local time. Non-annual schedules must use the fixed-offset path."

---

### FINDING 4 — Severity: Low — `compute_schedule_offset` truncation silent for non-step-aligned starts

**Location:** `environment.rs:643`

```rust
(seconds_into_year / step_secs as u64) as usize
```

If `start_time` is not aligned to a step boundary (e.g., start at 00:01 with 15-minute steps), integer truncation silently rounds down. For common ResStock schedules with hourly or 15-minute resolution this is benign because simulation start times are always on step boundaries. However, there is no assertion or error if the remainder is non-zero.

**Fix:** Add a debug assertion:
```rust
debug_assert_eq!(seconds_into_year % step_secs as u64, 0,
    "start_time is not aligned to schedule step boundary");
```

---

### Summary of index scheme

| Domain | Offset source | Midpoint correction | Leap-year aware? |
|---|---|---|---|
| Weather | `compute_annual_offset` | Yes (`midpoint_offset_secs`) | Yes (bugged for EPW) |
| Schedule (fixed-offset) | `compute_schedule_offset` | No (correct) | No (correct) |
| Schedule (DST) | re-derived from `civil_tz` each step | No (correct) | Yes (via ordinal0) |
| Solar override | None (bug) | N/A | N/A |

The fundamental design — separate offset computations for weather and schedule, with schedule using raw wall-clock seconds and weather using a midpoint-shifted position — is correct. The three defects above are implementation gaps rather than design flaws.

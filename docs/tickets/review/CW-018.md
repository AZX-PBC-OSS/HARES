## Background/Context

Mechanical ventilation (exhaust, HRV, ERV) config includes: flow rate (CFM→m³/s),
fan power (W), sensible/latent recovery effectiveness, and operating schedule.
HARES has a dedicated `ventilation.rs` equipment model.

## Findings

### F-1 [CRITICAL] Flow rate never converted CFM → m³/s; equipment silently uses default

**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:554`

The resolver writes the raw CFM value under the key `"ventilation_rate_cfm"`:

```rust
params.insert("ventilation_rate_cfm".to_string(), json!(flow_cfm));
```

`Ventilation::init()` in `crates/hares-equipment/src/ventilation.rs:217` reads only the key `"flow_rate_m3_s"`:

```rust
self.flow_rate_m3_s = config.get_f64(KEY_FLOW_RATE_M3_S).unwrap_or(DEFAULT_FLOW_RATE_M3_S);
// KEY_FLOW_RATE_M3_S = "flow_rate_m3_s"
```

Two distinct bugs compound here:

1. The key name does not match: `"ventilation_rate_cfm"` is written; `"flow_rate_m3_s"` is read. The HPXML value is never consumed.
2. No CFM → m³/s conversion exists anywhere in the resolver for this field. 1 CFM = 0.000471947 m³/s.

Result: every real building silently falls back to `DEFAULT_FLOW_RATE_M3_S = 0.035 m³/s` (~74 CFM) regardless of what HPXML specifies. Energy and thermal load calculations are wrong for any building whose ventilation rate differs from the default.

**Fix required:** Rename the resolver key to `"flow_rate_m3_s"` and apply the conversion:
```rust
params.insert("flow_rate_m3_s".to_string(), json!(flow_cfm * 0.000_471_947));
```

### F-2 [CRITICAL] Sensible/latent effectiveness keys never consumed; equipment uses hardcoded defaults

**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:578,585`

The resolver writes:
- `"sensible_recovery_efficiency"` — raw value from `SensibleRecoveryEfficiency`
- `"latent_recovery_efficiency"` — derived as `TotalRecoveryEfficiency - SensibleRecoveryEfficiency`

`Ventilation::init()` reads:
- `KEY_SENSIBLE_EFFECTIVENESS = "sensible_effectiveness"` (line 220)
- `KEY_LATENT_EFFECTIVENESS = "latent_effectiveness"` (line 224)

Neither resolver key matches the equipment key. Both values fall back to:
- `DEFAULT_SENSIBLE_EFFECTIVENESS = 0.70`
- `DEFAULT_LATENT_EFFECTIVENESS = 0.0`

An ERV with e.g. 75% sensible / 65% latent recovery from HPXML runs as a 70% sensible / 0% latent HRV. The latent mismatch is especially significant for humid climates.

Note: OCHRE uses `SensibleRecoveryEfficiency` and `AdjustedSensibleRecoveryEfficiency`. HARES reads only `SensibleRecoveryEfficiency`. HPXML 4.x introduced `Adjusted*` variants that account for temperature correction. This is an additional gap but lower priority than the key name mismatch.

**Fix required:** Rename resolver keys to match equipment constants:
```rust
params.insert("sensible_effectiveness".to_string(), json!(sensible_re));
// ...
params.insert("latent_effectiveness".to_string(), json!(latent_re));
```

### F-3 [CRITICAL] Ventilation type never wired; HRV/ERV/exhaust distinction always falls back to HRV

**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:571-572`

The resolver writes `"fan_type"` (raw HPXML string, e.g. `"energy recovery ventilator"`) and `"balanced"` (bool). It never writes the key `"ventilation_type"`.

`Ventilation::new()` reads `config.get_str("ventilation_type")` (line 114) and defaults to `VentilationType::Hrv` when absent. Possible string values are `"exhaust_fan"`, `"erv"`, `"hrv"`.

Consequence: an HPXML ERV (`FanType = "energy recovery ventilator"`) is instantiated as an HRV. Latent recovery is unconditionally zero for HRV (`effective_latent_effectiveness` returns 0.0 when `ventilation_type != Erv`). An exhaust-only fan is also instantiated as an HRV and incorrectly applies 70% sensible recovery effectiveness.

**Fix required:** Map the HPXML `FanType` string to the HARES `ventilation_type` key in the resolver:
```rust
let vtype = match ft_lower.as_str() {
    "exhaust only" | "supply only" => "exhaust_fan",
    "energy recovery ventilator" => "erv",
    _ => "hrv",
};
params.insert("ventilation_type".to_string(), Value::String(vtype.to_string()));
```

### F-4 [MEDIUM] Default fan power when `FanPower` absent not implemented; OCHRE uses W/CFM defaults

**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:556-561`

OCHRE `parse_vent_fan` (hpxml.py:1634) uses per-type default W/CFM multipliers when `FanPower` is absent:
```python
default_powers = {
    "energy recovery ventilator": 1,     # W/cfm
    "heat recovery ventilator": 1,
    "balanced": 0.7,
    "exhaust only": 0.35,
    "supply only": 0.35,
    "whole house fan": 0.1,
}
power = vent_fan.get("FanPower", flow_rate * default_powers[fan_type])
```

HARES resolver only writes `"fan_power_w"` when the element is present:
```rust
if let Some(power_w) = child_f64(fan, "FanPower") {
    params.insert("fan_power_w".to_string(), json!(power_w));
```

When `FanPower` is absent (common in older HPXML), HARES falls back to `DEFAULT_FAN_POWER_W = 50.0 W` regardless of fan type or flow rate. For a 100 CFM HRV (typical OCHRE default = 100 W), this is a 50% error.

**Fix required:** Apply OCHRE's W/CFM defaults when `FanPower` is absent, using the flow rate already parsed.

### F-5 [MEDIUM] `HoursInOperation` not read; schedule always constant 1.0

**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:532-595`

OCHRE asserts `HoursInOperation == 24` (hpxml.py:1622). The HARES resolver does not read or validate `HoursInOperation` at all, and the equipment supports only `ScheduleSource::Constant`. When a building has `HoursInOperation < 24` the ventilation runs full-time rather than intermittently, overestimating energy use and infiltration-equivalent ventilation load.

Typical ASHRAE 62.2 systems run 24 h/day, so this is edge-case but not rare in HPXML files generated by ResStock or custom tooling.

**Fix required:** Read `HoursInOperation` and, if < 24, either wire a fractional constant schedule (e.g. `HoursInOperation / 24.0`) or log an explicit warning that intermittent schedules are not yet supported.

### F-6 [LOW] `"power_w"` duplicate key emitted for ScheduledLoad fallback path

**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:560-561`

The comment says this key is "kept for compatibility" with a `ScheduledLoad` fallback path. This codebase has no backward-compat requirement (see project memory). The dead key adds noise to the config map and the comment incorrectly implies there is a second code path consuming it. If the ScheduledLoad fallback path is real it needs a reference; if it is dead code it should be removed.

### F-7 [LOW] Air density hardcoded at 1.2 kg/m³; altitude correction absent

**File:** `crates/hares-equipment/src/ventilation.rs:54`

```rust
const AIR_DENSITY_KG_M3: f64 = 1.2;
```

At Denver (~1600 m), air density is ~1.05 kg/m³ (-12%). Mass flow and therefore all thermal loads are overestimated by ~12% for high-altitude buildings. The `EnvironmentState` already carries weather data; outdoor pressure or elevation could drive a correction. This is a physics quality issue consistent with the project's EnergyPlus-grade physics requirement.

---

### F-8 [LOW] Fan heat gain to zone not modeled

**File:** `crates/hares-equipment/src/ventilation.rs:357-362`

Fan electrical energy (50–100 W) is entirely absorbed as electrical load but no portion is added to zone thermal gain. OCHRE's `ScheduledLoad` approach implicitly adds a fraction via `Convective Gain Fraction`. EnergyPlus adds fan heat to the supply air stream. For a 100 W fan running 24 h/day this is ~876 kWh/yr of missing zone heat, roughly 0.4–1% of annual heating load in cold climates.

### OCHRE Architecture Note

OCHRE's ventilation fan is a `ScheduledLoad` subclass (not a dedicated thermal model). Recovery effectiveness parameters are passed to the zone infiltration model (`zones["Indoor"]`), not to the equipment instance. HARES deliberately improves on this by computing actual supply-air temperature in the equipment — but the improvement is moot until the config wiring is fixed.

## Recommended Tests

All tests should be placed in `crates/hares-equipment/tests/` or added to the integration fixture set. Specific assertions are given below.

### T-1 — Flow rate conversion roundtrip
In a unit test for `Ventilation::init`, construct an `EquipmentConfig` with `"flow_rate_m3_s": 0.047` (100 CFM × 0.000471947) and assert `ventilation.flow_rate_m3_s ≈ 0.047`. This confirms the equipment side is correct. Then add a resolver-level test that parses a minimal HPXML `VentilationFan` node with `RatedFlowRate = 100` and asserts the emitted spec contains key `"flow_rate_m3_s"` with value `≈ 0.0472`.

### T-2 — Key name mismatch regression (sensible effectiveness)
Unit test: config with key `"sensible_recovery_efficiency": 0.80` should not be consumed (assert `sensible_effectiveness == 0.70` default to prove the bug). After the fix, assert `sensible_effectiveness == 0.80`. This is a regression guard, not a style test.

### T-3 — ERV latent recovery activated
Construct ERV config with `"ventilation_type": "erv"`, `"latent_effectiveness": 0.60`, call `step()` with high indoor humidity and low outdoor humidity, assert `q_latent_w > 0`. Separately, run the same config as `"hrv"` and assert `q_latent_w == 0`. This guards the ERV/HRV distinction.

### T-4 — Exhaust fan has zero recovery
Construct exhaust-fan config, call `step()` in heating conditions (outdoor -10°C, indoor 20°C), assert `sensible_recovery_w == 0` and `supply_temp_c ≈ outdoor_temp_c`.

### T-5 — Resolver: FanType → ventilation_type mapping
Integration test (resolver level): HPXML with `FanType = "energy recovery ventilator"` should produce a spec with `"ventilation_type": "erv"`. HPXML with `FanType = "exhaust only"` should produce `"ventilation_type": "exhaust_fan"`. HPXML with `FanType = "heat recovery ventilator"` should produce `"ventilation_type": "hrv"`.

### T-6 — Default fan power fallback (W/CFM)
Resolver test: HPXML without `FanPower` element but with `RatedFlowRate = 100` and `FanType = "energy recovery ventilator"` should produce `"fan_power_w" ≈ 100.0` (1 W/CFM). Same for `"exhaust only"` → `35.0 W` (0.35 W/CFM).

### T-7 — Parity test: HRV building end-to-end
Add a parity fixture (or reuse an existing one with an HRV) that simulates one full day in heating season. Assert annual fan energy within 5% of OCHRE reference and zone temperature MAE < 0.5°C. This is the integration regression guard that would have caught F-1 through F-3 at landing.

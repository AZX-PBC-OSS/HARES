## Background/Context

After FIX-031-001 added `ThermalCategory` (HvacHeating, HvacCooling, InternalGain,
JacketLoss, DuctLoss), every equipment must tag its thermal port contributions
with the correct category. Incorrect tagging means the envelope solver can't
distinguish heat sources, and output disaggregation is wrong.

### Finding 1 — BUG: Dehumidifier uses `InternalGain` despite removing latent energy from zone

**Severity: Moderate (disaggregation error)**

**File:** `crates/hares-equipment/src/hvac/dehumidifier.rs:434`

`sensible_gain_w = latent_removal_w + electric_power_w` (line 236). This is always
non-negative (the dehumidifier adds sensible heat to the zone as a side effect of
condensing moisture), so the sign is not the problem. The problem is semantic: the
sensible gain here is the thermodynamic byproduct of the refrigeration cycle, not
typical appliance waste heat. It is more precisely classified as `HvacHeating` than
`InternalGain` because it results from an active mechanical refrigeration process —
the dehumidifier is mechanically more similar to a heat pump than a toaster.

Using `InternalGain` causes the dehumidifier's sensible contribution to be lumped
with lighting and plug loads in the component gain breakdown, obscuring HVAC
disaggregation. OCHRE treats dehumidifier sensible gain as part of `Total Internal
Gains (W)` (it has no HVAC routing), so `InternalGain` is not catastrophically wrong,
but a dedicated `DehumidifierGain` or at minimum a comment explaining the choice would
prevent future confusion.

**Fix:** Either:
(a) Accept `InternalGain` as the closest available category, but add a code comment
    explaining that the dehumidifier's sensible contribution is the heat-of-compression
    byproduct, not a user-facing appliance load; or
(b) Add a `DehumidifierGain` variant to `ThermalCategory` for mechanical latent removal
    appliances whose sensible output is a refrigeration cycle byproduct.

Option (a) is lower risk and sufficient until disaggregated output is needed.

### Finding 2 — BUG: HPWH uses `InternalGain` for a signed zone-heat interaction

**Severity: Moderate (reporting correctness)**

**File:** `crates/hares-equipment/src/water_heater/heat_pump_wh.rs:775-800`

`sensible_gain_w = (hp_waste_w * shr + fan_parasitic_w + er_waste_w) * keep_fraction`
where `hp_waste_w = compressor_power_w - delivered_hp_w`. When COP > 1,
`hp_waste_w` is negative, making `sensible_gain_w` negative. The HPWH extracts more
thermal energy from the zone air than its compressor consumes — a net cooling effect.

`ThermalCategory::InternalGain` is documented as "waste heat from appliances, lighting,
occupancy — always a positive contribution." Posting a negative value under this category
is semantically inconsistent. The code comment at line 799 acknowledges this explicitly
("InternalGain captures the mixed character"), which is a signal that the category is wrong.

**Consequence for physics:** None. The signed value accumulates correctly into
`sensible_gain_w` on the `ThermalAccumulator`. The solver uses the total, not the
per-category breakdown.

**Consequence for reporting:** `sensible_for_category(InternalGain)` returns negative
values when the HPWH is in heat-pump mode, which breaks any tool or assertion that
assumes `InternalGain >= 0`. This is explicitly flagged in AR-003 F-004.

**Fix:** Add a `HeatPumpExtraction` variant to `ThermalCategory`. Update:
- `THERMAL_CATEGORY_COUNT` in `crates/hares-types/src/ports.rs`
- `ThermalCategory::index()` match arm
- `crates/hares-envelope/src/thermal_solver/mod.rs` (add a read for the new category
  in the `EnvelopeComponentGains` construction block and expose it as `hpwh_zone_exchange_w`)
- `heat_pump_wh.rs:800` — use `ThermalCategory::HeatPumpExtraction`

This is a data-model change with no physics impact. The existing test in
`crates/hares-types/tests/type_interop.rs` that exhaustively iterates all categories
must be updated to include the new variant.

### Finding 3 — GAP: Tankless water heater emits no thermal port

**Severity: Low (missing zone heat gain)**

**File:** `crates/hares-equipment/src/water_heater/tankless.rs`

The tankless WH emits only `Electrical` and `Fuel` port contributions. There is no
`PortContribution::Thermal` for zone jacket losses or parasitic heat, despite the unit
occupying conditioned space in most residential configurations.

Gas tankless: the pilot light and burner body radiate heat into the space. OCHRE models
this as a skin loss term. HARES does not.

Electric tankless: similarly, wire resistance losses in the heating elements are
incidentally transmitted to the zone — small but nonzero.

**Fix:** Assess whether the tankless jacket loss is large enough to model. If yes, add
a `skin_loss_w` computation (proportional to burner/element heat and an efficiency
factor) and emit it with `ThermalCategory::JacketLoss`. If the loss is judged
negligible, document the deliberate omission with a comment.

### Finding 4 — BUG: Ventilation uses `InternalGain`, masking a signed contribution

**Severity: Low–Moderate (disaggregation)**

**File:** `crates/hares-equipment/src/ventilation.rs:357-362`

`q_sensible_w` is the net sensible load from outdoor-air infiltration through the
ventilation system. In winter, `q_sensible_w < 0` (cold outdoor air cools the zone).
In summer or mixed climates, it can be positive. Posting a potentially-negative value
under `InternalGain` has the same semantic violation as Finding 2.

Ventilation heat exchange is not an appliance internal gain; it is a boundary condition
exchange with the outdoor environment. The most accurate category would be a new
`VentilationGain` variant, but as a pragmatic alternative, posting it under `HvacHeating`
(positive) or `HvacCooling` (negative) would at least not corrupt the `InternalGain`
breakdown.

**Fix:** Either:
(a) Add a `VentilationGain` variant to `ThermalCategory`, or
(b) Split the contribution: post positive `q_sensible_w` to `InternalGain` and
    negative `q_sensible_w` to `HvacCooling` to avoid negative `InternalGain` entries.

Note: when `q_sensible_w == 0` the contribution is gated (`sensible_gain_w != 0.0 || ...`)
so zero-value contributions are correctly suppressed.

### Finding 5 — CRITICAL BUG: `DuctLoss` category never emitted — confirmed

**Severity: Critical (output metric always 0)**

**Files:** `crates/hares-equipment/src/hvac/duct_distribution.rs:48-81`,
`crates/hares-envelope/src/thermal_solver/mod.rs:376-378`

This finding was previously documented in AR-006 Finding 2 and DL-004 Finding 1. The
investigation confirms it is still present.

`write_zone_thermal_contributions` accepts a single `category: ThermalCategory` argument
and broadcasts it uniformly to all zones — conditioned, basement, and duct zone alike
(lines 63-78). Every caller passes `HvacHeating` or `HvacCooling`:

- `furnace.rs:169,373` — `ThermalCategory::HvacHeating`
- `heat_pump/heater.rs:595` — `ThermalCategory::HvacHeating`
- `air_conditioner.rs:641` — `ThermalCategory::HvacCooling`
- `baseboard.rs:129` — `ThermalCategory::HvacHeating`

The duct zone entry (fraction = `1 - dse`, zone = `duct_zone_id`) therefore receives
`HvacHeating` or `HvacCooling`, not `DuctLoss`. `ThermalCategory::DuctLoss` is never
passed anywhere. `EnvelopeComponentGains.duct_loss_w` is structurally always 0.

Additionally, as documented in DL-004 Finding 2, the thermal solver reads `duct_loss_w`
from `indoor_acc` (the conditioned-zone accumulator), not from the duct-zone accumulator.
Even after the `write_zone_thermal_contributions` fix, the read will remain in the wrong
accumulator unless also fixed.

Finally, because duct-zone contributions are tagged `HvacHeating`/`HvacCooling`,
`hvac_heating_w` and `hvac_cooling_w` include the duct loss fraction, overstating
delivered HVAC energy by `(1 - dse)` — typically 10–20% for residential buildings.

**Fix:** Two changes are required:

1. `write_zone_thermal_contributions` must detect the duct zone and override the category:

```rust
for &(zone, fraction) in fractions {
    if fraction > 0.0 {
        let effective_category = if zone != self.zone_id {
            ThermalCategory::DuctLoss
        } else {
            category
        };
        ports.accumulate(&PortContribution::Thermal {
            zone,
            sensible_gain_w: sensible_gain_w * fraction,
            latent_gain_w: latent_gain_w * fraction,
            category: effective_category,
        })?;
    }
}
```

Note: the single-entry fast path (lines 61-68) applies only when `fractions.len() == 1`,
which means no duct zone is present, so the fast path does not need to change.

2. `thermal_solver/mod.rs:376-378` must be changed to read `DuctLoss` from the
   duct-zone accumulator (if available), or to derive duct loss as a scalar from
   `gross_capacity_w * (1 - dse)` mirroring OCHRE's approach (DL-004 Finding 2).

### Finding 6 — INFORMATIONAL: Battery thermal port posts only ohmic losses, not cell-to-zone UA heat

**Severity: Low (minor incompleteness)**

**File:** `crates/hares-equipment/src/battery/mod.rs:1033-1046`

The comment at lines 1033-1036 explains that `heater_w` is excluded to avoid
double-counting: heater energy enters the cell thermal model and reaches the zone
via the UA conductance pathway. Only ohmic losses are posted directly.

However, the `q_loss` term (cell-to-zone UA heat flux) is also not posted. The AR-003
review (F-XXX in battery section) noted that `q_loss.max(0.0)` should be posted as a
zone gain each step. The current code posts only `ohmic_loss_w`.

AR-003 recommendation is: post `q_loss.max(0.0)` as `InternalGain` (heat flowing from
hot cell into zone). Negative `q_loss` (zone warming cold cell) should also be posted
as a negative `InternalGain` or the new `HeatPumpExtraction` category after Finding 2
is resolved.

**Status:** This is a pre-existing gap noted in AR-003. Not newly introduced, but
confirmed still unresolved.

## Background/Context

Dehumidifiers should activate based on indoor humidity exceeding a setpoint, not
based on temperature or HVAC mode. They operate independently of the thermal solver.

## Investigation Instructions

1. Read HARES `dehumidifier.rs` — what drives on/off decisions?
2. Is humidity setpoint read from HPXML or defaulted?
3. Does it read zone humidity from `EnvironmentState`?
4. Compare with OCHRE dehumidifier behavior.

## Findings

### OCHRE Reference

OCHRE has no dehumidifier Equipment class. `Humidity.py` contains a `# FUTURE: Dehumidifier?`
comment and `hpxml.py` has `# TODO: add dehumidifier`. OCHRE test fixture XML files define
`<DehumidistatSetpoint>0.5</DehumidistatSetpoint>` and `<FractionDehumidificationLoadServed>`,
but OCHRE never instantiates dehumidifier equipment from this data. HARES therefore has no
parity target to check against — the HARES implementation is entirely original.

### Activation Logic (dehumidifier.rs:183–201)

On/off decisions are made in `update_is_on`, called from `update_control` (line 390), which
itself is called at the top of `step` (line 411). The control path is:

1. Reads `zone.relative_humidity` from `EnvironmentState`, clamped to `[0.0, 1.0]`.
2. Applies a two-threshold deadband hysteresis:
   - **Turn ON**: `current_rh > max_rh`  (strict greater-than)
   - **Stay ON**: `current_rh >= min_rh`  (inclusive)
   - **Turn OFF**: `current_rh < min_rh`
3. Default setpoint: `target_rh = 0.50`, deadband half-width = `0.025`, so
   `min_rh = 0.475`, `max_rh = 0.525`.

This is a standard two-threshold thermostat-style hysteresis. It is independent of the
thermal solver — no temperature or HVAC mode is consulted in the activation path.

### Bug: Asymmetric Deadband with `mode_override = Some(Standby)`

`update_is_on` (line 187) maps `OperatingMode::Standby` to `is_on = true`. `Standby`
conventionally means the equipment is idle (not actively running). Forcing `is_on = true`
on a Standby override causes the dehumidifier to run at full power, which contradicts the
mode semantics. Only `Cooling` should force on.

**Fix**: remove `Some(OperatingMode::Standby)` from the forced-on arm.

### Bug: `update_control` is called twice per step

`step` calls `self.update_control(env)` (line 411) and then independently re-reads
`zone.relative_humidity` for `performance_snapshot` (line 420). `update_control` is also
part of the `Equipment` trait and is called by the engine's control pass before `step`.
This means the activation logic runs at least twice per timestep, and the `is_on` flag
set in the trait-level `update_control` call is immediately overwritten by the call inside
`step`. If any external control signal was applied between the trait call and `step`, it
will be respected because `mode_override` is checked each time; however the redundant
call is wasted work and inconsistent with how other equipment is structured.

**Fix**: remove the internal `self.update_control(env)` call at line 411; rely on the
engine invoking `update_control` before `step` per the trait contract.

### Gap: No HPXML Parsing for Dehumidifier

`crates/hares-io/src/hpxml/resolve_loads.rs` does not parse `<Dehumidifier>` elements.
The HPXML fixture inventory test (`hpxml_fixture_inventory.rs:80`) loads
`base-appliances-dehumidifier.xml` but only asserts on unrelated appliance tags — it
does not assert that a `Dehumidifier` spec is emitted. Dehumidifiers specified in HPXML
are silently ignored.

**Fix**: Add a `parse_dehumidifier` function in `resolve_loads.rs` that reads
`DehumidistatSetpoint`, `Capacity` (pints/day), `IntegratedEnergyFactor`/`EnergyFactor`,
and `FractionDehumidificationLoadServed` from the HPXML `<Appliances><Dehumidifier>`
element and emits a `Dehumidifier` `EquipmentSpec`. Update the fixture inventory test to
assert that the spec is produced.

### Gap: No Dedicated Unit Tests for Dehumidifier Activation

There are inline tests in `dehumidifier.rs` (visible at lines 832, 849–853, 941, 954, 960)
that cover basic hysteresis transitions. However there are no tests in
`crates/hares-equipment/tests/` for:
- `min_rh`/`max_rh` boundary exactness (off-by-one on `>=` vs `>`)
- Behaviour when `zone` is absent from `EnvironmentState` (should be off, not panic)
- `mode_override = Some(Standby)` forcing on — this path is untested and the semantics
  are wrong (see bug above)
- Accumulated water removal accumulation over multiple steps

### Minor: IEF + EF-era curves warning is insufficient

Line 319 emits a `tracing::warn!` when `IntegratedEnergyFactor` is used with biquadratic
curves designed for the older `EnergyFactor` test standard. This mismatch can cause
systematic energy prediction errors. The warning is a runtime log — it should be surfaced
as a validation result or at minimum include the magnitude of potential deviation so
operators can assess impact.

## Recommended Tests

1. **`test_dehumidifier_turn_on_above_max_rh`** — assert that at `rh = max_rh` the unit
   stays off (strict `>` boundary), and at `rh = max_rh + epsilon` it turns on.
2. **`test_dehumidifier_stay_on_down_to_min_rh`** — assert that once on, the unit stays
   on at `rh = min_rh` (inclusive `>=`) and turns off at `rh = min_rh - epsilon`.
3. **`test_dehumidifier_missing_zone_stays_off`** — call `update_control` with an
   `EnvironmentState` that contains no matching zone; assert `OperatingMode::Off`.
4. **`test_dehumidifier_standby_override_semantics`** — verify expected behaviour
   once the Standby bug is resolved.
5. **`test_dehumidifier_accumulated_water_removal`** — step the equipment for N
   timesteps at a known RH and verify accumulated water matches
   `water_removal_l_day * total_seconds / SECONDS_PER_DAY`.
6. **`test_hpxml_dehumidifier_parsed`** — load `base-appliances-dehumidifier.xml` and
   assert a `Dehumidifier` spec is emitted with the correct setpoint and capacity.

## Background/Context

PV config includes: capacity, tilt, azimuth, module type, system losses, inverter
efficiency, shading, soiling. HARES has a SAM-derived efficiency LUT and a rainfall
soiling model that OCHRE doesn't — these are improvements to document, not remove.

OCHRE architecture note: OCHRE does NOT parse PV from HPXML at all. The
`parse_hpxml_equipment` function in `ochre/utils/hpxml.py` has no PV section. OCHRE
receives `capacity`, `tilt`, `azimuth`, `inverter_capacity`, `inverter_efficiency` as
constructor kwargs passed by the caller (ResStock pipeline or direct user code). OCHRE
passes these directly to PVWatts v8 via PySAM at simulation start.  All HPXML-to-PV
field extraction is HARES's own work.

## Findings

### F-1 (Critical): ModuleType case mismatch — premium and thin-film modules silently become standard

**File:** `crates/hares-equipment/src/pv/array_config.rs:22-28`

`ModuleType::from_str` matches only `"Premium"` and `"ThinFilm"` (title-case /
PascalCase). All real HPXML files emit lowercase: `"standard"`, `"premium"`,
`"thin film"` (with a space). The OCHRE OS-HPXML sample files confirm this:

```xml
<!-- vendors/OCHRE/test/OS-HPXML Sample Files/base-pv-battery-ah.xml:435,446 -->
<ModuleType>standard</ModuleType>
<ModuleType>premium</ModuleType>
```

The HARES parity fixtures use the same casing:

```
tests/fixtures/parity/cz4a_pv_only/building.xml:906  <ModuleType>standard</ModuleType>
tests/fixtures/parity/cz4a_pv_battery/building.xml:906  <ModuleType>standard</ModuleType>
```

When a fixture has `"premium"`, it falls through to `Standard`, setting gamma to
`-0.0047 /°C` instead of the correct `-0.0035 /°C`.  Power output error at 25 °C above
STC reference grows as `Δγ × ΔT × capacity_kw`, approximately `+3.5%` per 10 °C of
excess cell temperature.  The error is silent — no warning is logged.

The `"thin film"` variant (with space) used by real HPXML files likewise falls through
to `Standard`; the ThinFilm branch would require `"ThinFilm"` with no space.

**Fix required:** case-insensitive matching, handle both `"thin film"` and `"ThinFilm"`:

```rust
match s.trim().to_ascii_lowercase().as_str() {
    "premium" => Self::Premium,
    "thinfilm" | "thin film" | "thin_film" => Self::ThinFilm,
    _ => Self::Standard,
}
```

### F-2 (High): `ArrayTilt` extracted from HPXML but silently dropped before reaching `PvArray`

**File:** `crates/hares-io/src/hpxml/resolve_der.rs:43-45`

`resolve_pv` stores tilt as key `"tilt_deg"`. `PvArray::from_single_config` reads it
under that key first, then falls back to `KEY_ARRAY_TILT_DEG` (`"ArrayTilt"`). This
part works.

However, the resolver does NOT emit the key `"ArrayTilt"` at all; it emits `"tilt_deg"`.
The `KEY_ARRAY_TILT_DEG` fallback in `from_single_config` (`array_config.rs:72-73`) is
therefore unreachable from the HPXML path — it exists only as a direct-config bypass
(e.g. Python injection). That is acceptable as designed, but constitutes a dead code path
that misleads readers. Document or remove `KEY_ARRAY_TILT_DEG` fallback if it is only
for Python config, not for HPXML round-trip.

No silently wrong value here because the primary `"tilt_deg"` key is written and read
correctly — this is a code clarity issue, not a correctness defect.

### F-3 (High): `inverter_capacity_kw` not extracted from HPXML — DC/AC ratio clipping is never active

**File:** `crates/hares-io/src/hpxml/resolve_der.rs:56-63`

The resolver extracts `InverterEfficiency` from the inverter node but does not extract
any capacity field. HPXML does not have a dedicated `<InverterCapacity>` element in the
core spec, but it is common to over-size the DC array relative to a smaller inverter
(`dc_ac_ratio > 1`). OCHRE accepts an explicit `inverter_capacity` kwarg that enables
inverter clipping (`apply_inverter_limits`).  HARES has `KEY_INVERTER_CAPACITY_KW_ALT`
(`"InverterCapacity"`) as a config alias (`mod.rs:40`) but no path from HPXML wires it.

For a system with `dc_ac_ratio = 1.2` (typical ResStock assumption), the annual
clipping loss is typically 1–3%.  Without the cap, HARES overestimates peak AC output.

**Fix required:** if a `<InverterCapacity>` or equivalent extension element exists in
the target HPXML schema, extract and map it to `"inverter_capacity_kw"`.  If the schema
does not provide it, document the gap and default to `None` (no clipping) explicitly in
a comment.

### F-4 (Medium): `Tracking` type not extracted — fixed/1-axis/2-axis distinction lost

**File:** `crates/hares-io/src/hpxml/resolve_der.rs`

HPXML `<Tracking>` can be `fixed`, `1-axis`, `2-axis`. All OCHRE sample files use
`fixed`. HARES's physics model operates on pre-computed tilted-surface irradiance
(POA) and has no tracking model, so not parsing `Tracking` is acceptable for the current
implementation. However, if a fixture contains `1-axis` or `2-axis` tracking, HARES
will silently compute wrong POA irradiance (treating it as fixed).

**Fix required:** parse `Tracking`, emit a structured error or warning when the value is
not `"fixed"`.  Tracking support is out of scope for now, but a silent wrong answer is
worse than an explicit unsupported-feature error.

---

### F-5 (Medium): `Location` field not extracted — roof vs. ground mount distinction lost

**File:** `crates/hares-io/src/hpxml/resolve_der.rs`

HPXML `<Location>` on a `PVSystem` is typically `"roof"` or `"ground"`. Ground-mounted
systems can have a different albedo (ground-reflected component is larger) and free-air
convective cooling. HARES does not extract this field. For the common case of
roof-mounted residential PV the error is negligible; for ground-mounted the reflected
irradiance contribution differs. This is low-severity for residential HPXML but should
be parsed and stored for future use.

### F-6 (Low): System losses fraction validation rejects 1.0 exactly but admits values ≥ 1.0 via non-obvious open interval

**File:** `crates/hares-equipment/src/pv/mod.rs:404`

The validation check is `!(0.0..1.0).contains(&losses)` — the range is half-open
`[0.0, 1.0)` so `losses = 1.0` (100% loss) is rejected.  The error message says
"must be in [0.0, 1.0)" which matches, but the default HPXML value of `0.14` and the
common ResStock range are well within bounds. No correctness defect, but the comment
and error message would be clearer as `[0, 1)`.

---

### F-7 (Low): `system_losses_fraction` is applied to DC power before inverter conversion

**File:** `crates/hares-equipment/src/pv/mod.rs:272`

```rust
dc_power_kw *= 1.0 - self.system_losses_fraction;
let ac_power_kw = (dc_power_kw * self.inverter_efficiency).max(0.0);
```

The PVWatts v8 definition of `system_losses_fraction` covers DC-side losses (wiring,
mismatch, degradation, soiling).  Applying it to DC before the inverter is correct.
Confirm the ordering matches PVWatts Technical Reference (NREL/TP-7A40-80694, §2.5).
This is noted as a correctness assertion to verify rather than a confirmed defect.

### F-8 (Informational): HARES improvements beyond OCHRE

The following are HARES-only features not present in OCHRE. They are correct additions.

| Feature | HARES | OCHRE |
|---|---|---|
| Soiling model (Kimber) | `pv/soiling.rs` — Kimber rainfall-based accumulation | Not implemented |
| SAM LUT bypass | `pv/lut.rs` — 6-D parquet LUT for pre-computed SAM results | SAM called live at init |
| Wind-corrected cell temp | NOCT + wind speed correction (PVWatts v8) | Not implemented (OCHRE uses external SAM) |
| Multi-array per inverter | `KEY_ARRAY_COUNT`, indexed arrays | Single array per PV instance |
| Shading models | `pv/shading.rs` — 5 models incl. horizon profile | Not implemented |
| Inverter priority modes | Watt/Var/CPF | Watt/Var/CPF (matching) |

## Config Field Comparison Table

| HPXML Field | OCHRE Handling | HARES Resolver | HARES Equipment Key | Status |
|---|---|---|---|---|
| `MaxPowerOutput` (W) | Caller-provided `capacity` (kW) | Divides by 1000, emits `"capacity_kw"` | `KEY_CAPACITY_KW` | Correct |
| `ArrayTilt` (deg) | Caller-provided `tilt` | Emits `"tilt_deg"` | `KEY_TILT_DEG` | Correct |
| `ArrayAzimuth` (deg) | Caller-provided `azimuth` (0=south) | Emits `"azimuth_deg"` | `KEY_AZIMUTH_DEG` | Correct — convention matches |
| `ModuleType` | Not used (SAM handles internally) | Emits `"ModuleType"` string as-is | `KEY_MODULE_TYPE` → `from_str` | **Defect F-1**: case mismatch |
| `SystemLossesFraction` | Not used (SAM handles internally) | Emits `"system_losses_fraction"` | `KEY_SYSTEM_LOSSES_FRACTION` | Correct |
| `InverterEfficiency` (fraction) | Caller-provided `inverter_efficiency` | Extracted from `Inverter` node via idref | `KEY_INVERTER_EFFICIENCY` | Correct |
| `InverterCapacity` (kW) | Caller-provided `inverter_capacity` | **Not extracted** | `KEY_INVERTER_CAPACITY_KW_ALT` (dead path) | **Defect F-3** |
| `Tracking` | Not used (SAM handles) | **Not extracted** | No key | **Defect F-4**: no error on non-fixed |
| `Location` (roof/ground) | Not used | **Not extracted** | No key | **Defect F-5** |
| `AttachedToInverter` idref | Not used (single-inverter assumption) | Used to look up `InverterEfficiency` | — | Correct |
| Soiling | Not modeled | `pv/soiling.rs` (Kimber model, opt-in) | `KEY_SOILING_*` | HARES improvement |
| Shading | Not modeled | `pv/shading.rs` (5 models, opt-in) | `KEY_SHADING_*` | HARES improvement |
| NOCT cell temp | Not modeled (SAM does it) | SAM-NOCT + wind correction | `KEY_NOCT_C` | HARES improvement |

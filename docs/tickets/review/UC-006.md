## Background/Context

HPXML specifies Effective Leakage Area (ELA) in square inches. The ASHRAE infiltration
model expects ELA in cm² (or m²). Conversion: 1 in² = 6.4516 cm². An error here
directly scales infiltration rate.

## Investigation Instructions

1. **Read `building.rs` infiltration parsing:**
   - Where is ELA parsed from HPXML? What unit is it stored in?
   - Is `EffectiveLeakageArea` converted from in² to cm² or m²?
   - What about ACH50 and CFM50 — are these converted?

2. **Read `crates/hares-physics/src/infiltration.rs`:**
   - What unit does the infiltration calculation expect for ELA?
   - Is there a mismatch between parse-time unit and use-time unit?

3. **Compare with OCHRE `parse_indoor_infiltration()`.**

4. **Write findings** with the full unit chain: HPXML → parse → store → use.


## Findings

### Q1 — Where is ELA parsed and in what unit is it stored?

`building.rs:444–447` reads `<EffectiveLeakageArea>` (HPXML unit: sq-in) and immediately
multiplies by `6.4516` (1 in² = 6.4516 cm²).  The result is stored in
`BuildingData::infiltration_ela_cm2: Option<f64>` — **unit: cm²**.  This conversion is
correct for the HPXML source unit.

```
HPXML sq-in  ×6.4516  →  cm²  (BuildingData.infiltration_ela_cm2)
```

### Q2 — Where does cm²→m² happen before `ela_infiltration()`?

`ela_infiltration()` (`hares-physics/src/infiltration.rs:136–146`) accepts `ela_m2: f64`
and converts internally: `let ela_cm2 = ela_m2 * M2_TO_CM2` (×10 000).

The `InfiltrationMethod::Ela { ela_m2 }` enum variant (config.rs:64–70) carries the value
**in m²**.

For the **indoor/conditioned zone** (`solver_builder.rs:739–748`), `infiltration_ela_cm2`
(cm²) is **never** passed to `InfiltrationMethod::Ela` directly.  Instead, it is converted
to CFM50 via the Sherman-Grimsrud formula:

```
cfm50 = ela_cm2 × 0.0524 × 50^0.65   [cm², CFM units]
ach50 = (cfm50 × 60) / volume_ft3
```

That ACH50 then drives `aim2_coefficients_from_ach50` → `InfiltrationMethod::AshraeWindStack`.
**No cm²→m² conversion is required on this path** because `ela_cm2` is consumed entirely
in the intermediate scalar formula.

For **attic and foundation zones**, the SLA (m²/m²) × floor_area_m2 path computes
`ela_m2 = sla × floor_area_m2` directly in m² and passes it to `InfiltrationMethod::Ela`.
The cm² field from HPXML (`infiltration_ela_cm2`) is **not used on this path at all**.

Summary of cm²→m² handling:
- Indoor zone: cm² is consumed as a scalar in a CFM50 intermediate; no cm²→m² conversion needed.
- Attic/foundation: SLA path produces m² directly; HPXML ELA field is unused.
- No code path passes `infiltration_ela_cm2` (cm²) directly to `ela_infiltration()` — so no
  unit mismatch exists there.

### Q3 — ACH50 and CFM50 unit handling

`infiltration_ach50` is stored as the raw blower-door ACH value (dimensionless ratio: air
changes per hour at 50 Pa).  No unit conversion is needed at parse time; HPXML stores it
as a plain number under `<AirLeakage>`.

`infiltration_cfm50` (`building.rs:452`) is parsed from `<AirLeakage units="CFM50">` or
`<UnitofMeasure>CFM</UnitofMeasure>` and stored as-is in CFM.

The CFM50→ACH50 conversion in `solver_builder.rs:747`:
```
ach50 = (cfm50 × 60) / volume_ft3
      = (cfm50 × 60) / (volume_m3 × 35.3147)
```
The `× 60` converts minutes→hours; the `× 35.3147` converts m³→ft³.  This is correct.

### Q4 — Are ACH50, CFM50, ELA mutually exclusive?

They are treated as a **priority cascade**, not mutually exclusive:

```
resolved_ach50 = ach50  OR  cfm50_to_ach50(cfm50)  OR  cfm50_to_ach50(ela_to_cfm50(ela_cm2))
```

`building.rs` allows all three fields to be `Some` simultaneously (e.g., a malformed HPXML
could supply both).  The priority is:  **ACH50 wins > CFM50 > ELA**.

OCHRE (`calculate_ashrae_infiltration_params`, envelope.py:490) asserts
`UnitofMeasure in ["ACH"]` and never parses ELA for the indoor zone at all.  HARES is more
permissive but the cascade is deterministic and correctly documented.

### Q5 — Full unit chain: HPXML → parse → store → use

```
HPXML <EffectiveLeakageArea>  [sq-in]
  × 6.4516
  → BuildingData.infiltration_ela_cm2  [cm²]
  × 0.0524 × 50^0.65
  → cfm50  [ft³/min at 50 Pa]
  × 60 / (volume_m3 × 35.3147)
  → ach50  [ACH at 50 Pa]
  → aim2_coefficients_from_ach50()  [m³/s / K^n and m³/s / (m/s)^(2n)]
  → InfiltrationMethod::AshraeWindStack {c_s, c_w, ...}
  → ashrae_wind_stack()  [m³/s]

HPXML <AirLeakage units="CFM50">  [ft³/min at 50 Pa]
  → BuildingData.infiltration_cfm50  [ft³/min]
  × 60 / (volume_m3 × 35.3147)
  → ach50  [ACH at 50 Pa]
  → (same as above)

HPXML <AirLeakage> (ACH)  [ACH at 50 Pa]
  → BuildingData.infiltration_ach50  [ACH at 50 Pa]
  → (same as above from ach50)

Attic/foundation SLA path:
  sla  [m²/m²]  × floor_area_m2  [m²]
  → ela_m2  [m²]
  → InfiltrationMethod::Ela {ela_m2, stack_coeff, wind_coeff}
  → ela_infiltration(ela_m2, ...)  internally: ela_m2 × 10 000 = ela_cm2  [cm²]
  → Q  [m³/s]
```

All dimensions are consistent.

### Q6 — Comparison with OCHRE

OCHRE (`parse_indoor_infiltration`, hpxml.py:502–519) delegates entirely to
`calculate_ashrae_infiltration_params` which **asserts ACH50 is the only accepted unit**
for the indoor zone (envelope.py:490).  OCHRE never reads `<EffectiveLeakageArea>` for the
indoor zone.  The HARES ELA→CFM50→ACH50 cascade is therefore an **extension beyond OCHRE**,
not a replication — it is correct behaviour for HPXML files that only supply ELA.

For attic infiltration (hpxml.py:652–658) OCHRE stores ELA in cm² under the key
`"ELA (cm^2)"` and uses it directly in the ELA flow equation.  HARES mirrors this with
`InfiltrationMethod::Ela { ela_m2 }` and `ela_infiltration()`, which re-derives cm² from m²
internally.  The semantics match.

### Defects found

**DEFECT-1 — `0.0524` constant is unvalidated and physically suspect (MEDIUM)**

`solver_builder.rs:736,744` states:
```
cfm50 = ela_cm2 × 0.0524 × 50^0.65
```
The comment claims this is derived from "ELA defined at 4 Pa with Cd=1.0, scaled to 50 Pa
via power law".  The standard ASHRAE 136 formula in consistent SI + IP units is:

```
Q_4Pa [L/s per cm²] = Cd × sqrt(2 × 4 / ρ) × unit_factor
                    = 1.0 × sqrt(8/1.2) × (1/1000) [m→L, m²→cm²]
                    ≈ 0.002582 [m³/s per m²]  =  0.2582 [L/s per cm²]
```

Scaling to 50 Pa with n=0.65:  `Q_50Pa = Q_4Pa × (50/4)^0.65 = 0.2582 × 3.47 ≈ 0.896 L/s per cm²`

Converting L/s per cm² to CFM per cm²:  `0.896 × 2.1189 ≈ 1.898 CFM per cm²`

But the code computes `0.0524 × 50^0.65 = 0.0524 × 13.87 ≈ 0.727 CFM per cm²` — about
38% lower than the physics-derived value.

No test validates the constant against an independent reference (ResStock airflow.rb,
EnergyPlus, or manual derivation from first principles).  The existing test
`ela_to_cfm50_conversion` (solver_builder.rs:1056–1070) only checks that the result is
in a broad plausible range (50–500 CFM for 100 cm²) — it does not catch a 38% error.

**The derivation of `0.0524` must be verified against ResStock's `calc_airflow_ELA` or
ASHRAE 136 Table 2 before this code is relied upon for ELA-primary HPXML files.**

**DEFECT-2 — No test exercises the ELA→CFM50→ACH50 path with a known end-to-end value (LOW)**

The `ela_to_cfm50_conversion` test only checks monotonicity and a wide range gate.  There
is no test that, given a known HPXML with `<EffectiveLeakageArea>` in sq-in, verifies that
the resulting `InfiltrationMethod::AshraeWindStack` coefficients match expected values.
This means the ELA path could silently regress.

**DEFECT-3 — `infiltration_cfm50` parse path may also accept raw ACH50 value (LOW / pre-existing)**

`parse_air_leakage_cfm50` (building.rs:1742–1764) checks for `units="CFM50"` or
`UnitofMeasure="CFM"`, but the original `infiltration_ach50` parse path reads
`<AirLeakage>` without a unit check.  If an HPXML file has `UnitofMeasure="ACH"` alongside
`units="CFM50"` on the same element, both fields could be populated with the same numeric
value.  The priority cascade in solver_builder means ACH50 wins, so there is no incorrect
computation, but it could mask a mal-formed file silently.

### Unit chain correctness verdict

The in²→cm² conversion at `building.rs:447` is **correct**.  The cm²→m² path for
`ela_infiltration()` is never directly exercised from HPXML — that function is only called
from the attic/foundation SLA path where `ela_m2` is produced independently.  No unit
mismatch is present in the executed paths.  The only material concern is DEFECT-1: the
`0.0524` constant has no verified derivation.

## Recommended Tests

1. **`ela_in2_to_cm2_roundtrip`** (`hares-io/tests/`)
   Parse a minimal HPXML with `<EffectiveLeakageArea>10</EffectiveLeakageArea>` (10 sq-in).
   Assert `building.infiltration_ela_cm2 == Some(64.516)` (±0.001).

2. **`ela_to_cfm50_physics_reference`** (`hares-core/src/dwelling/solver_builder.rs`)
   Using a known reference value from ResStock `calc_airflow_ELA` (or ASHRAE 136 Table 2):
   Given `ela_cm2 = 100.0`, assert `cfm50` equals the reference value ±2%.
   This test must fail until DEFECT-1 is resolved or the constant is confirmed correct.

3. **`ela_primary_hpxml_end_to_end`** (`hares-core/tests/`)
   Build a `BuildingData` with only `infiltration_ela_cm2 = Some(645.16)` (100 sq-in)
   and known volume.  Call `build_solver_config` and assert `InfiltrationMethod` is
   `AshraeWindStack` with `c_s` and `c_w` matching values produced by the manually computed
   ACH50 from the same ELA.

4. **`ela_ach50_priority_cascade_integration`** (`hares-core/tests/`)
   Provide all three fields simultaneously.  Assert final `c_s`, `c_w` match the ACH50-only
   path (not the ELA or CFM50 paths).

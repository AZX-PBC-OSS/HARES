## Background/Context

Battery config: capacity, max charge/discharge power, round-trip efficiency,
SOC limits, chemistry-specific OCV curves. HARES has a richer battery model
(degradation, thermal, OCV tables) — document improvements.

### HARES improvements over OCHRE

- Asymmetric charge/discharge efficiency (OCHRE forces a single pack efficiency).
- Configurable per-chemistry OCV and U_neg tables (LFP, NMC).
- Piecewise-linear capacity derate model as an alternative to Arrhenius.
- Cell heater model with configurable threshold and power (Franklin/Tesla cold-climate behaviour).
- Configurable min/full-power temperature derating for both charge and discharge.
- Charging blocked below `min_charge_temp_c` (Li-ion plating safety; OCHRE ignores this).
- `import_limit` / `export_limit` default to `None` (unlimited) rather than OCHRE's 0-kW default that silently blocks all self-consumption unless explicitly overridden.
- Demand-response power fraction scaling.
- Catalog of real-world products (TeslaPw3, EnphaseIq5p, etc.) with manufacturer-verified specs.

### F-1 — CRITICAL: Double sqrt on RTE from HPXML (correctness bug)

**File**: `crates/hares-io/src/hpxml/resolve_der.rs:92-95`

```
if let Some(rte) = child_f64(battery, "RoundTripEfficiency") {
    params.insert("inverter_efficiency".to_string(), json!(rte.sqrt()));
}
```

**File**: `crates/hares-equipment/src/battery/mod.rs:755-759`

```rust
let sym_eta = config
    .get_f64(KEY_INVERTER_EFFICIENCY)
    .unwrap_or(DEFAULT_INVERTER_EFFICIENCY)
    .clamp(f64::EPSILON, 1.0);
let sym_split = sym_eta.sqrt();
```

`resolve_der.rs` stores `rte.sqrt()` under the key `inverter_efficiency`. `Battery::init` then reads `inverter_efficiency` and applies `sqrt()` a second time. The effective one-way efficiency becomes `rte^(0.25)` instead of `rte^(0.5)`. For a typical HPXML value of `RoundTripEfficiency = 0.90`, the actual round-trip efficiency applied by the engine is `0.90^(0.5)^2 = 0.90^0.5 ≈ 0.949` instead of 0.90 — an error of ~5.5 pp.

The fix in `resolve_der.rs` is to store the raw RTE (not the sqrt) under `inverter_efficiency`, consistent with what `Battery::init` expects. The comment in `resolve_der.rs` at lines 93-94 even describes the sqrt-split correctly but then applies it prematurely before the battery reads and re-applies it.

Alternatively, `resolve_der.rs` should store the RTE directly as `charge_efficiency` and `discharge_efficiency` (after the single sqrt split), bypassing the `inverter_efficiency` path entirely, which is the same approach the catalog's `BatterySpec::to_config()` uses correctly.

### F-2 — MEDIUM: Default `cell_ua_w_per_k` does not match OCHRE thermal_r default

**File**: `crates/hares-equipment/src/battery/mod.rs:123`

OCHRE `default_parameters.csv`: `thermal_r = 0.5 K/W` → `UA = 1/0.5 = 2.0 W/K`
HARES `DEFAULT_CELL_UA_W_PER_K = 5.0 W/K` → implied R = 0.2 K/W

The HARES default dissipates heat 2.5× faster than OCHRE's default, leading to lower cell temperatures in thermal simulations, which affects both the capacity derate model and the degradation accumulator. This diverges from the OCHRE reference baseline without documentation. The value should be set to `2.0 W/K` or the comment should clearly state the chosen reference and rationale.

### F-3 — MEDIUM: Pack topology (n_series) derived from incompatible pack voltage target

**File**: `crates/hares-equipment/src/battery/mod.rs:665-666`

When `ah_cell` and `v_cell` are provided in config, HARES derives `n_series` using a hardcoded `target_pack_v = 350.0 V`. OCHRE uses `initial_voltage = 50.4 V` (a low-voltage 14S LFP/NMC pack in SAM's Li-NMC dataset). The two approaches produce completely different topologies:

- OCHRE default: `n_series ≈ 14` (50.4 V / 3.6 V), `n_parallel ≈ 270` (for 10 kWh)
- HARES derived: `n_series ≈ 97` (350 V / 3.6 V), `n_parallel ≈ 40` (for 13.5 kWh)

Pack resistance = `r_cell × n_series / n_parallel`. For OCHRE defaults (r_cell=0.002 Ω): `R_pack = 0.002 × 14 / 270 ≈ 0.000104 Ω`. For HARES derived values (r_cell=0.005 Ω): `R_pack = 0.005 × 97 / 40 ≈ 0.012 Ω`. This is over 100× higher pack resistance, producing wildly different ohmic losses and thus different SOC trajectories under load.

For parity with OCHRE's reference model, when `ah_cell`/`v_cell` are provided without explicit `n_series`, use `initial_voltage = 50.4 V` as the pack voltage reference. The HARES struct default of `n_series=96, n_parallel=1` is also inconsistent with any realistic pack (single-cell parallel strings are not used in residential batteries), and should be cross-checked against the chemistry OCV tables and internal resistance values to ensure the ohmic model produces sensible terminal voltages.

### F-4 — LOW: `soc_min`/`soc_max` never populated from HPXML

**File**: `crates/hares-io/src/hpxml/resolve_der.rs:83-103`

The HPXML `Battery` element does not expose `MinSoC` or `MaxSoC` fields (they are not part of the HPXML 4.0 Battery schema). The HARES parser never populates `min_soc` or `max_soc` from HPXML. Batteries parsed from HPXML always use the struct defaults (0.15/0.95). This is expected behavior, not a bug, but it should be documented in the parser and in any user-facing HPXML documentation so users know to set these via external config or the Python API.

---

### F-5 — LOW: `import_limit`/`export_limit` default semantic mismatch with OCHRE

OCHRE `Generator.__init__`: `import_limit = self.parameters.get("import_limit", 0)` and `export_limit = ... get("export_limit", 0)`. With both at 0, OCHRE's self-consumption controller clamps `desired_power = max(min(net_power, 0), -0) = 0`, so all charging is blocked by default in self-consumption mode unless the user explicitly sets a non-zero import limit.

HARES defaults both to `None` (unlimited). This means self-consumption mode in HARES behaves fundamentally differently from OCHRE out of the box: HARES allows full charge/discharge in self-consumption mode, OCHRE allows none. The fix is not to copy OCHRE's broken default, but the divergence must be documented so parity test authors know what to expect.

---

### F-6 — LOW: `r_cell` default diverges from OCHRE

OCHRE `default_parameters.csv`: `r_cell = 0.002 Ω`. HARES `DEFAULT_CELL_RESISTANCE_OHM = 0.005 Ω`. The HARES default produces 2.5× higher cell resistance, affecting ohmic losses and the advanced efficiency model. The comment in `mod.rs:91` ("Typical 18650/21700 Li-NMC cell internal resistance at 25 C, mid-SOC") references a different cell format than the SAM Li-NMC dataset OCHRE uses. Either align the default with OCHRE's value or add a note explaining the intentional divergence.

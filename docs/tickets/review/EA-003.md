## Background/Context

Hot water delivery loses energy through: pipe heat loss (standpipe/distribution),
drain water heat (hot water going down the drain), and recirculation loop losses.
OCHRE accounts for these via distribution system efficiency factors. If HARES omits
them, water heater energy consumption is underestimated.

## Investigation Instructions

1. **Read OCHRE hot water distribution handling:**
   - How does OCHRE model pipe losses?
   - Is there a distribution system efficiency factor?
   - How is recirculation handled (if present in HPXML)?
   - How is drain water heat loss calculated?

2. **Read HARES `tank.rs`:**
   - How are draws modeled? Is outlet temperature mixed with cold inlet?
   - Are pipe losses accounted for between tank and fixture?
   - Is there a distribution efficiency factor?

3. **Read `draw_profile.rs`:**
   - How are draw profiles generated?
   - Does the profile include pipe loss adjustments?

4. **Read `resolve_water_heater.rs`:**
   - Is `PipingLength` parsed from HPXML?
   - Is distribution system efficiency calculated?

5. **Document** any missing loss mechanisms and their energy impact.

## Findings

### How OCHRE models hot water distribution losses

OCHRE models distribution losses entirely at the **draw-profile normalization stage**
(parse time), not at simulation runtime. The mechanism is:

1. `vendors/OCHRE/ochre/utils/hpxml.py:1204-1238` — When parsing HPXML,
   `parse_water_heater()` computes `distribution_gal_per_day` from the
   HPXML `<HotWaterDistribution>` block using the ANSI/RESNET 301-2014 Addendum
   A-2015 formula. The result is added to `fixture_gal_per_day` and stored as
   `"Average Water Draw (L/day)"`.

2. The per-step draw schedule is then a fractional profile scaled to that daily
   average. The distribution losses inflate the daily target volume, so the water
   heater processes more draws — the thermal energy required to heat the extra
   cold-water slug is the surrogate for pipe waste water loss.

3. No separate pipe-to-ambient conduction loss path exists in OCHRE for the
   distribution piping itself. There is no `h_loss_pipe` term, no recirculation
   pump heat injection, and no DWHR offset at simulation runtime. All of these
   are folded into the inflated draw volume.

**OCHRE recirculation handling (hpxml.py:1220-1223):**
- `distribution_factor = 1.0` if pipe R-value >= 3, else `1.11`
- `p_ratio = BranchPipingLoopLength / 10` (default 10 ft)
- `wd_eff = 0.1` (90% of structured waste water is credited back — approximating
  that a recirculation loop keeps the branch pipe hot, so less "purge" water is
  wasted per draw event)

**OCHRE standard distribution (hpxml.py:1212-1219):**
- `distribution_factor = 0.9` if pipe R-value >= 3, else `1.0`
- `p_ratio = PipingLength / default_length` (default length derived from floor
  area, floors, and basement type)
- `wd_eff = 1.0`

**OCHRE distribution waste formula (hpxml.py:1229-1234):**
```
ref_w_gpd = 9.8 * n_beds_adj^0.43
o_frac     = 0.25   # on-demand (cold-drain) fraction
o_cd_eff   = 0.0    # cold-drain recovery efficiency
o_w_gpd    = ref_w_gpd * o_frac * (1 - o_cd_eff)
s_w_gpd    = (ref_w_gpd - ref_w_gpd * o_frac) * p_ratio * distribution_factor
mw_gpd     = fixture_eff * (o_w_gpd + s_w_gpd * wd_eff)
```
`mw_gpd * fixture_multiplier` is the daily distribution volume added on top of
the fixture draw.

OCHRE does **not** model:
- Pipe standby heat loss to ambient (no RC model for piping)
- DWHR (drain water heat recovery) at simulation time — `o_cd_eff` is hardcoded
  to `0.0` and there is no runtime hook for it
- Recirculation pump electrical energy — no pump power term anywhere in
  `WaterHeater.py` or `Water.py`

### How HARES models hot water distribution losses

**Draw profile normalization (`crates/hares-io/src/draw_profile.rs`):**

HARES faithfully reimplements the full OCHRE ANSI/RESNET 301 draw-volume
inflation pipeline:

- `distribution_daily_hot_water_l` (draw_profile.rs:149-198): matches
  OCHRE exactly — same `o_frac=0.25`, `o_cd_eff=0.0`, same `distribution_factor`
  and `p_ratio` branches for Standard vs Recirculation, same `wd_eff=0.1`
  for Recirculation.

- `combined_daily_hot_water_l` (draw_profile.rs:213-226): sums fixture and
  distribution volumes identically to OCHRE's `fixture_gal_per_day +
  distribution_gal_per_day`.

- `normalize_draw_profile` (draw_profile.rs:46-70): scales the fractional
  schedule to match the daily target, identical to OCHRE's approach.

**HPXML parsing (`crates/hares-io/src/hpxml/resolve_water_heater.rs`):**

- `parse_distribution_system` (resolve_water_heater.rs:227-261): correctly
  parses `<Standard>/<PipingLength>` (converting ft to m) and derives the
  default piping length from conditioned floor area, floors, and basement type
  following the OCHRE formula (resolve_water_heater.rs:263-342).

- `parse_avg_water_draw_l_per_day` (resolve_water_heater.rs:161-220):
  resolves n_bedrooms, occupant-adjusted bedroom count, fixture efficiency,
  usage multiplier, and calls `combined_daily_hot_water_l`.

**Tank simulation (`crates/hares-equipment/src/water_heater/tank.rs`):**

The tank model (`apply_conduction_and_standby` and `apply_draw`) correctly
handles:
- Tank jacket (skin) losses to ambient via per-node UA (tank.rs:542-578)
- Cold mains water displacement during draws (tank.rs:585+)
- Tempered-draw TMV mixing valve logic (tank.rs:345+)

No pipe distribution losses are modeled at simulation runtime — this is correct
parity with OCHRE, which also does not model them at runtime.

### Correctness gap found: `ansi_resnet_daily_hot_water_l` simplified function

**File:** `crates/hares-io/src/draw_profile.rs:242-260`

The simplified public function `ansi_resnet_daily_hot_water_l` has a different
formulation from `distribution_daily_hot_water_l`. Specifically:

```rust
// draw_profile.rs:256-257
let s_w_gpd = (ref_w_gpd - ref_w_gpd * O_FRAC) * distribution_loss_factor;
let distribution_l = gal_to_l(fixture_efficiency * (o_w_gpd + s_w_gpd));
```

Compared to the full function (draw_profile.rs:195-196):
```rust
let s_w_gpd = (ref_w_gpd - ref_w_gpd * O_FRAC) * p_ratio * distribution_factor;
let mw_gpd = fixture_efficiency.multiplier() * (o_w_gpd + s_w_gpd * wd_eff);
```

The simplified version collapses `p_ratio * distribution_factor * wd_eff` into a
single `distribution_loss_factor` scalar — the `wd_eff` reduction (0.1x for
recirculation) is not separately expressible. A caller passing
`distribution_loss_factor = 1.11` (recirculation with uninsulated pipes) gets
100% of structured waste volume, whereas the full function would apply `wd_eff=0.1`
to reduce that to 11% of structured waste. This function is currently only called
in unit tests within `draw_profile.rs` and exported from `hares-io::lib`; if it
reaches callers that bypass `combined_daily_hot_water_l`, the daily draw volume
would be significantly overestimated for recirculation buildings.

Severity: **Medium** — currently test-only usage, but the exported public API
misleads future callers. The `distribution_loss_factor` parameter does not
correspond to any single ANSI/RESNET coefficient; the semantics are ambiguous
relative to the full `combined_daily_hot_water_l` path.

Recommendation: Deprecate or remove `ansi_resnet_daily_hot_water_l`. All callers
should use `combined_daily_hot_water_l` with an explicit `DistributionSystem`.

### Missing: recirculation pump electrical energy (improvement opportunity)

OCHRE does not model recirculation pump power. HPXML 3.x `<RecirculationPump>`
carries `<PumpPower>` (W) and `<ControlType>` (timer, temperature, demand, etc.).
HARES also does not model this. For all-always-on recirculation pumps, a typical
25–50 W pump running continuously adds ~220–440 kWh/yr of electrical load, which
is material for DR-capable buildings. This is a gap relative to real-world physics
but is not a regression versus OCHRE.

### Missing: pipe standby conduction to conditioned space (improvement opportunity)

Neither OCHRE nor HARES explicitly model the heat lost from hot distribution pipes
to the conditioned space (or unconditioned spaces). ASHRAE 140/EnergyPlus models
this separately. The current approach of inflating draw volume is a simplified
proxy. For buildings with long uninsulated pipe runs this can underestimate both
peak heating load and water heater cycling. This is a known OCHRE limitation.

### No issues found in core tank draw model

`apply_draw` and `apply_conduction_and_standby` in `tank.rs` are correct. The
stratified displacement model, mains water enthalpy accounting, TMV mixing, and
inversion mixing all match OCHRE's `Water.py` logic. The `outlet_temp_c` pre-draw
snapshot for the TMV estimate matches OCHRE Water.py:306.

to `distribution_gal_per_day` (via `usage_multiplier` argument), matching OCHRE

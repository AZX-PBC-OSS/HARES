## Background/Context

HPXML water heater fields: `TankVolume` (gallons), `HeatingCapacity` (BTU/hr),
`EnergyFactor` or `UniformEnergyFactor` (dimensionless), `HotWaterTemperature` (°F),
`TankHeight` (unknown unit). Each must be correctly converted to SI.

## Investigation Instructions

1. **Read `resolve_water_heater.rs`:**
   - `TankVolume` — gallons → liters? (1 gal = 3.78541 L)
   - Volume correction factor (0.9 electric, 0.95 gas) — is this applied?
   - `HeatingCapacity` — BTU/hr → W?
   - `HotWaterTemperature` — °F → °C?
   - `TankHeight` — feet → meters? What's the default?
   - `JacketRValue` — imperial → SI?

2. **Read `water_heater_ua.rs`:**
   - How is EF/UEF converted to tank UA?
   - What formula is used? Does it match DOE 10 CFR 430 standby loss test?
   - Compare with OCHRE's UA derivation.

3. **Check HPWH-specific conversions:**
   - HPWH COP from UEF — HARES uses `1.174536058 * UEF` (linear). Is this
     the same formula OCHRE uses? At what UEF range is it valid?

4. **Write findings** with per-field conversion table and formula comparison.


## Findings

### F-001 — SEVERITY: MEDIUM — Volume conversion: gallons → m³ but OCHRE stores liters

`resolve_water_heater.rs:45-46`: `tank_volume_m3` is converted directly to m³ and stored as `tank_volume_m3`.
OCHRE `hpxml.py:1048` stores `volume` in **liters** (`convert(volume_gal, "gallon", "L")`).
The downstream equipment code (`resistance.rs:259`, `gas.rs:259`, `heat_pump_wh.rs:350`) all read `tank_volume_m3` — so the HARES end-to-end chain is self-consistent in m³. This is not a bug per se, but the `TankVolume (L)` key name in OCHRE's output dictionary conflicts conceptually and must not be confused when comparing parity outputs.

Volume correction factors: `resolve_water_heater.rs:40-44` applies 0.9 (electric) / 0.95 (gas) **before** calling `volume_gal_to_m3`, matching OCHRE `hpxml.py:1044-1047` exactly.

For HPWH UA, `water_heater_ua.rs:99` re-applies the 0.9 factor to `tank_volume_rated_gal` (the raw gallon value) to select the volume bin. This is correct and matches OCHRE `hpxml.py:1070` which uses the already-corrected `volume_gal` for bin selection.

**Discrepancy**: `ua_for_electric_storage` (`water_heater_ua.rs:122`) computes `_volume_actual_gal = volume_gal * 0.9` but then does not use it in the UA formula. OCHRE's electric storage UA formula (`hpxml.py:1118`) also does not use volume in the formula — only `q_load`, `ef`, `T_SETPOINT`, `T_ENV`. The unused variable is dead code and misleading; it should be removed.

### F-002 — SEVERITY: LOW — HeatingCapacity conversion correct

`resolve_water_heater.rs:48`: `heating_capacity_btu_hr.map(conv::power_btu_h_to_w)` — uses the `uom`-backed constant (0.29307107 W per BTU/hr) at `units.rs:96-99`. Matches OCHRE `hpxml.py:1165`.

### F-003 — SEVERITY: LOW — HotWaterTemperature conversion correct

`xml_helpers.rs:38-55`: `child_temperature_c` reads `HotWaterTemperature` (or falls back to `Temperature`), defaults units to `"F"`, and applies `conv::temperature_f_to_c` which uses `uom` degree-Fahrenheit→Celsius. OCHRE `hpxml.py:1028` uses `convert(value, "degF", "degC")`. Both correct.

Default setpoint when the field is absent: `mod.rs:14` → `DEFAULT_SETPOINT_C = 51.666_666_7` (= 125°F). OCHRE `hpxml.py:1028` defaults to 125°F. Matches.

### F-004 — SEVERITY: LOW — TankHeight conversion correct; default matches

`resolve_water_heater.rs:49-51`: When `TankHeight` is absent, falls back to `conv::length_ft_to_m(4.0)` = 1.2192 m. OCHRE `hpxml.py:1036`: `convert(water_heater.get("TankHeight", 4), "ft", "m")`. Both default to 4 ft. Correct.

### F-005 — SEVERITY: MEDIUM — JacketRValue: HARES and OCHRE apply different correction formulas

**OCHRE** (`hpxml.py:1132-1138`): When `JacketRValue` is non-zero OCHRE computes a physics-based correction involving:
- Pre-jacket U-value of the existing insulation shell + air films: `u_pre_skin = 1/(jacket_thickness * 5 + 1/1.3 + 1/52.8)`
- Jacket thickness: 1 inch if electric & EF < 0.7, else 2 inches
- Lateral area in ft² (computed from volume in liters and height)
- Reduction: `ua -= tank_jacket_r / (1/u_pre_skin + tank_jacket_r) * u_pre_skin * a_side`

This formula accounts for the combined thermal resistance of the existing foam shell and the added jacket, and requires the final derived UA from EF/UEF before applying the reduction.

**HARES** (`mod.rs:136-151`): `apply_jacket_r_value` uses a much simpler formula:
`r_total = 1/ua_base + jacket_r / lateral_area_m2` → `1/r_total`

This treats `jacket_r` as if it's the total R of a parallel-path insulation layer over the full lateral surface, which is a different physical model from OCHRE. In OCHRE the jacket adds an R in **series** with the pre-existing shell R on the cylindrical area, whereas HARES treats the jacket R as a fraction of a simpler total. Additionally HARES applies the correction at **equipment init time** using `tank_volume_m3` → derived `diameter_m`, while OCHRE applies it in the parse phase on the UA computed from EF/UEF.

**Impact**: For any dwelling with a non-zero `JacketRValue`, the effective tank UA (and hence standby losses) will differ between HARES and OCHRE.

The JacketRValue correction also does not include OCHRE's jacket_thickness branch (EF < 0.7 → 1 inch, else 2 inches), which influences `u_pre_skin` and therefore the magnitude of the correction.

### F-006 — SEVERITY: LOW — EF→UA and UEF→UA formulas match OCHRE

**Electric storage EF path** (`water_heater_ua.rs:128`):
`ua = q_load * (1/ef - 1) / ((T_SETPOINT_EF_F - T_ENV_F) * 24.0)`
Matches OCHRE `hpxml.py:1118`.

**Electric storage UEF path** (`water_heater_ua.rs:134-135`):
`ua = q_load * (1/uef - 1) / ((24*(t-T_ENV)) * (0.8 + 0.2*((t_in-T_ENV)/(t-T_ENV))))`
Matches OCHRE `hpxml.py:1120-1124`.

**RESNET EF←UEF regression** (`water_heater_ua.rs:137`): `ef_equiv = 2.4029*uef - 1.2844`.
OCHRE `hpxml.py:1125`: `energy_factor = 2.4029 * uniform_energy_factor - 1.2844`. Exact match.

**Gas storage EF path** (`water_heater_ua.rs:163-166`):
Matches OCHRE `hpxml.py:1102-1107`. EF path uses `T_SETPOINT_EF_F = 135°F`.

**Gas storage UEF path** (`water_heater_ua.rs:171-175`):
Matches OCHRE `hpxml.py:1109-1115`. UEF path uses `T_SETPOINT_UEF_F = 125°F`.
Gas UEF→EF regression: `0.9066*uef + 0.0711`. OCHRE: `0.9066 * uniform_energy_factor + 0.0711`. Exact match.

**HPWH volume bin** (`water_heater_ua.rs:101-107`):
Bins at 3.6 / 4.0 / 4.7 Btu/hr·°F for ≤58 / ≤73 / >73 gal actual. Matches OCHRE `hpxml.py:1070-1075`. Correct.

**`T_IN_EF_F` is shared between EF and UEF paths in HARES** (`water_heater_ua.rs:220`): `let t_in = T_IN_EF_F;` with comment "inlet is the same for both test procedures." Both 10 CFR 430 EF and UEF procedures use 58°F for the inlet, so this is correct.

### F-007 — SEVERITY: LOW — HPWH COP formula: `1.174536058 * UEF` is directly from OCHRE/ResStock

`resolve_water_heater.rs:113`: `json!(1.174_536_058 * uef)`
OCHRE `hpxml.py:1187`: `wh["HPWH COP (-)"] = 1.174536058 * uniform_energy_factor`

Both derive from a ResStock simulation of the UEF test procedure at varying COPs — the constant is an empirical fit (linear through origin). OCHRE does not document the derivation further than "based on simulation." The coefficient is valid for typical residential HPWH UEF ranges (~2.0–4.5); at UEF=4.9 OCHRE hard-codes a different constant (COP=4.2) as a special case for 120V units. **HARES does not implement this special case.** If a 120V HPWH with UEF=4.9 is parsed, HARES will compute COP = 1.174536058 × 4.9 = 5.755, which diverges from OCHRE's 4.2.

OCHRE also includes a fallback when `uniform_energy_factor` is None: derive UEF from EF via `(0.60522 + energy_factor) / 1.2101`. `resolve_water_heater.rs` only enters the HPWH COP block when `uniform_energy_factor` is `Some`, and silently emits no `cop` key otherwise. If the equipment model has no fallback default COP, a HPWH with only EF (no UEF) will silently lose COP derivation.

### F-008 — SEVERITY: LOW — Tempering valve setpoint hardcoded correctly

`resolve_water_heater.rs:119-122`: HPWH tempering valve at 51.67°C (125°F) guarded by `storage_setpoint_c > 51.67`. OCHRE `hpxml.py:1157`: `"Tempering Valve Setpoint (C)": t_set` (storage setpoint). OCHRE always sets the tempering valve equal to the storage setpoint; HARES fixes it at 51.67°C unless the storage setpoint is already at or below that. This is a minor divergence — for standard 60°C (140°F) storage it produces the same 125°F delivery, but for non-standard setpoints HARES and OCHRE will behave differently.

### F-009 — SEVERITY: LOW — FirstHourRating correctly converted (gallons → m³)

`resolve_water_heater.rs:47`: `first_hour_rating_m3 = first_hour_rating_gal.map(conv::volume_gal_to_m3)`. The FHR is passed in raw gallons to `UaInputs.first_hour_rating_gal` for the UEF bin selection (which expects gallons), and is separately stored in m³ as `first_hour_rating_m3` for downstream equipment use. No double-conversion issue.

### F-010 — SEVERITY: LOW — RecoveryEfficiency passed through as dimensionless ratio; no conversion needed

`water_heater_ua.rs:155`: `re = inputs.recovery_efficiency.unwrap_or(0.78)`. OCHRE default is also 0.78 (`hpxml.py:1102` uses the HPXML-supplied value; no explicit default shown but OCHRE README confirms 0.78). RecoveryEfficiency in HPXML is a dimensionless fraction (0–1). No unit conversion required or applied. Correct.

### F-011 — SEVERITY: LOW — Instantaneous performance_adjustment default diverges from OCHRE

`resolve_water_heater.rs:139`: `child_f64(wh, "PerformanceAdjustment").unwrap_or(0.92)` — single default regardless of whether EF or UEF was supplied.

OCHRE `hpxml.py:1057-1061`:
- When UEF is used (EF is None): default is **0.94**
- When EF is used: default is **0.92**

HARES always uses 0.92. For tankless units parsed with UEF only, the effective efficiency will be 0.92/0.94 = ~2.1% lower than OCHRE's.

### F-012 — SEVERITY: LOW — Dead code: `_volume_actual_gal` in electric storage UA path

`water_heater_ua.rs:122`: `let _volume_actual_gal = volume_gal * 0.9;` is prefixed with `_` indicating it is intentionally unused. This is dead code — volume is not used in the electric storage UA formula. It should be removed to avoid confusion.

## Recommended Tests

### T-001 — JacketRValue correction parity test

Create a test in `crates/hares-io/src/hpxml/water_heater_ua.rs` or `resolve_water_heater.rs` that computes UA for a 50-gal electric water heater with EF=0.92 and JacketRValue=10 hr·ft²·°F/BTU, then verifies the resulting `ua_w_per_k` matches the OCHRE formula within 0.05 W/K. Currently HARES uses a simplified resistance-network formula; this test would expose the divergence (expected to fail until F-005 is resolved).

### T-002 — HPWH COP with only EnergyFactor (no UEF) does not silently drop COP

Parse a synthetic HPXML `<WaterHeatingSystem>` with `<WaterHeaterType>heat pump water heater</WaterHeaterType>` and `<EnergyFactor>3.4</EnergyFactor>` only (no `<UniformEnergyFactor>`). Assert that the produced params map contains a non-zero `cop` key derived via the EF→UEF inverse regression `(0.60522 + ef) / 1.2101`, or assert that `ua_for_hpwh` returns an error requiring UEF. Currently neither path is taken — the COP key will be absent from params.

### T-003 — Instantaneous UEF-only default performance_adjustment = 0.94

Parse a tankless water heater HPXML node with `<UniformEnergyFactor>0.87</UniformEnergyFactor>` and no `<EnergyFactor>` or `<PerformanceAdjustment>`. Assert that the emitted `performance_adjustment` param is 0.94, not 0.92. Covers F-011.

### T-004 — Electric 50-gal EF=0.92 end-to-end volume in m³

After full HPXML parse, assert `tank_volume_m3 ≈ 50 × 0.9 × 0.003785411784 = 0.17034`. Ensures the volume correction and unit conversion compose correctly without touching the UA formula.

### T-005 — HPWH UEF=4.9 special-case COP

If HARES chooses to implement the 120V HPWH special case: parse UEF=4.9 HPWH and assert `cop = 4.2`, `heating_capacity_w ≈ 1499.4 W`. If the special case is intentionally not implemented, document it as a known parity gap and assert `cop ≈ 1.174536058 * 4.9` so the behavior is explicit.

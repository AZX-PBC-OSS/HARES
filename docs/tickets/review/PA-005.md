## Background/Context

Rust `SimulationConfig` has `OutputFormat` enum with `Csv`, `Parquet`, `Arrow` variants.
Python only sees `output_to_parquet: bool`, meaning `Arrow` format cannot be selected.

## Investigation Instructions

1. Read `py_config.rs` — how is `output_format` mapped?
2. Assess: do users need Arrow output? For streaming? For IPC?
3. Recommend: expose as string enum? Or keep simplified?


## Recommended Tests

1. `test_simulation_config_output_to_parquet_true` — construct `SimulationConfig(output_to_parquet=True)`, call `to_sim_config()`, assert `output_format == OutputFormat::Parquet`.
2. `test_simulation_config_output_to_parquet_false` — same with `False`, assert `OutputFormat::Csv`.
3. `test_from_sim_config_round_trips_parquet` — build a `SimulationConfig` with `OutputFormat::Parquet`, call `from_sim_config`, assert `output_to_parquet == True`.
4. `test_from_sim_config_round_trips_csv` — same for `OutputFormat::Csv`.

These should live in `crates/hares-python/src/py_config.rs` (cfg(test) block) using `PyResult`-unwrapping test helpers, consistent with existing test style.

## Findings

### F1 — Premise incorrect: `OutputFormat::Arrow` does not exist (Severity: Info)

File: `crates/hares-io/src/config.rs:16`

The ticket background states "Rust `SimulationConfig` has `OutputFormat` enum with `Csv`, `Parquet`, `Arrow` variants." This is wrong. The actual enum has exactly two variants:

```rust
pub enum OutputFormat {
    Csv,
    Parquet,
}
```

There is no `Arrow` variant anywhere in the codebase. "Arrow" appears only as the underlying in-memory columnar format used by both the Parquet writer (`ArrowWriter`) and the batch flush pipeline — it is an internal implementation detail, not an exposed output format.

**The gap described in the ticket title does not exist as stated.**

### F2 — Real gap: Python API collapses the format choice to a bool (Severity: Medium)

File: `crates/hares-python/src/py_config.rs:77`, lines 327–330, 350

`PySimulationConfig` stores `output_to_parquet: bool` instead of mirroring `OutputFormat`. The conversion in `to_sim_config()` is:

```rust
output_format: if self.output_to_parquet {
    OutputFormat::Parquet
} else {
    OutputFormat::Csv
},
```

And `from_sim_config()` maps:

```rust
output_to_parquet: config.output_format == OutputFormat::Parquet,
```

This is technically correct for the two variants that currently exist, but it creates a structural problem: if a third format is ever added (e.g. Arrow IPC file, Feather, JSON), the Python API cannot represent it without a breaking change. The bool is the wrong abstraction — a string enum is more extensible and more legible (`"parquet"` vs `True`).

### F3 — `_hares.pyi` stub matches the bool API (Severity: Info)

File: `python/ochre_next/_hares.pyi:1342,1367`

The stub correctly declares `output_to_parquet: bool | None` as a constructor kwarg and `output_to_parquet: bool` as a getter. No mismatch with the implementation. No fix required for the current state.

### F4 — `__repr__` and `from_sim_config` are consistent (Severity: Info)

File: `crates/hares-python/src/py_config.rs:301`, `349–351`

Both correctly reference `output_to_parquet`. No silent data loss occurs for the two current variants.

## Review Notes

The `Arrow` variant premise is false — it was never implemented. The actual issue is weaker: the Python surface uses a boolean where a string enum would be safer for future extensibility and more readable. No existing functionality is broken.

If Arrow IPC output is planned (e.g. for in-process HELICS data transfer without writing to disk), that would require:
1. Adding `OutputFormat::ArrowIpc` to the Rust enum.
2. Replacing `output_to_parquet: bool` in `PySimulationConfig` with `output_format: str` (validated to `"csv" | "parquet" | "arrow_ipc"`).
3. Updating `to_sim_config()`, `from_sim_config()`, `__repr__`, and the `.pyi` stub.

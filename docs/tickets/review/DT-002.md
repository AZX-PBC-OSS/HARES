## Background/Context

`EventBasedLoad` models appliances like clothes washers, dryers, and dishwashers that
fire discrete events based on a stochastic or deterministic schedule. The event timing
must be evaluated in local wall-clock time so that events cluster at realistic times of
day (e.g., laundry mid-morning, dishwasher after dinner).

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### How HARES times events

**Deterministic (kW-series) path** (`event_load.rs:508–535`)

Events are pre-extracted at `init()` from the `KEY_EVENT_POWER_KW_SERIES` array as
`ExtractedEvent { start_step, end_step, power_kw }`. During each `step()` call:

```rust
let step = self.current_step % self.schedule_len.max(1);
// cursor advance + in-event check purely by integer step position
self.current_step += 1;
```

The event boundary comparison is **integer step counter vs. integer step range** — no
wall-clock time is consulted in the hot path. The schedule position is implicitly
anchored by `schedule_start_offset` (computed once in
`compute_schedule_offset`, `environment.rs:630–644`) when the schedule domain is
populated at environment init. So the first schedule row delivered at step 0 corresponds
to the correct position in the year, but from that point on event timing is purely
counter-driven.

**Stochastic fallback path** (`event_load.rs:538–541`)

When no kW series exists:
```rust
let window_open = self.event_window_source.value_at(env)? > 0.0;
let probability = self.event_probability_source.value_at(env)?;
```
`ScheduleSource::ColumnRef` reads from `env.custom_domains` (the schedule payload),
indexed by `compute_schedule_idx` — also step-counter-based unless the `dst` feature
and `civil_timezone` are active.

`ScheduleSource::DailyProfile` uses `env.current_time.hour()` directly
(`schedule.rs:478`), making it sensitive to whatever UTC offset is embedded in
`current_time`.

### How OCHRE times events

OCHRE attaches the local timezone from the weather/schedule file to `start_time` at
`Dwelling.__init__` (line 87):
```python
self.start_time = self.start_time.replace(tzinfo=schedule.index.tzinfo)
```
All `event_start`/`event_end` entries in `all_events` are `pandas.Timestamp` values
carrying that timezone. The control check (`update_internal_control`, lines 251–261)
compares `self.current_time < self.event_start` — both are tz-aware local timestamps.
Events fire by **local wall-clock time**.

### F1 — SEVERITY: HIGH — UTC/local mismatch: `start_time` offset unvalidated against EPW timezone

**Location:** `crates/hares-equipment/src/event_load.rs:508` and
`crates/hares-core/src/environment.rs:630–644`

HARES schedule indexing is correct only if the `start_time` passed to
`EnvironmentManager::new` carries the correct local UTC offset. If a caller constructs
`start_time` with `FixedOffset::east(0)` for a UTC-7 location, `compute_schedule_offset`
uses UTC hours, offsetting all event windows by 7 hours. The PDF for a clothes washer
peaking at 8 AM local will fire at 1 AM instead.

There is no validation that `start_time`'s embedded offset matches the EPW/weather
file's `timezone_offset_h`. OCHRE avoids this by deriving the timezone from the schedule
index itself.

**Fix:** In `EnvironmentManager::new_with_resample`, after loading weather, compare
`start_time.offset().local_minus_utc()` against
`(weather.meta.timezone_offset_h * 3600.0) as i32`. Return a new
`EnvironmentManagerError::TimezoneMismatch` variant if they differ by more than a
rounding tolerance (e.g., ±30 s). Document the contract in the `new` doc comment.

---

### F2 — SEVERITY: MEDIUM — `current_step` not cross-checked against `env.current_time`

**Location:** `crates/hares-equipment/src/event_load.rs:508–535`

`current_step` is a raw monotonic counter. `env.current_time` is available in `step()`
but is never consulted in the deterministic event path. After a checkpoint restore the
counter is serialised and restored (`event_load.rs:587, 1047`), so it should remain
coherent, but there is no guard against the equipment being stepped while the
environment clock is held still, or vice versa.

OCHRE compares absolute timestamps so such drift cannot occur.

**Fix:** In debug builds (`#[cfg(debug_assertions)]`), compute the expected step index
from `(env.current_time - start_time).num_seconds() / dt_s` and assert it matches
`current_step % schedule_len`. Capture `start_time` as a field during `init()` to enable
this check without additional allocations.

---

### F3 — SEVERITY: LOW — `map_ochre_pdf_to_cycle_schedule` assumes minute-0 alignment

**Location:** `crates/hares-equipment/src/event_load.rs:1144–1177`

This utility maps a 1440-minute daily PDF (minute 0 = midnight local) into a
timestep-probability vector. The mapping always starts from minute 0, implicitly
assuming the schedule domain's first slot is midnight. If `schedule_start_offset` is
non-zero (i.e. the simulation begins mid-day), the PDF slot and the schedule column row
are misaligned.

**Fix:** Document the alignment pre-condition in the function's doc comment. Optionally
accept a `start_minute_of_day: usize` parameter that rotates the input slice before
aggregation.

---

### F4 — SEVERITY: LOW — `DailyProfile` hour indexed by `env.current_time.hour()` — UTC sensitive

**Location:** `crates/hares-types/src/schedule.rs:478`

When `ScheduleSource::DailyProfile` is used as the `event_window_source`, it calls
`env.current_time.hour()`. If `current_time` is near-UTC (small offset), daily event
windows will fire at the right local hours only by accident. This affects the stochastic
fallback path of both `EventBasedLoad` and `WetAppliance`.

This is a direct consequence of F1 — if the UTC offset on `start_time` is correct,
`current_time` fields will reflect local time. Fix F1 and this is mitigated.

## Recommended Tests

1. **`test_event_utc_offset_alignment`** in `crates/hares-equipment/tests/`:
   Construct an `EventBasedLoad` with a 15-minute-wide event window centred at hour 8
   local, using a UTC-5 `start_time` (`FixedOffset::east(-18000)`). Step through
   24 hours of simulated time and assert the active window aligns with hour 8, not
   hour 13.

2. **`test_schedule_start_offset_matches_event_cursor`** in integration tests:
   Run a deterministic kW-series appliance for one full year starting at a non-midnight
   offset (e.g. 06:00 UTC-7). Assert the first event fires at the correct step index,
   not shifted by the UTC offset.

3. **`test_environment_manager_rejects_offset_mismatch`** (after F1 fix):
   Pass a `start_time` with `FixedOffset::east(0)` against a weather file with
   `timezone_offset_h = -5.0` and assert `EnvironmentManager::new` returns
   `Err(EnvironmentManagerError::TimezoneMismatch)`.

### F-001 — CRITICAL — OCV curve is a different chemistry model than OCHRE's reference

OCHRE uses a single 11-point table (`degradation_curves.csv`) that is sourced from
SAM (System Advisor Model) Li-NMC defaults and applies to all battery chemistry
instances. HARES embeds four separate 51-point PyBaMM-derived curves (NMC Chen2020,
LFP Prada2013, NCA Kim2011, LTO Colclasure2011).

**Numeric deviation at matched SOC points (NMC, interpolated):**

| SOC | OCHRE V_oc (V) | HARES V_oc (V) | Δ (V) | OCHRE U_neg (V) | HARES U_neg (V) | Δ (V) |
|-----|---------------|----------------|--------|-----------------|-----------------|--------|
| 0.0 | 3.0000 | 2.5000 | −0.500 | 1.2868 | 1.1054 | −0.181 |
| 0.1 | 3.4679 | 3.0504 | −0.417 | 0.2420 | 0.5741 | +0.332 |
| 0.2 | 3.5394 | 3.2276 | −0.312 | 0.1818 | 0.3570 | +0.175 |
| 0.3 | 3.5950 | 3.3637 | −0.231 | 0.1488 | 0.2565 | +0.108 |
| 0.4 | 3.6453 | 3.4480 | −0.197 | 0.1297 | 0.2013 | +0.072 |
| 0.5 | 3.6876 | 3.6670 | −0.021 | 0.1230 | 0.1332 | +0.010 |
| 0.6 | 3.7469 | 3.7702 | +0.023 | 0.1181 | 0.1284 | +0.010 |
| 0.7 | 3.8400 | 3.8878 | +0.048 | 0.1061 | 0.1228 | +0.017 |
| 0.8 | 3.9521 | 3.9673 | +0.015 | 0.0925 | 0.0926 | +0.001 |
| 0.9 | 4.0668 | 4.0249 | −0.042 | 0.0876 | 0.0920 | +0.004 |
| 1.0 | 4.1934 | 4.2000 | +0.007 | 0.0859 | 0.0920 | +0.006 |

The PyBaMM Chen2020 source for HARES is higher fidelity than SAM's 11-point table,
and is intentionally different from OCHRE's reference (project goal is to match or
exceed OCHRE physics, not replicate OCHRE's approximate data). This is **by design**
and consistent with project memory `feedback_ashrae_not_ochre.md`.

However, two implications must be noted explicitly:

1. The low-SOC deviation is large: at SOC=0.0 the V_oc differs by −0.5 V and U_neg
   by −0.181 V. The Smith 2017 degradation Tafel term for mechanism 1 is
   `exp(α_b1·F/R × (U_neg/T − U_ref/T_ref))` where α_b1 = −1, F = 96485. At T=298K,
   a U_neg difference of 0.181 V produces a Tafel factor difference of
   `exp(96485/8.314 × 0.181/298) ≈ exp(7.04) ≈ 1140×`. Deep-discharge events
   (SOC < 0.2) therefore produce radically different calendar-fade estimates between
   HARES and OCHRE. Whether this is HARES being more accurate (PyBaMM) or introducing
   a simulation-domain mismatch is unresolved. **This needs a comment in the code.**

2. The U_neg curve at SOC=0.1 shows HARES is **2.4× higher** than OCHRE (0.574 V vs
   0.242 V). OCHRE's 0.242 V at SOC=0.1 is consistent with graphite staging plateaus;
   HARES's 0.574 V at the same point is in the region where HARES curves the response
   much more steeply. A PyBaMM graphite LFP anode reference check would clarify which
   is more physically accurate. **No test exercises U_neg at SOC < 0.2.**

**Verdict:** The OCV curve divergence from OCHRE is intentional (PyBaMM > SAM), but
the degradation implications at low SOC are uncharacterized and untested.

### F-002 — HIGH — Pack topology derivation uses a hard-coded 350 V target, silently
overriding OCHRE's `initial_voltage`-based approach

`mod.rs:664–676`: When `ah_cell` + `v_cell` are provided, HARES estimates n_series via:

```rust
let target_pack_v = 350.0_f64;
self.n_series = (target_pack_v / v_cell).round() as u32;
```

OCHRE (`Battery.py:98–100`) derives n_series from `initial_voltage` (default 50.4 V):

```python
n_series_by_voltage = self.parameters.get("initial_voltage", 50.4) / self.parameters["v_cell"]
self.n_series = self.parameters.get("n_series", n_series_by_voltage)
```

With OCHRE's defaults (v_cell=3.6 V, initial_voltage=50.4 V):
- OCHRE: n_series = 14, n_parallel ≈ 2.83, r_internal ≈ 0.0099 Ω
- HARES: n_series = round(350/3.6) = **97**, pack resistance completely different

This means passing `ah_cell=70, v_cell=3.6` to HARES produces a fundamentally
different pack topology than OCHRE would generate from the same inputs. Any user or
adapter that passes OCHRE-style `ah_cell`/`v_cell` parameters will get silently wrong
pack resistance and ohmic losses.

The 350 V target is only appropriate for modern high-voltage residential packs.
OCHRE's 50 V topology is realistic for older or smaller packs (e.g., the reference
10 kWh SAM model). The hard-coded constant needs to be either:
- An `initial_voltage` config key (matching OCHRE), or
- Removed; require explicit `n_series` instead.

**File:** `crates/hares-equipment/src/battery/mod.rs:664`

### F-003 — HIGH — Default pack resistance is inconsistent with OCHRE's defaults and
produces ~49× higher pack resistance

HARES defaults:
- `DEFAULT_N_SERIES = 96`, `DEFAULT_N_PARALLEL = 1`, `DEFAULT_CELL_RESISTANCE_OHM = 0.005 Ω`
- Pack resistance = 0.005 × 96 / 1 = **0.480 Ω**

OCHRE defaults (`default_parameters.csv`):
- v_cell=3.6 V, ah_cell=70 Ah, r_cell=0.002 Ω → n_series=14, n_parallel≈2.83
- Pack resistance = 0.002 × 14 / 2.83 = **0.0099 Ω**

Ratio: 0.480 / 0.0099 ≈ **49×**

For a 5 kW discharge at SOC=0.5 (pack OCV ≈ 352 V):
- Current I ≈ 5000 / 352 = 14.2 A
- HARES ohmic loss = 14.2² × 0.480 = **96.8 W**
- OCHRE equivalent (re-scaled to 350V pack) = 14.2² × 0.0099 = **2.0 W**

This factor-of-48 ohmic loss difference means HARES's efficiency correction is much
more aggressive than OCHRE's even though the operating range is sub-10% of P_max.
Actual real-world losses for a 5 kW / 350 V pack fall closer to OCHRE's figure.

The root cause is that HARES's DEFAULT_N_SERIES=96 (a 350 V modern high-voltage pack)
combined with DEFAULT_CELL_RESISTANCE_OHM=0.005 Ω (per-cell) is internally consistent
for a high-voltage 96S pack, but the absolute ohmic loss magnitude is not validated
against OCHRE's or any manufacturer's published round-trip efficiency at rated power.

**This is a correctness risk, not just a parity divergence.** The round-trip efficiency
calculated by the `compute_electrical()` path will overstate ohmic losses for all
catalog products that don't explicitly set `n_series`/`n_parallel`/`cell_resistance_ohm`.

**File:** `crates/hares-equipment/src/battery/mod.rs:87–91`

### F-004 — MEDIUM — catalog.rs products do not set `n_series`, `n_parallel`, or
`cell_resistance_ohm`, so all inherit default 96S1P/0.005Ω topology

`BatterySpec::to_config()` (`catalog.rs:126–179`) does not write `n_series`,
`n_parallel`, or `cell_resistance_ohm` keys. Every catalog product (TeslaPw3, Enphase
IQ 5P, etc.) therefore falls through to `DEFAULT_N_SERIES=96`, `DEFAULT_N_PARALLEL=1`,
`DEFAULT_CELL_RESISTANCE_OHM=0.005 Ω`.

For the Enphase IQ 5P (5 kWh LFP at 3.84 kW):
- At full charge power, I = 3840 / (cell_ocv_lfp × 96) ≈ 3840 / (3.3 × 96) ≈ 12.1 A
- Ohmic loss = 12.1² × 0.48 = **70.2 W** (1.8% of rated power)
- True LFP pack ohmic loss at 12.1 A through a realistic 10–20 mΩ pack is ~1.5–3 W

The ohmic overstatement means the efficiency model is producing inflated heat and
understated round-trip efficiency versus the catalog RTE values. Since `to_config()`
already writes the RTE-derived `charge_efficiency`/`discharge_efficiency`, and those
are then combined with the ohmic losses in `compute_electrical()`, the total efficiency
applied to charging/discharging is *both* the inverter eta *and* the ohmic losses —
potentially double-counting.

**File:** `crates/hares-equipment/src/battery/catalog.rs:126`

### F-005 — MEDIUM — `voltage_at_soc` linear interpolation uses O(n) scan; for
real-time simulation with uniform 0.02-step grid, binary search or index-direct lookup
would be correct

`ocv.rs:118`: The interpolation loop scans from `i=0` upward until `soc <=
soc_points[i+1]`. For the 51-point uniform grid with 0.02 steps, a direct index
lookup is possible: `i = (soc / 0.02) as usize`. The O(n) scan is not expensive at
n=51 but is inconsistent with `feedback_hot_loop_minimal.md` (called every timestep
for every battery, and also inside `degradation.accumulate()` every timestep).

This is a minor performance finding but noteworthy because the OCV interpolation is
in the hot loop.

**File:** `crates/hares-equipment/src/battery/ocv.rs:118`

### F-006 — LOW — `UNegTable::new()` validates for `is_finite && !is_nan` which is
redundant (`f64::is_finite()` already excludes NaN); `OcvTable::new()` requires `v > 0`
but `UNegTable::new()` does not enforce positivity

`ocv.rs:270–275`:
```rust
if !v.is_finite() || v.is_nan() {  // is_finite() already implies !is_nan()
```
`is_finite()` returns false for both `NaN` and `±Inf`, so the `v.is_nan()` check is
dead code. Additionally, `OcvTable::new()` enforces `v > 0.0` for voltages, but
`UNegTable::new()` does not enforce `v >= 0.0` for electrode potentials. While negative
electrode potentials are physically impossible (Li-ion), the validation gap is an
inconsistency.

**File:** `crates/hares-equipment/src/battery/ocv.rs:270`

### F-007 — LOW — LFP and NCA share the NMC graphite U_neg curve

`UNegTable::for_chemistry()` (`ocv.rs:199–205`) maps Lfp and Nca to the NMC graphite
curve. The comment notes "LFP and NCA share the NMC graphite anode curve." While LFP
cells (LFP/Graphite) and NCA cells (NCA/Graphite) do share a graphite anode, the
graphite electrode staging behavior (and therefore U_neg vs SOC) depends on the
lithiation state range, which differs between LFP and NMC cathodes due to different
usable stoichiometry windows. The PyBaMM Prada2013 LFP model would use a different
graphite utilization range than Chen2020 NMC. Sharing the NMC curve for LFP is a
simplification that affects the Tafel U_neg correction in degradation, particularly
at low SOC.

**File:** `crates/hares-equipment/src/battery/ocv.rs:199`

### F-008 — LOW — `OcvTable` and `UNegTable` are separate structs with duplicated
interpolation logic

Both `voltage_at_soc()` (`ocv.rs:108`) and `potential_at_soc()` (`ocv.rs:225`) are
identical O(n) scan interpolators operating on `(soc_points, values)` pairs. A single
`SocLookupTable` with a generic value type or an internal shared function would
eliminate duplication and reduce maintenance surface.

### F-009 — INFO — OCHRE uses a single fixed OCV table for all archetype instances;
HARES uses per-chemistry tables dispatched at init time

OCHRE has one degradation_curves.csv and applies it regardless of which battery product
is being simulated. HARES dispatches different OCV curves by chemistry at init time,
which is the correct approach. All four HARES curves are clearly sourced from published
PyBaMM parametrisations. This is a **positive divergence** from OCHRE.

### F-010 — INFO — OCHRE default `efficiency_type="advanced"` efficiency calculation
structure matches HARES `compute_electrical()`, but OCHRE uses `is_output_power` flag
to select between two linearisations; HARES always uses the quadratic formula

OCHRE `Battery.py:289–304` provides two paths:
- `is_output_power=True`: quadratic formula (same as HARES)
- `is_output_power=False`: linear approximation `V = Voc + P/Voc * R`

HARES `compute_electrical()` always uses the quadratic formula regardless of context.
The quadratic formula is more accurate. The linear approximation in OCHRE is used only
for initial setpoint-from-SOC estimation in `get_setpoint_from_soc()`. HARES avoids
this by not needing the linear path. This is a **positive divergence**.

## Recommended Tests

### T-001 — Pack resistance round-trip check against manufacturer RTE
For each catalog product, compute the effective round-trip efficiency implied by the
ohmic model at rated power and compare against `spec.round_trip_efficiency`. The
computed RTE must be within ±2% of the spec value. If the 96S1P default causes a
larger deviation, catalog entries must set explicit topology.

### T-002 — Degradation Tafel sensitivity at low SOC
Run the degradation accumulator for 1 simulated day at SOC=0.05 and SOC=0.1 with both
OCHRE-equivalent U_neg values and HARES PyBaMM U_neg values. Confirm the resulting
b1_eff values are within a documented tolerance (or document the expected deviation).
This validates that low-SOC behaviour in HARES is intentional and bounded.

### T-003 — Pack topology derivation from OCHRE-style ah_cell/v_cell inputs
Pass `ah_cell=70, v_cell=3.6` (OCHRE defaults) and assert that the resulting
`n_series` and `r_internal` are within ±20% of OCHRE's expected values (n_series=14,
r_internal≈0.0099 Ω) — or assert that HARES documents the intentional departure and
applies a different input convention.

### T-004 — OCV monotonicity and physical bounds for all chemistry curves
Existing `all_chemistries_strictly_increasing` test covers NMC, LFP, NCA, LTO. Add
assertions that U_neg curves are also strictly decreasing with SOC for graphite anodes
(U_neg decreases as SOC increases for graphite), and strictly flat-to-decreasing for
LTO (near-flat plateau).

### T-005 — O(1) interpolation equivalence for uniform grid
If F-005 is fixed by replacing the O(n) scan with index-direct lookup, add a test
that iterates all 51 grid points and all midpoints between them, asserting the new
implementation matches the reference scan to within 1e-12.

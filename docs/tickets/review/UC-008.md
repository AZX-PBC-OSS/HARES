## Background/Context

Foundation walls and slabs have specific HPXML fields: `Height` (ft), `DistanceToTopOfInsulation`
(ft), `DistanceToBottomOfInsulation` (ft), `InsulationRValue`, slab `PerimeterInsulationDepth`
(ft), `UnderSlabInsulationWidth` (ft). All length units are feet, R-values are imperial.

### Per-Field Conversion Table

All conversions are applied via `parse_value_with_units` / `convert_length_to_m` /
`convert_r_to_m2_k_w`. The default-when-no-units fallback is: length → feet, area → ft², R-value
→ hr·ft²·°F/BTU.

| Field | HPXML native unit | HARES stored unit | Conversion applied | Location |
|---|---|---|---|---|
| `FoundationWall/Height` | ft | m | `ValueKind::Length` → ft→m | `building.rs:1096` |
| `FoundationWall/DepthBelowGrade` | ft | m | `ValueKind::Length` → ft→m | `building.rs:1097-1098` |
| `DistanceToTopOfInsulation` | ft | m | `ValueKind::Length` → ft→m | `building.rs:1129-1131` |
| `DistanceToBottomOfInsulation` | ft | m | `ValueKind::Length` → ft→m | `building.rs:1123-1126` |
| Insulation `NominalRValue` (fnd wall, LUT string) | IP (hr·ft²·°F/BTU) | **IP (raw)** | **none — intentional** | `building.rs:1112-1115` |

| `PerimeterInsulation/Layer/NominalRValue` (slab LUT) | IP | **IP (raw)** | **none — intentional** | `building.rs:1161-1163` |

The "intentional no-conversion" rows are correct: the LUT CSV stores insulation lookup keys using
IP values ("2ft R10 Perimeter", "R13", etc.), so the raw HPXML IP numbers must be round-tripped
directly into those format strings without conversion. This matches OCHRE's behaviour, where
`get_fnd_wall_insulation` and `get_slab_insulation` operate on unmodified HPXML dicts that still
carry IP values.

### OCHRE Comparison

**Critical design difference — `Height`/`DepthBelowGrade` units at the point of ratio computation:**

In OCHRE, `get_fnd_wall_insulation` (envelope.py:434-459) receives the raw HPXML dict where
`Height` and `DepthBelowGrade` are still in **feet** (the ft→m conversion of `Height` happens
on line 183 of hpxml.py, *after* calling `get_fnd_wall_insulation`). The insulation-height
threshold test `insulation_height <= height / 2` therefore compares feet to feet.

In HARES, `extract_foundation_wall_insulation` (`building.rs:1096-1103`) calls
`parse_value_with_units(..., ValueKind::Length)` for both `Height` and `DepthBelowGrade`,
converting both to **metres**. The ratio `depth_below_grade / height` and the half-wall
threshold `insulation_height <= height / 2.0` are computed in metres.

The ratio `depth_below_grade / height` is dimensionless, so computing it in metres or feet
produces the same value. The half-wall threshold `insulation_height <= height / 2.0` is also
dimensionless once both sides are in the same unit (metres). The logic is therefore
**numerically equivalent** to OCHRE's despite operating in SI.

**`DistanceToTopOfInsulation` / `DistanceToBottomOfInsulation`:** OCHRE reads them raw (feet);
HARES reads them via `ValueKind::Length` (→metres). Both sides compare distance to `height`
in the same unit, so again numerically equivalent.

**`NominalRValue` in insulation detail strings:** OCHRE rounds with Python's `:n` format
(no trailing `.0` for integers). HARES uses `.round() as i32` then formats with `{r_int}`.
For whole-number R-values (R-5, R-10, R-13, R-19, R-21, R-30…) the outputs are identical.
For fractional IP R-values (e.g. R-3.8) OCHRE would emit `"R3.8"` while HARES would emit
`"R4"`. HPXML residential R-values are almost universally integers, so this is low risk, but
it is a divergence from OCHRE that could cause a LUT miss on non-standard inputs.

**Slab `InsulationDepth` / `InsulationWidth`:** OCHRE reads raw (feet) and embeds directly in
format strings. HARES also reads raw via `n.text_as_f64()` (no `parse_value_with_units` call)
and rounds to integer before formatting. Consistent with OCHRE for integer foot values.

### Defects Found

**F1 — Fractional R-value truncation in LUT format string (MEDIUM)**
File: `crates/hares-io/src/hpxml/building.rs:1138`

```rust
let r_int = r_ip.round() as i32;
```

OCHRE uses Python's `:n` format which renders `3.8` as `"3.8"` and `10.0` as `"10"`. HARES
always rounds to integer. For any non-integer R-value present in a LUT entry key, HARES will
produce a different string and cause a LUT miss, silently falling back to a default construction.

The same truncation exists for slab R-values at lines 1186 and 1194 (slab under-slab R), and
line 1179 (perimeter R). The slab `InsulationDepth`/`InsulationWidth` fields also use
`.round() as i32` at lines 1178 and 1194.

If all LUT keys happen to use integer R-values and integer foot dimensions, this is harmless.
The LUT CSV should be verified. If any key has a decimal value (e.g. "2.5ft R10 Perimeter"),
the HARES code will produce the wrong key string.

**F2 — `DistanceToTop/BottomOfInsulation` compared to `height` in metres, fallback values in
metres, but OCHRE defaults in feet (LOW)**
File: `crates/hares-io/src/hpxml/building.rs:1127, 1132`

HARES defaults `dist_bottom` to `height` (metres) and `dist_top` to `0.0` when the fields are
absent. OCHRE defaults to `height` (feet) and `0`. Since the ratio
`(dist_bottom - dist_top) / height` is what matters for the threshold, and `dist_bottom`
defaults to `height` in both cases, the resulting `insulation_height` defaults to `height`
(full wall) in both. The half-wall threshold then correctly yields `height <= height / 2.0`
which is false, so full-wall `"R{n}"` is produced as a default. Behaviour is equivalent.

**F3 — `reduce(f64::min)` on insulation heights (LOW)**
File: `crates/hares-io/src/hpxml/building.rs:1135`

`reduce(f64::min)` returns `None` when `insulation_layers` is empty, in which case
`.unwrap_or(height)` supplies the full-wall default. The empty-layers case is caught earlier
by `if r_ip > 0.0` (line 1117), so this can only be reached when layers are non-empty, making
it safe. However, if a layer has `NominalRValue > 0` but no `DistanceToBottom/Top`, the
default of `(height - 0.0) = height` is used, which is again correct (full wall). No bug.

---

### Summary

ENV-005 and ENV-006 are implemented and the core logic is correct. The primary conversion
strategy — lengths to metres for geometry, raw IP kept for LUT key strings — correctly mirrors
OCHRE's split behaviour. The one actionable defect is **F1**: fractional R-value rounding in
format strings could produce LUT misses; verify the LUT CSV has only integer R-value keys or
switch to a format that preserves one decimal place when the value is non-integer (matching
Python `:n`).

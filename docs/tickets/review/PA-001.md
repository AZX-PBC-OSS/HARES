## Background/Context

`DwellingTelemetry` has `timestep_index` and `current_time` fields that are only
visible in `__repr__`, not as Python getters. Users cannot programmatically read the
current simulation time from a telemetry snapshot.

## Investigation Instructions

1. Read `py_telemetry.rs` — what is exposed via `#[pyo3(get)]` vs what exists in Rust?
2. Read `telemetry.rs` — what fields does `DwellingTelemetry` carry?
3. Document the gap and recommend whether these should be exposed.
4. Check: does `PyDwelling.step()` return the current time in its dict? If so, the
   telemetry gap may be less critical.

## Findings

### 1. `Telemetry` object exposes neither `timestep_index` nor `current_time` (Confirmed defect)

`DwellingTelemetry` carries both fields correctly at every step:
- `crates/hares-core/src/telemetry.rs:12-13` — `timestep_index: u64`, `current_time: DateTime<FixedOffset>`

`PyTelemetry` in `crates/hares-python/src/py_telemetry.rs` exposes only four items:
- `#[getter] total_power_kw` (line 52)
- `#[getter] reactive_power_kvar` (line 57)
- `fn zone()` returning a dict (line 30)
- `fn equipment()` returning a dict (line 41)

`timestep_index` and `current_time` appear only inside `__repr__` (line 64), making
them visible in string output but unreachable as Python attributes. The `.pyi` stub
at `python/ochre_next/_hares.pyi:789-796` confirms the gap — neither property is
declared.

### 2. `step()` returns `timestamp` but not `timestep_index`

`crates/hares-python/src/py_dwelling.rs:566` sets `"timestamp"` (wall-clock datetime)
in the `StepResult` dict, matching the `StepResult` TypedDict in the stub. No integer
step index is included in the step result either.

**Consequence:** there is no way to obtain an integer timestep counter from the Python
API without the caller maintaining its own counter, which duplicates Rust-side state
and is prone to going out of sync after errors or rewinds.

### 3. `zone()` dict does expose outdoor_temp_c and outdoor_rh

`py_telemetry.rs:36-38` — both `outdoor_temp_c` and `outdoor_rh` are included in the
`zone()` dict. This sub-question from the review notes is resolved: no gap there.

### 4. Misleading `__repr__`

`__repr__` (line 62-65) prints `step=N, time=T`, which works at runtime but creates
a user expectation that these fields are accessible as attributes. They are not. This
is a usability trap for anyone inspecting the repr output interactively.

---

## Impact Assessment

- Users cannot determine which simulation timestep a `Telemetry` snapshot belongs to
  without external bookkeeping.
- Time-conditional control logic (e.g. HELICS synchronisation, RL episode boundaries,
  scheduled dispatch) must re-derive the step index from a separate counter, creating
  a class of subtle off-by-one bugs.
- OCHRE exposes `timestamp` on its `generate_results` output. HARES `step()` matches
  that via `StepResult.timestamp`. The `Telemetry` object — used by actors and RL
  agents — lagging behind is an inconsistency.

---

## Recommendation

Expose both fields as `#[getter]` properties on `PyTelemetry`:

```rust
// crates/hares-python/src/py_telemetry.rs
#[getter]
pub fn timestep_index(&self) -> u64 {
    self.inner.timestep_index
}

#[getter]
pub fn current_time<'py>(&self, py: Python<'py>) -> PyResult<Py<PyAny>> {
    let datetime = py.import("datetime")?.getattr("datetime")?;
    let obj = datetime.call_method1(
        "fromisoformat",
        (self.inner.current_time.to_rfc3339(),),
    )?;
    Ok(obj.unbind())
}
```

Note: the existing `tz_to_py_datetime` helper accepts `DateTime<chrono_tz::Tz>` but
`current_time` is `DateTime<FixedOffset>`. A second helper for `FixedOffset` should
be extracted (or the existing one generalised to accept a common trait) rather than
inlining the conversion, to avoid duplicated fromisoformat calls.

Update `python/ochre_next/_hares.pyi` `Telemetry` class to add:

```python
@property
def timestep_index(self) -> int: ...
@property
def current_time(self) -> datetime.datetime: ...
```

Also add `timestep_index` to `StepResult` TypedDict (currently only `timestamp` is
present as the time identifier; adding the integer index makes it consistent with
Telemetry).

## Recommended Tests

In `tests/python/test_py_dwelling.py`:

```python
def test_telemetry_exposes_timestep_index_and_current_time():
    dw = build_minimal_dwelling()
    dw.initialize()
    for n in range(1, 4):
        dw.step()
        t = dw.telemetry()
        assert t.timestep_index == n
        assert isinstance(t.current_time, datetime.datetime)
```

The test must assert the *value* of `timestep_index` (not just its existence) to
catch off-by-one errors in how the index is assigned relative to when `telemetry()`
is called (before vs after the internal counter increment).

## Background/Context

`DispatchRequest` in Python has static constructors for most signal types but is
missing `ev_plug_in`, `ev_drive`, `ev_set_ready_by` — these exist on `Signal` but
not on `DispatchRequest`. Python actor authors who want to control EVs must use a
workaround.

## Investigation Instructions

1. Read `py_actor.rs` `PyDispatchRequest` — list all static constructors.
2. Read `py_control.rs` `PyControlSignal` — list all EV-related constructors.
3. Identify the gap: which signals can be created on `ControlSignal` but not on
   `DispatchRequest`?
4. Assess: can users work around it? How painful is the workaround?
5. Recommend fix.

- `test_dispatch_request_ev_drive`: construct `DispatchRequest.ev_drive("ev", kwh=10.0)`, verify field.

- Round-trip test: all four EV variants on `DispatchRequest` → `into_dispatch_request()` → `ControlSignal` match expected Rust value.

## Findings

### Gap 1 (MEDIUM): `DispatchRequest` missing three EV convenience constructors

`PyDispatchRequest` (`py_actor.rs:414-578`) has static methods for:
`thermal_setpoint`, `thermal_setpoint_delta`, `mode_override`, `load_fraction`,
`power_limit`, `power_setpoint`, `soc_target`, `duty_cycle`, `demand_response`,
`ideal_capacity`.

`PySignal` enum (`py_actor.rs:200-250`) includes `EvPlugIn`, `EvDrive`,
`EvSetReadyBy` as variants, and `PySignal` has static factory methods for all
three (`py_actor.rs:661-676`). However `PyDispatchRequest` has **no** static
constructors for any EV variant.

Concrete gap (evidence at `py_actor.rs:414-578` — no `ev_*` methods):

| Signal | PySignal variant | PySignal constructor | PyDispatchRequest constructor |
|---|---|---|---|
| EvPlugIn | yes | yes | **missing** |
| EvDrive | yes | yes | **missing** |
| EvSetReadyBy | yes | yes | **missing** |

The `.pyi` stub confirms: `DispatchRequest` exposes no `ev_*` static methods
(`_hares.pyi:707-774`), while `Signal` also exposes no `ev_*` stubs
(`_hares.pyi:667-705`).

### Gap 2 (MEDIUM): `EvAwayCharge` absent from actor API entirely

`ControlSignal::EvAwayCharge { power_kw }` is a first-class Rust variant
(`control_signal.rs:127-129`) used to set the external away-charger power rate.
It exists on `PyControlSignal` (`py_control.rs:260-263`) with a static constructor
and full `from_dict`/`to_dict` round-trip support. However:

- `PySignal` has **no** `EvAwayCharge` variant (`py_actor.rs:200-250`).
- `PyDispatchRequest` has **no** `ev_away_charge` constructor.
- `PySignal::into_control_signal()` match arm is absent — any code path reaching
  it via `PySignal` is unreachable by construction.
- The `.pyi` stub confirms absence (`_hares.pyi:667-705`).

This means a Python actor author cannot send `EvAwayCharge` through the
`Actor.decide()` → `DispatchRequest` pipeline at all. The only workaround is
`apply_control()` if the dwelling exposes it directly, but actors do not have
direct dwelling access — so the signal is **unreachable from Python actors**.

### Gap 3 (LOW): `EventDelay` absent from actor API entirely

`ControlSignal::EventDelay { delay_s }` (`control_signal.rs:137-139`) is
supported by `PyControlSignal` (`py_control.rs:379-381` in `from_dict`) but is
absent from `PySignal` and `PyDispatchRequest`. It is not an EV-specific signal
but follows the same pattern as `EvAwayCharge`.

### Gap 4 (LOW): `.pyi` stub for `Signal` missing EV constructors

`Signal.ev_plug_in`, `Signal.ev_drive`, `Signal.ev_set_ready_by` exist as
`#[pymethods]` in Rust (`py_actor.rs:661-676`) but are absent from the
`_hares.pyi` stub (`_hares.pyi:667-705`). Users relying on IDE autocomplete or
`mypy` will not discover these constructors exist.

### Workaround assessment

There is no actor-layer workaround for `EvAwayCharge` or `EventDelay`. A Python
actor that needs to signal EV away-charging power cannot do so at all through the
`decide()` return type. For `EvPlugIn`, `EvDrive`, and `EvSetReadyBy` the
workaround is to construct a `Signal` manually and then construct `DispatchRequest`
directly via its constructor (`DispatchRequest(target=..., signal=...,
priority=...)` using `from_py_object` field init) — this is undocumented and
non-obvious.

## Recommended Fix

**`crates/hares-python/src/py_actor.rs`**

1. Add `EvAwayCharge { power_kw: f64 }` to the `PySignal` enum and a
   `match` arm in `PySignal::into_control_signal()` mapping it to
   `ControlSignal::EvAwayCharge { power_kw }`.

2. Add static constructors to `PyDispatchRequest` for all four EV variants:
   - `ev_plug_in(target, state: PyEvConnectionState, priority=None)`
   - `ev_drive(target, kwh, priority=None)`
   - `ev_away_charge(target, power_kw, priority=None)`
   - `ev_set_ready_by(target, departure_hour, target_soc, priority=None)`

**`python/ochre_next/_hares.pyi`**

3. Add `ev_plug_in`, `ev_drive`, `ev_set_ready_by` stubs under `class Signal`.
4. Add `ev_plug_in`, `ev_drive`, `ev_away_charge`, `ev_set_ready_by` stubs under
   `class DispatchRequest`.

`EventDelay` should receive the same treatment (add to `PySignal`, add
`DispatchRequest.event_delay(target, delay_s, priority=None)`) unless the
intent is to reserve it as an internal-only mechanism — if so, add a comment
to the Rust type explaining the restriction.

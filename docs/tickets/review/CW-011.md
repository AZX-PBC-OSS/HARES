## Background/Context

Electric resistance water heaters have upper and lower elements, a stratified tank,
deadband thermostats, and standby losses (UA). Config includes tank volume, element
capacities, setpoint, deadband, UA, and element positions within the tank.

## Investigation Instructions

1. **Read OCHRE `ElectricResistanceWaterHeater.py`:**
   - List every config key in `__init__()`.
   - Note: upper/lower element capacity, deadband, setpoint, tank nodes, UA.
   - How are element positions determined (which tank nodes)?

2. **Read OCHRE `parse_water_heater()` in `hpxml.py`:**
   - What fields are extracted for ERWH?
   - How is UA derived from EF or UEF?

3. **Read HARES `resolve_water_heater.rs`:**
   - What keys are set in `EquipmentSpec.parameters`?
   - Is UA derived the same way?

4. **Read HARES `resistance.rs` and `tank.rs`:**
   - What config keys are consumed?
   - How is the stratified tank configured (number of nodes, initial temps)?
   - How are element positions assigned?

5. **Build comparison table** (expect 15+ fields).

6. **Pay special attention to:**
   - Upper vs lower element capacity — are they equal or different?
   - Tank node count and element node assignment
   - Deadband upper/lower limits — how are they derived from setpoint?

### Finding 1 — Upper element node index (1-indexed OCHRE vs 0-indexed HARES, semantic mismatch)

**Severity: medium**

OCHRE assigns the upper element to node "1" (1-indexed from the top) when `n_nodes < 12`, and node "3" when `n_nodes >= 12`. HARES assigns `upper_element_node` from config, defaulting to index 0 (0-indexed from the top). For ≤12 nodes the outcome is the same (index 0 = node "1"), so this is correct.

However, HARES also exposes `upper_element_node` and `lower_element_node` as config keys, but `resolve_water_heater.rs` never writes these keys. This means the HPXML path cannot override element placement away from the defaults, which is acceptable for standard residential WHs (upper=top, lower=bottom) but is not documented and not tested.

**Evidence:**
- OCHRE `WaterHeater.py:57`: `upper_node = "3" if self.model.n_nodes >= 12 else "1"`
- HARES `resistance.rs:115–119`: default `upper_element_node=0`, `lower_element_node=n_nodes-1`
- `resolve_water_heater.rs`: zero writes to `upper_element_node` / `lower_element_node`

**Fix:** Document that element node placement is not configurable from HPXML. Alternatively, for parity with 12-node OCHRE behaviour (`upper_node="3"` = index 2), write `upper_element_node = 2` into params when `tank_nodes >= 12`. This is a behavioural difference when 12-node mode is used.

---

### Finding 2 — Default node count mismatch: OCHRE 2-node, HARES 6-node

**Severity: low / informational**

OCHRE defaults ERWH to `water_nodes=2`. HARES defaults to 6 nodes (`tank_nodes` not set from HPXML). Neither the HPXML resolver nor any defaults store writes `tank_nodes`, so the default always fires. This is a deliberate higher-fidelity choice in HARES (more stratification). It is a known difference rather than a defect, but it affects parity tests and should be documented.

**Evidence:**
- OCHRE `WaterHeater.py:31`: `nodes = kwargs.get("water_nodes", 2)`
- HARES `resistance.rs:112–114`: `parse_usize(config.get_f64("tank_nodes")).unwrap_or(6).clamp(1,12)`
- `resolve_water_heater.rs`: no write to `tank_nodes`

**Note:** With 6 nodes and OCHRE's thermostat logic, the upper thermostat fires on node index 0 (matching OCHRE "1") and lower on node index 5 (matching OCHRE `str(n_nodes)=str(6)` = "6", but OCHRE only had 2 nodes so the effective index was 1). Because HARES has more nodes, the lower thermostat references a physically different (cooler, lower) position in the tank — this is the intended stratification improvement.

### Finding 3 — Jacket R-value physics model differs from OCHRE

**Severity: low**

OCHRE applies a two-layer jacket correction that accounts for the existing foam insulation and internal/external film coefficients:

```python
jacket_insulation = 5.0  # R5 foam (IP), F·ft²·hr/BTU per inch
jacket_thickness = 1 if is_electric and energy_factor < 0.7 else 2  # inches
# film coefficients: 1.3 (internal convection) and 52.8 (external radiation) BTU/hr·ft²·°F
u_pre_skin = 1.0 / (jacket_thickness * jacket_insulation + 1.0/1.3 + 1.0/52.8)
ua -= tank_jacket_r / (1.0 / u_pre_skin + tank_jacket_r) * u_pre_skin * a_side
```

HARES uses a simpler series-resistance formula, treating the jacket R-value as adding directly in series with the existing tank UA:

```rust
// mod.rs:150–151
let r_total = 1.0 / ua_base + jacket_r / lateral_area_m2;
1.0 / r_total
```

The OCHRE formula correctly models the jacket as replacing only the outer foam layer, not the existing internal insulation plus film resistances. HARES's formula is physically reasonable but will compute a lower (more insulating) effective UA than OCHRE when a jacket is present, because it treats the full existing UA as if it were just the foam skin, not accounting for the inherent film resistances.

In practice, jacket R-values are uncommon in typical ResStock/HPXML files, so the real-world impact is small. This is a known physics gap that does not affect parity for the standard test fixtures.

**Evidence:** `mod.rs:136–152`, OCHRE `hpxml.py:1131–1138`

---

### Finding 4 — Solar thermal fraction on UA not modelled

**Severity: informational**

OCHRE's `parse_water_heater` accepts a `solar_fraction` parameter and scales UA by `(1 - solar_fraction)`. This represents a solar thermal pre-heat system reducing standby losses. HARES does not parse `SolarFraction` from HPXML and does not apply any UA scaling for solar thermal. For the standard ERWH case this is irrelevant (no solar thermal), but any HPXML file with a solar water heater would silently ignore the solar assist.

**Evidence:** OCHRE `hpxml.py:1139`: `ua *= 1.0 - solar_fraction`; `resolve_water_heater.rs`: no `SolarFraction` read.

---

### Finding 5 — `UaResult.conversion_efficiency` discarded by resolver (benign for ERWH)

**Severity: benign for ERWH, latent for gas path**

`ua_from_energy_factor` returns a `UaResult` struct containing `ua_w_per_k` and `conversion_efficiency`. The resolver (`resolve_water_heater.rs:94–108`) only extracts `ua_w_per_k` and discards `conversion_efficiency`. For ERWH, `eta_c` is always 1.0 so no impact. For the gas water heater, the gas burner's `burner_efficiency_constant` is set from a config key (`burner_efficiency`) that the resolver also never writes — the gas WH path has a separate defect not covered by this ticket.

**Evidence:** `resolve_water_heater.rs:95–96`, `water_heater_ua.rs:54–61`

---

### Summary

Fourteen of the nineteen surveyed fields are fully equivalent. The material gaps are:

1. Upper element node for ≥12-node tanks should be at index 2 (matching OCHRE "3") but currently defaults to 0 — a parity difference when `tank_nodes=12`.
2. Default node count (HARES: 6, OCHRE: 2) is a deliberate choice but undocumented and not asserted anywhere.
3. Jacket UA physics differs slightly from OCHRE's model; not impactful for standard fixtures.
4. Solar thermal fraction ignored (no fixture exercises this).
5. `conversion_efficiency` discarded from UA result; harmless for ERWH.

## Recommended Tests

1. **`erwh_12node_upper_element_at_node_2`** — Construct a `ResistanceWH` with `tank_nodes=12` and no explicit `upper_element_node`. Assert `upper_element_node == 2` (OCHRE parity: node "3" = index 2). This test is expected to **fail** until Finding 1 is resolved.

2. **`erwh_default_node_count_is_documented`** — A unit test or fixture that verifies `tank_nodes` defaults to 6 (not 2) for ERWH, with a comment explaining the deliberate divergence from OCHRE's 2-node default.

3. **`erwh_ua_from_ef_50gal_matches_ochre`** — Already exists as `electric_ef_50gal_matches_ochre` in `water_heater_ua.rs`. Extend to also assert the resulting `ua_w_per_k` is correctly inserted into the `params` map by `resolve_water_heater.rs` when called with a synthetic HPXML node for a 50-gal electric storage WH with EF=0.92.

4. **`erwh_jacket_r_reduces_ua_vs_ochre`** — Compute UA for a 50-gal electric WH with EF=0.92 and `JacketRValue=5` (R5 IP) using both HARES's formula and OCHRE's formula. Assert that HARES produces a lower effective UA (more insulating) and that the difference is within 10 % of the OCHRE value. Document the known divergence.

5. **`erwh_setpoint_from_hpxml_default`** — When HPXML omits `HotWaterTemperature`, the resulting `setpoint_c` must equal 51.67°C (125°F). Assert this in `resolve_water_heater` integration tests.

6. **`erwh_heating_capacity_from_hpxml`** — When HPXML provides `HeatingCapacity=4500 BTU/hr`, assert `heating_capacity_w ≈ 1318 W` in params; when absent, assert `heating_capacity_w` is absent from params (so the equipment falls back to `DEFAULT_ELEMENT_POWER_W=4500 W`). This exercises the Btu/hr→W conversion at the parse boundary.

## Background/Context

OCHRE auto-generates interior walls (area = zone floor area) and furniture
(area = zone_area * fraction: 40% Indoor/Foundation, 10% Garage, 0% Attic).
These contribute to zone thermal mass and longwave radiation exchange.

## Investigation Instructions

1. Read OCHRE interior wall and furniture generation.
2. Read HARES `building.rs` equivalent (lines ~572-655).
3. Compare: same fractions? Same surface properties (R-value, mass)?

## Findings

### Finding 1 — LOW — `PartitionWallMass` HPXML extension element silently ignored

**Location:** `crates/hares-io/src/hpxml/building.rs:572–603`

OCHRE reads `Enclosure/extension/PartitionWallMass` and asserts that if present,
`AreaFraction == 1.0`, `InteriorFinish.Type == "gypsum board"`, and
`InteriorFinish.Thickness == 0.5` (`hpxml.py:752–757`). HARES does not parse
`PartitionWallMass` at all — there are zero references across all crates.

**Impact:** Numeric output is identical for all valid HPXML files, because OCHRE's
`AreaFraction` guard only allows the value 1.0 (matching the HARES hard-coded default).
The divergence is a validation gap: an HPXML file supplying `AreaFraction != 1.0`
would cause OCHRE to crash with an assertion error while HARES silently proceeds with
the wrong area. This is not a parity defect under normal input, but is an input
validation gap.

**Fix:** In the interior wall generation block, read
`Enclosure/extension/PartitionWallMass/AreaFraction` and return an error if it is
present and not equal to 1.0. Similarly reject non-default `InteriorFinish` values.
This matches OCHRE's intent without adding configurable scaling that neither
implementation supports.

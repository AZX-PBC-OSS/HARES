## Background/Context

Central air conditioners are the most common cooling system. Config includes rated
capacity, SEER/EER, SHR (sensible heat ratio), biquadratic performance curves,
fan power, and duct parameters.

### BUG-1 (Severity: High) — EIR always falls back to 0.35 for HPXML-sourced single-speed AC

**File:** `crates/hares-equipment/src/hvac/air_conditioner.rs:424`

`CoolingCore::init` derives the EIR default via:
```rust
first_f64(config, &["seer", "SEER"])
```
`resolve_hvac.rs:insert_annual_efficiency` inserts `"efficiency_seer"` (or `"cooling_efficiency"` when `AnnualCoolingEfficiency` is used), never the bare key `"seer"`. Therefore, for every HPXML-sourced central AC, the SEER value is present in the config but invisible to the EIR computation. The equipment falls back to `DEFAULT_EIR_FALLBACK = 0.35`, which corresponds to ≈ 9.8 SEER — far below the legal residential minimum of 13–15 SEER. All per-stage EIR values and the Cd curve selection are computed from this wrong baseline.

This is the root cause confirmed by UC-002 ("single-speed AC always uses default EIR").

**Fix:** In `CoolingCore::init`, extend the key list to include `"efficiency_seer"` and `"cooling_efficiency"`:
```rust
first_f64(config, &["seer", "SEER", "efficiency_seer", "cooling_efficiency"])
```

### BUG-2 (Severity: Medium) — Default SHR diverges from OCHRE when HPXML omits `SensibleHeatFraction`

**File:** `crates/hares-equipment/src/hvac/air_conditioner.rs:468`

When `SensibleHeatFraction` is absent, `resolve_hvac.rs` does not insert a `shr` key. OCHRE defaults to `SHR = 1.0` (pure sensible load). HARES defaults `rated_shr = 0.75`, which is ASHRAE typical but not the OCHRE parity value.

For parity tests, any HPXML fixture that omits `SensibleHeatFraction` will produce a different SHR, changing latent cooling, coil Ao factor, and annual energy.

**Fix:** Document the intentional deviation, or insert `"shr": 1.0` in `resolve_hvac.rs` when no `SensibleHeatFraction` is present, matching OCHRE. The current 0.75 default is physically more correct for a real coil, so this needs a policy decision. Mark as deliberate deviation if not changing it.

### BUG-3 (Severity: Medium) — `fan_power_w` (absolute W) silently ignored for AC/HP cooler

**Files:** `crates/hares-io/src/hpxml/resolve_hvac.rs:353,466`, `crates/hares-equipment/src/hvac/hvac_core.rs:336-340`

`resolve_hvac.rs` inserts `"fan_power_w"` when the HPXML extension has `FanPowerWatts`. `hvac_core.rs::HvacEquipment::init` only reads `fan_power_w_per_m3_s` and `fan_power_w_per_cfm` — it never reads `fan_power_w`. For furnaces, `furnace.rs` reads it explicitly at line 308. For AC and HP cooler there is no equivalent, so the absolute fan power override is silently discarded and the default 0.365 W/CFM is used instead.

**Fix:** In `HvacEquipment::init`, after the per-CFM handling block, add a fallback:
```rust
} else if let Some(w) = extract_numeric(config, "fan_power_w") {
    // Absolute fan power supplied; convert to per-(m³/s) using rated airflow.
    // Rated airflow = airflow_m3_s_per_w * capacity_w; capacity is not yet
    // known here, so store the absolute value and resolve in equipment init.
    // Alternative: require the caller to pass fan_power_w_per_cfm instead.
}
```
The cleanest fix is to convert in `resolve_hvac.rs` at the point of insertion (before calling `build_spec`), using the known capacity and 400 CFM/ton to produce `fan_power_w_per_cfm`. That keeps `hvac_core.rs` unchanged.

### BUG-4 (Severity: Low) — OCHRE low-SEER single-speed PLF override not replicated

**File:** `vendors/OCHRE/ochre/Equipment/HVAC.py:1065-1068`

OCHRE overrides the EIR PLF quadratic coefficients to `[0.8, 0.2, 0]` for single-speed AC with SEER < 13. This produces a steeper part-load efficiency penalty for old low-efficiency equipment. HARES has no equivalent path — the `eir_plr_coefficients` injection in `resolve_hvac.rs` only fires for multi-speed equipment (inside `apply_multispeed_cooling_parameters` which returns early when `n_speeds <= 1`).

Impact: for ResStock stock with pre-13-SEER AC (common in older vintages), HARES will over-predict part-load efficiency at low duty cycles relative to OCHRE.

**Fix:** In `resolve_hvac.rs::insert_startup_degradation` or a new adjacent helper, after computing `n_speeds == 1` and `seer < 13.0`, insert `"eir_plr_coefficients": "[[0.8, 0.2, 0.0]]"` into params so `hvac_core.rs` picks it up.

### BUG-5 (Severity: Low) — `FanPowerWattsPerCFM` CFM/ton baseline mismatch

**File:** `crates/hares-io/src/hpxml/resolve_hvac.rs:351` (cooling), OCHRE `utils/hpxml.py:896`

OCHRE converts `FanPowerWattsPerCFM` → absolute W using **312 CFM/ton** for all cooling equipment. HARES passes `fan_power_w_per_cfm` through to `hvac_core.rs`, which then multiplies by actual airflow at **400 CFM/ton** for `AcCooler`. Result: for a 3-ton AC with 0.365 W/CFM, HARES computes `0.365 × 400 × 3 = 438 W` fan power vs OCHRE's `0.365 × 312 × 3 = 342 W` — a 28% higher fan power. Note this defect is masked by BUG-3 when `FanPowerWatts` (absolute) is provided instead.

**Fix:** Align CFM/ton baseline. The physically correct value for a ducted central AC is 400 CFM/ton (RESNET HERS Addendum 82), not 312. If OCHRE parity is required, convert in the resolver using 312; if physical accuracy is preferred, document the deviation.

### Note on startup capacity degradation (UC-002 context)

The `Startup Capacity Degradation (-)` / `startup_cd` path is correctly wired:
- `resolve_hvac.rs:insert_startup_degradation` computes Cd using `efficiency_seer` or `cooling_efficiency`.
- `hvac_core.rs` reads `startup_cd` (priority), then `cooling_cd`, then `cd`.
- The Cd value is used in `StartupConfig.c_d` for the startup ramp model.

However, because BUG-1 causes the wrong EIR to be used at runtime, the actual energy consumption during the startup ramp is also wrong — the ramp shape is correct but scales against a wrong rated EIR.

### Biquadratic curve loading for single-speed AC

`resolve_hvac.rs` only calls `apply_multispeed_cooling_parameters` which returns early for `n_speeds <= 1`. Therefore, for single-speed AC, **no biquadratic curves are injected** from the defaults store; `load_curve_pair` in `ac_config.rs` falls back to the hardcoded constants:
- capacity: `[1.5509, -0.07505, 0.0031, 0.0024, -0.00005, -0.00043]`
- EIR: `[-0.30428, 0.11805, -0.00342, -0.00626, 0.0007, -0.00047]`

OCHRE also loads from a CSV file (`Biquadratic Air Conditioner.csv`) keyed by speed type. The hardcoded HARES values match OCHRE's single-speed coefficients (verified by coefficient sign pattern), so this is not a defect, but there is no mechanism to override them per efficiency tier via the resolver.

## Recommended Tests

1. **EIR from SEER round-trip test** (`crates/hares-equipment/tests/hvac_tests.rs` or new file):
   Build an `AirConditioner` config with `efficiency_seer = 14.0` (key that resolve_hvac.rs sets). Assert that `hvac.eir_by_stage[0]` equals `BTU_PER_HR_PER_W / 14.0` (≈ 0.2437). Repeat for `cooling_efficiency = 13.0` with `cooling_efficiency_units = "SEER"`. This pins BUG-1 against regression.

2. **SHR default parity test**:
   Build an `AirConditioner` config with no `shr` key. Assert `rated_shr == 0.75` (current HARES default). Separately document the OCHRE default (1.0). When the policy decision on BUG-2 is made, update this assertion.

3. **`fan_power_w` absorption test**:
   Build an `AirConditioner` config with `fan_power_w = 500.0` (absolute). Assert that `hvac.fan_power_w_per_m3_s` is not the default `0.365 * CFM_PER_M3_S` — i.e., that the override was applied. Currently this test will fail, pinning BUG-3.

4. **Low-SEER PLF coefficient injection test**:
   Build a resolve_hvac params map for a 12-SEER single-speed central AC. Assert `params["eir_plr_coefficients"]` equals `"[[0.8, 0.2, 0.0]]"`. Currently absent, pinning BUG-4.

5. **Cd round-trip with correct SEER for boundary conditions** (extend existing `c_d_cooling_single_speed_low_seer` / `high_seer` tests):
   Verify that `insert_startup_degradation` reads `efficiency_seer = 12.0` → Cd = 0.20 and `efficiency_seer = 14.0` → Cd = 0.07. These pass today but must be guarded against the key-name fix in BUG-1 inadvertently breaking resolver-side Cd computation (which correctly reads `efficiency_seer` already).

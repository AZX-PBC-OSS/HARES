## Background/Context

Scheduled loads (lighting, plug loads, refrigerator, ceiling fan, MELs) derive
annual energy from HPXML fields, then modulate by schedule fractions. Config includes
annual kWh, sensible/latent gain fractions, and schedule column mapping.

## Investigation Instructions

1. **Read OCHRE lighting parsing** — how is annual kWh derived from HPXML?
   - LED/CFL/incandescent fractions × reference energy × floor area
   - Interior, exterior, garage, basement lighting

2. **Read OCHRE plug load / MEL parsing.**

3. **Read HARES `resolve_loads.rs`:**
   - `derive_lighting_annual_kwh()` — same formula?
   - Plug loads / MELs — same derivation?
   - Ceiling fan — `n_fans * 3000 / efficiency * 10.5 * 365 / 1000`?
   - Refrigerator/freezer — pass-through or derived?

4. **Read HARES `scheduled_load.rs`:**
   - What config keys are consumed?
   - How is annual kWh converted to instantaneous power?
   - Are sensible/latent gain fractions correct?

5. **Build comparison table** per load type.

6. **Check the suspected bug:** `resolve_loads.rs` gas cooking range sets both
   `annual_electric_kwh` and `annual_gas_therms` to the same value — is this correct?

### Detailed Findings

#### F1 — SEVERITY HIGH: Lighting sensible gain fraction is wrong
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:616-617`, `crates/hares-equipment/src/scheduled_load.rs`

OCHRE `parse_lighting` returns `"Convective Gain Fraction (-)": 1` for all lighting (interior, exterior, garage, basement). HARES `default_gain_fractions` returns 0.70 for all lighting names. This causes a 30% systematic undercount of lighting heat gain to the thermal zone. For interior lighting this directly degrades the thermal energy balance, affecting HVAC load calculations.

Fix: Change `default_gain_fractions` for all lighting variants to `(1.00, 0.00)`.

#### F2 — SEVERITY HIGH: MELs ("other") sensible/latent gain fractions are wrong
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:615`

OCHRE `parse_mel` with `load_name=="other"` uses sensible_gain_default=0.855 and latent_gain_default=0.045. HARES `default_gain_fractions` returns (0.73, 0.02) for "MELs". These values belong to a different source (likely OS-HPXML defaults used by ResStock) and are the correct fractions when `FracSensible`/`FracLatent` override values are present in the extension — but OCHRE's fallback is 0.855/0.045, not 0.73/0.02. When HPXML lacks `FracSensible`, the wrong defaults are used.

Fix: Change MELs fallback to (0.855, 0.045). Note that when `FracSensible`/`FracLatent` are present in the extension, `parse_schedule_extension_params` already captures them as `frac_sensible`/`frac_latent`, overriding the defaults at `init_from_config` time, so the override path is correct.

#### F3 — SEVERITY HIGH: TV sensible/latent gain fractions are wrong
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:615`

OCHRE: TV ("TV other") → sensible=0, latent=0 (no heat gain to zone). HARES: TV → (0.73, 0.02). TVs in OCHRE are treated as not contributing internal gains (this may reflect that TV heat is small or goes to a non-modeled zone). The 73% assignment is incorrect and overestimates cooling loads.

Fix: Change TV fallback to (0.00, 0.00).

#### F4 — SEVERITY HIGH: Ceiling fan sensible gain fraction is wrong
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:618`

OCHRE: ceiling fan passes through `parse_mel("CeilingFan")` → load_name is "CeilingFan", which is neither "other" nor "fireplace" → sensible=0, latent=0. HARES assigns (1.00, 0.00). Ceiling fan power in OCHRE is treated as not producing sensible gains to the zone (the airflow effect is modeled separately via comfort delta, not heat gain). Adding 100% sensible gain is both physically wrong for the zone energy balance and inconsistent with OCHRE.

Fix: Change Ceiling Fan fallback to (0.00, 0.00).

#### F5 — SEVERITY MEDIUM: Freezer sensible gain fraction is wrong
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:614`

OCHRE `parse_freezer` returns `"Convective Gain Fraction (-)": 0` with a TODO comment about getting freezer location. HARES returns (1.00, 0.00). Freezers are typically located in garages or basements and OCHRE conservatively emits zero gain to avoid routing to the wrong zone. HARES incorrectly routes 100% to the conditioned zone.

Fix: Change Freezer fallback to (0.00, 0.00). This is also consistent with the OCHRE TODO which intends to add location-based routing — 0.00 is the conservative/correct default.

#### F6 — SEVERITY MEDIUM: Refrigerator location not read; gain fraction wrong for non-indoor units
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:74,81-92`

OCHRE computes `"Convective Gain Fraction (-)": annual_kwh_conditioned / annual_kwh` based on whether each refrigerator's `Location` field maps to "Indoor". A garage refrigerator contributes 0 sensible gain to the conditioned zone. HARES always uses the hardcoded default (1.00, 0.00) from `default_gain_fractions`. Additionally, HARES ignores the `AdjustedAnnualkWh` extension field (OCHRE uses this as the priority source over `RatedAnnualkWh`).

Fix: (a) Read the `Location` field from each Refrigerator node; if it is not "conditioned space" / "living space" / absent, set sensible_gain_fraction=0.0. (b) Check for `extension/AdjustedAnnualkWh` before `RatedAnnualkWh`.

#### F7 — SEVERITY MEDIUM: No default annual energy for Refrigerator or Freezer
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:74-92`

OCHRE defaults to `637 + 18*n_bedrooms` kWh for a primary refrigerator and `319.8` kWh for a freezer when `RatedAnnualkWh` is absent. HARES silently creates a load with no energy source (the `power_source` becomes `ScheduleSource::Constant(0.0)`), resulting in a zero-output load with no warning.

Fix: Add fallback energy derivation for Refrigerator (primary: 637+18×n_bedrooms kWh; secondary: 0 kWh) and Freezer (319.8 kWh), matching OCHRE hpxml.py:1393-1396 and 1417-1420.

#### F8 — SEVERITY MEDIUM: Cooking range does not read IsConvection from Oven node
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:272-273`

OCHRE reads `oven_dict.get("IsConvection", False)` from the sibling `Oven` element and applies `oven_ef = 0.95` for convection ovens. HARES hardcodes `oven_ef = 1.0` with a comment acknowledging this gap. For a gas range with a convection oven, this yields ~5% overestimate of both electric and gas annual energy.

Fix: Look up `details.path(&["Appliances", "Oven"])` (or a sibling lookup relative to the CookingRange node) and read `IsConvection`. Apply `oven_ef = 0.95` when true.

#### F9 — SEVERITY LOW: Gas dryer sensible fraction uses approximation
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:164`

OCHRE computes a BTU-weighted blend of electric and gas sensible fractions: `(1−frac_lost) × (0.90×elec_btu + 0.8894×gas_btu) / (elec_btu + gas_btu)`. HARES uses a fixed 0.89 factor approximating a typical 7%/93% electric/gas energy split. For CEF values that produce different splits, the two results diverge. The comment in code documents this correctly. Since ResStock typically produces the assumed split, this is low severity.

Fix is optional: implement the exact energy-weighted formula using the computed annual_kwh and annual_therm values, which are already available at the point where the fraction is calculated.

#### F10 — SEVERITY LOW: Label rate constants hardcoded (ClothesWasher, Dishwasher)
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:131-135, 244-246`

OCHRE reads `LabelGasRate`, `LabelElectricRate`, `LabelAnnualGasCost` from the HPXML node before falling back to defaults. HARES hardcodes the defaults without checking for per-appliance overrides. This matters if HPXML files contain non-default rates (ResStock sometimes varies them).

Fix: Read `child_f64(node, "LabelGasRate")`, `child_f64(node, "LabelElectricRate")`, `child_f64(node, "LabelAnnualGasCost")` from the appliance node and use those values if present.

#### F11 — SEVERITY LOW: Well pump and Gas Grill use 0.5 sensible fallback
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs` (indirectly via `scheduled_load.rs:257-263`)

OCHRE assigns sensible=0 for well pump and grill (outdoor equipment). HARES does not have these in `default_gain_fractions`, causing the `scheduled_load.rs` `init_from_config` fallback to emit a warning and use 0.5. The 0.5 is wrong for outdoor equipment; well pump and grill should emit 0 zone gain.

Fix: Add "Well Pump", "Gas Grill" to `default_gain_fractions` returning (0.00, 0.00).

#### F12 — SEVERITY LOW: Gas Fireplace latent fraction missing
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs` (default_gain_fractions not defined for Gas Fireplace)

OCHRE: sensible=0.5, latent=0.1 for fireplace. HARES: Gas Fireplace not in `default_gain_fractions`, so the 0.5 fallback coincidentally matches sensible but latent=0 instead of 0.1.

Fix: Add "Gas Fireplace" to `default_gain_fractions` returning (0.50, 0.10).

#### F13 — SEVERITY LOW: Gas Lighting sensible fraction wrong
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:617`

OCHRE: gas lighting (FuelLoad type "lighting") → sensible=0 (load_name=="lighting", else branch in parse_mel). HARES: "Gas Lighting" is grouped with electric lighting in `default_gain_fractions` and gets (0.70, 0.00). Gas outdoor lighting should have zero zone sensible gain.

Fix: Move "Gas Lighting" to its own match arm returning (0.00, 0.00).

#### F14 — INFO: Gas cooking range "same value for kWh and therms" — NOT a bug
**File:** `crates/hares-io/src/hpxml/resolve_loads.rs:279-282`

The ticket suspected a bug where `annual_electric_kwh` and `annual_gas_therms` are set to the same computed value `(22.6 + 2.7*n_bedrooms)`. This matches OCHRE exactly: the formula `22.6 + 2.7*n_bedrooms` is applied independently for both the electric parasitic kWh and the gas combustion therms (which happen to use the same base formula from ERI). The units are different (kWh vs therms), so the thermal magnitudes are not equal. This is correct behavior.

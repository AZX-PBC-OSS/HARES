## Background/Context

PV fields: `MaxPowerOutput` (W), `ArrayTilt` (degrees or pitch), `ArrayAzimuth`
(degrees), `SystemLossesFraction` (dimensionless). The tilt may be expressed as roof
pitch (rise/12 run) which needs conversion to degrees via `atan(pitch/12)`.

## Investigation Instructions

1. **Read `resolve_der.rs` PV parsing:**
   - `MaxPowerOutput` — W → kW? Or stored as W?
   - `ArrayTilt` — is pitch-to-degrees conversion applied? (`atan(pitch/12) * 180/π`)
   - `ArrayAzimuth` — compass degrees, any conversion needed?
   - `SystemLossesFraction` — stored as fraction (0–1)?
   - Inverter efficiency — how is it obtained?

2. **Read `array_config.rs`:**
   - What units does the PV model expect for tilt and azimuth?
   - Is there a double conversion risk?

3. **Compare with OCHRE:**
   - `pitch2deg()` in `units.py` — `atan(pitch/12)` in degrees.
   - What unit does OCHRE store tilt in?

4. **Write findings** with conversion table.


## Findings

### Q1 — MaxPowerOutput: W → kW conversion

**Correct.** `resolve_der.rs:39-41` reads `MaxPowerOutput`, divides by 1000.0, and
stores the result as `capacity_kw`. The HPXML spec defines `MaxPowerOutput` in watts (W)
for `PVSystem`. The equipment model (`array_config.rs`, `PvArray::capacity_kw`) works in
kW throughout. No unit error.

### Q2 — ArrayTilt: pitch-to-degrees conversion

**Not applicable to PV; OCHRE's `pitch2deg()` is for roof surfaces, not PV arrays.**

The HPXML 4.x spec defines `<ArrayTilt>` on `<PVSystem>` as degrees (0 = horizontal,
90 = vertical). The fixture files confirm this: every `<ArrayTilt>` value (e.g. `20.0`)
is already in degrees. `resolve_der.rs:43-44` reads it verbatim and stores it as
`tilt_deg`. No pitch conversion is needed or attempted, which is correct.

OCHRE's `pitch2deg()` (`vendors/OCHRE/ochre/utils/units.py:25-27`,
`math.atan(pitch/12)` → degrees) is used only for roof boundary tilts (`hpxml.py:169`),
not for `PVSystem/ArrayTilt`. HARES is correct to skip pitch conversion here.

### Q3 — Two tilt parse paths: resolve_der.rs vs building.rs:751

**BUG: Dead field that validates the wrong HPXML element.**

Two independent code paths parse tilt from the HPXML document:

1. `resolve_der.rs:43` reads `PVSystem/ArrayTilt` → stored as equipment param
   `tilt_deg` → flows into `PvArray::tilt_deg` via `array_config.rs:72-73`.
2. `building.rs:751` calls `find_descendant_f64(details, "Tilt", ValueKind::Raw)` →
   stored as `Building::pv_tilt_deg` → consumed **only** by `validation.rs:273`.

The second path is broken in two ways:

- `find_descendant_f64(details, "Tilt", ...)` is a first-descendant search across the
  entire `BuildingDetails` subtree. The HPXML element is `<ArrayTilt>`, not `<Tilt>`.
  Using the bare name `"Tilt"` risks matching unrelated elements (e.g. roof `<Tilt>`
  elements from boundary data) and will miss `<ArrayTilt>` entirely in well-formed
  HPXML 4.x documents.
- Even if the match were correct, `Building::pv_tilt_deg` is never forwarded to the
  equipment spec. It is read during validation but cannot influence the actual simulation
  tilt angle.

The validation at `validation.rs:273` therefore validates a field that is either wrong
(matched from a non-PV element) or absent (silently returns `None` when `<ArrayTilt>`
is present), giving no assurance the equipment tilt is in range.

### Q4 — ArrayAzimuth: compass degrees, any conversion needed?

**No conversion needed; conventions are consistent.**

`resolve_der.rs:46-47` reads `ArrayAzimuth` verbatim and stores it as `azimuth_deg`.
HPXML defines `<ArrayAzimuth>` in compass degrees (north=0, east=90, south=180,
west=270). HARES physics (`hares-physics/src/pv_sizing.rs:23`) uses the same north=0
convention. No conversion is required.

Note: OCHRE's SAM wrapper (`Equipment/PV.py:58`) applies `(azimuth + 180) % 360` to
convert from OCHRE's internal south=0 convention to SAM's south=180 convention. HARES
does not use SAM and uses north=0 throughout, so no such adjustment is needed.

### Q5 — SystemLossesFraction: AC vs DC interpretation

**Applied to DC only, consistent with PVWatts.**

`pv/mod.rs:272` applies `system_losses_fraction` directly to `dc_power_kw` before
multiplying by `inverter_efficiency`. This is correct PVWatts v8 behavior: the HPXML
`SystemLossesFraction` represents DC-side losses (wiring, mismatch, soiling, shading,
nameplate, etc.) and does not include inverter conversion losses. The post-factor
`inverter_efficiency` is then applied to the derated DC value to produce AC output.
No bug here.

### Q6 — Tilt range: array_config allows [0,180] but validation.rs enforces [0,90]

**Defect: inconsistent bounds and semantically wrong upper limit in validation.**

- `array_config.rs:157` accepts `tilt_deg` in `[0, 180]`.
- `validation.rs:274` rejects anything outside `[0, 90]` as an error, and warns
  above 60°.

A 90° tilt (vertical wall-mounted panel) is physically valid and used in practice.
Tilts above 90° are physically meaningful (downward-facing panel) but produce no
useful power and are not supported by HPXML. The correct enforcement is:

- `array_config.rs` should tighten its limit to `[0, 90]` to match HPXML semantics
  (HPXML defines `ArrayTilt` as 0=horizontal, 90=vertical).
- `validation.rs` should match that bound and apply its check against the equipment
  spec's `tilt_deg` value parsed from `<ArrayTilt>`, not from the broken
  `Building::pv_tilt_deg` field.

As-is, a `tilt_deg` of 120° (downward-facing) will pass equipment validation but fail
the building-level validation on a field that may not even have matched the correct XML
element.

### Q7 — inverter_efficiency default

**Correct; default is 0.96, matching PVWatts v8.**

`pv/mod.rs:56`: `DEFAULT_INVERTER_EFFICIENCY = 0.96`.
`pv/mod.rs:379-382`: loaded from `KEY_INVERTER_EFFICIENCY` with fallback to 0.96.
`resolve_der.rs:56-63`: inverter efficiency is obtained from the linked `<Inverter>`
element via `AttachedToInverter/@idref`. If absent, no key is inserted into `params`
and the model falls back to the 0.96 default. This is correct and matches the PVWatts
default referenced in OCHRE `Equipment/PV.py:28`.

### Q8 — ModuleType case sensitivity

**BUG: HPXML uses lowercase values; HARES matches PascalCase only.**

Fixture files and the HPXML spec use lowercase: `standard`, `premium`, `thin film`.
`array_config.rs:22-27` (`ModuleType::from_str`) matches `"Premium"` and `"ThinFilm"`
(PascalCase, no space). Any HPXML document passes lowercase `"standard"` or `"premium"`
which silently falls through to `ModuleType::Standard`. A `premium` array will use the
standard module gamma coefficient (-0.0047/°C) instead of the premium coefficient
(-0.0035/°C), producing incorrect temperature derating for premium modules. The
`thin film` HPXML value (`"thin film"`, with a space) can never match `"ThinFilm"`.

## Summary of Defects

| Severity | Location | Issue |
|----------|----------|-------|
| HIGH | `building.rs:751`, `validation.rs:273` | `pv_tilt_deg` matches wrong XML element (`Tilt` instead of `ArrayTilt`); field is dead (never reaches equipment spec); validation is unreliable |
| MEDIUM | `array_config.rs:157`, `validation.rs:274` | Tilt upper bound inconsistency: equipment allows `[0,180]`, validation errors on `>90`; both should be `[0,90]` per HPXML |
| MEDIUM | `array_config.rs:22-27` | `ModuleType::from_str` matches PascalCase but HPXML emits lowercase; `premium` and `thin film` are silently treated as `Standard` |
| INFO | — | No pitch conversion is needed or incorrectly applied for PV (OCHRE `pitch2deg` is for roofs only) |
| INFO | — | `MaxPowerOutput` W→kW correct; `SystemLossesFraction` applied to DC before inverter correct; azimuth north=0 consistent; inverter default 0.96 correct |

## Recommended Tests

All tests should be deterministic and placed in `crates/hares-io/tests/` or
`crates/hares-equipment/src/pv/mod.rs` as appropriate.

1. **`test_pv_resolve_der_capacity_kw`** (`hares-io`): parse a minimal HPXML with
   `<MaxPowerOutput>4000.0</MaxPowerOutput>` and assert the resulting equipment spec
   has `capacity_kw == 4.0`. Confirms W→kW conversion is not regressed.

2. **`test_pv_resolve_der_tilt_passthrough`** (`hares-io`): parse HPXML with
   `<ArrayTilt>30.0</ArrayTilt>` and assert `tilt_deg == 30.0` in the spec. Catches
   any accidental pitch conversion being added.

3. **`test_pv_resolve_der_module_type_lowercase`** (`hares-io`): parse HPXML with
   `<ModuleType>premium</ModuleType>` and assert the resulting `module_type` is
   `ModuleType::Premium`, not `Standard`. Currently expected to fail until the
   case-sensitivity bug is fixed.

4. **`test_pv_resolve_der_thin_film_lowercase`** (`hares-io`): parse HPXML with
   `<ModuleType>thin film</ModuleType>` and assert `ModuleType::ThinFilm`. Currently
   expected to fail.

5. **`test_pv_building_pv_tilt_deg_is_from_array_tilt`** (`hares-io`): parse an HPXML
   document containing a `<PVSystem><ArrayTilt>25.0</ArrayTilt></PVSystem>` and assert
   `building.pv_tilt_deg == Some(25.0)`. Currently expected to fail because
   `find_descendant_f64(details, "Tilt", ...)` will not match `<ArrayTilt>`. Confirms
   the field is populated from the correct element after the fix.

6. **`test_pv_array_config_rejects_tilt_above_90`** (`hares-equipment`): construct a
   `PvArray` with `tilt_deg = 100.0` and assert `Err`. Currently expected to pass
   through because `array_config.rs` accepts `[0,180]`. This test documents the
   intended bound after tightening.

7. **`test_pv_system_losses_applied_to_dc_before_inverter`** (`hares-equipment`):
   step a PV with known irradiance, `system_losses_fraction=0.1`,
   `inverter_efficiency=0.9`, temperature at STC. Assert AC power equals
   `capacity * irradiance_fraction * (1 - 0.1) * 0.9`. Confirms DC-side application.

8. **`test_pv_inverter_efficiency_default_fallback`** (`hares-io` or
   `hares-equipment`): parse HPXML with no `<Inverter>` element. Assert the
   resulting PV equipment uses `inverter_efficiency == 0.96`.

## Background/Context

Foundation zones (basements, crawlspaces) have unique thermal behavior: ground coupling
on walls and floor, air exchange with conditioned space above, and thermal mass from
concrete. The RC network representation must capture all three.

## Findings

### FINDING 1 — BUG: Foundation zone volume uses conditioned-zone ceiling height instead of actual foundation wall height

**Severity: High**

**File:** `crates/hares-io/src/hpxml/building.rs:677`

HARES computes foundation zone volume as `floor_area_m2 * default_height_m` where
`default_height_m` is the conditioned zone ceiling height (typically 2.4 m). OCHRE
derives foundation volume as `first_floor_area * foundation_wall_height`
(`vendors/OCHRE/ochre/utils/hpxml.py:679-684`), where the wall height comes from the
parsed `FoundationWall/Height` element.

A crawlspace wall is typically 0.6–1.2 m tall; an unfinished basement might be 2.4 m.
Using ceiling height (2.4 m) inflates the crawlspace zone capacitance and ACH-based
infiltration volumetric flow rate by 2–4×. For a 100 m² crawlspace at 2 ACH the
sensible loss rate scales linearly with volume, producing a direct proportional error in
foundation zone heat balance.

HARES does parse `FoundationWall/Height` and `FoundationWall/DepthBelowGrade` in
`extract_foundation_wall_insulation` (`building.rs:1096`) for area-scaling purposes, but
this parsed height is not stored on the zone for volume computation. The `Zone` struct
receives only `floor_area_m2` and `volume_m3 = None` at parse time
(`building.rs:1432-1441`); volume is filled in later using `default_height_m`
(`building.rs:677-679`).

**Fix required:** Parse the `FoundationWall/Height` element when building the foundation
zone and store it as `volume_m3 = floor_area_m2 * foundation_wall_height` before the
volume fill-in pass, mirroring OCHRE's approach.

### FINDING 2 — BUG: Foundation zone SLA ventilation path ignored — always falls back to ACH

**Severity: High**

**File:** `crates/hares-core/src/dwelling/solver_builder.rs:844-852`

OCHRE supports three infiltration methods for the foundation zone: `ACHnatural`, `SLA`,
and a vented-crawlspace default of 2 ACH (`hpxml.py:695-724`). When the HPXML
`VentilationRate/UnitofMeasure` is `SLA`, OCHRE converts to ELA:
```python
fnd_ela = sla_value * floor_area_cm2
# then uses InfiltrationMethod: ELA with zone-height-dependent coefficients
```

HARES building.rs correctly parses `ventilation_sla` from the HPXML
(`building.rs:1430`). However `solver_builder.rs:844-852` for
`ZoneType::Foundation` only reads `ventilation_ach`; it never checks
`ventilation_sla`, and has no `InfiltrationMethod::Ela` path for the foundation zone.
When HPXML specifies SLA, the parsed `ventilation_sla` is silently discarded and the
code falls back to `InfiltrationMethod::Ach { ach: 2.0 }` for a vented crawlspace. For
most ResStock HPXML inputs (which use SLA) this causes an incorrect ventilation rate.

This is a distinct issue from Finding 1 — even if the volume were correct, the wrong
infiltration method is selected.

**Fix required:** Mirror the OCHRE SLA→ELA conversion: when `bz.ventilation_sla` is
`Some(sla)`, convert to ELA using `ela_m2 = sla * floor_area_m2` (in SI), then apply
`calculate_ela_coefficients` logic to set stack/wind coefficients keyed to foundation
height. Use `InfiltrationMethod::Ela` for this case.

### FINDING 3 — ACCEPTABLE DIFFERENCE: Slab and foundation wall are correctly connected to ground temperature

**File:** `crates/hares-io/src/envelope_lut.rs:295`, `crates/hares-core/src/dwelling/conversions.rs:238`

The default exterior zone for `BoundaryType::Slab` and `BoundaryType::FoundationWall`
is `ZoneType::Ground` in `envelope_lut.rs:295`. The `resolve_exterior` function in
`conversions.rs:238` maps `ZoneType::Ground` to `ExteriorTarget::Ground`. The thermal
solver's input-vector filling loop (`thermal_solver/mod.rs:499-502`) writes
`env.weather.ground_temp_c` into all `ground_temp_input_indices` B-matrix columns each
timestep.

Ground temperature is derived from the Kusuda-Achenbach formula (environment.rs:305).
Slab and foundation-wall boundaries therefore drive heat flow through the actual
undisturbed ground temperature, not outdoor air. This is correct physics.

---

### FINDING 4 — ACCEPTABLE DIFFERENCE: Slab and foundation walls are modeled with thermal mass (RC nodes)

**File:** `crates/hares-envelope/src/boundary_rc.rs:322-365`

When the OCHRE envelope LUT provides precomputed layers, each layer becomes a
capacitor node in the RC graph (`build_precomputed_boundary`). Foundation slabs and
walls look up the LUT via boundary names `"Floor"`, `"Foundation Floor"`, or
`"Foundation Wall"` / crawlspace/basement variants (resolved in `envelope_lut.rs`).
When the LUT is present and hits, RC nodes with concrete-mass capacitance are created.
When the LUT misses and only assembly R-value is available, the fallback path
(`boundary_rc.rs:468-496`) creates a lumped resistance with zero capacitance.

This means thermal mass representation is LUT-dependent. For HPXML buildings with a
full LUT hit, concrete mass is modeled. For purely HPXML-assembly-R configurations or
LUT misses, concrete slab and wall mass is absent. This is functionally the same
trade-off as OCHRE (which also uses the same LUT), so parity is maintained, but it
should be documented that foundation mass is only present when the LUT covers the
boundary type.

### FINDING 5 — ACCEPTABLE DIFFERENCE: HARES correctly distinguishes vented crawlspace, unvented crawlspace/basement, and conditioned basement

**Files:** `crates/hares-io/src/hpxml/building.rs:1424-1428`, `crates/hares-core/src/dwelling/solver_builder.rs:844-852`, `crates/hares-io/src/hpxml/resolve_hvac.rs:192-220`

- Vented/unvented crawlspace is determined from `<FoundationType><Crawlspace><Vented>`
  or the tag name (`building.rs:1424-1428`).
- `foundation_name` in the building model is set to `"Crawlspace"`, `"Unfinished
  Basement"`, or `"Finished Basement"` (`building.rs:467-488`).
- The ASHRAE 152 duct-loss string for Foundation zones uses all three distinctions plus
  insulation state (`resolve_hvac.rs:192-220`).
- For `SlabOnGrade` and `Ambient`, `foundation_name` is `None` and no Foundation zone
  is created, matching OCHRE (`hpxml.py:286-287`).

The vented/unvented distinction is correctly propagated. The only gap is that the
vented-crawlspace infiltration may be wrong due to Finding 2 (SLA path missing).

### FINDING 6 — GAP: No inter-zone air exchange between foundation and conditioned zone

**Severity: Medium**

**File:** `crates/hares-envelope/src/thermal_solver/infiltration.rs:62-68`, `crates/hares-core/src/dwelling/solver_builder.rs:844-860`

The infiltration model always uses `t_out` (outdoor dry-bulb) as the driving
temperature for infiltration sensible load (`infiltration.rs:71`). All zones —
including the foundation zone — exchange air with outdoor air. There is no explicit
inter-zone air exchange term coupling the foundation zone to the conditioned zone.

For conditioned (finished) basements this is a structural gap: a finished basement
receives 20% of HVAC capacity in OCHRE (`resolve_hvac.rs:228-235`), but any air
exchange between the conditioned basement and the conditioned zone above it is modeled
purely through conduction across the floor boundary (the floor between them has an RC
path), not through advective air exchange. OCHRE also does not implement an explicit
inter-zone convective air-exchange term between the conditioned zone and finished
basement beyond the RC conduction coupling; it relies on the floor boundary RC for
coupling.

This is therefore an acceptable simplification shared with OCHRE for the common case.
However if a future model requires explicit inter-zone air mixing (e.g., when duct
leakage is located in the foundation zone), this would need a dedicated coupling term.

### FINDING 7 — GAP: Foundation zone INTERIOR_MASS_MULTIPLIER may over-estimate capacitance

**Severity: Low**

**File:** `crates/hares-envelope/src/boundary_rc.rs:225-237`

`derive_zone_capacitances` applies `INTERIOR_MASS_MULTIPLIER = 7.0` uniformly to all
zones including Foundation. The 7× multiplier was calibrated for the conditioned zone
to account for furniture, partition walls, and floor coverings. A crawlspace or
unfinished basement has minimal furniture and interior mass; using a 7× multiplier
overestimates the thermal capacitance of the foundation zone air node by a significant
factor. OCHRE does add "Foundation Furniture" internal mass (`hpxml.py:629`), but this
is a separate boundary contributing to the RC graph rather than inflating the zone air
node capacitance.

The practical impact is that the foundation zone temperature will respond more sluggishly
than reality, smoothing out diurnal temperature swings in the foundation. For well-coupled
basements the error is minor (dominant pathway is conduction through walls/floor), but for
vented crawlspaces where infiltration and conduction are both significant the inflated
capacitance slows down the hourly temperature dynamics.

**Fix required:** Either skip `INTERIOR_MASS_MULTIPLIER` for Foundation zones in
`derive_zone_capacitances`, or pass a per-zone multiplier vector. A value of 1.0–2.0
would be more physically appropriate for a crawlspace; 3.0–4.0 for an unfinished
basement with some furniture.

## Recommended Tests

### Test 1 — Foundation zone volume uses wall height (Finding 1)

Parse a crawlspace HPXML where `FoundationWall/Height` is 1.0 m and floor area is
100 m². Assert that the resulting foundation zone `volume_m3` is approximately 100.0 m³,
not 240.0 m² (2.4 m ceiling height).

```rust
// crates/hares-io/tests/comprehensive_tests.rs or building.rs unit tests
// Build XML with FoundationWall Height=3.28ft (~1.0m), FloorArea=1076ft²(~100m²)
// Assert building.zones[foundation_idx].volume_m3 ≈ 100.0 (±1.0)
```

### Test 2 — SLA ventilation resolves to ELA infiltration method (Finding 2)

Parse an HPXML with `VentilationRate/UnitofMeasure=SLA` and `Value=0.0001` for a
100 m² crawlspace. Assert that the resulting `InfiltrationMethod` for the Foundation
zone is `Ela { ela_m2, stack_coeff, wind_coeff }`, not `Ach { ach: 2.0 }`. The
`ela_m2` should equal `0.0001 * 100.0 * 1e4 = 100.0 cm²` (= `0.01 m²`).

This requires a solver_builder integration test — parse the HPXML, build the solver
config, inspect `thermal_cfg.infiltration` for the foundation zone.

### Test 3 — Vented crawlspace default ACH when no VentilationRate (Finding 2 / Finding 5)

When `vented = true` and no `VentilationRate` element is present, assert that the
foundation zone receives `InfiltrationMethod::Ach { ach: 2.0 }`. This verifies the
OCHRE-default fallback is present for vented crawlspaces.

### Test 4 — Ground temperature drives slab boundaries (Finding 3 — verify regression safety)

Build a single-zone RC model with a slab boundary and a ground boundary, step one
timestep with `ground_temp_c = 10.0` and `outdoor_temp_c = -10.0`. Assert that the
heat flux into the zone via the slab is positive (warm ground, cold outdoor) and uses
the ground temperature, not outdoor.

This test should already pass given current code, but documents the contract.

### Test 5 — Foundation zone INTERIOR_MASS_MULTIPLIER investigation (Finding 7)

Add a diagnostic test that builds a foundation zone with a known floor area and asserts
the zone air capacitance is at most 2× the dry-air-only value, rather than 7×. This
will initially fail, documenting the known gap until Finding 7 is addressed.

### Test 6 — Parity test: crawlspace building annual heating/cooling energy

Run a full annual simulation on a building with a vented crawlspace (use existing parity
fixtures) and compare foundation zone temperature trajectory against OCHRE output. The
MAE should be ≤ 1°C. Differences larger than this indicate the volume and/or SLA bugs
are affecting the simulation.

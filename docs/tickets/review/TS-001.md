## Background/Context

The thermal solver's initial state vector (node temperatures) must represent a
physically plausible starting condition. OCHRE runs a "warmup" period or uses
steady-state initialization. Wrong initial conditions cause large transients in the
first hours of simulation, distorting results.

## Findings

### Finding 1 — ACCEPTABLE DIFFERENCE: initialize_steady_state() correctly solves dT/dt = 0

`crates/hares-envelope/src/thermal_solver/initialization.rs:12`

HARES performs a genuine analytical steady-state solve: the RC network is solved with
zone air temperatures pinned as boundary conditions. The algorithm:

1. Builds input vector `u` from outdoor temp, ground temp, and indoor temp (no HVAC
   heat, no solar — reasonable for dT/dt=0 at steady state).
2. Partitions the state matrix: zone air nodes are removed from the free-variable set
   and their coupling is moved to the RHS.
3. Solves the reduced system analytically:
   - Continuous path: `-A_c_reduced * x = B_c * u + A_c[:,j] * T_j`
   - Discrete path: `(I - N_reduced) * x = B_eff * u + N[:,j] * T_j`
4. Re-inserts the fixed zone temperatures into the result.

This is functionally equivalent to OCHRE's `initialize_state()` at
`vendors/OCHRE/ochre/Models/Envelope.py:1026`:
```python
x = -np.linalg.inv(A).dot(B).dot(u)
```
OCHRE pins only T_LIV (living zone) and zeroes energy-flow states. HARES generalizes
to an arbitrary number of multi-zone pinned nodes using the same continuous-matrix
solve path. Both approaches are correct for dT/dt=0.

The singular-matrix fallback (returning uniform `indoor_temp_c`) is safe and tested.

### Finding 2 — GAP: Foundation zones initialized to outdoor_temp_c, not ground_temp_c

`crates/hares-core/src/environment.rs:738-741`

```rust
let temp = match zone.zone_type {
    ZoneType::Conditioned => default_temp,
    _ => outdoor_temp_c,      // Foundation, Attic, Garage all use outdoor temp
};
```

Foundation/crawlspace zones are thermally coupled to the ground, not the outdoor air.
Starting them at `outdoor_temp_c` instead of `ground_temp_c` introduces an initial
condition error whose magnitude equals `|outdoor_temp_c - ground_temp_c|`. In cold
climates in January this can easily be 15–25°C.

OCHRE's `initialize_state()` correctly passes `ground_temp` as a separate boundary
condition input (`T_GND`) into the steady-state solve
(`vendors/OCHRE/ochre/Models/Envelope.py:1017-1020`). The steady-state result for the
foundation-adjacent wall nodes and floor nodes will be driven toward ground temp, not
outdoor temp.

HARES's `initialize_steady_state()` does receive ground temp via
`wiring.ground_temp_input_indices` and places it in the input vector `u`
(`initialization.rs:28-32`), so the interior wall/floor nodes adjacent to ground will
converge correctly *if* the zone air node for the foundation zone is initialized to a
physically reasonable value. The current code initializes that zone air node to
`outdoor_temp_c`, which is the wrong starting point.

The fix is to detect `ZoneType::Foundation` and initialize to `ground_temp_c` from
the weather series initial value. `ZoneType::Attic` and `ZoneType::Garage` correctly
use outdoor temp.

### Finding 3 — ACCEPTABLE DIFFERENCE: OCHRE adds a random ±deadband/2 jitter to indoor_temp; HARES does not

`vendors/OCHRE/ochre/Models/Envelope.py:1002-1008`

OCHRE adds `np.random.uniform(low=-deadband/2, high=deadband/2)` to the initial
indoor setpoint temperature. This jitter (typically ±0.5°C) introduces non-determinism.
HARES omits this intentionally: deterministic tests require reproducible initial conditions.
This is a correct decision consistent with `feedback_deterministic_tests.md`.

### Finding 4 — ACCEPTABLE DIFFERENCE: OCHRE setpoint selection reads from the live schedule; HARES reads from the HPXML building setpoint arrays

`crates/hares-core/src/environment.rs:762-788`

HARES reads `building.heating_weekday_setpoints_c[start_hour]` and
`building.cooling_weekday_setpoints_c[start_hour]` at initialization time.
OCHRE reads `initial_schedule["HVAC Heating Setpoint (C)"]` from the first schedule row.
Both produce the same result for typical simulations starting at hour 0. For a simulation
starting mid-day this could differ by the magnitude of the schedule setpoint variation,
but this is a minor edge case and not a correctness defect.

The 12°C outdoor-temperature threshold for heating vs cooling mode selection matches
OCHRE exactly (`vendors/OCHRE/ochre/Models/Envelope.py:1006`).

### Finding 5 — ACCEPTABLE DIFFERENCE: initialization_duration parameter is fully implemented and working

`crates/hares-core/src/dwelling/mod.rs:1032-1040, 1750-1762`
`crates/hares-python/src/py_dwelling.rs:1577-1596`
`crates/hares-python/src/py_config.rs:454-463`

The `initialization_duration` parameter is wired end-to-end:

1. Python layer (`py_dwelling.rs:1577`) extracts it from `**kwargs` as seconds and
   stores it as `std::time::Duration` in `DwellingConfig`.
2. `DwellingConfig::from_config` path also exposes it via `py_config.rs:454`.
3. `Dwelling::from_preparsed` (`dwelling/mod.rs:1032`) calls `run_warmup()` after
   `auto_register_actors()` if the value is `Some`.
4. `run_warmup()` steps the simulation silently for the specified duration, then
   `simulation_results.steps.clear()` discards warmup output, and the clock is reset.
5. The `DwellingConfig.initialization_duration` property is exposed in the `.pyi` stub
   (`_hares.pyi:1404`).

The earlier report that it was "silently dropped from Python" appears to have been
fixed prior to this audit. The only test that covers this path tests the round-trip of
the config value (`tests/python/test_py_config.py:127`), not that the warmup steps
actually execute and are discarded. See Recommended Tests below.

OCHRE's equivalent is `initialization_time` passed to `Simulator.__init__()`, which
calls `self.initialize()` after construction. The semantics are identical.

### Finding 6 — IMPROVEMENT: Discrete vs continuous path consistency in initialize_steady_state

`crates/hares-envelope/src/thermal_solver/initialization.rs:77-123`

The code selects the continuous-time path (`-A_c⁻¹ * B_c * u`) when `a_c` and `b_c`
are both present (the `from_continuous` construction path), and the discrete path
(`(I - N)⁻¹ * B_eff * u`) otherwise. This is correct. However, the comment at
`state_space.rs:239-244` contains a debug assertion that flags if the discrete branch
is reached when `a_c` is present — this is a good guard but it only fires in debug
builds. In production, a model constructed via `from_continuous` that somehow lost its
`a_c` field (e.g., via serialization round-trip if that ever becomes a path) would
silently use the discrete approximation, which may not produce the same result. This
is a low-risk theoretical concern, not a current defect.

### Finding 7 — IMPROVEMENT: zone_fixes dedup_by_key may silently drop a valid pinning if two zones share the same state index

`crates/hares-envelope/src/thermal_solver/initialization.rs:59-60`

```rust
zone_fixes.sort_by(|a, b| b.0.cmp(&a.0));
zone_fixes.dedup_by_key(|f| f.0);
```

`dedup_by_key` on a sorted-descending vector keeps the *first* (highest-valued)
element when duplicates are adjacent. In the normal case each zone maps to a distinct
state index, so this is safe. If two different zones were incorrectly assigned the same
state index by the wiring builder, one zone's pinning temperature would silently win
over the other's. This should instead be a `debug_assert!` or at minimum a
`tracing::warn!` so the wiring mismatch is surfaced rather than silently resolved.

### Ordering Verification (Review Note answered)

`crates/hares-envelope/src/thermal_solver/mod.rs:136`
`crates/hares-core/src/environment.rs:716`

Zone temperatures are set in `initial_zones()` (environment.rs), which is called
before `ThermalSolver::new()`. `ThermalSolver::new()` calls `initialize_steady_state()`
with the already-populated `env.zones`. The ordering is correct.

### ground_temp_c NaN/zero at init (Review Note answered)

`crates/hares-envelope/src/thermal_solver/initialization.rs:28-32`

If `env.weather.ground_temp_c` is NaN at init time, it is placed directly into `u`
and propagates through the matrix solve, producing NaN node temperatures. There is no
guard here. In practice, the EPW parser (`hares-io/src/epw.rs`) is expected to provide
valid ground temperatures; however a defensive `is_finite()` check and fallback (e.g.,
to outdoor temp) would be appropriate. This is low risk given the EPW parser but worth
noting.

## Recommended Tests

### T1 — Foundation zone initial temperature uses ground_temp_c (regression blocker)

Once Finding 2 is fixed, add a unit test to `crates/hares-core/src/environment.rs`
tests that calls `initial_zones()` with a `Building` containing a `ZoneType::Foundation`
zone and asserts the returned zone's `temperature_c` equals `ground_temp_c`, not
`outdoor_temp_c`. Test with `outdoor_temp_c = -10.0` and `ground_temp_c = 8.0` to
catch any regression where the two are conflated.

### T2 — initialization_duration warmup executes and output is discarded

Add an integration test (Rust or Python) that:
1. Builds a `DwellingConfig` with `initialization_duration = Some(3600)` (1 hour).
2. Constructs the `Dwelling` and verifies the first output timestep's `current_time`
   is equal to `start_time` (not `start_time + 1 hour`), confirming the clock was
   reset.
3. Simulates one step and checks that temperatures are plausible (finite, within
   10–35°C for a conditioned zone).
The existing `test_initialization_duration_round_trips` only tests the config struct;
it does not verify runtime behavior.

### T3 — Steady-state solve with ground input for foundation-adjacent floors

Add a unit test in `initialization.rs` with a 3-node system:
- Node 0: conditioned zone air (pinned)
- Node 1: floor mass node (free)
- Node 2: ground boundary input only

Assert that at steady state the floor mass node converges to a weighted average of
conditioned zone and ground temperature, not outdoor temperature.

### T4 — Singular continuous A_c matrix fallback in initialize_steady_state

Add a test that constructs a `from_continuous` model with a singular `A_c` matrix and
verifies the fallback returns a vector of `indoor_temp_c` (not a panic or NaN).

### T5 — Duplicate zone state index produces a warning (Finding 7)

Once the `debug_assert!` or `tracing::warn!` is added for duplicate state indices in
`zone_fixes`, add a test that provides two zones with the same state index and verifies
the diagnostic fires.

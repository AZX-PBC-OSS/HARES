## Background/Context

Users pass `**kwargs` to `Dwelling.from_hpxml()` to override equipment parameters.
These kwargs must flow through Python→Rust config → HPXML resolver → equipment init.
FX-014 found that `initialization_duration` was silently dropped. There may be
other kwargs that don't arrive at their target.

---

## Findings

### F1 — CRITICAL: `overrides` and `resample_overrides` are hardcoded `None` in `build_config`

**File:** `crates/hares-python/src/py_dwelling.rs:1605–1615`

`build_config` constructs the final `DwellingConfig` with:

```rust
Ok(DwellingConfig {
    ...
    overrides: None,          // line 1611 — always None
    ...
    resample_overrides: None, // line 1614 — always None
})
```

Neither field is ever populated from `kwargs`. `DwellingConfig` (in `py_config.rs`) correctly
parses and validates both fields, but `build_config` is a parallel implementation that has never
been updated to handle them. This means:

```python
Dwelling.from_hpxml(hpxml, sched, weather, overrides={"hvac": {"capacity_w": 5000}})
```

silently produces a misconfigured dwelling with no error and no warning. The `overrides` value
reaches `from_config` → `resolve_equipment` in `dwelling/mod.rs:849`, but because `build_config`
hardcodes `None`, it never gets there via the Python path.

This was previously identified in PS-001:F1 but remains unresolved. It is confirmed present in
the current diff — `build_config` is unchanged.

**Fix:** Extract `overrides` and `resample_overrides` from `kwargs` inside `build_config` using
the same parsing logic as `PyDwellingConfig::new` in `py_config.rs`, or (better) refactor
`build_config` to delegate to `PyDwellingConfig::new` + `to_dwelling_config()`.

---

### F2 — HIGH: `build_config` does not reject unknown kwargs

**File:** `crates/hares-python/src/py_dwelling.rs:1452–1616`

`build_config` reads individual keys via `k.get_item(key)` and silently ignores every other key
in `kwargs`. A caller typo such as `duraiton_s=86400` or `Overrides={...}` is silently dropped
with no error. The validated code path in `PyDwellingConfig::new` also has no unknown-key check.

**Fix:** After extracting all known keys, assert that `kwargs` contains no remaining unrecognised
keys and raise `PyValueError` for any unknown key.

---

### F3 — HIGH: Parallel implementations of the same logic will diverge

**Files:** `crates/hares-python/src/py_dwelling.rs:1452`, `crates/hares-python/src/py_config.rs:391`

`PyDwellingConfig::new` (in `py_config.rs`) and `build_config` (in `py_dwelling.rs`) are two
independent implementations of Python-kwargs → `DwellingConfig`. They handle the same fields but
with different validation coverage:

| Feature | `PyDwellingConfig::new` | `build_config` |
|---|---|---|
| `overrides` | parsed and validated | hardcoded `None` |
| `resample_overrides` | parsed with key/method validation | hardcoded `None` |
| `initialization_duration < 0` check | yes | yes |
| `setpoint_deadband_c` finiteness | yes | no |
| `duration % time_res == 0` check | yes | no |
| `output_verbosity > 8` check | yes | no |
| `config: SimulationConfig` object kwarg | yes | yes |

Any future field added to one path must be manually duplicated in the other. This is a
maintainability defect that will produce silent divergence over time.

**Fix:** `build_config` should construct a `PyDwellingConfig` internally and call
`to_dwelling_config()`, eliminating the duplication entirely.

---

### F4 — MEDIUM: `.pyi` stub retains `**kwargs: Any` on `from_hpxml`

**File:** `python/ochre_next/_hares.pyi:1645`

The stub enumerates all accepted flat kwargs explicitly (lines 1632–1644) but then appends
`**kwargs: Any`. This means static type checkers (mypy/pyright) accept any additional keyword
with any value, providing no protection against F2. The `**kwargs: Any` escape hatch is redundant
if F2 is resolved with unknown-key rejection, and actively harmful before that.

Missing from the stub's `from_hpxml` signature: `initialization_duration`, `resample_overrides`,
`overrides`, `config`. These are accepted at runtime (for `initialization_duration`, `config`)
or silently ignored (for `overrides`, `resample_overrides`), but none appear in the stub.

**Fix:** Remove `**kwargs: Any`. Add `initialization_duration`, `resample_overrides`, `overrides`,
and `config` to the explicit signature. Stub should match runtime exactly.

---

### F5 — LOW: `setpoint_deadband_c` and `duration % time_res` validation missing in `build_config`

**File:** `crates/hares-python/src/py_dwelling.rs:1545–1568`

`PyDwellingConfig::new` validates `setpoint_deadband_c` (must be finite and >= 0) and that
`duration % time_res == 0`. `build_config` extracts both fields but performs neither check.
A caller passing `setpoint_deadband_c=float('nan')` via `from_hpxml` kwargs will propagate
`NaN` into `SimulationConfig` with no error.

**Fix:** Apply the same guards present in `PyDwellingConfig::new` (easiest via delegating to it,
as described in F3).

---

### F6 — LOW: `overrides` getter round-trip uses JSON serialise→deserialise

**File:** `crates/hares-python/src/py_config.rs:527–542`

The `PyDwellingConfig::overrides` getter converts each value to a JSON string then calls
`json.loads()` to convert back to a Python object. This is unnecessarily expensive for a
property getter and risks lossy round-trips for values that are already `serde_json::Value`
(e.g., `f64` precision). A direct `json_value_to_py` helper would be cleaner and faster.

This is a pre-existing issue not introduced in this diff, but it will be exercised at runtime
once F1 is fixed.

## Recommended Tests

1. **`overrides_propagate_through_from_hpxml`** — Pass a known-valid override (e.g. a heating
   capacity override for the furnace in `cz2a_gas_furnace_ac_res_wh`) through `from_hpxml`'s
   `overrides` kwarg. Assert that the resulting equipment's parameter matches the override value,
   not the HPXML-derived default. Currently this will fail (F1 confirmed broken).

2. **`resample_overrides_propagate_through_from_hpxml`** — Pass `resample_overrides={"ghi": "zoh"}`
   to `from_hpxml`. Assert no exception and that the dwelling initialises. Currently silently
   ignored (F1).

3. **`unknown_kwarg_raises_value_error`** — Pass `duraiton_s=86400` to `from_hpxml`. Assert
   `PyValueError` is raised. Currently silently ignored (F2).

4. **`setpoint_deadband_nan_raises`** — Pass `setpoint_deadband_c=float('nan')` to `from_hpxml`.
   Assert `PyValueError`. Currently passes through to `SimulationConfig` unvalidated (F5).

5. **`duration_not_divisible_raises`** — Pass `duration_s=86401, time_res_s=60` to `from_hpxml`.
   Assert `PyValueError`. Currently silently accepted (F5).

6. **`from_hpxml_stub_kwargs_match_runtime`** — Static analysis test (pyright/mypy) asserting
   that `_hares.pyi` `from_hpxml` signature has no `**kwargs: Any` and enumerates all accepted
   kwargs (F4).

## Background/Context

Tankless (instantaneous) water heaters have no tank (no standby losses), high capacity,
and modulate to match demand. Config is simpler but includes parasitic power (standby
electronics).

## Findings

### Registry name

HARES registers only `"Tankless Water Heater"` in `tankless.rs:441-446`. The resolver at
`resolve_water_heater.rs:340` produces `"Gas Tankless Water Heater"` for gas instantaneous
units. There is no registration for `"Gas Tankless Water Heater"` anywhere. This is the
AR-005 finding; it remains unresolved. A gas instantaneous unit from HPXML will fail to
resolve to any equipment instance at runtime.

---

### F-1 — FuelType key name mismatch (Severity: HIGH)

`build_spec` (hares-io/src/hpxml/equipment.rs:86-89) inserts `"fuel_type"` (lowercase) into
`parameters`:

```rust
parameters.insert("fuel_type".to_string(), Value::String(format!("{fuel_type:?}")));
```

`TanklessWH::init` reads it via `config.get_str("FuelType")` (PascalCase, line 171). The
`HashMap` lookup is case-sensitive, so `"fuel_type"` is never found under `"FuelType"`.

`parse_tankless_fuel_type` returns `FuelType::Electric` when the key is absent (line 448-450):

```rust
fn parse_tankless_fuel_type(raw: Option<&str>) -> FuelType {
    parse_fuel_type(raw).unwrap_or(FuelType::Electric)
}
```

Consequence: every gas tankless unit instantiated from HPXML will be treated as electric.
It will emit electrical consumption, not gas consumption; the gas port will never be
declared; and the parasitic electric draw path will never execute.

This is the same root cause identified in AR-002. The fix must be applied in either
`build_spec` (normalize key to `"FuelType"`) or in `tankless.rs::init` (also look up
`"fuel_type"`).

---

### F-2 — Efficiency key mismatch: resolver inserts `"energy_factor"`, init never finds it (Severity: HIGH)

The resolver inserts `"energy_factor"` (lowercase) for the raw EF value at
`resolve_water_heater.rs:65`. `TanklessWH::init` at line 185-190 looks up keys in order:
`["EnergyFactor", "UniformEnergyFactor", "efficiency_factor"]`. None of these match
`"energy_factor"` or `"uniform_energy_factor"` (also lowercase from the resolver at line 68).

Result: `self.efficiency_factor` falls back to `DEFAULT_EF = 0.9` for every HPXML-sourced
tankless unit, regardless of what EF was specified. A unit with EF=0.82 or EF=0.95 gets the
same 0.9 default.

---

### F-3 — Performance adjustment default discrepancy (Severity: MEDIUM)

OCHRE (`hpxml.py:1057-1061`) uses two different defaults:
- When only UEF is provided (EF absent): default `PerformanceAdjustment = 0.94`
- When EF is provided: default `PerformanceAdjustment = 0.92`

HARES resolver (`resolve_water_heater.rs:139`) uses a single default of `0.92` for all
cases:

```rust
let perf_adj = child_f64(wh, "PerformanceAdjustment").unwrap_or(0.92);
```

When a UEF-only HPXML tankless record is parsed without an explicit `PerformanceAdjustment`,
HARES applies 0.92 rather than OCHRE's 0.94, causing a 2.2% underestimate in effective
efficiency.

Additionally, due to F-2, even the correctly computed `performance_adjustment` value is
applied to `DEFAULT_EF = 0.9` rather than the actual EF, so the combined error is
significant.

---

### F-4 — Rated capacity key mismatch: `"heating_capacity_w"` never read (Severity: HIGH)

The resolver inserts `"heating_capacity_w"` (`resolve_water_heater.rs:71`). `TanklessWH::init`
looks for `["max_thermal_power_w", "RatedCapacityW", "capacity_w"]` (line 196-201). None
match `"heating_capacity_w"`.

Result: rated thermal capacity always falls back to `DEFAULT_MAX_THERMAL_POWER_W = 20_000 W`.
For any unit with a specified `HeatingCapacity` different from 20 kW (common for smaller
residential units, e.g. 10-18 kW), the model silently uses the wrong capacity for every
demand-limit calculation.

---

### F-5 — Gas parasitic power not computed or forwarded (Severity: HIGH)

OCHRE (`hpxml.py:1188-1190`) computes bedroom-count-dependent parasitic power for gas
instantaneous units:

```python
on_time_frac = [0.0269, 0.0333, 0.0397, 0.0462, 0.0529][n_beds - 1]
wh["Parasitic Power (W)"] = 5 + 60 * on_time_frac
```

This produces values in the range 6.61–8.17 W for 1–5 bedroom homes.

HARES never computes or inserts `"parasitic_power_w"` in the resolver. The equipment
falls back to `DEFAULT_GAS_PARASITIC_POWER_W = 7.38 W` (corresponds to 3 bedrooms).
The bedroom count is already available in the resolver via `parse_avg_water_draw_l_per_day`,
but is scoped to that function and not propagated. For homes that are not 3 bedrooms, the
parasitic draw (and thus annual standby electricity) is incorrect.

Additionally, due to F-1, the gas fuel path in the equipment is never activated even if the
correct parasitic were computed.

---

### F-6 — `"Gas Tankless Water Heater"` registry name has no registered handler (Severity: CRITICAL)

`canonical_water_heater_name` returns `"Gas Tankless Water Heater"` for gas instantaneous
units (`resolve_water_heater.rs:340`). `register_with_registry` in `tankless.rs:441-446`
only registers `"Tankless Water Heater"`. There is no second `registry.register` call for
`"Gas Tankless Water Heater"`.

When the actor registry tries to instantiate a gas tankless unit, the lookup will fail
(unknown equipment name). This is the AR-005 finding reproduced in context. The two options
are: (a) register the same `TanklessWH` constructor under both names, or (b) collapse gas
and electric tankless to a single canonical name and rely on F-1's fix to set fuel type
correctly.

---

### F-7 — `equipment_type` field hardcoded to `"Tankless Water Heater"` for gas units (Severity: LOW)

At `tankless.rs:89`, the descriptor is initialized with:

```rust
equipment_type: Cow::Borrowed("Tankless Water Heater"),
```

This is never updated after `init` re-reads `fuel_type`. A gas unit will self-describe as
`"Tankless Water Heater"` rather than `"Gas Tankless Water Heater"`. This is a telemetry
fidelity issue; downstream parity checks or output formatters that key on `equipment_type`
to distinguish fuel will misclassify gas units.

## Recommended Tests

### T-1 — Gas tankless registry lookup does not panic

```
cargo test -p hares-equipment -- water_heater::tankless::tests::gas_tankless_registry_lookup
```

Construct an `EquipmentRegistry`, call `register_with_registry`, then attempt to create a
`"Gas Tankless Water Heater"` config. Assert the lookup succeeds. Currently this test would
fail (finding F-6).

### T-2 — Gas fuel type is preserved after HPXML round-trip

Supply a gas instantaneous HPXML fixture with `<FuelType>natural gas</FuelType>`. Parse
with `resolve_water_heaters`. Assert the resulting `EquipmentSpec::fuel_type` is
`FuelType::Gas` and that the `parameters` map contains a key readable as `FuelType::Gas` by
`parse_tankless_fuel_type`. Instantiate the equipment; assert `descriptor.fuel == FuelType::Gas`
and that the fuel port is present. Currently fails at the instantiation step (F-1).

### T-3 — EF is forwarded from resolver to equipment

Parse a tankless HPXML record with `<EnergyFactor>0.82</EnergyFactor>`. Instantiate the
equipment. Assert `efficiency_factor` equals `0.82 × 0.92 = 0.7544` (EF × default perf_adj).
Currently the equipment uses `0.9 × 0.92 = 0.828` due to F-2.

### T-4 — UEF-only uses 0.94 performance adjustment default

Parse a tankless HPXML record with `<UniformEnergyFactor>0.87</UniformEnergyFactor>` and no
`<EnergyFactor>`. Assert `efficiency_factor ≈ 0.87 × 0.94 = 0.8178`. Currently produces
`0.9 × 0.92 = 0.828` due to both F-2 and F-3.

### T-5 — HeatingCapacity forwarded correctly

Parse a tankless HPXML record with `<HeatingCapacity>68243</HeatingCapacity>` (20 kW in
Btu/hr). Assert `rated_thermal_power_w ≈ 20_000 W`. Then use a non-default value such as
40 000 Btu/hr (≈11.72 kW) and assert the equipment reflects that value. Currently always
returns 20 000 W due to F-4.

### T-6 — Gas parasitic power scaled by bedroom count

After F-5 is fixed, for a 1-bedroom gas tankless home: assert `parasitic_power_w ≈ 6.61 W`
(5 + 60 × 0.0269). For a 5-bedroom home: assert ≈ 8.17 W (5 + 60 × 0.0529). Assert that
the equipment emits electricity equal to the computed parasitic, not a gas consumption, even
when the burner is off.

### T-7 — Electric tankless has no fuel port; gas tankless has both fuel and electrical ports

Parse electric and gas instantaneous HPXML records. Assert:
- Electric: `ports` contains exactly one electrical port and one DHW fluid port; no fuel port.
- Gas: `ports` contains one fuel port, one electrical port, one DHW fluid port.

### T-8 — No tank UA is computed for instantaneous type

Verify `ua_w_per_k` key is absent from `parameters` for `"instantaneous water heater"` type.
This is already tested in `water_heater_ua.rs::instantaneous_returns_none` but should also
be tested at the resolver integration level.

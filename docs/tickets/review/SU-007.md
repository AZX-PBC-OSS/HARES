## Background/Context

Each call to `Dwelling::step()` dispatches to `run_timestep()`. The project memory
(`feedback_hot_loop_minimal.md`) forbids sorts and allocations in the hot loop and
requires preprocessing at init with pre-allocated buffers. This ticket audits the
actual hot path for every per-step heap allocation and ranks the top-5 hotspots.

The codebase already has substantial mitigation in place: `record_scratch`,
`timestamp_buf`, `zone_temp_scratch`, `actor_dispatch_buf`, the
`EnvironmentManager::update_in_place` swap-based pattern for schedule and mains
payloads, and the `ZoneColumnCaches` pre-resolution at init. Violations found below
are genuine regressions against the stated policy.

---

## Hotspot 1 — `check_invariants`: three `Vec::new()` + N `format!` per step in debug/CI builds

**Severity: HIGH — fires on every step in debug builds and in CI**

`crates/hares-core/src/dwelling/mod.rs:2378-2468`:

```rust
let mut conditioned_temps: Vec<f64> = Vec::new();
let mut unconditioned_temps: Vec<f64> = Vec::new();
// ... push per zone ...
let mut tank_temps_c: Vec<f64> = Vec::new();
// ... push per water heater node ...
let mut infiltration_latent_by_zone: Vec<(ZoneId, f64)> = Vec::new();
// ... push from payload chunks ...
```

All three Vecs are allocated from scratch every timestep. `check_invariants` is
active under `cfg(any(debug_assertions, feature = "check_invariants"))` — this
includes every CI run, every `cargo test`, and every developer build. At a typical
5-zone, 6-node-tank dwelling this is 5+ small allocations per step, millions of
calls over a year-long simulation.

Additionally, inside the invariant loop at line 2402:

```rust
let key = format!("tank_node_{i}_c");
```

This `format!` fires N times per step (once per tank node, typically 12), producing
a new `String` heap allocation each iteration solely to perform a HashMap lookup.
Should use `tk::` constants or a pre-built static key slice.

**Fix:** Move `conditioned_temps`, `unconditioned_temps`, `tank_temps_c`, and
`infiltration_latent_by_zone` to scratch fields on `Dwelling` (pre-allocated at
init, cleared and refilled each step). Replace the `format!("tank_node_{i}_c")`
key generation with a pre-built `Vec<String>` of node keys, sized at init from the
water heater descriptor's node count.

## Hotspot 2 — `StepResult::zone_temperatures_c`: double-clone every step

**Severity: HIGH — two `Vec<(ZoneId, f64)>` clones on every step**

`crates/hares-core/src/dwelling/mod.rs:2131`:

```rust
zone_temperatures_c: self.zone_temp_scratch.clone(),
```

`self.zone_temp_scratch` is a `Vec<(ZoneId, f64)>` pre-allocated at init and
updated in-place each step (lines 2111-2120). It is cloned here to construct
`StepResult`, then the entire `StepResult` is cloned again at line 2152:

```rust
self.simulation_results.steps.push(step_result.clone());
```

This means `zone_temperatures_c` is heap-allocated twice per step in addition to
the original scratch buffer:
1. The `.clone()` at 2131 to build `StepResult` to return to the caller.
2. The `.clone()` of `StepResult` at 2152 for `simulation_results`.

For a 8760-step annual simulation with 3 zones, this is ~17,520 small Vec
allocations for temperatures alone.

**Fix:** Either:
- Eliminate `simulation_results.steps` entirely and have callers accumulate results
  themselves (the fleet runner already does this externally), or
- Construct `StepResult` once and move it into `simulation_results.steps`, then
  return a second copy only if the caller needs it (or return a reference/index).

The secondary clone at line 2152 also doubles allocation cost for every other
`StepResult` field. Eliminating this clone is the highest-leverage single change.

## Hotspot 3 — `equipment_telemetry` fill: per-step `String` key clone made inevitable by `clear()` in `update_in_place`

**Severity: MEDIUM — N `String` key allocations per step when actors are active**

`crates/hares-core/src/dwelling/mod.rs:1830-1841`:

```rust
if !self.actors.is_empty() {
    for eq in &self.equipment {
        let desc = eq.descriptor();
        let telemetry = eq.telemetry();
        if let Some(existing) = self.latest_env.equipment_telemetry.get_mut(&desc.name) {
            existing.clone_from(telemetry);  // reuse allocation — fast path
        } else {
            self.latest_env
                .equipment_telemetry
                .insert(desc.name.clone(), telemetry.clone());  // slow path — allocates
        }
    }
}
```

The `clone_from` fast path correctly reuses the existing `Telemetry` map. However,
`EnvironmentManager::update_in_place` calls `state.equipment_telemetry.clear()` at
`environment.rs:561` before this block runs. `HashMap::clear()` drops all entries
and their owned `String` keys. On the next step, all equipment names must be
re-inserted via `desc.name.clone()`, making the fast path unreachable every step.
For a 5-equipment dwelling, that is 5 `String` allocations + 5 `Telemetry` clones
every step.

**Fix:** Remove the `state.equipment_telemetry.clear()` call from
`update_in_place`. The equipment set is fixed per step; stale keys cannot accumulate.
The `clone_from` branch then handles all updates in-place with no allocations. If
a clean-slate guarantee is needed for safety, do a targeted clear only when equipment
changes (the `add_equipment` / `remove_equipment` paths already exist).

## Hotspot 4 — Solver `DomainUpdate` returns: four `Vec` allocations per step

**Severity: MEDIUM — four Vec-bearing `DomainUpdate` structs allocated per step**

`crates/hares-core/src/dwelling/mod.rs:2032-2084`:

```rust
let thermal_update = self.thermal_solver.resolve(&self.ports, &self.latest_env, dt);
// ...
let humidity_update = self.humidity_solver.resolve(...);
let electrical_update = self.electrical_solver.resolve(...);
let fluid_update = self.fluid_solver.resolve(...);
// ...
self.latest_env.upsert_domain(thermal_update);
self.latest_env.upsert_domain(humidity_update);
self.latest_env.upsert_domain(electrical_update);
self.latest_env.upsert_domain(fluid_update);
```

`DomainUpdate` (`crates/hares-types/src/domain_solver.rs:15`):

```rust
pub struct DomainUpdate {
    pub domain_id: DomainId,
    pub zone_temperatures_c: Vec<(ZoneId, f64)>,
    pub custom_payload: Option<Vec<f64>>,
}
```

Each `resolve()` call constructs and returns a new `DomainUpdate` with a freshly
allocated `zone_temperatures_c` (and often a `custom_payload`). `upsert_domain`
replaces the old slot — dropping the old Vec and taking ownership of the new one.
The old Vec's allocation is not recovered.

The `environment.rs` swap-based pattern (lines 507-528) already recovers capacity
for the schedule and mains payloads. No equivalent recovery exists for the four
solver domains.

**Fix:** Extend the swap pattern: have `upsert_domain` return the replaced
`DomainUpdate` so its inner Vecs can be handed back to the solver as scratch
buffers for the next step. Alternatively, change `DomainSolver::resolve` to accept
a `&mut DomainUpdate` to fill in-place (avoiding the return allocation entirely).
For `custom_domain_solvers` (user-defined, line 2082), the in-place approach is
cleanest.

## Hotspot 5 — `per_actor_timing` String allocation under `actor_profiling`; `DispatchTarget` clone in `drain_tiers`

**Severity: LOW (profiling feature) / LOW (production dispatch)**

### 5a: `per_actor_timing` — `to_string()` per actor per step under `actor_profiling`

`crates/hares-core/src/dwelling/mod.rs:1859-1860`:

```rust
self.per_actor_timing
    .push((actor.name().to_string(), start.elapsed()));
```

`actor.name()` returns `&str`; `.to_string()` allocates a `String` per actor per
step when the `actor_profiling` feature is enabled. For a 3-actor dwelling at
5-minute steps over a year: 105,120 `String` allocations solely for actor names.

**Fix:** Pre-allocate actor name strings once at init into a `Vec<String>` on
`Dwelling`; index into it at profiling time. `per_actor_timing` then stores
`(usize, StdDuration)` with name resolved from the pre-built slice only at
reporting time.

### 5b: `DispatchTarget::clone()` in `drain_tiers`

`crates/hares-core/src/dwelling/mod.rs:321`:

```rust
self.seen_targets.push((request.target.clone(), tier_idx));
```

`DispatchTarget::ByName(Arc<str>)` clone is a cheap atomic increment with no heap
allocation. `ByEndUse(EndUse)` is `Copy`. This is technically a clone per dispatched
signal per step, but at 1-4 signals per step it is not a material cost. Flagged for
completeness only.

## Additional Finding — `DomainUpdate::zone_temperatures_c: Vec::new()` in non-swap paths

**Severity: NOTE — zero-cost, but context is worth confirming**

`crates/hares-core/src/environment.rs:532,537` use `zone_temperatures_c: Vec::new()`
inside the swap-based custom_domains construction. `Vec::new()` in Rust allocates no
heap memory (zero-capacity Vec is a dangling-but-valid pointer). These are harmless.
Similar `Vec::new()` literals in `hares-equipment/src/water_heater/mod.rs:412,419,656`
and `event_load.rs:1531` are all init-time or cold-path. No hot-path concern.

## Recommended Tests

1. Add a test under `#[cfg(feature = "profiling")]` that runs a 10-step simulation
   and asserts `profiling.hot_path_alloc_violations == 0`. The `hot_path_alloc_counter`
   infrastructure in `synthetic.rs` is already in place; no test currently exercises it.
   This would catch regressions before they land.

2. Add a benchmark (`benches/`) for `Dwelling::step()` with a representative
   HPWH+HVAC+Battery+PV dwelling. Without a benchmark, allocation regressions are
   invisible until someone profiles manually.

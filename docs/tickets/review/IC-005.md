## Background/Context

OCHRE's HPWH `solve_ideal_capacity()` runs the model with HP at 100%, determines if
HP alone satisfies demand. If not, it computes the ER supplement needed. This HP/ER
split decision is critical for energy efficiency — the HP has COP>1 while ER is COP=1.

## Investigation Instructions

1. **Read OCHRE `HeatPumpWaterHeater.solve_ideal_capacity()`:**
   - How does it determine HP-only vs HP+ER?
   - What is the priority order (HP first, then ER)?
   - How is the HP duty cycle computed?

2. **Read HARES `heat_pump_wh.rs`:**
   - Is there ideal capacity mode?
   - How is the HP/ER split decided?

3. **Check PARITY-013** — was HP/ER duty cycle splitting implemented?

4. **Document** the decision logic comparison.


## Findings

### F1 — CRITICAL: ER backup trigger is a single configurable offset, not OCHRE's two-node thresholds

**Severity:** High (behavioral divergence from OCHRE reference)

**OCHRE** (`WaterHeater.py:595-599`) uses two independent hardcoded thresholds to decide between
HP-only and HP+ER modes:

```python
# ER upper element activates when upper-node temp drops below setpoint - 13°C
if t_upper < self.setpoint_temp - 13:
    return "Upper On"
# ER lower element stays on if lower-node temp is below setpoint - 15°C
elif self.mode in ["Upper On", "Lower On"] and t_lower < self.setpoint_temp - 15:
    return "Lower On"
```

These thresholds are:
- Applied to **separate physical nodes** (`t_upper_idx` = node 2 for 12-node tank, `t_lower_idx` = node 9).
- Hardcoded at **13°C** (upper element trigger) and **15°C** (lower element continued-on hysteresis).
- Independent of the HP deadband; they represent severe heat deficit requiring ER assist.

**HARES** (`heat_pump_wh.rs:628-629`) collapses this to a single scalar test against
the composite 3/4+1/4 control temperature:

```rust
let below_backup_threshold = self.control_temp_c()
    <= self.effective_setpoint_c() - self.backup_enable_offset_c;
```

`backup_enable_offset_c` defaults to 8.0°C (`DEFAULT_BACKUP_ENABLE_OFFSET_C` in
`hpwh_compressor.rs:23`). This means HARES triggers ER substantially earlier than OCHRE (8°C
vs 13°C deficit on the upper node). Additionally HARES has no separate lower-element continued-on
condition equivalent to the 15°C threshold.

Practical impact: HARES will activate the 4.5 kW backup element more aggressively, driving up
energy consumption and suppressing compressor runtime compared to OCHRE. In HP-only mode this
is moot, but in the default `MutuallyExclusive` mode it directly changes the HP/ER split.

**Files:** `heat_pump_wh.rs:628-629`, `hpwh_compressor.rs:23`

### F2 — MODERATE: COP/capacity curve uses volume-weighted tank average, not condenser-node weighted temperature

**Severity:** Medium (physics inaccuracy)

**OCHRE** (`WaterHeater.py:632`):

```python
t_lower = np.dot(self.hp_nodes, self.model.states)  # use node connected to condenser
```

`hp_nodes` for a 12-node tank is `[0, 0, 0, 0, 0, 5, 10, 15, 20, 25, 30, 5] / 110` — a
condenser-weighted temperature emphasizing the lower half of the tank where the condenser
coil sits. This is the physically correct input: compressor performance degrades with the
temperature of the water it is actually heating, not the bulk average.

**HARES** (`heat_pump_wh.rs:698-699`):

```rust
let tank_avg_temp_c =
    weighted_average_tank_temp(self.tank.node_temps(), self.tank.node_volumes_m3());
```

This is a volume-weighted average across all nodes. For a stratified tank the top nodes are
significantly hotter than the bottom half, so `tank_avg_temp_c` is systematically higher than
OCHRE's `t_lower`. A higher tank temperature input to the COP curve suppresses computed COP
(the `x2` coefficient in the default COP curve is -0.01113, so 1°C higher input → ~1.1% lower
COP). The error grows as stratification increases.

Note: the same `tank_avg_temp_c` value is also used for the capacity curve, which will similarly
underestimate capacity when the tank is stratified.

**Files:** `heat_pump_wh.rs:698-703`

### F3 — MODERATE: `compressor_power_w` semantics differ from OCHRE — HARES treats it as rated capacity, OCHRE as rated input power

**Severity:** Medium (silent unit/semantics mismatch)

**OCHRE** (`WaterHeater.py:453-456`):

```python
if "HPWH Capacity (W)" in kwargs:
    self.hp_capacity_nominal = kwargs["HPWH Capacity (W)"]  # max heating capacity, in W
else:
    hp_power_nominal = kwargs.get("HPWH Power (W)", 500)  # in W
    self.hp_capacity_nominal = hp_power_nominal * self.cop_nominal  # in W
```

OCHRE's primary internal quantity is `hp_capacity_nominal` — the **delivered heat** in watts.
Electrical input is `delivered / cop`. The default for `hp_power_nominal` is 500 W input,
giving `hp_capacity_nominal = 500 × COP` ≈ 1250–2000 W delivered.

**HARES** (`hpwh_compressor.rs:21`, `heat_pump_wh.rs:710-714`):

```rust
pub(super) const DEFAULT_COMPRESSOR_POWER_W: f64 = 1_200.0;
// ...
let capacity_actual_w = self.compressor_power_w * cap_mult;
let compressor_power_w = if self.compressor_on {
    (capacity_actual_w / cop) * hp_duty   // electrical draw
```

HARES calls the field `compressor_power_w` but uses it as if it is the **rated delivered
capacity** (multiplied by `cap_mult` to get `capacity_actual_w`, then divided by COP for
electrical draw). The comment on line 710 confirms this: "capacity_actual_w = rated compressor
input * cap_mult (rated capacity delivered)." The comment is internally contradictory: it says
"rated compressor input" but describes the result as "rated capacity delivered." The 1,200 W
default is closer to delivered capacity than to compressor input power, suggesting the field
stores capacity but is named as input power.

This is a naming/documentation defect. If an integrator passes `CompressorPower` from HPXML
thinking it is electrical input power, HARES will misinterpret it as rated delivered capacity
and compute electrical draw as `(1200 * cap_mult) / COP` — which is correct only coincidentally
if COP ≈ 1. The field should be renamed to `rated_capacity_w` or the semantics documented
unambiguously.

**Files:** `hpwh_compressor.rs:21`, `heat_pump_wh.rs:710-714`

### F4 — LOW: No ideal-capacity (fractional duty cycle) mode; HARES uses on/off hysteresis only

**Severity:** Low (feature gap, documented)

OCHRE implements `solve_ideal_capacity()` (`WaterHeater.py:528-581`) — a predictive mode that
runs the tank model one step ahead with HP at 100%, determines whether HP alone reaches setpoint,
and if not, solves for the exact HP duty cycle (0–1) plus a partial ER supplement. This yields
sub-timestep duty cycles and avoids overshoot.

HARES has no equivalent. It uses bang-bang thermostat control with fixed duty-cycle overrides
from external signals. The `duty_cycle`, `hp_duty_cycle`, and `er_duty_cycle` fields allow
fractional operation, but the internal thermostat always makes a binary on/off decision. The
ideal-capacity path in OCHRE is activated by `use_ideal_capacity=True` (the main simulation
default); HARES never enters this path.

Impact depends on timestep size. At 1-minute resolution the on/off model closely approximates
ideal capacity. At longer timesteps (≥5 min) energy over- and under-delivery become significant.

**Files:** `heat_pump_wh.rs` (entire `update_control` method — no ideal-capacity branch)

### F5 — LOW: PARITY-013 reference in investigation instructions is incorrect

PARITY-013 is "Framing factor / parallel-path U-value" (wall assembly physics), unrelated to
HPWH HP/ER split. The investigation instructions contained a stale or copy-paste reference.
No PARITY ticket for HP/ER ideal-capacity splitting was found.

### F6 — LOW: `hp_only_mode` disables ER but does not prevent ER activation under ModeOverride

**Severity:** Low (minor control-path gap)

`hp_only_mode` is checked when `mode_override` is `None` (`heat_pump_wh.rs:601`). However, the
`BackupElement` and `HeatingER` mode-override branches (`heat_pump_wh.rs:613-615`) check
`backup_allowed` but that flag is only set based on `hp_only_mode`:

```rust
Some(OperatingMode::BackupElement) | Some(OperatingMode::HeatingER) => {
    self.compressor_on = false;
    self.backup_on = call_for_heat && backup_allowed;
}
```

This is correct — `hp_only_mode` does block ER even under override. However the
`HeatingHPAndER` override branch (`heat_pump_wh.rs:617-619`) also correctly gates on
`backup_allowed`. So this is not a defect but warrants a note: external controllers should not
send `HeatingHPAndER` overrides to HP-only units; the signal will silently drop ER activation.
No documentation or error is emitted.

**Files:** `heat_pump_wh.rs:617-619`

## Recommended Tests

All tests should be added to `crates/hares-equipment/tests/water_heater_tests.rs` or a
dedicated `hpwh_control_tests.rs`.

### T1 — ER backup threshold triggers at correct tank temperature deficit

Construct a 6-node HPWH. Set setpoint 60°C. Cool all nodes to 60 − 7°C = 53°C (above
backup_enable_offset of 8°C; should be HP-only). Step once and assert `backup_on == false` and
`compressor_on == true`. Then cool all nodes to 60 − 9°C = 51°C and assert `backup_on == true`.
Also verify OCHRE-equivalent: at 13°C deficit on upper node with `backup_enable_offset_c = 13.0`
configured, ER fires exactly at threshold and not before.

### T2 — COP/capacity curve uses condenser-weighted temperature, not volume-weighted average

Configure a 12-node HPWH. Set the lower 6 nodes to 30°C and upper 6 nodes to 60°C. Compute
expected `t_lower` as the OCHRE condenser dot-product (should be ~34°C for the 12-node weights)
versus a volume average (~45°C). Assert that the COP emitted in telemetry matches the value from
the COP biquadratic evaluated at `t_lower_condenser`, not `t_avg`. This test documents the
current divergence (and should be updated when F2 is fixed to assert the corrected value).

### T3 — `compressor_power_w` field semantics: rated capacity, not electrical input

Configure a HPWH with `compressor_power_w = 1200.0` and COP = 3.0. After one step with compressor
on and duty cycle = 1.0, assert `delivered_hp_w ≈ 1200.0` (field = capacity) and
`compressor_power_w_electrical ≈ 400.0` via `COMPRESSOR_POWER_W` telemetry. This pins the
current semantics so a rename cannot silently change behavior.

### T4 — HP-only mode: ER never activates regardless of tank deficit

Configure `hp_only_mode = true`. Cool tank to 10°C below setpoint. Step and assert
`backup_on == false` in all states: no override, HP override, ER override,
HPAndER override. The ER override result should remain `backup_on == false`.

### T5 — Ambient lockout forces ER-only (no compressor) when outside bounds

Set ambient zone temperature to 3°C (below `min_ambient_temp_c = 7.22°C`). Cool tank below
setpoint. Step and assert `compressor_on == false` and `backup_on == true`. Repeat at 50°C
ambient (above `max_ambient_temp_c = 43.33°C`).

### T6 — Min-on-time: compressor does not turn off before minimum elapsed time

Configure `min_on_time_s = 600.0`. Start compressor on. Satisfy call-for-heat to false after
1 step (30 s). Assert compressor remains on. Advance 570 more seconds and assert compressor
turns off on the next step after `compressor_on_since_s >= 600.0`.

### T7 — Simultaneous mode: both HP and ER run when tank is severely cold

Configure `element_hp_control_mode = Simultaneous`. Cool tank to 20°C below setpoint. Step
and assert both `compressor_on == true` and `backup_on == true`. Assert combined electrical
draw ≈ `compressor_power_w/cop + backup_element_power_w + fan_power_w`.

### T8 — DR GridEmergency sheds all load immediately

Apply `DemandResponse { level: GridEmergency, duration_s: None }`. Cool tank below setpoint.
Step and assert both `compressor_on == false` and `backup_on == false` and
`electric_power_w ≈ 0`.

### T9 — Max-tank-temp cutout fires when any node exceeds limit

Set `max_tank_temp_c = 80.0`. Pre-heat one node to 81°C via `StratifiedTank` state injection.
Step and assert `OperatingMode::Off` and zero electrical draw even when tank average is below
setpoint.

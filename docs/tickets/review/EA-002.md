## Background/Context

Backup generators are less common but important for grid outage simulation and
resilience analysis. This ticket traces the full behavior comparison.

---

## Findings

All 47 unit tests in `generator.rs` pass. The physics core is sound, but there
is one correctness defect, one coverage gap, and several minor observations.

---

### F-001 — CRITICAL: fuel type hardcoded to Gas; non-gas generators silently
misbehave

**Severity: High**
**Files:** `crates/hares-equipment/src/generator.rs:378,667`
           `crates/hares-io/src/hpxml/resolve_der.rs:143,162-163`

`Generator::new()` unconditionally sets `fuel: FuelType::Gas` in the descriptor
(line 378) and also hardcodes `FuelType::Gas` in the `PortContribution::Fuel`
written during `step()` (line 667).

`resolve_generators` in `resolve_der.rs` correctly parses the HPXML `<FuelType>`
element via `parse_fuel()` (line 143) and passes the result as `fuel_type` to
`build_spec()`, which stores it as the string `"fuel_type"` in
`EquipmentSpec.parameters` (via `build_spec`, `equipment.rs:86-89`). However,
`Generator::new()` never reads the `"fuel_type"` key from config. The value is
thrown away silently.

The practical consequence: a propane-fuelled standby generator (common in
residential resilience scenarios) will report `FuelType::Gas` consumption in
telemetry and accumulate to the wrong fuel bucket in output metrics. The
OCHRE reference has the same structural limitation (`is_gas` is a class-level
boolean, not a runtime field), but HARES explicitly supports `FuelType::Propane`
and `FuelType::Oil` in the type system, so silently ignoring the config value
is a regression against the platform's own capabilities.

The fix pattern exists in `hvac/furnace.rs`, which calls `parse_fuel_type()` from
`hvac/helpers.rs` to read the config value and stores it as a struct field, then
uses it for both the descriptor and port accumulation. Generator should follow
the same pattern.

**Fix required:**
1. Add a `fuel_type: FuelType` field to `Generator` struct.
2. Read it in `new()` via `parse_fuel_type(config.get_str("fuel_type"))`,
   defaulting to `FuelType::Gas`.
3. Use `self.fuel_type` at line 378 and line 667 instead of the literal.
4. Add a test: resolve a propane generator from HPXML and assert the spec's
   `fuel_type` and the equipment descriptor's `fuel` field both equal
   `FuelType::Propane`.

### F-002 — COVERAGE GAP: `FuelCell` has no HPXML resolution path

**Severity: Medium**
**Files:** `crates/hares-io/src/hpxml/resolve_der.rs:162-163`

`resolve_generators` always emits `"Gas Generator"` as the equipment name
regardless of the XML content (line 163). There is no XML attribute or element
that would cause it to emit `"Gas Fuel Cell"` instead. The `FuelCell` type can
only be instantiated via the non-HPXML direct config path.

This matches OCHRE's own limitation (no HPXML loading of `GasFuelCell` exists in
the OCHRE codebase either — `GasFuelCell` is only accessible through Python
`kwargs`). However, HARES intends to be the primary interface for HPXML-based
building descriptions, so this gap should be documented and a path forward
chosen: either add a discriminating XML element (e.g., `<GeneratorType>fuel
cell</GeneratorType>`) or explicitly document that fuel cells require the direct
config path.

No code change is strictly required now, but the gap must be tracked.

### F-003 — OBSERVATION: ramp-rate units differ from OCHRE by a factor of 60

**Severity: Informational (intentional divergence)**
**Files:** `crates/hares-equipment/src/generator.rs:43-70`

OCHRE uses `ramp_rate` in kW/min and accumulates over `_dt_minutes` each step.
HARES uses `delta_kw_per_s` in kW/s and accumulates over `dt.as_secs_f64()`.
The default values differ: OCHRE's effective default is unset (None, meaning no
ramp limit); HARES defaults to `1.0 kW/s`.

This divergence is intentional and correctly documented in the source and
`der_parity.rs` (test `generator_ramp_rate_is_kw_per_second`). The HARES default
is physically more realistic for residential reciprocating units. No action
required, but interoperability note: if migrating OCHRE parameter files that use
`ramp_rate` in kW/min, the value must be divided by 60 before passing to HARES.

### F-004 — OBSERVATION: CHP thermal port is fully implemented in HARES vs
stubbed in OCHRE

**Severity: Informational (HARES improvement)**
**Files:** `crates/hares-equipment/src/generator.rs:637-695`

OCHRE's `calculate_power_and_heat()` computes `power_chp = power_input *
efficiency_chp` but never routes it anywhere — the variable is commented out at
line 39 ("not implemented"). `sensible_gain` in OCHRE captures only
`electric_kw - power_input` regardless of CHP mode.

HARES fully routes CHP heat: `q_thermal_w = fuel_w * eta_thermal` goes to the
fluid loop when `chp_loop_id` is configured, and `q_flue_w = fuel_w -
electrical_w - q_thermal_w` goes to the zone. When no fluid loop is configured,
all waste heat goes to the zone. Energy balance is enforced and tested. This is a
correct improvement over OCHRE.

### F-005 — OBSERVATION: OCHRE quadratic formula has a bug; HARES fixes it

**Severity: Informational (deliberate divergence)**
**Files:** `crates/hares-equipment/src/generator.rs:119-121,141-143`

OCHRE Generator.py line 172: `return min(eff, 0.001)` floors efficiency at a
very large value (0.001 is the ceiling, not the floor — this should be `max`).
The comment in HARES at line 119 correctly identifies this as a typo and uses
`eff.max(0.001)` instead. This is a correct fix; the direction of divergence from
OCHRE is intentional and documented.

### F-006 — MINOR: `capacity_min_kw` clamp-up semantics differ from OCHRE in
one edge case

**Severity: Low**
**Files:** `crates/hares-equipment/src/generator.rs:476-480`

OCHRE `get_power_limits` sets `max_power = -capacity_min` when
`capacity_min is not None`. In OCHRE's negative-generation convention this means
the generator cannot operate between 0 and `capacity_min` kW; values in that
range are rejected via the power-limit clamp. In the self-consumption path OCHRE
can therefore produce a setpoint in the forbidden zone and immediately have it
clamped to `capacity_min` (upward) — the same intent as HARES.

However, OCHRE's clamp applies to all setpoints including external
`P Setpoint` commands. HARES `determine_target_kw` applies the same floor for
setpoints via the code path at lines 476-480 (`if raw > 0.0 && raw < min_kw`),
which is tested by `capacity_min_clamps_setpoint_up`. The behaviour matches.

No action required, but the test `generator_capacity_min_enforced` in
`der_parity.rs` (line 645) asserts `!(0.1..1.9).contains(&electric_kw)` which
uses a loose range rather than an exact threshold. If `capacity_min_kw` is
changed in a future refactor, this test could pass with a wrong value. Prefer a
direct equality assertion: `(electric_kw - 2.0).abs() < 1e-9` for the clamped
case, or `electric_kw < IDLE_KW_THRESHOLD` for the off case.

### F-007 — MINOR: `update_control` uses stale setpoint as mode proxy

**Severity: Low**
**Files:** `crates/hares-equipment/src/generator.rs:586-598`

`update_control` derives a provisional mode from `self.power_setpoint_kw` or
`self.current_power_kw`. When `power_setpoint_kw` is `None` (self-consumption
mode), the mode reported is based on the _previous_ step's output, not the
current net load. If the net load has dropped to zero between steps, the mode
will incorrectly read `Standby` until the next `step()` call resolves it. This
is a minor latency issue of one timestep in mode reporting; it does not affect
physical output. OCHRE has the same latency (modes are determined in
`update_internal_control` before power calculation). No fix required for
correctness, but worth noting if mode accuracy between steps matters for
telemetry consumers.

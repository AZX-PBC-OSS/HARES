## Background/Context

Battery has significant unreviewed physics. OCHRE `Battery.py` adds degradation states, SOC control bounds, and a thermal model. HARES has dedicated `degradation.rs` and `ocv.rs`. No ticket traces: OCV model equivalence, round-trip efficiency symmetry, BMS TOU dispatch correctness, or thermal effects on capacity.

## Findings

### F1 — CRITICAL: Discharge efficiency applied in wrong direction in SOC update (double-loss bug)

**File:** `crates/hares-equipment/src/battery/mod.rs:943-952`

```rust
let dc_power_kw = if power_kw > 0.0 {
    power_kw * self.charge_efficiency       // AC → DC: correct (loss reduces DC)
} else {
    power_kw / self.discharge_efficiency    // AC → DC: WRONG direction
};
```

When discharging, `power_kw` is negative (discharge = AC generation). To find DC power removed from the cells you need `DC = AC / discharge_eta`. Because `power_kw` is negative and `discharge_efficiency < 1`, dividing gives a value *more negative* than the AC power — the cells are being debited extra energy that was never there. The correct formula is `DC = AC * discharge_eta` (the cells must supply more DC than the AC output, not less).

OCHRE `Generator.py:187-193` uses:
```python
if self.electric_kw < 0:          # discharging
    self.power_input = self.electric_kw / self.efficiency   # power_input < electric_kw (more negative)
```
OCHRE's `power_input` is defined as "input including losses", which for a discharger is the DC side (more energy out of cells than reaches the grid). In OCHRE the SOC update uses `power_input` directly:
```python
self.next_soc = self.soc + self.power_input * self.time_res_hours / self.capacity_kwh
```
So OCHRE does `power_input = AC / eta` for discharge, which makes cells lose *more* energy than the AC output — this is correct: `|DC| = |AC| / eta_discharge` meaning more energy is taken from the battery than delivered to the grid.

HARES computes `dc_power_kw = power_kw / self.discharge_efficiency` where `power_kw < 0`. Since `0 < discharge_efficiency < 1`, the result is a more-negative number (larger magnitude) — numerically HARES matches OCHRE's direction for the cell debit, but then immediately subtracts ohmic losses *again* at line 949:
```rust
let effective_cell_power_kw = if dc_power_kw > 0.0 {
    dc_power_kw - ohmic_loss_w / 1000.0
} else {
    dc_power_kw + ohmic_loss_w / 1000.0   // dc_power_kw already includes R losses via terminal-V model
};
```
The `compute_electrical()` call already computes `ohmic_loss_w` as part of the quadratic terminal-voltage solution — those losses are embedded in the DC-side power balance. Adding them again in `effective_cell_power_kw` means ohmic losses are applied twice to the SOC update on discharge.

**Impact:** At high C-rates (≥0.5C) with non-zero cell resistance, every discharge step removes excess energy from the SOC. Over many cycles the SOC drifts low, making the battery appear to degrade faster than it does and reducing usable energy. The magnitude depends on `cell_resistance_ohm × n_series / n_parallel × I²`; for the default 96S1P at 5 kW discharge that is ~2.5 W, a small but systematic error that accumulates.

### F2 — HIGH: Degradation `b2` (cycle aging) formula diverges from OCHRE — intentional but undocumented contract gap

**File:** `crates/hares-equipment/src/battery/degradation.rs:317`

OCHRE `Battery.py:418`:
```python
b2 = b2_ref * ((b2_arr * cycles["ncycle"]) ** 2).sum() ** 0.5 / deg_time
```
This squares the per-cycle Arrhenius-weighted count, sums them, takes a square root, and divides by elapsed days. It does not use DOD amplitude at all — a 10% DOD cycle and a 100% DOD cycle have identical weight.

HARES `degradation.rs:317`:
```rust
let dq_li2 = B2_REF * self.b2_accum * sum_squared_dod.sqrt();
```
HARES accumulates the Arrhenius factor per-timestep and weights by `sqrt(Σ count_i × DOD_i²)` (rainflow DOD² sum). This is physically more correct per Smith 2017 Eq. 13 and is documented inline. However:

1. The inline comment cites the deliberate divergence from OCHRE but the ticket context (TP-004) labelled degradation as "behaviourally inert". If capacity fade is wired correctly and is now active, parity test suites will diverge here. The test at `crates/hares-equipment/tests/battery_tests.rs` (if any) must verify this is intentional.
2. OCHRE omits DOD from `b2`, so HARES will compute higher cycle fade for deep-discharge scenarios and lower fade for shallow cycling. This is correct physics but will fail any direct numerical parity test against OCHRE.

**No code change needed** but a `# Intentional divergence` note above the formula should reference the ticket number and Smith 2017 Eq. 13 so reviewers do not re-open this as a regression.

### F3 — HIGH: Degradation `b3` sign convention differs from OCHRE

**File:** `crates/hares-equipment/src/battery/degradation.rs:320`

OCHRE `Battery.py:426`:
```python
q3 += deg_time / tau_b3 * min(b3 - q3, 0)   # q3 always decreasing, always negative
q3 = max(q3, b3)
```
OCHRE's `q3` starts at 0 and decreases (becomes more negative over time), adding to capacity because `b3_ref = -2.805e-2` (negative). In OCHRE the final sum is `b0 - (q1 + q2 + q3)` where `q3 < 0`, meaning q3 *increases* capacity at beginning-of-life (BOL transient boost).

HARES `degradation.rs:320`:
```rust
let dq_li3 = (self.b3_accum - self.q_li3).max(0.0) / TAU_B3;
...
self.q_li3 += dq_li3;
...
let remaining = (B0 - self.q_li1 - self.q_li2 - self.q_li3).max(0.0);
```
`B3_REF = -2.805e-2` so `b3_accum` is negative. `(b3_accum - q_li3).max(0.0)` — if `q_li3` starts at 0 and `b3_accum < 0`, then `b3_accum - 0 < 0`, so `max(0.0)` always returns 0.0. **`dq_li3` is always 0 and `q_li3` never updates.** This confirms the TP-004 finding: mechanism 3 (BOL transient) is effectively inert.

In OCHRE the BOL transient provides a brief capacity boost in the first ~15 days then decays. HARES silently skips it. For simulations starting from a new cell, this means the rated capacity is underused slightly at BOL — a minor physics gap, but the code path is dead and misleading.

**Fix:** Either implement the sign-correct q3 update (q3 can be negative, representing capacity gain) or remove the mechanism and document the gap clearly. A dead code path that does nothing is a broken-window defect.

### F4 — HIGH: OCV used in degradation accumulation is post-SOC-update, not at-step-start

**File:** `crates/hares-equipment/src/battery/mod.rs:1062-1067`

```rust
// -- Degradation per-timestep accumulation --
{
    let cell_temp_k = self.cell_temp_c + 273.15;
    let v_oc = self.ocv_table.voltage_at_soc(self.soc);   // self.soc already updated by step
    self.degradation.accumulate(dt_s, cell_temp_k, v_oc, self.soc);
}
```

`self.soc` is updated at line 957 (SOC += energy_delta / capacity) before this point. The OCV and SOC passed to `accumulate()` therefore reflect the end-of-timestep value, not the start. OCHRE accumulates based on the pre-step SOC (the SOC snapshot used when `degradation_data.append((self.soc, t_batt))` is called, which happens before `update_results()` advances the SOC).

For the Tafel correction in mechanism 3 (`v_oc / T`) this is a minor first-order error (OCV is smooth), but for the daily DOD tracking it can cause a one-timestep lag in the reported SOC extremes, slightly misreporting `dod_max_today`.

### F5 — MEDIUM: OCHRE efficiency model uses two separate per-direction constants; HARES uses one symmetric RTE split

**File:** `crates/hares-equipment/src/battery/mod.rs:385-391`, `vendors/OCHRE/ochre/defaults/Battery/default_parameters.csv`

OCHRE defaults:
- `efficiency` (discharge): 0.98
- `efficiency_charge`: 0.98 (both defaults are equal)
- `efficiency_inverter`: 0.97

OCHRE total round-trip efficiency = `0.98 × 0.97 × 0.98 × 0.97 = 0.908` (discharge × inverter × charge × inverter).

HARES defaults:
- `DEFAULT_INVERTER_EFFICIENCY = 0.97`, split as `sqrt(0.97) ≈ 0.9849` per direction.

HARES total RTE = `0.9849² = 0.97` — the inverter efficiency is the only contributor; the internal cell-level efficiency is subsumed into the ohmic loss model. This is a valid design choice but it means HARES omits the cell-efficiency term that OCHRE applies on top of ohmic losses. Users configuring HARES to match an OCHRE run must set `inverter_efficiency = 0.97 × 0.98 × 0.98 ≈ 0.930` to achieve parity — this is undocumented and likely to cause user misconfiguration.

The OCHRE `"advanced"` mode uses the quadratic OCV formula for internal efficiency (same as HARES `compute_electrical`), then multiplies by `efficiency_inverter`. The non-advanced path uses separate flat constants. The key difference: in OCHRE advanced mode, `efficiency_internal` (ohmic losses) and `efficiency_inverter` (inverter) are separately tracked; in HARES `discharge_efficiency` conflates both when the user only provides `inverter_efficiency`.

### F6 — MEDIUM: SOC setpoint controller uses proportional error without efficiency correction

**File:** `crates/hares-equipment/src/battery/mod.rs:513-517`

```rust
if let Some(target) = self.soc_target {
    if dt_hours > 0.0 {
        let error = target - self.soc;
        let power = error * self.capacity_kwh / dt_hours;
        return self.clamp_power(power);
    }
}
```

This computes the raw DC energy needed to reach target SOC in one timestep, but does not apply inverter/ohmic efficiency. OCHRE `Battery.py:199-203`:
```python
power_dc = (soc - self.soc) * self.capacity_kwh / self.time_res_hours   # DC
efficiency = self.calculate_efficiency(power_dc, is_output_power=False)
power_setpoint = power_dc / efficiency if power_dc > 0 else power_dc * efficiency
```
OCHRE converts DC power to AC power setpoint using the efficiency model. HARES passes the DC-equivalent directly as AC power to `clamp_power`, then `compute_electrical` converts it again. The result is that charging underpowers and discharging overpowers by the efficiency factor squared: the setpoint is in DC units but treated as AC.

**Impact:** With `charge_efficiency = 0.985`, a SOC-target charge command will deliver about 3% less energy per step than intended, causing the SOC to undershoot and requiring extra steps. Discharging overshoots slightly.

### F7 — MEDIUM: Thermal model heat source wired incorrectly for discharge path

**File:** `crates/hares-equipment/src/battery/mod.rs:1016`

```rust
let q_in = ohmic_loss_w + heater_w;
```

The thermal model adds heater power and ohmic losses as heat sources. For the discharge path, `ohmic_loss_w` is computed from `actual_ohmic_w` (line 983), but `ohmic_loss_w` at line 1016 still refers to the value from the *first* `compute_electrical` call (line 931), not the post-clamp recomputed value from line 983. The rebinding on line 964 is:
```rust
let (actual_power_kw, ohmic_loss_w) = if actual_soc_delta.abs() < f64::EPSILON ...
```
This shadows `ohmic_loss_w` in the inner block but the outer `ohmic_loss_w` binding from line 931 persists in scope at line 1016 if the SOC was not clamped. When the SOC hits a bound and actual_power_kw = 0, the shadowed binding returns 0.0 for `ohmic_loss_w`, but the `q_in = ohmic_loss_w + heater_w` at line 1016 uses the *original* pre-clamp value because `ohmic_loss_w` in the outer destructuring is the one in scope there.

Concretely: if a charge command brings the SOC exactly to `eff_max_soc`, the actual energy transfer drops to near zero, but the thermal model receives the full pre-clamp ohmic heat as if the charge continued. This causes a phantom temperature spike on boundary steps.

**Severity note:** This only fires on SOC-limit steps, which are frequent at end-of-charge. The magnitude is bounded by the ohmic loss at max charge power (~2–5 W for default parameters), but each daily charge termination will spike cell temperature by a few millidegrees unnecessarily.

### F8 — LOW: OCV interpolation uses O(n) linear scan; should be O(1) for uniform grids

**File:** `crates/hares-equipment/src/battery/ocv.rs:118-128`

`voltage_at_soc()` iterates from `i=0` searching for the bracket. The default grids are strictly uniform (51 points, 0.02 step). For a uniform grid the index is `floor(soc / step)` — a single arithmetic operation. As called once per timestep for OCV (line 445) and again per timestep for degradation (line 1064), this is two O(n) walks per step through a 51-element array. In a fleet of 100 batteries stepping at 1-minute resolution, this executes 102,000 times per simulated hour. The array fits in a cache line but the branch predictor will see a semi-random early-exit depth.

This is a hot-loop concern per project policy. The fix is to detect uniform grids at `OcvTable::new` time and branch accordingly in `voltage_at_soc`. For user-injected non-uniform LUTs the current loop is acceptable.

### F9 — LOW: `b2_accum` is labelled as a temperature factor but has units of day·(dimensionless)

**File:** `crates/hares-equipment/src/battery/degradation.rs:171`

```rust
/// Σ exp(−Ea_b2/R · (1/T − 1/T_ref)) · dt_day
b2_accum: f64,
```

The field accumulates `arr(T) × dt_day` each timestep. After 1 day at 25°C this equals 1.0 (day). The `update_daily` call then does:
```rust
let dq_li2 = B2_REF * self.b2_accum * sum_squared_dod.sqrt();
```
where `B2_REF` is `1.541e-5 cycles^-1`. The unit of `b2_accum` here is effectively a day-weighted temperature factor. The units work out but the field name and doc-comment do not make the "day" unit explicit, making it easy to misuse if the daily-reset is accidentally moved. Should read: `Σ exp(−Ea_b2/R · (1/T − 1/T_ref)) · dt_day  [day, resets daily]`.

### F10 — LOW: Rainflow extraction uses reversed-window slice instead of standard front-removal

**File:** `crates/hares-equipment/src/battery/degradation.rs:87-97`

For a 4+-point window OCHRE uses the Python `rainflow` library (ASTM E1049-85). HARES uses a custom implementation that processes `[n-3, n-2, n-1]` from the *end* of the buffer. This is algorithmically equivalent to ASTM's standard but means the reversal buffer grows unboundedly for long non-cycling periods (e.g. a battery parked at a fixed SOC for days, then a reversal occurs — the buffer has `n` duplicates of the same SOC before the first reversal push). The `reset_daily()` call does *not* trim the reversal buffer, only the `daily_cycle_dods` list:

```rust
pub(crate) fn reset_daily(&mut self) {
    // Keep the full reversal buffer.
    self.daily_cycle_dods.clear();
}
```

For a year-long simulation the reversal buffer can accumulate O(timesteps-per-day × non-cycling-days) duplicates. At 5-minute resolution that is 288 entries per day of stale pre-reversal data. The `push()` method merges identical consecutive SOCs only if they differ by less than `f64::EPSILON`, but monotone drift (e.g. self-discharge) will not be merged, and each step appends a new value.

**Fix:** Add a length cap or prune runs of identical values more aggressively. The OCHRE implementation avoids this because it discards all data at midnight.

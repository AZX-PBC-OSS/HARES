## Background/Context

OCHRE WH outputs: `"Water Heating Delivered (W)"`, `"Water Heating COP (-)"`,
`"Water Heating Total Sensible Heat Gain (W)"`, `"Hot Water Unmet Demand (kW)"`,
`"Hot Water Outlet Temperature (C)"`, `"Hot Water Delivered (L/min)"`,
`"Hot Water Heat Injected (W)"`, `"Hot Water Heat Loss (W)"`,
`"Hot Water Average/Min/Max Temperature (C)"`, `"Hot Water Mains Temperature (C)"`.

## Investigation Instructions

1. Read OCHRE WH and tank model `generate_results()`.
2. Read HARES WH telemetry for each type (resistance, gas, HPWH, tankless).
3. Read HARES tank model telemetry.
4. Build comparison table.
5. Check: is "Total Sensible Heat Gain" (jacket loss to zone) reported?


## Findings

### [HIGH-1] HPWH `ELECTRIC_KW` not saved/restored across checkpoint round-trips

**File:** `crates/hares-equipment/src/water_heater/heat_pump_wh.rs`

`HpwhState` (line 43) has no `electric_kw` field. `save_state` (line 862) never reads `tk::ELECTRIC_KW` from the telemetry map. `load_state` (line 899) never writes it back. The field is initialised in `default_telemetry` (line 1059) and written every step (line 833), but it is zeroed out whenever a checkpoint is restored. Any consumer that reads `ELECTRIC_KW` from HPWH after `load_state` before the first step will receive `0.0`. Affects HELICS federation handshake, warm-start reloads, and fleet aggregators.

**Fix:** Add `electric_kw: f64` to `HpwhState`; save `self.telemetry.get(tk::ELECTRIC_KW).unwrap_or(0.0)` in `save_state`; restore in `load_state`.

---

### [HIGH-2] `ResistanceWhState.electric_power_w` field name implies W but holds kW — unit semantic mismatch

**File:** `crates/hares-equipment/src/water_heater/resistance.rs`

Line 553 stores `electric_power_w / 1_000.0` under `tk::ELECTRIC_KW` (kW). Line 590 (`save_state`) reads that kW value from telemetry into a field named `electric_power_w`. Line 622 (`load_state`) inserts it back under `tk::ELECTRIC_KW` — so the round-trip is numerically correct — but the struct field name misleads any future consumer that reads `ResistanceWhState.electric_power_w` directly and assumes W units, producing a 1000× error.

**Fix:** Rename `ResistanceWhState.electric_power_w` to `electric_kw`.

---

### [MEDIUM-1] HPWH `telemetry_fields` omits `ELECTRIC_KW` from the declared schema

**File:** `crates/hares-equipment/src/water_heater/heat_pump_wh.rs:1070`

`default_telemetry` (line 1059) inserts `tk::ELECTRIC_KW` and `telemetry()` therefore always contains it. `telemetry_fields` (line 1070) does not declare a `TelemetryField` for it. Downstream consumers that iterate `telemetry_fields` to build output columns (Python bindings schema, HELICS publisher declarations) silently drop total electric draw for HPWH.

**Fix:** Add `TelemetryField { name: tk::ELECTRIC_KW, unit: "kW", description: "Total electric draw (compressor + backup + fan + parasitic)" }` to `telemetry_fields` in `heat_pump_wh.rs`.

---

### [MEDIUM-2] HPWH `load_state` does not restore `WALL_SENSIBLE_GAIN_W` or `UNMET_LOAD_W`

**File:** `crates/hares-equipment/src/water_heater/heat_pump_wh.rs:899`

Both fields are in `default_telemetry` (lines 1065–1066) and written every step (lines 838–839), but neither is in `HpwhState` nor restored in `load_state`. After restore they read `0.0` until the next step. `UNMET_LOAD_W` is used by supervisory logic and HELICS observers that may read telemetry before the first post-restore step.

**Fix:** Add `wall_sensible_gain_w: f64` and `unmet_load_w: f64` to `HpwhState`; save and restore them following the same pattern as existing telemetry fields.

---

### [MEDIUM-3] `OUTLET_TEMP_C` and `UNMET_LOAD_W` absent from `ResistanceWH` and `GasWH` telemetry

**Files:** `resistance.rs`, `gas.rs`

OCHRE `Water.generate_results()` (lines 440–441) emits `Hot Water Unmet Demand (kW)` and `Hot Water Outlet Temperature (C)` at verbosity ≥ 3 for all WH types. `StratifiedTank::step` computes both `unmet_load_w` and `outlet_temp_c` in the `DrawResult` for all tank-backed models. HPWH exposes `UNMET_LOAD_W`; `ResistanceWH` and `GasWH` expose neither.

**Fix:** Add `tk::OUTLET_TEMP_C` and `tk::UNMET_LOAD_W` to `default_telemetry`, `telemetry_fields`, the step update path, and checkpoint save/restore in both `resistance.rs` and `gas.rs`.

---

### [LOW-1] `SKIN_LOSS_W` registered via `register_node_telemetry` but not saved/restored for any tank-backed WH type

**Files:** `resistance.rs:587–596`, `gas.rs:546–556`, `heat_pump_wh.rs:875–896`

`tank.rs:242` inserts `tk::SKIN_LOSS_W` during `register_node_telemetry`. None of the three `*WhState` structs persist it. After a restore the value reads `0.0` for one step interval. `SKIN_LOSS_W` is declared in `telemetry_fields` for all three variants (resistance line 786, gas line 747, HPWH line 1135), so schema consumers expect it to be non-zero post-restore.

**Fix:** Add `skin_loss_w: f64` to each `*WhState` struct; save `self.tank.skin_loss_w()` and restore it via the appropriate tank setter.

---

### [LOW-2] No `MAINS_TEMP_C` telemetry key — OCHRE parity gap

**Files:** `crates/hares-types/src/telemetry_keys.rs`, all WH step implementations

OCHRE `Water.generate_results()` line 451 emits `Hot Water Mains Temperature (C)` at verbosity ≥ 7. No equivalent key exists in `telemetry_keys.rs` or in any WH step function. This is a diagnostic gap that affects post-processing comparisons and parity test tracing.

**Fix (lower priority):** Add `pub const MAINS_TEMP_C: &str = "mains_temp_c"` to `telemetry_keys.rs` and emit the resolved mains temperature from all tank-backed WH step functions.

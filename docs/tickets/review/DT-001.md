## Background/Context

OCHRE evaluates all schedule lookups in local wall-clock time — the schedule index is
derived from the simulation's localized `DatetimeIndex`. HARES has had chronic issues
where some code paths use UTC or fixed-offset time while others use civil/local time.
`ScheduledLoad` is one of the most common equipment types (lighting, plug loads,
refrigerator, etc.) and must evaluate its schedule in local time to get correct
day/night and weekday/weekend patterns.

## Recommended Tests

1. **`test_daily_profile_hour_uses_local_offset`** — Build a `ScheduledLoad` with a
   `DailyProfile` that places a unique non-zero value in only one hour slot (e.g. hour 7).
   Construct an `EnvironmentState` with `current_time` carrying a negative `FixedOffset`
   (e.g. UTC-7) and wall-clock hour = 7. Assert the returned power is non-zero. Then re-run
   with `current_time.hour() = 14` (UTC) but the same wall-clock hour-7 semantics encoded in
   the offset, and assert the same result. This guards the wall-clock-digits convention.

2. **`test_time_windows_weekday_minute_resolution`** — Build a `TimeWindows` source with a
   window that covers `[480, 540)` on `DayFilter::Weekdays` (Monday 08:00–09:00). Advance a
   mock `EnvironmentState` through Monday 07:59, 08:00, 08:30, 08:59, and 09:00. Assert only
   the three middle steps return the window value. This is a regression guard against the
   `minute_of_day` computation using the wrong field.

3. **`test_column_ref_indexes_current_schedule_row`** — Inject a 2-row schedule payload via
   `custom_domains` and a `ColumnRef { col_idx: 0, boundary: Clamp }` source. Call
   `value_at()` twice with payloads holding `[1.0]` then `[2.0]` (simulated by swapping the
   domain payload between calls). Assert the returned values match the payload, not a stale
   cursor, confirming `ColumnRef` reads from the environment-supplied row rather than
   maintaining its own cursor.

4. **`test_dst_schedule_offset_shifts_with_civil_tz`** (requires `dst` feature) — Compare
   the schedule index computed by `compute_schedule_idx` for a step that falls on a spring
   DST transition (e.g. `America/New_York`, 2024-03-10 02:00 → 03:00). Assert the index
   jumps by 2 steps (one hour gap) rather than 1, confirming DST skips are handled, and that
   weather index is unaffected (it remains sequential).

## Findings

### Architectural Decision: Local Time Only

**Project policy:** HARES uses local time internally throughout. HPXML and EPW weather are always in local time. There is no reason to support UTC or multiple timezones. All internal timestamps are local to the building site. `start_time` from Python is interpreted as local time. EPW `timezone_offset_h` is metadata for solar position calculation only, not for time conversion. Any findings about UTC/offset mismatches should be resolved by removing UTC conversion entirely, not by fixing the conversion.

### 1. HARES Schedule Evaluation Path

**`ScheduledLoad::step`** (`crates/hares-equipment/src/scheduled_load.rs:370`)
calls `self.power_source.value_at(env)`, which dispatches to `ScheduleSource::value_at`
(`crates/hares-types/src/schedule.rs:469`).

The three time-indexed variants behave as follows:

**`DailyProfile`** (schedule.rs:472–487)
```
let hour = env.current_time.hour() as usize;
let month_idx = env.current_time.month0() as usize;
let is_weekend = env.current_time.weekday().num_days_from_monday() >= 5;
```
All three accessors act on the `DateTime<FixedOffset>` wall-clock digits. The offset is
embedded in the type and `chrono` returns local hour/weekday/month directly. Correct.

**`TimeWindows`** (schedule.rs:549–570)
```
let weekday = env.current_time.weekday();
let minute_of_day = env.current_time.hour() as u16 * 60 + env.current_time.minute() as u16;
```
Same pattern — wall-clock digits used correctly. Correct.

**`ColumnRef`** (schedule.rs:488–502)
Does not inspect `current_time` at all. It reads `env.custom_domains` for
`SCHEDULE_DOMAIN_ID` and indexes by `col_idx` into the payload slice. The payload is
assembled by `EnvironmentManager::update_in_place` (environment.rs:489–521), which
picks the row via `compute_schedule_idx` and writes it to the payload each step. The
`ColumnRef` consumer therefore always sees the current-row value; no stale cursor is
involved. Correct.

**`SolarAware`** (schedule.rs:503–523) uses `current_time.hour()` and
`env.weather.solar_altitude_deg`. Correct by the same reasoning.

**`DailyProfile` month multiplier double-application** (scheduled_load.rs:277–281)
When `power_source` is `DailyProfile`, `month_multipliers` is explicitly cleared so the
outer `month_scale` factor (scheduled_load.rs:369) does not double-scale. This is correct
and intentional.

### 2. `current_time` Timezone Convention

`EnvironmentState::current_time` is `DateTime<FixedOffset>` set from `clock.current_time()`
(environment.rs:563). The clock is initialized with `start_time: DateTime<FixedOffset>`
carrying the EPW site's UTC offset (clock.rs module doc: "HARES treats all timestamps as
local time … the `.hour()` accessor is used directly"). The offset is baked into the
`FixedOffset` at construction time; `chrono`'s `.hour()` / `.weekday()` return wall-clock
digits, not UTC digits. All schedule-evaluation call sites use `.hour()` / `.weekday()` /
`.month0()` — so local time is used correctly throughout.

When the `dst` feature is enabled and `civil_timezone` is set,
`compute_schedule_idx` (environment.rs:324–344) converts `sim_time` to civil time via
`with_timezone(&tz)` before computing the schedule row. Weather indexing always uses the
sequential step-based offset, unaffected by DST. This is the correct separation.

When `civil_timezone` is NOT set, the fixed-offset fallback
`(step + schedule_start_offset) % schedule_len` (environment.rs:344) is used. The
`schedule_start_offset` is computed by `compute_schedule_offset` from `start_time`, so the
offset aligns the annual schedule array to the simulation start correctly.

### 3. OCHRE Comparison

OCHRE's schedule is a pandas `DataFrame` with a timezone-localized `DatetimeIndex`
(schedule.py:116 `df.index = df.index.tz_localize(timezone)`; EPW path at line 176
retains `df.index.tzinfo`). The index carries a fixed UTC offset identical to the EPW
site timezone. OCHRE advances through the schedule by a step counter
(`_sched_step`, Simulator.py:213–214) and reads `schedule[col].to_numpy()[i]` — it does
not re-derive the row from wall-clock time at each step. This is equivalent to HARES'
`compute_schedule_idx` in the fixed-offset fallback: both are sequential row-cursor
approaches that are anchored to the same local-time start.

`ScheduledLoad.update_internal_control` (ScheduledLoad.py:67–80) reads from
`self.current_schedule["Power (kW)"]`, which has already been set to the current row
value by `Simulator.update_inputs`. There is no direct `current_time` lookup in the
equipment code itself — the row has already been selected by the framework.

HARES' `DailyProfile` and `TimeWindows` re-derive the schedule value from `current_time`
at each step rather than advancing a cursor. This is semantically equivalent when the
schedule is uniformly sampled (which it always is for these synthetic sources), and it is
strictly more correct: it handles simulation restarts and checkpoint loads without
requiring cursor state to be perfectly synchronized.

**Alignment verdict:** the two implementations are semantically equivalent for correctly-
configured runs. HARES is not worse than OCHRE and is more restart-safe for the
non-cursor sources.

### 4. Identified Issues

**None found.** The evaluation path is correct end-to-end:

- Wall-clock hour/weekday/month are consistently extracted from `DateTime<FixedOffset>`.
- `ColumnRef` reads from the environment-supplied payload row, not a self-managed cursor.
- The `DailyProfile` double-scaling guard is in place and correct.
- DST-aware indexing is correctly scoped to the schedule only (not weather).
- `compute_schedule_offset` correctly aligns annual schedules to a mid-year simulation start.

### 5. Testing Gap

The four tests described in **Recommended Tests** above do not currently exist. Their
absence means regressions (e.g. accidentally calling `.hour()` on a UTC-converted time)
would not be caught. This is a coverage gap but not a correctness defect in the current
code.

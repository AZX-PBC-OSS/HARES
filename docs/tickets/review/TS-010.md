## Background/Context

HARES has a separate humidity solver with its own moisture balance, `moisture_buffering_multiplier = 15.0`, and latent heat accounting. No existing ticket covers this subsystem.

## Investigation Instructions

1. **Read `humidity_solver.rs` end-to-end.** Document the moisture balance equation, buffering model, and latent heat of vaporization constant.
2. **Compare with OCHRE's `Humidity.py`:** Does OCHRE use the same buffering multiplier? Same latent heat constant?
3. **Trace latent gain inputs:** Does the humidity solver correctly receive latent gains from all equipment types (HVAC dehumidification, water heater evaporation, occupant respiration, cooking, showering)?
4. **Verify moisture buffering multiplier = 15.0:** Source? EnergyPlus uses a similar "effective moisture penetration depth" model — is 15.0 consistent?

## Findings

### 1. Moisture Balance Equation

HARES implements the ASHRAE 2017 HOF Ch. 24 moisture balance:

```
ΔW = (Q_latent × Δt) / (h_fg × ρ_air × V × μ)
```

where:
- `Q_latent` [W] — net latent gain to the zone
- `Δt` [s] — timestep
- `h_fg` [J/kg] — latent heat of vaporisation
- `ρ_air` [kg/m³] — moist air density evaluated at current zone T, W, P
- `V` [m³] — zone volume
- `μ` — `moisture_buffering_multiplier` (effective capacitance scaler)

The updated humidity ratio is clamped to `[0, w_sat(T, P)]`. The saturation bound uses `humidity_ratio_from_tdp(t_zone_c, p_pa)`, which computes the saturation humidity ratio at the dew-point equal to the dry-bulb — this is the saturation humidity ratio at the zone temperature. The lower clamp of zero is correct; no condensation accounting is performed (condensate leaves the zone).

Implementation: `humidity_ratio_increment` in `humidity_solver.rs:162–173`. The `moisture_buffering_multiplier.max(f64::EPSILON)` guard prevents divide-by-zero when the multiplier is misconfigured to zero.

Derived state (RH, wet-bulb, zone temperature) is written to a flat `custom_payload` as `[zone_id_f64, w_new, rh, wet_bulb_c]` quads for consumption by downstream solvers.

### 2. Moisture Buffering Multiplier = 15.0

**Matches OCHRE exactly.** OCHRE `Humidity.py:10` sets `humidity_cap_mult = 15.0`. HARES `HumiditySolverConfig::default()` also sets `moisture_buffering_multiplier = 15.0`.

**Source attribution.** The 15× value originates from the EnergyPlus Effective Moisture Penetration Depth (EMPD) model, which assigns an effective moisture capacitance 10–20× the air-volume capacitance depending on material properties. A value of 15× is the mid-range default representing typical residential construction (painted gypsum board, carpet, wood). OCHRE adopted this value without citing a specific table. Neither OCHRE nor HARES currently vary the multiplier by construction type. This is a known simplification.

**Algebraic equivalence between HARES and OCHRE.** OCHRE's normalisation is:
```python
latent_gains_w = latent_gains_W * dt_s / 1000 / (density * volume * h_vap_kJ)
w_new = w + latent_gains_w / humidity_cap_mult
```
which expands to:
```
w_new = w + (Q_W × Δt) / (h_vap_kJ×1000 × ρ × V × μ)
```
This is algebraically identical to the HARES formula. The implementation is correct.

### 3. Latent Heat Constant

**Critical inconsistency.** There are three different values for latent heat in use across HARES:

| Module | Constant | Value |
|---|---|---|
| `hares-physics/src/constants.rs` | `LATENT_HEAT_VAPORISATION_0C_KJ_KG` | 2 501 000 J/kg |
| `hares-physics/src/constants.rs` | `LATENT_HEAT_VAPORISATION_J_KG` | 2 450 000 J/kg |
| `hares-equipment/src/ventilation.rs:338,344` | `LATENT_HEAT_VAPORISATION_J_KG` | **2 450 000 J/kg** |
| `hares-envelope/src/thermal_solver/mod.rs:34` | `H_FG_J_PER_KG` via `0C_KJ_KG × KJ_TO_J` | 2 501 000 J/kg |
| `hares-envelope/src/humidity_solver.rs:35` | `h_fg_j_kg` via `0C_KJ_KG × KJ_TO_J` | 2 501 000 J/kg |
| OCHRE `Humidity.py:9` | `h_vap` | 2 454 000 J/kg |

The thermal solver (infiltration path, `infiltration.rs:211`) and the humidity solver both use 2 501 000 J/kg — they are internally consistent with each other.

**The ventilation equipment (`ventilation.rs`) uses 2 450 000 J/kg**, which is ~2% lower than the humidity solver's 2 501 000 J/kg. Ventilation emits a `latent_gain_w` via the `PortContribution::Thermal` port, which feeds directly into the humidity solver's `latent_gain_w` sum. This means:

- Ventilation computes its latent load using 2 450 000 J/kg (lower h_fg → higher apparent moisture flux for a given humidity difference)
- The humidity solver converts that energy back to moisture mass using 2 501 000 J/kg (higher h_fg → lower resulting ΔW)

The net effect is that ventilation-driven moisture changes are **~2% lower in HARES than they should be** when computed end-to-end. This is a correctness defect, not a style issue. The existing `latent_heat_round_trip_through_thermal_domain_payload` test in `humidity_solver.rs` does not exercise the ventilation path (it uses the thermal custom_payload path).

OCHRE uses `h_vap = 2454 kJ/kg` for both the infiltration latent gain computation in `Envelope.py:668` and the moisture balance in `Humidity.py:52`. HARES uses 2501 kJ/kg in both of these paths — internally consistent but a deliberate 2% upward deviation from OCHRE, justified in constants.rs by the note that 2501 kJ/kg is the ASHRAE 0°C reference used for enthalpy calculations. The constant name `LATENT_HEAT_VAPORISATION_J_KG = 2_450_000` in constants.rs is described as the "~20°C approximation" — the comment describes it as the value appropriate for zone-temperature moisture balance. There is therefore an argument that `ventilation.rs` is actually using the more physically correct value for the zone operating temperature (~20°C), while infiltration and the humidity solver use the 0°C reference. The inconsistency should be resolved by settling on one value codebase-wide and documenting the choice.

### 4. Latent Gain Source Tracing

HARES aggregates latent gains from two paths in `humidity_solver.rs:108–114`:

**Path A — `ports.thermal` (equipment latent gains via PortSlots):**
These are accumulated by the hot-loop equipment step and include:
- HVAC cooling/dehumidification: `air_conditioner.rs`, `dehumidifier.rs` (negative latent_gain_w — removes moisture)
- Heat pump water heater evaporation: `heat_pump_wh.rs:779` (negative for dehumidification during HP mode)
- Ventilation (ERV/HRV/exhaust): `ventilation.rs:338`
- Appliances with non-zero `latent_gain_fraction`: `event_load.rs:380`, `scheduled_load.rs:428` (covers cooking, clothes washer, dishwasher etc. when `latent_gain_fraction` is set)
- PV, battery, boiler, generator: `latent_gain_w: 0.0` — correctly excluded

**Path B — `custom_payload` from the THERMAL domain update:**
The thermal solver emits per-zone latent loads (from infiltration/ventilation computed internally) via `custom_payload` as `[zone_id_f64, latent_w]` pairs. The humidity solver reads these at `humidity_solver.rs:91–101` and accumulates them into `self.latent_buf`. These represent the infiltration moisture exchange only.

**Confirmed present:**
- HVAC latent cooling / dehumidification: present via Path A
- Heat pump WH dehumidification: present via Path A
- Infiltration moisture exchange: present via Path B
- Occupant latent gain: partially present — occupants must have a non-zero `latent_gain_fraction` configured in the occupant load equipment. No separate occupant moisture source exists; it relies on the schedule-driven `ScheduledLoad` or `EventLoad` with `latent_gain_fraction` set. This matches OCHRE, which adds `occupancy × occupancy_latent_gain` separately. It is not confirmed that HARES's occupant equipment always sets a non-zero `latent_gain_fraction` matching OCHRE's default 0.437 fraction.
- Cooking: same as occupant — depends on `latent_gain_fraction` being set in the cooking appliance config. OCHRE sets `latent_gain_fraction` per appliance from HPXML. HARES supports this but correctness depends on the HPXML resolver populating it.
- Showering / domestic hot water draws: **not modelled as a direct moisture source** in either OCHRE or HARES. OCHRE's standard water heater sets `latent_gain = 0` (`WaterHeater.py:292`). Shower moisture is implicitly carried by the occupancy latent gain fraction; there is no dedicated draw-evaporation model. This is a pre-existing OCHRE parity simplification, not a new HARES defect.

**Missing / unverified:**
- `ScheduledLoad.latent_gain_fraction` and `EventLoad.latent_gain_fraction` are supported in the equipment code, but no test verifies that the HPXML resolver (`hares-io/src/hpxml/resolve_loads.rs`) maps HPXML `LatentFraction` or `FracLatent` attributes to these fields for occupant/cooking/clothes-washer loads. If the resolver silently drops these fractions, the humidity solver will see zero latent gain from all schedule-driven appliances, producing unrealistically dry interiors.
- Natural ventilation latent gains: if HARES has a natural ventilation code path separate from the ASHRAE infiltration model, it must also emit `latent_gain_w` to Path A or contribute via the thermal solver's Path B. Not audited in this ticket.

## Defects

### DEFECT-1 (Severity: Medium) — Ventilation latent heat constant inconsistent with humidity solver

**File:** `crates/hares-equipment/src/ventilation.rs:338,344`

`ventilation.rs` uses `LATENT_HEAT_VAPORISATION_J_KG = 2_450_000 J/kg` to compute ventilation latent gains. The humidity solver uses `2_501_000 J/kg` to convert those gains back to moisture mass. The resulting end-to-end moisture flux from ventilation is ~2% lower than it should be. The thermal solver's infiltration path uses `H_FG_J_PER_KG = 2_501_000 J/kg`, making the two infiltration paths inconsistent with each other.

Fix: change `ventilation.rs` to import and use `LATENT_HEAT_VAPORISATION_0C_KJ_KG * KJ_TO_J` (= 2 501 000 J/kg) for consistency. Alternatively, adopt 2 454 000 J/kg codebase-wide to match OCHRE; document the choice.

### DEFECT-2 (Severity: Medium) — HPXML resolver correctness for latent_gain_fraction unverified

The humidity solver depends on `ScheduledLoad` and `EventLoad` emitting non-zero `latent_gain_w` for occupants, cooking, and clothes washer. This requires that the HPXML resolver (`hares-io/src/hpxml/resolve_loads.rs`) correctly maps HPXML `FracLatent` / latent fraction attributes to the `latent_gain_fraction` config key. No test covers this chain end-to-end for the humidity impact. If the resolver drops these fractions, the dwelling will have no occupant or cooking latent gains and RH will be systematically low.

Fix: add an integration test that loads a known HPXML with occupant and cooking loads and verifies that the resolved equipment configs have non-zero `latent_gain_fraction`, and that after a simulated occupied period the zone RH rises above the ambient start value.

## Recommended Tests

1. **Ventilation latent heat round-trip test** (covers DEFECT-1): simulate a zone with an ERV/exhaust ventilation unit and outdoor air at higher humidity than indoor. Run one timestep. Verify that `(w_new - w_old) × ρ × V` equals `Q_ventilation_latent × dt / h_fg_humidity_solver` to within 1e-6 kg. This will fail until the ventilation h_fg is corrected.

2. **HPXML occupant latent fraction integration test** (covers DEFECT-2): load a minimal HPXML with `NumberofResidents`, verify the resolved `ScheduledLoad` or `EventLoad` for occupancy has `latent_gain_fraction ≈ 0.437`. Run one occupied timestep and verify the humidity solver receives a positive latent contribution from the occupant port.

3. **HPXML cooking latent fraction integration test**: same as above but for a cooking range load. Verify `latent_gain_fraction > 0` is preserved through the HPXML resolver.

4. **Multi-source latent accumulation test**: configure a zone with simultaneous HVAC dehumidification (negative latent), occupant gain (positive), and infiltration with dry outdoor air (negative). Verify the net latent in the humidity solver is the algebraic sum of all three and that the resulting W change has the correct sign.

5. **Buffering multiplier regime test**: with `moisture_buffering_multiplier = 15.0`, apply a 500 W latent load for 1 hour and verify that ΔW is 1/15 of the unbuffered ΔW (multiplier=1.0). This verifies the multiplier is applied in the denominator, not as an additive offset.

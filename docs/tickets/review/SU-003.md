## Background/Context

Multiple tickets found checkpoint gaps: TP-003 (HPWH ELECTRIC_KW not checkpointed),
DC-007 (active_power_kw mutated in-place), TP-007 (reactive power dropped). This ticket
systematically audits checkpoint round-trip for EVERY equipment type.

## Findings

### Severity classification

- **DEFECT** — field affects physics in the immediately subsequent step after restore;
  simulation diverges or is incorrect.
- **MINOR** — field is a derived/telemetry value that can be reconstructed on the next
  step; incorrect for at most one timestep.
- **BENIGN** — field is transient (reset unconditionally in update_control or step), is
  static (set only at init), or is always recomputed before first use.

---

### Finding 1 — DEFECT: `hvac.thermostat.hysteresis_c` not checkpointed for AC, HP heater,
  and IdealHvac

**Files:**
- `crates/hares-equipment/src/hvac/air_conditioner.rs:1048`
- `crates/hares-equipment/src/hvac/heat_pump/heater.rs:1098`
- `crates/hares-equipment/src/hvac/ideal_hvac.rs:496`

`apply_control_unchecked` for `ThermalSetpoint` with a `deadband_c` value mutates
`self.hvac.thermostat.hysteresis_c` (AC, HP heater) or `self.thermostat.hysteresis_c`
(IdealHvac). None of the corresponding state structs (`AirConditionerState`,
`HeaterState`, `IdealHvacState`) include this field. After restore the thermostat reverts
to the `init()`-configured deadband value, which changes thermostat trigger thresholds
and alters mode-switching behavior indefinitely.

This is a permanent drift once a non-default deadband has been applied via a control
signal — not a single-step transient. It affects all simulations that use demand response
or actor-driven setpoint adjustments that also change the deadband.

**Required fix:** add `thermostat_hysteresis_c: f64` to `AirConditionerState`,
`HeaterState`, and `IdealHvacState`; save and restore `hvac.thermostat.hysteresis_c` /
`thermostat.hysteresis_c`.

### Finding 2 — DEFECT: `time_at_current_speed_s` not checkpointed for two-speed AC and
  HP heater

**Files:**
- `crates/hares-equipment/src/hvac/hvac_core.rs:197` (field declaration)
- `crates/hares-equipment/src/hvac/staging.rs:65,94,118,124` (accumulates and gates
  speed changes)
- `AirConditionerState` at `air_conditioner.rs:107` — field absent
- `HeaterState` at `heat_pump/heater.rs:136` — field absent

`HvacEquipment.time_at_current_speed_s` accumulates each step and is compared against
`min_time_per_speed_s` (default 300 s) to prevent rapid stage hunting in two-speed
equipment. After restore the field is reset to 0, so the unit will immediately accept a
speed-stage change even if it had been locked in the current stage for 299 s at
checkpoint time. This permanently breaks min-stage-hold protection for the remainder of
the first 300-s window after restore.

**Required fix:** add `time_at_current_speed_s: f64` to `AirConditionerState` and
`HeaterState`; save from `hvac.time_at_current_speed_s` and restore to it.

### Finding 3 — MINOR: `PV.last_ac_power_kw` not checkpointed

**File:** `crates/hares-equipment/src/pv/mod.rs:138,492`

`PV.last_ac_power_kw` is read in `update_control` to determine whether the PV system is
`Standby` or `Off`:

```rust
fn update_control(&mut self, _env: &EnvironmentState) -> OperatingMode {
    if self.last_ac_power_kw > 0.0 {
        OperatingMode::Standby
    } else {
        OperatingMode::Off
    }
}
```

After restore this will be 0.0, so `update_control` reports `Off` instead of `Standby`
for the first step following restore even if the PV was actively generating. This is a
single-step error in the reported `OperatingMode`; AC output power is unaffected because
it is recomputed from irradiance each step.

**Required fix:** add `last_ac_power_kw: f64` to `PvCheckpoint`; save and restore it.

---

### Finding 4 — MINOR: `HeatPumpHeaterCore.last_heating_rtf` not checkpointed

**File:** `crates/hares-equipment/src/hvac/heat_pump/heater.rs:104`

`last_heating_rtf` is read by the HP system coordinator via `last_heating_rtf()` and
passed as `companion_heating_rtf` to the companion cooler's `step()` call for crankcase
heater power accounting (`max(cooling_rtf, heating_rtf)`). After restore this field is
0.0, so the crankcase heater calculation on the first post-restore step assumes the
heating coil was idle even if it was running at checkpoint time. This is a one-step error
in crankcase heater power.

`last_heating_rtf` is recomputed unconditionally at the end of every `step()` call (line
612), so the error does not persist beyond the first step.

**Required fix:** add `last_heating_rtf: f64` to `HeaterState`; save and restore it.

### Fields confirmed benign (transient or static, correctly excluded)

- `Battery.custom_ocv`, `Battery.custom_u_neg` — static flags set by `set_ocv_table()` /
  `set_u_neg_table()`; these are call-site invariants, not simulation state.
- `EV.away_charge_actual_kw` — recomputed in every `step()` branch; correctly hardcoded
  to 0.0 in `load_state`.
- `EV.v2l_active`, `EV.v2l_power_kw` — recomputed in `step()`; correctly reset to
  false/0.0 in `load_state`.
- `CoolingCore.ctrl_load_fraction` — reset to 1.0 at the start of `update_control`;
  transient.
- `HeatPumpHeaterCore.ctrl_load_fraction` — same pattern as above.
- `HeatPumpWH.ctrl_load_fraction` — same pattern.
- `ResistanceWH.ctrl_load_fraction` — same pattern.
- `GasWH.ctrl_load_fraction` — same pattern.
- `TanklessWH.ctrl_load_fraction` (via `power_limit_w`) — same pattern.
- `HvacEquipment.static_setpoints` — set once at `init()`, never mutated by control
  signals; `runtime_setpoints` handles runtime overrides and is checkpointed.
- `HvacEquipment.heating_setpoint_source` / `cooling_setpoint_source` — always
  `ColumnRef` (stateless) or `DailyProfile` (stateless); no cursor state to preserve.
- Water heater `draw_l_per_min_source` / `mains_temp_c_source` — always `ColumnRef`;
  stateless.
- `CoolingCore.last_cooling_rtf` — recomputed each step from PLR; transient.
- `HvacEquipment.time_at_current_speed_s` for single-stage equipment (furnace, boiler,
  baseboard) — `min_time_per_speed_s` is 0 for these variants; the guard is trivially
  satisfied.
- `HvacEquipment.mode_start_at` for boilers/baseboards — these have no `min_on_time_s` /
  `min_off_time_s` configuration; the field is unused.

### Infrastructure notes

- The `DwellingCheckpoint` container (`checkpoint.rs`) is complete; it covers
  `equipment_states`, `envelope_state`, `humidity_states`, `fluid_states`, RNG state,
  `thermal_last_u`, and `lwr_t_prev_c`. No gaps at the dwelling level.
- The `save_postcard` / `load_postcard` helpers are correct; they use postcard and are
  panic-free for the field types in use.
- The `delegate_equipment!` macro correctly delegates `save_state` / `load_state` to the
  inner field; wrapper types (`AirConditioner`, `ASHPHeater`, etc.) do not introduce
  additional checkpoint state.

## Recommended Tests

For each DEFECT-level finding add a deterministic unit test that:

1. Creates the equipment and applies a control signal that mutates the missing field
   (e.g., `ThermalSetpoint` with a non-default `deadband_c`; or a speed-change scenario
   that runs for < `min_time_per_speed_s`).
2. Calls `save_state()` and `load_state()` on a fresh instance.
3. Asserts the restored field equals the saved value.
4. Runs one simulation step and asserts the behavior (mode switch, stage transition) is
   identical to the pre-checkpoint behavior.

For the MINOR PV finding, test that `update_control` returns `Standby` (not `Off`)
immediately after a `load_state()` when the saved `last_ac_power_kw` was > 0.

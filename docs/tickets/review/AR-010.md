## Background/Context

The `hares-control` crate is the bridge between actors (who emit `ControlSignal`) and equipment (who consume them). It routes by `EndUse` and by equipment name. No existing ticket systematically audits this crate. A routing bug here silently delivers the wrong control to the wrong equipment.

## Investigation Instructions

1. **Read `dispatch.rs` end-to-end:**
   - How does `DispatchTarget::ByEndUse` resolve to equipment instances?
   - When two equipment share an EndUse, does the dispatch broadcast to both or pick one?
   - What is the priority ordering when multiple actors emit conflicting signals for the same equipment in the same timestep?

2. **Read `dwelling/mod.rs` dispatch integration:**
   - Line ~318 contains "higher priority signal overwriting earlier signal for same equipment" — trace the priority mechanism.
   - Is there a signal queue or is it last-writer-wins?

3. **Compare with OCHRE's control routing:**
   - OCHRE routes controls via `equipment.update_external_control(control_signal)` per equipment.
   - Does HARES's dispatch layer produce equivalent behavior?

4. **Check actor telemetry:**
   - Per project requirements, actors must emit telemetry for dispatched actions/controls.
   - Does the dispatch layer log or record what signals were routed to which equipment?

## Findings

### F-1 — BUG: `conflicts_with` never detects cross-variant conflicts

**Severity: HIGH**

**File:** `crates/hares-control/src/dispatch.rs:52-58`

`DispatchTarget::conflicts_with` returns `false` for all mixed-variant pairs regardless of whether they resolve to the same equipment:

```rust
_ => false,  // ByName("hvac") vs ByEndUse(HVAC_HEATING) → false, even if same equipment
```

This means the conflict-detection logic in `ControlDispatcher::drain_tiers` (`crates/hares-core/src/dwelling/mod.rs:311-313`) will never log a debug warning and never set `overwrote_earlier = true` when one actor sends `ByEndUse(HVAC_HEATING)` at `Schedule` priority and another sends `ByName("Furnace")` at `Grid` priority. The signals still both reach the equipment (because routing is independent of conflict detection), but the observer's `DispatchedSignal::overwrote_earlier` field will be wrong (always `false`), making the `observe` feature unreliable for debugging cross-variant conflicts.

The `seen_targets` mechanism is described in the doc comment as detecting "control signal conflicts within a single timestep" — a cross-variant conflict is a conflict and must be detected. There is a test `conflicts_with_different_variants_never_conflict` that explicitly asserts this broken behavior is intentional (`crates/hares-control/src/dispatch.rs:166-170`), which locks in the defect.

**Fix:** `conflicts_with` must resolve both targets against the equipment registry to check if they resolve to any overlapping instances. Because the `ControlDispatcher` operates on `&mut [Box<dyn Equipment>]`, the simplest fix is a `conflicts_with_equipment` helper in `drain_tiers` that checks both variants against the equipment list rather than comparing targets abstractly. The `conflicts_with` method on `DispatchTarget` itself cannot know the equipment list and should either be removed or clarified to only apply to same-variant comparison.

### F-2 — GAP: Public `apply_control` API hardcodes `Schedule` priority

**Severity: MEDIUM**

**Files:**
- `crates/hares-core/src/dwelling/mod.rs:1084-1090` (`Dwelling::apply_control`)
- `crates/hares-core/src/dwelling/mod.rs:1103-1126` (`Dwelling::apply_control_validated`)
- `crates/hares-core/src/dwelling/mod.rs:1129-1135` (`Dwelling::queue_end_use_control`)
- `crates/hares-fleet/src/fleet.rs:388-394` (`Fleet::apply_control`)

All three public control-injection APIs hardcode `priority: Default::default()` which is `PriorityTier::Schedule`. External callers (Python, HELICS, fleet) therefore always inject signals at the lowest tier with no way to express `UserOverride`, `Grid`, or `Safety` priority from outside the Rust actor model. This is a capability gap for DR programs and grid-edge controllers using the Python or fleet APIs who need to express higher-priority overrides. The typed `queue_dispatch(DispatchRequest)` API exists and exposes priority, but it is not exposed in the Python bindings (`crates/hares-python/src/py_dwelling.rs`), leaving no priority-aware path for Python actors.

**Fix:** Expose `queue_dispatch` (or an equivalent `apply_control_with_priority`) in `PyDwelling` with a `PriorityTier` parameter. The fleet `apply_control` should similarly accept an optional priority.

### F-3 — BUG: `ByEndUse` broadcasts to ALL matching equipment — OCHRE deliberately does not

**Severity: MEDIUM**

**Files:**
- `crates/hares-core/src/dwelling/mod.rs:345-356` (`route_request` ByEndUse branch)
- `vendors/OCHRE/ochre/Dwelling.py:241-244` (OCHRE's `update_model`)

HARES `ByEndUse` routing calls `apply_to_matching` which iterates all equipment and delivers the signal to every instance whose `end_use` field matches. OCHRE's equivalent (`update_model`, lines 241-244) copies the control signal keyed by end-use into the individual equipment's dict only if that equipment's name is not already in the `control_signal` dict — it therefore gives per-equipment signals priority over end-use signals, and still broadcasts to all matching equipment when no per-equipment override is present. So far this matches HARES.

However, OCHRE raises an error at construction time when more than one equipment shares `HVAC Heating`, `HVAC Cooling`, or `Water Heating` (`vendors/OCHRE/ochre/Dwelling.py:145-146`), and issues a warning for other duplicates. HARES has no equivalent guard: a `ByEndUse(HVAC_HEATING)` dispatch with two matching HVAC units silently broadcasts to both, which is almost certainly wrong physics (two heating setpoints applied simultaneously). HARES `get_equipment_by_end_use` has no analog.

**Fix:** Add a construction-time check (or at least a warning) when multiple equipment share `HVAC_HEATING`, `HVAC_COOLING`, or `WATER_HEATING`. This mirrors OCHRE's behavior and prevents silent physics errors in pathological configs.

### F-4 — GAP: Actor telemetry for dispatched decisions is feature-gated behind `observe`

**Severity: MEDIUM**

**Files:**
- `crates/hares-core/src/dwelling/mod.rs:282-298` (`dispatch_into_observed`, `#[cfg(feature = "observe")]`)
- `crates/hares-core/src/observer.rs:136-153` (`DispatchCapture`, `DispatchedSignal`)
- `crates/hares-core/src/dwelling/mod.rs:1879-1891` (step dispatch site)

Project memory (`feedback_actor_telemetry.md`) requires actors to emit telemetry for dispatched actions/controls. The dispatch layer does capture full per-signal telemetry (`DispatchedSignal` with `target`, `signal`, `priority`, `overwrote_earlier`, `delivered`), but only when the `observe` feature is enabled and `enable_observer()` has been called. In the default build (no `observe` feature), dispatch is a silent `drain_tiers(…, |_,_,_|{})` call: no logging, no structured record, no telemetry visible to Python users.

The tracing call at `mod.rs:315-319` emits a `tracing::debug!` only when a higher-priority overwrite is detected — it is silent for every successful delivery. In production runs where `observe` is not compiled in, there is no way to inspect what signals were dispatched, to which equipment, and at what priority. This creates an observability blackout for DR experiments and fleet simulations running without the debug feature.

**Fix:** The dispatch layer should emit at minimum a `tracing::trace!` per delivered signal (unconditionally, not feature-gated) so that `RUST_LOG=trace` users get dispatch visibility without recompiling. The full `DispatchCapture` observer path is appropriate for deep debugging and can stay feature-gated.

### F-5 — GAP: `PRIORITY_TIER_COUNT` is a runtime assertion, not a compile-time guarantee

**Severity: LOW**

**File:** `crates/hares-control/src/dispatch.rs:8-9, 122-127`

`PRIORITY_TIER_COUNT = 4` is a plain constant, and its match to the enum variant count is checked only in a `#[test]` at runtime. Adding a new `PriorityTier` variant without updating the constant compiles cleanly, producing a `by_tier` array that is too small at runtime (out-of-bounds index in `queue()`). Rust arrays are fixed at compile time, so the index `request.priority.index()` will panic or exhibit UB in unsafe builds.

**Fix:** Use a `const` assertion or the `static_assertions` crate: `const_assert_eq!(PRIORITY_TIER_COUNT, std::mem::variant_count::<PriorityTier>())` (stabilised in Rust 1.86). Alternatively, replace the hand-rolled constant with `PriorityTier::COUNT` derived via a macro that matches the enum definition.

### F-6 — GAP: `Actor` trait has no `telemetry()` method

**Severity: LOW**

**File:** `crates/hares-core/src/actor.rs:43-66`

The `Actor` trait exposes only `name()`, `interests()`, and `decide()`. There is no `telemetry()` method, so an actor cannot report its internal state (e.g., BMS mode, EV connection state, TOU price tier decision) as structured data alongside equipment telemetry. The project memory requirement (`feedback_actor_telemetry.md`) says actors must emit telemetry for dispatched actions/controls.

Currently the only observable output from an actor per-step is the set of `DispatchRequest`s it pushes to `actor_dispatch_buf`, which are visible only through the `observe` feature. There is no mechanism for an RL gym, a HELICS co-simulator, or a Python callback to query "what did actor X decide this step and why?" without enabling the full observer.

**Fix:** Add `fn telemetry(&self) -> Option<Telemetry>` with a default `None` implementation to the `Actor` trait. Built-in actors (BMS, EvDriver) should override it to report their internal decision state. The dwelling should collect actor telemetry alongside equipment telemetry in `DwellingTelemetry`.

### F-7 — ACCEPTABLE DIFFERENCE: Tier ordering is last-write-wins, not deduplication

**Severity: INFO**

**File:** `crates/hares-core/src/dwelling/mod.rs:251-327`

HARES uses a last-write-wins priority model: signals are drained from `Schedule` (tier 0) through `Safety` (tier 3), and every signal fires against the equipment in order. Equipment `apply_control_unchecked` is expected to be overwrite-safe. A `Safety` signal arriving after a `Schedule` signal to the same equipment will overwrite the earlier state.

OCHRE has no priority system: `update_model` iterates equipment in registration order, calling `update_external_control` once per equipment per step with a merged dict. There is no concept of priority tiers or conflict resolution; the last Python caller to write a key into the `control_signal` dict wins by dict assignment.

HARES's tier model is strictly more expressive than OCHRE and the behavior is well-specified and tested (`dispatch_same_tier_same_target_last_write_wins` at line 3683, `dispatch_by_end_use_targets_all_matching_equipment` at line 3719). This is an intentional, correct improvement over OCHRE's flat control dict.

### F-8 — GAP: Auto-registered actors use deterministic but unconfigurable seed derivation

**Severity: LOW**

**File:** `crates/hares-core/src/dwelling/mod.rs:2658-2661`

When `build_actors_from_seeds` auto-creates an `EvDriverActor`, the RNG seed is derived from the equipment name bytes:

```rust
let seed_val = name
    .as_bytes()
    .iter()
    .fold(0u64, |acc, &b| acc.wrapping_mul(31).wrapping_add(b as u64));
```

Two dwelling instances with identically named EVs (e.g., "Electric Vehicle") will produce identical behavioral schedules. In fleet mode this generates correlated driving patterns across the fleet, which may bias aggregate DR results. The project memory (`feedback_deterministic_tests.md`) requires deterministic tests, but fleet-scale production results should have per-dwelling diversity. There is no way for a caller to inject a per-dwelling seed via the `ActorSeed` protocol.

**Fix:** Include a dwelling-level seed (e.g., `bldg_id` or a monotonic counter from the `Dwelling` struct) in the fold so that fleet-scale seeds are uncorrelated. The `ActorSeed::Ev` variant should carry an optional `seed_override` field so the Python layer can control this.

### F-9 — IMPROVEMENT: `apply_control_validated` eagerly applies state-update signals then re-queues them

**Severity: LOW**

**File:** `crates/hares-core/src/dwelling/mod.rs:1103-1126`

The comment at line 1094-1099 explains that `is_immediate_state_update` signals (e.g., `EvPlugIn`) are applied immediately so subsequent validated signals in the same timestep see the updated state, and are then also queued for the dispatcher so the `observe` capture fires. This means such signals are applied twice: once eagerly in `apply_control_validated` and once via the dispatcher during `dispatch_into`.

This is documented as "re-applying an idempotent state-assignment is safe," but it creates a correctness dependency on all `is_immediate_state_update` signals being truly idempotent. If any equipment's `apply_control_unchecked` for such signals accumulates or has side effects (e.g., incrementing a counter), the double-application will produce wrong behavior. There is no compile-time or test-time enforcement that `is_immediate_state_update` signals are unconditionally idempotent.

**Fix:** Add a comment to `apply_control_unchecked` implementations for EV (and any future equipment using `is_immediate_state_update`) explicitly stating the idempotency requirement, and add a unit test that calls `apply_control_validated` with such a signal twice and asserts state is equivalent to calling it once.

## Recommended Tests

### T-1: Cross-variant conflict detection
Registers one `ByEndUse(HVAC_HEATING)` signal at `Schedule` and one `ByName("Furnace")` at `Grid` where `"Furnace"` has `end_use == HVAC_HEATING`. Enables the observer. Asserts that both `DispatchedSignal` entries are captured, that the `Grid` signal's `overwrote_earlier` is `true`, and that the equipment's final state reflects the `Grid` signal. This fails today because `conflicts_with` returns `false` for cross-variant pairs.

### T-2: `ByEndUse` broadcast count
Constructs a dwelling with two pieces of equipment that share the same `EndUse` (valid for custom/non-critical end uses). Dispatches `ByEndUse` and asserts both receive the signal. Separately confirms that a `ByEndUse(HVAC_HEATING)` with two matching HVAC units triggers a warning.

### T-3: Priority tier respected from Python API
Verifies that a `UserOverride` or `Grid` priority signal can be expressed through the `PyDwelling` interface once `queue_dispatch` is exposed. Currently not possible; this test should be added as a specification test to drive the fix for F-2.

### T-4: `is_immediate_state_update` idempotency
Calls `apply_control_validated` with an `EvPlugIn` signal twice in succession on the same equipment. Asserts final equipment state is identical after both applications (no double-application side effects).

### T-5: Dispatch trace-level logging
With `tracing_test` or equivalent, asserts that every delivered signal produces at least one `trace!` log event containing the target and signal type, in the default (no-`observe`-feature) build.

### T-6: Fleet EV seed diversity
Constructs a fleet with N dwellings all having an `Electric Vehicle` equipment. Steps all dwellings for one day. Asserts that EV drive-departure schedule diversity across dwellings is non-zero (at least two different departure times are represented). This fails today because the name-derived seed is identical for all identically-named equipment.

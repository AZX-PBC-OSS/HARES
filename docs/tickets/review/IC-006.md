## Background/Context

Gas water heaters have a single burner. Ideal capacity should compute the duty cycle
(0–1) needed to maintain setpoint given current tank state and draw demand.

## Investigation Instructions

1. Read OCHRE `GasWaterHeater.solve_ideal_capacity()` — is it the base WH class?
2. Read HARES `gas.rs` — ideal capacity implementation.
3. Compare duty cycle computation.
4. Check: does ideal mode account for recovery efficiency (eta_c)?


## Findings

### F1 — No ideal capacity mode: binary on/off only (HIGH)

HARES `GasWH` has no `solve_ideal_capacity` path. The OCHRE base `WaterHeater` class
auto-enables `use_ideal_capacity` when `time_res >= 5 minutes` (WaterHeater.py:52-53).
In ideal mode OCHRE computes how much heat is needed to bring the lower node to
setpoint in the next timestep and back-calculates a fractional duty cycle
(WaterHeater.py:193-211). HARES `step()` always uses binary on/off: the burner runs at
`burner_input_w * duty` (gas.rs:414-415) where `duty` comes from an externally provided
`DutyCycle` control signal or defaults to 1.0 — never from an internal energy-balance
solve. At 5-minute or coarser timesteps this produces overshoots and then dead time that
add up to systematic energy and temperature errors. The gap is confirmed by the Review
Notes in the ticket stub.

### F2 — `capacity_rated` semantic mismatch: OCHRE vs HARES (MEDIUM)

OCHRE `capacity_rated` is "maximum heat delivered to the tank, in W" (WaterHeater.py:67).
The duty cycle is dimensioned against delivered heat (`duty = h_desired / capacity_rated`),
and fuel power is back-computed as `delivered_heat / efficiency` (WaterHeater.py:276).
HARES names the field `burner_input_w` and treats it as thermal input (fuel-side) power.
Delivered heat then follows: `gross_heat_w = burner_input_w * efficiency`, and flue loss
is subtracted from that (`tank_heat_w = gross_heat_w * (1 - flue_loss_fraction)`,
gas.rs:426-428). The semantics are consistent internally, but the config key
`heating_capacity_w` (gas.rs:291) is read as input power. If a HPXML file or OCHRE
config supplies `Capacity (W)` (which is delivered heat), ingesting it as `heating_capacity_w`
will silently over-state rated fuel consumption by a factor of `1 / efficiency`. The
`hares-io` HPXML resolver should be checked to confirm which value it maps.

### F3 — Thermostat sensor node vs OCHRE node selection (MEDIUM)

OCHRE's single-mode (gas) thermostat (`run_thermostat_control`, WaterHeater.py:213-224)
reads from `t_lower_idx`, which is the bottom node of the tank (node 10 of 12, or node N
of N for smaller tanks). For N >= 3 it averages the bottom node with the node above it
(WaterHeater.py:218-219). HARES `should_fire()` reads exclusively `node_temps()[burner_node]`
(gas.rs:216) — a single node with no averaging. `burner_node` defaults to `n_nodes - 1`
(gas.rs:116-118, 260-262), which is the bottom node, so the node selection matches. The
averaging of adjacent nodes is absent. For 6-node tanks the practical impact is small but
the deviation exists and will produce marginally earlier cutoff (less heat delivered) vs
OCHRE when the bottom node is cooler than the node above it during a recovery cycle.

### F4 — Flue loss double-counted against efficiency (LOW)

HARES computes `gross_heat_w = burner_input_w * efficiency` and then subtracts flue loss:
`tank_heat_w = gross_heat_w * (1 - flue_loss_fraction)` (gas.rs:426-428). OCHRE does not
model a separate flue loss fraction for the storage gas WH; it uses a single `efficiency`
that already represents the fraction of fuel input delivered to the water (WaterHeater.py:66,
276). Having both `efficiency` and `flue_loss_fraction` active simultaneously reduces the
effective thermal efficiency to `efficiency * (1 - flue_loss_fraction)`. With defaults of
0.78 and 0.10, effective tank heating efficiency is 0.702 rather than 0.78. This is
physically sound if the intent is that `efficiency` is combustion efficiency (ratio of
heat released to fuel HHV) and `flue_loss_fraction` is the fraction of that heat lost up
the stack rather than transferred to the water. However the field names in init
(`thermal_efficiency`, `EnergyFactor`, `UniformEnergyFactor`, gas.rs:339-347) suggest
users will supply an EF/UEF, which already accounts for all losses including standby and
flue. If that interpretation is correct, applying `flue_loss_fraction` on top of EF
double-counts flue losses. The intent needs to be documented and validated against rated
EF test-procedure definitions; a unit test that checks the implied standby EF at default
parameters against the DOE test procedure result would catch miscalibration.

### F5 — Pilot fuel is always added to fuel port regardless of burner state (LOW / CORRECT)

`fuel_input_w = burner_input_w + self.pilot_power_w` (gas.rs:463). The pilot contributes
continuously even when the burner is off, which is correct for standing-pilot units. The
test `gas_wh_dr_grid_emergency_forces_off` explicitly verifies this. OCHRE does not model
standing pilot at all for the storage gas WH class. This is a deliberate HARES
improvement; no action required.

### F6 — `ctrl_load_fraction` not included in `mode_override` guard (LOW)

`should_fire()` guards on `dr_load_fraction <= 0.0`, `mode_override == Off`, and
`duty_cycle <= 0.0` (gas.rs:210-213). `ctrl_load_fraction` is not checked here —
it is applied later in the product `duty_cycle * dr_load_fraction * ctrl_load_fraction`
(gas.rs:412-413). So when `ctrl_load_fraction == 0.0` the step computes
`burner_input_w = 0.0` (correct) but `burner_on` is still set to `true` by
`should_fire()` if the thermostat calls for heat (gas.rs:396). The fan is then enabled
(`rated_fan_electric_w = fan_power_w`, gas.rs:471-474). This means a `LoadFraction: 0.0`
control signal suppresses fuel and heat delivery but still draws fan electricity.
Whether this is intentional (fan stays on to maintain airflow during curtailment) needs
a decision and documentation; if unintentional, `ctrl_load_fraction <= 0.0` should be
added to the `should_fire` guard.

## Recommended Tests

**T1 — Ideal-capacity gap regression (5-minute timestep energy balance)**
Verify that at a 5-minute timestep, stepping from a tank state 3°C below setpoint with
zero draw produces a `burner_power_w` that brings the bottom node to within 0.5°C of
setpoint in exactly one step. This will currently fail (burner fires full-rate and
overshoots) and documents the gap until ideal capacity is implemented.

**T2 — `heating_capacity_w` is fuel-side input, not delivered heat**
Configure a GasWH with `heating_capacity_w = 11000`, `burner_efficiency = 0.78`,
`flue_loss_fraction = 0.0`. Step one second with burner on. Assert
`telemetry[FUEL_INPUT_W] == 11000` and `telemetry[BURNER_POWER_W] == 11000` (fuel
input), and that heat injected to the tank equals `11000 * 0.78`. This pins the semantic
contract of the config key.

**T3 — Effective tank efficiency with both parameters active**
With `burner_efficiency = 0.78` and `flue_loss_fraction = 0.10`, step one second and
assert that heat delivered to the tank equals `burner_input_w * 0.78 * 0.90 ≈ 0.702 *
burner_input_w`. Document the multiplication in a comment so future callers understand
that supplying an EF as `burner_efficiency` and leaving `flue_loss_fraction` at default
is incorrect.

**T4 — `LoadFraction: 0.0` disables fan electricity**
Apply `ControlSignal::LoadFraction { fraction: 0.0 }` to a cold-tank GasWH. Step and
assert `fan_electric_w == 0.0` once the expected behavior of the fan under full load
curtailment is decided. Test should encode the decision either way.

**T5 — Thermostat averaging parity: 6-node vs OCHRE**
For a 6-node GasWH where node N-1 (burner node) is 1°C below setpoint−deadband but
node N-2 is at setpoint, assert whether `should_fire()` returns `true`. This pins the
divergence from OCHRE's two-node average and documents the single-node behavior as a
known difference.

## Review Notes

Gas WH has no ideal capacity mode at all — `use_ideal` flag is not checked in `gas.rs`. Always uses binary duty cycle. This is a GAP vs OCHRE for 5-minute+ timesteps. Reframe: don't presuppose ideal mode exists — confirm its absence first.

## Background/Context

OCHRE WH duty cycle: for ERWH, a single total ER duty cycle is optimally split
between upper and lower elements when `use_ideal_capacity=True`. For HPWH, separate
HP and ER duty cycles can be specified via `DutyCycleComponent`.

## Investigation Instructions

1. Read OCHRE `WaterHeater.run_duty_cycle_control()`.
2. Read HARES WH duty cycle handling in resistance.rs and heat_pump_wh.rs.
3. Is `DutyCycleComponent::Compressor` vs `BackupElement` properly routed?
4. Compare upper/lower split logic.

---

## Findings

### F1 — CRITICAL: ERWH ideal-capacity path ignores lower element when upper is active (incorrect power suppression)

**File:** `crates/hares-equipment/src/water_heater/resistance.rs:450-473`

In the ideal-capacity branch, HARES picks exactly one active element (upper if
`upper_element_on`, else lower) and computes ideal power for that one node only:

```rust
let (active_w, element_node) = if self.upper_element_on {
    (self.upper_element_power_w, self.upper_node)
} else {
    (self.lower_element_power_w, self.lower_node)
};
```

This is always exclusive: the `if`/`else` means even in `Simultaneous` mode, when
both `upper_element_on` and `lower_element_on` are true, only the upper element's
ideal capacity is calculated and only the upper element delivers power during an
ideal-capacity step. The lower element duty is silently suppressed to zero even
though `lower_element_on == true`.

OCHRE `ElectricResistanceWaterHeater.solve_ideal_capacity()` (line 376) computes
separate ideal heat demands for upper and lower zones and assigns independent duty
cycles:

```python
d_upper = min(max(h_upper / self.capacity_rated, 0), 1)
d_lower = min(max(h_lower / self.capacity_rated, 0), 1 - d_upper)
self.duty_cycle_by_mode = {"Upper On": d_upper, "Lower On": d_lower, ...}
```

Both elements can deliver heat in the same timestep, with upper getting priority
on available capacity headroom. HARES cannot replicate this — it fires at most one
element per ideal-capacity step.

Under MasterSlave mode this is never visible because the lower element is locked
out when upper is on, and in the default thermostat path the two elements never
fire simultaneously. The gap only manifests for `Simultaneous` mode with coarse
timesteps. However the `ideal_capacity_for_node` call also uses only the
**element's local node** rather than the full-tank heat deficit from that level
downward (see F2), which is a second deviation in both modes.

### F2 — HIGH: `ideal_capacity_for_node` computes single-node deficit, not zone deficit

**File:** `crates/hares-equipment/src/water_heater/tank.rs:268-285`

HARES `ideal_capacity_for_node` estimates the power needed to restore a **single
node** to setpoint after one standby-loss step:

```rust
let t_off = t_now - ua * (t_now - ambient_c) * dt_s / mcp;
let deficit_k = (setpoint_c - t_off).max(0.0);
(deficit_k * mcp / dt_s).max(0.0)
```

OCHRE `solve_ideal_capacity` (lines 382–398) computes the dot product of
temperature deficit × thermal capacitance across **all nodes at or above the
element's level**, capturing the full stored-energy deficit in that zone of the
tank:

```python
h_upper = np.dot(
    set_states[:t_upper_idx+1] - off_states[:t_upper_idx+1],
    self.model.capacitances[:t_upper_idx+1],
) / dt_s
```

For a 6-node tank the upper zone covers 1 node and the lower zone covers 5 nodes,
so the HARES estimate for the lower element is approximately 5× too small for large
temperature deficits. The error shrinks as the tank approaches setpoint and grows
during recovery from a large draw event.

Consequence: at coarse timesteps HARES under-dispatches the lower element during
recovery, extending reheat time and causing parity error with OCHRE on energy
consumption metrics.

### F3 — HIGH: Upper thermostat does not apply averaging; lower sensor averaging condition is inverted

**File:** `crates/hares-equipment/src/water_heater/resistance.rs:197-230`

OCHRE `run_thermostat_control` (line 405) reads the upper element temperature
directly from node state:

```python
t_upper = self.model.states[self.t_upper_idx]
```

No averaging — correct.

For the lower sensor, OCHRE averages with the node **above** the lower node (index
`t_lower_idx - 1`) when `n_nodes > 2`. HARES does the same at line 225–226 with
the condition `n >= 3 && self.lower_node > 0`.

However OCHRE's node numbering is 1-based and it maps `lower_node = n_nodes`
(the last node), so `t_lower_idx - 1` is always the second-to-last node. HARES
uses 0-based indexing and maps `lower_node = n_nodes - 1`. Therefore `lower_node -
1` in HARES is the same relative position — this part is correct.

The remaining subtle issue: the condition `self.lower_node > 0` will be `false`
only when `lower_node == 0`, meaning both lower_node and upper_node are at node 0
(single-node-effective tank). That edge case correctly falls through to the bare
temperature. This is consistent with OCHRE's `n_nodes <= 2` guard. **No bug here**,
but the condition `n >= 3` is redundant with `self.lower_node > 0` for standard
configs — minor clarity issue, not a correctness problem.

### F4 — HIGH: ERWH thermostat upper-priority logic diverges from OCHRE

**File:** `crates/hares-equipment/src/water_heater/resistance.rs:416-426`

OCHRE `run_thermostat_control` (line 414–422):

```python
lower_threshold_temp = self.setpoint_temp - self.deadband_temp
if t_upper < lower_threshold_temp or (self.mode == "Upper On" and t_upper < self.setpoint_temp):
    return "Upper On"
if t_lower < lower_threshold_temp:
    return "Lower On"
if self.mode == "Upper On" and t_upper > self.setpoint_temp:
    return "Off"
if t_lower > self.setpoint_temp:
    return "Off"
```

Key behaviour: upper element turns on when the upper node is **below the deadband
floor**, OR when it is **already running and below setpoint** (sticky hysteresis on
upper only, not lower). The lower element turns on only when upper is satisfied
AND lower is below the deadband floor.

HARES `thermostat_calls` feeds both elements through the same generic
`hysteresis_call` with identical arguments — the same setpoint, the same deadband,
the same `currently_on` flag:

```rust
let upper_call = hysteresis_call(upper_temp, effective_sp, self.deadband_c, self.upper_element_on);
let lower_call = hysteresis_call(lower_temp, effective_sp, self.deadband_c, self.lower_element_on);
```

The mutual lockout happens after the fact in `update_control`:

```rust
self.lower_element_on = !self.upper_element_on && lower_call;
```

The functional result for MasterSlave mode is nearly equivalent to OCHRE, but
there is one divergence: OCHRE's upper thermostat uses a **wider effective deadband
for turn-on** than the lower thermostat, because the upper only fires when it falls
below `setpoint - deadband`, and its hysteresis latch holds it on until it reaches
`setpoint`. HARES implements the same logic via `hysteresis_call`, so this matches.

The actual divergence is that OCHRE's lower thermostat has no latch: it can only
be "Lower On" when `t_lower < setpoint - deadband` (strict off trigger when `t_lower
> setpoint`). HARES's `hysteresis_call` for the lower element latches on until
`t_lower < setpoint`, giving the lower element a wider operating range than OCHRE
intends. This means HARES keeps the lower element on longer per cycle, over-heating
the lower zone by up to `deadband_c / 2` on average.

**Concrete difference:** In OCHRE, once the lower element turns on, it fires until
`t_lower` reaches `setpoint`. In HARES, `hysteresis_call(lower_temp, sp, db,
currently_on=true)` fires while `lower_temp < sp` — this is the same condition.
So both implementations turn the lower element off at `t_lower >= setpoint`. **This
part matches.** However in OCHRE, the lower element turns on only when `t_lower <
setpoint - deadband`. In HARES when `currently_on=false`, `hysteresis_call` fires
when `t_lower <= setpoint - deadband`. The `<=` vs `<` for off-to-on is a deliberate
HARES deviation (documented at line 156–160) and is a minor physical preference, not
a behavioural bug. **This finding is withdrawn at the thermostat level** — the
implementations are functionally equivalent for MasterSlave with the noted minor
boundary preference.

### F5 — MEDIUM: Single scalar `duty_cycle` applied to both upper and lower elements — no independent per-element external duty cycle for ERWH

**File:** `crates/hares-equipment/src/water_heater/resistance.rs:441-473`

OCHRE's `run_duty_cycle_control` for ERWH accepts a single total ER duty cycle and
splits it optimally between upper and lower via `solve_ideal_capacity`. An external
controller can therefore send one duty cycle value and OCHRE allocates it across
elements based on which zone has more heat deficit.

HARES accepts a single `DutyCycle { on_fraction }` signal and stores it in
`self.duty_cycle`. This scalar scales whichever element wins the thermostat
contest for that step — it does not independently split upper vs lower allocation.
There is no `DutyCycleComponent::UpperElement` or `LowerElement` variant.

This means that when a DR controller sends a partial duty cycle (e.g. 0.5) to an
ERWH, OCHRE may direct 0.3 to the upper zone and 0.2 to the lower zone based on
energy deficit, while HARES directs 0.5 to whichever single element won the
thermostat contest. During recovery from a large draw, OCHRE's split produces faster
simultaneous heating of both zones; HARES serialises them, potentially extending
recovery time by half.

### F6 — MEDIUM: `ideal_capacity_for_node` uses only per-node UA for standby loss, omits inter-node conduction

**File:** `crates/hares-equipment/src/water_heater/tank.rs:280-284`

The ideal capacity calculation does one forward Euler step with only jacket UA:

```rust
let t_off = t_now - ua * (t_now - ambient_c) * dt_s / mcp;
```

This ignores inter-node conduction heat transfer, which can be significant when
adjacent nodes have large temperature gradients (e.g. immediately after a cold draw
fills the bottom). OCHRE's `solve_ideal_capacity` runs the full model forward
(`self.model.update_model()`) to compute `off_states`, capturing all thermal
pathways in the tank's state-space model.

At short timesteps this error is negligible, but at 60-minute coarse timesteps it
can cause the ideal capacity estimate to be measurably wrong during recovery events.

### F7 — LOW: `Simultaneous` mode has no test coverage for ideal-capacity path

**File:** `crates/hares-equipment/src/water_heater/resistance.rs:793+`

Searching the test suite finds no test that sets `element_priority_mode = Simultaneous`
AND `time_res >= 300s`. The bug in F1 (lower element suppressed during ideal-capacity
in Simultaneous mode) would not be caught by existing tests.

## HPWH HP/ER Split Verification

`heat_pump_wh.rs` correctly routes `DutyCycleComponent::Compressor` to
`self.hp_duty_cycle` and `DutyCycleComponent::BackupElement` to `self.er_duty_cycle`
(lines 984–991). Both are independently multiplied with `base_fraction` to produce
`hp_duty` and `er_duty` (lines 683–685). Three dedicated tests cover these cases
(`split_duty_cycle_curtails_compressor_independently`,
`split_duty_cycle_curtails_backup_independently`,
`whole_equipment_duty_cycle_backward_compatible`). **No issues found for HPWH.**

## Recommended Tests

1. **`erwh_simultaneous_ideal_capacity_both_elements_fire`** — Configure
   `element_priority_mode = Simultaneous`, `time_res = 300s`, tank uniformly cold.
   After one step both `upper_element_power_w > 0` and `lower_element_power_w > 0`
   must hold.

2. **`erwh_ideal_capacity_lower_zone_deficit_multi_node`** — 6-node tank, top node
   at setpoint, bottom 5 nodes cold. Single 300s step in ideal-capacity mode.
   Assert delivered power approximately equals the energy deficit of the lower 5
   nodes divided by `dt_s`, within 5% tolerance.

3. **`erwh_duty_cycle_partial_during_recovery`** — Large draw depletes lower zone.
   Apply `DutyCycle { on_fraction: 0.5 }`. Assert that the lower element delivers
   ~50% of rated power during recovery (not 0 due to upper priority stealing the
   duty).

## Background/Context

Currently, equipment is configured at `Dwelling::from_config()` time via HPXML parsing and cannot be modified afterward. Users need to:

1. **Add** equipment not in the HPXML (e.g., add a battery to a home that doesn't have one)
2. **Remove** equipment (e.g., remove gas furnace before adding heat pump)
3. **Replace** equipment (e.g., swap water heater type)
4. **Update** equipment parameters (e.g., change battery capacity, PV tilt)

This enables scenario analysis (what if we add a battery?), equipment upgrade modeling, and programmatic fleet configuration without modifying HPXML files.

**Rust-side methods already exist — this ticket is Python binding work only:**

- `Dwelling::add_equipment(&mut self, eq: Box<dyn Equipment>)` — exists at `dwelling/mod.rs:760`. Appends equipment and calls `refresh_equipment_caches()` internally.
- `Dwelling::clear_equipment(&mut self)` — exists at `dwelling/mod.rs:766`. Clears all equipment and calls `refresh_equipment_caches()`.
- `Dwelling::refresh_equipment_caches(&mut self)` — exists at `dwelling/mod.rs:772`. Rebuilds `equipment_execution_order` and `solver_feedback_actor` dispatch targets. Must be called after any direct mutation.
- `Dwelling::equipment(&self) -> &[Box<dyn Equipment>]` — exists at `dwelling/mod.rs:732`.

**What does NOT exist in Rust yet:**
- `remove_equipment(name: &str)` — needs to be added to `dwelling/mod.rs`
- `replace_equipment(name: &str, new: Box<dyn Equipment>)` — needs to be added
- `next_equipment_id` counter — not present; check whether ID collision is a real risk before deciding if this is required

**`refresh_equipment_caches()` semantics:** Rebuilds the equipment execution order and solver feedback dispatch targets. It does NOT rebuild a `PortSlots` type (none exists on `Dwelling`). It does NOT flush a recorder buffer (no recorder on `Dwelling`; telemetry is collected externally). The docstring in the existing code is authoritative — do not document behaviors beyond what the code does.

## Work to Do

### Rust-side: Missing mutation methods on Dwelling

- [ ] Add `remove_equipment(&mut self, name: &str) -> Result<Box<dyn Equipment>>` to `dwelling/mod.rs`:
  - Finds equipment by name (match on `eq.descriptor().name`), removes from vec
  - Calls `refresh_equipment_caches()`
  - Returns the removed equipment
  - Returns `HaresError` if name not found
- [ ] Add `replace_equipment(&mut self, name: &str, new_equipment: Box<dyn Equipment>) -> Result<Box<dyn Equipment>>` to `dwelling/mod.rs`:
  - Finds equipment by name, swaps in-place
  - Calls `refresh_equipment_caches()`
  - Returns the old equipment
  - Returns `HaresError` if name not found

### Python-side: Equipment construction and mutation

- [ ] Add equipment factory methods to `PyDwelling` that accept LUTs at construction time:
  - `add_battery(name: str, capacity_kwh: float, **kwargs) -> None`:
    - Creates Battery equipment from provided params
    - kwargs: max_charge_kw, max_discharge_kw, initial_soc, min_soc, max_soc, n_series, n_parallel, cell_resistance_ohm, inverter_efficiency, etc.
    - **LUT kwargs accepted at construction:**
      - `charging_curve`: polars DataFrame, numpy dict, Parquet path, or list of (soc, power_fraction) tuples — CC-CV taper curve
      - `ocv_table`: polars DataFrame, numpy dict, Parquet path, or list of (soc, voltage) tuples — open-circuit voltage vs SoC
      - `uneg_table`: polars DataFrame, numpy dict, Parquet path, or list of (soc, potential) tuples — negative electrode potential for degradation
    - If LUT kwargs are provided, they're injected immediately after construction (internally calls `set_equipment_lut` from PY-013)
    - Calls `self.inner.add_equipment(eq)` — `refresh_equipment_caches()` is called automatically by `add_equipment`
  - `add_pv(name: str, capacity_kw: float, tilt: float, azimuth: float, **kwargs) -> None`:
    - Creates PV equipment from provided params
    - kwargs: soiling config, shading config, inverter_efficiency, module_type
    - **LUT kwarg:** `sam_lut_path` — Parquet path for SAM-generated AC power lookup table
  - `add_ev(name: str, capacity_kwh: float, **kwargs) -> None`:
    - Creates EV equipment from provided params
    - kwargs: max_charging_power_kw, `charging_level: ChargingLevel` (enum from PY-005), efficiency, schedule_csv_path, `driver_archetype: DriverArchetype` (enum from PY-005), v2l/v2g config
    - **LUT kwargs accepted at construction:**
      - `charging_curve`: same formats as battery — CC-CV power fraction vs SoC. Internally uses `LutType.ChargingCurve` from PY-005.
      - `pybamm_lut_path`: Parquet path (existing config key, backward compat)
    - If both `charging_curve` and `pybamm_lut_path` provided, `charging_curve` takes precedence
  - These use existing `PyBattery`, `PyPv`, `PyEv` config classes from `py_equipment.rs`, extended with LUT fields
- [ ] Add mutation methods to `PyDwelling`:
  - `remove_equipment(name: str) -> None` — wraps `Dwelling::remove_equipment`; raises `ValueError` on not found
  - `replace_equipment(name: str, **kwargs)` — wraps `Dwelling::replace_equipment`; raises `ValueError` on not found
- [ ] Add parameter update method:
  - `update_equipment(name: str, **kwargs) -> None`:
    - Updates equipment parameters without full replacement
    - For Battery: capacity_kwh, max_charge_kw, max_discharge_kw, soc bounds
    - For PV: capacity_kw (e.g., degradation simulation)
    - For EV: max_charging_power_kw, capacity_kwh
    - Internally: find equipment, apply parameter changes via setter methods (may need new Rust setters)
- [ ] Update `_hares.pyi` with stubs for all new methods
- [ ] Write `tests/python/test_py_equipment_mutation.py`:
  - **Add battery with LUTs**: `add_battery("TestBat", 10.0, charging_curve=[(0,1),(0.8,0.8),(1,0.1)], ocv_table=lfp_df)` → verify equipment has LUT applied → step → verify power tapers at high SoC
  - **Add battery without LUTs**: `add_battery("TestBat", 10.0)` → verify `equipment_names()` includes "TestBat" → step → verify battery telemetry exists
  - **Add PV**: `add_pv("TestPV", 5.0, 30.0, 180.0)` → step with solar → verify PV power output
  - **Add EV with charging curve**: `add_ev("TestEV", 75.0, charging_curve=cc_cv_df)` → verify LUT applied → charge → verify taper
  - **Add EV without LUT**: `add_ev("TestEV", 75.0)` → verify exists in equipment list
  - **Remove**: `remove_equipment("TestBat")` → verify not in `equipment_names()` → step succeeds
  - **Replace**: Add battery → `replace_equipment("TestBat", capacity_kwh=20.0)` → verify new capacity via descriptor
  - **Update**: `update_equipment("TestBat", max_charge_kw=10.0)` → verify changed behavior
  - **Name conflict**: `add_battery("ExistingName", ...)` raises ValueError
  - **Not found**: `remove_equipment("NoSuch")` raises ValueError
  - **Post-mutation step**: After any mutation, `step()` produces valid results
  - **Checkpoint round-trip**: Add equipment → `save_state()` → `load_state()` → verify equipment persists
  - **Multiple mutations**: Add battery + add PV + remove furnace → simulate → verify valid results

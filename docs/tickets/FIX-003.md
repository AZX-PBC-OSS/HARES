# FIX-003: HVAC runs with stale zone temperatures

> **REVISED** (Codex review 2026-03-19): Replaced "intermediate full thermal solve" with zone gain accumulator approach — a second `thermal_solver.resolve()` would double-apply timestep physics and distort integration.

**Severity:** CRITICAL
**Crate:** `hares-core`
**File:** `crates/hares-core/src/dwelling.rs`

---

## Bug

In `dwelling.rs` lines 788-820, equipment executes in two passes: non-thermal (pass 3a, lines 791-803) then thermal/HVAC (pass 3b, lines 809-820). Zone temperatures are NOT updated between the passes. HVAC thermostat decisions use zone temps from the PREVIOUS timestep, not reflecting heat gains from scheduled loads, water heaters, etc. that just ran in pass 3a.

```rust
// dwelling.rs:791-803 -- Pass 3a: non-thermal equipment
for &idx in &indices {
    let stage = self.equipment[idx].descriptor().stage;
    if stage == ExecutionStage::Thermal {
        continue;
    }
    let _ = self.equipment[idx].update_control(&self.latest_env);
    if let Err(err) = self.equipment[idx].step(&self.latest_env, dt, &mut self.ports) {
        // ...
    }
}
self.stage_snapshot = Some(StageSnapshot {
    ports: self.ports.clone(),
});

// dwelling.rs:809-820 -- Pass 3b: thermal equipment (HVAC)
for &idx in &indices {
    if self.equipment[idx].descriptor().stage != ExecutionStage::Thermal {
        continue;
    }
    let _ = self.equipment[idx].update_control(&self.latest_env);
    if let Err(err) = self.equipment[idx].step(&self.latest_env, dt, &mut self.ports) {
        // ...
    }
}
```

The thermal solver `resolve()` only happens AFTER pass 3b (line 836). So HVAC sees zone temperatures from the previous timestep, not reflecting pass 3a contributions (e.g., 5kW scheduled load sensible gains).

## OCHRE Reference

OCHRE `Dwelling.py` runs equipment sequentially. Each equipment's `add_gains_to_zone` is called during its step, and the zone state is updated incrementally. When HVAC equipment runs, it sees the cumulative zone state including all prior equipment gains from the same timestep.

## Fix

**Do NOT run a second `thermal_solver.resolve()` between passes.** That would double-apply timestep physics (solar gains, infiltration, envelope conduction) and distort the integration.

Instead, after pass 3a completes, accumulate the non-thermal equipment sensible and latent gains from the ports into a zone gain preview that the HVAC thermostat can read:

Option A (preferred): After pass 3a, sum all sensible/latent port contributions from non-thermal equipment into a `pending_zone_gains` struct. Pass this to HVAC `update_control()` so the thermostat can compute an estimated zone temp delta: `delta_T_preview = sum(sensible_gains_W) * dt / zone_thermal_mass`. The thermostat uses `T_zone_prev + delta_T_preview` for its control decision.

Option B: Expose accumulated port contributions as a read-only preview on the `Environment` struct. HVAC thermostat reads `env.preview_zone_temp()` which adds the gain-based delta to the last-solved zone temp.

Insert between pass 3a and pass 3b:

```rust
// Accumulate non-thermal equipment gains for HVAC thermostat preview.
// This does NOT resolve the envelope — it only provides a preview of
// zone temp change so HVAC sees current-timestep internal gains.
let pending_gains = self.ports.sum_sensible_gains_w(ExecutionStage::NonThermal);
self.latest_env.set_zone_gain_preview(pending_gains, dt);
```

## Test

- **Integration test:** Dwelling with ScheduledLoad (5kW sensible gain) + Furnace. Verify furnace's duty cycle is LOWER than a dwelling with 0kW load at the same timestep (proving the thermostat sees the heat gain via the preview).
- **Unit test:** Verify `pending_zone_gains` after pass 3a includes the sensible gain from scheduled loads.
- **Unit test:** Verify `preview_zone_temp()` returns a value higher than the previous-timestep zone temp when positive internal gains are present.
- **Negative test:** Verify the thermal solver `resolve()` is called exactly ONCE per timestep (not twice).

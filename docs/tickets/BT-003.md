## Background/Context

`solve_ideal_capacity_for_target` (stepping.rs:24) uses `self.last_u` — the previous timestep's input vector. The dwelling step sequence calls `solver_feedback_actor.collect_and_solve()` at step 1c, well before `thermal_solver.resolve()` at step 4 where `build_input_vector` runs.

At 1-hour resolution with Denver's sharp solar ramps, the ideal capacity estimate is systematically wrong during morning/afternoon transitions. The zone escapes setpoint for a full hour before correction, causing Case 600 cooling to be ~10% under the reference band.

The call graph is clean and linear:
```
DomainSolver::resolve (mod.rs:647)
  → resolve_internal (stepping.rs:68)
    → build_input_vector (mod.rs:402)
```

`resolve_internal` is called **only** from the trait impl. `build_input_vector` is called **only** from `resolve_internal`.

### Critical design constraint: HVAC port staleness

The dwelling step sequence is:
1. `prepare()` — builds input vector u (weather, solar, infiltration, **but ports still have previous-step HVAC values**)
2. `collect_and_solve()` — ideal solver reads `last_u` to back-solve for required HVAC capacity (the HVAC entry in `last_u` is overwritten by the solver — its value doesn't matter, only the background solar/weather/infiltration entries need to be current)
3. Control dispatch — HVAC equipment writes dispatched capacity into `self.ports`
4. `step()` — must integrate with **current** HVAC port values from step 3

Therefore `step()` must rebuild `u` from scratch (calling `build_input_vector` again with post-dispatch ports), NOT reuse the cached `u` from `prepare()`. The double `build_input_vector` cost is accepted for correctness — the first build gives the ideal solver current weather/solar background, the second gives the integrator current HVAC capacity.

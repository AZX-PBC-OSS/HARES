# FIX-023: Scheduled load sensible_gain_fraction defaults to 0.0

> **Clarified** (Codex review 2026-03-19): Fix should populate gain fractions in the IO/HPXML parse layer (not in equipment runtime with string matching). During HPXML equipment spec construction, insert default `sensible_gain_fraction` and `latent_gain_fraction` from OCHRE's defaults per equipment type. Keep a runtime warning + conservative default (e.g., 0.5) as safety net only.

> **Architecture note:** HARES Rust core must use clean, typed, SI-unit config keys only. Any OCHRE key/unit translation happens in the Python adapter layer (`python/ochre_next/compat/`). Do not add dual-key lookups or OCHRE naming conventions to Rust code.

**Severity:** CRITICAL
**Crate:** `hares-equipment`
**File:** `crates/hares-equipment/src/scheduled_load.rs`

---

## Bug

In `scheduled_load.rs` lines 282-294, when no explicit `sensible_gain_fraction`, `frac_sensible`, `convective_gain_fraction`, or `radiative_gain_fraction` is provided, the sensible gain fraction falls through to 0.0:

```rust
// scheduled_load.rs:282-294
self.sensible_gain_fraction = config
    .get_f64(KEY_SENSIBLE_GAIN_FRACTION)
    .or_else(|| config.get_f64("frac_sensible"))
    .or_else(|| {
        let conv = config.get_f64(KEY_CONVECTIVE_GAIN_FRACTION).unwrap_or(0.0);
        let rad = config.get_f64(KEY_RADIATIVE_GAIN_FRACTION).unwrap_or(0.0);
        if conv > 0.0 || rad > 0.0 {
            Some(conv + rad)
        } else {
            None
        }
    })
    .unwrap_or(0.0);
```

Equipment draws power (kilowatts visible in output) but contributes zero thermal gain to the zone. For interior lighting and plug loads, this can underestimate zone heat gains by 50-80%, causing the thermal model to under-predict cooling loads and over-predict heating loads.

## OCHRE Reference

OCHRE `ochre/equipment/scheduled.py` and `Equipment.py` use per-equipment-type default gain fractions loaded from HPXML defaults and internal tables:

- **Interior Lighting:** sensible ~0.70, latent ~0.0
- **Plug Loads (MELs):** sensible ~0.73, latent ~0.02
- **Cooking Range:** sensible ~0.40, latent ~0.30
- **Clothes Dryer:** sensible ~0.15, latent ~0.05
- **Dishwasher:** sensible ~0.60, latent ~0.15
- **Clothes Washer:** sensible ~0.80, latent ~0.0

OCHRE never uses 0.0 for sensible gain fraction on an interior load.

## Fix

Gain fractions are populated during IO/HPXML parsing in `hares-io`, not via equipment-type string matching in Rust equipment code. Equipment receives `sensible_gain_fraction: f64` as one clean typed key.

1. In `hares-io` HPXML equipment spec construction, add a lookup table mapping equipment type enums (not string patterns) to default gain fractions (matching OCHRE/HPXML defaults).
2. During spec construction, insert `sensible_gain_fraction` and `latent_gain_fraction` from this table when HPXML does not provide explicit values.
3. The equipment runtime reads the single `sensible_gain_fraction: f64` field from config. If missing (should not happen after IO fix), log a warning and use a conservative default (0.5).

Default gain fractions to populate in `hares-io`:

| Equipment Type     | sensible | latent |
|--------------------|----------|--------|
| Interior Lighting  | 0.70     | 0.00   |
| Plug Loads (MELs)  | 0.73     | 0.02   |
| Cooking Range      | 0.40     | 0.30   |
| Clothes Dryer      | 0.15     | 0.05   |
| Dishwasher         | 0.60     | 0.15   |
| Clothes Washer     | 0.80     | 0.00   |

In `scheduled_load.rs`, replace the final `.unwrap_or(0.0)` with `.unwrap_or_else(|| { tracing::warn!("sensible_gain_fraction missing for '{}'; using 0.5", self.name); 0.5 })`.

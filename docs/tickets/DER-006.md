## Background/Context

The EV equipment model inherited OCHRE's monolithic design: arrival/departure scheduling, charging strategies, daily driving patterns, TOU awareness, and plug-in policies are all baked into the equipment `step()`. This violates the HARES architecture where equipment is self-contained physics and actors push external control signals.

This ticket strips the EV to a dumb battery-on-wheels. All behavioral intelligence moves to the EV Driver Actor (DER-007). The EV equipment accepts control signals for plug-in state and driving consumption, and does physics: SOC tracking, thermal model, efficiency, degradation, charging curve derating.

**Default state**: `plugged_in = true`. If no actor is attached, the EV is permanently connected and charges via control signals (PowerSetpoint, SOCTarget, etc.) — same as Battery.

**Breaking change**: This removes all behavioral config keys (`driver_archetype`, `daily_drive_miles_*`, `event_day_ratio`, etc.) from the EV equipment. HARES is a greenfield codebase with no backward-compat obligations. Old configs using these keys will have them silently ignored by the equipment (standard `EquipmentConfig` behavior for unrecognized keys).

### `crates/hares-types/src/control_signal.rs` — new control signal variants

- [ ] Add `EvPlugIn { state: EvConnectionState }` variant to `ControlSignal` — actor sets the EV's location/connection state (HomePluggedIn, AwayPluggedIn, Disconnected).

- [ ] Add `EvDrive { kwh: f64 }` variant — actor tells EV to deduct driving energy from SOC. Applied as a single SOC step on departure (not smoothed — the EV draws zero residential power while disconnected, so step vs smooth has no impact on the residential load profile). Invariant: rejected unless `connection_state == Disconnected` (can't drive while plugged in anywhere).

- [ ] Add `EvAwayCharge { power_kw: f64 }` variant — actor tells EV to charge from an external source (workplace L2, DCFC). The EV equipment runs its full battery physics: CC-CV taper from charging curve LUT, thermal derating, degradation tracking, SOC update — but does NOT emit a `PortContribution::Electrical` to the residential meter. The power_kw is the external charger's rated power; the EV's internal CC-CV curve and SOC taper still limit actual intake. Invariant: rejected unless `connection_state == AwayPluggedIn`.

- [ ] Add `EvSetReadyBy { departure_hour: f64, target_soc: f64 }` variant — actor tells the EV's BMS "be at this SOC by this hour". The actor does the trip planning (miles → SOC calculation). The BMS just schedules when to start charging to hit the target on time. This is how real EVs work: the owner sets "ready by 7am at 80%" and the car delays charging to minimize time on the grid.

- [ ] Add `ControlCapabilities` flags: `const EV_PLUG_IN = 1 << 19;`, `const EV_DRIVE = 1 << 20;`, `const EV_AWAY_CHARGE = 1 << 21;`, `const EV_SET_READY_BY = 1 << 22;`

**Simplify `step()`**:
- [ ] Remove calls to `maybe_roll_event_for_day()` and `update_connection()`
- [ ] Three-branch core loop based on `connection_state`:
  ```
  match connection_state:
      HomePluggedIn:
          // Full physics, contributes to residential port
          charge_derate → compute_power → thermal → SOC update → degradation
          ports.accumulate(Electrical { active_power_kw })
          // Telemetry: active_power_kw = actual draw, location = "home"

      AwayPluggedIn:
          // Full battery physics (CC-CV taper, thermal, degradation)
          // but NO residential port contribution
          charge_derate → compute_power(limited by away_charger_power_kw) → thermal → SOC update → degradation
          // NO ports.accumulate — power from external source
          // Telemetry: away_charge_power_kw = actual intake, active_power_kw = 0 (residential), location = "away"

      Disconnected:
          // Thermal drift only, calendar degradation
          thermal_update → heater_if_needed → degradation(calendar_only)
          // Telemetry: active_power_kw = 0, location = "disconnected"
  ```
  Away charging runs the SAME battery physics as home charging (CC-CV from charging_curve_lut, thermal derating, ohmic losses, degradation) — only the port contribution is suppressed. A Tesla at a 250kW DCFC still tapers per its NCA charging curve at high SOC.

**Equipment-level BMS default ("charge to ready")**:

When `HomePluggedIn` and no actor has set a `power_setpoint_kw` or `soc_target`, the EV equipment charges at rated power up to `soc_max` — same as a real car's onboard BMS. This is the existing behavior (line 779-781: `power_setpoint_kw.unwrap_or(derated_rated)`). Keep this intact.

BMS state fields:

- [ ] `ready_soc: f64` — default charge target (default = `soc_max`, configurable via `KEY_READY_SOC`)
- [ ] `ready_by_hour: Option<f64>` — deadline from actor via `EvSetReadyBy` (None = charge immediately)
- [ ] `ready_by_soc: Option<f64>` — target SOC from actor via `EvSetReadyBy` (None = use `ready_soc`)

BMS step behavior — the equipment is a car with an onboard charger, the actor is the driver:

- [ ] When `HomePluggedIn` and `ready_by_hour` is set:
  - BMS computes latest start: `start_hour = ready_by_hour - (soc_deficit × capacity / rated_power / efficiency)`
  - Before start hour: idle (0 power)
  - After start hour: charge at rated power to `ready_by_soc`
  - Actor (driver) sets the deadline; BMS (car) decides when to start
- [ ] When `HomePluggedIn` and no deadline set: charge immediately to `ready_soc`
- [ ] When actor sets explicit `SOCTarget` or `PowerSetpoint`: overrides BMS planning
- [ ] When `AwayPluggedIn`: charge to `ready_soc` at `away_charger_power_kw`, NO port contribution
- [ ] When `Disconnected`: 0 power

The actor (driver proxy) reads EV telemetry (SOC, capacity) to plan:
1. On arrival home: compute tomorrow's trip miles from `ScheduleSource`, convert to required SOC
2. Send `EvSetReadyBy { departure_hour: 7.0, target_soc: 0.75 }`
3. BMS delays charging until necessary, then charges at rated power with CC-CV
4. On departure: actor sends `EvPlugIn { Disconnected }` + `EvDrive { kwh }`

**Simplify `compute_power_kw_with_time()`**:
- [ ] Remove behavioral holds (delay_hold_active, in_tou_block_window, required_ready_power_kw)
- [ ] Keep all internal BMS physics — these are non-negotiable regardless of what the actor requests:
  - CC-CV charging curve from LUT (power fraction tapers with SOC, temp, c-rate, SoH)
  - Thermal derating (linear ramp between `min_charge_temp_c` and `full_power_temp_c`)
  - Degradation-adjusted capacity (`capacity_kwh × (1 - capacity_fade_pct)`)
  - OCV-based voltage model (chemistry-aware per DER-004)
  - Taper limit (prevents SOC overshoot: `(target - soc) × capacity / dt / efficiency`)
  - Power limit enforcement (from DR or actor)
- [ ] Target SOC precedence (highest wins):
  1. `soc_target` (explicit actor override via SOCTarget signal) — highest priority
  2. `ready_by_soc` (from EvSetReadyBy — driver told the car's computer)
  3. `ready_soc` (equipment default — BMS fallback)
  - Code: `target = soc_target.or(ready_by_soc).unwrap_or(ready_soc)`
  - If `soc >= target` → 0 power. Otherwise → charge at `power_setpoint_kw.unwrap_or(derated_rated)` with all physics applied.
- [ ] `PowerSetpoint` also overrides BMS delayed-start: if actor sets explicit power, BMS charges at that power regardless of ready-by scheduling. The actor is taking manual control.
- [ ] Ready-by scheduling logic:
  - Compute `hours_needed = soc_deficit × capacity / (derated_rated × efficiency × CC_CV_MARGIN)` where `CC_CV_MARGIN = 0.85` accounts for CC-CV taper at high SOC (constant-power formula underestimates charge time)
  - `start_hour = ready_by_hour - hours_needed`
  - If `start_hour < 0` (wraps past midnight): charge immediately (deadline too tight)
  - If deadline already passed (current hour > `ready_by_hour` on same day): charge immediately
  - If SOC already >= target: idle (0 power)
  - Otherwise: if current hour >= start_hour → charge; else → idle (BMS delays)
  - `ready_soc` defaults to `soc_max` (initialized from `soc_max` field, not hardcoded)

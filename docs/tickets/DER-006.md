## Background/Context

The EV equipment model inherited OCHRE's monolithic design: arrival/departure scheduling, charging strategies, daily driving patterns, TOU awareness, and plug-in policies are all baked into the equipment `step()`. This violates the HARES architecture where equipment is self-contained physics and actors push external control signals.

This ticket strips the EV to a dumb battery-on-wheels. All behavioral intelligence moves to the EV Driver Actor (DER-007). The EV equipment accepts control signals for plug-in state and driving consumption, and does physics: SOC tracking, thermal model, efficiency, degradation, charging curve derating.

**Default state**: `plugged_in = true`. If no actor is attached, the EV is permanently connected and charges via control signals (PowerSetpoint, SOCTarget, etc.) — same as Battery.

**Breaking change**: This removes all behavioral config keys (`driver_archetype`, `daily_drive_miles_*`, `event_day_ratio`, etc.) from the EV equipment. HARES is a greenfield codebase with no backward-compat obligations. Old configs using these keys will have them silently ignored by the equipment (standard `EquipmentConfig` behavior for unrecognized keys).

## Background/Context

`batch_step_py` calls `Python::attach(|py| ...)` on every Rayon iteration, re-acquiring the GIL per thread. Since CPython's GIL is held by exactly one thread, the parallel map executes serially.

## Work to Do

- [ ] **Do NOT restructure `PyDwelling` internals** — it already holds `Mutex<Dwelling>`, and `step_core()` only uses `self.dwelling.lock()` (GIL-free). Adding `Arc` would create redundant reference counting on top of Python's existing refcount
- [ ] Rewrite `batch_step_py` to: bind all `Py<PyDwelling>` to `Bound<'_, PyDwelling>` while still holding the GIL, extract `&PyDwelling` references, then release GIL via `py.detach()` and run Rayon `par_iter` over the extracted references
- [ ] **Key constraint**: `PyRef<'_, PyDwelling>` is not `Send`. The pattern that works is: collect handles into a `Vec<T>` where `T` is `Send` before entering the parallel section (e.g., raw pointers or shadowed references)
- [ ] Perform all Rust-only computation (`step_core`) in the parallel section without GIL
- [ ] Only re-acquire GIL for Python object conversion (`PyDict`) after the parallel section completes
- [ ] Add benchmark that exercises the Python FFI layer (not just `benches/rl_step.rs` which uses bare `Dwelling`)

**Note**: Actions passed to `batch_step_py` are silently discarded (line 101: `let _ = actions.get(idx)`). This is a separate issue — the Python caller applies controls via `_apply_controls` before calling batch_step. Track separately if needed.

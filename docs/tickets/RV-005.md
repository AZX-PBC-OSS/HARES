## Background/Context

`EnvironmentManager::update()` constructs a fresh `EnvironmentState` every timestep with 5+ Vec allocations that are immediately dropped when `self.latest_env = env` replaces the previous state. At 525,600 steps/year this produces ~7-10M alloc/free cycles, causing memory fragmentation and cache pressure.

Separately, `equipment_telemetry` in `dwelling/mod.rs:1642-1648` clones `desc.name` (String) and `eq.telemetry()` (HashMap) for every equipment piece every step when actors are present — another ~2-5M allocations/year.

This is the single highest-impact allocation source in the hot loop.

**Note:** This ticket subsumes RV-008 (StepResult clone, thermal_update clone, timestamp allocation) to avoid concurrent modifications to `dwelling/mod.rs`. All dwelling step-loop allocation work is consolidated here.

## API Change Risk

Changing `update()` from returning `EnvironmentState` to mutating `&mut EnvironmentState` is a significant internal API change. All call sites within `dwelling/mod.rs` that consume the returned value must be updated. No external callers exist (the method is `pub(crate)`), so this is safe. Verify no code caches a returned `EnvironmentState` by value.

## Progress

**Session 2026-03-27 (T2-6, T2-8, telemetry, zone lookup maps):**

- [x] **(T2-6)** `thermal_update` clone eliminated: `apply_thermal_update_to_zones` is now called before `upsert_domain(thermal_update)` so the value is moved, not cloned. Clone is retained only under `#[cfg(feature = "observe")]`.
- [x] **(T2-8)** `timestamp_buf`: pre-allocated `String` field on the recorder. Formatted in-place via `write!` with `%+` format instead of `to_rfc3339()`. No per-step String allocation.
- [x] **equipment_telemetry**: removed per-step `clear()`. Uses `get_mut()` + `clone_from()` for in-place updates — avoids String key reallocation on steady-state steps.
- [x] `zone_infiltration_columns` and `zone_lwr_columns` converted from `Vec<(ZoneId, usize)>` to `HashMap<ZoneId, usize>` for O(1) lookups in `record_step`.
- [x] One-step telemetry lag documented with a clear comment in source.
- [ ] **(T2-5)** `StepResult` clone is structurally unavoidable: `step()` returns `Result<StepResult>` AND stores it in `simulation_results.steps`. Both consumers need ownership; there is no safe borrow-then-move ordering here. Documented with a comment in source.

Still needed:
- [ ] `EnvironmentManager::update()` signature change (return → mutate in place)
- [ ] Pre-allocated solar irradiance, schedule_values, custom_domains, and zones Vecs on `EnvironmentManager`
- [ ] `InvariantChecker` as a `Dwelling` field (see also RV-019 T7-6)

## Work to Do

- [x] **(From RV-008 T2-6):** Restructure `thermal_update`: read by reference for `apply_thermal_update_to_zones`, then move into `upsert_domain`. No clone needed (except under `observe` feature flag).
- [x] **(From RV-008 T2-8):** Replace per-step `to_rfc3339()` with a pre-allocated `String` buffer on the recorder, formatted in-place via `write!`.
- [x] For `equipment_telemetry` in dwelling: use `get_mut()` + `clone_from()` to overwrite values without reallocating String keys each step.
- [ ] **(From RV-008 T2-5):** `StepResult` clone — structurally unavoidable given dual ownership requirements. Documented in source.
- [ ] Change `EnvironmentManager::update()` signature from `fn update(...) -> EnvironmentState` to `fn update(&mut self, state: &mut EnvironmentState, ...)` — mutate in place
- [ ] For `solar_irradiance`: pre-allocate the Vec as a field on `EnvironmentManager`. Use `.clear()` + `.extend()` each step. Avoid the second allocation when PV roof coverage is applied — mutate entries in place
- [ ] For `schedule_values`: pre-allocate as a field. Use `copy_from_slice` or indexed assignment
- [ ] For `custom_domains`: pre-allocate the two `DomainUpdate` structs and their inner Vecs as fields. Update values in place each step
- [ ] For `zones`: stop cloning. Either share via `Arc<[ZoneState]>` or update in place via indexed assignment
- [ ] Update all call sites of `update()` to pass `&mut self.latest_env` instead of receiving a new struct
- [ ] **Dynamic equipment:** `equipment_telemetry` HashMap must handle equipment added after init. Use `entry()` API to insert new keys on first encounter rather than assuming all keys exist at init

## Tests Added

**hares-core:**

- `environment_update_produces_identical_state` — run a 24-hour simulation (1440 steps). Assert all `EnvironmentState` fields match a reference trace captured before the refactor at every step. This is the correctness regression guard
- `environment_update_solar_irradiance_matches` — compare per-surface irradiance values for 10 representative timesteps (sunrise, noon, sunset, night) against known values. Assert identical within f64 epsilon
- `environment_update_schedule_values_match` — compare schedule column values at day/night transition. Assert identical
- `equipment_telemetry_update_preserves_values` — step a dwelling with 4 equipment pieces and actors. Assert `equipment_telemetry` HashMap contains correct names and values at each step
- `equipment_telemetry_handles_dynamic_equipment` — add equipment after init (if supported), step the simulation. Assert the new equipment's telemetry appears in the HashMap without panic or missing entries
- `step_result_move_preserves_all_fields` — run a 100-step simulation. Assert `simulation_results.steps` contains all 100 entries with correct zone temperatures, electrical values, and timestamps
- `thermal_update_move_produces_identical_zones` — run 24-hour simulation. Assert zone temperatures match pre-refactor values at every step to f64 precision
- `timestamp_formatting_matches_rfc3339` — verify the new buffer-based timestamp matches `to_rfc3339()` for edge cases: midnight, timezone offset, end-of-year

## Background/Context

Two allocation inefficiencies in the hot path:

**1. Telemetry clones (py_telemetry.rs):**
`PyTelemetry::zone()` and `equipment()` methods clone all vectors before converting to Python dicts. The cloned data is immediately consumed by `set_item()` and never used again. Since PyO3 copies the data into Python objects anyway, the Rust-side clone is pure waste.

**2. Step() string allocations (py_dwelling.rs:112-130):**
Every call to `step()` allocates zone temperature key strings via `format!()`:
```rust
format!("Temperature - Zone_{} (C)", zone_id.0)
```
For a 525,600-step simulation, this creates 525,600 × n_zones temporary strings that are immediately consumed. The keys are deterministic and should be pre-computed.

## Work to Do

### Telemetry clone elimination
- [ ] In `PyTelemetry::zone()`: pass references directly to `set_item()` instead of cloning vectors. PyO3's `set_item` accepts `&[T]` for sequence types and `&str` for strings — no need to clone.
- [ ] In `PyTelemetry::equipment()`: same pattern — remove `.clone()` on vectors before `set_item()`
- [ ] If `PyTelemetry` currently stores owned data: verify whether it can store references instead (lifetime may require `Py<T>` or owned data — if owned data is needed, the clones happen at construction time in `PyTelemetry::new()`, not at each `zone()` call)
- [ ] Audit `PyTelemetry::new()` — does it clone from `DwellingTelemetry`? If so, the `zone()`/`equipment()` clones are double-cloning

### Step() string allocation reduction
- [ ] Pre-compute zone key strings once during `PyDwelling` construction or first `step()` call
- [ ] Store as `Vec<String>` on `PyDwelling` struct (or lazily initialize)
- [ ] In `step()`, use `&self.zone_keys[i]` instead of `format!()` per call
- [ ] If zone count can change during simulation (unlikely but check): invalidate cache on zone change

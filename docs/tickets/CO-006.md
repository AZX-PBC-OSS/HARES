## Background/Context

DER and load equipment types need real `core_output()` implementations. These are
the most critical because they have different sign conventions:
- PV/Generator: `ElectricPower::Generation`
- Battery/EV: `ElectricPower::Bidirectional`
- Loads: `ElectricPower::Consumption`

## Work to Do

For each equipment:
- [ ] Add `core_output: CoreOutput` field.
- [ ] Set `core_capabilities` in descriptor.
- [ ] Build local CoreOutput in step() from same state as ports. Assign on success.
- [ ] Override `fn core_output(&self) -> &CoreOutput`.
- [ ] `core_output` is NOT persisted in checkpoints — recomputed on next step().

### Load fuel capability:
ScheduledLoad and EventLoad both emit `PortContribution::Fuel` when
`gas_consumption_w > 0.0` (scheduled_load.rs:417, event_load.rs:390).

**Capability semantics rule:** A capability flag means "this instance is
configured to support this feature," NOT "current magnitude is non-zero."
If a ScheduledLoad is configured with a fuel type other than `FuelType::None`,
set `FUEL` in its `core_capabilities` at construction time. The field
`core_output.flows.fuel_w` MUST then be `Some(FuelPower { ... })` every step
— even when consumption is 0.0 (off/idle). Same rule for `REACTIVE`:
if PV or ScheduledLoad is configured with reactive power support, set
`REACTIVE` and always populate `reactive_power_kvar` (0.0 when idle).

### PV reactive power:
PV writes `reactive_power_kvar`. Positive = inductive/lagging (IEEE 1547).
Test: PV with capacitive setting produces negative Q in core_output.

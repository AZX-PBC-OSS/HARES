# FIX-029: Exterior radiation bypasses rad_frac and uses wrong input index

## Status: Open

## Problem

Three bugs in the exterior surface heat balance path across `thermal_solver.rs` and `dwelling.rs`:

1. **Wrong input index (both solar AND LWR)**: For surfaces with material layers, `ExteriorSurfaceInfo::input_index` is unconditionally set to `zone_sensible_input_indices` (zone air node) in `dwelling.rs:1261-1267`. The physics requires radiation to drive the **outermost RC node's** heat input column — otherwise the thermal gradient through the construction is never driven by external radiation. Both solar and LWR are affected: they both bypass the outer skin and dump heat directly into zone air. OCHRE sets `h_idx` to the outermost node's input column (`Envelope.py:859-867`).

2. **No rad_frac modulation on solar**: `apply_exterior_solar_inputs` injects full `absorptance × area × POA` without `rad_frac` scaling (`thermal_solver.rs:591`). The iterative LWR path scales by `rad_frac` (`thermal_solver.rs:695`). OCHRE applies `rad_frac` to the **combined** (solar + LWR) flux: `h_radiation * _ext_rad_fracs_to_inputs[i]` (`Envelope.py:1154-1156`).

3. **Solar missing from iterative convergence output**: After the iterative surface temperature convergence, only `q_lw * info.rad_frac` is injected back into the RC network (`thermal_solver.rs:695`). The converged `solar_w` term is computed inside the loop but never injected. The correct injection is `(solar_w + q_lw) * rad_frac`.

## Impact

For a typical roof surface (rad_frac ≈ 0.6, absorptance = 0.6, area = 10 m², summer POA = 600 W/m²):
- Solar overcounted by `600 × 0.6 × 10 × (1.0 - 0.6) = 1440 W` continuously
- All radiation bypasses construction thermal mass, eliminating lag/attenuation through roofs and walls
- Drives zone temperatures too high, inflating cooling loads

## Fix

Two files need changes:

### `crates/hares-core/src/dwelling.rs` (lines 1261-1267)
When `layer_info` exists for a boundary, `input_index` must resolve to the outermost RC node's heat input column (a new B_c column with `1/C_node` gain), not `zone_sensible_input_indices`. For surfaces without material layers (`rad_frac == 0`), the current zone air routing is correct.

### `crates/hares-envelope/src/thermal_solver.rs`
- `apply_exterior_longwave_inputs_iterative` (line 695): change `q_lw * info.rad_frac` to `(solar_w + q_lw) * info.rad_frac`
- `apply_exterior_solar_inputs`: skip surfaces with `rad_frac > 0` (they are handled by the iterative path)
- Surfaces with `rad_frac == 0` continue through the existing non-iterative paths unchanged

## Edge Cases
- `rad_frac == 0` surfaces (no material layers): unaffected — solar and LWR both go to zone air unscaled, which is correct
- All existing tests use `rad_frac: 0.0` so this fix will not break them; new tests with `rad_frac > 0` are needed

## Not a Bug
The iterative LWR path uses `t_ext` (outdoor air) for the ground-hemisphere `(1-svf)` component instead of `ground_temp_c`. This matches OCHRE intentionally (`Envelope.py:261`: "ground + air are combined since both use ambient temp"). The non-iterative branch is more physically accurate by using separate `ground_temp_c`, but the difference is minor.

## Files
- `crates/hares-core/src/dwelling.rs`: `ExteriorSurfaceInfo` construction (input_index assignment)
- `crates/hares-envelope/src/thermal_solver.rs`: `apply_exterior_solar_inputs`, `apply_exterior_longwave_inputs_iterative`

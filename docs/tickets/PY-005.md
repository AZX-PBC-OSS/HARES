## Background/Context

Several enum and bitflag types need Python exposure for IDE autocomplete, type safety, and use in other PyO3 APIs (e.g., typed ControlSignal constructors in PY-006, equipment descriptors in PY-008).

**Already implemented in `py_actor.rs` and registered in `lib.rs` — do NOT duplicate:**

- `PyDRLevel` (name: `DRLevel`) — 5 variants: Normal, Moderate, High, Critical, GridEmergency
- `PyPriority` (name: `Priority`) — 4 variants: Schedule, UserOverride, Grid, Safety
- `PyMode` (name: `Mode`) — 4 variants: Off, Heating, Cooling, Standby

**`PyMode` coverage gap:** The full Rust `OperatingMode` has 12 variants. `PyMode` covers only 4. This ticket must extend `PyMode` to all 12 variants and register it as `OperatingMode` in Python (keeping `Mode` as an alias for backward compat). Do not create a separate `PyOperatingMode` type — extend `PyMode` in `py_actor.rs`.

**`PyEndUse` is a newtype, not an enum.** Rust `EndUse` is `EndUse(Cow<'static, str>)` with associated constants. The Python binding must be a `#[pyclass]` with `#[classattr]` for each standard constant — not a `#[pyclass(eq, hash, frozen)]` enum.

**Signal disambiguation:** `PySignal` in `py_actor.rs` is for actor dispatch requests (high-level, target-bearing). `PyControlSignal` in `py_control.rs` is the equipment-level signal type. Both are needed; they serve different layers of the control stack.

**Note:** There are two distinct `SimStatus` enums in the codebase — `hares_core::engine::SimStatus` and `hares_fleet::fleet::SimStatus`. Both have identical variants (Ok, Flagged, Failed) with the same semantics. Expose a single `PySimStatus` that can convert `From<>` both Rust types.
